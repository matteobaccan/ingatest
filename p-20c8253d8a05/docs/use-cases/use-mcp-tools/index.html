Give local models the tools of MCP servers

What you get

Section titled “What you get”

Inga is an MCP host: the tools of the MCP (Model Context Protocol) servers you list — a filesystem, a database, a search engine, a calendar… — are offered to the local models that call tools, in the web UI, inga run and the APIs. Every call is shown to you and runs only once you allow it, or when you put the tool on an allow-list.

The servers are listed in mcp.json, in the format Claude Desktop and LM Studio read, so you can copy theirs. Servers reached by URL (Streamable HTTP, or the older HTTP+SSE) work as they are. Servers that are programs (stdio: "command" in mcp.json) are the one place where Inga starts another program: only when you start Inga with --allow-mcp-commands, and only once you have approved that exact command.

(part 2):

  • servers that want you to sign in (OAuth) sign in with inga mcp login NAME (section 8); a token in headers still works;
  • a server’s resources and prompts are offered to the model too, as the tools SERVER__read_resource and SERVER__get_prompt, approved like the others;
  • sampling (a server asking the model to write during a call) is answered by the chat’s model once you allow it (section 9);
  • a skill can name the MCP tools it uses (section 10);
  • a server whose tools change (list_changed) is listed again on the next use, without reconnecting.

Requirements

Section titled “Requirements”
  • Windows, Linux or macOS; any x86-64 or ARM64 CPU.
  • A chat model whose chat template has tools (the Models tab’s model card says tools): Qwen3, Llama 3.1+, Mistral, gpt-oss…
  • MCP servers: a URL, or a program you install yourself (many are run with npx from Node.js or uvx from Python; Inga installs nothing).

5. Use the tools in the browser

Section titled “5. Use the tools in the browser”

The web UI hides MCP for now (the maintainer’s decision of 2026-11-09: no MCP page, no MCP button in the chat, no approval box there). MCP works from the command line, with mcp.json and inga mcp list, inga mcp tools and inga mcp approve (above), in inga run --mcp-tools (section 6) and in API requests with inga_mcp (section 7).

Without a terminal (a script, -p in a pipe) only the calls of --mcp-auto-approve run. --tool-approval changes runs the tools a server marks read-only without asking ([MCP files:list_directory running, read-only (the server's hint; --tool-approval changes)]), --tool-approval auto asks nothing and runs only the pre-approved calls.

7. Use the tools from an API client

Section titled “7. Use the tools from an API client”

A request asks for the MCP tools with inga_mcp (its approval level: section 8). API clients cannot answer a prompt, so with "inga_mcp": true only the calls of the server’s allow-list run:

The answer’s message lists the calls in inga_mcp_calls (stage done with chars, secs, preview, or refused with the reason). A client that streams can ask like the web UI with "inga_mcp": {"approval": "ask"} and "stream": true: each call not on the allow-list sends an inga_mcp delta {"stage": "approval", "id", ...}, answered with POST /api/inga/mcp/approve {"id": N, "allow": true}. A list of servers ("inga_mcp": ["github"], or "servers": [...] with "approval") offers the tools of those servers only; a scheduled task’s mcp / mcp:SERVER tools send it, and run the calls of --mcp-auto-approve only, since no one is there to answer. The same field works in /v1/messages, /v1/responses and Ollama’s /api/chat; the routes are in docs/api/inga.yaml (/api/inga/mcp*).

8. Approval levels and the “always” kept

Section titled “8. Approval levels and the “always” kept”

A chat says how its tool calls are approved, with one of three levels (the web UI’s approval chip under the message box, "inga_tool_approval" in an API request, --tool-approval for inga run):

Level What runs without asking What asks
ask — “Ask for everything” (the default of inga run) the pre-approved calls (--mcp-auto-approve, an “always” kept), the server’s own readers every other MCP call and every change
changes — “Ask only for changes” (the default of the web UI’s chats) also what only reads: the MCP tools a server marks read-only the MCP tools that may change something, and the changes below
auto — “Only pre-approved tools” the pre-approved calls only nothing: the rest is refused, and the model told why

What counts as reading and as a change:

Tool Reads or changes
web_search, fetch_url reads
list_files, read_file, search_files (the workspace) reads
the document tools (documents_list, documents_search, document_read, documents_grep) reads
recall reads
load_skill, read_skill_file reads
write_file changes (an “always” can be kept per workspace folder)
remember, forget change the memory
run_skill_script changes (a script “always allowed” runs at every level)
an MCP tool with annotations.readOnlyHint: true (and no destructiveHint: true, no openWorldHint: true) reads, if you trust the server’s hints
an MCP tool with openWorldHint: true (it reads the web or other people’s data), even read-only changes: what it brings back may carry instructions written to the model
any other MCP tool, an MCP server’s sampling changes

An MCP server’s annotations are hints it gives about itself (the MCP specification says not to trust them from servers you do not trust). Inga believes them, by default, for a program it starts on your machine (command in mcp.json, which you approved), and not for a server reached by URL: every call of a URL server’s tools asks at changes. To believe a server you trust, or to stop believing a program, write:

inga mcp tools shows each tool’s hint (read_only_hint) and what Inga believes (read_only). Without a level in the request, each tool works by default: MCP calls by inga_mcp, a file write and a script ask, the memory’s changes do not. Scheduled tasks never ask: they run what is pre-approved only, and never write files, not even in a folder allowed “always”.

An always answer is kept on disk, in ~/.cache/inga/tool-approvals.json (only you can read it), per MCP server and tool, and per workspace folder for file writes, across restarts. It never expires: it lasts until you take it back. List them and take them back:

inga mcp revoke github:* takes back every tool of a server. The API lists them with GET /api/inga/tool-approvals and takes one back with POST /api/inga/tool-approvals/revoke {"kind": "mcp_tool", "server": "github", "tool": "create_issue"} (or {"kind": "workspace_write", "folder": "/home/me/notes"}); a running server sees the change at its next call.

9. Sign in to a server (OAuth)

Section titled “9. Sign in to a server (OAuth)”

A server reached by URL that answers “401” wants you to sign in: inga mcp list says so. Inga finds the server’s authorization server, registers itself as a client once (or uses the client you give in mcp.json), and opens the sign-in address in a new tab; once you sign in, the browser comes back to Inga and the server connects. From the terminal:

Inga opens no browser itself: copy the address. The tokens are kept in ~/.cache/inga/mcp-tokens.json (only you can read it), refreshed when they expire, and never shown; Sign out or inga mcp logout notion forgets them. A server that does not register clients needs one you registered on its site:

Every sign-in address must be https (or http on this machine), and Inga signs in only with PKCE.

10. Let a server sample the model

Section titled “10. Let a server sample the model”

Some servers ask the model to write during a call (MCP “sampling”: a summary, a classification…). Inga answers with the chat’s model, after asking you: inga run shows the messages the server sent and asks y / n / a on the terminal. API requests and scheduled tasks refuse it unless you allow it with --mcp-auto-approve SERVER:sampling/createMessage (a rule for the whole server does not allow sampling). At most 4096 tokens; images in the request are not passed to the model.

Options worth knowing

Section titled “Options worth knowing”
Option Effect
--mcp FILE The servers of FILE instead of ~/.cache/inga/mcp.json (run, serve, mcp; implies --mcp-tools for run)
--mcp-tools inga run: offer the MCP tools to the model
--tool-approval L inga run: ask (default), changes or auto (section 8)
--allow-mcp-commands Let approved programs (stdio servers) start; off by default
--mcp-auto-approve S[:T] Run the calls of server S (or its tool T) without asking; repeatable or comma-separated; * for every server; S:resources/read, S:prompts/get for its resources and prompts, S:sampling/createMessage to let it sample the model
--mcp-timeout S The time limit of a call (60 s; a server’s "timeout" wins); a call that takes longer is cancelled and reported to the model
--no-mcp inga serve: no MCP servers

Results longer than 16,000 characters are cut (the model is told how much); images in results are described, not shown to the model. A program gets only the variables it needs to start (PATH, HOME, the locale, the temporary folder…) plus its own "env": Inga’s API key and tokens are not passed to it.

Troubleshooting

Section titled “Troubleshooting”
  • “it starts a program …: –allow-mcp-commands”: start Inga with --allow-mcp-commands; “its command is not approved yet”: approve it on the MCP page or with inga mcp approve NAME.
  • “cannot start npx”: the program is not on the PATH Inga passes, or on Windows needs its extension (npx.cmd).
  • “no MCP servers are configured” (400): write mcp.json and restart the server.
  • “the approval level “ask” needs “stream”: true” (or “changes”): prompts come in the stream; without streaming use "inga_mcp": true and --mcp-auto-approve.
  • A tool you allowed “always” still asks, or one runs you no longer want: inga mcp always lists what is kept; inga mcp revoke SERVER:TOOL takes one back.
  • The model never calls a tool: its chat template has no tools, or the tool’s description does not match the question; inga mcp tools shows what the model sees.
  • A server’s tools changed: Inga lists them again on the next use when the server says so; otherwise run inga mcp test again.
  • “wants you to sign in”: run inga mcp login NAME; “does not register clients”: give "oauth": {"clientId": ...} in mcp.json.
  • “lets MCP servers sample only when this server allows it”: the request could not ask you (an API client, a scheduled task): add --mcp-auto-approve SERVER:sampling/createMessage.
