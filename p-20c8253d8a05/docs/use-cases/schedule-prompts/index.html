Run prompts at set times

What you get

Section titled “What you get”

inga serve runs prompts by itself, with no one at the keyboard: “every weekday at 06:00 UTC, search the web for news on X and summarise it”, “every Monday, list what I asked you to remember”, “on 1 December at 09:00, remind me of …”. Each task has a time (in UTC or its own time zone), a prompt, a model and the tools it may use (web search, the memory, skills, the MCP host’s tools); each run is kept on the server, shown in the web UI’s Schedules page and opened there as a chat, and can also be sent to a webhook (Slack, Discord, n8n, Home Assistant …) or written as a Markdown file.

A task only runs a model and the tools you allow: no shell commands, no files read.

What was checked, and how: the cron parser and the next-run computation against a table of expressions (month ends, leap years, steps, ranges, names), the scheduler on a clock the tests move (runs due, missed runs after a restart, a run skipped while the previous one is still running), and a whole server with a synthetic model: a task due two seconds later runs once by itself, its webhook (a local receiver) gets the result, its Markdown file is written, Run now and a failing model are recorded. Real models, real Slack / Discord webhooks and long-running servers are still to be tried (docs/todo/real-world-checks.md).

Requirements

Section titled “Requirements”
  • A model that inga serve runs: try it by hand first (see serve-openai-and-anthropic-apis.md).
  • The home, --home DIR (default ~/.cache/inga): tasks and results are kept there.
  • The server must be running at the task’s time: to keep it on, run it as a service (run-inga-as-a-service.md).
  • For web search, a model that calls tools (Qwen3, Llama 3.1+, gpt-oss, …) and the network (not --offline).

Times: UTC, or the task’s time zone

Section titled “Times: UTC, or the task’s time zone”

A task’s when is a five-field cron expression, read in UTC unless the task names a time zone (tz, below):

* is every value, 1,15 a list, 1-5 a range, */15 or 0-30/10 a step; @hourly, @daily, @weekly, @monthly and @yearly are shortcuts. When both the day of the month and the day of the week are given (neither is *), a day that matches either one runs, as in cron. A single run is once 2026-12-01T09:00 (in the task’s time zone; with a trailing Z, in UTC).

An expression that never runs (0 0 31 2 *) is refused, saying why. The web UI lists the next five runs as the server computes them, in the task’s zone with its abbreviation at each run (CEST, then CET after the clock changes; UTC and your browser’s time in the tooltip); POST /api/inga/schedules/preview {"when": "...", "tz": "..."} gives them too (next_runs_utc, next_runs_local, next_runs_abbr).

Time zones: tz is an IANA name (Europe/Rome, America/New_York, Asia/Tokyo …: GET /api/inga/timezones lists the 97 Inga bundles, with today’s rule of each), a fixed offset (UTC+05:30) or a POSIX TZ string (CET-1CEST,M3.5.0,M10.5.0/3). 0 6 * * 1-5 with tz: Europe/Rome runs at 06:00 in Rome, winter and summer (05:00 or 04:00 UTC). When summer time starts, a time the clock skips (02:30) runs an hour later on the clock; when it ends, a time that happens twice runs once, the first time. The table holds each zone’s current rule, so a country that changes its rules needs a newer Inga. A zone the table lacks (Pacific/Chatham, America/Nuuk …) is read from the system’s zoneinfo when there is one ($TZDIR, /usr/share/zoneinfo: Linux, macOS, the BSDs; not Windows): only the rule at the end of its file is used, as for the bundled ones.

From the web UI

Section titled “From the web UI”
  1. Start the server: inga serve hf://unsloth/Qwen3-4B-GGUF.
  2. Open http://127.0.0.1:8080, then Schedules → New task.
  3. Fill in the name and When: a menu of the usual forms — every N minutes, every hour at a minute, every day, weekdays or chosen days of the week at a time, a day of the month, once at a date and time — writes the Cron expression (advanced) under it; typing a cron there puts the menu on its form (0 9 * * mon-fri is weekdays at 09:00, @weekly Sundays at 00:00), or on Advanced (cron) for one the menu has not (0 */2 * * *), keeping the text as written. Pick the Time zone (your browser’s for a new task): the next five runs appear under them, or what is wrong, in words (“Choose at least one day of the week”, “That time has already passed”, the server’s reason for a cron it cannot read). Then the prompt, the model (empty: the server’s default model), the tools, what to do with a run missed while the server was off, the webhooks (one URL per line) and whether to write Markdown files; every field says what it does in a line under it. Save.
  4. Run now tries it at once. Its result appears under Results when it ends, with a dot while unread; Continue in chat opens it as a new chat (the prompt, the answer, its sources) to go on with the conversation.

From the terminal

Section titled “From the terminal”

inga schedule talks to a running server (--url, default http://127.0.0.1:8080, or client.url; --api-key or client.api_key if it has a key):

list prints each task’s state (waiting, queued, running, disabled, done), when, next run and last result; results the newest records (* marks the unread ones, --limit N); show one record whole: how and when it ran, the model, the answer, its sources and what each delivery did. --json prints the server’s JSON.

From the API

Section titled “From the API”

The routes are in docs/api/inga.yaml (tag schedules); with --api-keys, they belong to the admin group.

GET /api/inga/schedules lists the tasks with their next runs, PUT and DELETE /api/inga/schedules/{id} change and delete one, POST /api/inga/schedules/{id}/run runs it now, GET /api/inga/results[?schedule=ID] lists the records, GET /api/inga/results/{id} gives one whole, POST /api/inga/results/{id}/read marks it read.

How a run goes

Section titled “How a run goes”
  • The server looks at the clock every second. A run due joins a queue; the queue runs one task at a time, after the chats being answered (a run waits for them up to five minutes), as a chat request would: the task’s model (loaded if the server can load others, then unloaded by --idle-unload as usual), its system message and prompt, its sampling, the tools it allows run by the server, within max_tokens and timeout_minutes (10 by default; the run is stopped there and the record says so).
  • Missed runs: a run due while the server was off (or asleep for more than two minutes) follows the task’s missed: run_once runs it once when the server starts, however many were missed; skip records it as skipped. The record says how many were missed and since when. Changing a task’s time, or turning it back on, starts from now.
  • A run due while the task’s previous run is still queued or running is skipped, and the record says so.
  • A tool the server has turned off (web search with --offline or --no-web-search, the memory with --no-memory) makes the run fail with that reason, rather than answer without it. A model the server does not serve and cannot load fails the run too.
  • Skills (skills: every skill installed and on; skill:NAME: one; --skills, --skill NAME): the model may load them as in a chat (use-skills.md). No one is there to approve a skill’s script: a run only runs the scripts you allowed with Always allow this script in a chat.
  • MCP tools (mcp, mcp:SERVER; --mcp, --mcp-server NAME): the tools of the server’s MCP host (use-mcp-tools.md) that may run without an approval: those of inga serve --mcp-auto-approve SERVER[:TOOL], and those a person answered Always allow in a chat since the server started. Their resources and prompts too, with SERVER:resources/read / SERVER:prompts/get; a server that asks the model to write (sampling) during a run is refused unless SERVER:sampling/createMessage is in the list. A skill that names MCP tools (allowed-tools) offers those that may run unattended once loaded. A server that wants a sign-in must be signed in first (inga mcp login).
  • Collections of documents (documents:NAME, one per collection; --docs a,b; or #name in the prompt, #"name with spaces"): the run answers from them, as a chat that names them in inga_documents (chat-with-documents.md). A bare documents is refused: naming a collection is the permission. A collection that is gone fails the run with “no collection NAME”. documents_mode is tool by default: the model gets the document tools (documents_list, documents_search, document_read, documents_grep) over the task’s collections and no other, and searches, reads and greps as it needs (chat-with-documents.md); each call is a line on the terminal. A model whose chat template takes no tools gets the closest excerpts in the prompt instead, and the record’s warning says so ("documents_mode": "context" asks for the excerpts directly). The record keeps the documents report, and the files the tools read in its sources, each cited collection › file.
  • The terminal shows each run: inga: schedule news-on-x: running …, answered in 12.3 s (412 tokens), each webhook’s HTTP status.

Where results go

Section titled “Where results go”
  • The server (always): one JSON record per run in ~/.cache/inga/results/, at most 50 per task and 1000 in all (the oldest go first): the task, why it ran (schedule, missed, manual), when it was due, started and ended, the model, the prompt, the answer with its reasoning and sources, what the memory tools did, the tokens, the error if any, and each delivery’s outcome. Listed and deleted with inga data list results and the Storage page; deleting a task keeps its records.
  • Webhooks: a POST of JSON to each URL (10 seconds at most, no redirects): {"event": "inga.schedule.result", "text": "*Name*\n\nanswer", "content": ..., "schedule": {"id", "name"}, "result": {...}}. text is what Slack’s incoming webhooks show, content (2000 characters) what Discord’s do; the whole record is under result for n8n or Home Assistant. A failed run is sent too, with its error. Webhooks are only called by the server, only to the URLs you gave, never with --offline. A webhook that fails (no answer, HTTP 408, 429 or 5xx) is tried again after 5 and 30 seconds; the record says how many attempts it took.
  • Markdown files: one file per answered run, named by the run’s id (20261012T060000_news-on-x.md), in the folder you gave (absolute, or starting with ~; created if missing) or, with an empty folder, ~/.cache/inga/results/files. A file is never overwritten.

Good to know

Section titled “Good to know”
  • Tasks run only while inga serve runs; time zones follow the bundled table’s current rules.
  • At most 100 tasks, five deliveries each; prompts up to 32 KiB.
  • The tools are web search, the memory, skills and the MCP host’s tools.
  • In an Inga mesh, tasks run on the server where they were created.
