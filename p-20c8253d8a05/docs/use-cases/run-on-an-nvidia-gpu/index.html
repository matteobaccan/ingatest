Run a model on a GPU: NVIDIA, AMD, Intel or Apple

What you get

Section titled “What you get”

Some or all of a model’s layers run on your graphics card, the rest on the CPU, with the same answers as on the CPU alone and faster generation: on a 4 GB Quadro P1000, Llama-3.2-1B writes about 40 tokens per second instead of 14. Only the driver is needed: no CUDA Toolkit, no extra DLL. Steps 1–7 use an NVIDIA card through CUDA; other GPUs are in Vulkan (AMD, Intel, NVIDIA), Metal (Apple Silicon) and HIP (AMD, experimental); several GPUs of one PC in step 12.

Requirements

Section titled “Requirements”
  • An NVIDIA GPU of the Pascal generation or newer (compute capability 6.1: GeForce GTX 10xx, Quadro Pxxxx and later) and its driver, release 550 or newer. Windows or Linux.
  • A model whose layers the GPU runs today: Llama, Mistral, Qwen2, Qwen3, Phi-3/4, Gemma 1 to 3, gpt-oss, the mixtures of experts (attention, shared and routed experts: Qwen2 / Qwen3 MoE, OLMoE, Mixtral, GLM-4.5, Ling), the hybrid Qwen3.5 / 3.6 and Qwen3-Next, Mamba-2 and Nemotron-H / Nemotron 3 (section 5), with F32, F16, Q8_0, Q4_0, Q4_1, Q5_0, Q5_1, Q2_K, Q3_K, Q4_K, Q5_K, Q6_K, IQ4_NL or IQ4_XS weights (every Q2_K … Q8_0 file and IQ4_XS). Gemma 4 (12B, 31B, 26B-A4B) runs on Vulkan and Metal, and on CUDA and HIP: its global layers have heads of 512 values, which CUDA’s and HIP’s attention takes (two values of a head per thread; checked against the CPU on the host, pending a check on a real NVIDIA card). Other models (Gemma 3n, Gemma 4 E2B / E4B, DeepSeek, Kimi, LFM2, …) run on the CPU, with a note saying why (supported-models.md lists them).
  • Enough free GPU memory for the layers (see step 4); the rest stays on the CPU.

1. Get Inga

Section titled “1. Get Inga”

Download the archive for your system from the Releases page and put inga on your PATH (details); inga --version checks it.

2. Check that Inga sees the GPU

Section titled “2. Check that Inga sees the GPU”

“free” counts what other programs (the desktop, a browser) already use. Without a driver the command says CUDA: no NVIDIA GPU: ... and Inga runs on the CPU. The last line says which GPU --device auto (the default) uses, and which one it tries next if the first cannot run a model.

The Vulkan lines list every GPU the Vulkan loader sees, of any vendor (AMD, Intel, NVIDIA; software ones such as Mesa’s lavapipe are marked software). An NVIDIA GPU appears under both APIs: CUDA is the faster and more complete one, and --device auto uses it; step 8 runs layers on the Vulkan ones.

3. Run a model: the GPU is used by default

Section titled “3. Run a model: the GPU is used by default”

With no option Inga puts on the best usable GPU as many layers as its free memory holds and runs the rest on the CPU (serve, bench, perplexity and info too). When no GPU is used, a line says why, for each device it looked at:

The reasons are: no driver or no Vulkan loader, an old GPU (not usable), too little free memory for even one layer, a weight type or an architecture the GPU’s kernels do not run (the next GPU is tried, then the CPU), a software device, or your choice (--device cpu, --gpu-layers 0). The note: runs on line repeats them (GPU: not used (...)). When a GPU runs layers, that line starts with it and its share of the layers, then the CPU with its own (+ CPU (AVX2, 8 threads: layers 0-3)).

4. When the model does not fit

Section titled “4. When the model does not fit”

--gpu-layers N puts the last N layers on the GPU. With --gpu-layers all Inga puts as many as fit in the free memory and says so:

On Windows the driver would otherwise move what does not fit to system memory, much slower than leaving those layers on the CPU. Closing programs that use the GPU (a browser with hardware acceleration) frees memory for more layers.

5. See where each part runs, and what would help

Section titled “5. See where each part runs, and what would help”

When a model loads, Inga shows where every part of it runs and how much memory it takes, then tips when something would make it faster:

The last two lines are what the GPU holds beside the parts: the activations of the prompt chunks, and the memory left free for the driver and other programs (256 MiB and 5 % of the card, 10 % on Windows; gpu.keep_free changes it).

For a mixture of experts the GPU takes the output layer first (one product of the whole vocabulary per token, the largest of a decode step), then the attention of as many layers as fit, the last ones first, then, when every attention block is there, the shared experts beside them (shared experts of layers ...), then the routed experts of as many layers as the memory left holds, whole layers from the last one back (routed experts of layers 20-39, as llama.cpp’s --n-cpu-moe keeps the first ones on the CPU). The others and the routers stay on the CPU, in RAM or, when the RAM is short, read from the disk: the GPU first, then the RAM, then the disk. The router picks each token’s experts on the CPU; the GPU runs them and sums their outputs, and only the sum comes back.

A hybrid model (Qwen3.5, Qwen3.6, Qwen3-Next: three DeltaNet layers for each full-attention layer) puts its output layer, then the mixing blocks of its layers (the full-attention layers with their KV cache, the DeltaNet layers with their recurrent states), then their shared experts on the GPU, as far as they fit; only the routed experts stay on the CPU:

A hybrid model with dense feed-forward networks (Qwen3.5 and Qwen3.8-27B: DeltaNet and full attention) that does not fit the card goes by whole layers: under --device auto the planner tries every count of last layers whose attention, cache and network go to the GPU, and keeps the one whose decode step it estimates fastest (the CPU’s and the GPU’s reads, a round trip for each GPU layer). The first layers run whole on the CPU, the last ones whole on the GPU. Qwen3.8-27B Q4_0 on a 16 GB RX 9060 XT with --ctx 65536 (from the hardware profiles):

A model that fits, --gpu-layers N and --device NAME place it as any other model.

A prompt’s DeltaNet layers run the chunked delta rule on the GPU (on CUDA, Vulkan and HIP): the tokens go by chunks of 32, as on the CPU, and the state is read once per chunk instead of twice per token. Generation keeps the token-by-token rule. Layers that run whole on the GPU one after the other (the last 48 layers above, or every layer of a Nemotron-H model on the card) go in one call: the hidden state stays on the card between them instead of coming back to the CPU after each layer. Nothing to set: the gpu: line is the same, and so are the answers but for the order of the float sums. On a software device (lavapipe, three runs on a busy machine) a 512-token prompt of a synthetic Qwen3.5-style model went from 28-37 to 36-54 tokens per second; the speed on real cards is still to be measured with inga bench -p 512 (see measure speed).

Gemma 4 26B-A4B places as the other mixtures: the attention of its layers, then its dense networks (as the shared experts), then the routed experts of the last layers while they fit; --experts-on and --cpu-moe apply. The router, the norms around the experts, the per-layer embedding and the layer’s output scale stay on the CPU. Checked against the CPU on lavapipe (Vulkan) only; the Metal code is compile-checked; on CUDA and HIP (heads of 512 above) pending a check on a real NVIDIA card.

Mamba-2 and Nemotron-H models (Nemotron-H, Nemotron Nano 2, Nemotron 3 Nano and Super) do the same with their three kinds of layers: the Mamba2 layers (input projection, causal convolution, selective scan, gated grouped norm, output projection) with their recurrent states and checkpoints, the attention layers with their KV cache, then the squared-ReLU feed-forward networks (Nemotron-H) or the shared experts (Nemotron 3), on CUDA and on Vulkan; the routers, the experts’ latent projections and the routed experts stay on the CPU. For Nemotron 3 Super (layer lists abridged as Inga prints them):

Nemotron 3’s routed experts stay on the CPU whatever the card’s memory: Inga does not run its squared-ReLU routed experts on the GPU. For the other mixtures (Qwen3-Next and Qwen3.5’s, say), on a card with more memory (a 16 GB card through Vulkan), the routed experts of the last layers go there too; how many depends on the free memory and the file (the layer numbers below are an example):

  • --experts-on auto (the default) does that; --experts-on cpu keeps every routed expert on the CPU, --experts-on gpu asks for all of them and fails when they do not fit, saying how many do.
  • --cpu-moe N keeps the first N layers’ routed experts on the CPU (llama.cpp’s --n-cpu-moe N), to leave GPU memory to a longer context or another program.
  • The experts’ weight types are those of the GPU’s products (CUDA: F32, F16, Q8_0, Q4_0, Q4_1, Q5_0, Q5_1, Q5_K, Q2_K, Q3_K, Q4_K, Q6_K, IQ4_NL, IQ4_XS; Vulkan the same); a layer whose experts are of another type keeps them on the CPU and the tip says why. Their activation: SwiGLU, or gpt-oss’s clamped SwiGLU with its biases.

“SSD (read while running)” marks parts read from the disk while the model runs (a model larger than the RAM): more RAM helps most there. inga info <model> --gpu-layers all shows the same before loading anything (--json: under placement), and the web UI’s GPU badge says what runs on the GPU.

6. Choose the device

Section titled “6. Choose the device”
  • --device auto (the default): the best GPU that can run the model (an NVIDIA GPU through CUDA first, the one with the most free memory; then Metal on a Mac; then a Vulkan GPU that is not software, discrete before integrated; then an AMD GPU through HIP), with as many layers as fit (or the last N of --gpu-layers N); otherwise the CPU, with the reason on standard error. A GPU that cannot run the model (a weight type its kernels lack) is passed over for the next one, and the line gpu: passed over: ... says so.
  • --device cuda (or cuda:N for GPU N): that GPU or an error (every layer unless --gpu-layers says otherwise); use it in scripts that must not fall back silently.
  • --device vulkan (or vulkan:N, the number inga devices shows): a Vulkan device, see step 8.
  • --device metal (or metal:N): a Mac’s GPU, see step 10; --device auto picks it on an Apple Silicon Mac.
  • --device hip (or hip:N): an AMD GPU through ROCm’s runtime, see step 11.
  • --device cuda:0,vulkan:1: several GPUs, a dense model’s layers split between them, see step 12.
  • --device cpu or --gpu-layers 0: the CPU only.
  • device = "cpu" in [gpu] of inga.toml (or cuda:0, vulkan:1, …; --set gpu.device=cpu for one run) does what --device does, for every command; --device wins over it. Handy to try another backend when one misbehaves.
  • In the web UI, the Device selector beside the chat’s model and its GPU layers field choose per model (see chat-in-the-browser.md).
  • debug.cuda_graphs=false: launch every kernel of a generated token one by one instead of replaying the recorded CUDA graph (same output, a little slower; for comparisons).
  • llama.cpp’s kernels: on a GPU of compute capability 8.0 or newer (Ampere: A100, RTX 30xx and later), generation goes through llama.cpp’s matrix-vector products (debug.cuda_mmvq), a prompt’s attention through its flash attention (debug.cuda_fattn), a decode step’s RMS norms and RoPE through its small kernels (debug.cuda_ggml_small), LFM2’s short convolutions run on the GPU (debug.cuda_short_conv) and several sessions decoding together share one attention launch per operation (debug.cuda_batch_attention). Below 8.0 (Pascal, Turing) and on HIP they are off: unmeasured there. A value you set wins either way: --set debug.cuda_fattn=false goes back to Inga’s own kernel, =true tries it on an older card. debug.cuda_ggml_new_types and debug.cuda_moe_router stay off. The speed on an A100, off against on, is in performance (for example Qwen3-8B Q4_K_M, pp512 1869.3 → 4111.0 tokens/s with debug.cuda_fattn).
  • A mixture of experts whole on the GPU (debug.cuda_moe_ids): on a GPU of compute capability 8.0 or newer each MoE layer of Qwen3-MoE, OLMoE, Mixtral, Qwen2-MoE and Qwen3.5-MoE stays on the GPU, the experts’ products reading the router’s choices there (llama.cpp’s MUL_MAT_ID) instead of going back to the CPU once a layer: Qwen3-30B-A3B Q4_K_M generates at 147.5 tokens/s instead of 44.6 on an A100 (see performance). Against llama.cpp b11489 on the same A100 (Inga ee60ddef, the code of main 51cbffa, 3 repetitions, every layer on the GPU) it generates at 0.90 of llama.cpp’s speed (157.7 ± 0.0 against 175.4 ± 4.1 tokens/s) and reads a 2048-token prompt 1.62 times as fast (6356.7 ± 63.4 against 3930.1 ± 87.9). Below 8.0 and on HIP it is off, unmeasured there; --set debug.cuda_moe_ids=false goes back to the old path, =true tries it on an older card. The log says which layers took it and why the others did not.

8. AMD, Intel and other GPUs: Vulkan

Section titled “8. AMD, Intel and other GPUs: Vulkan”

AMD Radeon, Intel Arc and integrated GPUs, NVIDIA cards and other Vulkan 1.1 devices run layers through Vulkan, with only the graphics driver installed (it brings the Vulkan loader, vulkan-1.dll or libvulkan.so.1):

  • --device vulkan picks a discrete GPU, then an integrated one, and a software one (Mesa’s lavapipe, SwiftShader: Vulkan emulated on the CPU, slower than Inga’s own CPU code) only when there is nothing else; --device vulkan:N picks device N of inga devices. Software devices are marked (software) wherever Inga says where the model runs; --device auto never picks them.
  • Integrated GPUs (an APU’s, an Intel iGPU’s): their memory is their own heap (the BIOS carve-out, often 512 MiB) plus their shared one (GTT on Linux, “shared GPU memory” on Windows), at most what the driver gives a process of it. inga devices shows both (6.83 GiB (512.0 MiB dedicated + 6.33 GiB shared)), and the layers go to the shared heap once the carve-out is full. That memory is the RAM: the GPU takes at most the RAM available less what the CPU keeps (the token embeddings, the program), and the gpu: line at load says how much it took (... (2707 MiB of its shared memory, taken from the RAM)). igpu_pool = false in [gpu] of inga.toml (--set gpu.igpu_pool=false) sizes it by its own heap alone.
  • Weights: F32, F16, Q8_0, Q4_0, Q4_1, Q5_0, Q5_1, IQ4_NL, Q2_K, Q3_K, Q4_K, Q5_K, Q6_K and IQ4_XS (the Q4_0, Q2_K, Q3_K_*, Q4_K_*, Q5_K_*, Q6_K, Q8_0, IQ4_NL and IQ4_XS files; the K-quants and IQ4_XS need widths that are multiples of 256, such as Llama-3.2’s); a model with other types (the smaller i-quants, BF16) stays on the CPU under --device auto, and is an error under --device vulkan.
  • The matrix products use subgroups and, where the GPU has it fast, the 8-bit integer dot product; debug.vk_subgroups=false and debug.vk_int_dot=false turn them off (to compare, or to work around a driver bug), debug.vk_int_dot=true uses the dot product wherever the driver offers it.
  • Same models as CUDA (Llama, Mistral, Qwen 2 / 3, Phi, Gemma 1–3, the attention of MoE models and the routed experts of as many of their layers as fit, Qwen3.5 / 3.6 / Qwen3-Next’s attention and DeltaNet layers, Mamba-2 and Nemotron-H / Nemotron 3’s Mamba2, attention and feed-forward layers), heads up to 256 values, Mamba2 states up to the workgroup size (256 on most GPUs; Nemotron’s are 128).
  • Buffers share blocks of 256 MiB of device memory (one allocation of its own from 16 MiB), so a mixture of experts’ routed experts (three buffers per expert, 768 for a layer of 256 experts) stay far below a driver’s 4096 allocations (maxMemoryAllocationCount, as AMD’s on Windows); before, each buffer took one and such a driver refused one with ERROR_OUT_OF_DEVICE_MEMORY while its memory was a third used. inga devices prints each Vulkan device’s heaps with the driver’s budget and usage (VK_EXT_memory_budget) and both limits (memory: line, and heaps, max_memory_allocation_count, max_memory_allocation_size in --json); a failed allocation, and the fallback that keeps less on the GPU after it, say how many allocations and bytes Inga held with the same numbers.
  • Prompts go through tiled products, in chunks sized by the GPU memory left (--prefill-chunk). On a GPU with cooperative matrices (VK_KHR_cooperative_matrix: AMD RDNA3 and RDNA4, NVIDIA from Turing), the products of more than 8 tokens run on llama.cpp’s matrix-matrix shader instead, in f16 with the sums in f32, for Q4_0, Q4_1, Q5_0, Q5_1, Q8_0, Q2_K, Q3_K, Q4_K, Q5_K and Q6_K weights (F16 weights keep Inga’s shaders, which read their activations in f32). inga devices shows the matrices (coopmat 16x16x16 f16), and the load log says which path the prompt takes and why (prompts' products through llama.cpp's matrix-matrix shader on cooperative matrices or through Inga's own shaders: no cooperative matrices). Intel GPUs keep Inga’s shaders for now. inga bench --ab debug.vk_coopmat=false compares both on one loaded model, the logits within a rounding bound rather than byte for byte: Inga’s own shaders round the activations to 8 bits and are the less precise side (issue #1038). Not measured on a GPU yet: only the CPU-emulated Vulkan ran the launch, without the matrices themselves.
  • A memory barrier goes only between commands that depend on each other: before a dispatch or copy that reads or writes a buffer an earlier one wrote since the last barrier, or writes one it read. Which buffers a shader writes comes from its SPIR-V (its bindings without readonly). Independent products, such as an F16 layer’s Q, K and V, no longer wait for each other; the results are the same bits. --vk-barriers all (run, serve, bench; debug.vk_barriers = "all" in inga.toml) puts a barrier after every command as before, for a driver that misbehaves; inga bench --ab debug.vk_barriers=all compares the two.
  • Each norm’s output is quantized to 8 bits once for every product that reads it: Q, K and V, gate and up, a shared expert’s products and the routed experts’ gate and up read one quantized copy, so the quantized products of one input no longer wait for each other either, and a decode step runs fewer dispatches. The results are the same bits.
  • Several sessions decoding together (inga serve --parallel N, inga bench --users N): a batched decode step’s RoPE, KV store and attention run for all its sessions in one dispatch each, on devices that bind 19 buffers at once (the desktop ones); debug.vk_batch_attention = false goes back to each session’s rows in turn. The KV caches are pages of 16 positions from one pool per layer, taken as the sessions write (inga serve --kv-pages); debug.vk_paged_kv = false goes back to each session reserving its context. The results are the same bits either way.

9. Check each device against the CPU

Section titled “9. Check each device against the CPU”

When answers look wrong, or to see which backend is fastest on your machine:

Each device runs the same tokens as the CPU; OK means the same most likely token at every step and logits within 5 % of the largest one, DIFFERS or FAILED (with the error) that this backend has a problem: use another one (--device cpu, cuda:N, vulkan:N, metal:N, hip:N) and please report it. --model FILE tests your model instead (as many of its layers as fit), --json writes the results as JSON. The command fails (exit code

  1. when a device differs or fails.

10. Apple Silicon Macs: Metal

Section titled “10. Apple Silicon Macs: Metal”

On a Mac with Apple Silicon (M1 or newer, macOS 14 or newer) the GPU runs every layer of the model and the output layer through Metal, which is part of macOS: nothing to install.

  • --device auto uses it (a Mac has no NVIDIA GPU, which would come first); --device metal (or metal:0) asks for it, or fails with the reason.
  • The GPU shares the Mac’s memory: the weights are read from the memory-mapped model file without a copy, so the model takes its file size once. The memory Inga plans with is the GPU’s recommended working set (inga devices: about two thirds to three quarters of the RAM).
  • The kernels are compiled from their source when the model loads (well under a second; no Xcode needed); the gpu: Metal 0 ... line says how long it took, and how many weights were wrapped in place or copied (weights converted at load, such as --quantize, are copied once).
  • Weights: every GGUF block type, read as stored in the file and decoded by the kernels (no conversion at load, no copy): F32, F16, BF16, Q8_0, Q4_0, Q4_1, Q5_0, Q5_1, Q1_0, Q2_0, Q2_K to Q6_K, the i-quants (IQ1_S, IQ1_M, IQ2_XXS, IQ2_XS, IQ2_S, IQ3_XXS, IQ3_S, IQ4_NL, IQ4_XS), MXFP4 (gpt-oss) and NVFP4; so every Q*_K_M, IQ* or Q4_0 file runs on the GPU.
  • Same models as Vulkan (dense models, the attention and routed experts of mixtures of experts, Qwen3.5 / 3.6 / Qwen3-Next’s DeltaNet layers, Mamba-2 and Nemotron-H), heads up to 1024 values.
  • Checked for correctness only, on GitHub’s macOS runners (a virtual Apple GPU): the logits and the greedy text of the CPU on synthetic models of every architecture and weight type above. The speed is unmeasured: the kernels use only the baseline Metal features, and prompts go through the decoding kernels eight tokens at a time; the simdgroup_matrix prefill and attention tiles and the comparison with llama.cpp’s Metal backend need a real Mac (phase M3–M4 of the Metal backend).
  • An Intel Mac’s AMD GPU is listed as not usable: the Metal backend is for Apple Silicon (unified memory).

Experimental: faster prompts on M1 and later. Kernels on simdgroup_matrix for prompts (products in 8 x 8 tiles, flash attention) and SIMD-group sums for generation are in the executable but off, because they are unverified on a real Apple Silicon GPU. Turn them on with inga --set debug.metal_simdgroup=true run ...; the gpu: Metal ... line says whether they are used and why not. If you try them, the maintainer would like to hear how it went (the README’s call for Mac testers).

11. AMD GPUs through HIP (ROCm), experimental

Section titled “11. AMD GPUs through HIP (ROCm), experimental”

Built and checked without an AMD GPU: unverified on an AMD card, so Vulkan (step 8) stays the way --device auto uses one.

AMD Radeon RX 6000 / 7000 / 9000 cards, the Radeon 680M / 780M / 890M and Strix Halo APUs, Radeon VII and the Instinct MI50 / MI100 / MI200 / MI300 run layers through AMD’s HIP runtime with the same kernels as CUDA, compiled for AMD’s chips:

  • What to install. On Linux, ROCm’s runtime packages (libamdhip64.so.6 or .7, in /opt/rocm/lib or on the loader’s path; the SDK is not needed). On Windows, the HIP runtime the AMD driver installs (amdhip64_6.dll in System32; Inga loads it from there only). Without it Inga runs as before, and inga devices says HIP: no AMD GPU through HIP: no HIP runtime found when Vulkan sees an AMD GPU.
  • Chips. The kernels are built for gfx1030–gfx1036 (RDNA2), gfx1100–gfx1103, gfx1150 and gfx1151 (RDNA3 and 3.5), gfx1200 and gfx1201 (RDNA4), gfx906, gfx908, gfx90a and gfx942; another chip is listed as not usable, with its name. ROCm itself supports fewer consumer cards on Linux than this list; HSA_OVERRIDE_GFX_VERSION is not needed for the chips above.
  • Choosing it. --device hip (or hip:N, gpu.device=hip, or the web UI’s Device menu, where each card is listed once with its APIs) asks for it, or fails with the reason; --device auto uses an AMD card through Vulkan only, never through HIP until HIP is measured on real cards, and never an integrated GPU beside a discrete card (issue #401).
  • The same as CUDA: the models, the weight types (F32, F16, Q8_0, Q4_0, Q4_1, Q5_0, Q5_1, Q2_K–Q6_K, IQ4_NL, IQ4_XS), the routed experts, the DeltaNet and Mamba-2 layers, the sampling on the GPU, partial offload and the fallback when memory runs out. Decode steps are not recorded as graphs unless debug.hip_graphs=true; debug.hip_sync=true waits after every kernel, so an error names it.
  • Please test it. inga devices --test compares the AMD GPU with the CPU (step 9); the maintainer would like to hear the result, and INGA_HIP=1 cargo test -p inga-cuda -p inga-hip -- --ignored runs the kernel tests on the card.

12. Several GPUs: the layers split between them

Section titled “12. Several GPUs: the layers split between them”

Two cards in one machine, or an integrated GPU and a card: name them all in --device, in order, and each runs a contiguous range of the layers with those layers’ KV cache (llama.cpp’s --split-mode layer). The first GPU takes the earliest layers, the last the latest ones and the output layer; between two GPUs the hidden state of the tokens (a few KB per token) goes through the host. Any mix works: two NVIDIA cards (cuda:0,cuda:1), an NVIDIA card and an AMD or Intel one through Vulkan (cuda:0,vulkan:1), CUDA, Vulkan and Metal devices alike (inga devices gives each its api:N).

  • The shares: by default each GPU’s free memory weighed by its speed, measured when the model loads (a product by a 16 MiB matrix, a few milliseconds): two equal cards share by memory, a GPU four times slower takes a fifth of what its memory would hold. --gpu-split 3,1 (or 0.75,0.25) sets them instead, one number per GPU of --device, as llama.cpp’s --tensor-split.
  • What a GPU cannot hold goes to the others; what none holds stays on the CPU (the first layers). With --device naming the GPUs, every layer asked for must fit (--gpu-layers N asks for fewer), as with one GPU; inga info --device cuda:0,cuda:1 shows the plan without loading.
  • The output is the one of a single GPU: the same layers run with the same kernels, only the hidden state crosses from one device to the next.
  • Dense transformer models only (Llama, Qwen3, Gemma, Mistral…): a mixture of experts (Qwen3-30B-A3B, Qwen3.6-35B-A3B, Ornith-1.5-35B-A3B), a hybrid model (Qwen3.5 and later, whose DeltaNet layers run through the attention stages) and Mamba-2 models run on one GPU, the rest on the CPU; name one in --device (such as --device vulkan:0). The error says so (issue #401).
  • serve and the web UI take the same list (--device, gpu.device, the Device field of POST /api/inga/device).
  • One card to try it: debug.cuda_split=2 lists each NVIDIA GPU as two logical ones (cuda:0 and cuda:1, each with half of the memory and its own context).

Good to know

Section titled “Good to know”
  • Several GPUs split whole layers only, one after the other (no tensor parallelism across GPUs, no two batches in flight on two GPUs); one machine (with --nodes, --expert-nodes or --tp-nodes every layer runs on the CPU).
  • The KV cache of the GPU’s layers is f16 whatever --cache-type says.
  • The plan keeps 256 MiB and 5 % of the GPU’s memory free (10 % on Windows, whose driver budget can shrink while a model loads, and which moves a too full card’s memory to the RAM without an error: on a 16 GB RX 9060 XT the budget fell from 15.06 GiB to 13.1–13.5 GiB once a model filled the card, issues #401 and #489, and llama.cpp’s 14.94 GiB there ran at a quarter of its speed, issue #1038); where the model runs says it under the parts, with the activations of the prompt chunks. --set gpu.keep_free=5% (or gpu.keep_free = "5%" in inga.toml, a size such as "1GiB" too) keeps another share; when it would put a model’s last routed experts on the card, a tip says so. On Windows compare inga bench with and without it.
  • The memory check counts what the sessions really hold: one KV cache (and, for DeltaNet and Mamba-2 layers, a state and its checkpoint) per serve --parallel session, of the context chosen for the model, each session’s activations for its decode steps, and once for all of them the activations of the prompt chunks (the sessions take turns with them; issue #1038: eight users of Qwen3.8-27B counted 4108 MiB for chunks of 512 when each session had its own). When the activations of chunks of 256 tokens would keep weights off the GPU, prompts go in chunks of 128 or 64 instead, and the gpu: line says how much more stays on the GPU that way (gpu: prompts in chunks of up to 128 tokens (chunks of 256 would leave 143 MiB of weights off Vulkan 0 ...)): a weight on the CPU slows every token, a smaller chunk only makes a prompt read the GPU’s weights more often. --prefill-chunk N keeps the chunk you choose. If the GPU still runs out of memory while loading, Inga keeps less there (the routed experts first, then the feed-forward blocks, then the layers: a sixteenth of them at the first retry, then an eighth, then a quarter at a time) and the placement says so (a gpu: line with the device’s numbers, also when the device refuses one of the routed experts’ allocations and the rest of them stay on the CPU); a GPU that cannot hold even that leaves the model on the CPU, with the reason, and the load succeeds. Loading a model in the web UI waits for the one it replaces to free its GPU memory.
  • A session makes its activations when it opens (the scratch of every prompt chunk size, Vulkan’s room for the prompts’ 8-bit activations, the routed experts’), not at the first prompt that needs them: a driver whose budget shrinks after the load (AMD’s on Windows, issue #489: “allocating 17825792 bytes: ERROR_OUT_OF_DEVICE_MEMORY” at the second or third answer) no longer fails an answer. When the GPU has no room for the largest prompt chunk, prompts go in smaller chunks (gpu: prompts in chunks of up to 128 tokens (... refused the activations of chunks of 256 when the sessions opened)); when a step’s routed experts find no room, they run on the CPU for that step.
  • Prompts use f32 activations on the GPU (8-bit ones on the CPU): after a long prompt the answer can differ from the CPU’s where two words were almost equally likely; the quality is the same (perplexity within 0.3 %).
  • The token embeddings stay on the CPU; the output layer goes to the GPU when every layer and it fit (the note then says “and the output layer”). With the output layer on an NVIDIA GPU (CUDA) or on Vulkan (AMD, Intel, NVIDIA), the GPU also draws the next token when the request needs nothing else from the logits — greedy, or a temperature with top-k from 1 to 128, top-p and min-p; on Vulkan also with the repetition, presence and frequency penalties and for models that soft-cap their logits (Gemma 2, 3n and 4); it draws what the CPU would with the same seed — and only the token comes back (4 bytes instead of the row of logits, 1 MiB for Gemma’s 262,144 tokens). inga run’s report says N sampled on the GPU. Anything else (DRY, mirostat, XTC, typical-p, top-n-sigma, logit bias, log-probabilities, a grammar, --parallel, top-k 0, and on CUDA the penalties and soft-capped logits) samples on the CPU; debug.gpu_sampling=false always does.
  • Mixtures of experts (Qwen2/3 MoE, OLMoE, Mixtral, gpt-oss, Qwen3.5 / 3.6 MoE, Qwen3-Next…) put the attention of their layers on the GPU, then the routed experts of as many layers as fit (section 5); the rest of the experts run on the CPU, and the speed depends on how many of them are left there. DeepSeek (latent attention) stays on the CPU. The routed experts and the Mamba-2 layers are checked against the CPU on Vulkan (lavapipe) and on CUDA (the maintainer’s Quadro P1000); their speed on real models and larger cards is in the real-world checks (docs/todo/real-world-checks.md).
  • Gemma 3n, Gemma 4 E2B / E4B, LFM2, DeepSeek V2 / V3 / V4, Kimi Linear / K3, Qwen3.8-Flash-Next, GLM-5.3-Flash and the diffusion language models run on the CPU (Gemma 4 12B, 31B and 26B-A4B on Vulkan, Metal, CUDA and HIP, see Requirements) (with --device auto the placement says why); so do Gemma 3’s images (--image) when layers are on the GPU (an error says so). The GPUs do not apply LoRA adapters, so Phi-4-multimodal runs on the CPU.
