Keep a folder in sync with a collection

What you get

Section titled “What you get”

A collection of documents that follows a folder of yours (notes, a wiki, a code repository, a folder of recordings): read, cut and embedded once with the encoder measured best for its content, then read again as its files change, only the changed passages embedded again, its recordings transcribed by speaker. The chats, the API and inga docs search ask it as any collection (keep-documents-in-a-collection.md).

Requirements

Section titled “Requirements”
  • What chat-with-documents.md needs: a chat model and the documents (PDF with a text layer, DOCX, HTML, Markdown or text, code).
  • An embedding model, or none: the folder’s mode downloads the one it chooses the first time (its size said first).
  • For recordings, a speech-to-text model (transcribe-audio.md).

1. Get Inga

Section titled “1. Get Inga”

Download the archive for your system from the Releases page and put inga on your PATH (details); inga --version checks it.

2. Keep a folder in sync

Section titled “2. Keep a folder in sync”

A collection can also follow a folder: notes, a wiki, a code repository. From the command line (the server need not run; a running inga serve sees the changes):

docs add reads the folder at once with a progress line (42 % · 312 of 1204 files · 5210 chunks · src/store.rs · ~6 min left). Without --embed-model, the folder’s mode chooses (--mode, Automatic by default): Inga reads the language of a sample of its documents (up to 48) and counts the files its code parser reads, then takes, for the documents and for the code, the encoder measured best for that content, and says which and why:

The three modes:

Mode Documents in English Documents in Italian and other languages Code
Fast potion-retrieval-32M potion-multilingual-128M potion-code-16M-v2
Quality all-MiniLM-L6-v2 granite-embedding-107m-multilingual all-MiniLM-L6-v2
Automatic Fast’s when it loses at most docs.fast_loss (0.02), else Quality’s the same rule the same rule

Fast encoders are static (Model2Vec): a folder is embedded in seconds, a question in well under a millisecond, for a loss the table of docs/experiments.md (“Retrieval”) measures. With today’s measurements and docs.fast_loss at 0.02, Automatic takes potion-retrieval-32M for English documents, granite-embedding-107m for Italian ones (and for other languages, which are not measured: it says so) and all-MiniLM-L6-v2 for code (docs.fast_loss 0.02 was decided by the maintainer on 2026-11-13). A model the mode chooses is downloaded the first time (its size said first); with --offline and the model missing, the web UI’s embedding model is used instead, said. A folder with code and documents takes one encoder for every file, the one its mode takes for code (“code and documents, 701 files: one encoder for both, all-MiniLM-L6-v2; an encoder per kind measured lower (0.676 against 0.693 nDCG@10 on inga-mixed)”); with docs.split_encoders = true under [docs] each kind gets its own, and a search embeds the question once per encoder and merges the two lists. To change the mode of a folder already indexed: inga docs sync notes --mode fast; it asks first, with the passages to embed again and the time it takes (--yes without a terminal). On the Documents page each folder has the same picker (Automatic, Fast, Quality) and a line with the encoders of its documents and its code, why in its tooltip; a change asks first in the same way, the time said with its basis: the model that will embed each kind (the embedding model when the encoder the mode chose is not downloaded), the passages, the rate and where it was measured (the encoders’ table, measured on another machine; or this folder’s last sync on this computer), or that there is no rate to estimate with yet. While a folder syncs, its line says the time left and the passages per second measured so far. --embed-model M names one model for every file instead. The folder remembers the models its files were embedded with: inga docs sync needs no --embed-model (and loads no model when nothing changed); given another one, it says so, embeds the new and changed files with it and tells how to embed them all again (inga docs sync notes --full --embed-model M). Only the files the globs take are read (--include and --exclude, written as in .gitignore), the folder’s .gitignore and .ingaignore files apply, and .git/, target/, node_modules/, .obsidian/ and .trash/ are left out; binary files and files above 64 MiB are skipped. Each file is kept with its size, time and SHA-256: the next sync opens only the files whose size or time changed, reads again only those whose bytes changed, and removes the files gone from the folder with their passages; in a changed file, the passages that did not change keep their vectors, so editing one section of a long document embeds only that section again. inga docs status says what a sync would do now; inga docs rm notes ~/notes stops following the folder. Files can be added without a folder too, as the Documents page’s uploads: inga docs add contracts rossi.pdf bianchi.docx.

A big first sync, faster or gentler. Indexing runs at low priority on half the logical CPUs, so the computer stays responsive while a big folder is read; the first line says so (indexing at low priority (nice 10, disk best-effort 7), 4 threads), and so does each folder’s report. On Linux that is nice 10 and the lowest best-effort disk priority of the thread, on macOS the background QoS class (the efficiency cores on Apple silicon), on Windows the threads’ background mode. If the system refuses it, the sync goes on at normal priority and says why. While the chunks of some files are embedded, the next files are read, cut and tokenized on the threads the embedding model leaves, and the chunks of several small files are embedded together. To go faster on a computer you are not using, inga docs sync notes --full-speed (or docs add ... --full-speed) indexes at normal priority on every thread; to be gentler still, fewer threads: inga --set docs.ingest_threads=2 docs sync notes, or ingest_threads = 2 under [docs] in inga.toml, which inga serve’s syncs follow too. The server’s syncs always run at low priority, and lower its embedding model’s threads, which it shares with the searches: they stay so while the model is loaded (Linux lets no ordinary user raise them again), which only slows a search while the computer is busy with something else.

To see what a question finds, as the chats search it:

Each passage comes with its citation (notes.md#3-costs, todo.txt:12-40, report.pdf p. 4), its heading path and a bullet’s date; --explain adds its rank in the vectors’ list, in the words’ (BM25) list and in the dates’ list, its cosine and the reranker’s score, and the time of each step: the tool to see why a passage came first, or did not come.

--where keeps only the passages whose file or bullet meets its conditions, before they are scored: KEY=VALUE, !=, <, <=, >, >=, separated by commas. A key is one of the front matter’s (tags, category, created…), path (a glob, as .gitignore writes them), kind (Markdown, PDF), title, heading or date (a bullet’s date, else the front matter’s). Dates compare as dates at the value’s precision (date=2026-08 is August 2026), numbers as numbers, the rest ignoring case; a list matches when one of its items does.

After an update of Inga. Each file remembers the version of the chunker that cut it. When Inga’s chunker changes (version 2 added the heading paths, anchors, lines, front matter and dated bullets), a sync reads the folders’ files again even if they did not change, and says so (note: 120 files are read again: Inga's chunker changed ...; cut again by the new chunker in the report); the passages whose heading and text did not change keep their vectors. inga serve does it at the next sync of a folder synced every so often or watched; inga docs status says re-index needed for the others (inga docs sync NAME), and an uploaded file is added again. Until then the old chunks are searched as before, without the new places, dates and filters.

inga serve syncs the folders added with --every 1h, and watches those added with --watch (their sizes and times every 5 seconds; a change is read once it stood still for one look, so a file being saved is not read half-way). A sync waits between files, and between the passages of a file, while a chat answer is being generated. An inga docs sync of a folder that inga serve is syncing (or the other way round) says who holds it and waits for it to end, then does what is left. The web UI’s Documents page shows each folder’s last sync, or the progress of the one running, with Sync now, Cancel and Stop syncing; Map a server folder… adds one, but only under the folders the server was given with --docs-root DIR (docs.roots in inga.toml): the API never reads a folder its caller names elsewhere. Without them, the folder is doc beside the inga executable, made at start with a README.md that says what it is for.

The job’s events (mode, scan, file, chunks, error, paused, done) carry the percentage, the files and chunks done, the time left and the errors; POST /api/inga/documents/sync {"collection": "notes"} syncs now and DELETE /api/inga/documents/jobs/ID cancels.

How well does it find things? inga eval rag --questions FILE.toml indexes a folder into a throw-away collection, asks the questions of the file and prints recall@5/10/20, MRR@10, nDCG@10 and the search times, per kind of question (tests/rag/inga-code.toml is a sample on Inga’s own sources, tests/rag/inga-docs.toml on its docs/ folder read as a wiki, tests/rag/wiki-synth.toml a synthetic wiki, tests/rag/pdf.toml PDF reports and Word files; each step’s time is given as its median and its 95th percentile: embed, dense, BM25, fusion, rerank). Keep a questions file for your own folder outside it, and compare embedding models and searches on it: --mode dense, bm25, hybrid or hybrid+rerank (with --rerank-model M; several at once on one index: --mode bm25,dense,hybrid), and any [docs] key with --set (inga --set docs.hub_penalty=1 eval rag ...). --collection NAME measures a collection already indexed, without reading the folder again. An answer written file.md#anchor, file.md:L10-40 or src/a.rs::name is also matched by place: the chunk found must hold that section, those lines or that function. Beside the scores, the report says how long indexing took (chunks per second), what it kept busy (the cores, the disk) and which of the two held it back, the memory the index takes, and the encoder, chunker, threads and search settings the numbers were measured with; --baseline before.json (an earlier --json report) shows each score before → after.

Public sets measure the search on data that is not yours: python3 tools/rag-sets.py build scifact ~/rag-sets (also squad-it, Italian questions, and hotpotqa, questions that need two pages; a few MB each, their licences listed by python3 tools/rag-sets.py list) writes a set in BEIR’s layout, and inga eval rag --beir ~/rag-sets/scifact --embed-model M measures it; any set in that layout (corpus.jsonl, queries.jsonl, qrels/test.tsv, as BEIR and MTEB publish them) works the same way. Larger synthetic sets need no download: python3 tools/rag-gen.py wiki-synth ~/rag-sets --pages 300 writes a wiki of 300 pages with its 40 questions (~/rag-sets/wiki-synth-300.toml), and python3 tools/rag-gen.py pdf ~/rag-sets the PDF and Word set again. The numbers measured so far are in experiments, “Retrieval”.

3. Recordings in a folder, transcribed at the sync

Section titled “3. Recordings in a folder, transcribed at the sync”

A folder’s recordings (WAV, MP3 and FLAC files) are transcribed by Inga when its sync meets them, once a speech-to-text model is chosen, and read by speaker turn as a transcript is (meeting transcripts). Choose the models once, in inga.toml:

(or --set docs.transcription_model=FILE; transcribe-audio.md says where the models come from). Then:

The model is loaded only when a recording has to be transcribed, on the indexing’s threads at low priority ([docs] ingest_threads), one recording at a time. Each transcript is kept by the recording’s bytes and the models in transcripts/ beside the store, so a sync that reads the file again (--full, a new chunker) does not transcribe it again: the sync then says its transcript from the cache. A recording without speech is listed with why and not read again until it changes. Without a transcription model the sync lists the recordings as not transcribed, with the key to set, and transcribes them at the first sync after it is set. The Documents page’s Indexing tooltip, inga docs status NAME --files and the API’s indexing (model, diarizer, duration, audio) say how each recording was transcribed; the sync’s report lists them (transcribed, not_transcribed). A recording is decoded whole, up to 30 minutes and the 64 MiB a folder’s file may be.

Options worth knowing

Section titled “Options worth knowing”
Option What it does
inga docs add NAME DIR follow a folder (--include, --exclude, --watch, --every 1h)
--mode fast|quality|automatic the folder’s encoders (Automatic by default)
--embed-model M one embedding model for every file instead
--full-speed index at normal priority on every thread
docs.ingest_threads the indexing’s threads (half the logical CPUs)
inga docs status, sync, rm, search what a sync would do, sync now, stop following, search
--docs-root DIR (serve) the folders the web UI and the API may map

Troubleshooting

Section titled “Troubleshooting”
  • The models changed: a sync given another --embed-model embeds only the new and changed files with it; inga docs sync NAME --full --embed-model M embeds them all again.
  • re-index needed in inga docs status: Inga’s chunker changed; inga docs sync NAME reads the files again.
  • A folder the web UI cannot map: start the server with --docs-root DIR above it.
