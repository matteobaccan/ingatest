Run a mixture-of-experts model, even one larger than your RAM

Supported since: 0.4.0; the routed experts on a GPU (--experts-on, --cpu-moe): 0.24.0; the prefix cache of the layers on a GPU: 0.31.0

What you get

Section titled “What you get”

Chat with a mixture-of-experts (MoE) model, such as Qwen3-30B-A3B, OLMoE, Qwen1.5-MoE or Mixtral, on the CPU. An MoE model stores many “experts” per layer but uses only a few for each token, so it is fast for its size. When the whole model does not fit in RAM, Inga keeps the experts on disk and reads the ones each token needs into a cache, instead of failing or thrashing.

Requirements

Section titled “Requirements”
  • Windows, Linux or macOS; any x86-64 or ARM64 CPU.
  • Disk space for the model file. Qwen3-30B-A3B in Q4_K_M is about 18.6 GB. OLMoE-1B-7B in Q4_K_M is about 4.2 GB and is a good first try.
  • RAM: ideally the file size plus 1–2 GB. With less RAM the model still runs, at the speed of your disk (an NVMe SSD helps a lot); the minimum is the non-expert part of the model (about 1.5 GB for Qwen3-30B-A3B), the KV cache and a few hundred MB.
  • Network access for the download (see run-a-model-from-hugging-face.md).

How it works

Section titled “How it works”

  • Each token’s router picks the most probable experts of every layer, exactly as llama.cpp does (softmax, top-k, renormalization where the model asks for it), so the greedy output matches llama.cpp’s.

  • A prompt is read grouped by expert: the rows of a chunk that go to the same expert go through it together, so each expert’s weights are read once per chunk, not once per token (on the CPU, on Vulkan since 0.26.3, on CUDA and Metal and for gpt-oss’s experts with biases since 0.27.0). debug.moe_grouped=false turns it off (the GPU then takes each expert’s rows eight at a time), to measure the difference with inga bench model.gguf -p 512 --ab debug.moe_grouped=false --ab-tolerance 1 (one row at a time takes the decode kernels, whose sums round differently).

  • In RAM, experts are read through the memory-mapped file. On disk, the experts a step needs are read in parallel into a least-recently-used cache sized from your free memory; frequently used experts stay in memory. Since 0.14.0, while a layer computes, the next layer’s router is applied to the layer’s input to guess the experts the next layer will need, and those are read from disk meanwhile (router lookahead): the reads overlap the computation, and a wrong guess costs only the read.

  • Since 0.28.0 (research), the guess can be trained: inga profile model.gguf --text calibration.txt --prerouter also collects, at each MoE layer, the hidden state and the experts the next layer then picked, trains a small head per layer on the CPU (a correction of the next router’s guess), prints for each layer the share of the next layer’s experts it predicts beside the router lookahead and the previous token’s experts, and keeps a head only where it beats the lookahead (the file goes beside the profile, .prerouter). inga run, serve and bench with --prerouter then read ahead the experts it picks. The output does not change, only which experts are read early. inga bench model.gguf --mem-limit 8G -r 3 --prerouter ends with a line such as experts: ... predicted: prerouter (46 heads) 88.1 %, router lookahead 81.4 %; without --prerouter it gives the lookahead’s rate alone.

  • Since 0.14.0, inga run and inga serve count how often each expert is used, in ~/.cache/inga/experts/ (--home moves it), and the next run starts by reading the experts used most into the cache, where they stay: half the cache by default, --pin-experts N to choose, --pin-experts 0 for none. bench and perplexity neither read nor update the counts. Since 0.22.2 the counts are a profile (<model file>-<size>.profile): for every expert, the tokens routed to it and the sum of the router weights they gave it, kept for every mixture of experts (not only when the experts are read from disk); the .txt files of earlier versions are read and replaced.

  • inga profile model.gguf --text calibration.txt runs a text through the model (in chunks of --ctx, 512 by default; --chunks N for the first N) and writes its importance matrix, as llama.cpp’s llama-imatrix collects it (per input column of every matrix of the layers, the sum of the squared activations, and the rows), beside the profile (.imatrix, llama.cpp’s imatrix GGUF format; -o imatrix.gguf writes it there too, for llama-quantize --imatrix). inga run and inga serve collect it while they run with --collect-imatrix (off by default), adding to the one kept. The experts’ rows are all counted; the other matrices, as in llama-imatrix, only in passes of at least 16 tokens. Layers run on a GPU or on other machines are not collected (inga profile runs every layer on the CPU). inga data list profiles lists the files, inga data rm deletes them.

  • Since 0.16.0, --mirror DIR (repeatable) names a directory on another disk holding a copy of the model’s files (the same names and sizes): the experts read from disk are then read from the originals and the copies in turn, so two or more disks read at once (striping without rewriting the files). bench takes it too, to measure it.

  • Since 0.27.0, --experts-dir DIR (repeatable) stripes the experts over the disks instead of copying the whole model to each: every directory gets a share of each layer’s experts (expert e in the e % n-th one), written once (as stored, or converted with --quantize-experts), and each expert is then read from its own disk. Two NVMe drives read about twice as fast, for one extra copy of the experts in all:

    The first run writes the stripes (experts: striped over 2 directories (...)), the next ones read them. Deleting a directory only costs that copy again.

  • The cache keeps the experts used most: it evicts the one least recently used, weighted by how often each expert was used in earlier runs (the profile) and in this one, so a burst of rare experts does not push out the common ones. A long prompt does not go through it: the experts the cache lacks are read into two buffers (the next read while the current one runs, the next layer’s read ahead) and dropped after use, so after the prompt the cache still holds what decoding needs.

  • debug.direct_reads=true reads the experts past the operating system’s page cache, which would otherwise keep a second copy of what Inga’s cache already holds; compare both with inga bench MODEL --ab debug.direct_reads=true.

  • With a GPU, the memory plan counts only what stays in RAM: the attention, KV cache, output layer and experts a card with its own memory takes leave their RAM to the experts the CPU runs (inga run prints the experts kept in RAM and how much more free RAM would keep them all).

  • The rest of the model (attention, norms, embeddings, the shared expert) stays in RAM, unless even that does not fit: the layers are then streamed from disk as for a dense model.

Quantize the experts on their own

Section titled “Quantize the experts on their own”

The routed experts are most of an MoE model, and they tolerate a coarser quantization than the rest. Since 0.17.0, --quantize-experts TYPE converts them when loading (q2_k, q3_k, q4_k, q5_k, q6_k or q8_0, as llama.cpp’s reference quantizers do, from any stored type), and --quantize-down TYPE gives their down projections another type; --quantize converts the rest (from F32 / F16 / BF16):

The conversion is done once: the converted experts are kept in ~/.cache/inga/cache/experts/<key>/ (default ~/.cache/inga/cache/experts; one file per MoE layer and a manifest.json), and the next loads of the same model with the same types read them from there, converting nothing (experts: converted experts read from ... on the terminal). The memory plan is made after the conversion, so a model whose experts only fit once converted keeps them in memory; experts that still do not fit are streamed from the cache’s files, one read per expert. Experts larger than the RAM are converted too, layer by layer in bounded memory (a large model takes a while the first time). Deleting the directory only costs one conversion; a damaged or incomplete entry is rebuilt. Converting already quantized experts (a Q8_0 GGUF file to Q2_K) loses more than quantizing from the original weights.

Hot, warm and cold experts: precision by use

Section titled “Hot, warm and cold experts: precision by use”

--quantize-experts converts every expert. When the experts do not fit in the RAM at their own precision, --experts-precision auto (since 0.22.2; run, serve, bench, perplexity) converts only what it must, and sizes the result to the free memory (less the other weights, the KV cache and --mem-limit):

  • The experts are ranked by the router weight they carried per byte, from the model’s profile (~/.cache/inga/experts/<model>.profile, kept by every run; inga profile makes one from a text). Without a profile yet, they are ranked alike and none is hot (a note says so); the next runs rank them.
  • Warm experts are converted to --experts-warm TYPE and kept in RAM. Without --experts-warm, the type is the first of q4_k, q3_k, q2_k that saves at least one bit per weight on the model’s experts: q4_k from a Q8_0 or 16-bit file, q3_k from a Q4_K_M file, q2_k from a Q3_K file. When no type saves a bit per weight (a Q2_K file, or --experts-warm q4_k on a Q4_K_M file), nothing is converted, the experts are loaded as without the option and one line says why. If the warm experts do not all fit, the best ranked are warm and the rest are cold: converted to --experts-cold TYPE (default the warm type; e.g. q2_k) and read from disk when used, with a small cache (a line says how many). If memory is left once every expert is in RAM, the best ranked keep the model’s own precision: hot.
  • The groups take no more RAM than the cache of streamed experts would without the option (the free memory less the other weights, the KV cache and the overhead). The hot and warm experts are read into Inga’s expert cache once, each in one read and a layer’s in parallel, as streamed experts are, and stay there.
  • The conversion is done once and kept in ~/.cache/inga/cache/experts (as for --quantize-experts), one expert at a time, so it takes little memory whatever the model’s size. The hot experts are read from the model file and left out of it: they are neither read nor converted. The entry is kept while what it fixes still fits (its cold experts, and the experts it left out, which stay hot), so a profile that moves on, or a little less free memory, does not convert the model again; inga data rm on the entry makes the next load choose again.
  • The GPU gets what it gets without the option (attention, shared experts, output layer): only the routed experts change.
  • Only the routed experts change: attention, routers, shared experts, norms and the output layer are never converted. A matrix is never given more bits than it has (a Q4_K file is not taken to Q5_K), and converting a source of 4 bits or less prints a warning: errors add up, so the best source is a Q8_0 or BF16 file.

It is off by default: converting weights changes the output, and Inga otherwise gives llama.cpp’s output for the same file. When the experts would stream from disk without it, Inga prints what it would do, e.g. note: experts streamed from disk; --experts-precision auto would keep them in RAM at about 4.5 bits per weight. Measure the cost on your own text before relying on it (see measure-model-quality.md):

The second command keeps the KL divergence it measured for that model and those types in ~/.cache/inga/experts/<model>.quality, and the suggestion line shows it from then on (measured on this model: KL 0.0800). Rough expectations, to be replaced by such measurements: Q8_0 to Q4_K, a few percent of perplexity; Q2_K without an importance matrix, large losses on small models, smaller on large mixtures.

With a GPU: experts in VRAM, then RAM, then disk

Section titled “With a GPU: experts in VRAM, then RAM, then disk”

Since 0.24.0, with a GPU (CUDA, Vulkan or Metal, used by default) a mixture of experts fills it in this order: the output layer, the attention of its layers with their KV cache, the shared experts, then the routed experts of as many whole layers as the memory left holds, from the last layer back. The other experts run on the CPU, from RAM or, when the RAM is short, from the disk. The router runs on the CPU; each token’s experts and weights go to the GPU, which computes them and returns only their weighted sum. The placement printed at load says which layers’ experts are where:

  • --experts-on cpu keeps every routed expert on the CPU, --experts-on gpu asks for all of them on the GPU (an error, saying how many fit, when they do not).
  • --cpu-moe N keeps the first N layers’ experts on the CPU (llama.cpp’s --n-cpu-moe N), to leave GPU memory for a longer context.
  • Experts of a weight type the GPU does not read (the smaller i-quants, BF16), and Nemotron 3’s latent experts, stay on the CPU; the tip says why.

The tip gives the smallest step (the free GPU memory the next layer’s experts need) and all of them. When the experts are read from the disk, the RAM tip says how much RAM Inga found, how many experts stay in RAM once read and how much more would keep them all. inga info MODEL shows the same placement before loading. More in run-on-an-nvidia-gpu.md.

With the experts on the CPU (and above all from the disk), processing a chat’s history is the slow part. Since 0.31.0 inga serve’s prefix cache and --kv-disk keep copies of the GPU’s KV cache and of a hybrid model’s DeltaNet states too: when another chat comes between two turns, the next turn reads its conversation back from RAM (or disk) to the GPU and processes only its new tokens, instead of the whole history (keep-long-conversations.md). inga bench -d N starts each run of a hybrid model on a GPU from such a copy.

Troubleshooting

Section titled “Troubleshooting”
  • “does not fit in the memory budget, expect disk-bound speed”: even the non-expert part and the smallest expert cache do not fit, so the layers are streamed from disk too (see run-a-dense-model-larger-than-ram.md); for more speed, close other programs, use a smaller context (--ctx), a quantized KV cache (--cache-type q8_0) or a smaller quantization.
  • Slow with experts on disk: the speed is bounded by the disk; an NVMe SSD reads 2–7 GB/s, a SATA SSD about 0.5 GB/s, a hard disk far less. More free RAM means a bigger cache and fewer reads.
  • “model architecture … not supported”: Inga runs Mixtral, Qwen1.5/2 MoE, Qwen3 MoE and OLMoE (0.4.0), gpt-oss and DeepSeek V2 / V3 (deepseek2, 0.13.0), Qwen3.5 MoE and Qwen3-Next (0.14.0), DeepSeek V3.2 and GLM 5 (deepseek32, glm-dsa, 0.20.0); see the comparison for the others.
