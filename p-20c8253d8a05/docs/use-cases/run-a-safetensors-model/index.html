Run a Hugging Face model in its original format

What you get

Section titled “What you get”

Run a model straight from its Hugging Face repository in the original format (config.json, *.safetensors, tokenizer.json), with no conversion to GGUF and no Python. This is useful for brand-new models, which often have no GGUF yet, and for fine-tunes you trained yourself. Weights are used as they are (BF16, F16 or F32), or converted to Q8_0 while loading to halve the memory.

Requirements

Section titled “Requirements”
  • Windows, Linux or macOS; any x86-64 or ARM64 CPU.
  • A Llama, Mistral, Qwen2/2.5 or Qwen3 model (LlamaForCausalLM, MistralForCausalLM, Qwen2ForCausalLM, Qwen3ForCausalLM in config.json), or a Mixtral, Qwen MoE or OLMoE one; also Phi-3 and Phi-4-mini (Phi3ForCausalLM), Phi-4-multimodal (Phi4MMForCausalLM, chat-about-an-image.md) and Ling 2.0 (BailingMoeV2ForCausalLM). Also the embedding and reranking models of the BERT family (sentence-transformers directories such as all-MiniLM-L6-v2, bge-small-en-v1.5, paraphrase-multilingual-MiniLM-L12-v2), served by inga serve on /v1/embeddings and /v1/rerank.
  • RAM for the weights: about 2 bytes per parameter in BF16 (Qwen3-0.6B: 1.2 GB), or 1 byte per parameter with --quantize q8_0.
  • Network access to download it, or the model directory on disk.

1. Get Inga

Section titled “1. Get Inga”

Download the archive for your system from the Releases page and put inga on your PATH (details); inga --version checks it.

2. Run it from Hugging Face

Section titled “2. Run it from Hugging Face”

When the repository has no GGUF files, Inga downloads config.json, the tokenizer files (tokenizer.json, tokenizer_config.json, generation_config.json) and the model*.safetensors weights into the Hugging Face cache, then chats. A repository that offers both formats is read as GGUF; to choose, see run-a-model-from-hugging-face.md.

3. Or from a directory on disk

Section titled “3. Or from a directory on disk”

Any directory with config.json, the safetensors weights (one file or shards with model.safetensors.index.json) and tokenizer.json works. You can pass the directory or its config.json:

inga info shows the architecture, the tokenizer, the tensor types and the memory plan, as for a GGUF file.

4. Quantize while loading

Section titled “4. Quantize while loading”

Every weight matrix is converted to Q8_0 as the model loads (in parallel; a few seconds for a 1B model). The output is the one llama.cpp gives for the Q8_0 GGUF conversion of the same model, and the memory needed is about half of BF16. inga info --quantize q8_0 shows the memory plan after conversion.

5. Quantized checkpoints

Section titled “5. Quantized checkpoints”

Repositories quantized with GPTQ or AWQ (4 bits) or published in FP8 (F8_E4M3 with block scales, as DeepSeek and Qwen do) load directly, e.g. hf://Qwen/Qwen2.5-0.5B-Instruct-AWQ. Each layer is converted while loading: GPTQ and AWQ groups become Q4_1 blocks, exactly (GPTQ’s act-order, desc_act, gives F16 instead), and FP8 weights become BF16. The memory needed is that of the converted weights.

6. Apple MLX models

Section titled “6. Apple MLX models”

The MLX conversions of these architectures (the mlx-community repositories, e.g. hf://mlx-community/Qwen3-0.6B-4bit, mlx_lm.convert -q outputs, LM Studio’s MLX folders) load too. Their config.json has a quantization object, and each quantized layer (packed uint32 codes with scales and biases per group) is converted when the model loads: 2–4 bits to Q4_K, 5–6 bits to Q6_K, 8 bits to Q8_0 (rows that are not whole 256-value blocks to Q8_0), mxfp4 to MXFP4 exactly. --quantize TYPE converts them straight to TYPE instead. Inga prints what it converted, e.g.:

inga info shows the same line without converting anything. The conversion runs on every core at each load, and the converted weights stay in RAM. Modes other than affine and mxfp4 (nvfp4, mxfp8) are refused with their name; see the spec.

On the CPU and on a Mac’s GPU (--device cpu, --device metal, and --device auto on a Mac) the affine weights are not converted: they are read as stored by MLX kernels (scale * q + bias, as MLX computes them), so the model gives the values MLX gives, with no second rounding and no conversion time:

For an NVIDIA or Vulkan GPU (which have no MLX kernels), with --device auto off a Mac, and with --quantize, they are converted as above. debug.mlx_native=true keeps them as stored, debug.mlx_native=false converts them, whatever the device (see the spec).

Notes

Section titled “Notes”
  • The weights are memory-mapped from the safetensors files. They are not copied, unless you quantize them.
  • Llama models use the same RoPE as the GGUF conversion, applied to the original Q/K layout, so no tensor has to be rewritten.
  • Mixture-of-experts models in safetensors (Mixtral, Qwen MoE, OLMoE) work too, and --quantize q4_k halves the memory again (Q4_K, as llama.cpp quantizes it).

Troubleshooting

Section titled “Troubleshooting”
  • “safetensors model X (supported: …)”: the architecture in config.json is not one Inga runs yet; look for a GGUF conversion of a supported architecture.
  • “no config.json at the repository root” or “… is not a language model”: the repository holds something else than a transformers language model (docling’s layout and TableFormer models, an RT-DETR object detector, an image classifier); Inga runs generative and embedding models.
  • “tensor … has dtype …”: a checkpoint quantized another way than GPTQ, AWQ (4 bits, GEMM), FP8 or MLX; use the BF16 or F16 release of the model.
  • “mlx: …”: an MLX directory Inga cannot convert (a mode such as nvfp4, or tensors that do not match config.json’s quantization): the message names the module; use another conversion of the model.
  • “pre-tokenizer unrecognized”: the tokenizer splits text in a way Inga does not implement yet; the GGUF conversion of the same model usually works.
