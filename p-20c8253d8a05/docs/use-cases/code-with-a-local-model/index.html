Code with a local model

What you get

Section titled “What you get”

A coding agent on your project, answered by a model on your own machine, in one command:

inga code chooses a coding model that fits this computer (asking before it downloads anything, with the size), starts the server, indexes the folder’s code so the model can ask “who calls this function?”, and opens Inga’s own agent in the terminal. The agent reads the files, shows every edit as a diff before it is written, takes an edit back with /undo, and, if you allow it, runs the project’s tests, each run asked. The files never leave this computer: the file and code tools run in inga code itself, and only the model’s requests go to the server.

Prefer Claude Code, Codex or OpenCode? The same command starts them instead, already connected (step 9).

First: the context, 64k for another agent

Section titled “First: the context, 64k for another agent”

Inga’s own agent starts at 32768 tokens of context; the other coding CLIs want 65536 (Ollama’s guide asks 64k for each). inga code --agent NAME and inga connect say so when the server has less: start it with --ctx 65536 (--cache-type q8_0 takes half of the cache’s memory back).

Requirements

Section titled “Requirements”
  • Windows, Linux or macOS.
  • A project folder (a git repository or not; not your home folder or a disk’s root).
  • Free disk for the model: 5 to 19 GB, depending on the model Inga chooses for this machine (step 3). A model already on the disk is taken first.

1. Get Inga

Section titled “1. Get Inga”

Download the archive for your system from the Releases page and put inga on your PATH (details); inga --version checks it.

2. Start it in the project, and trust the folder

Section titled “2. Start it in the project, and trust the folder”

The first time in a folder, Inga’s agent asks whether you trust it, before it reads anything of it (an example; the path is yours):

  • On a terminal you choose with the arrows and Enter (y, t and n choose at once); without one (a script, a pipe) the same choices are typed: y, t, or n, the default.
  • Yes remembers it for the whole git repository (every folder inside it), for this session only trusts it until you exit, No stops: nothing of the folder was read and nothing was sent, and inga code says so in two lines (no error).
  • Your home folder is trusted for one session at most, never remembered; inga code --untrust forgets it.

3. What Inga chose, and why

Section titled “3. What Inga chose, and why”

On a terminal the start is a few short blocks: the folder, the model, the server, the index, the agent (an example; the names and numbers are this machine’s):

Every choice with its technical detail (why this model, the encoders, the second pass, the code tools) is one line in ~/.cache/inga/logs/code-start.log; without a terminal (a script, a pipe) those lines are printed instead, and inga code --plan prints them all and stops there: nothing downloaded, indexed or started.

The server. A server already answering on this machine (http://127.0.0.1:8080, or the port serve.port of inga.toml names) is reused as it is; --url URL names one on another machine. Otherwise inga code starts inga serve itself, at 32768 tokens of context (what coding agents need), and stops it when you leave.

The model. Inga picks from its list of coding models, all of which call tools:

Model Size Planned for
Qwen3 8B Q4_K_M 5.0 GB a CPU with 16 GB of RAM
Qwen3.5 9B Q4_K_M 6.0 GB a CPU with 16 GB of RAM and a GPU of 8 GB
gpt-oss 20B MXFP4 12.1 GB a GPU of 12 to 16 GB
Qwen3-Coder 30B-A3B Q4_K_M 18.6 GB a CPU with 32 GB of RAM, a GPU of 8 GB (experts in RAM) or of 24 GB

It checks each one against this machine at 32768 tokens of context, as inga setup does for a first model: the largest that runs whole on the GPU; else the largest that runs in memory at 8 tokens a second or more; else the smallest that runs in memory; never one that would read its layers from the disk. One of the list already on the disk is taken before any download. The line names the model, how it runs here and what the coders’ benchmark says of it:

(An example: the model, the memory and the GPU are this machine’s.) On a terminal you choose it from a menu instead, the one Inga recommends first:

The order: the recommended one, the coding models already on this disk that run here, the other models on this disk that call tools, the coding models to download (with their size), then the remote models of your nodes.json, never the default (your code’s text leaves the machine only when you choose one). A model to download is downloaded once chosen, not asked again. When a running server lists several models (its own and the remote ones), the same menu lists them, its loaded one first. --model M (a file, a model of the disk or hf://..., or code.model in inga.toml) is kept as given and said so; one whose chat template never reads tools is refused, since the agent needs tool calls.

The index. The folder becomes a collection of this machine’s store, named after it, its files counted by language, .gitignore honoured, build folders such as target/ and node_modules/ skipped. A fast encoder makes the first index in seconds; the full encoder then re-embeds the folder in the background when its estimate is under code.full_index_minutes (10), the fast index answering meanwhile. The index is kept in sync while inga code runs. --no-index skips it: the agent then reads the files only, without the code tools.

The code index, measured on Inga’s own Rust sources (1,187 files, about 733,000 lines; inga docs add with the static encoder potion-code-16M-v2, a development build on a shared 4-vCPU machine with no GPU): the first index in 18.8 s, and callers found all 76 call edges of 30 functions checked by hand (the run). How the index reads the code, the tools it gives the agent and what they cost in the context: how-inga-code-reads-your-code.md.

4. Ask a check question

Section titled “4. Ask a check question”

Then the agent says what it read and waits at the prompt, which names the mode:

On a terminal inga code starts with “INGA” and its version; you type between two lines, over the context’s fill (ctx 10.4k / 40k, 25 % (8.7k from the cache), compaction at 32.8k), the last turn’s time, tokens/s and the day’s tokens; a Latin word turns while the model reads or thinks; each tool and round says its tokens and time.

AGENTS.md, the common standard (no other tool’s file), is read from the repository’s root down to the folder. Ask something only the code answers, such as “who calls parse_args?”. Each tool call is one line with the first 3 lines of its result (an example):

/show 1 prints the whole result. The code tools (find_definition, find_references, callers, callees, outline) are ask-questions-about-a-code-base.md’s, run here over the folder’s index.

5. An edit, its diff, and /undo

Section titled “5. An edit, its diff, and /undo”

Ask for a change (“rename parse_args to parse_cli”). The model edits only a file it has read, unchanged since; each edit is shown as a diff and, in the ask mode, asked:

  • Every question of inga code is such a menu on a terminal: ↑↓ and Enter, or a choice’s initial letter (a for “every edit”, which holds in the next sessions too: inga mcp revoke --workspace DIR takes it back); “tell the model why” asks for the reason. Esc stops the turn: nothing applied, the model told, back at the prompt. A pipe types the letters: y, n use a shorter name, a.

  • /undo puts back the files of the last turn’s edits (again: the turns before); a file you changed since is shown and asked first:

  • /diff shows the session’s changes against the files as they were before.

The copies are kept in Inga’s own folder for code.keep_sessions days (7): your git repository is never written.

6. The three modes

Section titled “6. The three modes”
Mode An edit or a new file
ask (the default) shown and asked: yes, every edit, no, no with a reason
auto-edit applied, its diff shown; /undo takes it back
plan none: the edit tools are not offered, the model answers with a plan

Shift+Tab moves to the next mode at once (ask → auto-edit → plan → ask; from a pipe, Shift+Tab then Enter); /mode auto-edit names one; --mode plan (or code.mode) sets the start:

7. Let it run the project’s tests: --allow-commands

Section titled “7. Let it run the project’s tests: --allow-commands”

The agent may then run the commands the folder’s manifests name, and only those: cargo test and the rest for a Cargo.toml, a package.json’s scripts, pytest, mvn test, gradle test, go test, a Makefile’s targets, and those you add as [code] commands in inga.toml, with only the arguments each takes (a test’s name), never a shell. The start says what the command sandbox closes on this machine. Every run is asked, in every mode, with what will run, its sandbox and its time limit (an example):

There is no “always”: the next run is asked again (a pipe types y, or n and a reason). plan runs none. Where the system has no sandbox, the start and each question say “NOT sandboxed”, and you decide. The details (the commands per manifest, the clean environment, [code] sandbox_read and sandbox_write): use-with-coding-agents.md.

8. Questions over many files: explore

Section titled “8. Questions over many files: explore”

For a question such as “where is the configuration read?”, the agent may hand the reading to an explorer: a sub-agent with a fresh context that only reads (it changes nothing, runs nothing and asks you nothing) and gives back a short report with the files and lines it rests on, so the agent’s context keeps only the report. It works in every mode, plan included. Its model is the smallest coding model of the list that calls tools and fits beside the agent’s in the free memory, else the agent’s own; the start says which and why. Each explorer is one line as it starts and one as it ends:

(An example: the calls, the tokens and the time are the run’s.) --no-explore turns it off; code.explore_model names another model. More: use-with-coding-agents.md.

9. Another agent instead: --agent

Section titled “9. Another agent instead: --agent”

--agent takes claude-code, codex, opencode, pi, aider, qwen-code, droid, copilot, deepseek-harness or openclaw (or inga, the default). The same setup is made (the server, the model, the index), then the agent is started as inga connect TOOL --run starts it, for this run only, with the folder’s code tools served by inga code on 127.0.0.1 as its MCP server (a key made for the run). pi and Aider read no MCP server, and Inga gives none to Droid, Copilot CLI, DeepSeek Harness and OpenClaw: they get the model only, said with why. A context under 64k is said too (above). An agent that is not installed is said with its install command, before anything is started or downloaded. The agent keeps its own approvals and modes; --mode, -p and --trust are Inga’s agent’s. Words after -- go to the agent unchanged:

10. On a mesh satellite

Section titled “10. On a mesh satellite”

On a PC that is a satellite of an Inga mesh (run-a-model-on-a-mesh.md) with no server of its own, inga code takes the mesh’s master as the server and starts no local one, which would take memory from the mesh’s layers (an example):

The index and the code tools stay on the satellite, where the files are; only the model’s requests go to the master. --url names another server; --model is refused here, since no server is started.

The server inga code starts for itself has no web page (--no-webui): it is a terminal tool. For the web UI as well, start inga serve first; inga code uses it as it is.

11. The same by hand

Section titled “11. The same by hand”

inga code does what these four commands do, for who wants each step in their hands:

inga connect gives the agent Inga’s MCP server, whose code tools read the collection of the current folder: ask-questions-about-a-code-base.md, use-with-coding-agents.md.

The session’s commands

Section titled “The session’s commands”

On a terminal the prompt’s box stays on its last rows, the answer scrolling above it (code.sticky_box = false: after the output). Type /: the matching commands show under it, ↑↓ choose, Tab completes, Enter runs. /help lists them in your terminal’s language (the web UI’s chat has the same); //text sends /text.

Command What it does
/status tabs Status, Usage, Config and Stats (tokens per day, 30 days); ←/→ switch, Esc closes
/model [N|NAME] the models to switch to; NAME, hf:// or a path: that one
/mode [NAME], Shift+Tab the next mode at once (ask → auto-edit → plan), or that one
/context, /compact, /clear how the context is used; the older turns summarized; a new conversation
/diff, /undo, /review the session’s changes; the last turn’s put back; the model reviews them
/init the model drafts an AGENTS.md, shown as a diff and approved like an edit
/show N, /tools the whole result of the call N; the tools offered and their tokens
/copy, /export [FILE] the last answer to the clipboard (and a file); the conversation as text
/feedback, /trust, /exit a GitHub issue filled in, shown first; the folder’s trust; leave

!COMMAND runs your command in the folder’s shell, its output folded (/show N) and joined to your next message; Ctrl-C stops it, twice at an empty prompt leaves. The model’s questions (ask_user) are a menu; Esc stops the turn.

The web: web_search and fetch_url, each asked first (Yes, this time / Yes, every page of that site / No). fetch_url gives the page as Markdown, kept whole in Inga’s cache: a long page asked with a question is read part by part by the explorer, which copies the passages that answer; asked again, “from Inga’s cache, read 12 minutes ago” (say “read it fresh”). Save it to work on it: .inga/downloads/, or a file you name. Off: code.web = false.

Another model in the middle of a session: /model

Section titled “Another model in the middle of a session: /model”

/model opens the start’s list: the agent’s model first and marked, then the coding models, the other models on this disk that call tools, the downloads; type letters to filter it by name (Backspace widens, Esc clears), a digit chooses while no filter is typed, Enter chooses, Esc keeps the model. /model 3, /model gpt-oss 20B, /model hf://REPO/FILE.gguf or a path choose directly. A switch is said before → after; the conversation is kept and read again by the new model at the next message.

A served model is used from the next message; one not served, on the server inga code started, is said (its download and size, how it runs, the model unloaded) and asked (Esc keeps it); your own server is not changed.

Good to know

Section titled “Good to know”
  • One instruction from a script: inga code --mode auto-edit --trust -p "rename parse_args to parse_cli" runs one turn and prints the answer. --trust trusts the folder for that run only; with nobody to ask, no command runs and, in ask, no edit is made.
  • Every option: inga help code; [code] in docs/config.md.
  • A server that needs a key: LOCAL_LLM_API_KEY in the environment, or client.api_key in inga.toml.
