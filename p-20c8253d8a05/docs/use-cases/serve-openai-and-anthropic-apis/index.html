Serve a model to OpenAI and Anthropic clients

Supported since: 0.6.0

What you get

Section titled “What you get”

inga serve exposes a local model over HTTP with the two most widely used chat APIs: OpenAI’s /v1/chat/completions and Anthropic’s /v1/messages, streamed or not, with tool calling. Anything that speaks one of them can use Inga instead of a cloud service: the official Python and JavaScript SDKs, curl, Open WebUI, editors and agents such as Claude Code. Since 0.13.0 it also answers the Ollama API (/api/chat, /api/generate, …), for tools written for Ollama.

Requirements

Section titled “Requirements”
  • Windows, Linux or macOS; any x86-64 or ARM64 CPU.
  • A model Inga runs (see chat-with-a-local-gguf-model.md and run-a-model-from-hugging-face.md). For tool calling, a model trained for it. Inga reads the calls of Qwen2.5 / Qwen3 (Hermes <tool_call> JSON), Qwen3.5 / Qwen3-Coder (<function=…><parameter=…> XML), Llama 3.1+, Mistral, GLM 4.5+, Granite, DeepSeek V3 / R1 / V3.1, gpt-oss and Gemma 4 (<|tool_call>call:NAME{key:<|"|>…<|"|>}<tool_call|>, since 0.28.0), and a JSON call in a ```json block or after a sentence when it names a tool of the request. When a model asks for a tool in another format, the answer carries inga_warning (shown in the web UI under the answer, and on the server’s standard error) instead of failing silently.

1. Get Inga

Section titled “1. Get Inga”

Download the archive for your system from the Releases page and put inga on your PATH (details); inga --version checks it. This guide needs 0.6.0 or later.

2. Start the server

Section titled “2. Start the server”

The server listens at once and loads the model in the background (since 0.26.3): GET /health answers 503 loading until it is ready, then 200, so a script waits for the 200 rather than for a line of the console. A request that comes meanwhile waits up to --load-wait (120 s) for the model, then gets 503 with Retry-After. A model that fails to load leaves the server up: /health and the web UI say why, requests for it get 503 with the error, and POST /api/inga/load loads it again (--exit-on-load-error stops the server with exit 1 instead).

The server listens on 127.0.0.1:8080, which is reachable from this machine only. Use --port N to change the port and --host 0.0.0.0 to accept other machines. Then set a key with --api-key KEY (or serve.api_key in inga.toml): clients send it as Authorization: Bearer KEY, as the OpenAI SDKs do with their api_key, or as x-api-key: KEY, as the Anthropic SDKs do. Only GET /health answers without it. The traffic is not encrypted: put the server behind an HTTPS proxy outside a trusted network. For a web page served from another origin, allow that origin with --cors ORIGIN (or --cors '*'). Every run option works too: --ctx, -t, --temp (the default when a request sets none), --mem-limit, --quantize, --cache-type, --offline.

Each model’s recommended sampling (since 0.21.0: general.sampling.* in a GGUF file, generation_config.json in a Hugging Face directory) fills what a request leaves out. For each of temperature, top-k, top-p, min-p, repeat penalty and window, XTC and mirostat, the server takes the request’s field, else the inga serve option if given (--temp 0.7), else the model’s recommendation, else Inga’s default. --no-model-sampling skips the model’s step. GET /api/inga/status shows, for each loaded model, recommended_sampling and sampling (what a request without sampling fields gets).

By default requests are answered one at a time and others wait. With --parallel N, up to N requests are answered at once, each by its own session with its own KV cache (so the KV cache takes N times the memory); the tokens of the sessions generating at the same time are computed as one batch, which reads the weights once for all of them: on Llama-3.2-1B, four clients get 1.5x the total tokens per second of --parallel 1. A request goes to the free session that already holds the longest part of its prompt. Each session keeps its conversation’s KV cache, so each new turn of a chat only processes the new messages. When requests switch between conversations (several clients, or one client with several chats), a session keeps a copy of the KV cache of the conversations it leaves, up to 1 GiB in all (--prefix-cache SIZE, shared by the sessions; 0 to turn it off): coming back to one of them only processes what is new. OpenAI responses report the tokens taken from the cache in usage.prompt_tokens_details.cached_tokens.

More on serving many clients and models, with the memory each option takes, is in serve-many-users-and-models.md.

Several models

Section titled “Several models”

Give inga serve several models and clients choose one with the request’s model field (the names GET /v1/models lists: the file name without .gguf, or the hf:// reference):

The first model is loaded at start, the others when a request first names them. With --models-max N (default 1), at most N stay loaded: loading another unloads the least recently used one once its requests are answered. A request without model goes to the first model; an unknown name gets 404. The options (--ctx, --parallel, --quantize, …) apply to every model.

An image model (a Stable Diffusion checkpoint, since 0.20.0) is served alone, with OpenAI’s /v1/images/generations and the chat page’s image mode: see generate-images.md.

Thinking models and long chats

Section titled “Thinking models and long chats”

Thinking models (Qwen3, DeepSeek-R1, …) write their reasoning between <think> and </think> before the answer. inga serve returns it apart: as reasoning_content in OpenAI messages and deltas, and as a thinking block before the text in Anthropic messages. --reasoning-format none leaves it in the answer.

Thinking can be switched off or on (since 0.20.0), for models whose template has the switch (Qwen3, Qwen3.5, DeepSeek V3.1, SmolLM3, …; gpt-oss takes an effort instead):

  • for the whole server: --think off, --reasoning-effort low, or any template variable with --chat-template-kwargs '{"enable_thinking": false}';
  • per request, over the server’s choice: chat_template_kwargs ({"enable_thinking": false}, as llama-server and vLLM), reasoning_effort ("low", "medium", "high"; reasoning.effort in the Responses API), Ollama’s think (true, false or an effort) and Anthropic’s thinking ({"type": "enabled"} or {"type": "disabled"});
  • in the web UI, the Thinking choice in the settings.

inga run takes the same options, and /think on or /think off during a chat. More in use-thinking-models.md; long chats are in keep-long-conversations.md.

A conversation longer than the context is refused (400) unless the server runs with --context-shift: then its oldest turns after the system messages are dropped until the prompt leaves room for the answer (up to max_tokens, at most half the context). An answer that fills the context while it is generated still stops there, unless the server runs with --cache-cap N (since 0.16.0): a context of N tokens whose older half, after the first 4 tokens, is forgotten when an answer reaches it, so the answer goes on (it implies --ctx N --context-shift).

3. Talk to it

Section titled “3. Talk to it”

In a browser (since 0.18.0): open http://127.0.0.1:8080/ for Inga’s chat page (a step-by-step tour is in chat-in-the-browser.md). The conversations stay in the browser’s storage; the settings at the bottom left choose the model, the temperature, the answer length and the system prompt, and hold the API key when the server has one. --no-webui turns the page off.

The chat renders answers as Markdown; hover a message for copy, edit, regenerate and delete; the box above the chats searches them, a double click renames one, and the two arrows export and import them as JSON. Sampling in the settings holds every sampler (temperature, top-k/p, min-p, typical-p, top-n-sigma, the repetition, presence and frequency penalties, DRY, XTC, mirostat, seed, stop strings, JSON output) and the presets (Balanced, Precise, Creative, Code, and the ones you save). The paper clip attaches images and audio (WAV, MP3, FLAC) for models with a projector; the bar under the box shows how much of the context the chat fills.

Compare with in the settings (since 0.20.0) is an arena: every question also goes to a second model (serve both, e.g. inga serve a.gguf b.gguf --models-max 2), the two answers appear side by side, and a vote picks the one the chat goes on with; the votes are counted per pair of models.

The rail on the left of the page (since 0.19.0) has two more tabs, as LM Studio does:

  • Models: search Hugging Face for GGUF models, open a repository to see its files (quantization, size, projectors, already downloaded or not), download them into the Hugging Face cache with a progress bar (cancel at any time), and manage the downloaded models: whether Inga runs each one, Load (it becomes the chat’s model; beyond --models-max the least recently used one is unloaded), Unload, Delete. Models loaded from the page use the server’s options (--ctx, --quantize, …).
  • Server: the models and their state, the requests, tokens and speeds of /metrics, and the server’s settings, refreshed every two seconds.

The same operations are a small JSON API under /api/inga/ (guarded by --api-key like the others): GET search?q=, GET repo?id=, POST pull {"model"}, GET pulls, POST pull/cancel {"id"}, GET library, POST library/delete {"repo"}, POST load {"model"}, POST unload {"model"}, GET status.

Tool calling

Section titled “Tool calling”

Pass tools as each API defines them. Inga gives them to the model’s chat template. When the answer contains tool calls, they come back as OpenAI tool_calls (finish_reason: "tool_calls") or Anthropic tool_use blocks (stop_reason: "tool_use"). Send the results back as tool messages (OpenAI) or tool_result blocks (Anthropic) to continue. With tools, the answer is sent once complete rather than token by token.

Web search

Section titled “Web search”

Since 0.22.0, "web_search": true on /v1/chat/completions offers the model a built-in web_search({query}) tool that the server runs itself: DuckDuckGo by default, or the search services you list, tried one after the other until one answers (--search-backends searxng=https://searx.example/search,brave,duckduckgo, or the web UI’s Search services: DuckDuckGo, Wikipedia, SearXNG, Brave Search, Tavily). The model gets the numbered results, may search again (three times at most) and answers; the answer streams token by token, and the results it was given come back as inga_sources. When DuckDuckGo blocks the server’s address (a 202 with its anti-bot page), Inga waits a second and asks DuckDuckGo’s lite page; when that is blocked too, the tool’s answer tells the model so and not to search again (see chat-in-the-browser.md):

Streamed, each search is announced by a {"inga_search": {"query": "..."}} delta and the sources come in the chunk with the finish_reason. Your own tools can be sent too: their calls come back as usual. {"web_search": {"fetch_pages": 2}} also gives the model the text of the first two pages. inga serve --web-search searches for every request that does not say "web_search": false. Web search is a server-wide switch, on unless the server runs --no-web-search or --offline, changed while it runs with POST /api/inga/settings {"web_search": true, "search_services": [{"id": "duckduckgo", "on": true}]} (or the web UI’s Server tab), which keeps the choice in ~/.cache/inga/settings.json for the next start (an explicit --no-web-search or --search-backends wins over it; Brave Search’s and Tavily’s keys go in the encrypted key store with {"search_keys": {"brave": "KEY"}}); a request asking for it while it is off gets a 400. The model must be able to call tools (its template renders tools: Qwen 2.5 / 3, Llama 3.1+, Mistral, gpt-oss, …); see chat-in-the-browser.md.

The other chat APIs run the same search (since 0.22.1):

  • Anthropic (/v1/messages): the standard server tool, "tools": [{"type": "web_search_20250305", "name": "web_search"}] (its options are ignored), or "web_search": true. The answer has usage.server_tool_use.web_search_requests and inga_sources; streamed, an inga_search event announces each search (the SDKs skip it) and message_delta carries the sources.
  • Ollama (/api/chat): "web_search": true; the last object’s message holds inga_sources, and a streamed line with inga_search announces each search.
  • Responses (/v1/responses): the standard "tools": [{"type": "web_search"}] (or web_search_preview), or "web_search": true. Each search is a web_search_call output item (response.web_search_call.* events when streamed), each [n] in the text a url_citation annotation, and the response has inga_sources.

In the terminal, inga run model.gguf --web-search does the same: the searches are announced on stderr and the sources printed under the answer.

What is supported

Section titled “What is supported”

Every route is described field by field, as OpenAPI 3.1, in docs/api/ (open the files in Swagger UI or Redocly, or generate a client from them).

Endpoint Notes
GET /v1/models The models being served
GET /health {"status": "ok", "models": [{"id", "state"}], "busy": N}: each model loaded, loading or unloaded, and the sessions answering a request; 503 with "status": "loading" while no model is loaded (a model being swapped in with --models-max)
GET /metrics Prometheus counters: inga_requests_total, inga_prompt_tokens_total, inga_prompt_tokens_cached_total, inga_tokens_predicted_total, the seconds spent on each, inga_requests_processing, inga_sessions_busy, inga_models_loaded
POST /v1/embeddings OpenAI’s format: input (a string or a list of strings) → unit-length vectors of the model’s hidden size, the final hidden states pooled as the model says (a GGUF file’s pooling_type, a sentence-transformers directory’s pooling module; else the mean; --pooling mean|cls|last overrides it). Since 0.20.0 embedding models of the BERT family (all-MiniLM, bge, paraphrase-multilingual, bge-m3, nomic-embed-text; GGUF or a Hugging Face directory) answer it, and only it and /v1/rerank: a chat or completion request gets a clear error. A sentence-transformers model without a Normalize module returns its vectors unscaled, as sentence-transformers does
POST /v1/classify Since 0.15.0: input (the text), labels (the classes), instruction (optional, default “Classify the text with one of the labels.”) → label (the most likely), labels (label, probability, logprob, most likely first): the model is asked which label fits, and each label’s tokens are scored after the question; the probabilities are normalized over the labels
POST /v1/completions OpenAI’s legacy text completion: prompt (one string, continued without the chat template), max_tokens (default 16), the sampling fields, stop, logprobs (0 to 5, not with stream), stream, stream_options.include_usage
POST /v1/chat/completions messages (text), max_tokens / max_completion_tokens, temperature, top_p, top_k, min_p, seed, repeat_penalty, repeat_last_n, llama-server’s dry_multiplier, dry_base, dry_allowed_length, dry_penalty_last_n, dry_sequence_breakers, xtc_probability, xtc_threshold, mirostat, mirostat_tau, mirostat_eta, typical_p, top_n_sigma, logit_bias (OpenAI’s object or llama.cpp’s [[token, bias]], false banning a token), stop, logprobs / top_logprobs, n (up to 8), response_format (json_object, json_schema) and grammar (see get-structured-output.md), tools, stream, stream_options.include_usage
POST /v1/responses OpenAI’s Responses API (since 0.18.0): input (text, or items: messages with input_text / input_image / input_audio parts, function_call, function_call_output), instructions, max_output_tokens, temperature, top_p, seed, tools (functions), text.format (JSON schema), stream (the response.* events); responses are not stored, so previous_response_id is refused
POST /v1/messages system, messages (text, tool_use, tool_result), max_tokens, temperature, top_p, top_k, stop_sequences, tools, stream
POST /v1/messages/count_tokens The prompt size in tokens
GET /api/version, GET /api/tags, GET /api/ps, POST /api/show Ollama’s model listing
POST /api/chat, POST /api/generate Ollama’s chat and completion: messages / prompt (with system, or raw), stream (default true: one JSON object per line), format ("json" or a JSON schema), tools, options (temperature, top_k, top_p, min_p, seed, repeat_penalty, repeat_last_n, mirostat, mirostat_tau, mirostat_eta, the dry_* and xtc_* fields, num_predict, stop); thinking for reasoning models
POST /api/embed, POST /api/embeddings Ollama’s embeddings: input (a string or a list) → embeddings; prompt → embedding
POST /infill llama.cpp’s code completion (since 0.14.0): input_prefix and input_suffix (the code around the cursor), input_extra (other files, [{"filename", "text"}]), prompt (the start of the middle), n_predict (default 128), the sampling fields, stop, stream; answered as llama.cpp does (content, stop, stop_type, tokens_predicted, timings). Needs a model with fill-in-the-middle tokens, such as Qwen2.5-Coder
POST /api/v1/generate, POST /api/extra/generate/stream The KoboldAI API as KoboldCpp serves it (since 0.17.0), for SillyTavern and other KoboldAI clients: prompt continued without the chat template, max_length (default 100), temperature, top_k, top_p, min_p, rep_pen, rep_pen_range, sampler_seed, the dry_*, xtc_* and mirostat* fields, stop_sequence; {"results": [{"text", "finish_reason"}]}, or message events of {"token", "finish_reason"}. Also POST /api/extra/tokencount, GET /api/v1/model, /api/v1/info/version, /api/extra/version, /api/v1/config/max_context_length, /api/extra/true_max_context_length
POST /v1/rerank (also /rerank, /v1/reranking) Since 0.17.0: query, documents (strings or {"text"}), top_n, return_documents, instruction → results of {"index", "relevance_score"}, most relevant first, and usage. A reranker GGUF (a classification head, such as llama.cpp’s conversion of Qwen3-Reranker or bge-reranker-v2-gemma) scores as llama-server’s rank pooling, with its rerank prompt template; any other chat model is asked whether each document meets the query and scores with the probability of “yes”. Since 0.20.0 a BERT cross-encoder (ms-marco-MiniLM, bge-reranker-base / v2-m3) scores [CLS] query [SEP] document [SEP] with its classification head, and an embedding model scores the cosine similarity of the embeddings
POST /tokenize, POST /detokenize llama.cpp’s format: {"content", "add_special", "with_pieces"} → {"tokens"}, and {"tokens"} → {"content"}
GET /api/v0/models, GET /api/v0/models/{id}, POST /api/v0/chat/completions, /api/v0/completions, /api/v0/embeddings LM Studio’s REST API (since 0.20.0): each model’s state (loaded, not-loaded), type, arch, quantization, max_context_length; chat answers add stats, model_info and runtime
GET /lora-adapters The adapters loaded with --lora (since 0.20.0): [{"id", "path", "scale"}]; a request’s lora field picks among them
/api/inga/* The web UI’s model hub and status (since 0.19.0; see chat-in-the-browser.md)

Images (since 0.15.0, with a vision model and its projector, --mmproj) go in OpenAI image_url parts as data: URLs, Anthropic image blocks and Ollama images; with --allow-image-urls (since 0.16.0), also as http(s) URLs the server downloads; see chat-about-an-image.md. Audio (since 0.17.0, with an Ultravox, Qwen2-Audio or Voxtral model and its projector) goes in OpenAI input_audio parts as WAV, MP3 or FLAC; see ask-about-audio.md. Since 0.18.0, logprobs works with stream too (the log-probabilities come in a chunk just before the choice’s finish_reason), and n asks for up to 8 choices, generated one after the other.

Traces

Section titled “Traces”

With --otlp-endpoint http://collector:4318 (or OTEL_EXPORTER_OTLP_ENDPOINT in the environment; since 0.17.0), every request becomes an OpenTelemetry span, sent in batches to the collector’s /v1/traces (OTLP over HTTP with JSON: the OpenTelemetry Collector, Jaeger, Grafana Tempo and most tracing services accept it). A request carrying a W3C traceparent header joins that trace. Generations carry the GenAI attributes: gen_ai.operation.name, gen_ai.request.model, gen_ai.request.max_tokens, gen_ai.request.temperature, gen_ai.usage.input_tokens / output_tokens, gen_ai.response.finish_reasons, gen_ai.server.time_to_first_token (seconds) and inga.cached_tokens. The export runs on a thread of its own: a slow or missing collector never delays an answer (spans are dropped when 4096 wait), and a failing export is reported once on stderr.

Troubleshooting

Section titled “Troubleshooting”
  • “this model has no chat template”: the model file carries no template; use an instruct/chat version of the model.
  • 400 “the prompt has N tokens, which exceeds the maximum context length of M tokens of this session” (OpenAI code: context_length_exceeded): start the server with a larger --ctx.
  • Another program already uses port 8080: pass --port.
  • 401 “invalid or missing API key”: the server was started with --api-key (or serve.api_key); give the client the same key.
