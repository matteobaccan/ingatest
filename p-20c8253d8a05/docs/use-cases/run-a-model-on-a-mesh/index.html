Run a model on a mesh of PCs

What you get

Section titled “What you get”

Start Inga on several PCs of your network and they run one model together, with no addresses to type and no copy of the model on the other PCs:

  • They find each other. Every Inga of the same mesh announces itself on the LAN by mDNS (_inga._tcp.local) every 2 seconds; a node unheard of for 6 seconds is gone. Where multicast does not pass, --peers names the other nodes.
  • One is the master. The node with the highest score is elected, and says why: the highest --priority, then the master already in place, then a node that serves a model, then the most RAM, then the lowest id — every node reaches the same result.
  • The satellites receive what they run. The master measures each satellite (how fast its CPU and GPU run the weights, its free memory, the round trip), places contiguous ranges of layers where a token is fastest (a satellite that would slow it down is left out), and sends each satellite only its layers, checked by SHA-256. The satellite keeps each layer in a file of its own: when it comes back, or another master sends the same model, nothing travels again.
  • A satellite that leaves is replaced. If a satellite fails or leaves in the middle of an answer, its layers move to another satellite (or to the master itself), which receives the missing chunks and replays the inputs it needs: the answer goes on, the same as on one machine.
  • You see everything. The terminal, inga mesh show, GET /api/inga/mesh and the web UI’s Mesh page say who is the master and why, each node’s resources, what it runs, the links’ round trips, the bytes sent and every decision. On the page’s map the nodes can be dragged to match the office, with the mouse, a finger or the arrows; the browser keeps their places for the mesh, Arrange goes back to the automatic layout and Lock stops dragging.

Like --nodes (split-a-model-across-machines.md) this is a pipeline: the PCs work one after the other, so a mesh runs a model too large for one PC, it does not make a small one faster.

What was checked, and how: the mesh was run as several processes on one machine — with --peers over 127.0.0.1 in the tests (tests/mesh.rs, crates/inga-dist/tests/mesh.rs: the answers equal one process’s, also after the satellite running the layers is killed mid-answer, on dense and hybrid models) and by hand with mDNS over the machine’s network interface. Real PCs on a real LAN are still to be tried (docs/todo/real-world-checks.md).

Requirements

Section titled “Requirements”
  • Two or more PCs with Linux, Windows or macOS on one LAN. Every connection between nodes is encrypted; give the mesh a key (below) so that only your PCs can join it: without one, anyone on the LAN can join a mesh by its name.
  • Mesh protocols that overlap on every node (nodes of another version): a node whose protocol is too old is listed, flagged with the update to install, and not used.
  • The PCs’ clocks within 30 seconds of each other when the mesh has a key (an announcement older than that is taken for a replay): any PC that sets its clock from the internet is.
  • On the master, a GGUF model (one file or a split -00001-of-0000N.gguf set; a Hugging Face directory is not sent: convert it with inga quantize). The satellites need no model, only free memory and some disk for the parts they run: the bytes of their layers, on any drive (NTFS, ext4, XFS, APFS, FAT32, exFAT; each layer is a file of its own, see The satellite’s cache).
  • UDP port 5353 (mDNS) open between the PCs, or --peers; UDP port 9090 open on every node (the mesh port of all of them) and TCP 9090 on the satellites. On Windows the network must be Private (a Public one drops the mesh’s packets; the node says so at start), or inga.exe allowed in Windows Defender Firewall. On Linux with ufw or firewalld active, the node names the ports to open. Inga never changes a firewall rule.

0. Give the mesh a key

Section titled “0. Give the mesh a key”

On one PC, make the key of the mesh (home here) and print it:

On each other PC, keep the same key (typed, pasted or copied in a file; dashes, spaces and case do not matter):

From then on inga serve --mesh home and inga satellite --mesh home use it by themselves. --mesh-key FILE (or - for standard input) and the mesh.key variable give a key without keeping it, e.g. in a service. With a key:

  • every announcement carries a MAC (HMAC-SHA256) and a time: a node without the key, with another one, or replaying an old announcement is ignored, and said once (mesh home: node pc9 (192.168.1.40) ignored: different mesh key);
  • every TCP connection (the layers’ parts, the activations, the KV caches, the cache cleaning) opens with a Noise handshake (NNpsk0, the key as the pre-shared key) and runs encrypted with ChaCha20-Poly1305: a node without the key is refused (wrong or no mesh key), and a byte changed on the way breaks the connection;
  • the nodes show the key’s fingerprint, never the key: the start line (encrypted (key 9c41e2b0)), inga mesh show and the Mesh page (a lock on each node, the nodes ignored listed under the events).

To change the key (someone left the office, the key was shown on a screen): inga mesh key new --mesh home --force on one PC, then inga mesh key import - --mesh home --force on the others, and restart the nodes. Until a node has the new key, the others ignore it and say why.

A node with a key tells, and the Mesh page lists, a node without one (“it has no mesh key”), and the other way round. A mesh with no key at all still runs encrypted, with a pre-shared key every Inga knows: a PC that only listens cannot read it, but any PC can join it.

1. Start a satellite on each other PC

Section titled “1. Start a satellite on each other PC”

That line is what a service, a pipe or CI reads. On a terminal the same start is Inga’s banner: the logo, then the rows Mesh, Listening (the address), Serves, Machine (threads, the weights’ speed measured, the GPUs), Parts (where the parts received are kept, and how much) and Security.

The address in brackets is the one the node announces: that of its LAN interface (the first with a private address: 10.x, 172.16-31.x, 192.168.x), never a virtual adapter’s (WSL and Hyper-V’s vEthernet, Docker, VirtualBox, VMware, Tailscale) while a real one is up. The others are listed after it, e.g. pc2 (192.168.1.20; also 172.17.32.1, virtual, not used); with --peers, it is the interface that reaches the first peer, and --advertise IP sets it by hand. mDNS joins the multicast group and sends on every LAN interface, and an interface that comes up later (a cable plugged in, a VPN) is joined at the next heartbeat.

The satellite joins the mesh as soon as its port is bound, then measures its machine (its CPU in a quarter of a second, its GPU’s probe sometimes in seconds) and sends the measure at once: a slow measure no longer delays its discovery. The master says found pc2 …; it measures its machine, its measure follows, then pc2 sent its measure: 11.80 GiB/s of weights; it may be planned on now, and plans on no satellite before its measure. Then it waits. --cache DIR moves its cache, -t N sets its threads, --port N its port, --node-name NAME the name the mesh shows.

Every node’s mesh port is 9090 by default. A second node on the same PC finds 9090 taken and takes the next free one, and says which: UDP port 9090 is taken on this machine (another node?): this node uses 9091. --peers HOST without a port means 9090.

The cache directory is checked at start: it is made if missing, and a small file is written and removed in it. A drive that does not exist or a directory that cannot be written stops the satellite with exit 2 (--cache X:\inga-cache: the drive X: does not exist). The start line says the room left there and the cache’s limit; the satellite announces both, and the master gives it no more layers than fit.

The satellite’s cache

Section titled “The satellite’s cache”

A satellite keeps each layer it received in a file of its own, in a directory per model (~/.cache/inga/cache/mesh/<model id>/): blk.012.bin holds layer 12’s tensors, header.gguf the model’s header (metadata, tokenizer), globals.bin the small tensors outside the layers, index.json what is there. No file is as large as the model, a copy or a backup takes what the files take, and FAT32 or exFAT drives work. A satellite given other layers of the same model receives only the files it lacks; a layer half received when the connection broke resumes where it stopped. The layers are mapped in place when the satellite loads them, as a model file is.

The cache keeps under a limit: --cache-max 50G, or by default 80 % of the room its drive has for it (what it holds plus the free space). Before receiving, the layers used least recently go first, then a model with none left; never the layers of a model the satellite has loaded. The satellite announces what more may come, counting what it would remove.

--cache-clean MODEL takes the model’s id (or its first digits) or its file’s name, --cache-clean --all every model; a model loaded or being received is kept and said. The Mesh page shows each node’s cache, and Clean cache on a satellite that runs no layers now (the master forwards the request: POST /api/inga/mesh/clean).

A cache of an older Inga (the model’s whole file, sparse) is removed at the satellite’s start, in one line; nothing of it is loaded.

2. Start the master with the model

Section titled “2. Start the master with the model”

The model is placed when it loads, on the satellites alive and measured then. The wait before it is --mesh-wait S at most (3 s), and less once the nodes you expect are there, each with its measure: every --peers entry answered, and/or --mesh-expect N other nodes. The line after the wait names the rule that ended it:

A satellite that joins (or sends its measure) after the model was placed is weighed at once: the master runs its placement with and without it and, when the model runs 10 % faster with it, or fits the mesh’s memory where it did not, or ran on the master alone for want of a satellite, places the model again between requests (an answer under way is never cut). The layers each satellite already holds stay in its cache: only what it lacks travels. The model’s conversations in RAM start over, as after any reload.

or, when it would not pay, pc3 joined after Qwen3-8B-Q4_K_M.gguf was placed: the plan stays (about 2.5 tok/s with it against 2.4 now: less than 10 % faster). GET /api/inga/mesh lists these decisions in replans (waiting for the requests in flight, done, or dropped when the model was unloaded meanwhile: its next load places it with every satellite there). The last line of the plan lists each satellite’s outcome: used with its layers, left out and why (version, its TCP port 9090 does not answer (a firewall), a failure while it received), or not asked. The mesh’s lines printed while the model loads go above the loading spinner, each on its own line. Clients use the master as any inga serve (serve-openai-and-anthropic-apis.md). The web UI’s chat says where the model ended up, beside the context (this PC (master): layers 0–9 · pc2: layers 9–35, or only this PC: ... · satellites not used (why)), from runs_on of GET /api/inga/status; GET /api/inga/mesh lists the models run alone in alone.

The server listens at once: the web UI and its Mesh page open while the layers travel, which takes minutes for a large model. GET /health answers 503 loading until the model is ready, then 200; a chat request waits up to --load-wait (120 s) for it, then gets 503 with Retry-After. If the load fails the server stays up: the model is failed with its error in /health and the web UI, and the web UI’s Models page (or POST /api/inga/load) loads it again; --exit-on-load-error stops the server instead.

A satellite that fails while it receives its layers

Section titled “A satellite that fails while it receives its layers”

A satellite whose disk is full, that times out or closes the connection while its layers are sent is left out, and the model is placed again without it:

A satellite’s errors are named as such (satellite pc3 (192.168.1.30:9090): …), never as the model file’s (invalid file is kept for a GGUF that cannot be read). It is not asked again for that model for 10 minutes, or until it restarts. The load fails only when no node can run the model. A satellite that announced too little room gets fewer layers from the start, and the plan says so: pc3: 2.10 GiB free in its cache, 4.50 GiB needed for layers 31-39: given layers 36-39 (2.00 GiB); --cache on a bigger drive, or a larger --cache-max, for more. Its card on the Mesh page says it too: Layers 36–39: limited by its cache (2.10 GiB free, 4.50 GiB needed for layers 31–39).

The satellite says why it cannot take its layers, and the master repeats it with what to do: no room in its cache, a write its drive refused (cannot write D:\inga-cache\…\blk.031.bin.part: …, with the file), no memory for a message, a chunk changed on the way, or an internal error. Each is also a line in the satellite’s own terminal and log, with the bytes received:

A send that fails is tried once more while the satellite still announces itself, resuming from the chunks it kept (a layer half received is not sent again); a second failure leaves it out, with the reason:

A satellite closes without saying why only when it could not: its process ended, its PC slept, or the network dropped. Check, in this order: its terminal, or ~/.cache/inga/logs/satellite.log on it (the satellite writes its lines there, with a crash’s), or the Log button of its card while it runs; that inga satellite still runs; the firewall on its TCP port. A satellite of Inga 0.46.0 or older (mesh protocol 10 or less) closes without a reason also when it hit an error: the master says so (the reason is unknown: it runs Inga 0.46.0 (mesh protocol 10), which closes without saying why), and the reason is in its terminal; updating it makes the master say it. A connection that breaks (the connection to pc3 broke …) or stops answering is the network, or the satellite stopped. A cache without room, or a drive that refuses writes, is not tried again: the remedy is on the satellite (--cache on another drive, a larger --cache-max). The card of a satellite that failed shows the reason and what to do, in the page’s language.

GPUs in the mesh

Section titled “GPUs in the mesh”

Every node uses its GPU for the layers it runs, as inga serve does on one machine:

  • Each node announces its GPUs. At start a satellite (and the master) opens the GPUs --device allows (auto by default: CUDA, then Metal, then a Vulkan GPU), reads the memory weights may take and measures its speed on a matrix; its start line names them: 8 threads AVX2, 9.50 GiB/s of weights measured; CUDA 0 GeForce GTX 1070 (8.00 GiB, 210.00 GiB/s). inga satellite --device cpu keeps a satellite on its CPU.
  • The placement plans each node like one machine. A node’s layers go first to its GPU’s memory (the attention and the KV cache first, then a mixture’s routed experts), the rest to its RAM, each at its own speed. A mixture of experts’ token costs only what it reads, its attention, its shared expert and k of its n routed experts, not the layer’s whole size. The plan’s line names the devices: this machine layers 0-5 (attention on Vulkan 0 Quadro P1000, experts in RAM), DESKTOP-1VFB0M9 layers 6-39 (6.80 GiB on CUDA 0 GeForce GTX 1070, the rest in RAM). A link slower than 2 ms gets a note: with GPUs a node’s share of a token is milliseconds, and a slow link may cost more than it saves.
  • A satellite runs its layers on its GPU. It plans the layers the master gives it like inga serve does (whole layers, or their attention with the experts in RAM; less when the GPU runs out of memory) and prints it: layers 6-39 on CUDA 0 GeForce GTX 1070: attention of layers 6-39. A GPU named by --device that cannot take them is an error the master sees; under auto the satellite falls back to its CPU and says why.
  • The master keeps its GPU for its own layers and the output layer. --mesh-local N still caps its layers.
  • Several GPUs in one node: --device cuda:0,cuda:1 (or cuda:0,vulkan:1, with --gpu-split) on a satellite or on the master splits the node’s own layers across its GPUs as inga serve splits a whole model, the first GPU taking the earliest; the output layer goes to one of them on the master only.
  • Every session has its cache on the satellite’s GPU: the master tells each satellite how many sessions it serves at once (--parallel), and the satellite plans its GPU’s memory for that many KV caches, not one.
  • A satellite whose GPU cannot take its layers (a --device cuda without the memory) is not left out: the master loads the layers there as soon as they are sent, and when the GPU fails them it places the model again with that satellite’s CPU only: DESKTOP-1VFB0M9: its GPU cannot run layers 6-39 of Qwen3.6-35B-A3B-Q4_K_M.gguf: ...; placing the model again with its CPU only.
  • A satellite reads prompts on its GPU: when the master runs a model whole and sends its prompts to a satellite (disaggregated prefill), the satellite loads it with its GPU, as inga worker --device does: prompts of Qwen3-8B-Q4_K_M.gguf read on CUDA 0 GeForce GTX 1070: layers 0-35 and the output layer. It announces its GPU’s prompt speed, so the master picks it over a CPU-only satellite.

Which node should be the master

Section titled “Which node should be the master”

When a model loads, the master also plans it with each other node as the master. When one would be more than 20 % faster, it says so, with how to make it the master (the master never moves by itself). A node up for less than an hour must be 50 % faster (a laptop that comes and goes is a poor master); among plans within 10 % of the fastest, a node that already serves the APIs (a door) is preferred, and a suggestion that moves the API’s address says so (it serves no API now: the users would connect to 192.168.1.30 instead):

On the Mesh page the suggestion is a banner with the comparison of each node as the master and alone. When the node may coordinate (an inga serve --mesh of the mesh, not a satellite) and has the model file, Make master hands the master’s place over:

The master names the node in its announcement; the node takes a priority above every node’s (the rule that wins the election) and is elected; the old master steps down once it is, and loads its models again on itself, while the new master loads its own split across the mesh. POST /api/inga/mesh/handover {"node": "DESKTOP-1VFB0M9"} does the same. A satellite cannot be handed the place: the banner shows the command that starts it as a master instead (inga serve MODEL --mesh home --priority 10). A master started with HTTPS (--tls self-signed or --tls-cert) announces its certificate’s fingerprint and inga mesh handover calls it over HTTPS trusting that certificate alone, with no warning to accept. The announcement is signed only when the mesh has a key (inga mesh key new, copied to every node): without one, inga mesh handover says that the certificate it trusts is whoever’s answers as the master on the LAN. Every node that hands over must be 0.46.5 or later: an older one calls an HTTPS master over plain HTTP and gets a 400.

GET /api/inga/mesh gives it in the model’s suggestion (the text) and suggested (the node, the expected tok/s, whether the handover can make it the master, the reasons and the comparison). inga mesh show --suggest MODEL compares, from what the nodes announce, the mesh with each node as the master and each machine alone, which is often the honest answer:

The figures are the placement’s estimates (the numbers above are the placement suite’s profile of three machines, not a measurement); compare them with inga bench on each machine.

3. See the mesh

Section titled “3. See the mesh”

Open http://pc1:8080/ and press Mesh in the side bar: the master in the middle, the satellites around it, each link with its round trip (green under 2 ms, yellow under 10, red above), a bar per model coloured by the node that runs each range of layers, every node’s details and APIs, and the decisions, newest first. A node that left is struck through for a minute. The same list holds the server’s API nodes (other servers and providers whose whole models it serves, use external models), where they are added, tested and removed.

From any PC of the LAN:

--json prints the same as GET /api/inga/mesh (with --suggest, its comparison in suggest). Each node lists its GPUs in devices (device, name, memory, the bytes free for weights, speed); on the Mesh page’s map a box shows them beside the CPU, with a memory bar per GPU next to the RAM bar.

Nodes of another version

Section titled “Nodes of another version”

A node of another Inga version is shown with both versions. Each Inga speaks a range of mesh protocols (0.46.5: protocol 11, and 10 and 9 still: 10 is the protocol of 0.41.0 to 0.46.0, 9 of 0.28.0 to 0.40.x), and two nodes work together when their ranges overlap: a connection runs at the lower one, and the newer node sends an older one nothing it does not know (its log, an update: said as not available on that node). So a 0.40 satellite is still used by a 0.41 master. A node with no protocol in common is not used, and the Mesh page shows a banner with the update: pc3 runs Inga 0.27.1 (protocol 7); this node needs protocol 9 or later (encrypted connections). Update it: followed by the release’s asset for its system (inga-windows-x86_64-0.41.0.zip), or docker pull ghcr.io/matteobaccan/inga:0.41.0 for a node in a container, and the release’s page. inga mesh show prints the same note under the node ((older, used) for one that is used), and the load’s last line says pc3 left out: version (Inga 0.27.1, protocol 7). GET /api/inga/mesh gives each node’s version_ok, version_used, session, version_note and update.

An older node says so, even when it is used: its card on the Mesh page reads Inga 0.38.1, this node 0.41.0: update (the newest version among the nodes, from their announcements: nothing is asked of GitHub), then the command that updates it by hand, for its system, to type on that machine with the satellite stopped:

  • Linux and macOS: gh api -H "Accept: application/vnd.github.raw" repos/matteobaccan/inga/contents/tools/install.sh > install.sh && sh install.sh --version 0.41.0 (add --prefix DIR for Inga in another folder, and sudo for a folder of root’s such as /usr/local/bin);
  • Windows, in PowerShell: gh release download v0.41.0 -R matteobaccan/inga -p inga-windows-x86_64-0.41.0.zip; Expand-Archive -Force inga-windows-x86_64-0.41.0.zip -DestinationPath (Split-Path (Get-Command inga).Source);
  • in a container: docker pull ghcr.io/matteobaccan/inga:0.41.0, then recreate it;

with the release’s archive for its system and the release’s page beside it. inga mesh show prints the same command under the node (by hand: …). A node only knows of releases the mesh runs; a satellite is updated by hand, with that command.

A node’s log, from the master

Section titled “A node’s log, from the master”

GET /api/inga/mesh/nodes/ID/log gives a node’s last lines (2,000, with their level, time, source and request id; API keys, bearer tokens and key= values masked before they are kept), read by the master over the mesh’s encrypted connection; ?after=, level=, q= and request= filter them, download=1 gives a text file. GET /api/inga/mesh/log?request=ID merges every node’s lines of one request by time: the master tells each satellite the id of the request its layers run for. A node of Inga 0.40 or older answers log not available on Inga 0.40.0.

4. When a satellite leaves

Section titled “4. When a satellite leaves”

Unplug pc2 in the middle of an answer:

The answer goes on where it was. A satellite with room is chosen first; when none has room, the master runs the layers itself (a stand-in worker in its own process). The inputs replayed are kept up to 256 MiB per conversation; a longer one stops that answer and the next request starts over.

Options

Section titled “Options”
Option Where Meaning
--mesh NAME serve, satellite, mesh show the mesh (satellite and show: default inga)
--port N / --mesh-port N satellite / serve the mesh port, 9090 for both (UDP announcements; a satellite’s TCP for the master); a default taken moves to the next free one
--peers H[:P],... all the other nodes (never this one) to announce to besides mDNS, at their mesh port (default 9090)
--no-mdns all --peers only
--advertise IP serve, satellite the address announced (default: the LAN interface’s, virtual adapters left out)
--priority N serve, satellite higher wins the election
--roles R,... serve, satellite door, coordinator, compute (serve: all; satellite: compute)
--node-name NAME serve, satellite the name shown (default: the host name)
--mesh-key FILE|- serve, satellite, mesh show the mesh key, from a file or standard input (also mesh.key; default: the key kept by inga mesh key new or import for the mesh’s name, else none)
--mesh-wait S serve, mesh show seconds to wait for the others, at most (default 3; serve: less once every --peers entry answered and the --mesh-expect nodes are there, measured)
--mesh-expect N serve, mesh show the wait ends once N other nodes are there with their measure
--mesh-local N serve the master runs at most N layers (0: a door that only embeds and samples)
--mesh-prefill auto|off|NAME serve the satellite that reads the prompts of a model the master runs whole (default auto: the fastest measured prompt speed, 1.5x the master’s at least; a name makes the master run the model whole; see disaggregated prefill)
--device D satellite where its layers run: auto (its best GPU), cpu, cuda[:N], vulkan[:N], metal[:N] (inga serve has its own --device)
--suggest MODEL mesh show MODEL’s expected tok/s with each node as the master and each machine alone
mesh handover NODE (command) the master hands its place to NODE (--mesh, --peers, --mesh-wait to find it; --api-key its key)
--cache DIR satellite where the parts are kept (default ~/.cache/inga/cache/mesh); checked at start
--cache-max SIZE satellite the most the cache keeps (default: 80% of its drive’s room)
--cache-list, --cache-clean MODEL satellite list the cache, or remove a model (--all: every one), and exit
--load-wait D serve how long a request waits for a model being loaded (default 120s), then 503
--exit-on-load-error serve stop (exit 1) when the first model fails to load, instead of staying up

Good to know

Section titled “Good to know”

The mesh places one master’s GGUF model by layers on CPUs and GPUs, on a LAN. A new master after a handover must hold the model’s file, and the conversations start over; a satellite that joins late is used when the model is placed again, between requests. A node with the key is trusted: it sees the activations of the layers it runs.

Troubleshooting

Section titled “Troubleshooting”

When the nodes do not see each other

Section titled “When the nodes do not see each other”

Check in this order:

  1. The address each node announces (its start line): a LAN address, not a virtual adapter’s (see below).
  2. --peers: the other nodes, never this one. A node whose --peers names its own address and port stops at start: 10.11.4.149:9090 is this machine (CYBERSPACE): --peers names the other nodes, e.g. the server at its --mesh-port. A listed peer that has not answered after 10 s is said, every minute while it lasts: 10.11.4.154:9090 has not answered in 10 s: a wrong address, the node not started, or a firewall (on Windows: allow inga.exe on private networks); a node found at that address on another port gets the port to give instead, and … answered after N s follows when it finally does.
  3. The firewall: on Windows, a network marked Public drops the mesh’s packets without a word on either side; the node says so at start (the network of 10.11.4.149 is Public: …): mark it Private (Settings > Network & Internet > the network’s properties), or allow inga.exe. On Linux the node names the ports to open when ufw or firewalld is active. Inga never changes a rule.
  4. A satellite seen over UDP whose TCP port does not answer: the master says pc3 (192.168.1.30:9090) is seen over UDP but its TCP port 9090 does not answer: a firewall on pc3 lets the announcements through and blocks the connections (Windows: allow inga.exe on private networks, TCP 9090), or … is closed when the port refuses the connection (the satellite is not listening there, or listens on another --port). It is left out and the load goes on.
  • No other node found: multicast does not pass (Wi-Fi isolation, a firewall, a VPN): give --peers (inga satellite --mesh home --peers pc1, or the satellites’ addresses on the master); a firewall must let UDP 5353 and 9090 through, and TCP 9090 to the satellites.
  • The start line shows a virtual address (172.17.x.x on Windows with WSL or Hyper-V, 172.17.0.1 with Docker): the node says the address of a virtual adapter when no other interface is up. Check the network cable or Wi-Fi, or give the LAN address with --advertise IP (ipconfig on Windows, ip addr on Linux).
  • mDNS is off: port 5353 cannot be shared: another program holds the port without sharing it; use --peers.
  • cannot bind UDP port 9090: a port given by hand is taken by another node (or inga worker) on this PC: give it another --port. Without one, the node takes the next free port by itself.
  • A satellite is listed but not used: the master says why (another protocol version, not reachable, or not worth its round trip), and the load’s last line lists every satellite’s outcome. Check inga mesh show.
  • the master has not sent every part: the transfer was cut; load the model again, only the missing chunks travel.
  • … closed the connection after … without saying why: the satellite’s process ended or the network dropped while its layers were sent; the master tried once more. Read the satellite’s terminal or ~/.cache/inga/logs/satellite.log on it, check that inga satellite runs, and its firewall’s TCP port (see “A satellite that fails while it receives its layers”).
  • no room in …: the satellite’s cache is on a drive too small for its layers, or at its --cache-max with the layers of a loaded model. Start it with --cache DIR on a drive with room, or a larger --cache-max. The master leaves it out and goes on without it.
  • the drive X: does not exist at the satellite’s start: --cache names a drive this PC does not have.
