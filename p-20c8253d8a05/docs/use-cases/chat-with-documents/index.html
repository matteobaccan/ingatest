Chat with documents: PDF, Word, Markdown and text files

What you get

Section titled “What you get”

Attach a PDF, a Word document (DOCX), an HTML page, a Markdown or a text file to a chat message and ask about it. Inga reads the file itself (pure Rust, nothing leaves the machine) and gives the model either the whole document, when it fits in a third of the model’s context, or, for a longer one, the passages closest to your question: the document is cut into chunks of about 500 tokens by headings and paragraphs, each chunk is embedded once by an embedding model (BERT encoders such as nomic-embed-text or BGE-M3), and the closest chunks are given to the model numbered, so the answer cites them by file and place ([2] → report.pdf p. 12, notes.md#3-costs, todo.txt:12-40). The answer also says which of the two Inga did, and why.

Each chunk keeps where it is in its file: its heading path (Report › 3 Costs › 3.2 Energy, embedded with it), the anchor of its heading as GitHub makes them (#32-energy), its page and, for text and Markdown files, its lines in the file. A heading of level 1 or 2 always starts a chunk; Markdown’s fenced code is never cut at a blank line. A Markdown file’s front matter (--- lines with title, tags, created…) is not text: it is kept as typed values for filters (dates as dates, lists as lists). Each dated bullet of a timeline (- 2025-03-14: ..., bold or not) is a chunk of its own, with its date.

The same works through the APIs: OpenAI file parts, Anthropic document blocks, Responses input_file parts, and inga_documents in any of them (Ollama’s too).

Documents you ask about again and again go into a collection: a named set of files read, cut into chunks and embedded once, kept on the server (~/.cache/inga/store, beside the memories). A chat picks its collections with its Collections button, and an API request names them in inga_documents (see 5. Keep documents in a collection).

Requirements

Section titled “Requirements”
  • Windows, Linux or macOS; any x86-64 or ARM64 CPU (or a GPU, see run-on-an-nvidia-gpu.md).
  • A chat model, and for long documents an embedding model (about 300 MB to 1.2 GB). Without an embedding model the chat model embeds the chunks itself: it works, but more slowly and with worse retrieval.
  • The documents: PDF files with a text layer (a scanned PDF is images only: Inga does not read text in images), DOCX (not the old .doc), HTML, Markdown or text, up to 11 MB each in the web UI (16 MB per request through the APIs).

1. Get Inga

Section titled “1. Get Inga”

Download the archive for your system from the Releases page and put inga on your PATH (details); inga --version checks it.

2. Get a model

Section titled “2. Get a model”

A chat model with a context large enough for your documents; for example:

And an embedding model, chosen once in the web UI: the Models tab’s Embedding model section proposes nomic-embed-text v1.5 (English) or BGE-M3 (multilingual), and Download and use downloads and chooses it (see embeddings-reranking-and-classification.md). The choice is kept in ~/.cache/inga/settings.json, and Inga uses it for documents and for /v1/embeddings requests that name no model.

3. Start the engine

Section titled “3. Start the engine”
  • --ctx sets how much the model reads at once: a document up to a third of it (about 5,400 tokens, some 15 pages, here) goes in whole.
  • The embedding model you choose loads beside the chat model and does not count against --models-max: it never unloads the chat model, and the log says where it went and how much memory it holds.

Open http://127.0.0.1:8080/.

4. Check that it works

Section titled “4. Check that it works”

In the chat, Attach (the + in the message box) → File (or drop the file on the message box) and pick a PDF or DOCX file: it waits above the box as a Document · read by the server card. Type a question and send. Under the answer:

  • In the prompt, whole: report.pdf — the document fitted in a third of the context and the model read all of it, with [page N] marks;
  • or 4 excerpts of report.pdf, the closest to the question (embedded by nomic-embed-text-v1.5): the documents are longer than a third of the context — open it to see each excerpt’s number, page and similarity; the answer cites them as [n].

The document stays with its message: every later question in the chat retrieves the passages closest to that question. The first question on a long document embeds it (a 300-page PDF is about 1,000 chunks: tens of seconds on a CPU with a small encoder); the next ones reuse the embeddings (the server keeps the last 16 documents).

Text and source files that fit in a third of the context still go into the message as they are, as before; longer ones are sent to the server like documents.

Through the OpenAI API:

The answer’s message holds inga_documents:

(streamed, it comes in the chunk after the first). Any API also takes the documents in inga_documents, given with the last user message:

Anthropic’s document blocks ({"type": "document", "source": {"type": "base64", "media_type": "application/pdf", "data": "..."}, "title": "report.pdf"} or a text source) work too.

5. Keep documents in a collection

Section titled “5. Keep documents in a collection”

Open the Documents page (in the left bar). Collections need the embedding model: without one the page says so, and Choose an embedding model opens the Models page’s Embedding model panel. In the New collection, or add to one box, write a collection’s name (Manuals), then choose: Add files… picks files from this computer, indexed once, Add folder… copies a whole folder of this computer, and Map a server folder… keeps a folder of the server in sync (below); all wait for the name. Add folder… first says how many files Inga reads (PDF, Word, HTML, Markdown, text), their size, the files it skips by type and any over 24 MiB, and sends nothing until you confirm; each file keeps its path in the folder (Manuals/sub/plan.docx), a file that fails is listed at the end without stopping the rest, and the copy is read once: to follow changes, map the folder instead. Each file is read by the server, cut into passages and embedded, one at a time (a 300-page PDF takes tens of seconds on a CPU). The page lists each collection with its files, their kind, pages, passages, size and date, 10 to a page (10, 25 or 50 in Files per page; first, previous, next and last under the list, with 1–10 of 2,387); the search box above the lists keeps the files whose name or folder holds every word written, in any case. The page and the search are kept on a reload of the tab. Add files adds more to a collection, Delete deletes one file, Delete the collection a whole one and Delete all every collection. A file added again under the same name replaces the old one. Through the API, GET /api/inga/documents?q=report&offset=50&limit=50 gives one page of each collection’s files that match, with total, matched, offset and limit (collection=NAME for one collection); without those parameters every file, as before.

Two columns say where each file stands and how it was read. State: indexed; to re-index (cut by an older version of the chunker, or a folder’s source file whose grammar version changed: the folder’s next sync reads it again, an uploaded one is added again); queued or in progress while its folder’s sync runs; error, in the error colour, for a file its folder’s last sync could not read, with the reason as the tooltip (a new file that failed is listed too, with no size, since nothing of it is kept). Indexing: tree-sitter · Rust for parsed code (the grammar and its version as the tooltip), plain text: no grammar for Ruby in this build for code cut as plain text (or why the parser fell back), and text for documents with how their text was taken (text · PDF text layer, text · DOCX body, text · HTML visible text, text · Markdown); an uploaded file is text, since only a folder’s files are parsed. When some files are to re-index or in error, a list beside the search shows only those (All states, To re-index (N), Error (N)); through the API state=outdated or state=error, each file’s state and indexing, and each collection’s unread files and states counts. inga docs status NAME --files prints the same in the terminal.

Every column sorts: click its header (or Tab to it and press Enter) to sort the files by it, again for the reverse order; the arrow beside the header says which. The server sorts every file of the collection, not only the page shown, then cuts the page (back to the first one on each new sort); State sorts the errors first, then the files to re-index, those queued or in progress, the indexed ones last, and Indexing by method, then language. Ties go by name. The files a folder’s sync could not read stay at the top of the first page, sorted the same way among themselves. Each collection keeps its sort on a reload of the tab. Through the API, sort= name, kind, pages, passages, size, added, state or indexing with order=asc or desc (another value is refused with a 400).

In a chat, Collections opens the list of collections: tick the ones this chat uses (the choice is kept with the chat; the button then reads Collections (1)). Every message then gets the passages of those collections closest to it, beside the files attached to the chat, and the report under the answer names each excerpt’s collection, file and page: 2 excerpts of Manuals, the closest to the question (embedded by nomic-embed-text-v1.5).

Through the API, the same: add a file with POST /api/inga/documents, then name the collection in any chat request.

The answer’s inga_documents is in excerpts mode, its files holds the collection ({"name": "Manuals", "kind": "collection", "files": 1, "chunks": 40}) and each excerpt says its collection, document, page and pages. GET /api/inga/documents lists the collections and their files, DELETE /api/inga/documents/ID deletes one file, DELETE /api/inga/documents?collection=NAME one collection, DELETE /api/inga/documents all of them; inga data list documents and inga data rm documents:ID do the same from the command line, and the Storage page shows them.

The chunks are embedded by the embedding model chosen when the file was added; after choosing another one, the first question on a collection embeds it again with the new one.

Reranking. When a reranker is given (docs.reranker in inga.toml, loaded when first needed), or one is loaded on the server (a model whose use is reranker, such as bge-reranker-v2-m3, loaded with Load in the Models page or named to inga serve), the best chunks are ordered again by it before the excerpts are picked: the first 32 (docs.rerank_top) of the collections’ search, with their file’s name and heading, and those of the attached files. The answer’s inga_documents names it in reranker, and each excerpt has its rerank score beside its similarity. A reranker that fails (a chunk longer than its context) is said in rerank_error, and the search’s order is kept. See 7. How the collections are searched.

In the terminal and in scheduled tasks: #name. Write # and a collection’s name in the prompt: inga run and a scheduled task then answer from that collection, with nothing else to set.

  • #name names a collection only when one has that name (in any case): #1, #TODO, C# and page.html#part stay text. A name with spaces is written #"Contratti 2026"; \#wiki is the text #wiki. The text keeps its #, so “compare #contratti with #wiki” still reads well. A #word one letter away from a collection is said once: “no collection contrati; did you mean contratti?”.

  • inga run --docs a,b names collections for every message (with the #names, the union). The closest excerpts go into the message, the encoder is the web UI’s embedding model (else the one inga docs add embedded the folder with), and a line on stderr lists the excerpts: note: 4 excerpts of contratti in the prompt (hybrid search, embedded by nomic-embed-text-v1.5): [1] contratti › rossi.pdf p.7; ....

  • A scheduled task names its collections in its tools, "tools": ["documents:contratti"] (--docs contratti); a bare documents is refused, since naming a collection is the permission. #name in its prompt works too. A collection that is gone fails the run with “no collection contratti”: a task that decides must not decide without its data. The run’s record keeps the documents report.

  • Two modes: context puts the excerpts into the prompt (the default of the chat and inga run), tool gives the model the document tools to search and read as it needs (the default of scheduled tasks, documents_mode; inga run --docs-mode tool, "inga_documents_mode": "tool" in a request). A model whose chat template takes no tools gets the excerpts instead, and Inga says so (on stderr, in the run’s warning, in the answer’s inga_documents: documents_mode_asked, documents_mode_note).

  • The document tools (tool mode) work on the collections the prompt names and no other; a call naming another is refused with “not referenced by this prompt: …”, and with no collection named there are no document tools:

    • documents_list(): the collections named, their sources (folders, uploads), files, chunks, last sync and encoder.
    • documents_search(query, collection?, where?, k?): the hybrid search of the collections (all of them fused by rank, or one), 8 hits by default (at most 20), each with its file and place (#anchor, :12-40, §heading, p. 4), a bullet’s date, a snippet of 600 characters and what to pass to document_read; where filters as inga docs search --where does.
    • document_read(file, section | page | lines): a file as collection › path (or the path alone), read from the store with numbered lines (the file’s own lines for text and Markdown, its front matter at the top): a section (§7, #revisione-prezzi, a heading’s title), a page, lines (120-180), or the whole document (its outline and its start when it is long). At most 12,000 characters a call (docs.read_chars in inga.toml), cut at a line with the lines to ask for next.
    • documents_grep(text | regex, collection?): the lines that contain a text (any case unless it has a capital) or match a regular expression (200 characters at most, bounded backtracking, 2 seconds), 50 lines at most, each collection › path:line; for names, codes and numbers an embedding misses.

    Each result is numbered as a source ([n], one number per file, shared with web_search and fetch_url), at most 8,000 characters (document_read aside), and each call is an inga_tool event of the stream (the web UI shows it under the answer) and a line on the terminal (inga: documents_search({"query": ...}) -> ...; in inga run, [documents_search {...}] on stderr). The text read is what was indexed: a file deleted from its folder since the last sync still reads, and says so.

  • The OpenAI, Anthropic and other compatible APIs never read #: a client’s text is its own. They keep inga_documents, which takes several collections.

  • Each excerpt is cited with its collection first and its place: contratti › rossi.pdf p. 4, wiki › models/x.md#timeline (cite in the answer’s inga_documents, with heading, anchor, lines and a bullet’s date). The web UI’s # picker comes in a later release.

  • An API request filters a collection with where, as inga docs search --where does: "inga_documents": [{"collection": "wiki", "where": "category=models, tags=video"}].

6. Keep a folder in sync

Section titled “6. Keep a folder in sync”

A collection can also follow a folder: notes, a wiki, a code repository. From the command line (the server need not run; a running inga serve sees the changes):

docs add reads the folder at once with a progress line (42 % · 312 of 1204 files · 5210 chunks · src/store.rs · ~6 min left). Without --embed-model the web UI’s embedding model is used. The folder remembers the model its files were embedded with: inga docs sync needs no --embed-model (and loads no model when nothing changed); given another one, it says so, embeds the new and changed files with it and tells how to embed them all again (inga docs sync notes --full --embed-model M). Only the files the globs take are read (--include and --exclude, written as in .gitignore), the folder’s .gitignore and .ingaignore files apply, and .git/, target/, node_modules/, .obsidian/ and .trash/ are left out; binary files and files above 64 MiB are skipped. Each file is kept with its size, time and SHA-256: the next sync opens only the files whose size or time changed, reads again only those whose bytes changed, and removes the files gone from the folder with their passages; in a changed file, the passages that did not change keep their vectors, so editing one section of a long document embeds only that section again. inga docs status says what a sync would do now; inga docs rm notes ~/notes stops following the folder. Files can be added without a folder too, as the Documents page’s uploads: inga docs add contracts rossi.pdf bianchi.docx.

A big first sync, faster or gentler. Indexing runs at low priority on half the logical CPUs, so the computer stays responsive while a big folder is read; the first line says so (indexing at low priority (nice 10, disk best-effort 7), 4 threads), and so does each folder’s report. On Linux that is nice 10 and the lowest best-effort disk priority of the thread, on macOS the background QoS class (the efficiency cores on Apple silicon), on Windows the threads’ background mode. If the system refuses it, the sync goes on at normal priority and says why. To go faster on a computer you are not using, inga docs sync notes --full-speed (or docs add ... --full-speed) indexes at normal priority on every thread; to be gentler still, fewer threads: inga --set docs.ingest_threads=2 docs sync notes, or ingest_threads = 2 under [docs] in inga.toml, which inga serve’s syncs follow too. The server’s syncs always run at low priority, and lower its embedding model’s threads, which it shares with the searches: they stay so while the model is loaded (Linux lets no ordinary user raise them again), which only slows a search while the computer is busy with something else.

To see what a question finds, as the chats search it:

Each passage comes with its citation (notes.md#3-costs, todo.txt:12-40, report.pdf p. 4), its heading path and a bullet’s date; --explain adds its rank in the vectors’ list, in the words’ (BM25) list and in the dates’ list, its cosine and the reranker’s score, and the time of each step: the tool to see why a passage came first, or did not come.

--where keeps only the passages whose file or bullet meets its conditions, before they are scored: KEY=VALUE, !=, <, <=, >, >=, separated by commas. A key is one of the front matter’s (tags, category, created…), path (a glob, as .gitignore writes them), kind (Markdown, PDF), title, heading or date (a bullet’s date, else the front matter’s). Dates compare as dates at the value’s precision (date=2026-08 is August 2026), numbers as numbers, the rest ignoring case; a list matches when one of its items does.

After an update of Inga. Each file remembers the version of the chunker that cut it. When Inga’s chunker changes (version 2 added the heading paths, anchors, lines, front matter and dated bullets), a sync reads the folders’ files again even if they did not change, and says so (note: 120 files are read again: Inga's chunker changed ...; cut again by the new chunker in the report); the passages whose heading and text did not change keep their vectors. inga serve does it at the next sync of a folder synced every so often or watched; inga docs status says re-index needed for the others (inga docs sync NAME), and an uploaded file is added again. Until then the old chunks are searched as before, without the new places, dates and filters.

inga serve syncs the folders added with --every 1h, and watches those added with --watch (their sizes and times every 5 seconds; a change is read once it stood still for one look, so a file being saved is not read half-way). A sync waits between files, and between the passages of a file, while a chat answer is being generated. An inga docs sync of a folder that inga serve is syncing (or the other way round) says who holds it and waits for it to end, then does what is left. The web UI’s Documents page shows each folder’s last sync, or the progress of the one running, with Sync now, Cancel and Stop syncing; Map a server folder… adds one, but only under the folders the server was given with --docs-root DIR (docs.roots in inga.toml): the API never reads a folder its caller names elsewhere. Without them, the folder is doc beside the inga executable, made at start with a README.md that says what it is for.

The job’s events (mode, scan, file, chunks, error, paused, done) carry the percentage, the files and chunks done, the time left and the errors; POST /api/inga/documents/sync {"collection": "notes"} syncs now and DELETE /api/inga/documents/jobs/ID cancels.

How well does it find things? inga eval rag --questions FILE.toml indexes a folder into a throw-away collection, asks the questions of the file and prints recall@5/10/20, MRR@10, nDCG@10 and the search times, per kind of question (tests/rag/inga-code.toml is a sample on Inga’s own sources, tests/rag/wiki-synth.toml a synthetic wiki). Keep a questions file for your own folder outside it, and compare embedding models and searches on it: --mode dense, bm25, hybrid or hybrid+rerank (with --rerank-model M), and any [docs] key with --set (inga --set docs.hub_penalty=1 eval rag ...). --collection NAME measures a collection already indexed, without reading the folder again.

7. How the collections are searched

Section titled “7. How the collections are searched”

Each question is searched two ways, and the two lists are fused (docs.search = "hybrid", the default):

  • By meaning: the question’s vector against the chunks’ vectors (the embedding model’s; exact, every chunk compared). It finds paraphrases, but an English-only model reads Italian poorly, and a rare name, code or date counts for little in a vector.
  • By words (BM25): every chunk’s words in an index kept in step with the folder. Identifiers are split and kept whole (embed_missing is found by embed_missing, by embed and by missing; so are camelCase, src/cli.rs, Store::search, dates such as 2025-03-14 and codes such as MRV-3); words lose their case and accents (perché → perche), Italian and English stop words are left out (an acronym such as PUE or CI is kept), and plurals and Italian endings are folded (aziende, azienda). A word in the file’s title (front matter’s title, else its first # heading), its path, the chunk’s heading path or the front matter’s values weighs more than one in the text.
  • By date: when the question names a date (2026-01-20, December 2025, 14 dicembre 2025, Dec 3, 2025), the timeline bullets of that date (or month) make a third list, ordered by their words; a year alone is too wide and is not taken.
  • Fusion: each chunk scores 1 / (60 + its rank) in each list (docs.rrf_k), the word list’s share multiplied by docs.bm25_weight (2 by default: with an English-only embedding model the words found more on Italian and code). inga_documents says which retrievers found each excerpt (retrievers: dense, bm25, date) and its rank, and search gives the settings and the time of each step.
  • Sections: when two or more chunks of one section (a heading of level 1 or 2) are found and the section is at most 1,500 tokens, the model gets the section whole, once, at the best chunk’s place (section: true in inga_documents).
  • Several collections: each is searched and fused as above, and their lists are fused again by rank (1 / (60 + its rank in its collection)): a score of one collection is never compared with another’s, which may have its own embedding model and its own word statistics.

Long files and index pages. A change log or an index page of hundreds of chunks holds, by chance, a chunk that looks close to almost any question. Each list keeps at most 3 chunks of a file (docs.per_file), and a file’s many chunks lower each one’s score (docs.hub_penalty, 0.5 by default: the best of n chunks is expected to stand √(2 ln n) spreads above the others, and that much of it is taken back). Pages that only list other pages are better left out of the folder: inga docs add wiki ~/wiki --exclude log.md --exclude index.md (or add the excludes later: inga docs add again on the same folder, with its include globs and the new excludes; the next sync removes those files).

docs.search = "dense" or "bm25" use one of the two; the reranker, when there is one, orders the first docs.rerank_top fused chunks again (docs.rerank_mode = "fuse" fuses its order with the search’s instead of replacing it). A question’s vector is kept for the next time it is asked (the last 1,024 questions).

Options worth knowing

Section titled “Options worth knowing”
Option Effect
--ctx N The context: documents up to a third of it go in whole, and the excerpts fill that third.
--models-max N Chat models kept loaded (1); the embedding model and a reranker are not counted.
The web UI’s Embedding model The encoder that embeds the chunks and the questions (embedding_model in POST /api/inga/settings); collections need it.
A loaded reranker, or docs.reranker Orders the best chunks again before they are picked (docs.rerank_top, docs.rerank_mode).
docs.search hybrid (default), dense or bm25: how the collections are searched; docs.rrf_k, docs.bm25_weight, docs.candidates, docs.per_file and docs.hub_penalty tune it (config).
--pooling How the embedding model pools (auto follows the model).
--docs-root DIR A folder under which the web UI and the API may add folders kept in sync (repeatable; docs.roots); without one, doc beside the executable.
docs.ingest_threads, --full-speed The threads that index a folder, at low priority (half the logical CPUs by default); inga docs sync --full-speed indexes at normal priority on every thread.

Troubleshooting

Section titled “Troubleshooting”
  • “… has no text layer: its pages are images (a scan?)”: the PDF is scanned. Run it through an OCR program that adds a text layer (or print it from a viewer that does) and attach the result.
  • “the PDF is encrypted”: Inga does not decrypt PDF files; print it to a new PDF, or save it without a password.
  • “the old Office format (.doc, .xls, .ppt) is not read”: save it as DOCX or PDF.
  • “… is N MiB: documents up to 64 MiB are read” or a 413 from the server: the request is limited to 16 MiB; split the document.
  • Odd text from a PDF (words glued or out of order, tables read by columns): Inga reads the text layer as the PDF draws it; multi-column layouts and tables come out in the order the file draws them.
  • Slow first answer on a long document: it is being embedded, chunk by chunk; choose a small embedding model. A file you ask about often is better kept in a collection: it is embedded once.
  • “the collections of documents need an embedding model” (409): choose one in the Models page’s Embedding model panel, or POST /api/inga/settings {"embedding_model": "hf://..."}.
  • “no collection NAME” (400): the collection was deleted, or its name is spelled otherwise (names are case-sensitive); GET /api/inga/documents lists them.
