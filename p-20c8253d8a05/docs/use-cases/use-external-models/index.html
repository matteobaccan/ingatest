Use external models through Inga

Supported since: 0.26.0 (API nodes, model_map, inga connect); 0.26.5 (routes, a global fallback list, best-by-eval)

What you get

Section titled “What you get”

inga serve serves, next to its own models, the models of other servers reached through their API — another inga serve, Ollama, LM Studio, vLLM, llama-server — and of providers such as OpenAI, Anthropic, OpenRouter or Groq. Inga calls these servers API nodes. Each node’s models appear as NODE/MODEL (groq/llama-3.3-70b-versatile, claude/claude-sonnet-4-5, work-pc/qwen3-30b-a3b) in every API Inga serves (OpenAI, Anthropic, Ollama, LM Studio, KoboldAI) and in the web UI’s model menu, with a cloud, local network or house (this machine) icon, their capabilities, context and price.

  • One endpoint. A client written for one API reaches every model: a request in the API the node speaks is passed through as it came (the answer byte for byte, its model set to NODE/MODEL); any other is translated — OpenAI ⇄ Anthropic, tools, images, reasoning (reasoning_effort ⇄ thinking budgets) and usage included.
  • No local model needed. inga serve with no model and a few nodes is a web UI and an API in front of external inference.
  • Coding agents unchanged. Claude Code, Codex, OpenCode or Aider pointed at Inga keep their own model names; model_map sends each one to the model you choose, local or remote, and inga connect prints what to set.
  • Keys stay on the server. A key comes from an environment variable or from an encrypted store; it is sent to its node only and never appears in a log, a listing, an answer, the browser or inga data.
  • Inga says what answered. The answer’s model, the X-Inga-Node and X-Inga-Route headers, inga_route in translated answers, and the web UI’s footer name the node and the rule that chose it.

What was checked, and how: every part runs in the test suite against mock OpenAI and Anthropic servers and a second inga serve (passed through, translated, streamed or not, tools and images, keys searched for in every log line, listing and answer). The real providers are checked by the maintainer with tests reading INGA_TEST_OPENAI_KEY / INGA_TEST_ANTHROPIC_KEY (cargo test --test api_nodes -- --ignored): no real provider was called while this was built.

Requirements

Section titled “Requirements”
  • For a provider: an account and an API key. For a server of yours (Ollama, LM Studio, another Inga): its address, reachable from this machine.

1. Get Inga

Section titled “1. Get Inga”

Download the archive for your system from the Releases page and put inga on your PATH (details); inga --version checks it. This guide needs 0.26.0 or later.

2. Add a node

Section titled “2. Add a node”

Inga knows 113 providers and servers (presets): their address, their API and the variable their key is read from. The whole list, with each provider’s documentation, is in api-node-presets.md.

A * marks a provider whose model list does not name its models: add --models M,.... A {NAME} in a URL is your own part (an account, a resource, a region): inga node add reads it from the variable NAME, or asks for it on a terminal, or takes the whole URL (inga node add cloudflare https://api.cloudflare.com/...). The -anthropic presets are the Anthropic-compatible endpoints some providers offer for Claude Code (DeepSeek, Moonshot, Z.ai, MiniMax, Fireworks…).

5. Coding agents: model_map and inga connect

Section titled “5. Coding agents: model_map and inga connect”

Coding agents ask for fixed names (claude-opus-*, claude-sonnet-*, gpt-5*). model_map in nodes.json turns them into the models you choose — exact names or globs; the most specific pattern wins, * last:

local/NAME names a model of this server. A name nothing maps and no model has is not answered by a silent default (unless * is mapped).

inga connect prints what the tool needs, in your shell’s syntax, then sends one test request and says which model answered; it starts no program:

inga connect codex, opencode, aider, qwen-code and openai-sdk print OPENAI_BASE_URL (or aider’s OPENAI_API_BASE) and OPENAI_API_KEY, pi the provider for its models.json; --shell fish|powershell|cmd, --write FILE (to source it), --model M, --url URL, --no-test. The server’s own key (inga serve --api-key) is printed as a reference to $LOCAL_LLM_API_KEY, never as the key.

inga connect TOOL --run starts the tool with these settings itself, for that run only (--serve MODEL starts a server when none answers); with several models and no --model, the tool’s own names are used when model_map maps them. One page per tool: docs/integrations/.

6. Keys

Section titled “6. Keys”
  • Environment variable (key-env=VAR, --key-env VAR, a preset’s default): nothing on disk; the variable must be set where inga serve runs (the service’s environment, Docker secrets).
  • Key store (--key-stdin, the Mesh page): ~/.cache/inga/secrets.json, each key encrypted with ChaCha20-Poly1305 under a machine key in ~/.cache/inga/secret.key, both readable by their owner only on Linux and macOS. This protects a copied nodes.json, a backup or a screenshot; it does not protect a key from someone using your account. On Windows the files are in your profile, with its permissions.
  • Never on the command line: --api-node ...,key=... and inga node add --key are refused.
  • inga data list nodes and inga data list secrets show the nodes and which ones have a stored key (never the keys); inga data clear secrets deletes every stored key.

7. Who may use the nodes: the server’s API keys

Section titled “7. Who may use the nodes: the server’s API keys”

The keys above are the ones Inga sends to the providers. Clients of inga serve use the server’s own keys: --api-key KEY (one key for everything) or the named keys of --api-keys FILE (serve many users and models explains the file). A node’s models are models like the others:

  • Adding, testing, enabling, disabling and removing nodes (/api/inga/nodes*, the Mesh page) are admin routes: team above cannot call them, ops can.
  • A key’s models names the nodes’ models as NODE/MODEL (a * at the end matches a prefix): team may use groq/... and the local qwen3... models, and gets a 403 for claude/.... A name model_map turns into a node’s model is checked as that model.
  • Requests per minute, tokens per day and the usage of GET /api/inga/keys count the requests answered by nodes as the local ones, with the tokens the node reports (or, when it reports none, estimated at 3.5 characters per token).
  • The client’s key is never sent to a node.

8. Privacy

Section titled “8. Privacy”

Every node is local (this machine), lan or cloud: its tags say it (tags=cloud), else its address does (127.0.0.1 is local, 10.x / 192.168.x / .local names are LAN, the rest cloud). Presets of providers are tagged cloud. inga serve --no-cloud leaves cloud nodes out entirely; --catalog local keeps the API models out of the client listings (they stay usable by name). Nothing is sent to a node you did not add.

10. Routes: one name, the best model for each request

Section titled “10. Routes: one name, the best model for each request”

A route is a name clients ask for in model, answered by the best eligible target of a chain: this server’s models, the nodes’ models, other routes. Routes live in ~/.cache/inga/routes.json (or inga serve --routes FILE), read again when the file changes; the Mesh page’s Routes section shows them, explains a request and edits the file.

For each request Inga:

  1. Leaves out the targets that cannot take it, and says why: a local-only request (X-Inga-Privacy: local-only, or the route’s "privacy") never goes off this machine, lan-only never to the cloud — no rule can change that; the policies (allow / deny lists of local, lan, cloud, api, a node’s name, tag:T, model:GLOB, matched by API key, header or route); the API key’s models; capabilities (an image, tools; a capability a node does not report counts as absent); the context (the prompt at 3.5 characters per token plus max_tokens); cost ceilings (if.max_cost_usd, or the route’s max_cost_usd: prompt tokens × the input price + max_tokens (4096 when not set) × the output price; a price unknown is never under a ceiling); a node disabled or whose key was refused; a target cooling down; a node at its max_concurrency.
  2. Ranks the rest with the route’s strategy: order (the default: the first eligible, then the next ones), least-busy (the fewest requests in flight), latency (the lowest time to the first token measured, a moving average), cost (the lowest estimated cost), weighted (at random by each target’s "weight"), affinity (the same conversation — the client’s user, X-Inga-Session, else its first messages — on the same target), classify (the request’s class picks one of classes: the route’s rules first, then its classifier, a small local model asked with Engine::classify, then built-in rules: an image, tools, the text’s category code, math or writing, a long prompt is hard), best-by-eval, cascade and ensemble (see below). {"any": [...], "strategy": "..."} makes a group of alternatives inside an ordered chain. A target may name another route (four deep at most; cycles are refused when the file is read), but a cascade’s steps may not reach an ensemble route, nor an ensemble’s a cascade: a route is one strategy at a time.
  3. Tries them in that order, then the global fallback list of nodes.json (unless the route says "global_fallback": false): a node that cannot be reached is retried with backoff; a 429 waits for its Retry-After when it is short (max_wait), else cools the node down for it; a 5xx (or Anthropic’s 529) goes to the next target; a context too long goes to a target with a larger context; a refusal by the provider goes back to you unless the route says "on_refusal": "next"; other 4xx go back to you. Failures in a row open a target’s breaker for cooldown.seconds, doubled at each re-open up to 15 minutes; then one request is let through. When every target is cooling down, the one that opened first is tried anyway.

The answer says what happened: X-Inga-Route (passed-through answers) and inga_route (name, class, failed: the targets that failed and why, fallback, splice, cascade, ensemble) name the target that answered and why it was chosen. Nothing reaches the client before the first token, so a failover before it only takes longer; after it, the answer ends with the API’s error, unless the route says "failover": "continue": the next target is then asked to continue the partial answer (Anthropic’s prefill, continue_final_message for vLLM and other OpenAI-compatible servers; this server’s own models cannot continue one yet) and inga_route.splice says where the answer changed hands.

Routes by your evals. A best-by-eval route sends each request to the target with the best score in its category — the newest inga eval run of each model (~/.cache/inga/evals; --set math, code, writing or your own sets) and the web UI arena’s votes (each model’s expected share of wins), averaged when both exist — among the eligible ones, then the others by score. The category comes from the route’s rules and classifier as for classify, else from the request’s text (code, math, writing, general); categories lists others. Re-run inga eval and the route follows (the scores are read again when the files change); the Routes section shows the table it uses.

Cascades: the small model first. A cascade route asks its first target (a small, fast, local model) and goes on to the next step only when the answer looks weak:

An answer of every step but the last is weak when it is empty, a refusal (“I can’t help with that”, “I don’t know”, also in Italian; "refusal": false turns this off), the mean log-probability of its tokens is under min_logprob (this server’s models always give them; an API node is asked for them, logprobs: true, only when min_logprob is set — Anthropic gives none), or the optional judge model grades it under judge_min (the evals’ judge prompt, a SCORE out of 10). With "stream": "hold" (the default) a streamed answer is held until it is judged, so you only ever see the answer kept; with "mark" it streams at once, and a weak one is followed by [inga: escalated (why)] and the next step’s answer. When every later step fails, the weak answer is given anyway. inga_route.cascade says what happened (answers: each judged answer’s verdict, its mean log-probability and the judge’s grade; escalated; saved_usd against the last step), the Routes section and GET /api/inga/routes → cascades the share escalated and the cost saved per route.

The threshold depends on the model and on your prompts: every judged answer’s mean log-probability is kept (no prompt, no text) in ~/.cache/inga/evals/cascade.jsonl, and once the first step has given 20 answers, inga route calibrate smart shows the share each threshold would send on, --share 20% the one that sends a fifth, and --write puts it into routes.json:

Several answers, one judge. An ensemble route asks one target of each of its steps at once — an any group is one step whose next target stands in when the first fails — then its judge (a model, not a route) gives one answer:

  • "mode": "pick" (the default, best-of-N): the judge grades each answer with the same prompt inga eval uses (0 to 10, SCORE: N) against the route’s "rubric" (by default: correct, complete, answering the question asked) and the best answer is given; equal grades go to the earlier step.
  • "mode": "write" (a mixture of agents): the judge gets your conversation and every answer, numbered, and writes the answer itself, streamed to you as it writes it.

The answers are not streamed while they are written: with pick the one chosen comes at once when the judge has graded them all. With one answer there is nothing to judge; when the judge cannot take the request (a local-only request and a judge in the cloud) or fails, the first answer is given and the answer says why. When no target of the ensemble answers, the global fallback list answers as for any route. It costs every answer plus the judge: inga_route.ensemble lists each answer (its text, tokens, time, cost and grade, which one was given) with the total cost, the web UI keeps them with the chat under the answer (closed until you open it), and the Routes section’s ensembles counts the requests, the answers given per target and what they cost. Use it where quality matters more than cost.

From the command line:

POST /api/inga/routes/explain asks the running server, which also weighs latency, load and breakers. Budgets (in currency, per key, node or route) are not applied yet: they come with the named API keys’ costs.

Troubleshooting

Section titled “Troubleshooting”
  • down: key rejected: the node answered 401 or 403; check the key (inga node test NAME).
  • the key of node X is read from $VAR, which is not set: set the variable where inga serve runs, or store the key: inga node add X ... --key-stdin.
  • the API node X has no model Y; its models: ...: the name after the prefix must be one the node lists (inga node models X), or in its models allow-list.
  • Audio, video, grammars, LoRA adapters, log-probabilities are not sent to API nodes through a translated request: they need a model of this server (a request in the node’s own API, such as response_format on /v1/chat/completions to an OpenAI node, is passed through as it is).
  • Documents and the memory are added to the prompt of this server’s own models only.
  • no target of R can take this request (...): every target of the route was left out; the list says why for each (inga route explain R -p ... shows it without sending anything).
  • every target of R failed: ...: each target was tried and failed; the list says how. GET /api/inga/routes shows the breakers that opened.
