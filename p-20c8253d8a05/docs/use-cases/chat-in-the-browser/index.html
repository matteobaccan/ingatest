Chat in the browser and manage models from the web UI

What you get

Section titled “What you get”

A chat page served by inga serve itself, with nothing else to install: conversations kept in your browser, answers rendered as Markdown, every sampler, images and audio, and a Models tab, as LM Studio’s, that searches Hugging Face, downloads models into the Hugging Face cache and loads them into the running server. Inga’s logo at the top of the left column opens Server: this machine, with the loaded models and live metrics.

The menu

Section titled “The menu”

The left column holds New chat, every page (Chat, Memory, Documents, Images, Decide, Schedules, Skills, Storage, Mesh, Models — just below Mesh, with its sections and Speed under it — and the Developer group under its heading: Server, Logs, API docs, CLI), and on the chat page your chats (Recents, with their search, export, import and share); at its foot the server the page talks to (a green dot, red when it does not answer) and Settings. In a low window the column scrolls. Images is the page that draws (see Images below). While the Models page is open its sections (Search, Installed, Embedding, Voice, Images) show under its entry, and while Images is open its modes (Create, Edit, Inpaint). Under 1025 px the column is a strip of icons and the chats a drawer (the ☰ button of the chat’s top bar); on a phone the pages are a bar at the bottom that scrolls sideways. The command palette (Ctrl+K) lists every page.

Images

Section titled “Images”

The Images page draws with an image model, loaded into the server beside its chat model (see generate-images.md): its picker lists this machine’s image models, and choosing one loads it there, with the load’s progress on the canvas, no restart (Load for the one chosen last; a load that fails says why, with Try again). When there is no room for both, the idle chat model is unloaded first and the page says so; it loads again at its next message. Without any image model it offers SD-Turbo (the fastest on a CPU) with Download and a link to the Models page’s Images section. Started with an image model alone (inga serve IMAGE_MODEL), the chat draws pictures too until a chat model is loaded. Under the canvas, Image models on this computer lists the ones Inga can draw with, each with its state (not loaded, loading, loaded and in use) and Load, and Find more image models opens the Models page’s Images section.

  • At the top the image model and the modes: Create (a picture from a prompt), Edit (a picture redrawn, image to image, with its strength) and Inpaint (a part repainted: paint the mask with the brush, the eraser and Clear mask).
  • On the left the prompt, the negative prompt (folded), the aspect ratio with its swap (portrait or landscape), the resolution (the longer side; empty: the model’s own), steps, guidance (CFG) and the seed (random when empty); Advanced holds the sampler (Stable Diffusion’s models), Flux’s guidance and the number of pictures (1 to 4). Only what is set is sent: the rest is the model’s. Ctrl+Enter or Generate draws; Stop cancels.
  • On the right the canvas: the pictures with Download (PNG), Edit it (the picture becomes Edit’s source) and Send to chat (a chat of its own with the prompt and the pictures, kept in this browser), and the line of their size, steps, guidance, seed and time.
  • The chat’s image mode still draws from the message box, as before.

The Models page’s Images section lists the recommended text-to-image models, fastest on a CPU first: SD-Turbo and SDXL-Turbo (one checkpoint each, hf://stabilityai/...; Stability AI’s repositories ask you to accept their licence and set HF_TOKEN), FLUX.1 schnell and Qwen-Image (kits: a transformer, a VAE and text encoders, GET /api/inga/kits). Each shows its size, whether it fits (its files plus what drawing takes, against the RAM or GPU memory free), its files with each one’s download bar, and Download, which takes every file; once here, the inga serve command that serves it (with a kit’s files by their options). Below, On this machine lists the image models found: in the Hugging Face cache (a single .safetensors checkpoint, a GGUF file of stable-diffusion.cpp or ComfyUI-GGUF, a diffusers repository) and in the model folders (A1111’s and ComfyUI’s checkpoints, diffusers folders).

Settings (the gear at the foot of the column) is a dialog: a search box and its sections, General (the version, the language, the keyboard shortcuts and the models in memory, each with where it runs and Unload), Appearance (the themes), Models and memory, GPU, Chat, Tools, Voice, Server and API key, Mesh, Storage and About; the sections that live on a page of their own have a row that opens it. Hover a row’s name (or give it the keyboard’s focus) for what it does; type in the search box to keep the rows that match, across the sections.

The composer is one box: the message, then a row with + (attach a picture, a file, a recording or a video), the approval chip, the tools (Web, Files, Memory, Collections), Skills (use the installed skills in this chat, the list, Manage skills…), Think (for a model that thinks: its model default, on, off or an effort), the microphone and Send, a round button that becomes a square Stop while the answer streams. The chip says how the tools’ calls are approved in this chat: Ask for all (“Ask for everything”: every MCP call not pre-approved and every change asks you first), Ask for changes (“Ask only for changes”, the default of a chat: what only reads — the web, the files, the documents, recalling memories, the MCP tools a server marks read-only — runs without asking; a file write, a change of the memory, a skill script and the other MCP tools ask) or Pre-approved only (“Only pre-approved tools”: a call runs only when inga serve --mcp-auto-approve or an “Always” answer allows it, the others are refused without asking). What reads and what changes, and how to take back an “Always”: use-mcp-tools.md, “Approval levels and the “always” kept”. An empty chat shows a greeting with the composer in the middle. A model that loads shows as a toast at the top right (its phase and percentage; × hides it); until the first token the answer says whether the model is loading or reading the prompt, and the mark at the top of the column moves with it: a slow breath while a model waits, its halves taking turns while it loads or reads, a beat at the pace of the tokens while it answers (still with the system’s reduced motion).

The chat has a top bar: the model, where it runs, its options (the sliders button: context, device, GPU layers, Thinking, the preset, the chat’s settings, the API key) and, on the right, the context used (hover it for the detail; its ring opens what fills it), a new chat, the chat’s settings, share and export.

Every picture is also in the dark theme (NAME-dark.png beside it).

Requirements

Section titled “Requirements”
  • Windows, Linux or macOS; any x86-64 or ARM64 CPU; a recent browser (tested in Chromium; Firefox, Safari and phones are in the real-world checks, docs/todo/real-world-checks.md).
  • Free RAM for the model you chat with (Qwen3-0.6B in Q8_0: about 1 GB).
  • Network access to huggingface.co to search and download models from the page.

Section titled “1. Get Inga”

Download the archive for your system from the Releases page and put inga on your PATH (details); inga --version checks it.

3. Start the engine

Section titled “3. Start the engine”

Open the Web UI address in a browser. (Outside a terminal, in a service or a pipe, the start is the plain lines of a log instead: serving the APIs.)

Or start it with no model at all — inga serve alone — and pick one on the page: the chat says No model loaded, with Load a model (the Models page’s Installed section, where Load loads any model on the machine; Search downloads one), the models already on the machine with a Load button each, each with its quantization, its size and its speed here, saying how that speed is known: measured here once it has run on this machine, computed (the memory planner’s estimate corrected by this machine’s measures) or theoretical (the estimate alone, from its size and the memory’s bandwidth); no speed where it does not run here — and the API nodes’ models with Use. The two are apart, Models on this computer and Models through API nodes, each with the five used last in this browser (loaded or chatted with; without that, the ones downloaded last and the nodes’ in the server’s order), the others counted; the search box above them finds any model of either by name. Until a model is loaded the APIs answer 503 no model is loaded yet; the page never moves to another tab by itself.

On a machine with no model at all (none downloaded, none in the model folders, no API node), the page shows the setup card instead: this computer’s memory and GPU, a model proposed for it — the largest of the six Qwen3 sizes (0.6B to 30B-A3B, Apache-2.0) that runs on the GPU, else the largest that runs in memory at 8 tokens per second or more — with what it is good at, its size, where it runs and how fast, and Download and start: the download (with its progress), the load and a first question in the chat (“Say hello and tell me in one sentence what you can do.”), each step said in plain words. Two ticks add the voice models and the document search’s embedding model, which become the server’s. Other choices lists the others that fit and the Hugging Face search; Not now hides the card in this browser. GET /api/inga/starters gives the list with the verdict of each.

Open http://127.0.0.1:8080/. To reach the page from another device of your network, start the server with --host 0.0.0.0 and an --api-key KEY (the page asks for the key: API key → Set… in the settings); --no-webui turns the page off and leaves only the APIs.

Where the page keeps the API key: for this browser tab only (its sessionStorage), so it goes when the tab closes and a new tab asks for it again. Tick Remember the API key on this device (Settings → Server and API key) to keep it in the browser’s localStorage for every tab: it is then readable by anyone who can read that browser’s data. Unticking it removes that copy. A key saved by an earlier version is moved, the first time the page opens, from its clear copy in localStorage into the tab, and that copy is deleted: tick the box to keep it across restarts. The key is sent only to the server it is for (this server, or B in remote mode below), as before.

Chat with the models of another PC (remote mode)

Section titled “Chat with the models of another PC (remote mode)”

The page can talk to another inga serve instead of the one that served it: for example the models on a desktop PC (B) and the browser on a laptop (A) that runs its own inga serve, with no mesh. Start B so that it accepts the page of A:

--cors takes the page’s origin exactly as the browser shows it (http:// plus the host and port you opened A with, e.g. http://127.0.0.1:8080), or *. Then on A’s page open the server’s row at the foot of the left column (This server; also Settings → Server and API key, and on the Models tab the Server… button at the top), give B’s address (http://192.168.1.20:8080, or just 192.168.1.20:8080) and its key, and press Test or Connect. The answer is in plain words:

Message What to do
... answers: Inga 0.26.3, 2 models. Connect: the page now talks to B.
... cannot be reached B is not running, the address or port is wrong, B listens on 127.0.0.1 only (add --host 0.0.0.0), or a firewall blocks it.
... answers, but does not let this page call it Restart B with --cors and the origin the message gives.
The server needs an API key (401) / refused the API key (401) Give B’s key, or check it.

Connected, the Server window says so once, with how to come back, and a bar across the top of every page names B (Using the models of the server http://192.168.1.20:8080) with Change… and Disconnect; the Models page’s first line says the same (Remote server http://192.168.1.20:8080: the models below, their loads and the generation are on that server., or This server (http://127.0.0.1:8080) when not connected) with Change… and Disconnect beside it. Everything the page asks goes to B: the chat, the model menu, and the Models (downloads go to B’s disk), Server, API, Memory, Schedules and Storage tabs. The conversations stay in A’s browser as always. The address is kept in the browser’s storage for A’s page and the key like the API key of this server (for the tab, unless remembered: above), never sent to A. If B goes away or its key changes, the bar turns red and says why. Disconnect forgets B’s address and key and the page talks to A again.

4. Check that it works

Section titled “4. Check that it works”

Type a message and press Enter (Shift+Enter for a new line). The answer streams in; under it a line gives the tokens per second while it is written and, at the end, N tokens in, M out, X tokens/s, first token after Y s.

The chat

Section titled “The chat”
  • Conversations are kept on the server, under your profile (where the chats are kept); before, they stayed in the browser’s storage. The box above the list searches them; a double click renames one.
  • When a chat is not saved: a save the server refuses (its limits: 4 MiB of text per chat, 1 GiB in all) or cannot take (it does not answer) is said by a bar over the chat, with the size of the chats and of their pictures: Retry, Export every chat (the chats still open in the tab, nothing lost) and Delete pictures (asked first: the pictures of every chat but the one open go, their text stays with a note where each was). Past 80 % of the limit the list of chats says how much the profile holds, and the Storage page always has a line for the chats kept on the server.
  • Export and import: the download button saves the chat shown as Markdown, as a self-contained web page (HTML: code blocks, the reasoning folded, the sources listed; no script, readable offline) or as JSON — OpenAI’s messages list (role, content, reasoning_content), the system prompt first, with Inga’s own fields under inga (model, time, statistics, sources, attached files, the other versions of the conversation) and, at the top, the title, model, settings and times — or every chat as a backup. The upload button reads a JSON export back as a new chat (also a plain list of OpenAI messages), or a backup’s chats.
  • Share: the link button keeps a snapshot of the chat shown (its HTML export) on the server and gives a link, http://HOST:PORT/shared/<id>, that anyone can open read-only in a browser. The id is 128 random bits and is the only secret: with --api-key, creating, updating and revoking a link need the key, opening it does not, so give it only to whom may read the chat. Update snapshot puts the chat as it is now behind the same link; Revoke deletes it (the link then leads nowhere); the window also lists every chat shared from the server, from any browser. The snapshots are in ~/.cache/inga/shared/ (readable by the server’s user only, at most 12 MiB each and 1000 in all) and are the kind Shared chats of the Storage tab and of inga data (inga data list shared, inga data clear shared). The page is served sandboxed: no script runs in it and it loads nothing from elsewhere (pictures sent as links, not as files, do not show). The link uses the address the page was opened with: open the web UI by the computer’s name or LAN address, not localhost, to share it with others. Over HTTP: POST /api/inga/shared, GET /api/inga/shared, DELETE /api/inga/shared/{id}.
  • Messages: hover one for copy, edit, regenerate, delete. Code blocks have a copy button. A thinking model’s reasoning is shown apart, in a collapsible Reasoning block; while it streams, its Stop thinking button ends the reasoning and the model answers at once.
  • Formulas and diagrams: $...$ and \(...\) in a line, $$...$$ and \[...\] on lines of their own are drawn by KaTeX (a price such as “$5 and $10” stays text; a display formula has Copy LaTeX). A ```mermaid block is drawn once its closing fence arrives, with Copy source, Source, Download SVG and Download PNG. Both libraries come with Inga (/webui/lib/, loaded the first time an answer needs them): nothing is fetched from the internet. The HTML export and shared links keep the formulas and diagrams as text.
  • Typing while an answer streams: the button reads Queue; the message waits above the box (edit it there, or remove it) and is sent when the answer ends, the next queued one after it. Send now on a queued message, or Ctrl+Enter in the box, stops the answer (its text stays) and sends at once. After Stop the queue waits: Send now, or Send with the box empty.
  • The model’s questions: when a chat uses the server’s tools (web search, the memory, skills or MCP tools) a model that calls tools may stop and ask up to four questions (ask_user): a card in the answer shows them with their choices and a field for your own words; Answer sends them and the model goes on, Skip lets it go on without. It waits ten minutes; the answers stay under the message. In the terminal: inga run model.gguf --ask-user.
  • Branches: editing a question (it becomes a box with Send and Cancel) or regenerating an answer — any answer, not only the last — keeps the old version: arrows ‹ 2/3 › under the message switch between the versions, each with the conversation that followed it. Delete on such a message deletes the version shown and what follows it. Chats saved by an older Inga are read as they are.
  • Attach (the + in the message box) → File attaches text files — source code (.java, .py, .js, .php, …), Markdown, JSON, CSV, logs, up to 2 MiB each — for any model: their content goes into the message as a fenced block named after the file (File \Hello.java`:`), and the chat shows it folded under the message. Inga warns when a file is close to the context size. Files can also be dropped on the message box. PDF and Word documents go to the server, which reads them (chat-with-documents.md).
  • Where the model runs shows beside it: CPU · AVX2 (the device and its kernels), RAM, disk when weights or experts are read from the disk (slower), network when part of it runs on other machines; the Server tab lists it for each loaded model, with the sizes. inga run and inga serve print the same line (note: runs on CPU (AVX2, 8 threads) · weights 4.20 GiB in RAM ...). A GPU badge (CUDA 0 Quadro P1000) names the GPU that runs layers; without one, hovering the CPU badge says why no GPU is used.
  • Attachments wait above the message box as cards (Sent with your next message): name, kind, lines and tokens for a file, a player for audio, a close button to remove one.
  • Under the box, the chat’s model says what it is and what it reads (Language model (LLM) · reads text, Vision-language model (VLM) · reads text, vision); Image and Audio are enabled only for a model that reads them (known once it is loaded), and an attachment it cannot read is marked in red.
  • The Attach menu (the + in the message box; each item’s tooltip says what it takes): Image attaches pictures (PNG, JPEG) and Audio recordings (WAV, MP3, FLAC), for a model that sees or hears them (vision / audio in the Models tab) with its projector (see chat-about-an-image.md and ask-about-audio.md). The ring in the bar at the top of the chat closes as the chat fills the context (orange past 75 %, red past 90 %); a click on it shows what fills it: the system prompt, your messages and files, the answers (counted with the model’s tokenizer) and the rest (the chat template, images, audio and tools), with the tokens still free. There, Compact has the model summarize the older messages; a chat whose last prompt took 80 % of the context is compacted before its next message. The summary is a message of its own, editable, with the original messages collapsed under it and Restore to bring them back (keep-long-conversations.md).
  • Beside the ring, a line says where the chat’s model runs (runs_on of GET /api/inga/status): Qwen3-8B · this PC: GPU 24 layers, CPU 16, · this PC (master): layers 0–23 · pc2: layers 24–35 on a mesh, or · only this PC: ... · satellites not used (why); a click shows each node and device with its memory, and the Models page’s header says the server’s mesh role (master of mesh home, no mesh).
  • The first page of a browser session opens on a short splash (the Inga mark, “by Matteo Baccan”); a click or a key skips it.
  • Settings (bottom left): the Model, a Preset (Balanced, Precise, Creative, Code, and the ones you save with Save preset…), the Context, the Device and GPU layers, and Chat settings… (the system prompt, sampling and output: see below). The Model menu lists the loaded models and, under On this computer, the other models of the library that can chat: choosing one loads it (the server keeps up to --models-max loaded, 1 by default, and unloads the one used least recently; while one loads, the others already loaded keep answering); the API nodes’ models come last. Opened, it is a list with a filter box: typing keeps the models whose name holds what you typed, case and separators aside; the arrows move, Enter chooses, Esc closes.
  • Thinking: model default, on, off, or effort low / medium / high (gpt-oss’s levels; for the other thinking models, a reasoning budget of 1024, 4096 or 16384 tokens); models whose template has no switch ignore on and off (see use-thinking-models.md). Shown only while the chat’s model can think (its chat template has <think>, enable_thinking, reasoning_content, reasoning_effort or harmony’s channels: thinks in /api/inga/status); a model that cannot is sent no thinking options.

The device: CPU or a GPU

Section titled “The device: CPU or a GPU”
  • Device (left panel, under the Context): Auto (the server’s default: as many layers as fit on the best GPU, CUDA first, then Metal on a Mac, never a software device, the rest on the CPU), CPU, then every GPU of the server by API, number and name — CUDA 0 · Quadro P1000, Vulkan 0 · Quadro P1000, Metal 0 · Apple M2 (a Mac’s), HIP 0 · Radeon RX 7900 XTX, Vulkan 1 · llvmpipe (software) (Vulkan emulated on the CPU, offered for tests; Auto never picks it). A GPU Inga cannot use is listed but disabled, its reason on hover with its vendor, driver, Vulkan version or compute capability and free memory.
  • GPU layers: how many layers (the last ones) run on the GPU — a number, all, or empty for the default (Auto: as many as fit; a named GPU: every layer).
  • Several GPUs: POST /api/inga/device takes a list (cuda:0,vulkan:1), as --device does (run-on-an-nvidia-gpu.md).
  • A new choice reloads the model on the next message (POST /api/inga/device); the line under the fields then says where it really runs (Runs on CUDA 0 Quadro P1000: layers 0-15, ...) or, in red, why it fell back to the CPU (Runs on the CPU only: Vulkan 0 ...: too little free memory ...). A GPU chosen by name that cannot run the model makes the next message fail with the reason: choose Auto or the CPU.
  • Trying another backend is the quickest way around a GPU bug: if an answer looks wrong on one device, pick another and ask again; inga devices --test compares every device with the CPU (see run-on-an-nvidia-gpu.md).

Chat settings and the context window

Section titled “Chat settings and the context window”
  • Context (left panel, under the model): the model’s context window in tokens — how much of the conversation it sees — with the size it was trained for on hover. A new size reloads the model on the next message (POST /api/inga/ctx); empty goes back to the server’s --ctx.
  • Chat settings… opens a window with the system prompt and every setting, by group: Sampling (temperature, max tokens, top-k, top-p, min-p, seed), Penalties (repeat penalty and window, presence, frequency, DRY with its base, allowed length and window), Advanced (typical-p, top-n-sigma, XTC, mirostat with tau and eta) and Output (stop texts, JSON output, a JSON schema for structured output, a GBNF grammar, logit bias). Every field explains itself on hover. An empty field is not sent: the server fills it with the model’s recommended value, or with its own default (inga serve’s options, then Inga’s), and the field shows that value in grey. The line under the button lists the fields you set.
  • The answer’s length (issue #1003): Max tokens empty is Auto. For a model of this server (or of your mesh) Auto sends no limit, so the answer may use all the room left in the context (the context minus the prompt; the server stops it when the context is full); for an API node’s model (a cloud service, whose tokens cost money) Auto keeps the limit the page always sent, 1024 tokens. The field shows which in grey (“Auto” or “1024”); a number there is a fixed limit for every model, kept with the chat. A 1024 saved by an older page becomes Auto once.
  • When an answer stops before its end, a note under it says why, with the number: “Stopped at the limit of 1,024 tokens”, “Stopped: the context is full (16,384 tokens)”, or “Stopped: the answer repeated itself (the same 80 tokens three times in a row)” — the loop guard of inga serve, which ends an answer that writes the same passage of 64 tokens or more three times back to back (a model looping) instead of letting it fill the context. Continue sends the chat again with the answer so far and asks the model to go on from where it stopped (in English: “Continue your previous answer exactly where it stopped, without repeating anything you already wrote.”); the rest is added to the same answer, and neither that request nor a second answer is kept in the chat. A chat whose context is nearly full is summarized first, as before a message. Raise the limit (for the limit) opens the chat settings at Max tokens. While an answer streams, a counter beside Stop says “N tokens of M available”: M is the room the server gave the answer (the context left, or the limit when smaller), or the limit sent when the server does not say (an API node).
  • Recommended by the model, at the top of the window, lists the sampling the chat’s model recommends (from its generation_config.json, or the general.sampling.* keys of its GGUF file) once it is loaded; Use the model’s settings writes those values into the fields. There is no need to press it for the model’s values to apply: empty fields already get them. Settings saved by earlier versions held Inga’s defaults as values; they become empty once.
  • The settings belong to the chat: switching chats brings each one’s back, and a new chat starts from the last ones used. Reset to defaults empties them, so the model’s recommendation applies again.

Web search and sources

Section titled “Web search and sources”

The model can search the web while it answers. Web, next to Audio under the message box, turns it on for the chat (each chat remembers it, and a new chat starts with the last choice); it takes effect with the next message. The server then offers the model a web_search tool: when the model calls it, Inga searches (DuckDuckGo by default, or the search services you checked, one after the other), gives the model the first results numbered [1], [2], …, and lets it answer — one search per answer, after which it may read a result’s page (fetch_url). While it searches, the line under the answer says searched the web for "…", reading the results…; the answer then streams as usual, with Searched the web: … above it and a Sources list under it: the title, link and site of every result the model was given, numbered as it saw them, so its [n] citations can be followed.

  • The model must be able to call tools: its chat template must render tool definitions (Qwen 2.5 / 3, Llama 3.1+, Mistral, gpt-oss, Gemma 4 and most recent instruct models). When it cannot, Web is greyed out and says why on hover.
  • Web search is a server-wide switch, on unless the server was started with --no-web-search or --offline. When it is off, Web offers to turn it on (for everyone using the server), and a chat that wants it shows Web search is turned off on this server with a Turn web search on button. With --offline it stays off.
  • Small models search less well than they chat: ask plainly (“search the web for …”) if the model answers from memory.
  • Web also lets the model read a page (fetch_url): one you name (“summarize https://…”) or a search result, as text, cited like the results; pages on your machine or your LAN are refused. Files, beside Memory, appears when the server has a workspace folder and lets the model list, read, search and (each write approved in a dialog) write its files (guide).
  • Each search goes from the machine running inga serve, not from the browser: it needs network access to the search services. DuckDuckGo may block many searches in a row: it then answers 202 with its anti-bot page, and Inga waits a second and asks DuckDuckGo’s lite page instead (first, for the next ten minutes). When that is blocked too, the model is told the search is blocked, not to search again and to say so; searches then fail at once for a minute. Checking another service in Search services avoids this: the search goes on to it.
  • The search costs the model fewer tokens. A page is read clean: its main (or its articles) first, without the header, the menus, the asides, the forms and the cookie banners, with light Markdown (headings, lists, tables, a link’s text) and without a line seen before; a result page then gives the model only its 1,500 characters nearest the question (BM25 over overlapping windows of the page), not its first 1,500. Snippets are cut at 300 characters, a result’s URL loses its tracking parameters (utm_*, fbclid, gclid, …) and the same page is listed once. The two web tools are described in fewer words (497 characters for both, 706 before). A URL written in your message is read at once, without a search first (under Supervised you are still asked before it opens; Search only opens none). Each step under the answer says about how many tokens it adds to the prompt (~N tokens: an estimate, one token per 3.5 characters, not the model’s tokenizer): the results, each page read, Wikipedia’s introductions, and the total the model reads.
  • Firecrawl (firecrawl.dev) is one of the Search services, unchecked like the others but DuckDuckGo: checked, the question goes to api.firecrawl.dev. It works without a key for a few searches a day; when the key-less day’s credits are used up it answers 429 and the step says so, with how to add its free API key (made at firecrawl.dev/app/api-keys), kept encrypted like Brave’s and Tavily’s. When pages are read, Firecrawl’s own Markdown of each result is used (cut by BM25) instead of fetching the pages.
  • Wikipedia as a second source (Also ask Wikipedia for encyclopaedic questions under the services, on by default; off with --search-backends, which uses the services it names only): a question that opens with “what is”, “who was”, “chi è”, “cos’è”, “storia di”, … (English and Italian), of at most 12 words and without words about now (today, news, price, weather, oggi, meteo, …), also sends its subject to Wikipedia in the question’s language, one call of MediaWiki’s API for the first two articles’ plain-text introductions (prop=extracts&exintro=1&explaintext=1), with a User-Agent that says who calls (Inga/VERSION (https://github.com/matteobaccan/inga)); they are numbered sources like the results, and the step Wikipedia (it.wikipedia.org): 2 introductions shows it.
  • Time limits: every limit of the search and of the pages it reads is a setting, in Settings → Web search time limits, by group (search, pages, approvals), each with its default, its unit, its range and a Reset (and one for all): the time a search on a service may take (10 s), the results per search (5), Firecrawl’s time with its pages (30 s), DuckDuckGo’s wait before its lite page (1 s), how long its HTML page is skipped after a block (10 min) and how long searches fail at once after both its pages were blocked (60 s), the time a page may take (15 s), the largest page read (2 MiB), the characters of a page (8,000) and of its passage (1,500) given to the model, the pages opened per answer (5) and per site (2), and the wait for an approval in Supervised mode (300 s). A change applies to the next search, without a restart. The same keys are in inga.toml’s [search] section (inga config, --set search.timeout=20; the file’s values win at start) and in web_limits of GET / POST /api/inga/settings. A page over a limit says so in the setting’s unit and names it (... is larger than 2 MiB (the search.max_body limit)).

Logs

Section titled “Logs”

Developer → Logs shows the server’s own log: what inga serve prints on its terminal (a model loading, the GPU it uses or passes over, an MCP server that does not start, a skill loaded, a web search, warnings and errors), which a user of the web UI or of inga service does not see otherwise. Each line has its time, its level (info, warnings in amber, errors in red), its source (inga, server, mcp, skills, websearch, gpu, mesh, nodes, schedules, …) and, when it was written while answering a request, the request’s id as a chip: a click shows that request’s lines only.

  • Filters, applied by the server to every line it keeps (not only those on screen): the level, the source (a menu of those seen), a search (any case; /regex/ for a regular expression) and Only errors.
  • Copy (the lines shown, as text), Download (inga-log-<time>.txt), Pause (the lines keep coming, drawn when it is pressed again), Clear view.
  • The server keeps its last 5000 lines in memory; as a service the older ones are in ~/.cache/inga/service/inga.log (the page says where). The terminal still shows every line.
  • Only requests (kept per browser; the Server page’s Requests log opens it): the request log instead of the lines, a row per API request with its time, status (warnings in amber, errors in red, the error under the path), method and path (streamed when it was), API family, duration, model, prompt → completion tokens, the API key’s name — never the key —, the client’s address and Logs, which opens that request’s lines (its tooltip has the request’s id, and its trace’s id when the server sends traces with --otlp-endpoint). The level, the search and Only errors filter it on the server too; Copy and Download give the rows as text. The web UI’s own polling is left out, and no prompt or answer text is kept. The server’s events (start and endpoints, a model loading, loaded, unloaded or failed, a key refused, a browser origin CORS refuses, a setting changed) are lines of the server source.

Every answer carries X-Request-Id: the client’s own when it sends one (1 to 64 visible characters), else 16 random hex digits; the request log’s row and its trace span (http.request.id) have it too. GET /api/inga/logs?after=N&limit=M&level=warn&target=mcp&q=TEXT&request=ID and GET /api/inga/logs/stream (Server-Sent Events, event: line) are admin routes, as every /api/inga/*. The request log is the last 1000 entries in the server’s memory: GET /api/inga/requests?after=N&limit=M&kind=request&level=warn&q=TEXT and GET /api/inga/requests/stream (Server-Sent Events, event: entry, the same filters).

Where the chats are kept

Section titled “Where the chats are kept”

The chats, with their pictures as files beside them, and what the page keeps that is not one of its own settings (the sampling settings, the presets, the system prompt, the switches of a new chat, the Images and Videos pages’ settings and prompts, the project open, the opt-ins, the models used last) live on the server, under the user’s profile: profiles/default/ of Inga’s data folder (DIR/profiles/default/ with --home DIR).   • A change is written 400 ms after the last one, and tried again while the server does not answer; when the page closes, every write still waiting leaves at once. When the server stops

Section titled “When the server stops”

The page watches the server it talks to (this one, or B in remote mode): it asks GET /health every 5 seconds while the tab is shown (every 30 seconds while it is hidden), and every request it makes counts too. When the server stops, cannot be reached or answers only with errors (a 502 of a proxy before it), a bar at the top of the page says so: Inga is not responding — the server at http://127.0.0.1:8080 stopped or cannot be reached. Retrying in 4 s…, with what to do (start inga serve again, check the address; in remote mode, B’s --cors) and Retry now. It tries again after 2, 4, 8 and 16 seconds, then every 30. Meanwhile:

  • the logo turns grey and the Server tab gets a red dot;
  • Send is off (its tooltip says why) and the text you typed stays in the box;
  • an answer that was streaming keeps what came, with Connection lost: the answer stopped here under it;
  • the other tabs show their data greyed under Not live: last updated 10:42:17, and their buttons (Load, Download, Delete, …) are off with the reason; Change… and Disconnect still work.

When the server answers again the bar says Connected again. for a few seconds, and the models, the status and the tab shown are read again. If it restarted meanwhile (another start time in /health), the bar says The server restarted: loaded models were reset.: load the model again from the menu; after an upgrade it offers Reload page for the new version’s page. The conversations are never touched. The installed app opened with no server running shows the same bar instead of an empty page.

When Inga closes by itself

Section titled “When Inga closes by itself”

inga serve is a small guardian that runs the server as a second process: it loads no model and does not touch the GPU. When the server closes unexpectedly (a crash, or a GPU driver that ends it: on Windows the NVIDIA dialog “An application has requested more GPU memory than is available… Error code: 6”, after which the program closes), the guardian writes a line with the time in the terminal and in ~/.cache/inga/logs/serve.log, Inga stopped unexpectedly (exit code …); restarting in 3 s, and starts it again on the same port. The page reconnects by itself.

So that a crash does not repeat, the server marks each heavy GPU step (a model’s load and placement, an image model’s load on the GPU) while it runs. If it closed during one, the restart loads that model on the CPU, and the page says it once, in plain words: Inga closed because the graphics card ran out of memory while loading Qwen3 4B, most likely. It restarted; Qwen3 4B now uses the CPU. (the model’s reference, the device and the exit are in the tooltip), until Got it. The CPU choice lasts until inga serve is started again. After 3 crashes in 5 minutes the guardian stops trying and says so.

It does not restart after Ctrl-C, a normal exit, --exit-on-load-error, or an error at start (a port in use, a model not found). --no-guardian (or serve.guardian = false in inga.toml) runs the server in the process you started, with no guardian; a service of inga service install never has a guardian, its system restarts it. Not covered: a GPU that runs out of memory later than the load (a context that grows) restarts the server but loads the model the same way again. The code is src/commands/guardian.rs.

On a phone, and as an installed app

Section titled “On a phone, and as an installed app”

At phone width the tabs move to a bar at the bottom, the menu button (left of the attach buttons) opens the chats and settings as a drawer that a tap beside it, its close button or Escape closes, buttons and fields grow to finger size, the page never scrolls sideways, and while you type the on-screen keyboard takes the place of the tab bar instead of hiding the message box.

The page is also an installable app (a PWA): the browser’s Install (or Add to Home screen) puts Inga on the desktop or the home screen with its own icon and window, without the address bar. Inga serves the manifest (/manifest.webmanifest), the icons (/icons/*) and a service worker (/sw.js) that keeps only the page and its icons, so the app opens even while the server restarts; chats, answers and API calls always go to the server and are never cached. The cache is named after Inga’s version: after an upgrade the next visit loads the new page.

Browsers allow the install and the service worker only on https:// addresses and on localhost. On the computer that runs Inga, http://localhost:8080/ is enough. From a phone on the LAN:

  • Without HTTPS (inga serve --host 0.0.0.0, then http://192.168.1.20:8080/ on the phone) the page works fully in the phone’s browser, and Add to Home screen still adds a shortcut, but the browser does not install it as an app nor run the service worker.
  • As an app: put a TLS reverse proxy in front of Inga, for example Caddy with a certificate the phone trusts (caddy reverse-proxy --from inga.home.example --to 127.0.0.1:8080 for a name with a public DNS record, or Caddy’s tls internal with its root certificate installed on the phone), or Tailscale’s tailscale serve 8080, which gives the computer an https://*.ts.net address with a valid certificate on your tailnet. Keep Inga on 127.0.0.1 behind the proxy and set --api-key if the proxy is reachable by others.

Themes and languages

Section titled “Themes and languages”

Settings, the last entry of the side bar (a phone’s bottom bar), opens a menu with the theme, the language and About (the version, the build, a link to the releases); arrow keys move in it and Escape closes it. Theme: Auto follows the computer’s light or dark setting, Light and Dark fix one, Matrix is phosphor green on black in a monospace font with a faint falling code behind the conversation (still when the system asks for reduced motion), Blade Runner is neon orange, cyan and magenta on a teal night, Tron is a black grid lit in cyan with your messages in orange, and Commander has Norton Commander’s colours: cyan text on a VGA blue screen, yellow headings, the selection as a cyan bar, square double borders and a monospace font. Language picks the interface’s language: Automatic follows the browser’s languages (navigator.languages; pt-BR and pt-PT are both Português), else English, Italiano, Français, Deutsch, Español, 简体中文, Português (Brazil’s wording), Русский, 日本語 or हिन्दी. Dates and numbers follow the page’s language too. Japanese and Hindi use the system’s fonts for their scripts in every theme, the monospace ones included. Both choices stay in the browser (localStorage keys inga.theme and inga.lang). Only the page is translated: the models’ answers, model names, API paths, code samples and the OpenAPI files of the API docs stay as they are.

The page’s tooltips are its own: a box in the theme’s colours instead of the browser’s grey one, shown after 300 ms on hover or keyboard focus, above or below the element and inside the window, with its line breaks kept; leaving, scrolling, a click or Escape closes it (screen readers get it through aria-describedby; with reduce motion it does not fade).

Troubleshooting

Section titled “Troubleshooting”
  • Report: an error’s notice and an answer that failed have a Report button. It shows the issue as it will be sent, field by field (the error, the version, the system, the GPUs, the model, the page; no folders, user or host names, and the server’s address as <server>), says where it goes, then Open on GitHub opens the form filled in, in the page’s language, in a new tab; the issue exists only when you submit it there. Copy gives the same text to send another way (offline, or while the project’s repository is not public). The terminal does the same: under an error, its last line is the link, the line above says what it carries.
  • The page shows “Ollama is running”: the request did not ask for HTML (a script or curl); open the address in a browser. Ollama clients use the same GET /.
  • “invalid or missing API key”: set the server’s key in API key → Set….
  • A bar says “Inga is not responding”: inga serve stopped (closed terminal, crash, a stopped service) or the address changed; start it again, and the page reconnects by itself (or press Retry now). See When the server stops above.
  • “Inga stopped unexpectedly …; restarting in 3 s” in the terminal: the server closed (a crash, a GPU driver) and its guardian started it again; see When Inga closes by itself above. If it says not starting it again, the lines above it and ~/.cache/inga/logs/serve.log say why; a model that does not fit on the GPU runs with --device cpu or fewer --gpu-layers.
  • The answer says the web search failed: the server cannot reach DuckDuckGo (no network, or a proxy it does not use: Inga reads HTTPS_PROXY), or DuckDuckGo blocks this address (“refusing automated searches”, HTTP 202, on both its HTML and lite pages); wait a few minutes, or check another service in Search services.
  • “The model asked for the tool … in a format Inga does not read”: Inga reads the call formats of Hermes / Qwen, Qwen3.5, Llama 3.1+, Mistral, GLM, Granite, DeepSeek, gpt-oss and Gemma 4 (<|tool_call>call:...); report another model’s format on GitHub with the answer as shown.
  • Search or download fails with “cannot reach …”: the server has no network access to Hugging Face, or needs HTTPS_PROXY; gated models need HF_TOKEN in the server’s environment (see run-a-model-from-hugging-face.md).
  • “not enough disk space for …”: the download folder’s disk has no room for the files; press Another folder… (or Models → Model folders → Download folder) and choose a folder on a disk with more free space, or move the models there.
  • A downloaded model says NOT SUPPORTED: the reason follows it; see supported-models.md.
  • No Install button, or “no service worker” in the browser’s console: the page was opened over plain http:// from another machine; see On a phone, and as an installed app above.
  • A shared link says “No shared chat here”: it was revoked (from the page, the Storage tab or inga data), or the home (--home) differs between the server that made it and the one that answers.
  • The chats are gone: they live on the server, in the profile of its data folder (profiles/default/, or under --home DIR): a server started with another --home starts empty. Chats an older Inga kept in this browser are not moved: the Storage page counts them and exports them, and Import adds that file back. Save them with Export (Every chat) and add them back with Import.
  • “Your chat is not saved: the server refused it”: the chat passed the server’s limits (4 MiB of text per chat, 1 GiB for the profile). Export every chat from the bar, then Delete pictures or delete old chats; the bar goes once a save fits again. “Your latest changes are not saved on the server”: the server did not answer; the page tries again by itself, and Retry tries now.
