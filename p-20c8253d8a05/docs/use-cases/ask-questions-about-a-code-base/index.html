Ask questions about a code base

Experimental: checked on synthetic folders and one fixture per language; the numbers of the spec’s §9, against tokensave on a real code base, are unmeasured.

What you get

Section titled “What you get”

Keep a folder of source code in sync with a collection, as any folder of documents, and Inga also reads its structure: its Rust, Python, Java, TypeScript (TSX too), JavaScript (JSX too), C#, Go and PHP files are parsed with tree-sitter, so

  • their passages are cut at syntax boundaries (functions, methods, classes, impl blocks, the comments, attributes and annotations above them), small neighbours merged and large items split into their members, each passage with its heading path (src/store.rs › impl Store › fn search, src/Shapes.java › class Shapes › method add, shapes.go › func (c *Circle) Area) and its lines in the file;
  • their definitions and references are kept beside the passages: where a function, method, class, struct, trait, interface, enum or record is defined, who calls it, what it calls, a file’s outline (in all but Rust and Python also the imports and the types a file names);
  • a model that calls tools gets five code tools beside the document tools: find_definition, find_references, callers, callees and outline, in the chat APIs, in inga run and in Inga’s MCP server, for other agents;
  • inga docs outline and inga docs refs answer the same in the terminal, and the Documents page shows each folder’s languages and a symbol’s definition and references next to a passage.

Everything stays on your computer. The parser is C (tree-sitter and its grammars, compiled into the desktop builds only, never the browser page): it never runs in Inga’s own process, but in a child Inga starts from its own executable (inga __parse); a file that takes longer than 2 seconds stops the child, a crash costs only that file, and either way the file is cut as plain text and the folder says why.

What it is not. References are by name, as the grammar sees them: no types, no imports resolved. A call x.sign() is a reference to every sign in the collection; every answer says so. For type-aware navigation use your editor’s language server; for more languages, see tokensave.

Requirements

Section titled “Requirements”

  • Windows, Linux or macOS (the desktop builds; the browser page has no code parsing).

  • An embedding model for the collection, as in chat-with-documents.md.

  • For the code tools in a chat: a model whose chat template takes tools (Qwen3, Llama 3.1+, Mistral and most recent instruct models).

  • Languages parsed, on the runtime tree-sitter 0.27.1:

    Language Files Grammar
    Rust .rs tree-sitter-rust 0.24.2
    Python .py, .pyi tree-sitter-python 0.25.0
    Java .java tree-sitter-java 0.23.5
    TypeScript, TSX .ts, .mts, .cts; .tsx tree-sitter-typescript 0.23.2
    JavaScript (JSX included) .js, .mjs, .cjs, .jsx tree-sitter-javascript 0.25.0
    C# .cs tree-sitter-c-sharp 0.23.5
    Go .go tree-sitter-go 0.25.0
    PHP .php tree-sitter-php 0.25.1

    Files of C, C++, CUDA, GLSL, WGSL, Ruby, Kotlin, Swift, Scala, Lua, shell and PowerShell have no grammar in Inga: their passages are cut at the functions, classes and modules a heuristic chunker finds (the lines that define them, then their braces or indentation), each with its heading path, and their definitions and references are not kept (the code tools do not see them).

1. Get Inga

Section titled “1. Get Inga”

Download the archive for your system from the Releases page and put inga on your PATH (details).

2. Keep the folder in sync

Section titled “2. Keep the folder in sync”

The first sync reads every file, parses the source files in the child, embeds the passages and keeps the definitions and references. Later syncs read only the files that changed; an edited file’s definitions and references are replaced with it, a deleted file takes them away. A folder indexed by an older Inga, before its code was parsed, is read again once (its unchanged passages keep their vectors).

The folder’s encoder is chosen by its mode (--mode, Automatic by default) and said at the first sync: for a code base with its docs, one encoder for every file, the one measured best on code; in Automatic all-MiniLM-L6-v2 (the static potion-code-16M-v2 is 0.035 nDCG@10 below, past docs.fast_loss). On Inga’s own sources and guides the code’s encoder alone beat an encoder per kind (0.693 against 0.676), so the source files and the other files (a README, the docs) share it; docs.split_encoders = true gives the documents their own. --mode fast takes a static encoder (Inga’s own sources, 635 files, embedded in 10 s by potion-code-16M-v2 against 2.5 h by all-MiniLM-L6-v2, measured on a shared 4-vCPU machine), --mode quality the best full one; --embed-model M names one model. With the encoders split, a search embeds the question once per encoder and merges the two lists by how far each passage stands above what its encoder gives an ordinary passage for that question.

inga docs status myproject says what became of the code, per language:

A file that fell back is listed with why (not parsed: the parser took longer than 2.0 s and was stopped, no grammar for Ruby in this build); --json gives every language’s counts, the grammars and the first 20 fallbacks.

3. Search the code

Section titled “3. Search the code”

When the passages found hold source code, Inga orders them for code, and --explain says per passage what changed its place:

  • file coherence: a file with several passages found has its best one raised (0.2 × the best score, times its share of the hits: file coherence +0.20 (3 hits of its file)), so the file that does the work comes before a file that mentions it once;
  • path prior: tests, examples, compatibility shims, vendored and generated code (tests/, *_test.go, *.spec.ts, vendor/, node_modules/, *.min.js, *.pb.go…) are lowered (× 0.3; TypeScript’s .d.ts and re-export files by its square root): path prior ×0.30 (test code).

Measured on Inga’s own sources with potion-code-16M-v2: hybrid nDCG@10 from 0.726 to 0.778 on 22 questions, from 0.728 to 0.780 with the tests in the folder; folders of documents only are not changed (the measures). The keys of inga.toml set them: docs.file_coherence and docs.path_prior (0 and 1 turn them off), and two that are off by default, docs.symbol_weight (the names a passage defines weighed apart) and docs.definition_boost (a passage defining a name the question writes raised); inga eval rag measures a change on your own questions.

4. Look a symbol up in the terminal

Section titled “4. Look a symbol up in the terminal”

A qualified name (Store::search, Signer.sign; . and :: both work) narrows the definitions to that type’s member; references and callers are matched by the last part.

5. Ask a model

Section titled “5. Ask a model”

Name the collection in the prompt and ask in tool mode, so the model calls the tools itself:

The model sees documents_search, document_read, documents_grep and, because the collection holds parsed code, the five code tools. Each result is numbered as a source ([1] myproject › src/store.rs:14-40), with what to pass to document_read to read the lines, so the answer cites them.

The same through the APIs of inga serve: inga_documents: [{"collection": "myproject"}] with inga_documents_mode: "tool" on /v1/chat/completions (or the Anthropic, Ollama and Responses routes). GET /api/inga/documents/code?collection=myproject&symbol=Store::search gives the same tables as JSON (API).

6. From another agent, over MCP

Section titled “6. From another agent, over MCP”

Inga’s MCP server (POST /mcp of inga serve, or inga mcp serve for clients that start a program) lists the code tools beside the memory’s when a collection holds parsed code. There each call names its collection (collection is required, and listed in the tools’ descriptions), since an MCP client has no prompt to name it in:

See share-the-memory-with-agents.md for connecting Claude Code, Cursor or Codex to it.

7. On the Documents page

Section titled “7. On the Documents page”

Each folder of code shows a line with its languages, the files parsed and the grammar versions, and the files cut as plain text, folded, with why. A collection holding parsed code has a Find symbol box: a name gives its definitions with their signature, the items that call it, what it calls and its references. A search hit inside a function or a class has a Definition and references button that looks that item up. In the collection’s file table, the Indexing column says per file tree-sitter · Go (the grammar’s version as the tooltip) or plain text: no grammar for Ruby in this build (its tooltip says how many items the heuristic chunker found), and State says to re-index for a file parsed by an older grammar version, read again at the folder’s next sync (inga docs status NAME --files prints both).

tokensave, for the other languages

Section titled “tokensave, for the other languages”

tokensave keeps a tree-sitter symbol graph of more than 50 languages and serves it over MCP. Give it to Inga as an MCP server (inga serve --mcp FILE, see use-with-coding-agents.md) for the languages Inga does not parse; its callers and callees tools are named tokensave_callers and tokensave_callees.

Good to know

Section titled “Good to know”
  • Eight grammars: Rust, Python, Java, TypeScript and TSX, JavaScript, C#, Go, PHP.
  • References are by name only: no types, no imports.
  • Files above 2 MiB are not parsed; the parsing child has a time limit per file (2 s).
  • Uploaded files (the Documents page’s Add files, inga docs add NAME FILE...) are not parsed: only a folder’s sync parses.
  • Unverified on real code bases: the passages’ quality and the tools’ answers with local models are measured by ingausecase’s tokensave case (real-world checks).
