Measure the speed of a model on your machine

What you get

Section titled “What you get”

The prefill and decode speed of a model on your CPU, in tokens per second, for one or more thread counts and instruction sets, in a table shaped like llama.cpp’s llama-bench, so you can pick the best settings and compare Inga with llama.cpp.

Requirements

Section titled “Requirements”
  • Windows, Linux or macOS; any x86-64 or ARM64 CPU. Inga uses AVX-512, AVX2 or NEON when the CPU has them, SSE4.1 on an x86-64 CPU without AVX2 (Celeron, Pentium Silver, Atom, Sandy Bridge and Ivy Bridge), portable scalar code otherwise.
  • Free RAM for the model file plus a few hundred MB, and the disk space for the file.
  • A way to download a file (a browser, curl or wget).

1. Get Inga

Section titled “1. Get Inga”

Download the archive for your system from the Releases page and put inga on your PATH (details); inga --version checks it.

2. Get a model

Section titled “2. Get a model”

Any GGUF file inga info reports as supported works; see chat-with-a-local-gguf-model.md. The examples below use Llama-3.2-1B-Instruct in Q4_K_M, a common size for laptops:

Or let Inga download it into the Hugging Face cache: inga bench hf://bartowski/Llama-3.2-1B-Instruct-GGUF:Q4_K_M ... works as well (see run-a-model-from-hugging-face.md).

3. Run the benchmark

Section titled “3. Run the benchmark”
  • -p N: prefill test, N prompt tokens processed in one pass (pp<N>); 0 skips it.
  • -n N: decode test, N tokens generated one at a time (tg<N>); 0 skips it.
  • -t A,B,...: the thread counts to test, one row pair each (default: every logical CPU).
  • -r N: repetitions of each test (default 5); the table shows mean ± standard deviation. Each test first runs once untimed, as llama-bench’s warm-up does, so the first repetition does not pay for the first launches of the GPU’s kernels at that size or, for a model whose experts (or layers) are read from the disk, for the cache’s first reads; --json’s samples_ts has each repetition’s speed, in order.

The prompt tokens are random ids (as in llama-bench), so the result does not depend on a prompt, and the model’s chat template is not used.

4. Read the result

Section titled “4. Read the result”

The load time goes to stderr, the table to stdout. This output was measured with inga 0.2.0 on a 4-vCPU Xeon (Linux, AVX-512), on a file with the shape and weight types of Llama-3.2-1B Q4_K_M (written by tools/bench_model.py, see performance.md); with the real file the speeds are the same, only the size and the model column differ slightly:

  • pp (prefill) is how fast a prompt is read: it decides the wait before the first word of an answer. tg (decode) is how fast the answer is written.
  • backend names the instruction set in use.
  • Decode is limited by memory bandwidth: past a few threads it stops improving, and on CPUs with hyperthreading the number of physical cores is often best. Inga generates on one thread per physical performance core by default and reads prompts on every logical CPU; without -t, inga bench measures those defaults and the threads column shows each test’s. Use the fastest decode count with inga run --threads-decode N (-t N sets prompts and generation).

5. Compare instruction sets and engines

Section titled “5. Compare instruction sets and engines”

Force an instruction set with the key cpu.isa of inga.toml, or --set cpu.isa=NAME (scalar, sse41, avx2, avx512, neon, neondot, neoni8mm), e.g. to see what the SIMD kernels bring (on an ARM64 CPU with i8mm, an Apple M2 or later, cpu.isa=neondot against the default neoni8mm measures the smmla prompt tiles):

An instruction set the CPU lacks is an error (this CPU cannot run AVX-512 kernels).

To compare with llama.cpp, run its llama-bench with the same tests on the same file: llama-bench -m Llama-3.2-1B-Instruct-Q4_K_M.gguf -p 128 -n 64 -t 1,4 -r 3. performance.md has both engines side by side, each row the latest measurement.

6. Measure at depth: a prompt added to a long chat

Section titled “6. Measure at depth: a prompt added to a long chat”

-p 512 reads a prompt into an empty cache. In a chat or an agent, every turn adds a prompt to a cache that already holds the conversation, and attention costs more the longer it is. -d N (llama-bench’s -d) fills the cache with N random tokens first, not timed, then runs -p and -n from there:

(Illustrative numbers.) Each repetition starts from the same filled cache: it is cut back to the depth, or, for models with recurrent layers (Qwen3.5, Mamba hybrids), restored from a copy taken after the fill. The depth plus the longest test must fit in the model’s context. With --json, each test has llama-bench’s n_depth.

7. Compare two paths: --ab

Section titled “7. Compare two paths: --ab”

A speed change must change nothing but the speed (performance.md). --ab KEY=VALUE runs the default and the path a key of inga.toml selects (the [debug] switch of a new kernel, such as debug.vk_tiles=false, or debug.moe_grouped=false, a mixture of experts’ prompt one row at a time instead of grouped by expert, or debug.direct_reads=true, the experts streamed from disk read past the page cache) on one load of the model:

  • a warm-up of each, then -r runs of each in ABBA / BAAB order, so neither side always gets the warm cache or the cool GPU;

  • the default runs with the variable removed, the variant with it set; it is put back as it was at the end;

  • the final logits of every run must be the default warm-up’s, byte for byte, or within --ab-tolerance X (the largest absolute difference) when the change reorders sums; --include-selection also checks the greedy token after every step. The first difference stops the bench with the run, the logit and the largest difference.

  • debug.moe_grouped=false cannot give the default’s bits (issue #401): an expert’s rows go through other kernels, which sum their products in another order (a few millionths apart), and where two experts’ scores of a token are that close the router picks the other one, which every later token sees: the logits move by as much as with another instruction set (1.68 of a spread of about 16 on the reporter’s Ornith-1.5-35B-A3B, 40 layers, the same on 0.26.5 and 0.27.1). Without --ab-tolerance it is compared as distributions, at every position of the warm-ups (the prompt’s tokens and each generated one) and at the last of each timed run. The rule over the warm-ups’ positions:

    • the mean Kullback-Leibler divergence of the next token’s distribution from the default’s is at most 0.01 nats, and at most 0.5 at any one position;
    • each side’s most likely token is within one logit of the other side’s first;
    • at most 1 % of the positions (one at least) have another most likely token than the default’s outside a near tie (both sides’ first two within 0.5).

    The divergence is taken over the default’s 64 most likely tokens and the rest as one, a lower bound of the whole that keeps a position in 1 KiB. The bounds come from Qwen3-0.6B-Q8_0 on the CPU (2026-11-07, text of 510 scored positions):

    Run against the default Mean KL Largest Other first tokens
    debug.attn_split=true (rounds otherwise) 1.3e-3 4.1e-2 0
    the same file on lavapipe (other kernels) 1.9e-3 5.8e-2 0
    a bias of RMS 0.3 in layer 14 (perplexity +7.8 %) 5.8e-2 1.14 29
    a bias of RMS 0.1 in layer 14 (perplexity +1.5 %) 7.4e-3 0.36 3

    inga bench --ab debug.attn_split=true -d 600 -p 512 -n 128 on the same file (its random tokens) measured a mean of 1.7e-4 and at most 3.1e-3 over pp512’s positions. The old rule (0.1 nats at the last position only) let the 0.3 bias through at 83 % of the positions; the new one fails it on its mean. The 0.1 bias, below the noise of a perplexity, passes both. Not measured yet: a real mixture of experts with debug.moe_grouped=false, whose routes flip (the bounds leave 5x over the largest mean measured). The table shows the positions, the divergence’s mean and largest and the other first tokens; --json gives ab_kl (the mean), ab_max_kl (its bound), ab_kl_largest, ab_kl_largest_bound, ab_positions and ab_other_top.

(Illustrative numbers.) The ratio is the variant’s speed over the default’s; the table goes into the pull request as it is. The switch must be read while the model runs, not once at load: the switches Inga has today (cpu.isa, debug.cuda_graphs, debug.metal_simdgroup, …) are read when the device or the model is set up, so --ab would run the same path on both sides; for them, compare two inga bench runs. --ab works with -d, --ctx-sweep and --json (one object per side, with ab_variant, ab_ratio and ab_max_abs_diff), not with --profile.

--ab also takes a configuration key where one replaces a variable. It knows debug.vk_barriers: --ab debug.vk_barriers=all runs a Vulkan device with a memory barrier after every command against the default, which puts one only where a command depends on an earlier one; the logits must match byte for byte:

8. The speed curve of a growing context: --ctx-sweep

Section titled “8. The speed curve of a growing context: --ctx-sweep”

-d measures one depth. --ctx-sweep START:MAX:STEP (default 2048:32768:2048, K for 1024: 2K:32K:2K) grows one cache frontier by frontier, as ds4’s ds4-bench does, and measures at each:

  • the prompt speed of the tokens just added: STEP tokens from the previous frontier (START from an empty cache for the first), in batches of 2048;
  • the speed of -n tokens generated from the frontier (default 128), not kept;
  • the KV cache’s size there.

(Illustrative numbers.) A pp row is the prompt that brought the context to ctx; a tg row generates from ctx. Each repetition of a prompt starts again from the previous frontier (cut back to it, or restored from a copy for recurrent layers).

  • --json: each object also has ctx_tokens and kvcache_bytes; n_depth is where the test started (the previous frontier for a prompt).
  • --csv FILE: one row per frontier with ds4-bench’s columns (ctx_tokens, prefill_tokens, prefill_tps, gen_tokens, gen_tps, kvcache_bytes), so the two engines’ curves plot the same way.
  • --prompt-file FILE: a real text instead of random tokens (repeated if shorter).
  • --ab ENV=VALUE: both paths at every frontier, with the output checked.
  • Where it stops: at the last frontier the model’s context and the memory hold (the free RAM, or --mem-limit beside the weights; a GPU’s cache when it cannot be made), and it says why: ctx-sweep: 15 frontiers up to 30720 tokens; stopped there: 32768 tokens plus 128 generated exceed the model's context of 32768 tokens.

9. Many users at once: --users

Section titled “9. Many users at once: --users”

The tests above measure one conversation. --users N[,N...] measures what a server gives several users at once, as vLLM’s benchmark_serving does against a server: for each count, that many sessions start together, each with its own prompt of -p random tokens, and each generates -n tokens (greedy, with the end-of-text tokens banned so every user generates them all). The sessions run as inga serve --parallel N runs its requests: their decode steps go through the same batcher, one pass of the model for all of them, where the model’s placement allows it; otherwise they take turns. A short Each count first runs once untimed (the warm-up, the same prompts’ lengths and answers); -r repeats each count (once by default).

(Measured on 2026-10-16 with 0.31.0+ on a 4-vCPU AVX-512 cloud VM shared with other builds, two threads, on a file with Llama-3.2-1B’s shapes and random Q4_K_M weights from tools/bench_model.py.) Eight users get 1.6 times one user’s total tokens per second here: the short generations leave most of the time to the eight prompts, which queue behind each other (the TTFT). The columns:

  • total t/s: every user’s generated tokens over the time from the first start to the last token: what the machine serves.
  • per user t/s: a user’s generation speed after its first token, the mean over the users: what each one sees.
  • TTFT p50 / p95: the time to the first token, its median and 95th percentile; the prompts of users who start together queue behind each other.
  • ITL p50 / p95: the time between two pieces of a user’s text (the inter-token latency, counted between the streamed pieces as vLLM counts it).
  • batch: the sessions’ decode steps per pass of the model, on average; turns when the model’s placement cannot batch them, and the header line says exactly why (not batched yet: a GPU without part copies): layers on other machines, Llama 4’s / Mistral 3’s attention temperature, a GPU without part copies (Metal, WebGPU), a control vector (the high-throughput serving spec brings them). A dense model’s layers on a CUDA or Vulkan GPU batch, as the CPU’s do; Gemma 4 12B / 31B’s too (heads of two shapes); the mixtures (their experts on the GPU or the CPU) and the hybrid models (DeltaNet, Mamba2 and LFM2 layers on the GPU, their states per session) too.

A long prompt among the answers: --long-prompt L gives one user of each count a prompt of L tokens instead of -p, started once the others have their first token. Its time to the first token is a column of its own (long TTFT ms, left out of the TTFT columns), and the others’ ITL p95 shows how long it stops their streams. Prompts are mixed with the decode steps by default (each chunk of at most 512 tokens in the same pass as the others’ next tokens, as inga serve --parallel does); --no-mixed-prefill measures the same with each prompt in passes of its own:

On a file with Qwen3-0.6B’s shapes and random Q8_0 weights (tools/bench_model.py), on this project’s 4-vCPU cloud VM shared with builds (a sanity check, not a speed), the three users’ ITL p95 was 107 ms mixed against 209 ms apart, and the long prompt’s first token came after 3.6 s against 4.3 s.

--json gives one object per count: n_users, n_prompt, n_gen, reps, batched, batch_blocker (the reason they take turns, null when batched), avg_batch, total_ts, samples_total_ts (each repetition’s, in order), per_user_ts, ttft_p50_ms, ttft_p95_ms, ttft_mean_ms, itl_p50_ms, itl_p95_ms, itl_mean_ms, gen_tokens and secs (with --long-prompt also n_long_prompt, long_ttft_ms, mixed_prefill and mixed_steps), beside the model and backend fields of the other tests. --users runs on the threads of inga.toml (cpu.threads, cpu.threads_decode), and is not combined with -d, -t, --ab, --ctx-sweep, --speculative, --profile or --decide. Speculative decoding, which inga serve uses with --parallel 1, is not used.

10. Speeds measured on real runs

Section titled “10. Speeds measured on real runs”

Inga keeps the speeds it sees in ~/.cache/inga/measured.json:

  • What is recorded. Every answer of inga serve and inga run records its prompt speed (from 32 tokens not in the cache) and its generation speed (from 8 tokens). inga bench records its pp and tg tests once it ends (the default threads, no -d, --ab, --profile or --ctx-sweep).
  • How it is kept. Per model (the SHA-256 of its file), machine, device (CPU, or the GPU that ran layers) and number of GPU layers. The last 20 runs are kept and their median is shown.
  • Where it shows. inga list, the Models page and inga pull’s picker show the measure instead of the planner’s estimate: 16.4 tok/s gen · 210 tok/s prompt (measured, 2026-10-12).
  • The estimate learns. After three measures on a machine and device, the planner multiplies its estimates there by the median of measured over estimated (a measure more than 20 times off, such as a tiny test model’s, is left out). This also applies to models not run yet, and to inga search. The tooltip says so: “Estimate: ~18 tok/s (the planner’s ~12 tok/s, corrected ×1.5 by 7 measures on this machine)”.

Runs split over machines (--nodes, the mesh), speculative decoding and answers stopped early are not recorded. Delete the file to start over, for example after a hardware change.

Options worth knowing

Section titled “Options worth knowing”
Option Meaning
-p N, -n N Prefill and decode test lengths in tokens (0 skips a test).
-t A,B,... Thread counts to test, each for prompt and generation (default: the defaults of inga run).
-r N Repetitions per test.
-d N[,N...] Tokens in the cache before each test, not timed (llama-bench’s -d); a depth column, n_depth in the JSON;.
--ab KEY=VALUE The default against the path a key of inga.toml selects (debug.*, gpu.max_load, run.speculative, …), in ABBA / BAAB order on one load, the output checked;, on keys.
--ab-tolerance X The largest logit difference --ab accepts (default 0: byte for byte; debug.moe_grouped=false: the next-token distributions at every position, a mean KL within 0.01 nats).
--include-selection --ab also checks the greedy token after every step.
--ctx-sweep [S:M:STEP] The prompt and generation speed at each context frontier from S to M (default 2048:32768:2048), a ctx and a KV cache column, stopping where the context or the memory ends; with --csv FILE (ds4-bench’s columns) and --prompt-file FILE.
--users N[,N...] A load test: N sessions at once for each count, each with a prompt of -p tokens and -n generated, as inga serve --parallel N runs them; total and per-user tokens per second, TTFT and ITL p50 / p95, the decode steps per pass (batch);.
--long-prompt L With --users: one user of each count reads a prompt of L tokens, arriving once the others answer; its TTFT apart (long TTFT ms);.
--no-mixed-prefill With --users: each prompt in passes of its own instead of by chunks among the decode steps (serve.mixed_prefill = false);.
--json The results as a JSON array, one object per test, with llama-bench’s -o json field names (n_prompt, n_gen, n_threads, avg_ts, stddev_ts, samples_ts, avg_ns, …), for scripts and dashboards;. inga info --json describes a model the same way.
--profile After the results, a table per test of where the time goes: calls and microseconds per token of each operation kind (matrix products by weight type, attention, norms, RoPE, element-wise operations), the time outside them, and the thread pool’s overhead (starting jobs, waiting for the other threads); with --json, a profile object in each test. Profiling adds a clock read per operation, so the speeds are a little lower;.
--set cpu.isa=... Force an instruction set (also for inga run; cpu.isa in inga.toml).

Troubleshooting

Section titled “Troubleshooting”
  • a test of N tokens exceeds the model's context of M tokens: use a smaller -p or -n; with -d, a depth of D tokens plus a test of N tokens exceeds ...: a smaller depth too.
  • --ctx-sweep: not even the first frontier of N tokens fits: the reason follows (the context, the memory); start the sweep lower or raise --mem-limit.
  • --ab ...: logit I is X instead of the default's Y: the variant computes something else. If the change only reorders sums, give the difference it may make with --ab-tolerance; otherwise it is a bug of the variant.
  • bench measures generation on the threads of -t (llama-bench's way): inga bench takes no --threads-decode; give the counts with -t (-t 2, or -t 2,4 to compare).
  • this CPU cannot run ... kernels: cpu.isa names an instruction set your CPU does not have; remove it to let Inga pick.
  • The chat in inga serve is slower than inga bench on a GPU: bench plans the GPU for its own context (-d plus the longest of -p and -n: 512 by default), the server for --ctx (4096 by default), and the KV cache takes room on the GPU for every position of the context. Compare the where the model runs table of both: on a card the model just fits, the server’s may keep the output layer on the CPU, or (with --device auto) a first layer or two there so that the output layer fits, which bench’s has on the GPU. inga bench model.gguf -d 3584 -p 512 -n 128 plans for the same 4096 positions as the server (and measures there); inga serve --ctx 2048 gives the GPU the room back if your chats are short.
  • Numbers vary a lot between runs (large ±): close other programs, raise -r, and on laptops plug in the charger (power saving lowers the clock).
