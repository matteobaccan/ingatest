Keep documents in a collection

What you get

Section titled “What you get”

Documents you ask about again and again go into a collection: a named set of files read, cut into chunks and embedded once, kept on the server (~/.cache/inga/store, beside the memories). A chat turns its collections on when you type # in the message, with its Collections button, or from the Documents page; an API request names them in inga_documents; and a collection can follow a folder (notes, a wiki, a code repository), indexed again as its files change (keep-a-folder-in-sync.md). How a document is read, cut and cited, and how to ask about one file attached to a message: chat-with-documents.md.

Requirements

Section titled “Requirements”
  • What chat-with-documents.md needs: a chat model and the documents (PDF with a text layer, DOCX, HTML, Markdown or text).
  • An embedding model: collections need one (the Models page’s Embedding model section downloads and chooses it, chat-with-documents.md).

1. Start the engine

Section titled “1. Start the engine”

Get Inga, a chat model and an embedding model, and start inga serve, as chat-with-documents.md says in its steps 1 to 3; open http://127.0.0.1:8080/.

2. Keep documents in a collection

Section titled “2. Keep documents in a collection”

Open the Documents page (in the left bar). Collections need the embedding model: without one the page says so, and Choose an embedding model opens the Models page’s Embedding model panel. In the New collection, or add to one box, write a collection’s name (Manuals), then choose: Add files… picks files from this computer, indexed once, Add folder… copies a whole folder of this computer, and Map a server folder… keeps a folder of the server in sync (keep-a-folder-in-sync.md); all wait for the name. Add folder… first says how many files Inga reads (PDF, Word, HTML, Markdown, text), their size, the files it skips by type and any over 24 MiB, and sends nothing until you confirm; each file keeps its path in the folder (Manuals/sub/plan.docx), a file that fails is listed at the end without stopping the rest, and the copy is read once: to follow changes, map the folder instead. A folder dragged from the computer and dropped anywhere on the page goes the same way, its subfolders included (files dropped alone go as Add files… sends them). Each file is read by the server, cut into passages and embedded, one at a time (a 300-page PDF takes tens of seconds on a CPU). While they go, the upload’s list under the box gives every file its state: queued, in progress with its seconds, indexed with its passages (indexed · 42 passages), or error with why; its first line counts them (Upload to Manuals: 3 of 5 files added · 1 not added), and it stays until the next upload (Hide closes it). A file that fails, with Add files… as with Add folder…, does not stop the others, and is kept with its collection: the collection’s card says 1 file not added with the file’s name, why and when, also after a reload of the page or a restart of the server, until the same file is added again or you Dismiss it (Dismiss all for all of a collection’s). A collection whose every file failed has its card too. Through the API, GET /api/inga/documents gives them as upload_failed and DELETE /api/inga/documents/failed?collection=NAME[&name=FILE] dismisses them. The page lists each collection with its files, their kind, pages, passages, size and date, 10 to a page (10, 25 or 50 in Files per page; first, previous, next and last under the list, with 1–10 of 2,387); the search box above the lists keeps the files whose name or folder holds every word written, in any case. The page and the search are kept on a reload of the tab. Add files adds more to a collection, Delete deletes one file, Delete the collection a whole one and Delete all every collection. A file added again under the same name replaces the old one. Through the API, GET /api/inga/documents?q=report&offset=50&limit=50 gives one page of each collection’s files that match, with total, matched, offset and limit (collection=NAME for one collection); without those parameters every file, as before.

To see why an answer missed, search a collection’s text without asking a model: each collection’s card (and, with two or more, the bar above them for all of them) has a search box that finds the passages as a chat’s question would. Each passage says its file and page, then why it is there, plainly first: meaning #2 (cosine 0.81) · words #1 (BM25 7.31) · fused 0.0492 · reranker 0.970 (the searches that found it, its rank and score in each, its score after their fusion, the reranker’s), its citation and what the code-aware ranking did as the tooltip; How it searched under the count gives the mode, the fusion’s settings, the reranker and each step’s time in milliseconds. GET /api/inga/documents/search?q=…&collection=…&k=20 gives the same fields.

The Search playground tab of the Documents page does the same with the choices in view: the question, one collection or all of them, How it searches (words and meaning, the hybrid search chats use; meaning only, the embedding model’s vectors; words only, BM25), the Passages at most (5, 10, 20 or 50) and With the reranker, when one is set. Search runs it that way; Compare the three ways runs the question by words and meaning, by meaning only and by words only, side by side (one under the other on a phone), and says how many passages all three found and how many only meaning or only words found: a passage only words find needs the words the question uses, one only meaning finds is missed by a search of its words. With the reranker asked for and none set or loaded, the column says the order is the fusion’s. The tab is kept on a reload. Through the API: mode=dense|bm25|hybrid and rerank=false (the answer’s rerank_off).

The Language column gives each file’s language, detected from its text when it is indexed, by Inga itself with no model: the scripts first (Cyrillic, Devanagari, kana, Han), then, for Latin letters, the most frequent short words of English, Italian, French, German, Spanish and Portuguese. A file has the language of more than half its text; a dash means none has (a mix), a text too short to tell, source code, or a file indexed before languages were detected (add it or sync it again). Each passage keeps its own language too (lang in the store and in the answer’s excerpts), and the column sorts like the others. Through the API, each file of GET /api/inga/documents has lang (ISO 639-1, absent when unknown).

Under an answer, each excerpt says its language beside its page (“[2] page 7 · written in Italian”). The answer itself comes in the language of your question, whatever the language of the documents: when the excerpts are in another language, Inga tells the model so with your question, naming the language it reads from the question’s words (the tooltip of the excerpts’ line says what the model was told, or that nothing was added). To have every answer of a chat in one language, pick it in the model’s options, Answer language (Automatic, or one of the ten languages of the web UI). Through the API it is "inga_answer_language": "it" (or auto) in any chat request, and the answer’s inga_documents.answer_language says what was asked:

Two columns say where each file stands and how it was read. State: indexed; to re-index (cut by an older version of the chunker, or a folder’s source file whose grammar version changed: the folder’s next sync reads it again, an uploaded one is added again); queued or in progress while its folder’s sync runs; error, in the error colour, for a file its folder’s last sync could not read, with the reason as the tooltip (a new file that failed is listed too, with no size, since nothing of it is kept). Indexing: tree-sitter · Rust for parsed code (the grammar and its version as the tooltip), plain text: no grammar for Ruby in this build for code cut as plain text (or why the parser fell back), and text for documents with how their text was taken (text · PDF text layer, text · DOCX body, text · HTML visible text, text · Markdown, transcript · 2 speakers, last turn at 46:58), and as its tooltip what the reader kept or dropped of the layout (2 tables kept as Markdown tables, a running header or footer dropped from 14 of 14 pages: "ACME · Annual report"); an uploaded file is text, since only a folder’s files are parsed. When some files are to re-index or in error, a list beside the search shows only those (All states, To re-index (N), Error (N)); through the API state=outdated or state=error, each file’s state and indexing, and each collection’s unread files and states counts. inga docs status NAME --files prints the same in the terminal.

Every column sorts: click its header (or Tab to it and press Enter) to sort the files by it, again for the reverse order; the arrow beside the header says which. The server sorts every file of the collection, not only the page shown, then cuts the page (back to the first one on each new sort); State sorts the errors first, then the files to re-index, those queued or in progress, the indexed ones last, and Indexing by method, then language. Ties go by name. The files a folder’s sync could not read stay at the top of the first page, sorted the same way among themselves. Each collection keeps its sort on a reload of the tab. Through the API, sort= name, kind, pages, passages, size, added, state or indexing with order=asc or desc (another value is refused with a 400).

Scanned pages and pictures

Section titled “Scanned pages and pictures”

A page of a PDF without a text layer (under 20 characters: a scan, maybe with its page number) is read by a vision model, as are PNG and JPEG pictures of pages added as documents through the API (POST /api/inga/documents, inga_documents). Choose the model once, in inga.toml:

(or inga serve --set docs.ocr_model=MODEL; a model as inga serve names it, or a file). Inga loads it only for a file with scanned pages, never reads them with the chat model by itself, and asks it for the page’s text as Markdown, [illegible] where it cannot read. The page’s text then takes the page’s place, so its passages are cited with their page (scan.pdf p. 3). Indexing says text · OCR by a vision model, and its tooltip what was done: 3 pages without text read by Qwen3-VL-2B (OCR) in N s: pages 2-4, the pages cut at 2,048 tokens, and the pages not read with why (a fax or JBIG2 picture, a JPEG 2000 one). Each page read is kept by its picture and the model in ocr/ beside the store, so a file added again is not read twice. Without a model, a file of scans only is not added and the error says how many pages wait and how to choose a model; one with text pages too is added with those, its tooltip naming the scanned pages left. Through the API the file’s ocr holds the same (model, pages, cached, cut, unread, seconds, summary).

Ask a collection in a chat

Section titled “Ask a collection in a chat”

A chat asks the collections you turn on for it. There are three ways, and they all do the same thing:

  • Type # in the message. A list of your collections opens where you type, each with its files, size and last update. Keep typing to narrow it (#man finds “Manuals”, whatever the case or the accents; from two letters on, the documents whose name matches are listed too, under their collection). Up and Down move, Enter or Tab takes the one selected, Esc closes the list; a click works too. The #word leaves the message and the collection is on.
  • The Collections button under the message box opens the list of collections: tick the ones this chat uses.
  • From the Documents page: each collection has Use in a new chat and Use in this chat (the chat open now), which go to the chat with that collection on.

The collections on show as chips at the top of the message box; the × of a chip turns its collection off. With none on, the box says how to ask them (“Ask your documents: type # or choose Collections”), and an empty chat names your collections. The choice is kept with the chat (the button reads Collections (1)).

Every message then gets the passages of those collections closest to it, beside the files attached to the chat, and the report under the answer names each excerpt’s collection, file and page: 2 excerpts of Manuals, the closest to the question (embedded by nomic-embed-text-v1.5).

Through the API, the same: add a file with POST /api/inga/documents, then name the collection in any chat request.

The answer’s inga_documents is in excerpts mode, its files holds the collection ({"name": "Manuals", "kind": "collection", "files": 1, "chunks": 40}) and each excerpt says its collection, document, page and pages. GET /api/inga/documents lists the collections and their files, DELETE /api/inga/documents/ID deletes one file, DELETE /api/inga/documents?collection=NAME one collection, DELETE /api/inga/documents all of them; inga data list documents and inga data rm documents:ID do the same from the command line, and the Storage page shows them.

The chunks are embedded by the embedding model chosen when the file was added; after choosing another one, the first question on a collection embeds it again with the new one.

Reranking. When a reranker is given (docs.reranker in inga.toml, loaded when first needed), or one is loaded on the server (a model whose use is reranker, such as bge-reranker-v2-m3, loaded with Load in the Models page or named to inga serve), the best chunks are ordered again by it before the excerpts are picked: the first 32 (docs.rerank_top) of the collections’ search, with their file’s name and heading, and those of the attached files. The answer’s inga_documents names it in reranker, and each excerpt has its rerank score beside its similarity. A reranker that fails (a chunk longer than its context) is said in rerank_error, and the search’s order is kept. See 7. How the collections are searched.

In the terminal and in scheduled tasks: #name. Write # and a collection’s name in the prompt: inga run and a scheduled task then answer from that collection, with nothing else to set.

  • #name names a collection only when one has that name (in any case): #1, #TODO, C# and page.html#part stay text. A name with spaces is written #"Contratti 2026"; \#wiki is the text #wiki. The text keeps its #, so “compare #contratti with #wiki” still reads well. A #word one letter away from a collection is said once: “no collection contrati; did you mean contratti?”.

  • inga run --docs a,b names collections for every message (with the #names, the union). The closest excerpts go into the message, the encoder is the web UI’s embedding model (else the one inga docs add embedded the folder with), and a line on stderr lists the excerpts: note: 4 excerpts of contratti in the prompt (hybrid search, embedded by nomic-embed-text-v1.5): [1] contratti › rossi.pdf p.7; ....

  • A scheduled task names its collections in its tools, "tools": ["documents:contratti"] (--docs contratti); a bare documents is refused, since naming a collection is the permission. #name in its prompt works too. A collection that is gone fails the run with “no collection contratti”: a task that decides must not decide without its data. The run’s record keeps the documents report.

  • Two modes: context puts the excerpts into the prompt (the default of the chat and inga run), tool gives the model the document tools to search and read as it needs (the default of scheduled tasks, documents_mode; inga run --docs-mode tool, "inga_documents_mode": "tool" in a request). A model whose chat template takes no tools gets the excerpts instead, and Inga says so (on stderr, in the run’s warning, in the answer’s inga_documents: documents_mode_asked, documents_mode_note).

  • The document tools (tool mode) work on the collections the prompt names and no other; a call naming another is refused with “not referenced by this prompt: …”, and with no collection named there are no document tools:

    • documents_list(): the collections named, their sources (folders, uploads), files, chunks, last sync and encoder.
    • documents_search(query, collection?, where?, k?): the hybrid search of the collections (all of them fused by rank, or one), 8 hits by default (at most 20), each with its file and place (#anchor, :12-40, §heading, p. 4), a bullet’s date, a snippet of 600 characters and what to pass to document_read; where filters as inga docs search --where does.
    • document_read(file, section | page | lines): a file as collection › path (or the path alone), read from the store with numbered lines (the file’s own lines for text and Markdown, its front matter at the top): a section (§7, #revisione-prezzi, a heading’s title), a page, lines (120-180), or the whole document (its outline and its start when it is long). At most 12,000 characters a call (docs.read_chars in inga.toml), cut at a line with the lines to ask for next.
    • documents_grep(text | regex, collection?): the lines that contain a text (any case unless it has a capital) or match a regular expression (200 characters at most, bounded backtracking, 2 seconds), 50 lines at most, each collection › path:line; for names, codes and numbers an embedding misses.

    Each result is numbered as a source ([n], one number per file, shared with web_search and fetch_url), at most 8,000 characters (document_read aside), and each call is an inga_tool event of the stream (the web UI shows it under the answer) and a line on the terminal (inga: documents_search({"query": ...}) -> ...; in inga run, [documents_search {...}] on stderr). The text read is what was indexed: a file deleted from its folder since the last sync still reads, and says so.

  • The OpenAI, Anthropic and other compatible APIs never read #: a client’s text is its own. They keep inga_documents, which takes several collections.

  • Each excerpt is cited with its collection first and its place: contratti › rossi.pdf p. 4, wiki › models/x.md#timeline (cite in the answer’s inga_documents, with heading, anchor, lines and a bullet’s date). The web UI’s # picker comes in a later release.

  • An API request filters a collection with where, as inga docs search --where does: "inga_documents": [{"collection": "wiki", "where": "category=models, tags=video"}].

Tables, lists and page headers

Section titled “Tables, lists and page headers”

Inga keeps the shape of a document as it reads it, so a passage reads as the page did:

  • Tables of DOCX and HTML files become Markdown tables, the first row their header, a merged cell followed by empty ones so the columns stay in line. A long table is cut between rows, never inside one, and every passage of it starts with the header again, so a row found by a search keeps its column names:

  • Lists of DOCX files keep their items, one per line with - , nested ones indented.

  • Running headers and footers of PDF files (a line that opens or closes at least half the pages of a document of three pages or more: its title, “Confidential”, the page number) are dropped, so they do not repeat inside every passage. The page each passage is on is still cited.

Each file says what was done in layout (the Documents page’s Indexing tooltip, inga docs status NAME --files, the API’s indexing.layout). Files indexed by an older version are read again by their folder’s next sync (an uploaded one when it is added again).

Meeting transcripts, by speaker and time

Section titled “Meeting transcripts, by speaker and time”

A transcript with times is read by speaker turn: a WebVTT (.vtt) or SubRip (.srt) file, as inga transcribe meeting.wav --output vtt writes it (with --diarizer its speakers are S1, S2…, see transcribe-audio.md) or as meeting tools export it (Microsoft Teams names the speaker in each cue, <v Marco Rossi>; Zoom writes Marco Rossi: before the words). Each turn of one speaker becomes a passage under the heading of its minute and speaker, so the answers cite them:

A question that names a speaker finds their turns by the name (the headings are searched with the words). A turn ends after a minute, under its new minute, and, without speakers, at a pause of more than 2 s. Short turns (a “yes”, an “ok”) join the next ones in one passage, each keeping its own ## 12:41 Giulia line; a passage never spans two ten-minute blocks, so two passages found close in time bring the other turns of their ten minutes with them. Each passage’s anchor in the APIs is its start in seconds as a media fragment (t=750). The Documents page says transcript · 2 speakers, last turn at 46:58 in the Indexing column, the speakers’ names as its tooltip.
