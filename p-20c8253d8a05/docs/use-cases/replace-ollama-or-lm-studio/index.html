Use Inga as an Ollama or LM Studio replacement

What you get

Section titled “What you get”

Tools written for Ollama or for LM Studio’s local server talk to Inga without a change but the address, and the models those apps already downloaded run in Inga without a second copy: Ollama’s store is read as GGUF files (ollama://name:tag), LM Studio’s models folder holds plain GGUF files and MLX folders (whose quantized weights Inga converts when they load). Without Ollama installed, inga pull ollama://name:tag downloads a model of Ollama’s library itself.

Requirements

Section titled “Requirements”
  • Windows, Linux or macOS; any x86-64 or ARM64 CPU.
  • For the models: an Ollama store (~/.ollama/models) or an LM Studio models folder (~/.lmstudio/models), or any model Inga runs.

1. Get Inga

Section titled “1. Get Inga”

Download the archive for your system from the Releases page and put inga on your PATH (details); inga --version checks it.

2. Get a model

Section titled “2. Get a model”

List what the other apps already have, with whether Inga runs each model (only the metadata is read):

--ollama reads OLLAMA_MODELS (default ~/.ollama/models): every model of the official library is ollama://name:tag, others ollama://namespace/name:tag (the tag defaults to latest); a vision model’s projector, which Ollama keeps as a layer of its own, is loaded with it. --lmstudio reads LMSTUDIO_MODELS, else the downloads folder chosen in LM Studio’s settings (downloadsFolder in ~/.lmstudio/settings.json, e.g. D:\LLM), else ~/.lmstudio/models (or the older ~/.cache/lm-studio/models), and lists its GGUF files by folder, as inga scan does. The web UI’s Models tab lists both by itself (see chat-in-the-browser.md). Both are references every command takes:

LM Studio’s MLX models (the mlx-community/... folders its MLX engine runs on a Mac) are listed and run too. On the CPU and on a Mac’s GPU their quantized weights are read as stored by MLX kernels (mlx: 4-bit affine weights (groups of 64) read as stored by MLX kernels (MLX4_G64_BF16): N tensors); for an NVIDIA or Vulkan GPU, or with --quantize, they are converted when the model loads (2–4 bits to Q4_K, 5–6 to Q6_K, 8 to Q8_0, mxfp4 to MXFP4), and the terminal and the web UI’s model card say so (mlx: ... converted to Q4_K at load: N tensors). The folder is the reference:

Or download a model of Ollama’s library, without Ollama:

The name is Ollama’s (qwen3:0.6b, hhao/qwen2.5-coder-tools:7b, or registry.example.com/team/model:tag for another registry; namespace library and tag latest by default). The manifest and the blobs (the GGUF file and, when the model has them, its projector, template, parameters, system prompt and licence) are saved in Ollama’s layout in Inga’s own store, ~/.cache/inga/ollama; --ollama-store writes into Ollama’s store instead (OLLAMA_MODELS or ~/.ollama/models), where ollama list sees it. Each blob’s SHA-256 is checked while it downloads, an interrupted pull resumes, and a blob already in a known store is not downloaded twice. inga list --ollama lists the models of both stores, inga run ollama://qwen3:0.6b runs it, and on a terminal inga run offers to pull a model it does not find. The web UI’s Models tab has an Ollama library box for the same (type the name: the library has no search). A private registry’s token goes in inga.toml ([ollama] token = { env = "MY_REGISTRY_TOKEN" }).

Or download a model the usual way: inga pull hf://Qwen/Qwen3-4B-GGUF:Q4_K_M (see run-a-model-from-hugging-face.md).

3. Start the engine

Section titled “3. Start the engine”

Switch Ollama off, switch Inga on

Section titled “Switch Ollama off, switch Inga on”

Inga answers Ollama’s API on Ollama’s port, and serves the models Ollama already downloaded by their names, so the ollama command and every Ollama client keep working with Ollama stopped:

ollama list, ollama ps, ollama show qwen3:8b, ollama run qwen3:8b, ollama stop qwen3:8b, ollama pull qwen3:0.6b, ollama create, ollama cp and ollama rm then talk to Inga (OLLAMA_HOST=127.0.0.1:11434 is their default; set it to Inga’s address when Inga runs elsewhere or on another port; inga serve --port 11434 puts every API on that one port instead). /api/tags lists every model of Ollama’s store and of Inga’s own (~/.cache/inga/ollama) with its size, digest and details; a request naming one (qwen3:8b; qwen3 is qwen3:latest) loads it as the web UI’s Models page would. On Linux the Ollama service keeps its store in /usr/share/ollama/.ollama/models: point OLLAMA_MODELS there (or add the folder in the web UI) so Inga reads it. To make it permanent, inga service install --like ollama starts Inga at boot in Ollama’s place (see run-inga-as-a-service.md), after sudo systemctl disable ollama.

Or name the models

Section titled “Or name the models”

On the port the clients expect: 11434 for Ollama, 1234 for LM Studio. Stop the other app first, then --like adds a listener on its port beside Inga’s own 8080:

The extra port answers only what that app answers (Ollama: its /api/* and the OpenAI /v1/*; GET / says Ollama is running); the other APIs and the web UI are on 8080, and a request for them on 11434 gets a 404 saying so. Put it in inga.toml to keep it: [api] like = ["ollama"]. --port 11434 alone still works: every API on that one port. For a port, address or set of APIs of your own, a [[api.listen]] table:

To serve only some APIs, --api-only ollama,openai,inga,webui (or [api] enabled), or --api-disable kobold for everything but those.

One server answers both apps’ APIs, the OpenAI and Anthropic ones and the web UI at once. Give it several models (inga serve a b c --models-max 1) to switch between them by name, as both apps do (see serve-many-users-and-models.md).

4. Check that it works

Section titled “4. Check that it works”

Ollama’s listing and chat (the shapes below are Inga’s answers, captured with a small test model; the text depends on the model):

GET / answers Ollama is running to clients that do not ask for HTML, as Ollama does. /api/version reports the Ollama version whose API Inga follows (0.12.0) and Inga’s own (inga_version). /api/ps lists only the models loaded, with the memory each holds (size, size_vram on a GPU), its context and when it unloads (expires_at, from keep_alive or --idle-unload); /api/show reads the model’s GGUF without loading it: its metadata as model_info, its template, parameters, system prompt, licence, a Modelfile and its capabilities (completion, tools, vision, thinking, insert, embedding), and a model the server does not have is a 404, so ollama run pulls it. /api/generate takes suffix (fill in the middle, for code completion), returns context and takes it back; options.num_ctx loads the model again with a larger context; logprobs and top_logprobs add the tokens’ log-probabilities; /api/embed cuts an input longer than the context unless truncate is false. The Ollama routes: GET /api/version, /api/tags, /api/ps, POST /api/show, /api/chat, /api/generate, /api/embed, /api/embeddings (the fields are in serve-openai-and-anthropic-apis.md), and POST /api/pull, which downloads a model of Ollama’s library into Inga’s store with Ollama’s progress lines, so a client’s “download model” works:

The pull shows in the web UI’s download list too.

Models are made, copied and deleted as with Ollama:

FROM takes a GGUF file, a model of a store (its layers reused) or a model the server runs; ADAPTER a GGUF LoRA, loaded with the model; safetensors weights are refused (convert them to GGUF first). The models go into Inga’s store, in Ollama’s layout, so Ollama reads them too; with inga serve --ollama-store, pulls, creates and copies go into Ollama’s own store, and ollama rm deletes there (without it, a model of Ollama’s store is refused with a 403). A delete removes the blobs no other model uses. A Modelfile’s TEMPLATE (a Go template) renders the model’s prompts: Inga translates the subset Ollama’s library uses (.System, .Prompt, .Messages, .Tools, if / range, eq, and, len, slice, json, …); a construct outside it (with, printf, define) is named by ollama create and ollama show, and the GGUF’s own template is used. A model pulled from the library keeps its GGUF’s template (the same text). /api/generate takes a template of its own too.

LM Studio’s REST API:

GET /api/v0/models/{id} gives one model; POST /api/v0/completions and /api/v0/embeddings are the OpenAI routes under LM Studio’s prefix. stop_reason is eosFound, maxPredictedTokensReached or stopStringFound, as LM Studio reports it.

Clients: Open WebUI takes Inga as an Ollama connection (http://127.0.0.1:11434) or an OpenAI one (http://127.0.0.1:11434/v1); the ollama CLI itself with OLLAMA_HOST=127.0.0.1:11434. Real Ollama clients are among the real-world checks (docs/todo/real-world-checks.md, group B); so far the APIs were checked with curl and the tests.

Options worth knowing

Section titled “Options worth knowing”
Option Effect
inga list --ollama, inga list --lmstudio The other apps’ models, with whether Inga runs them.
inga pull ollama://NAME[:TAG] A model of Ollama’s library, into ~/.cache/inga/ollama (--ollama-store: into Ollama’s store).
OLLAMA_MODELS, LMSTUDIO_MODELS Where those stores are, when not in the default place.
--ollama-version V The version /api/version reports (0.12.0 by default, the Ollama API Inga follows), for a client that wants a newer one.
--ollama-store The Ollama API’s pull, create and copy write into Ollama’s own store, and its delete deletes there.
--like ollama, --like lmstudio Also listen on the other app’s port (11434, 1234), with its APIs (--like ollama:PORT for another port).
--api-disable LIST, --api-only LIST Switch API families off, or keep only those on ([api] disabled / enabled).
--port N, --host ADDR Inga’s own port (8080), or the other app’s for every API on it; --host 0.0.0.0 for other machines (with --api-key).
--models-max N Models loaded at a time when serving several.
--ctx N Context size for every request (4096 by default, capped at the model’s).

Troubleshooting

Section titled “Troubleshooting”
  • “port 11434 of 127.0.0.1 is in use — Ollama listens there by default” (or “address already in use” with --port): Ollama or LM Studio still holds the port; quit it (systemctl stop ollama, the menu-bar or tray app), or drop --like.
  • “Ollama has no model name:tag in …”: the name is not in that store; inga pull ollama://name:tag downloads it, inga list --ollama shows the names, and OLLAMA_MODELS must point to the same store Ollama uses (on Linux the system service keeps it in /usr/share/ollama/.ollama/models).
  • “no tag 8b for qwen3”: the library has no such model or tag; its page on ollama.com/library lists the tags.
  • NOT SUPPORTED next to a model: the reason follows it (an architecture or a weight type Inga does not run; see supported-models.md).
  • 404 “no model ... here”: with several models, a request must name one that GET /v1/models (or /api/tags, /api/v0/models) lists.
