Serve many users and models

What you get

Section titled “What you get”

One inga serve for a team or a household: several requests answered at the same time, their tokens computed as one batch; several models behind one address, loaded when a request names them; an API key so that only your clients get in, or a key per person or app with its own limits and usage; and the browser pages of other origins allowed when you want them.

Requirements

Section titled “Requirements”
  • Windows, Linux or macOS; any x86-64 or ARM64 CPU.
  • Memory: each model loaded at once, plus one KV cache per parallel session (inga info MODEL shows the KV cache of one session at --ctx).
  • A network you trust, or an HTTPS proxy in front: Inga’s server speaks plain HTTP.

Section titled “1. Get Inga”

Download the archive for your system from the Releases page and put inga on your PATH (details); inga --version checks it.

3. Start the engine

Section titled “3. Start the engine”

  • --parallel N: up to N requests are answered at once, each by its own session with its own KV cache (so N times the KV cache’s memory). The tokens of the sessions generating at the same time are computed as one batch, which reads the weights once for all of them: on Llama-3.2-1B, four clients get 1.5x the total tokens per second of --parallel 1. This holds on a GPU too: a dense model’s layers on a CUDA, HIP or Vulkan GPU decode the sessions together, up to eight per pass, Gemma 4 12B / 31B included, mixtures (their experts on the GPU or the CPU) and hybrid models (their DeltaNet, Mamba2 or LFM2 layers on the GPU, each session’s state apart) (Metal and WebGPU take turns, and the log says why: note: the 4 sessions of this model take turns, their decode steps not batched yet: a GPU without part copies). The attention of the sessions decoding together runs in one launch per operation on Vulkan (debug.vk_batch_attention, on) and on CUDA GPUs of compute capability 8.0 and newer (debug.cuda_batch_attention, auto: off below and on HIP); on an A100, Llama-3.2-1B-Instruct Q4_K_M at 8 users went from 482.5 to 861.2 total tokens per second with it (performance). Against other servers under load on that A100, Inga’s total stays at about 255 tokens per second from 8 to 64 clients (Qwen3-8B Q4_K_M), where llama-server reaches 756 and vLLM with a 4-bit AWQ model 4955 (the serving runs, Inga 3bbb5222). Those runs came before the bigger decode groups: from compute capability 8.0, 16 to 64 sessions of a model without experts decode in one group (debug.cuda_big_groups), and inga bench --users on that A100 gave Qwen3-8B Q4_K_M 417.1 total tokens per second at 16 users (288.4 without, +45 %) and 474.4 at 64 (279.9, +70 %); a mixture of experts keeps groups of eight (the table). inga bench model.gguf --users 1,4,8 measures what your machine gives (measure-speed.md). A request goes to the free session that already holds the longest part of its prompt; the others wait for a free session.

  • --kv-pages N: the sessions’ KV caches are pages of 16 positions from one pool per model, taken as they are written (on the CPU and on a Vulkan GPU; CUDA, ROCm and Metal still reserve each session’s context), so a short chat holds a few pages and a long one many. By default the pool holds --parallel times the context and no request waits, as before; with --kv-pages N the sessions share N pages: a request starts when the pages its prompt and max_tokens may need are not promised to the requests running, and waits in the queue otherwise. So --parallel 16 --ctx 8192 --kv-pages 2048 lets 16 users chat at once in the memory of four full contexts, as long as they do not all fill their context; giving max_tokens lets more requests start at once (without it a request may need its whole context). Prompts that start the same way (a system prompt, a document several people ask about) share their pages: the second session takes them instead of reading the prompt again. /metrics shows inga_kv_pages_total, inga_kv_pages_used and inga_kv_pages_shared. The answers are the same as with contiguous caches; --set debug.kv_paged=false (CPU) and --set debug.vk_paged_kv=false (Vulkan) go back to them.

  • Prompts mixed with the answers (on by default): with --parallel 2 or more, a new request’s prompt no longer stops the sessions that are answering, nor waits for a turn of its own. It is read by chunks of at most 512 tokens (--batch, or --prefill-yield N, when smaller), and each chunk runs in the same pass of the model as the other sessions’ next tokens: the weights are read once for both, the others’ tokens wait one chunk at most, and the new prompt starts at the next step. This works wherever the decode steps are batched (the CPU, and the layers of a CUDA, HIP or Vulkan GPU, where the chunk runs beside the batch of decode steps), for dense models, mixtures and hybrid models (their DeltaNet, Mamba2 and LFM2 states each session’s own); a prompt holding an image, and models with multi-head latent attention (DeepSeek-V2/V3, GLM-4.7-Flash, Kimi) or Gemma 3n, keep passes of their own (the log says so). The answers are the same as one request at a time. /metrics counts inga_batch_steps_total, inga_batch_decode_rows_total, inga_batch_mixed_steps_total, inga_batch_prompt_chunks_total and inga_batch_prompt_tokens_total (divided by the steps: the prompt tokens per step). --no-mixed-prefill (serve.mixed_prefill = false) gives each prompt passes of its own, as before; inga bench --users 4 --long-prompt 2048 shows the difference on your machine (the inter-token latency’s p95 of the users answering while a long prompt arrives).

  • One request alone decodes as without --parallel: while a single session is generating, its tokens are not batched: each step runs as inga run and inga bench run it (on a GPU that holds the whole model, layers, norm and output layer in one pass, and the token drawn on the GPU when the sampler allows it: no grammar or JSON schema, no log-probabilities, no logit bias, DRY, mirostat or similar). A second request arriving waits for that one step, and from the next step on the two are batched; when one is left, it goes back to decoding alone. /metrics counts those steps in inga_batch_alone_steps_total, and the tokens the GPU drew itself in inga_tokens_device_sampled_total. The answers are the same either way.

  • --prefill-yield N (0 = off): with --parallel 2 or more, a long prompt no longer stalls the sessions that are answering. Its prompt is read by passes of at most N tokens, and the other sessions’ tokens go between two passes: they wait one pass at most (a decode batch goes first, a prompt gets one pass after each batch). The answers are the same as without it (the same as --batch N); shorter passes read the prompt a little slower. 256 to 512 on a CPU is a reasonable start. The prompts are mixed with the decode steps (above), and N is the size of their chunks; the turns of passes apply to the prompts that are not mixed (with --no-mixed-prefill, an image, or a model that does not mix them).

  • Model loads queue for the RAM: a model load waits while the memory-heavy jobs running (an image drawn by an image server of the same user, another Inga’s load) would leave too little RAM for it. The load is then in phase queued in /health, GET /api/inga/status and the web UI’s load line, with what it waits for; GET /api/inga/jobs lists every heavy job of the machine’s Inga processes, running or queued.

  • Several models: clients choose with the request’s model field, one of the names GET /v1/models lists (the file name without .gguf, or the hf:// reference). The first model is loaded at start, the others when a request first names them; with --models-max N (1) at most N stay loaded, and loading another unloads the least recently used one once its requests are answered. A request without model goes to the first model. The options (--ctx, --parallel, --quantize, …) apply to every model. The web UI can load more models while the server runs (see chat-in-the-browser.md).

  • --idle-unload D (30s, 10m, 1h30m, or seconds; default 0 = never): a loaded model that no request used for D is unloaded, its memory given back, and the next request that names it loads it again (that request waits for the load). A model answering a request is never unloaded. A request can choose for its model, until the next request does: Ollama’s keep_alive on /api/chat and /api/generate ("10m", seconds, 0 to unload it once answered, -1 to keep it loaded) and LM Studio’s ttl (seconds) on /v1/chat/completions, /v1/completions and their /api/v0/ routes. POST /api/generate with no prompt and "keep_alive": 0 unloads the model at once, as Ollama does. The web UI’s Server tab shows how long each model has been idle and when it will be unloaded.

  • --vram-evict PCT (1 to 100, default off; vram_evict in [serve] of inga.toml): before a model loads, while the GPU it will use is more than PCT % full, the least recently used model with layers on that GPU that answers no request and is not kept forever (keep_alive: -1) is unloaded, and the GPU is read again. Without it, a model that fits the GPU alone but not beside the others goes (partly) to the CPU. stderr says why (serve: unloading qwen3-8b (idle 14 min, 5.1 GiB on CUDA 0) for gemma-4-12b: CUDA 0 is 91 % full (--vram-evict 80)), as do the load’s progress and the model’s evicted in /health and GET /api/inga/status. Its conversations’ prompt caches stay in RAM (within --prefix-cache), so a request that continues one after it is loaded again reads only the new tokens. With --models-max, both rules unload. The web UI’s Server settings and POST /api/inga/settings {"server": {"vram_evict": 80}} (null: off) change it while the server runs.

  • --api-key KEY (or serve.api_key in inga.toml): clients send Authorization: Bearer KEY (the OpenAI SDKs’ api_key) or x-api-key: KEY (the Anthropic SDKs’). Only GET /health and the chat page itself answer without it; the page asks for the key.

  • --api-keys FILE: a key per person or app, each with a name, the routes it may call, the models it may use and its limits (see “A key per person or app” below). --api-key keeps working beside it as one more key that may call everything.

  • --host 0.0.0.0: accept other machines (the default, 127.0.0.1, is this machine only).

  • --allow NETWORK (serve.allow in inga.toml): the server answers only these networks, addresses or CIDR ranges, IPv4 or IPv6, repeatable or a comma list (--allow 192.168.1.0/24,fd00::/8). Any other address gets a 403 that names the flag to add; this computer (127.0.0.1, ::1) is always answered. Without a list every address is answered, as before, except the administration, which answers only this computer: every /api/inga/* route that is not the chat’s own (the settings, keys, logs, models and folders, the library, devices, skills’ and documents’ sources, approvals, usage, system), /metrics, /props, /slots, /lora-adapters and Ollama’s pull, create, copy, delete and push. With a list, the administration answers the listed networks too. Another computer that is answered can still use the chat, as before: its chats, profile, memory, projects, shared items, documents and their search, and stopping a generation. Until logins arrive (0.47.0) these are the server’s, not the person’s: what one computer keeps, the others see. It can also switch three options, memory, web search and the embedding model (only one the server already has), and they change for everyone, not only for that computer; every other setting is refused with a message naming it, and the settings it reads leave out the folders and the server block. The mesh’s handover is not limited by network: it is protected only by the API key, when the server has one. inga serve says at start which of the two is in force.

  • --tls self-signed (serve.tls = "self-signed"): HTTPS with a certificate Inga makes on the first start for this computer’s names and addresses (localhost, its name and NAME.local, 127.0.0.1, ::1 and its network addresses), kept in <home>/tls/ and reused (the key readable only by you: mode 0600 on Linux and macOS; on Windows it takes the permissions of Inga’s home folder, your user profile by default). The start prints its SHA-256 fingerprint:

    A browser warns the first time: open the certificate it shows (the padlock, then the certificate’s details), check that its SHA-256 fingerprint is the one printed, and accept it. A client program trusts the file <home>/tls/self-signed.crt.pem (curl --cacert, SSL_CERT_FILE, REQUESTS_CA_BUNDLE). A new one is made when a new address appears or fewer than 30 days are left (397 days each), and the start says why.

  • --tls-cert CERT.pem --tls-key KEY.pem (serve.tls_cert, serve.tls_key): HTTPS with your own certificate (PEM, the server’s first, then its chain) and its unencrypted key; one file holding both works with either flag alone. The start names the certificate’s subject, its names, its expiry and its fingerprint, and warns when it has expired or expires within 30 days. A file that cannot be used stops the start with what is wrong and what to do (a missing file, no PEM block, a key of another certificate, an encrypted key). With HTTPS on, every port of the server speaks it (the --like ones too), the URLs it prints and gives (GET /api/inga/server) start with https://, and a browser that asks for http:// is sent to https://. Without it, on an address other machines reach, the start says that requests cross the network unencrypted.

  • --cors ORIGIN (or '*'): let web pages served from ORIGIN call the server from the browser (answers carry Access-Control-Allow-Origin, preflights are answered).

A key per person or app (--api-keys FILE)

Section titled “A key per person or app (--api-keys FILE)”

Write the keys in a JSON file (keep it readable by you only, e.g. chmod 600):

  • key is the secret itself; key_sha256 its SHA-256 (printf %s 'the-key' | sha256sum), so that the file holds no secret; key_env an environment variable holding it. Exactly one of the three.
  • routes: chat (every generation API: OpenAI, Anthropic, Ollama, LM Studio, KoboldAI, embeddings, audio, images; the default) and admin (/api/inga/*, which the web UI’s pages use, /metrics, /lora-adapters); ["*"] for both.
  • models: the models the key may name (* at the end matches a prefix); none: all. The model lists show a key only these: GET /v1/models, Ollama’s /api/tags and /api/ps, LM Studio’s /api/v0/models (and /api/v0/models/ID answers 403 for another model), so the web UI’s model menu and any client list only what the key may use. A key with no models, --api-key and a server with no keys list every model; the admin views (/api/inga/*) and the public /health are not filtered.
  • requests_per_minute (a sliding minute) and tokens_per_day (prompt and generated tokens of a UTC day; a request that starts under the limit is finished).
  • usd_per_day and usd_per_month: budgets in US dollars per UTC day and per UTC calendar month, spent at the prices of the API nodes’ models (the catalog’s list prices, or prices in nodes.json): each answer costs its prompt tokens times the input price plus its generated tokens times the output price, per million tokens. Local models cost nothing, as do a node’s models with no known price. A request let in under the budget is finished, so the last one may overshoot it by its own cost.
  • user: kept and shown as is; accounts with a login will own keys.

Inga prints what each key may do:

Keys are compared in constant time, each against every key. What clients get back:

  • 401 for a missing or unknown key;
  • 403 for a route or a model the key may not use, saying which and what it may;
  • 429 with Retry-After (seconds) and "type": "rate_limit_exceeded" when a limit is reached (“API key alice: 30 requests per minute reached; retry in 12 s”), or its tokens for the day used, with the time until midnight UTC;
  • 429 with "type": "insufficient_quota" and Retry-After when a budget is spent, until the next UTC day or month (“API key agent: its budget of $2.00 for today (UTC) is spent ($2.03 used); requests are taken again in 3 h 12 min”). The admin routes stay open.

At 80 % of a budget the server’s terminal says so, once per day or month (“warning: API key agent: 84 % of its budget for today (UTC) spent ($1.68 of $2.00)”), and the Server tab colours the budget’s bar.

The use of every key (requests, refused requests, prompt and generated tokens, today’s and in all, the last minute’s requests, the last use; the cost today, this month and in all, this month’s tokens and cost by model, and each budget’s spent share and state: ok, warning, spent) is at GET /api/inga/keys (an admin route; secrets never shown) and in the web UI’s Server tab, and kept in ~/.cache/inga/keys-usage.json across restarts (written at most every two seconds). Edit the file while the server runs: it is read again within a second; a file that no longer parses leaves the previous keys in use, and the server says so.

A response cache and a queue with limits

Section titled “A response cache and a queue with limits”

When the same requests come back (scheduled tasks, evals, scripts, a node that charges per token), keep their answers; when many clients share one machine, let them know at once that it is busy instead of waiting without end:

  • The response cache keeps each answer under the SHA-256 of the named key, the model, the messages, the tools and the sampling. The same request again gets the same answer at once, costing nothing (no tokens counted against a key’s limits, no API node called); a stream is replayed as a stream. Only deterministic requests are kept: temperature: 0, or a seed of their own (add --response-cache-sampled to keep the others, or "inga_cache": true in one request). A request opts out with "inga_cache": false or Cache-Control: no-cache; a named key with "response_cache": false. Each answer not streamed says X-Inga-Cache: hit or miss.
  • Close questions: --response-cache-semantic 0.05 also answers a conversation whose last user message is within that cosine distance of a kept one (the rest of the conversation the same), embedded by the embedding model chosen in the web UI, if it is loaded (the cache never loads a model).
  • The queue: past 8 requests waiting for a session (or 32,000 prompt tokens), a request gets a 503 with Retry-After (“the server is busy: 8 request(s) wait for a session (–max-queued-requests 8); retry in 6 s”). When a session frees, the waiting request whose prompt is already in memory (the conversation that just ended, or a copy in the prefix cache) goes first; one passed over four times goes first anyway.
  • Embeddings and rerankings together: requests to the same encoder (a BERT-family embedding model or cross-encoder) on /v1/embeddings, /embedding, /api/embed, /api/embeddings and /v1/rerank that arrive within 2 ms of each other, or while a pass of that model runs, are encoded in one pass (up to 4,096 tokens), each answer the same as alone and with its own options (truncation, dimensions, pooling). Nothing to set. Encoders run on the CPU; decoder embedding models and rerankers (Qwen3-Embedding, Qwen3-Reranker) still take one input at a time.
  • /metrics counts it all: inga_response_cache_hits_total, inga_response_cache_semantic_hits_total, inga_response_cache_misses_total, inga_response_cache_entries, inga_response_cache_bytes, inga_requests_queued, inga_requests_queued_tokens, inga_requests_rejected_total, inga_requests_served_first_total, inga_encoder_batches_total, inga_encoder_batch_requests_total, inga_encoder_batch_inputs_total.

See who calls, and change settings live

Section titled “See who calls, and change settings live”

The web UI’s Developer → Server page shows where the server answers (every LAN address with --host 0.0.0.0), the loaded models, the statistics of the last five minutes (requests per minute, errors, tokens per second, latency p50 / p95, in flight and queued, by API, model and key); Developer → Logs with Only requests shows the requests live, a row each with its status, time, model, tokens, API key’s name (never the key) and client, and the server’s events (keys refused, models loaded and unloaded, CORS origins refused) are among its lines. The same log is an admin API (kind=request, level=warn and q=TEXT filter it):

GET /api/inga/requests/stream sends the same entries as Server-Sent Events as they come, GET /api/inga/requests/stats the statistics. CORS, just-in-time loading, the idle unload and the number of models kept change while the server runs (the page’s Server settings, or POST /api/inga/settings {"server": {"cors": "*", "jit": false, "idle_unload_s": 600, "models_max": 1}}) until it stops; with just-in-time loading off, a request for a model that is not loaded gets a 409 instead of loading it.

Options worth knowing

Section titled “Options worth knowing”
Option Effect (default)
--parallel N Requests answered at once, decoded as one batch (1).
--kv-pages N Pages of 16 positions of KV cache the sessions share; a request waits while the pages it may need are promised to others (--parallel × the context, nothing waits).
--prefill-yield N Long prompts read by passes of N tokens that let the other sessions’ tokens through (0 = off).
--no-mixed-prefill Each prompt in passes of its own, not by chunks among the other sessions’ decode steps (mixed: serve.mixed_prefill, true).
--models-max N Models loaded at a time (1).
--idle-unload D Unload a model unused for D; reloaded by the next request (0 = never).
--vram-evict PCT Before a model loads, unload the least recently used idle model on its GPU while that GPU is more than PCT % full (off; above).
--max-queued-requests N, --max-queued-tokens N Past N requests (or prompt tokens) waiting, a 503 with Retry-After (no limit; above).
--response-cache SIZE Answers kept and given again to the same deterministic request (0 = off; above).
--prefix-cache SIZE Memory for copies of the KV caches of the conversations the sessions switch between, shared by them (1G; 0 = off).
--kv-disk DIR The conversations that leave that memory, or whose model is unloaded, go to disk and are read back instead of processed again (auto: ~/.cache/inga/kv; --kv-disk-max SIZE, 20G; --kv-disk-keep); see keep-long-conversations.md.
--ctx N, --cache-type q8_0 Each session’s context and its KV cache’s storage.
--api-key KEY, serve.api_key Require a key.
--api-keys FILE Named keys with routes, models, limits, budgets and usage (above).
--cors ORIGIN Allow browser pages from ORIGIN.
--allow NETWORK, serve.allow Answer only these networks (CIDR ranges or addresses); the administration only this computer without a list.
--tls self-signed, serve.tls HTTPS with a certificate Inga makes and keeps; its fingerprint at start.
--tls-cert FILE, --tls-key FILE HTTPS with your certificate and key (PEM).
--host ADDR, --port N Where to listen (127.0.0.1:8080).

Troubleshooting

Section titled “Troubleshooting”
  • 404 “no model X here; the models are: …”: the request names a model the server does not serve; use one of the names listed.
  • Requests wait: all sessions are busy; raise --parallel if the memory allows (more sessions share the memory bandwidth, so each one’s speed drops while the total grows), or set --max-queued-requests so clients get a 503 with Retry-After instead.
  • Requests wait though sessions are free: with --kv-pages, the pages their prompts and max_tokens may need are promised to the requests running; raise --kv-pages, or have clients send max_tokens. A 503 “the KV pages are all in use” means a step found no page left (the prefix cache’s copies had been given back already): raise --kv-pages.
  • 503 “the server is busy”: the queue’s limits (--max-queued-requests, --max-queued-tokens) are reached; the client retries after Retry-After.
  • Answers stall while someone sends a long prompt: with --parallel 2 or more the prompts are mixed with the answers by default; check that --no-mixed-prefill is not set, and the log for a prompt that keeps passes of its own (an image, a model with latent attention or Gemma 3n). For those, add --prefill-yield 512.
  • A load says queued until there is RAM for it: another memory-heavy job runs (an image, another Inga’s load; GET /api/inga/jobs names it); the load starts when it ends.
  • Out of memory when a second model loads: lower --models-max (models are then swapped, and the first request after a swap waits for the load), or --ctx.
  • The first request after a quiet spell is slow: --idle-unload unloaded the model and the request waits for it to load again; raise D, or send keep_alive: -1.
  • --lookup or a request’s lora field are refused or ignored: per-request LoRA adapters and prompt lookup work with --parallel 1 only.
  • 401 “invalid or missing API key”: give the client the server’s key.
