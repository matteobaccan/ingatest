Integrate Inga in a JavaScript application

The browser build’s JavaScript API is an experiment, the module of Inga in the browser.

What you get

Section titled “What you get”

Two ways to put a local model behind your own JavaScript, web or not:

A. Inga inside your web page B. Your JavaScript talks to inga serve
Where the model runs In the visitor’s browser tab (WebAssembly on the CPU, or WebGPU) In the inga program, on your machine or a server
What the user installs Nothing inga (one file)
JavaScript runtimes Browsers (a Web Worker) Any: Node.js, Deno, Bun, Electron, a browser page
Models GGUF language models; about 4 GB of memory at most Everything Inga runs: larger models, the GPU natively, images, speech, tools, documents
API The module’s own (Loader, Model, …) OpenAI’s, Ollama’s, Anthropic’s (HTTP)

Choose A for a web app whose visitors chat with a small model and nothing leaves their device; choose B for everything else (a Node.js service, an Electron app, a script, a web app with a server behind it).

Nothing here is published to npm: A uses the files tools/build-wasm.sh builds, B any HTTP client.

Requirements

Section titled “Requirements”
  • A: Rust with the wasm32-unknown-unknown target and the wasm-bindgen command of the version crates/inga-wasm/Cargo.toml names (0.2.130 today), to build the module; a static web server over HTTPS (or http://localhost); a browser with module workers and WebAssembly SIMD (Chrome or Edge 102+, Firefox 114+, Safari 16.4+); WebGPU only for the GPU.
  • B: inga and a model (chat-with-a-local-gguf-model.md); for the examples, Node.js 18 or later (built-in fetch; they were run on 22), Bun, or Deno.

A. Inga inside your web page

Section titled “A. Inga inside your web page”

A1. Build the module

Section titled “A1. Build the module”

web/pkg/ then holds inga_wasm.js (the bindings, an ES module) and inga_wasm_bg.wasm (the engine with its WebGPU path: 7.6 MB, 2.0 MB gzipped, measured on 0.41.0). Without THREADS=0, and with the nightly toolchain the script names, it also builds web/pkg-threads/, the module that runs on every core (see A5).

A2. The files to host

Section titled “A2. The files to host”

Copy next to your page:

File What for
pkg/inga_wasm.js, pkg/inga_wasm_bg.wasm The engine: always
your worker (inga-worker.js below) Runs the engine off the page’s main thread
pkg-threads/inga_wasm.js, pkg-threads/inga_wasm_bg.wasm, web/thread.js Optional: every core (A5)

Serve .wasm as application/wasm (wasm-bindgen’s loader compiles it while it downloads; with another type it falls back to a slower path and warns on the console). The model itself is any GGUF file the page can fetch: Hugging Face’s https://huggingface.co/OWNER/REPO/resolve/main/FILE.gguf links answer cross-origin requests, or host it yourself.

A4. The JavaScript API

Section titled “A4. The JavaScript API”

What pkg/inga_wasm.js exports (crates/inga-wasm/src/web.rs documents each one):

Export What it does
init() (default export) Fetches and compiles the .wasm next to the module; init({ module_or_path }) takes a URL, bytes or a WebAssembly.Module
new Loader() A GGUF file received in chunks: push(Uint8Array) in file order, received(), then finish(name, ctx, kv), which returns the Model (ctx 0: 2048; kv "f16" (default), "q8_0" or "q4_0")
await Gpu.create(), Loader.withGpu(gpu) The WebGPU device, and a loader that sends the layers’ weights to it as they arrive (the GPU’s KV cache is F16)
openModel(name, size, read, budget, ctx, progress, ...) A model read at offsets by read(at, view), which fills view and returns how many bytes it wrote (a FileSystemSyncAccessHandle’s read(view, { at }), in a worker); within budget bytes (negative: no limit) what does not fit is read from the file while it runs; optionally a draft model
openModelGpu(gpu, name, size, read, budget, gpuBudget, ctx, progress, separate) The same on the GPU
model.chat(messagesJson, optsJson, onPiece) Answers a chat through the model’s chat template; onPiece(text, reasoning) gets the answer as it is decoded (reasoning true for a thinking model’s reasoning) and stops it by returning true; returns the statistics as JSON
model.complete(text, optsJson, onPiece) Continues a text as written, no chat template
model.chatBegin(...), model.completeBegin(...), model.step(onPiece), await model.ready(), model.stats() The same a token at a time: step returns 0 (a token), 1 (waiting for the GPU: await model.ready(), then step again) or 2 (done). A model on the GPU answers this way
model.countChat(messagesJson, optsJson) The tokens a chat takes in the context
model.reset(), model.info(), model.free() Forget the conversation; what the model is (JSON); release it
stop(), memoryBytes(), hasWebGpu(), hasThreads(), lastPanic() Stop the answer running (from onPiece); the module’s memory; the build’s features; why the module stopped after a trap

The options (optsJson, every key optional): max_tokens (default 256), temperature, top_k, top_p, min_p, repeat_penalty, presence_penalty, frequency_penalty, seed, and thinking (true / false, given to the chat template as enable_thinking). Errors are thrown as JavaScript Errors with Inga’s message (“the options are not JSON: …”, a model the GPU does not run, …).

When Gpu.create() or finish throws (no WebGPU, a model or weight type the GPU does not run), load the file again with new Loader(), on the CPU: the browser page does the same and says why (wasm.md, “What works”).

A5. Every core: cross-origin isolation

Section titled “A5. Every core: cross-origin isolation”

The module of pkg/ runs on one thread. pkg-threads/ uses WebAssembly threads, which browsers allow only on a page that is cross-origin isolated: served with

(then self.crossOriginIsolated is true). Every resource of the page must then be same-origin or allowed by CORS; Hugging Face’s downloads are CORS requests, so they work. A host that cannot send headers (GitHub Pages) can use the browser page’s service worker, web/coi.js and web/coi-sw.js. The threaded module has no WebGPU path: load pkg/ for the GPU. Starting its threads takes a few lines that web/worker.js’s start() and startThreads() show: inga.threadInit() gives the compiled module and its shared memory, each extra Web Worker (web/thread.js) instantiates the module on them and calls runWorker(), and the model is loaded once waitingWorkers() counts them all. The browser page measured 73.8–95.8 / 34.1–42.0 prompt / answer tokens per second on 4 threads against 25.1–30.0 / 10.6–13.9 on one (SmolLM2-135M-shaped Q8_0, headless Chromium on a 4-vCPU Linux container; run-a-model-inside-the-browser.md).

A6. Outside a browser: Node.js

Section titled “A6. Outside a browser: Node.js”

The module is built for browsers (wasm-bindgen --target web), and Node.js is not a target the project tests. Its CPU path does run in Node.js, though, when the .wasm bytes are handed to init (Node’s fetch does not read file: URLs): checked once, by hand, with Node.js 22.22 on Linux, the 0.41.0 module and SmolLM2-135M-Instruct Q8_0 (one thread, about 20 tokens per second on a container’s CPU):

(new Loader() with the file pushed in chunks works too.) What does not: the GPU (Gpu.create() stops the module with a Rust panic, “Accessing the GPU is only supported on the main thread or from a dedicated worker”: Node has no WebGPU), the threaded module (not tried), and anything beyond one model’s chat and completion. For Node.js, Deno and Bun, B below is the supported way: inga serve runs every model Inga runs, natively, on every core and GPU.

B. Your JavaScript talks to inga serve

Section titled “B. Your JavaScript talks to inga serve”

B1. Start the server

Section titled “B1. Start the server”

It listens on http://127.0.0.1:8080 (--port, --host 0.0.0.0 for the other machines of your network) and answers, on that one port, OpenAI’s API (/v1/...), Ollama’s (/api/chat, /api/generate, /api/tags, …), Anthropic’s (/v1/messages) and others (serve-openai-and-anthropic-apis.md, docs/api/). With one model, any model name (or none) goes to it; GET /v1/models lists the names when there are several.

B2. OpenAI’s API with fetch (Node.js, Deno, Bun, Electron, a browser)

Section titled “B2. OpenAI’s API with fetch (Node.js, Deno, Bun, Electron, a browser)”

The same file runs unchanged with node chat.mjs and bun chat.mjs (both checked), and should with deno run --allow-net chat.mjs (not checked). A thinking model’s reasoning comes apart, in message.reasoning_content.

B3. Streaming (Server-Sent Events)

Section titled “B3. Streaming (Server-Sent Events)”

With "stream": true the answer comes as data: {json} lines, a chunk per piece (choices[0].delta.content, or delta.reasoning_content for the reasoning), and ends with data: [DONE]:

for await over res.body works in Node.js and Bun (checked) and in Deno; in a browser, read res.body.getReader() in a loop (as in A3) and write to the page instead of process.stdout. Add "stream_options": { "include_usage": true } for the token counts in the last chunk.

B4. The openai npm package

Section titled “B4. The openai npm package”

The package needs an API key even when the server asks for none: any text does. It also reads OPENAI_BASE_URL and OPENAI_API_KEY, which inga connect openai-sdk prints for your server. Tool calling, JSON output and embeddings use the same client (tools, response_format, client.embeddings.create; get-structured-output.md, embeddings-reranking-and-classification.md). In a browser page the package refuses to run unless you pass dangerouslyAllowBrowser: true, because a key in a page is visible to anyone who opens it: with a local server and no key that is harmless; otherwise keep the key on a server of yours.

B5. Ollama’s API

Section titled “B5. Ollama’s API”

For code written for Ollama (or the ollama npm package), the same address:

"stream": false gives one object. With the ollama package, new Ollama({ host: "http://127.0.0.1:8080" }). To take Ollama’s own port as well, start the server with --like ollama (it also listens on 11434).

B6. API keys

Section titled “B6. API keys”

inga serve MODEL --api-key SECRET (or serve.api_key in inga.toml, or named keys with --api-keys FILE, serve-many-users-and-models.md) refuses every request without the key, sent as Authorization: Bearer SECRET, x-api-key: SECRET or api-key: SECRET:

(apiKey in the openai package’s constructor does the same). Keep the key out of code a browser downloads.

B7. Calling it from a web page: CORS

Section titled “B7. Calling it from a web page: CORS”

Programs (Node.js, Deno, Bun, an Electron app’s main process) send no Origin header with fetch, so CORS does not concern them (Node.js and Bun checked; Deno and Electron not). A web page does (an Electron window too, with its own origin), and by default inga serve lets only its own web UI’s page act on it: a page of another origin may read (GET), but its POSTs are refused with a 403 that names the origin, and the browser keeps the answers of the reads from the page. Allow your page’s origin:

(--cors '*' allows any origin; serve.cors in inga.toml, or the web UI’s Developer page, while the server runs). The server then answers the browser’s preflight (OPTIONS, with Authorization, Content-Type, x-api-key, api-key and anthropic-version allowed) and adds Access-Control-Allow-Origin to every answer. A refused origin is said once, with how to allow it, among the server’s requests (the web UI’s Logs page).

Troubleshooting

Section titled “Troubleshooting”
  • A: WebAssembly.instantiate fails or the page stops with “unreachable”: lastPanic() says why the module stopped (often memory: a model larger than the 4 GiB a 32-bit module addresses, or a browser that refused to grow it; try a smaller model or context). The model that was running must not be used again: free() it and load again.
  • A: the page freezes while it answers: the module runs on the thread that calls it; run it in a Web Worker, as in A3.
  • A: SharedArrayBuffer is not defined / crossOriginIsolated is false: the threaded module needs the two headers of A5; without them use pkg/.
  • B: TypeError: fetch failed / ECONNREFUSED: the server is not running, or listens elsewhere (inga serve prints its addresses when it starts); localhost may resolve to ::1 first on some systems: use 127.0.0.1.
  • B: 401: the server has an API key (B6). 403 “a page of … may not call …”: the page’s origin is not allowed (B7).
  • B: the answer stops early: raise max_tokens; the answer’s finish_reason is length when it ran out (serve-openai-and-anthropic-apis.md).

What was checked

Section titled “What was checked”
  • A3 (the worker and page above, the model served from the same folder instead of Hugging Face) ran in headless Chromium on Linux with the 0.41.0 module built by THREADS=0 sh tools/build-wasm.sh (inga_wasm_bg.wasm 7.6 MB, 2.0 MB gzipped): the haiku streamed, then its speed. The GPU loop of A4 was not run here (no WebGPU adapter in that browser); it is what web/worker.js does on the GPU. The threaded module of A5 was not built or run for this guide.
  • A6’s Node.js code ran as said there (both openModel and Loader, chat and the chatBegin / step loop).
  • B2–B5’s client code ran in Node.js 22.22 (B4 with openai 4.x) and B2, B3 and B5 in Bun, against a stand-in server that answers in the formats inga serve writes (OpenAI’s JSON and Server-Sent Events, Ollama’s lines of JSON). Not run against a real inga serve, nor in Deno or Electron: the routes, the options, --cors, the preflight and the API key headers were read from the server’s code (crates/inga-server/src/lib.rs, http.rs, requests.rs, keys.rs) and docs/api/.
