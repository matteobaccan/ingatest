Long conversations: compaction, context shift, rotating cache, saved chats

What you get

Section titled “What you get”

Chats that outlive the model’s context and your terminal session: the older turns summarized by the model when a chat nears the end of its context, or dropped when it no longer fits (instead of an error), answers that go on past the end of the context, conversations saved to a file and resumed later (as messages, or with their KV cache so nothing is processed again), and a server that keeps the KV caches of the conversations it switches between.

Requirements

Section titled “Requirements”
  • Windows, Linux or macOS; any x86-64 or ARM64 CPU; any chat model Inga runs.
  • Memory for the context you choose (the KV cache grows with --ctx; see step 3).

1. Get Inga

Section titled “1. Get Inga”

Download the archive for your system from the Releases page and put inga on your PATH (details); inga --version checks it.

2. Get a model

Section titled “2. Get a model”

Any chat model; see chat-with-a-local-gguf-model.md or run-a-model-from-hugging-face.md. The examples below were captured with a two-layer test model and a context of 64 tokens, to make the limits show quickly; the answers are noise.

3. Start the engine

Section titled “3. Start the engine”

First give the chat as much context as the memory allows: --ctx N (4096 by default, capped at the model’s trained context, which inga info shows), and --cache-type q8_0 to halve the KV cache’s memory, or q4_0 / q5_0 / q4_k to take it to about a quarter or a third (keys and values rotated head by head by a Walsh-Hadamard transform before they are quantized, q8_0 too; 4 bits cost some models much, Qwen3-0.6B four times its perplexity with q4_0; measure what it costs on your model with inga perplexity --cache-type q4_0, see measure-model-quality.md). inga info MODEL --cache-type q4_0 prints the KV cache’s size for the default context; it grows linearly with --ctx. Layers on a GPU keep their cache in f16 whatever the type.

When the chat nears the end of the context: compaction

Section titled “When the chat nears the end of the context: compaction”

The model summarizes the older turns into one text, kept in the system message after the line Summary of the earlier conversation:, and the chat goes on with the summary and the recent turns: what was decided at the start is still known, in fewer tokens. A later summary covers the earlier one. In the chat, /compact does it now (your last exchange stays as it is) and /compact show prints the summary; and before an answer whose prompt takes --compact-at F of the context (0.8 by default, 0 turns it off) it happens by itself:

The summary is about half of what it replaces (64 to 512 tokens); one that would not shorten the prompt is not used. /system TEXT keeps it, /clear drops it, /save saves it with the system message. A chat with images, audio or videos keeps every turn.

inga serve --compact-at F (0.8 by default) does it between the rounds of a long tool run (web searches, memory, skills, MCP tools): when the next round’s prompt takes F of the context, the earlier rounds are summarized, the question and the last call kept, and the run goes on; the stream says so with an inga_compact delta (summarized, summary, tokens_before, tokens_after). Any client can ask for a summary with POST /api/inga/compact ({model, messages, keep}, OpenAI’s messages; keep is the number of steps kept, 2 by default), which answers the compacted messages.

In the web UI, the context ring under the message box opens the context’s details, where Compact summarizes the chat now; a chat whose last prompt took 80 % of the context is compacted before its next message. The summary shows where the old messages were, with Edit (the model gets the edited text from the next message on), the original messages collapsed under it (kept in the chat and in its exports, no longer sent) and Restore to bring them back.

When the chat no longer fits: --context-shift

Section titled “When the chat no longer fits: --context-shift”

Without it, a turn that does not fit is refused, and every later one too:

With --context-shift, the oldest turns after the system message are dropped until the new one fits with room for the answer (up to -n, at most half the context):

inga serve --context-shift does the same for every request (without it, the request gets a 400). Chats with images or audio keep every turn.

When an answer reaches the end of the context: --cache-cap N

Section titled “When an answer reaches the end of the context: --cache-cap N”

An answer that fills the context stops there (context full). With --cache-cap N (it implies --ctx N --context-shift), the KV cache never fills: when an answer reaches N tokens, the older half of the conversation (after its first 4 tokens, which the attention leans on) is forgotten, the positions of the rest are shifted, and the answer goes on. The model then no longer sees what was forgotten. Not for Qwen3.5 / Qwen3-Next (their DeltaNet state cannot forget part of the past). It runs on the CPU: under --device auto (the default) a model with --cache-cap keeps every layer there and says so (gpu: not used, ...), since a GPU’s layers cannot forget positions; a GPU named with --device is refused with --cache-cap.

Save and resume a chat

Section titled “Save and resume a chat”

In the chat, /save FILE writes the conversation as JSON (OpenAI’s [{"role", "content"}], images as [image]) and /load FILE replaces the current one; --history FILE starts from a saved one. /clear starts over (the system prompt kept) and /undo removes the last exchange, to make room without leaving the chat; /show and /stats tell the context used (see the command-line reference’s chat commands):

A history is processed again when it is loaded. To skip that, --prompt-cache FILE saves the KV cache itself after each answer and restores it on the next run (same model, same --cache-type), so only what is new is processed:

In the server: the prefix cache

Section titled “In the server: the prefix cache”

inga serve keeps each session’s KV cache between requests, so a new turn of a chat only processes the new messages. When requests switch between conversations (several clients, or one client with several chats), the server keeps copies of the KV caches of the conversations it leaves, up to --prefix-cache SIZE (1G by default, shared by the sessions; 0 turns it off), and restores the one sharing the longest beginning with the next request. OpenAI answers report the tokens taken from the cache in usage.prompt_tokens_details.cached_tokens; /metrics counts them in inga_prompt_tokens_cached_total.

This holds for the layers on a GPU too (CUDA, Vulkan, Metal): their keys and values and a hybrid model’s DeltaNet or Mamba2 states are copied to RAM when the server leaves a conversation and written back to the GPU when a request continues it, bit for bit, and they go to --kv-disk with the rest. The copies count in --prefix-cache like the CPU’s. The load says so:

Layers run on other machines (a mesh) keep no copies: their KV caches stay there.

Before the first message: the warm-up (chat.warm, auto by default)

Section titled “Before the first message: the warm-up (chat.warm, auto by default)”

The first message of a chat has nothing cached: the system prompt and the tools’ definitions (thousands of tokens with web search, MCP, the workspace and skills on) are processed when it is sent. With chat.warm=auto, the default, the web UI asks the server to process that part while the chat waits for its first message: when a model is loaded, a new chat is opened, or the system prompt, the tools or the model change (POST /api/inga/warm, with the chat request’s body). The message then finds it in the cache, and its cached_tokens count it. A chat with a system prompt of about 500 tokens, Qwen3-0.6B Q8_0 on a 4-vCPU Xeon:

and the first answers of such chats started after 0.2 s instead of 1.3 s (medians of 5); with about 3,600 tokens of system prompt and tools, after 1.0 s instead of 20 s (Qwen3-8B Q4_K_M: 1.8 s instead of 112 s; performance.md).

It runs only while the model is idle, never loads a model nor uses an API node’s, and it goes by passes of 128 tokens: a request that comes stops it at the end of the pass under way (what it processed stays usable), so that request waits for one pass at most — about 0.4 s with Qwen3-0.6B and 2.3 s with Qwen3-8B on that CPU. auto warms the models whose layers all run on the CPU, where it was measured; true warms on a GPU too, unmeasured; false (--set chat.warm=false) never. The log says what each warm-up did (warm (chat.warm, POST /api/inga/warm): MODEL: 498 of the 498 tokens before the first message in the cache (491 processed in 1361 ms, 4 pass(es))).

Before that, when a chat model loads, the server runs a warm-up of its own before it says the model is ready, as llama.cpp’s server does: a mixture’s experts on the CPU are read from the file, then a short prompt and one token are run (on a GPU, its kernels are made ready), and that session is emptied. The first request then does not pay for it; the log says how long it took (load warm-up: 0.3 s (a 2-token prompt and one token on the CPU), done before the model is said to be ready, ...). chat.warm runs only after it, on a model said to be ready. Hybrid models (DeltaNet, Mamba) reuse it too. When it does nothing it says why: {"skipped": "chat.warm is off on this server (...)"}. The browser page (web/) has the same in Settings, Process ahead (off by default, on the CPU only, unmeasured in a browser).

On disk: conversations that leave the RAM

Section titled “On disk: conversations that leave the RAM”

With --kv-disk DIR (auto: ~/.cache/inga/kv), the copies that no longer fit in --prefix-cache are written to disk instead of being dropped, and so are the conversations of a model being unloaded (--idle-unload, --models-max); a request that continues one reads it back instead of processing it again — reading is many times faster than recomputing a long prompt on the CPU, and the answer is the same, bit for bit. With --prefix-cache 0 every conversation the server leaves goes straight to disk. The files take at most --kv-disk-max SIZE (20G; the least recently used go first), are readable by their owner only (they hold the prompts in clear) and are deleted when the server stops, unless --kv-disk-keep keeps them for the next start. A file cut short or damaged is noticed (its checksum), deleted, and the prompt processed again. The server says what it does:

inga data list kv (and the web UI’s Storage page) lists them: a run-* entry per running server (in use until it stops), one entry per model for the kept files.

Across restarts

Section titled “Across restarts”

--kv-disk-keep (alone it means --kv-disk auto) keeps the files for the next start, and makes the server stop in order: on Ctrl-C or SIGTERM (systemd, Docker, kill) it takes no more requests, answers those in flight (30 s at most; Ctrl-C again stops at once), writes the prefix cache’s copies and each session’s conversation to ~/.cache/inga/kv/<model>/, and exits. The next start says what it found, and the first prompt that continues a kept conversation reads it back:

A kept file is used only by the same model and settings: its layout, a sample of the model file’s bytes (a fine-tune or a new download with the same layout is another model), the Inga version, the KV cache type, --experts-precision, --cache-cap and the LoRA weights. The others are never read and leave as the least recently used. --kv-disk-max holds at start too. A hybrid model (Qwen3.5, Qwen3-Next) keeps its recurrent state at the conversation’s end only, so its kept conversations serve the next turn, not the same prompt asked again.

A context larger than the RAM

Section titled “A context larger than the RAM”

--kv-ram SIZE keeps at most SIZE of a context’s keys and values in RAM; the older positions go, by blocks of 256, to a file of each layer under --kv-disk (default ~/.cache/inga/kv), memory-mapped and read from there by attention. The output is the same as with the whole cache in RAM; the speed of the long context is the disk’s. The files go with the session. Not with --cache-cap (a cache split with the disk does not forget positions).

4. Check that it works

Section titled “4. Check that it works”

The (N cached) count in the line after each answer (or cached_tokens in the API) is the part of the prompt that was not processed again. It should be close to the whole conversation on every turn but the first, and after --prompt-cache or a switch back to a conversation the server cached.

Options worth knowing

Section titled “Options worth knowing”
Option Effect
--ctx N Context size (4096, capped at the model’s).
--cache-type q8_0 Half the KV cache memory, for a longer context in the same RAM.
--cache-type q4_0 About a quarter of it (q5_0, q4_k: rows of 256), rotated first.
--compact-at F Summarize the older turns once the prompt takes F of the context (0.8; run, and serve’s tool runs).
/compact [show] Summarize the older turns now; show the summary (run).
--context-shift Drop the oldest turns when a chat no longer fits (run, serve).
--cache-cap N A context of N tokens that never fills (run, serve).
--prompt-cache FILE Save and restore the KV cache (run).
--history FILE, /save FILE, /load FILE Save and resume the messages (run).
--prefix-cache SIZE Memory for the KV caches of other conversations (serve, 1G).
--kv-disk DIR Conversations that leave the RAM go to disk and come back from there (serve); where --kv-ram puts its blocks (run, serve).
--kv-disk-max SIZE, --kv-disk-keep Disk space for them (20G); keep them, with the prefix cache and the open conversations, for the next start (serve).
--kv-ram SIZE RAM for a context’s KV cache; the older blocks on disk (run, serve).
--batch N Process long prompts by passes of at most N tokens (2048): less memory.

Troubleshooting

Section titled “Troubleshooting”
  • “the prompt has N tokens, which exceeds the maximum context length of M tokens of this session; use a larger –ctx”: raise --ctx, or add --context-shift.
  • “the prompt has N tokens, which exceeds the model’s maximum context length of M tokens”: no --ctx helps; shorten the conversation, or use --context-shift.
  • The answer ends with context full: use --cache-cap, or a larger --ctx.
  • The model forgot the start of the chat: that is what context shift and --cache-cap do; compaction keeps a summary of it instead, and a larger --ctx keeps more.
  • “the summary was not shorter than the turns it replaced”: the turns before the last exchange are short already; nothing changed.
  • The summary missed something: edit it in the web UI; in the chat, tell the model again (/compact show prints what it kept).
  • “note: FILE not used: …”: the file was written for another model, KV cache type or context size; Inga processes the prompt again and overwrites the file. A restored conversation is reused only for the part the new prompt shares with it.
