Let Inga propose a smaller variant of a model, and pick which one runs

What you get

Section titled “What you get”

A model becomes one entry with several variants: the original you downloaded, plus the quantized copies Inga made of it. Inga looks at the model and at this machine, proposes the variant worth making (where it would run, how much faster, how much disk it takes, how close to the original it stays), makes it only when you say yes, and lets you choose which variant runs, on the command line and in the web UI. The original is never changed nor deleted, and it stays the default until you pick a variant.

A variant is a real GGUF file, the one inga quantize writes (byte for byte the file of llama.cpp’s llama-quantize), so llama.cpp and LM Studio open it too (quantize-a-model.md writes such files where you choose).

Requirements

Section titled “Requirements”
  • Windows, Linux or macOS; any x86-64 or ARM64 CPU.
  • A model Inga runs: a GGUF file, a Hugging Face model directory or an hf:// reference. Variants are made from 16- or 32-bit models best; a quantized model is only offered smaller types, with a warning.
  • Disk space for the variant (about half the F16 size for Q8_0, a quarter for Q4_K_M), in the home (~/.cache/inga, or --home DIR).

1. Get Inga

Section titled “1. Get Inga”

Download the archive for your system from the Releases page and put inga on your PATH (details); inga --version checks it.

3. See what Inga proposes

Section titled “3. See what Inga proposes”

Two lines are about variants:

The proposal follows a table:

The original Proposed Never proposed
F32 / F16 / BF16 Q8_0 (practically lossless), Q6_K, Q4_K_M; once an importance matrix is kept for the model (inga imatrix MODEL -f TEXT), also the i-quants IQ4_XS, IQ3_M, IQ3_XXS, IQ2_M and IQ2_XXS, made with it —
Already quantized (Q8_0, Q6_K, Q5_K, Q4_K, …) a smaller type, with a warning: quantizing a quantized file adds the losses anything as precise or more: precision lost is not recovered
A mixture of experts also the mixed precision of --experts-precision auto (listed; it is a run option, not a file) —

Each candidate is planned by the memory planner (what inga info prints as plan and estimate) with the GPU too: the GPU --device would pick (as inga info --device plans it: its free memory less a reserve) holds as many layers as fit, the rest goes to the RAM, what is left is read from disk. Inga proposes the most precise one that runs with nothing read from disk (on the GPU, on the GPU and from RAM, or from RAM), else the one reading the least per token. When the original already runs from memory, nothing is proposed (optimize: nothing proposed: the original runs from RAM here). inga info says which GPU it planned with (optimize: planned with CUDA 0 Quadro P1000 (3.2 GiB for layers)); --device cpu plans without one.

inga optimize without --type, when it proposes nothing, lists every candidate with where it would run and how much of it would be in VRAM, in RAM and on disk:

4. Make the variant

Section titled “4. Make the variant”

Without --type, Inga makes the variant it proposes (and says so, without converting anything, when it proposes none); --type q4_k_m makes another one. A progress bar shows the tensors being written; the last line gives the file:

Where it is kept: ~/.cache/inga/cache/models/<key>/<type>.gguf, <key> the SHA-256 of the original’s header, tensor table and size, with a manifest.json (the original’s reference and path, each variant’s type, size, date, the Inga that made it and its measured quality). A conversion is written to <key>/<type>.gguf.part, layer by layer (the tensors outside the layers first, then layer 0, 1, …); after each layer the file is made durable and the manifest’s partial list says how many layers it holds. A conversion stopped half-way (Ctrl-C, a crash, the machine turned off) is never used, and the next inga optimize --type of that type resumes it from the next missing layer:

The result is the same file, byte for byte, as a conversion made in one go. Two Inga never write the same variant at once (the second is refused while the first runs).

Make it while the model runs

Section titled “Make it while the model runs”

A model larger than the RAM runs with its layers streamed from disk, each read for every token. Converting it apart would read the whole original once more; instead, Inga can convert each layer right after the forward pass has read it, so the original is read once and the variant is appended layer by layer:

The first prompt converts every layer (so it is slower than the next ones); a run stopped before keeps the layers done, and the next run resumes. The variant is used only once whole, then remembered as the model’s choice. To ask for it ahead of the next run:

(A model that is not streamed from disk is then converted in a thread of its own while it runs; inga run finishes the conversion before it exits.)

5. Run it

Section titled “5. Run it”

The choice is remembered for the model (in ~/.cache/inga/settings.json): the next inga run, serve, bench or info of it runs the Q8_0 variant without --variant, and says so. --variant original goes back to the original (the default).

inga list shows each model’s variants under it, inga info lists them with their size, their measured quality once checked, and the conversions not complete.

With several models, inga serve takes the variant of each one by name: --variant MODEL=T, repeatable, MODEL as written on the command line or as the model is served (@ already names a revision in hf:// references, hence =):

6. Check it

Section titled “6. Check it”

How close is a variant to the original? Check measures it, as inga perplexity --kl-base does, on a short built-in text (the beginning of Alice’s Adventures in Wonderland and of Le avventure di Pinocchio, public domain: a few thousand tokens of English and Italian):

  • KL: the mean KL divergence of the variant’s predictions from the original’s (0: the same distributions);
  • same top token: the share of tokens where both put the same token first;
  • perplexity x: the variant’s perplexity over the original’s (1: the same).

The numbers are kept in the variant’s manifest, and shown next to it by inga info, inga list and the web UI. Without --variant, every variant made is checked; -f FILE measures on your own text. It takes about a minute for a small model, longer for a large one (both models run over the text).

7. In the web UI

Section titled “7. In the web UI”

Open http://127.0.0.1:8080/, then Models:

  • Optimize shows on the row of a model it can make smaller: never for a file already in the smallest types Inga proposes (Q1_0, Q2_K, Q3_K), whose variants would not be an improvement. For a model with a proposal its tooltip names it (Inga proposes a Q8_0 variant of this model for this machine).

  • Optimize on a model’s row (and in its Info window, also from the Server page) opens a window with the original as its first row (its size, where it runs, its speed estimate) and every candidate below it: its size (the disk its file takes) and how much smaller than the original (−42 %), where it would run (on the GPU, on the GPU and from RAM, from RAM, experts partly from disk, streamed from disk) with its VRAM / RAM / disk shares, the speed estimate and its change from the original’s (+73 %), the expected quality and, once checked, the measured one; the proposed one highlighted, and the GPU planned with. Make asks first, then converts in the background with a progress bar; the window can be closed meanwhile. A stopped conversion shows how far it got and Resume. Check on a variant made measures it (section 6) in the background.

  • The Info window lists the variants made with their measured quality.

  • A Version selector appears next to Load once a model has variants: the original or a variant, remembered for the model. The Server page shows the variant each loaded model runs.

  • Optimize automatically in the Server page’s settings (off by default): the variant Inga proposes for a model (named in Optimize’s tooltip) is made without asking, one at a time, and inga run / serve make it while the model runs. Nothing is converted without your yes otherwise.

The same from a program: GET /api/inga/variants?model=M (the variants, the conversions not complete and the proposal), POST /api/inga/optimize {"model": M, "type": "q8_0"} ("check": true to check it) and GET /api/inga/optimize?id=N (its progress), DELETE /api/inga/variants?model=M&type=q8_0 (&partial=true: a conversion not complete), POST /api/inga/load {"model": M, "variant": "q8_0"}, POST /api/inga/settings {"optimize_auto": true} (see docs/api/inga.yaml).

8. Proposals learnt from use

Section titled “8. Proposals learnt from use”

Inga keeps learning while models run, and turns it into proposals: each one is a note saying why, and nothing is applied without you.

  • The experts of a mixture. A mixture of experts whose experts stream from disk keeps a profile of which experts answer your tokens (~/.cache/inga/experts/). Once it holds about a thousand tokens (a few runs), a model whose use is skewed gets one of:

    or, when they do not fit in the experts’ cache, --experts-precision auto (the most used experts at the file’s precision, the others smaller, all in RAM). Each kind is shown once per model.

  • A new machine. The proposal depends on the RAM installed, the GPUs and the Inga version; Inga remembers them with each model’s proposal, and when they change (more RAM, a GPU added or gone, a new Inga) it proposes again, saying what changed: the original’s tip once more, or, for a variant that runs, that it is no longer needed (the original now runs from memory) or that a more precise variant now fits.

  • Variants not used. Each variant’s manifest keeps when inga run or serve last ran it; inga data points out the variants not run for 30 days, with their size:

    and inga data list variants says how long, next to the command deleting it (also unused in GET /api/inga/data, and the web UI’s Storage page).

9. Delete a variant

Section titled “9. Delete a variant”

or Delete in the Optimize window, or the web UI’s Storage page. A variant a loaded model runs is not deleted; the original is never deleted by any of these (inga rm deletes a downloaded model). A remembered choice whose variant is gone falls back to the original, with a note.

Troubleshooting

Section titled “Troubleshooting”

  • “a IQ2_XXS variant needs an importance matrix”: the 2-bit i-quants and IQ3_XXS are made with the model’s importance matrix: collect it once with inga imatrix MODEL -f TEXT (any text in the model’s languages; kept in ~/.cache/inga/experts/), then run inga optimize again. IQ4_XS and IQ3_S use it when it is there.

  • “has no Q4_K_M variant yet”: --variant names a variant not made (of a model that runs from memory): run the inga optimize ... --type q4_k_m the message gives, or add --while-running to it to make it during the next run.

  • “not smaller, and precision lost is not recovered”: the type is as precise as the original or more; pick a smaller one.

  • The proposal says nothing: the original already runs from RAM here; a variant can still be made with --type (it is smaller and faster, and a little less precise).

  • A conversion stopped half-way: it is not used; inga data list variants shows it as partial (... (partial: 17 of 36 layers)), inga optimize --type of that type resumes it, inga data rm variants:<key>.<type>.part deletes it.

  • “is being made by another Inga”: another inga optimize (or a server) is writing that variant; wait for it, or stop it (the layers it wrote are kept).
