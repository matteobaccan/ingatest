Find models and check that Inga runs them

What you get

Section titled “What you get”

Before downloading gigabytes, know whether Inga runs a model: search Hugging Face with a verdict per architecture, check a file or a whole disk of models, see a model’s memory needs and expected speed, and look at how it splits a text into tokens. Every check reads only the metadata and the tensor types, never the weights, so it takes seconds.

Requirements

Section titled “Requirements”
  • Windows, Linux or macOS; any x86-64 or ARM64 CPU.
  • Network access to huggingface.co for inga search (not for the other commands).

1. Get Inga

Section titled “1. Get Inga”

Download the archive for your system from the Releases page and put inga on your PATH (details); inga --version checks it.

2. Get a model

Section titled “2. Get a model”

Search Hugging Face

Section titled “Search Hugging Face”

(The layout of the output; the rows and numbers are those of the Hub on the day you run it.)

Each line is a GGUF repository with the architecture and size Hugging Face reads from its files, the downloads of the last month, the likes, the last update and whether Inga runs that architecture (supported, NOT SUPPORTED, or ? when Hugging Face does not say). --sort downloads (the default), likes, trending, updated or created; --supported keeps only what Inga runs; --limit N (20). The web UI’s Models tab does the same search, with each repository’s files (see chat-in-the-browser.md).

Fits here says, before the download, whether the file inga pull would download (the repository’s Q4_K_M, else its first model file) runs on this machine and how: GPU (every layer on the GPU), GPU+CPU (some there, the rest in RAM), CPU (every layer in RAM), disk (layers or experts read from the disk while it runs: slow), too big for the disk (the disk of the Hugging Face cache has no room for it: Another folder… opens the download folder, to choose one on a disk with room or move the models there; see run-a-model-from-hugging-face.md), does not run, or ? (its header could not be read). With it, the memory it takes there, the speed to expect and the context it leaves (the largest whose cache still fits where it lives, up to the model’s). Inga reads each file’s GGUF header from the Hub without its weights and without the tokenizer’s vocabulary (a few hundred KB in about ten ranged requests, where the whole header takes a few MB) and runs on it the planners of inga info, for a 4096-token context with --device auto; the speed reads each token’s bytes at this machine’s speeds (its RAM’s read bandwidth, measured once, and its GPU’s, from its name: cpu.ram_gbps sets the RAM’s). The first 32 results are checked, eight at a time; the lines under the table say why a model does not run on the GPU alone. --sort fit puts what fits best first, --fits keeps only what fits in memory (GPU, GPU+CPU or CPU), --no-fit skips the check (no header read). The web UI has the same Fits here column, sortable, for the search results and for each model file of a repository, with Only those that fit. Its verdicts have the colors of the terminal’s picker below (green, yellow, red: the same function decides them), and a repository’s files mark the one the picker’s cursor starts on as proposed, its Download the highlighted one; the line above the files names it.

Single files: an image model’s VAE and text encoders

Section titled “Single files: an image model’s VAE and text encoders”

Image and video models come in several files, often kept among many others in one repository (Comfy-Org’s split_files/vae/qwen_image_vae.safetensors). After the models, inga search lists the files its words name, each as an hf:// reference ready for inga pull and with what it is:

  • The files of the kits (the models inga image and inga video run, as sets of files: qwen-image, flux-schnell, flux-dev, sd3.5-medium, wan2.1-t2v-1.3b, z-image-turbo, chroma1-hd and the others of generate-images.md) whose family, part or file name hold every word: qwen image lists Qwen-Image’s three files, flux vae Flux’s VAE.
  • When the words read as a file name (an extension, a _ or a /), or no GGUF repository matches, the files inside any repository (safetensors ones too) whose path holds every word, the repositories looked for with the words, then with fewer of them. Each says what its path makes it: VAE, text encoder, transformer, projector, LoRA.
  • inga pull qwen_image_vae.safetensors (a kit file’s name) downloads that file, and says which other files of its kit are missing.
  • They are Hugging Face’s files: with --hub, they are looked for when hf is one of the hubs asked.

inga pull kit://NAME downloads a kit’s files together, kit://NAME:QUANT with another quantization of the transformer; see generate-images.md. The web UI’s Models search lists the same files under the repositories, each with Download, and Download all for a kit.

Search ModelScope too

Section titled “Search ModelScope too”

--hub says where to look: hf (the default), modelscope, ollama, or all, several with commas (--hub hf,modelscope). ModelScope’s results are ms:// references, run and pulled like hf:// ones (run-a-model-from-hugging-face.md):

ModelScope’s search has no format filter: a model counts as GGUF when its name or tags say so, and its architecture and size are read from the first 16 results’ main model file (two requests each), ? for the others; --sort trending and created take ModelScope’s own order. Ollama’s library has no public search API: --hub ollama says so, and its models are typed by name (inga pull ollama://qwen3:0.6b, the names on ollama.com/library). With several hubs, one that cannot be reached is said under the table and the others are listed. The web UI’s Models page has the same choice (Search on: Hugging Face, ModelScope, Ollama), each result saying its hub.

Choose and download in the terminal

Section titled “Choose and download in the terminal”

inga pull qwen coder (words instead of an hf:// reference, or no argument at all) and inga search -i qwen coder open a picker on a terminal:

  • the list is the search’s, searched again 300 ms after you stop typing; Up / Down, Page Up / Down, Home / End move; / types again, s changes the order, u hides what Inga does not run (greyed otherwise, and Enter on one says why);
  • Enter opens a repository: one row per GGUF model (a split one is one row) with its quantization, its size and whether it fits this machine: yes (green) in the GPU’s memory, or in RAM without a GPU; split (yellow) only between the GPU and RAM, or on the CPU beside a GPU; no (red: read from the disk while it runs, too big for the disk, or not run by Inga). It is first estimated from the file’s size, then replaced by the verdict of Fits here as each model’s header arrives (in the background, the row under the cursor first); the line under the list says why, and “estimated from its size” until then. The cursor starts on the largest that fits, else the default Q4_K_M or the closest quantization. Projectors and draft models are listed apart; files already downloaded have a ✓;
  • Space marks files (from several repositories too; a vision model’s projector is marked with it), and the status line counts them against the disk’s free space; Enter downloads the marked files, or the one under the cursor, one after another with the usual progress, then says how each went and the inga run line for each model. Esc goes back, q or Ctrl-C quits.

inga pull hf://org/repo on a repository without the default Q4_K_M opens the picker on its files the same way. Without a terminal (a pipe, a script) the picker never opens: inga pull WORDS prints the search’s list and ends with a usage error (exit 2), inga search -i prints the list.

What is already on your disks

Section titled “What is already on your disks”

inga list adds a here: line under each model Inga chats with: where it goes on this machine and how fast. Before the model has run here, the speed is the planner’s estimate:

Once it has run (a chat, inga run, inga bench), the measured speed takes its place, for example 16.4 tok/s gen · 210 tok/s prompt (measured, 2026-10-12). The Models page shows the same in its Fits here column, with the estimate in the tooltip. measure-speed.md says how the speeds are kept.

inga scan walks a directory (the current one by default) and lists every GGUF file and Hugging Face model directory with its size and verdict (captured on a folder of test files):

--supported keeps only the models Inga runs, --depth N limits how deep it goes (8), --all enters hidden directories too, --json prints {"models": [{"path", "size_bytes", "status", "supported"}]}. A vision or audio projector says supported projector (--mmproj).

3. Start the engine

Section titled “3. Start the engine”

Nothing to start: these are commands. To look at one model in detail, inga info (a file, an hf:// reference, which downloads it, or an ollama:// name):

--json gives the same as one JSON object (supported, problems, plan, memory, tokenizer, …), for scripts. --mem-limit, --quantize, --cache-type, --nodes show the plan those options would give, without loading anything.

4. Check that it works

Section titled “4. Check that it works”

inga tokenize shows how a model splits a text (as llama.cpp’s llama-tokenize), to count tokens or check a prompt’s special tokens:

(A test model with a byte-level vocabulary: one token per character. A real model’s vocabulary joins them into words.) -f FILE reads the text from a file; --no-bos leaves out the beginning-of-text token a model adds.

The full list of what Inga runs, by architecture, safetensors class, projector and weight type, is in supported-models.md.

Options worth knowing

Section titled “Options worth knowing”
Command Options
inga search WORDS --sort downloads|likes|trending|updated|created|fit, --supported, --fits, --no-fit, --limit N, --hub hf|modelscope|ollama|all, -i (the picker)
inga pull [WORDS] an hf:// or ms:// reference downloads it; words, or none, open the picker
inga list --ollama, --lmstudio
inga scan [DIR] --supported, --depth N, --all, --json
inga info MODEL --json, --mem-limit, --quantize, --cache-type, --nodes, --offline
inga tokenize MODEL -p TEXT or -f FILE, --ids, --json, --no-bos

Troubleshooting

Section titled “Troubleshooting”
  • NOT SUPPORTED: unsupported architecture ... (or a tensor type, a tokenizer, a projector): the reason is the part Inga lacks; supported-models.md lists what runs, and the model request form asks for it.
  • A LoRA adapter shows NOT SUPPORTED: invalid file: missing or mistyped metadata key ...: adapters are not models; load them with --lora (see apply-lora-adapters.md).
  • search fails with “cannot reach …” or “offline mode is on”: it needs the network; check HTTPS_PROXY and unset HF_HUB_OFFLINE.
  • ? in the inga column: Hugging Face has not read the repository’s files; open it (or download one file) and run inga info.
