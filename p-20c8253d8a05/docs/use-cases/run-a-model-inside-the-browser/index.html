Run a model inside the browser (experiment)

The GPU through WebGPU is experimental (spec 2026-10-09-webgpu-wasm-design.md §8, “As built”).

What you get

Section titled “What you get”

Inga compiled to WebAssembly, running a GGUF model in a web page on the device’s CPU: no server, nothing sent anywhere. The demo page in web/ picks a model (one of four small suggested models, a link, or a file of the device), keeps downloads in the browser’s private storage, and streams the answers with their speed. The same tokenizer, chat templates, model code and samplers as the inga executable: in headless Chromium the page’s greedy answer is the native engine’s on its scalar kernels, token for token (the SIMD128 kernels give the scalar kernels’ bits, and Inga computes exp, powf and sin_cos with its own functions, the same bits in the browser and natively; checked on synthetic models of two and four layers).

It is an experiment, one page for everything: small models (135M to 1B parameters) run best; a larger one runs slowly by reading the layers that do not fit from the browser’s storage at every token (step 6); the CPU is the default device, and the GPU through WebGPU, alone or with the CPU taking the layers it cannot hold, is a setting (step 7); a smaller model can draft for a larger one (step 8). The module uses WebAssembly SIMD (SIMD128, which every browser below has) for its quantized dot products, on one thread; on a page that is cross-origin isolated (step 5) a second module runs them on every core (up to 8). It has been tested in headless Chromium on Linux and on an iPhone 16 Pro in Safari (SmolLM2-135M-Instruct Q8_0 picked from the Files app, one thread: prompt 12.7 tok/s and answer 9.5 tok/s with the scalar kernels, 66.5 and 53.1 with SIMD128, 195 MiB of memory either way); untested in Firefox.

On the same iPhone, one thread with SIMD128, two larger models:

Model (iPhone 16 Pro, Safari, SIMD128, 1 thread) Prompt Answer Memory
SmolLM2-135M-Instruct Q8_0 32 tokens, 66.5 tok/s 32 tokens, 53.1 tok/s 195 MiB
Qwen3-0.6B Q4_K_M 10 tokens, 41.7 tok/s (37.9 in a second, cool run) 68 tokens, 25.0 tok/s (24.8; 59 of them thinking) 643.8 MiB
Llama-3.2-1B-Instruct Q4_K_M 37 tokens, 24.3 tok/s 7 tokens, 13.5 tok/s (a short answer: a rough figure) 878.9 MiB

Speeds on the phone vary between runs: a Qwen3-0.6B run right after several others (and after Llama, before the page started a fresh worker for each model) read 15.9 / 10.6 tok/s, while a later run on a fresh page gave 37.9 / 24.8 again; take single runs as indications.

Measured in headless Chromium on a Linux container with 4 vCPUs (synthetic weights of the models’ shapes; the spec’s §8.7 has the details):

Model Before (scalar, 1 thread) SIMD128, 1 thread SIMD128, 4 threads (isolated)
SmolLM2-135M Q8_0, prompt / answer tok/s 5.6–6.7 / 4.2–5.2 25.1–30.0 / 10.6–13.9 73.8–95.8 / 34.1–42.0
Llama-3.2-1B Q4_K_M, prompt / answer tok/s 1.0–1.1 / 0.7–0.9 6.0–6.4 / 3.2–4.1 20.7–26.0 / 11.7–13.1

The SIMD128 kernels cover every weight type of the usual downloads. The i-quants (IQ1_S to IQ4_XS, which IQ2_M, IQ3_M and Unsloth’s “UD” files use) have them, and so do Q2_K, Q3_K, Q5_K, Q4_1, Q5_0 and Q5_1, besides Q8_0, Q4_0, Q4_K and Q6_K. Before 2026-10-15 the i-quants and the other K-quants ran on the scalar kernels. Measured in the same container with 1B-shaped synthetic models on one thread, before → after:

Model (Llama-3.2-1B shape) Prompt tok/s Answer tok/s
IQ2_M (487 MiB) 0.65–0.67 → 4.96–5.06 0.61–0.68 → 2.17–2.69
Q3_K_M (654 MiB) 1.08–1.21 → 5.91–6.21 1.21–1.25 → 3.30–4.08

An IQ2_M file is smaller than a Q4_K_M one but not faster: its kernel does more work per weight. These are not phone figures. A gemma-4-E4B-it-UD-IQ2_M.gguf that answered at 0.4 tok/s on an iPhone 16 Pro before this change has not been measured since. The spec’s §8.7, “SIMD128 for the other weight types”, has each type’s kernel speed.

Requirements

Section titled “Requirements”
  • To build it: Rust with the wasm32-unknown-unknown target and the wasm-bindgen command of the version crates/inga-wasm/Cargo.toml names.
  • To serve it: any static web server; over HTTPS, except on localhost (browsers keep the private storage and module workers for secure pages).
  • A recent browser with module workers, the Origin Private File System and WebAssembly SIMD (Chrome or Edge 102+, Firefox 114+, Safari 16.4+); standard SIMD128 only, not relaxed SIMD, which Safari lacks.
  • For the threaded module only: the nightly toolchain tools/build-wasm.sh names (WebAssembly threads need a standard library built with atomics, -Z build-std), and a page served cross-origin isolated (step 5).

1. Build the page

Section titled “1. Build the page”

To try it first with nothing to build, open the published page, https://matteobaccan.github.io/ingatest/ (what it covers), and go on at step 3. To run your own copy, build it:

web/pkg/ now holds the module (about 5.5 MB, 1.6 MB gzipped, with its WebGPU path) and its JavaScript, built with SIMD128 on stable Rust; web/pkg-threads/ the threaded module (about the same size), built on the pinned nightly. Without that nightly the script skips web/pkg-threads/ with a message (THREADS=0 skips it on purpose, THREADS=1 makes it an error); the page then runs on one thread everywhere. SIMD128=0 builds a web/pkg/ without SIMD (the scalar kernels), for comparisons.

Any static server works; every path in the page is relative. On this machine:

3. Load a model

Section titled “3. Load a model”

The page offers three ways, all on its first screen, and a catalog:

  1. Browse models: a dialog of about fifty models on Hugging Face that Inga runs, with a search box, family chips and each quantization marked ✅ fits, ⚠️ tight or ❌ too big for this browser; Download and load on a card, Delete on a stored one (the page’s guide says how it judges and how the catalog is checked).

  2. A test model: a fixed list, so that runs on different devices compare (SmolLM2-135M-Instruct Q8_0, Qwen3-0.6B Q4_K_M, the draft model for Qwen3-4B, Llama-3.2-1B-Instruct Q4_K_M, Qwen3-4B Q4_K_M, Gemma 4 E4B IQ2_M), each with its file name, approximate size and licence, and “stored ✓” once this browser holds it. Get downloads it from Hugging Face into the browser’s private storage (OPFS), then loads it; a failed download names its HTTP error (a 404 says to check the link). SmolLM2-135M-Instruct (about 0.15 GB) is the quickest.

  3. A link to a GGUF file: Hugging Face’s resolve/main links work (they allow cross-origin downloads and ranges); an interrupted download resumes where it stopped.

  4. A file of this device: the file picker (on an iPhone or iPad it opens the Files app). The file is read in pieces and not stored, unless it is larger than Memory for weights (step 6): it is then copied into the browser’s private storage first. Where the page cannot download from Hugging Face (a page hosted in a sandbox that blocks other sites: Safari then says “Load failed”), Save file beside a test model lets the browser save it (on an iPhone, in Files → Downloads); pick it here. A picked file is stored under its own name: keep the list’s file name for “stored ✓” to show.

The page asks the browser to keep its storage (navigator.storage.persist()) and shows how much it uses of the quota. Stored models (in Models) lists every file the site keeps in OPFS: the downloads, with Load, Resume for an incomplete one, and Delete; a model without its download record (“complete or not: unknown”, Load still offered); and anything else the page finds, such as a Disk speed test interrupted or files left by an older version of the page (“not a model of this page”), each with Delete. An entry that cannot be read shows its error instead of hiding the list. Delete all stored data asks for confirmation inside the page, then closes the model it reads and removes everything the site stores.

When the quota is nearly full (the storage line says, for example, “14.25 GiB of 14.28 GiB available”), delete the models you do not use, or Delete all stored data: a download or a copy into storage needs room for the whole file, and a site at its quota may also be cleared by the browser.

The standard test

Section titled “The standard test”

Standard test (in Test, at the foot of the side bar, once a model is loaded) runs a fixed, comparable test whatever the Settings: a new conversation, the prompt “Ciao, presentati in tre frasi.”, thinking off, temperature 0 (greedy), at most 64 tokens. It prints one line to copy (Copy; where the clipboard is refused, the line is selected): the date, the device (CPU, or GPU and its adapter), the model file, the memory limit and GPU memory, the layers on the GPU and those read from storage, prompt and answer tok/s, WebAssembly memory and the GPU’s bytes, the bytes read per token, the GPU memory accounting, the tokens drawn on the GPU and a draft model’s figures. Every line is kept in this browser (Standard test results, with Copy all and Clear), so a matrix of runs (each test model on the CPU and on the GPU) can be pasted at once.

4. Chat

Section titled “4. Chat”

Write a message and press Send (or Enter; the Settings can make it Ctrl+Enter): the answer streams in a bubble with the model’s name; under it, the prompt’s (prefill) and the answer’s (decode) tokens per second and the time, and under the composer the full statistics and the module’s memory. Conversations are kept in this browser and listed in the side bar; New chat, at its top, starts another, and a conversation of the list opens it again. Settings has the sampler (temperature, top P, top K, min P, repeat, presence and frequency penalties), the most tokens of an answer, a system prompt, how many past messages are sent, the context size, the theme, the font size and the language; Think in the composer is the thinking switch (the page’s guide lists them all).

Thinking models (Qwen3, DeepSeek-R1 distills, Qwen3.5, gpt-oss, …) reason before they answer. The page shows the reasoning as it streams in a Thinking box above the answer, open while the model reasons and folded away when the answer starts (tap it to read it again); the statistics say how many of the answer’s tokens were thinking. Only the answer goes back to the model with the next message, as in inga serve’s web UI. The reasoning is told apart by the same code as inga serve’s reasoning_content, so a model whose chat template opens <think> itself (Qwen3.5) is split too.

Think (checked by default) is the chat template’s enable_thinking, as --chat-template-kwargs '{"enable_thinking": false}' natively: unchecked, Qwen3 answers at once without reasoning, which on a phone is much quicker. Models whose template has no such switch ignore it.

Loading a model after another starts a new worker first: WebAssembly memory never shrinks, so the second model would otherwise keep the first one’s peak (on the iPhone, 878.9 MiB after Llama 3.2 1B against 643.8 MiB for Qwen3 0.6B alone). A new model starts a new conversation; the earlier ones stay in the side bar.

Stop stops the answer at once when the page is cross-origin isolated (served with Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp); otherwise it ends the worker and loads the model again from storage (a few seconds for a small model), keeping the chat.

5. Every core: serve the page cross-origin isolated

Section titled “5. Every core: serve the page cross-origin isolated”

WebAssembly threads share the module’s memory between Web Workers (SharedArrayBuffer), which browsers allow only on a page that is cross-origin isolated. When the page is (self.crossOriginIsolated is true) and web/pkg-threads/ exists, its worker loads that module, starts one thread per core (navigator.hardwareConcurrency, at most 8; web/thread.js) and runs the matrix products and the attention on all of them; the line under the model then says SIMD128 kernels on N threads. Otherwise it loads web/pkg/ on one thread, as on a plain static host or a page embedded elsewhere; the answer is the same either way.

A page is isolated when it is served with these two headers:

  • nginx: add_header Cross-Origin-Opener-Policy same-origin always; and add_header Cross-Origin-Embedder-Policy require-corp always; in the location.
  • Caddy: header { Cross-Origin-Opener-Policy same-origin Cross-Origin-Embedder-Policy require-corp } in the site block.
  • Netlify, Cloudflare Pages: a _headers file in web/ with /* and the two lines above, indented.
  • Locally, python3 -m http.server cannot add headers; npx serve web with a web/serve.json of {"headers": [{"source": "**", "headers": [{"key": "Cross-Origin-Opener-Policy", "value": "same-origin"}, {"key": "Cross-Origin-Embedder-Policy", "value": "require-corp"}]}]} can.
  • GitHub Pages (and other hosts that send no custom headers): coi-serviceworker (MIT) adds them from a service worker. Copy its coi-serviceworker.js into web/ and load it first in index.html’s <head>: <script src="https://github.com/matteobaccan/inga/blob/main/docs/use-cases/coi-serviceworker.js"></script>. On the first visit it registers itself and reloads the page once, isolated. The page must be on HTTPS (or localhost).

Under require-corp every resource the page loads must be same-origin or allow it: the downloads from Hugging Face are CORS requests, which it allows. A page shown in someone else’s frame (a preview, a sandbox) is usually not isolated, and runs on one thread.

6. A model larger than the memory: layers read from storage

Section titled “6. A model larger than the memory: layers read from storage”

All of a model’s weights normally live in the page’s WebAssembly memory, and a phone ends a tab that takes too much (on an iPhone 16 Pro, Safari closed the tab with a 2.5 GB model). Settings → Memory for the model sets how much memory the model may use: its weights, its KV cache for the context and its working buffers, all counted. What does not fit is read from the browser’s private storage (OPFS) while the model runs, the way inga run streams a model larger than the RAM from the disk (“SSD (read while running)”). It is much slower, but the model runs; a model that cannot fit even so is refused, with what it needs, before it is loaded.

  • Auto (the default): 1600 MB on an iPhone or iPad, recognised from the browser’s user agent (a heuristic: an iPad that says it is a Mac is told apart by its touch screen); 3584 MB elsewhere (close to the 4 GiB ceiling below). The iPhone’s figure comes from an iPhone 16 Pro (8 GB): Safari kept the tab at 1.75 GiB of WebAssembly memory and ended it at about 2.2 GiB; Auto stays at 1600 MB, under that ceiling with a margin, because the plan is an estimate and the browser’s own allocations (the worker, the page) count against the same tab. A phone with less memory may need less: use Limit in MB.
  • All in memory: everything in WebAssembly memory, as before.
  • Limit in MB: a size of your choosing.

A longer Context needs a larger KV cache, which comes out of the same limit: the page then keeps fewer weights in memory. The Settings are kept in this browser, and the line under the model says the limit its load used (“limit 1500 MB (Limit in MB)”, “limit 1600 MB (Auto on iOS)”); a change while a model is loaded applies at the next Load.

A stored model is planned against the limit when it loads: one that fits stays whole in memory. A file picked from the device and larger than the limit is first copied into OPFS (the page checks that the site’s storage has room, then shows the copy’s progress) and stays in Stored models. What the plan reads from storage, in order, until the rest fits:

  1. the tables a token reads one row of, a row per token (a few KB): the token embeddings and, in Gemma 4’s E models, the per-layer embeddings, a table larger than the rest of the model;
  2. the output layer, read whole at every token in parts the size of a layer (on a model whose output layer is its token embeddings, as Gemma, Llama 3.2 and Qwen3, it is held with them until then);
  3. the last layers, whole at every token, into two buffers the size of a layer, one read while the other runs.

The norms and small tensors, the read buffers, the KV cache and the working buffers always stay; if they alone exceed the limit the load stops with “the model needs … at least … Try a smaller context or a larger memory limit”. The line under the model says what is read at every token and how many bytes that is, the embeddings read by row, the weights in memory and the total planned; the line under each answer how much was read and at what speed.

How fast depends on how fast the browser reads its storage, which Disk speed test (in Test) measures: it writes 256 MiB, reads it back in 8 MiB pieces through the same synchronous access handle, reports MB/s and deletes the file. Read right after writing, the data may come from the system’s cache, so take the figure as a best case.

The reads were about three quarters of the time at 1 GB; at 1500 MB fewer bytes a token and a faster read rate (more of the file stayed in iOS’s cache, probably) doubled the speed. The Disk speed test on that phone read 10.7 GB/s and wrote 1.24 GB/s, read right after writing: the system’s cache, not the flash the model is read from. That 1500 MB run’s total at a context of 2048 was about 1792 MB; Auto is now 1600 MB, with a margin under it. Gemma 4 E4B (unsloth’s gemma-4-E4B-it-UD-IQ2_M.gguf, 3.30 GiB) ended the tab at 1.80 GiB of its load with the old 1 GB: its embeddings were held in memory whatever the limit. It read 5.64 GiB from storage in 1.0 s of the about 50 s: the run is bound by compute, most likely the IQ2 types, which have no SIMD128 kernels and run on the scalar ones, and the 262,144-token output layer at every token.

Run the Disk speed test on the phone to know its figure.

The 4 GiB ceiling. A WebAssembly module addresses 4 GiB at most (wasm32), so what a model keeps in memory is capped near 4 GB whatever the limit: a model above that always reads part of itself from storage. Auto off iOS is 3584 MB, close to that ceiling with room for the browser’s own needs. WebAssembly Memory64 would lift the cap; Chrome has it, Safari does not, and Inga’s module is 32-bit. On a desktop with an NVIDIA Pascal card in Chromium, Ornith 1.5 9B Q4_K_M (about 5.5 GB) at the earlier Auto of 2048 MB answered “Ciao” with 12 prompt tokens at 0.6 tok/s and 47 tokens at 0.4 tok/s (36 of them thinking), 1.98 GiB of WebAssembly memory, 158.02 GiB read from storage in 56.3 s (3015 MB/s), 3.30 GiB per token after the first: reads were about 40 % of the time, the rest computing on one thread. And Gemma 4 E4B IQ2_M on an iPhone 16 Pro, with the SIMD128 i-quant kernels, answered at 1.3 tok/s (0.4 before; prompt 2.3 against 0.4), 1.59 GiB, reading 583.3 MiB per token after the first.

7. On the GPU (WebGPU, experimental)

Section titled “7. On the GPU (WebGPU, experimental)”

Settings → Device has three choices:

  • CPU (the default): WebAssembly SIMD on the device’s cores, as in the steps above.
  • GPU (WebGPU, experimental): the model’s first layers run on the GPU, in WGSL generated from the Vulkan backend’s shaders (crates/inga-webgpu, spec §8.8), as many as fit GPU memory; the rest run on the CPU, read from this site’s storage when the memory limit asks, as in step 6. Their weights go from the stored file straight into GPU buffers, a few MB at a time, never through WebAssembly memory. A picked file is copied into the site’s storage first. The option is greyed out, with the reason, where the browser has no WebGPU (navigator.gpu): Chrome and Edge 113+, Safari 26, Firefox 141+ on Windows have it.
  • Auto: the GPU where it was measured faster than the CPU, else the CPU; and the CPU for a model that needs storage under one limit (below), whatever the adapter. Nothing has been measured faster (on an iPhone 16 Pro the GPU was slower, see below), so Auto picks the CPU and the load line says so.

GPU memory (Auto, or Limit in MB) is what the GPU may hold: its layers’ weights, their KV cache and its working buffers. Auto is 1024 MB on an iPhone or iPad (Llama 3.2 1B, about 0.9 GiB on the GPU, is the largest model measured to load there; a larger one made iOS reload the page) and 3072 MB elsewhere: a guess, as WebGPU does not tell a GPU’s memory, which a 4 GB card holds (set yours in MB). A Qwen3-4B Q4_K_M model (about 2.5 GB) then runs whole on the GPU: its plan takes 2887 MiB there, 364 MiB of WebAssembly memory (measured on the Qwen3-4B shape of tools/bench_model.py).

GPU memory accounting says how the two limits meet:

  • One limit: the GPU’s bytes count against Memory for the model (step 6) with WebAssembly memory, in case the system counts a tab’s GPU buffers with its memory, as iOS seems to: the page plans both within one limit and refuses a model that cannot fit before reading it. A model that needs storage then runs slower on the GPU than on the CPU alone, since the GPU’s share leaves the CPU fewer weights while the reads per token stay: on an iPhone 16 Pro, Qwen3-4B Q4_K_M ran at 0.9 tok/s with 14 of 36 layers on the GPU (564.8 MiB of WebAssembly memory, 805.3 MiB of weights + 194.2 MiB on the GPU, 18 layers and the output layer in 5 parts read at every token, 1.32 GiB a token, 345.9 MiB of weights in memory) against 2.3 tok/s on the CPU alone at the same limit (1.18 GiB of weights in memory, 17 layers read). So Device Auto keeps such a model on the CPU, and with Device GPU the load line warns.
  • Apart: Memory for the model bounds WebAssembly memory only and GPU memory the GPU’s bytes, as on a desktop, whose graphics memory is not the tab’s.
  • Auto (the default): one limit on an iPhone or iPad, apart elsewhere.

The load line names the accounting it used (“GPU memory accounting: one limit, Auto on iOS (…)” or “apart, Auto off iOS (…)”).

Does iOS count GPU buffers in the tab’s limit? A test for the iPhone, which decides whether iOS can use “Apart” too:

  1. Settings: Device GPU; GPU memory Limit in MB 1024; Memory for the model Limit in MB 2600; GPU memory accounting One limit.
  2. Load Qwen3-4B Q4_K_M: about 1 GiB goes to the GPU and about 1.4 GiB stays in WebAssembly memory (the load line gives both), 2.4 GiB in all, above the 1.75 GiB at which Safari ended a tab on the CPU path but with WebAssembly memory under it.
  3. Run the Standard test.

If the tab survives, iOS does not count the GPU’s buffers with the tab’s memory: the page should then use “Apart” on iOS too (the limit for WebAssembly memory at 1600 MB, a GPU budget beside it). If the page reloads, keep one limit.

The load line says where everything runs and why, for example:

A model whose layers the GPU does not run here (mixtures of experts, DeltaNet or Mamba-2 layers, Gemma 4’s per-layer embeddings, weight types without a WebGPU kernel) loads on the CPU instead, and the line says why (for Gemma 4 E4B: “the GPU does not run this model: Gemma 4’s per-layer embeddings and widths (gemma4) do not run on the GPU in the browser yet”). A draft model (step 8) drafts on the CPU only: with Device GPU the model answers without it.

  • GPU info (next to the setting) shows the browser’s adapter and the limits that matter: maxBufferSize and maxStorageBufferBindingSize (a weight larger than one binding is split into several buffers), maxComputeWorkgroupStorageSize, shader-f16 and subgroups.
  • After a load and after each answer the page shows the WebAssembly memory and the GPU’s bytes (weights, and the other buffers: KV cache, activations).
  • Stop stops at the next token (the worker waits for the GPU between tokens).

Measured on an iPhone 16 Pro in Safari (iOS 26), with the first WebGPU build, before the optimizations below: Qwen3-0.6B answered at 16.3 tok/s on the GPU against about 25 on the CPU, and Llama 3.2 1B Q4_K_M’s prompt ran at 8.8 tok/s against 24.3 (answer 12.1 against about 13.5). The page now reads back one result per step (the logits, after the layers, the final norm and the output layer in one pass; before, the hidden state of every prompt chunk and then the logits), quantizes each norm’s output once for the products that read it, reuses its bind groups from token to token, and draws each token on the GPU when every layer and the output layer are there, reading back only its id (the answer’s line says “N drawn on the GPU”; a setting the GPU’s sampler does not have, such as a logit bias, is drawn by the CPU from the logits, the same tokens). Where the adapter has shader-f16 it reads the KV cache and F16 weights as f16 values, and on an Apple GPU the prompts run on tiles of 32 tokens (Inga’s Metal kernels’ size). These have to be measured on the phone again: on software renderers (the only GPUs here) they say little.

GPU benchmark (in Test, with a model loaded on the GPU) measures them in one tap: the loaded model runs the same prompt (about 80 tokens) and 32 tokens under eight kernel choices (the kernels before these changes, f16, Apple’s tiles, both, four rows per workgroup, all three, subgroups, subgroups with f16), each after a short warm-up run that compiles its kernels, and prints a table of prompt and answer tok/s and whether each gave the first row’s text. Rows that need shader-f16, or subgroups 32 wide, say so where the adapter lacks them. The chat starts again afterwards (the benchmark’s prompt is not part of it). The same switches are Gpu.tune("f16=off,rows=4,tiles=32,slab=128,sg=on") in JavaScript and off=... in the native example (spec §8.9, “The page’s draws on the GPU”).

Measured on a desktop with an NVIDIA Pascal card (P1000 class) in Chromium, with the page before these changes: Llama-3.2-1B-Instruct Q4_K_M, prompt 37 tokens at 17.6 tok/s, answer 7 tokens at 15.8 tok/s (260.9 MiB of WebAssembly memory, 762.6 MiB of weights + 126.3 MiB on the GPU); SmolLM2-135M-Instruct Q8_0, prompt 32 tokens at 70.5 tok/s, answer 32 tokens at 58.2 tok/s (43.1 MiB; 136.3 MiB + 59.5 MiB on the GPU). The card’s memory (about 80 GB/s) would allow far more on 0.76 GiB of weights per token: about 17 ms a token goes elsewhere (submissions, waiting for the read, the step’s second run), which the token drawn on the GPU (4 bytes read back instead of the logits) is to cut. Its adapter: maxBufferSize and maxStorageBufferBindingSize 2 GiB, maxComputeWorkgroupStorageSize 32 KiB, maxStorageBuffersPerShaderStage 16, subgroups, no shader-f16. Every kernel binds 6 storage buffers at most, under the 8 WebGPU guarantees; a device that binds fewer than a kernel needs gets no layer, and the load line names the kernel.

Under the hood the engine waits for the GPU between tokens rather than inside one: a token’s step runs again once the GPU’s result is there, the work already on the GPU skipped (spec §8.8). With the threaded module (a cross-origin isolated page), the GPU path still loads web/pkg’s module, which has it.

8. A draft model: several tokens for one read of the layers

Section titled “8. A draft model: several tokens for one read of the layers”

With layers read from storage, every token costs a read of those layers. A draft model, a smaller model of the same vocabulary held whole in memory, guesses the next few tokens, and the model checks them all in one pass: each layer read from storage is read once for every token the pass accepts. It is Inga’s speculative decoding, the same as inga run --draft (the text is the one the model writes alone).

  1. Store both models (Get, a link, or a file of this device).
  2. Settings → Draft model: choose the smaller one (None by default). The choice is kept in this browser.
  3. Load the model. The page loads both; the line under the model names the draft and its memory (“Draft model Qwen3-0.6B-Q4_K_M.gguf: 28 layers, 639 MiB in memory (weights, KV cache, activations), 4 tokens guessed before each check”).

Pairs that share a vocabulary: Qwen3-4B with Qwen3-0.6B, Qwen3-1.7B with Qwen3-0.6B, Llama 3.2 3B with Llama 3.2 1B, Gemma models of the same generation. The page checks that the two tokenizers have the same tokens, each with the same text, and refuses another pair before reading any weight (“… cannot draft for …: they must share a vocabulary”).

Memory. The draft is held whole, and its weights, KV cache for the context and working buffers come out of the same Memory for the model: the model gets what is left, so it reads more of its layers from storage at every pass. A draft that does not fit the limit alone is refused with its parts and sizes. A smaller context shrinks both KV caches.

When it pays. The page keeps the draft only while it makes the answer faster: after a few plain tokens it measures, by the clock, the tokens per second of the checks (reads, compute and the draft’s own guesses together) against those of plain tokens, and pauses the draft for a while when the checks are slower; a check that accepts nothing ends the measure at once. With layers read from storage a pass is dear, so a draft pays at a lower share of right guesses than natively; the page therefore has no minimum share (the gate of inga run’s default drafts pauses below 10 %), only the clock.

The line under each answer adds the guesses: proposed, accepted, accepted per check, the checks and the model’s passes, whether the draft was paused; and the bytes read per token after the first.

Measured only on synthetic files here (headless Chromium on a Linux server, one thread, SIMD128; tools/bench_model.py --shape qwen3-4b and --shape qwen3-0.6b, random weights; a 46-token prompt, 24 tokens, the second of two runs, both alike):

Synthetic Qwen3-4B shape at 1600 MB, headless Chromium Layers read per pass Read per pass Answer tok/s WebAssembly memory
No draft 18 of 36 and the output layer (5 parts) 1.37 GiB 0.84-0.86 1,539 MiB
Draft: the synthetic Qwen3-0.6B shape (639 MiB planned held whole) 28 of 36 and the output layer 1.96 GiB 0.58-0.59 1,569 MiB

Random weights make the two models disagree: here the draft’s 4 guesses were all wrong, the gate paused it after its first check, and the answer was slower because the model had 639 MiB less for its layers (28 layers read per pass instead of 18) and the draft read the prompt once. The share of guesses a real pair accepts decides whether a draft pays, and it has not been measured: try it on the phone with the real files (Qwen3-4B with Qwen3-0.6B), compare the answer’s tok/s with and without the draft, and look at “accepted per check”. As a rule of thumb, a check of 4 guesses that accepts 2 gives 3 tokens for one pass of the model plus 4 short passes of the draft.

Troubleshooting

Section titled “Troubleshooting”
  • “This browser has no Origin Private File System”: the page is not served over HTTPS (or localhost), or the browser is too old; a file of the device still loads.
  • The tab is closed or reloaded while loading a large model: the browser ran out of memory for the tab. The model needs its size plus its context in memory (a 1B Q4_K_M model: about 1 GB); use a smaller model or a smaller context, or a smaller Memory for the model (step 6), which reads the rest from storage while it runs. Check the limit the load line names: the Settings are kept in the browser, but a page from before they were did not keep them.
  • “The model needs … at least …”: even with everything that can be read from storage read from it, the rest does not fit the limit: a smaller Context (its KV cache is part of it) or a larger limit.
  • “This site’s storage has … free” when picking a large file: the model must be copied into the site’s storage to be read from there; delete a stored model, or choose All in memory.
  • The storage line says the site uses almost all its quota, but Stored models shows little: every file the site keeps is listed (step 3), what the page did not write too; delete what you do not need, or Delete all stored data. If a file cannot be deleted, close the page’s other tabs (a tab reading a model keeps its file open) and try again.
  • “Inga stopped: panicked at …” or “Inga stopped: out of memory …”: the engine stopped in the middle of a call; the message says where and why (before, the browser only said “Unreachable code should not be executed”). The model is unloaded: load it again. Out of memory: a lower Memory for the model or a smaller context. Otherwise please report the message.
  • A download fails with a CORS error: the server of the link does not allow cross-origin downloads; download the file and pick it from the device instead.
  • “on 1 thread” on a page you serve with the headers: check self.crossOriginIsolated in the browser console (both headers must be on the page itself), that web/pkg-threads/ was built (the build prints it), and the console: the worker says why the threaded module did not start before it falls back to one thread. The threaded module reserves up to 4 GiB of address space for its shared memory; a browser that refuses it (possibly on phones) falls back the same way.
  • “On the CPU: the GPU did not take this model (…)” on the load line: an architecture or a weight type the WebGPU kernels lack; the page loaded the model again on the CPU by itself. “the GPU runs N of M layers: …”: the rest runs on the CPU; raise GPU memory (or Memory for the model) to put more on the GPU.
  • The page reloads while a model loads on the GPU (iOS ends the tab): lower GPU memory and Memory for the model; both count against what iOS lets a tab use.
  • A WebGPU error naming a buffer size or a limit: the adapter’s limits (GPU info) are lower than a weight’s rows or the KV cache; a smaller context helps the cache.
