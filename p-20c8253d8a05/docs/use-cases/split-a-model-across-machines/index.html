Split a model across machines

What you get

Section titled “What you get”

A model too large for one machine runs on several: each machine holds a range of the model’s layers and its part of the KV cache. The machine you type on (the coordinator) runs the first layers, the embeddings and the output; inga worker processes on the other machines run the rest. For every step only the residual stream travels between machines (tokens × width × 4 bytes, e.g. 16 KiB per generated token for a model 4096 wide), and the answer is the same as on one machine.

This is pipeline parallelism: the machines work one after the other, so it lets you run a larger model, not run a model faster.

This includes the hybrid models (Qwen3.5, Qwen3.6, Qwen3-Next), whose DeltaNet layers keep a state instead of keys and values. The machines need a protocol version in common: this Inga speaks protocol 10, and 9 still (the protocol of 0.28.0 to 0.40.x), and a connection runs at the lower of the two; a worker of an older protocol is refused.

Requirements

Section titled “Requirements”
  • Two or more machines with Windows, Linux or macOS, on one network: the connections are encrypted, and with the same mesh.key on every machine (inga mesh key new prints one) only the machines that hold it connect.
  • The same Inga version on every machine is best; nodes of 0.28.0 and later still work together (above).
  • A copy of the model on every machine, reachable by the same name: an hf:// reference (each machine uses its own Hugging Face cache, or downloads into it) or the same absolute path.

1. Get Inga on every machine

Section titled “1. Get Inga on every machine”

Download the archive for each OS from the Releases page, extract it, and put the inga executable on your PATH:

2. Start a worker on each other machine

Section titled “2. Start a worker on each other machine”

--port N changes the port (default 9090), -t N the threads, --offline keeps the worker off the network when a model is not in its cache. Without --host the worker listens on 127.0.0.1 only, which is useful to try everything on one machine.

A worker serves any number of coordinators; it loads each model the first time one asks for it and keeps it.

3. Run the model through the workers

Section titled “3. Run the model through the workers”

On the coordinator, add --nodes with the workers’ addresses, in the order the layers should flow:

The layers are split in proportion to the memory each machine has available. Choose the split yourself with --node-layers, one count per machine, the coordinator first (here 4 layers on this laptop, 28 on the workstation):

--nodes works the same with inga serve (the API server answers through the workers), inga bench and inga info, which prints the split without loading anything on the workers. --quantize converts each machine’s own layers.

4. Check that it works

Section titled “4. Check that it works”

Compare with a single machine, if one can hold the model: with --temp 0 both print the same text.

5. Split every layer instead (tensor parallelism)

Section titled “5. Split every layer instead (tensor parallelism)”

--tp-nodes splits every layer instead of handing whole layers to each machine: each machine computes some of the attention heads and some of the feed-forward columns of every layer, at the same time, and the coordinator adds their results. Every token then waits for the slowest machine’s share of a layer rather than for each machine in turn, which helps when the machines are about as fast and the network is quick (each layer costs two round trips):

--tp-split 2,1 gives this machine twice the other’s share. There can be at most as many machines as the model has key-value heads (8 for Llama 3 8B). It works with dense models (Llama, Mistral, Qwen2, Qwen3, Gemma); mixture-of-experts models use --expert-nodes instead.

6. Read the prompt on one machine, write the answer on another (disaggregated prefill)

Section titled “6. Read the prompt on one machine, write the answer on another (disaggregated prefill)”

Reading a long prompt (prefill) is limited by the processor: every weight is multiplied by many tokens at once. Writing the answer (decode) is limited by the memory: every token reads every weight once. With --prefill-node, another machine with many cores reads the long prompts and sends back their KV cache, and this machine, the one with the big RAM, writes the answer. Both machines need the whole model (the same file or hf:// reference); the worker is the same inga worker as above:

  • --prefill-min N (default 64) sets the prompt tokens left to process from which a prompt goes there. Short follow-ups stay here: a round trip costs more than they do.
  • The KV cache comes back in its own format (--cache-type f16 or q8_0), so the answer is the same as on this machine alone.
  • Only what this machine lacks travels: in a conversation (or a --prompt-cache resumed) the positions it holds already stay here, and the node sends the ones after them. The first line then says how many were held: (the first: 1900 tokens (1834 held here), 1.5 MB of KV cache back in 180 ms).
  • If the prefill node cannot be reached or fails, the prompt is processed here and a line says why; the node is tried again 30 s later.
  • Not used when this machine’s layers run on a GPU or on workers (--nodes, --expert-nodes, --tp-nodes): their KV cache cannot take another machine’s (said once). Prompts with images or audio are processed here.

The prefill node on its GPU

Section titled “The prefill node on its GPU”

A machine with a GPU reads prompts much faster than its CPU. Start its worker with --device: the prompts of prefill requests then run on the GPU (as many layers as fit, as inga run places them; --gpu-layers and --prefill-chunk as for run), and the KV cache is read back from the card and sent in the decode machine’s format:

Layer ranges for --nodes still run on that worker’s CPU. The GPU’s keys and values are f16: an f16 cache arrives as the GPU computed it, a q8_0 cache is quantized from them on the GPU machine. The GPU’s numbers differ from the CPU’s in their last bits, so the answer may differ in a word now and then from the one this machine gives alone. Nemotron-H’s GPU layers cannot be read back: their prompts are processed on the decode machine, with the line that says why.

In a mesh

Section titled “In a mesh”

With inga serve --mesh, a master that runs a model whole (the plan keeps every layer there) has its prompts read by the satellite with the fastest measured prompt speed, when that is at least 1.5 times its own: it sends that satellite the parts of the model it lacks (every layer, the embedding and the output layer), then uses it as with --prefill-node. --mesh-prefill NAME names the satellite (the master then runs the model whole rather than splitting it), --mesh-prefill off keeps every prompt on the master. The mesh’s events say which satellite was chosen and why; each node announces its measured prompt speed (prefill_speed in GET /api/inga/mesh). A satellite with a GPU (inga satellite --device auto, the default) reads those prompts on it, as inga worker --device does, and announces its GPU’s prompt speed.

Troubleshooting

Section titled “Troubleshooting”
  • “worker …: cannot connect”: the worker is not running, listens on 127.0.0.1 only (start it with --host 0.0.0.0), or a firewall blocks the port.
  • “this worker’s copy of the model differs”: the worker resolved the name to another file; use the same hf:// reference or the same path on every machine.
  • “protocol version …”: the worker’s Inga has no protocol in common with this one (one of them is older than 0.28.0); install the same Inga version everywhere.
  • “–nodes, –expert-nodes and –tp-nodes cannot be combined yet”: use one of them.
  • “LoRA adapters work on one machine only”: --lora runs on one machine: drop the workers.
  • A worker stops mid-answer: the answer fails with the worker’s address; restart the worker and ask again.
  • Slow steps: every token crosses the network once per worker; use a wired LAN, and fewer, larger stages.

Good to know

Section titled “Good to know”
  • The coordinator needs the whole model file too (it reads only its own layers).
  • Mixture-of-experts models work, but experts are not streamed from disk on workers; to host experts on other machines instead, see host-experts-on-other-machines.md.
  • Workers compute with their own instruction set: machines with different CPUs can produce slightly different numbers than a single machine would.
