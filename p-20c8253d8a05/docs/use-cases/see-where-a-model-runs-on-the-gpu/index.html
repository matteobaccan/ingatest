See where each part of a model runs on the GPU

What you get

Section titled “What you get”

When a model loads, Inga prints where every part of it runs (on which GPU, in the RAM or read from the disk) and how much memory it takes, then a tip when something would make it faster. This guide reads that table for each kind of model, dense, mixtures of experts, hybrid, Gemma 4, Mamba-2 and Nemotron, and the options that move the parts: --experts-on, --cpu-moe and the op offload.

Requirements

Section titled “Requirements”
  • A GPU Inga runs layers on, with its driver: run-on-an-nvidia-gpu.md, run-on-an-amd-or-intel-gpu.md, run-on-a-mac.md.
  • A model; the examples are a mixture of experts on a 4 GB Quadro P1000 and models on a 16 GB RX 9060 XT.

1. Get Inga

Section titled “1. Get Inga”

Download the archive for your system from the Releases page and put inga on your PATH (details); inga --version checks it.

3. Read where the model runs

Section titled “3. Read where the model runs”

When a model loads, Inga shows where every part of it runs and how much memory it takes, then tips when something would make it faster:

The last two lines are what the GPU holds beside the parts: the activations of the prompt chunks, and the memory left free for the driver and other programs (256 MiB and 5 % of the card, 10 % on Windows; gpu.keep_free changes it).

A computer that runs only Inga (a server, a box under the desk) can keep less free: --memory-profile dedicated (or profile = "dedicated" under [memory] in inga.toml; inga setup asks, and a server run by inga service takes it by default) keeps 256 MiB of each GPU free and gives the models the RAM less 2 GiB. The start line says the profile and why (“memory: dedicated profile (–memory-profile): 256 MiB of each GPU’s memory kept free, …”), and the GPU’s line says kept free (dedicated profile: 256 MiB). A gpu.keep_free or --mem-limit you set is kept over the profile’s, and the lines say what the profile would have chosen.

On a PC used for everything (the desktop profile, the default), inga serve also watches the free memory of the GPUs it uses and of the RAM. When another program, a game or a video editor, takes memory and the free memory stays under what is kept free for 4 s, Inga gives some back: the copies of idle chats go to the SSD, an idle model’s layers go to the RAM (it keeps answering, slower) or, without room there, it is unloaded. A model answering a request, or one you placed yourself (--gpu-layers, --device, keep_alive: -1), never moves. Once the room is back for 30 s, Inga takes it again. Each move is one line in the log, for example:

and GET /api/inga/system/memory lists the last 100 under watcher.moves. The times are keys under [memory]: watch_fast (2 s), watch_slow (10 s), give_back_after (4 s) and take_again_after (30 s); take_again_per_hour (2) is how many times an hour one model is taken again, after which it stays in the RAM (or unloaded) and the log says so. One card two APIs list (a GeForce as CUDA 0 and Vulkan 0) is watched once, and Inga’s models on either are its own memory, never another program’s: only what other programs took since Inga last placed a model there makes it give memory back. The dedicated profile does none of this.

The web UI shows the same on the Server page, under the GPU view, in “How Inga shares the memory”: the profile in one sentence, whether Inga is watching and what it holds in the RAM to leave room, where the idle chats go (up to --prefix-cache in the RAM, then the SSD), and the last moves, newest first: what moved and where (“Moved to the RAM: Qwen3-8B · Q4_K_M (2.00 GiB) from CUDA 0 Quadro P1000; it keeps answering, slower”), why (“another program needed the memory of CUDA 0 Quadro P1000”), then the log’s line in small text. A model’s Info window on the Models page says where it is now (“In the RAM since 14:02: another program needed the memory of CUDA 0 …”).

The same box starts with the profile’s margins: what each GPU keeps free and why (“Each GPU keeps memory free so that the other programs and the driver find room: CUDA 0 NVIDIA L4 1.25 GiB”, the key gpu.keep_free under it), what the models may take of the RAM (the RAM the system says is free, or in the dedicated profile the RAM less 2 GiB), when the watcher gives the RAM back (under 1 GiB free, its [memory] keys under it), and a value you set yourself, kept with what the profile would have chosen (“The models may take 8.00 GiB of the RAM, as you set it (–mem-limit 8G). Inga does not change it.”). Above it, each card of the GPU view splits a model’s share by kind: its weights, its routed experts (a mixture’s, in a colour of their own), its KV cache, its activations and, with --expert-cache, the expert cache, whose slots are drawn as cells, those holding an expert filled. Under the model’s line the card says the cache’s slots (“72 of 96 slots hold the experts picked most, of 4 layers whose experts stay in the RAM”), its hit rate against the 5 minutes before (“82 % of the picks found their expert on the GPU since 14:05 (78 % from 14:00 to 14:05)”, then the picks counted), and where the rest of the model is (in the RAM, on the disk). GET /api/inga/system/memory gives the cache’s figures under expert_caches, and GET /api/inga/system beside each model’s share (cache, experts, ram, disk).

The idle chats’ moves name their chat: the web UI sends each chat’s title (the X-Inga-Chat header, which any client may send), so the log says “kv-tiers: chat ‘notes’: a chat’s KV cache of 117 tokens copied from its session to RAM …”. A chat written to the SSD is written on a thread of its own, so the answer that replaced it does not wait; its next message waits for that write, then reads it back. When the RAM is short (another program took it, in the desktop profile), a new message first has the idle chats in the RAM written to the SSD and waits for them, said (“kv-tiers: chat ‘notes’: waited N ms for RAM: … 2 idle chat(s) … written to the SSD to make room”); GET /api/inga/system/memory lists those under kv_tiers.waits. With --kv-tiers ram the chats stay in the RAM only, and each one dropped past --prefix-cache is a move of its own.

The GPU keeps the KV cache of its layers as f16, whatever --cache-type says: --cache-type q8_0 halves the cache of the layers on the CPU, and a tip says so. To fit more layers on the card with a long context, a smaller --ctx frees room there.

For a mixture of experts the GPU takes the output layer first (one product of the whole vocabulary per token, the largest of a decode step), then the attention of as many layers as fit, the last ones first, then, when every attention block is there, the shared experts beside them (shared experts of layers ...), then the routed experts of as many layers as the memory left holds, whole layers from the last one back (routed experts of layers 20-39, as llama.cpp’s --n-cpu-moe keeps the first ones on the CPU). The others and the routers stay on the CPU, in RAM or, when the RAM is short, read from the disk: the GPU first, then the RAM, then the disk. The router picks each token’s experts on the CPU; the GPU runs them and sums their outputs, and only the sum comes back.

A hybrid model (Qwen3.5, Qwen3.6, Qwen3-Next: three DeltaNet layers for each full-attention layer) puts its output layer, then the mixing blocks of its layers (the full-attention layers with their KV cache, the DeltaNet layers with their recurrent states), then their shared experts on the GPU, as far as they fit; only the routed experts stay on the CPU:

A hybrid model with dense feed-forward networks (Qwen3.5 and Qwen3.8-27B: DeltaNet and full attention) that does not fit the card goes by whole layers: under --device auto the planner tries every count of last layers whose attention, cache and network go to the GPU, and keeps the one whose decode step it estimates fastest (the CPU’s and the GPU’s reads, a round trip for each GPU layer). The first layers run whole on the CPU, the last ones whole on the GPU. Qwen3.8-27B Q4_0 on a 16 GB RX 9060 XT with --ctx 65536 (from the hardware profiles):

A model that fits, --gpu-layers N and --device NAME place it as any other model.

A prompt’s DeltaNet layers run the chunked delta rule on the GPU (on CUDA, Vulkan and HIP): the tokens go by chunks of 32, as on the CPU, and the state is read once per chunk instead of twice per token. Generation keeps the token-by-token rule. Layers that run whole on the GPU one after the other (the last 48 layers above, or every layer of a Nemotron-H model on the card) go in one call: the hidden state stays on the card between them instead of coming back to the CPU after each layer. Nothing to set: the gpu: line is the same, and so are the answers but for the order of the float sums. On a software device (lavapipe, three runs on a busy machine) a 512-token prompt of a synthetic Qwen3.5-style model went from 28-37 to 36-54 tokens per second; the speed on real cards is still to be measured with inga bench -p 512 (see measure speed).

Gemma 4 26B-A4B places as the other mixtures: the attention of its layers, then its dense networks (as the shared experts), then the routed experts of the last layers while they fit; --experts-on and --cpu-moe apply. The router, the norms around the experts, the per-layer embedding and the layer’s output scale stay on the CPU. Checked against the CPU on lavapipe (Vulkan) only; the Metal code is compile-checked; on CUDA and HIP (heads of 512, requirements) pending a check on a real NVIDIA card.

Mamba-2 and Nemotron-H models (Nemotron-H, Nemotron Nano 2, Nemotron 3 Nano and Super) do the same with their three kinds of layers: the Mamba2 layers (input projection, causal convolution, selective scan, gated grouped norm, output projection) with their recurrent states and checkpoints, the attention layers with their KV cache, then the squared-ReLU feed-forward networks (Nemotron-H) or the shared experts (Nemotron 3), on CUDA and on Vulkan; then, as for the other mixtures, Nemotron 3’s squared-ReLU routed experts of the last layers while they fit (Super’s in their latent space). For a prompt, the projections of those layers’ input into the experts’ latent space and of their sum back run on the card too; the routers, and a generated token’s projections, stay on the CPU. With a model larger than the RAM (Super’s 75 GB file on a PC with 32 GB), the experts left on the CPU are read from the disk while running, as for the other mixtures, and the ones on the card are not read again. For the other mixtures (Qwen3-Next and Qwen3.5’s, say), on a card with more memory (a 16 GB card through Vulkan), the routed experts of the last layers go there too; how many depends on the free memory and the file (the layer numbers below are an example):

  • --experts-on auto (the default) does that; --experts-on cpu keeps every routed expert on the CPU, --experts-on gpu asks for all of them and fails when they do not fit, saying how many do.
  • --cpu-moe N keeps the first N layers’ routed experts on the CPU (llama.cpp’s --n-cpu-moe N), to leave GPU memory to a longer context or another program.
  • --set gpu.op_offload=on makes a prompt read faster when the experts stay on the CPU: from 32 tokens a step, the experts go to the GPU in groups through pinned memory and are multiplied there, each layer’s once a step of up to 2048 tokens. The log’s line op offload: the last prompt step says what limits it (the GPU, the host’s copy into the pinned memory, or the bus). On a Colab L4 with LFM2-8B-A1B Q4_K_M (--experts-on cpu, 1466-token prompt) a prompt reads about 1340 tokens/s with it on, 237 with it off; generation is the same (about 47; performance). It is off by default: auto is not measured yet.
  • The experts’ weight types are those of the GPU’s products (CUDA: F32, F16, Q8_0, Q4_0, Q4_1, Q5_0, Q5_1, Q5_K, Q2_K, Q3_K, Q4_K, Q6_K, IQ4_NL, IQ4_XS; Vulkan the same); a layer whose experts are of another type keeps them on the CPU and the tip says why. Their activation: SwiGLU, or gpt-oss’s clamped SwiGLU with its biases.

“SSD (read while running)” marks parts read from the disk while the model runs (a model larger than the RAM): more RAM helps most there. inga info <model> --gpu-layers all shows the same before loading anything (--json: under placement), and the web UI’s GPU badge says what runs on the GPU.

Options worth knowing

Section titled “Options worth knowing”
Option What it does
--experts-on auto|cpu|gpu where a mixture’s routed experts go (auto: the last layers’ while they fit)
--cpu-moe N the first N layers’ routed experts on the CPU (llama.cpp’s --n-cpu-moe)
--set gpu.op_offload=on a prompt’s experts multiplied on the GPU when they stay on the CPU
--set gpu.keep_free=5% the share of the GPU’s memory kept free
--memory-profile dedicated 256 MiB of each GPU kept free and the RAM less 2 GiB, on a machine Inga has to itself
--cache-type q8_0 halves the KV cache of the layers on the CPU

Troubleshooting

Section titled “Troubleshooting”
  • Fewer layers on the GPU than expected: close programs that use the GPU (a browser with hardware acceleration), or a smaller --ctx; the tip says how much more memory would put the rest there.
  • When the model does not fit at all: run-on-an-nvidia-gpu.md.
