The maintainers’ roadmap tool: how Inga compares with the other inference engines, the apps people run local models in, and the routers and gateways in front of many models, and when each missing feature lands in Inga (../TODO.md). Every new piece of software looked at goes here with its comparison, and every idea taken from it points to its TODO.md item. Users looking for what Inga can replace read what-inga-replaces.md instead.

Part 1 — engines

Section titled “Part 1 — engines”

How Inga relates to other open-source inference engines and frameworks, and when each feature is planned to land in Inga. The engines are in three groups, each with its own table per feature area: local engines (closest to Inga), serving engines (multi-user GPU servers) and frameworks and runtimes (ML libraries and on-device runtimes, judged together with their LLM layer).

  • Last surveyed: 2026-10-09 (each project’s latest release and notes since the previous survey, local engines 2026-10-07, serving engines and frameworks 2026-10-08); Inga column updated with every release, last on 2026-10-14 (main: CHANGELOG.md up to [Unreleased]) and the releases decided that day (the other projects were not re-surveyed since, apart from the projects seen in the news below). Re-survey after every release, see RELEASING.md.
  • Sources: each project’s GitHub README and docs on the survey date, plus the landscape research in research/; the 2026-10-08 survey, with a source for every cell, is in research/notes/engines-survey-2026-10-08.md. Star counts are approximate.
  • Legend: ✅ supported · 🟡 partial / experimental · ❌ not supported · ❓ not verified. † = from prior knowledge, not re-checked on the survey date: check it before relying on it. In rows added on 2026-10-08, ❓ often only means that the project was not checked for that feature. In the Inga column: ✅ = implemented (🟡 = partly), with no release (the CHANGELOG says which one shipped it); a bold version number (0.31.0 … 0.38.0) = the release TODO.md plans it for; later = in TODO.md’s Later, no release yet; — = not planned. Every feature another engine has is scheduled; see ../TODO.md.

Where Inga stands

Section titled “Where Inga stands”

Colibri and ds4 already do much of what makes Inga different from llama.cpp: streaming MoE experts from disk, and splitting work across machines (Colibri runs remote experts, ds4 has pipeline and tensor parallelism). Inga therefore cannot claim those ideas as unique. What it can offer that none of them combine:

  1. Generic loader for standard formats. Colibri and ds4 need their own converted weights and support a handful of model families; Inga loads any supported architecture straight from GGUF and safetensors.
  2. Truly zero runtime dependencies, including CUDA. Only the NVIDIA driver is needed; no CUDA runtime, cuBLAS or extra DLL (layers on NVIDIA GPUs through CUDA, on Intel, AMD and NVIDIA through Vulkan, MoE experts, DeltaNet and Mamba-2 layers on either).
  3. Dense and MoE on the same memory hierarchy. Disk streaming and remote placement apply to dense models too, not only to routed experts.
  4. Rust: memory safety in a code base that parses untrusted files and network input, and an embeddable crate later.
  5. Windows as a first-class platform next to Linux and macOS.

The serving engines (vLLM, SGLang, Sonar; TGI is archived) aim at many users on datacenter GPUs, need Python and a CUDA-matched PyTorch, and treat Windows as unsupported: Inga takes their serving features (batching, prefix caching, multi-LoRA, chunked prefill, observability) into a single binary for one machine or a LAN. The frameworks and runtimes (Candle, Burn, MLX, ONNX Runtime, MNN, ncnn) are libraries to build engines with, or need models converted to their own format; their strengths Inga lacks are hardware reach (NPUs and mobile 0.38.0, WebGPU 0.36.0) and language bindings (0.38.0).

What Inga takes from the gateways

Section titled “What Inga takes from the gateways”

Scheduled in ../TODO.md through the API nodes spec (its §2 has the details and the lessons):

  • aliases, fallback chains and fallbacks by error class (LiteLLM, Portkey);
  • cooldowns and a circuit breaker per node (LiteLLM, Portkey, Envoy);
  • eligibility before scoring: capabilities, context, parameters (OpenRouter’s require_parameters, LiteLLM’s pre-call checks);
  • privacy as a routing input (OpenRouter’s data_collection / zdr → Inga’s local-only);
  • costs from a price table plus each answer’s usage, budgets, token limits (LiteLLM, Envoy);
  • connections with model prefixes and keys kept server-side (Open WebUI), peers named peer/model (llama-swap);
  • learned routing after the rules (RouteLLM, NVIDIA LLM Router).
