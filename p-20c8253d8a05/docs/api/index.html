The APIs of inga serve

OpenAPI 3.1 descriptions of every route inga serve answers, written from the code (crates/inga-server/src/), not copied from the upstream specifications: each file says which fields Inga reads, which it accepts and ignores (marked Accepted and ignored), and the extensions it adds.

File Covers
openai.yaml GET /v1/models, POST /v1/chat/completions (streaming, tools, images, audio, logprobs, n), /v1/completions, /v1/responses, /v1/embeddings, and the llama-server extensions: grammar, response_format (json_object, json_schema), lora, chat_template_kwargs, reasoning_effort, top_k, min_p, repeat_penalty, dry_*, xtc_*, mirostat*, logit_bias, typical_p, top_n_sigma
anthropic.yaml POST /v1/messages (streaming, tools, images, thinking blocks) and /v1/messages/count_tokens
ollama.yaml GET /, /api/version, /api/tags, /api/ps, POST /api/show, /api/chat, /api/generate, /api/embed, /api/embeddings, /api/pull
lmstudio.yaml LM Studio’s REST API: GET /api/v0/models, /api/v0/models/{id}, POST /api/v0/chat/completions, /api/v0/completions, /api/v0/embeddings
kobold.yaml The KoboldAI API as KoboldCpp serves it: POST /api/v1/generate, /api/extra/generate/stream, /api/extra/tokencount and the GET info routes
llamacpp.yaml llama-server’s native API: POST /completion (and /completions: raw prompts, token ids, several prompts, n_probs, streamed), /apply-template, /embedding (and /embeddings), GET /props, GET /slots, POST /lora-adapters
jev.yaml TypeSafe AI’s Jev decisions API: POST /v1/systemone (typed answers read from the logits: choice, score, yes / no) and GET /ready
inga.yaml Inga’s own and llama-server-style routes: /health, /metrics, /tokenize, /detokenize, /infill, /v1/rerank (and /rerank, /v1/reranking, /reranking), /v1/classify, /lora-adapters, and the web UI’s model hub /api/inga/*

A running server serves these files too, with no API key needed: GET /api/openapi lists them and GET /api/openapi/{file} returns one (the files of its version); the web UI’s API tab reads them to try every endpoint in place.

Security is the same everywhere: with --api-key KEY (or serve.api_key in inga.toml) every request but GET /health, GET /ready, GET /api/openapi* (and the chat page a browser gets at /) needs Authorization: Bearer KEY or x-api-key: KEY; without it, none is needed.

Families

Section titled “Families”

Each route belongs to one family, the API it comes from; every family is on unless the server’s maintainer switches it off: [api] disabled = ["kobold"] (or enabled = [...] for the only ones kept on) in inga.toml, inga serve --api-disable kobold,azure, --api-only openai,inga,webui, or live with POST /api/inga/server {"api": {"disabled": [...]}} (never inga there). A route of a family off answers 404 with "type": "api_disabled" and family, setting and source (file PATH:LINE, flag --api-disable, live) next to the message, in the family’s own error shape; its file leaves GET /api/openapi. GET /health belongs to no family and always answers. A route other families’ clients call too (GET /v1/models, /v1/rerank, /tokenize) stays on while its owner or one of those families is on. GET /api/inga/server lists the families (apis) with their state and where it comes from.

Other servers’ ports

Section titled “Other servers’ ports”

inga serve --like ollama ([api] like = ["ollama"]) also listens on Ollama’s port, 11434, answering there only what Ollama answers (ollama, openai); the other families answer 404 there, naming the main port. Stop the other server, start Inga, and its clients do not change:

--like Port Families on that port
ollama 11434 ollama, openai (GET / answers Ollama is running, even to a browser)
lmstudio 1234 lmstudio, openai
kobold (koboldcpp) 5001 kobold, openai
vllm 8000 openai
tgi, tei 3000 tgi / tei (0.33.0), openai
llamacpp (llama-server) 8080 every family: nothing to add on Inga’s default port

--like NAME:PORT picks another port (:0 a free one, listed by GET /api/inga/server). A port in use stops the start, naming the program that usually holds it. a1111 (7860) is refused until its API comes (0.33.0).

Viewing them

Section titled “Viewing them”

Any OpenAPI 3.1 viewer opens them; each file stands alone:

  • Swagger UI: docker run -p 8081:8080 -e SWAGGER_JSON=/api/openai.yaml -v "$PWD/docs/api:/api" swaggerapi/swagger-ui, then http://localhost:8081 (or paste the file into https://editor.swagger.io).
  • Redocly: npx @redocly/cli preview-docs docs/api/openai.yaml, or npx @redocly/cli build-docs docs/api/openai.yaml -o openai.html for a static page.
  • Editors: the OpenAPI extensions of VS Code and JetBrains IDEs.

To validate them: npx @redocly/cli lint docs/api/*.yaml, or openapi-spec-validator docs/api/*.yaml (Python).

How they stay true

Section titled “How they stay true”

tests/api_specs.rs (run by cargo test) scans the router in crates/inga-server/src/ (the ("GET", "/...") and ("POST", "/...") patterns, the starts_with prefix routes and the paths matched under them) and fails when a route is in no file, when a file describes a path the server does not route, or when a file is malformed: no source header, a tab, no openapi: 3.1.0, an info.version other than the crate’s version, an operation without operationId or responses, a duplicated path or operationId. A pull request that adds a route adds it here; the release PR sets info.version in every file to the new version.

The behaviour is tested end to end by tests/server.rs, which starts inga serve on a small synthetic model and talks raw HTTP to it:

Trying a real client

Section titled “Trying a real client”

Start a server (inga serve model.gguf; add --api-key KEY to try the key), then:

SDKs and apps only need the base URL: http://127.0.0.1:8080/v1 for OpenAI clients, http://127.0.0.1:8080 for the Anthropic SDKs, Claude Code (ANTHROPIC_BASE_URL), Ollama clients (OLLAMA_HOST=127.0.0.1:8080) and KoboldAI clients such as SillyTavern. Code generators that read OpenAPI (for example openapi-generator) can build a typed client from these files. More in serve-openai-and-anthropic-apis.md.
