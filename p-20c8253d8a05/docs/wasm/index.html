Inga in the browser

Page: https://matteobaccan.github.io/ingatest/ (public, published from main by .github/workflows/pages.yml to the public repository matteobaccan/ingatest: see how the page is published).

Inga compiled to WebAssembly: a GGUF model runs in a browser tab, on the device’s CPU or on its GPU through WebGPU, with nothing installed and nothing sent anywhere (the model is downloaded to the browser’s private storage and runs there). It is the page of web/, described step by step in Run a model inside the browser; this page says what it covers and how to report. To use the same build in your own web application, or to call inga serve from JavaScript, see Integrate Inga in a JavaScript application.

The page

Section titled “The page”

A side bar (a drawer behind ☰ on a phone) with Inga’s mark and name, three entries and the conversations: New chat (a new conversation in the chat view), Models (the catalog, the test models, a link, a file of the device, the stored models) and Settings; the conversations below them are the way back to an earlier chat (or to the one open, from another view). Its foot has About (ⓘ), the theme, the guide (this page) and Test, which opens the tests and the report (the Standard test, the GPU benchmark and kernel times, the disk speed test, Report on GitHub). The status line is above every view; its { } button shows the load log. The colours, icons and mark are those of inga serve’s web UI (its Light and Dark themes and SVG sprite).

  • Chat: the conversation’s title and message count at the top, with rename, export as Markdown, download as JSON and full screen (where the browser allows it; not on an iPhone). Messages as bubbles: yours on the right, the model’s on the left under the mark of the model that wrote it (its catalog family’s line icon on a round tile, or the family’s logo; Inga’s logo for a model loaded by link or from a file of the device; kept with each message, so an older conversation shows its own model’s) with its name and, under each answer, First token: N ms, Prefill: X tok/s, Decode: Y tok/s and the time. The time to first token (TTFT) runs from the request to the first piece of the answer (reasoning included), the prompt’s processing included, as the worker measures it; the status line under the chat says it too. The composer: the model’s chip (it opens the catalog), Think (only for a model whose chat template can think: <think>, enable_thinking, harmony’s channels…), a new chat, Stop, the context used and Send. An answer ends at the model’s end-of-generation token or at its template’s plain-text turn marker (Emma-6’s ### Risposta:).
  • Max tokens run out: an answer whose reasoning used all of Max tokens (or that ended with no answer after its reasoning) says so in its bubble, in place of “…”, with Raise to 2×N and regenerate (Max tokens doubled, the question asked again) and, for a model that thinks, Regenerate without Think; an answer cut by Max tokens is marked “Stopped: Max tokens reached (N)” with the same Raise. The engine cannot continue an answer it stopped (no assistant prefill), so there is no Continue: the question is asked again with more room. Max tokens left at its default (never changed by hand) is at least 2048 for a model that thinks while Think is on.
  • No model loaded: the empty chat says so, with Choose a model (it opens the catalog) and Try a small one, which downloads and loads the smallest variant that fits this browser of the catalog’s starter models ("starter": true: Qwen3.5 0.8B and Llama 3.2 1B Instruct); Send stays off, and the hint under it points to the button.
  • Inga’s mark in the side bar is inga serve’s animated one (copied from its web UI): its pieces burst apart and come back while a model loads or an answer is written, and it is still otherwise (always, with the system’s “reduce motion”).
  • Questions (deleting a chat, every chat, a stored model file, the model files, all stored data, the Standard test’s results; renaming a chat) are asked in the page’s own box, not the browser’s: a title, the message with the name in bold, Cancel and the action (red when something is deleted), and for Delete all an Export first. Escape and a click outside cancel; the focus stays in it and goes back where it was.
  • Context used: a ring next to Send, as in inga serve‘s web UI, that closes as the conversation fills the model’s context (the context window it was loaded with): the system prompt, the messages Past messages sent keeps and the message being written, counted with the model’s own tokenizer and chat template (Model.countChat), after each answer and when the typing pauses. Its tooltip reads “Context used: N of M tokens (P %)”; the ring turns amber past 75 % and red past 90 %, and from 85 % the tooltip adds that the oldest messages will be left out. A click or a tap opens its panel, as the web UI’s: the tokens used and free, the system prompt, the past messages sent, the draft and the room kept for the answer in bars, the older messages the next question would leave out (start a new chat to keep them), and the context’s size, the model’s n_ctx or the Settings’ value. The parts are counted only while it is open; a second tap, Escape or a tap outside close it. When a question would not leave the answer its room (Max tokens, at most half the context), the oldest messages are left out of what the model reads, a whole exchange at a time (the system prompt and the question stay), and the status line says how many; the conversation itself keeps them. New chat starts from an empty context. An answer that fills the context stops there, and its bubble says so: “Stopped: the context is full (N tokens: the question took P, the answer A). The answer did not fit”, with Raise the context to 2×N and regenerate (the model loads again with it, the conversation kept, then the answer is asked again). When the context loaded is less than the one asked, the load line, the ring’s tooltip and its panel say how much and why: “Context: 4096 of the 8192 asked: the GPU memory limit (6.00 GiB) and the memory limit (3.50 GiB) leave room for 4096; raise GPU memory in Settings” (the page loads the largest context the limits hold instead of refusing the model), or the model’s training context; then the bubble gives that reason instead of Raise. A context changed in Settings and still to be loaded is said in the panel too.
  • Speed said plainly: when layers run on the CPU because “GPU memory” does not hold them, or are read from storage at every token, the load line and the statistics under each answer say so with what to raise (“11 of 32 layers run on the CPU, not the GPU: GPU memory (6144 MB) does not hold them; raise GPU memory in Settings for speed”).
  • Idle: once loaded and answered the page runs nothing (no interval, no animation frame; the mark’s loop only while it loads or answers). Hidden, it stops the mark and the pending count; hidden for 10 minutes with a model on the GPU and nothing running, it ends the model’s worker, giving its memory and the GPU back (a tab left for hours with a 7B model froze its Chrome window on a Mac), and loads the model again when the tab is shown, the conversation kept.
  • A GPU that resets (WebGPU’s device lost: the GPU reset, its driver restarted, the system took its memory back): said once, “The GPU was reset (…): the model is no longer loaded. Reload it on the CPU or on the GPU.”, with the details a report needs (the adapter’s vendor, architecture, device and description, the browser, the model, the backend and its pacing, and whether it happened while loading, reading the prompt or answering, after how many tokens); the load log ({}) keeps the same in English with the user agent. Under the chat, Reload on the CPU (WebAssembly: slower, but nothing to reset) and Reload on the GPU. Nothing is retried by itself. The resets are counted per adapter in this browser (localStorage inga.gpuLost): after the second on the same adapter, its models load on the CPU (the reset message, the reload bar and the load line say so), and Try the GPU again (Settings, under Device, or the reload bar) lifts it until the next reset.
  • A phone’s GPU is paced: a mobile GPU’s driver resets the device when one submission of work runs too long (its watchdog). On the GPU, a prompt goes through the layers in chunks of up to 256 tokens, each chunk’s every layer in one submission (about 16 dispatches per layer), and each token’s layers and output layer in another. On a mobile-class device the page asks for prompt chunks of 64 tokens and at most 24 dispatches (about a layer) per submission (web/gpupace.js; the load log says “GPU: paced for a mobile GPU”). Mobile-class: the browser says it is a phone or tablet (navigator.userAgentData.mobile; Android, iPhone, iPad or iPod in the user agent; an iPad’s desktop user agent with a touch screen), or the adapter’s vendor is ARM (Mali) or Imagination (PowerVR); Qualcomm’s Adreno is left to the user agent, since Windows laptops have it too. Desktops keep the defaults and their speed; ?gpu_pace=mobile or ?gpu_pace=desktop in the address forces either.
  • Version: the side bar’s foot and About show the published page’s version, small: “v0.31.0 · 16 Oct 2026 · abc1234” (Inga’s version from Cargo.toml, the build’s UTC date in the page’s language, “16 ott 2026” in Italian, and its commit), which the Pages workflow writes into the page’s inga-version and inga-build meta tags; a page served locally says “dev”. The report and the Markdown exports carry it too.
  • Conversations are kept in this browser (IndexedDB) and listed in the side bar (title, message count, date), each opened again or deleted (the trash asks first, with the title, as inga serve’s web UI does); New chat starts one (stored at its first message). The open conversation’s entry brings you back to it as it is from another view (also while a model loads or answers, when the other entries wait; New chat then shows the chat without starting one). Loading a model starts a new one; the Standard test and the GPU benchmark run in a conversation of their own. In a private window that refuses IndexedDB they last for the visit, and the list says so.
  • Every conversation at once: the archive button next to “Conversations” opens Export all (JSON), Export all (Markdown), Import chats and Delete all. The JSON file (inga-chats-DATE.json) is the format of inga serve’s web UI’s “Every chat” backup, so a file moves between the two: a list of conversations, each with version: 1, its id, title, created and updated (milliseconds), model, settings (params: the sampler’s values of its last question; system: the system prompt sent) and messages (role, content, reasoning, model, mark, stats, at). The Markdown file holds every conversation under its title. Import chats reads such a file (this page’s, the web UI’s backup, or one conversation’s JSON) and adds what is not here by id: a conversation already here (the same messages) is skipped, one whose id is taken by another is added with a new id and a numbered title (“Title (2)”); nothing is overwritten, and the status line gives the counts. Delete all asks first, offering Export first.
  • About (the ⓘ button at the foot of the side bar): Inga’s logo and name (“a local inference engine in Rust, by Matteo Baccan”), what the page does, then three rows: it runs in this browser (the CPU through WebAssembly, or the GPU through WebGPU), it is private (nothing leaves the device but the model’s download), and the models, the conversations and the settings are kept in this browser; the version, and the links as rows: Matteo Baccan on GitHub, Report a problem (https://github.com/matteobaccan/ingatest/issues) and this guide. It closes with its ✕ button, Escape or a click outside.
  • Settings (kept in this browser; Reset all settings restores them):
    • Answers: temperature, top P, top K, min P, repeat penalty, presence and frequency penalties (Inga’s sampler, as inga run; an empty field leaves Inga’s default), max tokens. Preset: when a model loads, the sampling settings and the context you have not changed by hand take the model’s values (web/preset.js): its catalog entry’s sampling and ctx (below), else what its GGUF recommends (general.sampling.*, as inga run and inga serve use them), else Inga’s defaults. The Preset line says whose values are in use (“From the model: …”, or “Yours: … changed by hand”); Use the model’s settings gives the hand-set ones back to the model (the context at the next load). Seed: empty (the default), a new random seed for each answer, so asking again draws again; a number, the same seed every time (the same conversation and settings give the same answer). Each answer shows its seed under it and in the Markdown export; the Standard test keeps its fixed seed;
    • Conversation: a system prompt (sent first when checked), Past messages sent (the last N with each question, 0 for all; never starting on an answer), the send key (Enter, or Ctrl / ⌘ + Enter);
    • Model loading: the context window, the KV cache, Memory for the model, Device, GPU memory and its accounting, the draft model. The Context window left empty is Auto: the context the model was trained for (its GGUF’s context length), lowered only when its KV cache would take more than half of the memory its weights leave (the GPU memory limit on the GPU, else the memory limit, at most WebAssembly’s 4 GiB), never below 2048 unless memory forces it; the field, the ring’s tooltip and the load line then say what was chosen (“Auto: 32768 (model, KV Q8_0 2.13 GiB)”, “Auto: 12288 (memory; model 131072, KV F16 1.50 GiB)”); a number set wins. The KV cache (Auto, F16, Q8_0, Q4_0): Auto keeps F16 when the whole context fits, else Q8_0 (about half the bytes) before a shorter context; on the GPU the cache stays F16 (its layers have no other), and the tooltip says so. Max tokens is 1024 by default; a page saved with the old defaults (256, a context of 2048) never changed by hand takes the new ones. GPU memory’s Auto follows the adapter, since WebGPU does not tell a GPU’s memory, and the line under it says what it gives and why: 1024 MB on an iPhone or iPad; an Apple GPU (a Mac’s, sharing its memory) 3/4 of navigator.deviceMemory (Chrome reports at most 8 GB: 6144 MB, which holds a 7B Q4 model and its KV cache; 3072 MB left a third of Mistral 7B’s layers on the CPU of a 128 GB Mac, 4 tok/s), or the adapter’s maxBufferSize when larger; another adapter 4096 MB when its maxBufferSize (4 GiB) and the device’s memory (8 GB) are large, else 3072 MB; 16 GB at most. A change applies when Settings is left: the model loaded is loaded again with it (after the answer running, if one is), the conversation kept, and the status line says why (“Reloading Emma-6 on the CPU: the Device setting changed”); each of these fields says so. The Answers settings never reload the model;
    • Appearance: theme (Auto, Light, Dark; also the side bar’s theme button), font size, language (English or Italian: the side bar, headings, buttons and labels; the longer explanations and the status line stay in English), and the load log’s level (every step, the start, the end and errors, or off).
  • Models: the Test models are folded under their heading with their count (the page remembers whether they were open); Delete model files removes every stored model (conversations and settings stay); Delete all stored data removes every file the site stores and the conversations.

What works

Section titled “What works”
  • A model: from the model catalog (Browse models, below), one of the suggested test models (SmolLM2-135M to Qwen3-4B), a link to a GGUF file on Hugging Face (downloaded into the browser’s storage, OPFS; an interrupted download resumes), or a file of the device. Stored models stay for the next visit. While a model downloads, the status line says what is down of the whole file and the percent, the speed (an average over about 5 s, the first second and pauses left out; a resumed download counts only its own bytes) and the time left (“about 3 min 20 s left”, after “estimating…”); a server that does not say the size shows what is down and the speed only.
  • Chat with the answers rendered as Markdown; thinking models (Qwen3) show their reasoning folded.
  • Device: on the published page (or with ?published in the address elsewhere), the GPU (WebGPU) by default where the browser has it (not on iOS, where the CPU was faster); a model or weight type the GPU does not run loads on the CPU, and the status line says why. Device CPU in the Settings forces the CPU.
  • Every core: GitHub Pages cannot send the headers that allow WebAssembly threads, so a small service worker (web/coi-sw.js) adds them and the page reloads once; where that fails the page runs on one thread (the status line says how many).
  • Tests: the Standard test (a fixed prompt, comparable between devices; its line has ttft N ms before the prompt’s and the answer’s speeds), the GPU benchmark (tokens/s under each kernel choice) and Kernel times (each GPU kernel’s time per token), the load log under the status line, the disk speed test.
  • Report on GitHub (Test): opens a new issue on the public matteobaccan/ingatest with the browser, its GPU adapter, the model, the speeds, the load log and the errors filled in (the Inga in the browser report form once it is on ingatest, a plain issue with the same text until then); you add what you did and submit it. Copy report gives the same text.

The model catalog

Section titled “The model catalog”

Browse models opens the catalog: GGUF models on Hugging Face whose architecture Inga runs (llama, qwen2, qwen3, qwen35, gemma2, gemma3, gemma4, phi3, mistral3, granite, smollm3, lfm2), from well-known repositories (bartowski, unsloth, ggml-org, NousResearch, TheBloke, LiquidAI, mistralai, ibm-granite). A search box (words of the name, the family, a size, a quantization: qwen 1.5b q8), a chip per family (its line icon, a symbol of the page’s sprite, or its logo: an image of the page’s icons/, which wins over the icon; Emma’s, icons/emma.svg, is Inga’s own drawing in Egomnia’s teal, not Egomnia’s logo) and a card per model, whose list holds its variants (quantizations: Q4_K_M, Q5_K_M, Q6_K, Q8_0…) with their sizes and a mark:

  • ✅ fits: the weights plus about 256 MiB for the KV cache and buffers are under 85 % of the room;
  • ⚠️ tight: under the room but close, or larger, up to twice it: what does not fit is read from storage at every token (slow);
  • ❌ too big for this browser: more than twice the room, more than the storage the browser still gives the site, or larger than the room with “All in memory”.

The room is “Memory for the model” (Auto: 3584 MB, 1600 MB on an iPhone or iPad), at most the 4 GiB a 32-bit WebAssembly module addresses (the build does not use Memory64) and at most half of navigator.deviceMemory where the browser tells it; with Device GPU or Auto and a WebGPU adapter, plus “GPU memory” when it is counted apart (a desktop; Auto is a guess, as WebGPU does not tell a GPU’s memory). The dialog says what it judged on, with the adapter’s maxBufferSize and maxStorageBufferBindingSize (Inga splits a larger tensor into buffers of whole rows, so they do not limit a model). Models with no variant better than ❌ are hidden until Show models too big for this browser. A stored variant is marked downloaded and has a Delete, which frees its space. Once a download has measured a speed (kept in this browser), the others say how long they would take at it (“~8 min at your last measured speed”).

The catalog is web/catalog.json: families (label, icon) and models (name, family, architecture, parameters, licence, repository) with their variants (quantization, file name, size in bytes), and optionally a preset: ctx (the context its makers give) and sampling (temperature, top_p, top_k, min_p, repeat_penalty, presence_penalty, frequency_penalty, and source, where the values come from), over what the GGUF recommends (Emma-6: Egomnia’s own chat defaults; the newer models: the sampling their model cards recommend). Every file was checked on Hugging Face on 2026-10-31 by tools/wasm-catalog.py --write --arch: the sizes are exact, the paths exist and each GGUF’s general.architecture is the catalog’s ("checked" holds the date). A variant added by hand may carry an estimated size ("approx": true, shown as “about … (estimated, not yet checked)”) until the tool runs again. Run it after each change of the catalog:

It lists each repository through Hugging Face’s API, writes each file’s exact size, marks a file it does not find "missing" (or, with --drop-missing, leaves it out) and, with --arch, reads each file’s GGUF header to check general.architecture. HF_TOKEN is sent when set. The Pages workflow runs it with --drop-missing on the published copy, so the published page never offers a file that is gone; a step that cannot reach Hugging Face leaves the copy as committed. A file that is not where the catalog says fails on the page with the HTTP error and a message naming the catalog’s entry.

Left out of the catalog, with the reason: Phi 2 and Phi 1.5 (phi2), StableLM 2 Zephyr (stablelm), RedPajama INCITE (gptneox) and LFM3 1.7B (lfm3, released 2026-10-24; a support request in docs/todo/inbox.md): architectures the browser build does not run; Phi 3.5 vision: its images need a projector the browser build does not read (the text model is Phi 3.5 mini); TinyLlama Chat v0.4: superseded by v1.0, no well-known GGUF. Removed on 2026-10-31, superseded by newer models of their families: Llama 2 7B and 13B Chat, Llama 3 8B and 70B Instruct and Llama 3.1 70B Instruct (Llama 3.1 8B and 3.2), Qwen2 0.5B, 1.5B and 7B Instruct and Qwen2 Math 1.5B and 7B (Qwen2.5, Qwen3 and Qwen3.5), Qwen3 4B (Qwen3 4B Instruct 2507 and Thinking 2507), Mistral 7B Instruct v0.2 (v0.3 and Ministral 3), OpenHermes 2.5 and NeuralHermes 2.5 Mistral 7B and Hermes 2 Pro Llama 3 8B and Mistral 7B (Hermes 3), WizardMath 7B v1.1 and Gemma 2 2B JPN it (Gemma 3 and 4).

Answers that differ between devices

Section titled “Answers that differ between devices”

The CPU, the GPU and the native engine add up the same numbers in different orders, so their log-probabilities differ slightly: by up to about 0.1 to 0.3 on Emma-6 (Llama, Q8_0), which is normal rounding. A token that wins by less than that (a near tie) can therefore go either way, and from there the answers part. On Emma-6, “ciao” is such a tie at its first token: “ **” against “ [“, 0.01 to 0.09 apart on every device. The native CPU, the page’s CPU, WebGPU on lavapipe and WebGPU on SwiftShader each fall on one side or the other, with the same prompt tokens, at a context of 2048 or 4096 alike. A small model that starts on the worse branch can drift into turn after turn of its own format (”[ ] ### In risposta a [risposta di B] ### …“), and with a fixed seed it drew the same text every time. That is what the page first showed on WebGPU, and it was not a GPU bug (the probe below, 2026-10-16). Use the model’s preset (the Settings’ Preset, which for Emma-6 adds a repeat penalty of 1.1 and a top-p of 0.9) and the random seed of each answer. A question with a clear answer (“Dimmi la capitale d’Italia.” gives “ Roma.“) answers the same everywhere.

The probe is .github/workflows/wasm-probe.yml, run on a push to a branch ci/wasm-probe*. It runs a real model through the page’s worker in headless Chromium (the CPU, and WebGPU on SwiftShader), through the same Runner natively (the CPU, and WebGPU on lavapipe), and through inga run. It then compares the texts, the token ids and the first step’s top 5 log-probabilities in the run’s annotations (crates/inga-wasm/tests/probe-plan.json, probe-compare.cjs).

Good to know

Section titled “Good to know”
  • The page runs GGUF language models, as a chat: the server, the APIs, the tools, images and speech are the desktop inga’s.
  • Models larger than about 4 GB in memory: WebAssembly addresses 4 GiB; a larger model runs by reading layers from storage at every token, much slower.
  • On the GPU: Gemma 4’s E models stay on the CPU; the i-quants with grids (IQ1–IQ3) were tested on a software GPU only; the subgroup kernels are off by default.
  • Firefox: WebGPU only in recent versions; untested.

Browsers

Section titled “Browsers”
  • Chrome / Edge 113+ on Windows, macOS, Linux, Android: CPU and WebGPU.
  • Safari 16.4+ (macOS, iPhone, iPad): CPU; WebGPU from Safari 26. Measured on an iPhone 16 Pro.
  • Firefox: CPU; WebGPU where enabled. Untested.

A small model first (SmolLM2-135M, about 0.15 GB), then larger ones: a phone’s tab may be closed by the system for memory, which the page reports as a stopped worker.

How to report

Section titled “How to report”
  1. Load a model, ask something, open Test (at the foot of the side bar) and press Standard test (and, on the GPU, GPU benchmark).
  2. Press Report on GitHub, check the fields, say what you did and what went wrong, submit. Filing an issue needs a GitHub account (any: ingatest’s issues are public); without one, Copy report and send the text to the maintainer.

The report lists the browser, the GPU adapter’s name and limits, the model’s file name and the speeds: read it before submitting, it becomes a public GitHub issue.
