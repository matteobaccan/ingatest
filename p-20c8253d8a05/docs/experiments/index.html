Performance experiments

Every performance idea tried in Inga, whatever came of it. An idea that was measured and did not pay off is not deleted: it stays here as “set aside”, with its numbers, because it may work in another context (other hardware, models, batch sizes, context lengths). Before trying an idea, look for it here; after trying it, log it here.

The rule every performance pull request follows is in performance.md; the measured speeds of the released code are in performance.md.

Format

Section titled “Format”

One entry per idea, newest first within each verdict:

  • Source: the project, paper or link it comes from.
  • Date and Inga version it was measured with.
  • Measured on: the hardware and the model (file, type).
  • How: the command (inga bench ...), the same machine before and after.
  • Result: the numbers before and after.
  • Verdict: adopted, set aside or pending (not tried yet).
  • Why: what explains the result.
  • Could work when: the conditions under which it is worth trying again.

WebAssembly: SIMD128 kernels, and threads on Web Workers

Section titled “WebAssembly: SIMD128 kernels, and threads on Web Workers”
  • Source: the inga-cpu SIMD tables (NEON, SSE4.1) carried to core::arch::wasm32; the threads as wasm-bindgen-rayon starts them (Web Workers on the shared memory).
  • Date: 2026-10-14 · Inga version: 0.30.1 (branch exp/wasm-cpu)
  • Measured on: headless Chromium (Playwright 1.64) on a Linux container with 4 vCPUs; synthetic SmolLM2-135M Q8_0 and Llama-3.2-1B Q4_K_M (tools/bench_model.py)
  • How: node crates/inga-wasm/tests/browser.cjs bench <web> <model> 32 2 (Llama: 8 1), bench-isolated for the threads; spec §8.7 “Numbers, second step”
  • Result: SmolLM2 prompt 5.6–6.7 → 25.1–30.0 tok/s (one thread) → 73.8–95.8 (four), answer 4.2–5.2 → 10.6–13.9 → 34.1–42.0; Llama prompt 1.0–1.1 → 6.0–6.4 → 20.7–26.0, answer 0.7–0.9 → 3.2–4.1 → 11.7–13.1
  • Verdict: adopted
  • Why: the scalar kernels did not vectorise for wasm (LLVM leaves the reductions scalar, the first step’s “built with simd128” row); SIMD128’s extmul / extadd_pairwise / dot_i16x8 do 16 byte products in a few instructions, and the dot4 prefill kernels unpack each weight block once for four tokens (the scalar table has none, so the prompt was no faster than the answer). Every output stays computed by one thread, so threads change no bit.
  • Could work when: relaxed SIMD (i16x8.relaxed_dot_i8x16_i7x16) reaches Safari, or as a third module for Chrome and Firefox; four-row decode kernels for Q4_K / Q6_K.

The server’s decode loop as fast as bench’s forward pass (issue #461)

Section titled “The server’s decode loop as fast as bench’s forward pass (issue #461)”
  • Source: issue #461: Gemma 4 12B Q8_0 on an RX 9060 XT (Vulkan) generated 19.8 tok/s in inga bench and about 10 in the web UI; Gemma 4 26B-A4B (experts on the CPU) 18.2 and 9.8–12.8, the first prompt after load waiting 16.7 s.
  • Date: 2026-10-14 · Inga version: 0.29.0+ (branch fix/server-decode-speed)
  • Idea: (1) top-k over the logits in one pass, copying only those above the k-th best so far (compacted at 2k), instead of an (id, logit) pair per token of the vocabulary and a selection over all of them; (2) the speculation gate times PLAIN_PROBE = 4 plain steps before the first draft, and ends a measure after EARLY = 4 checks when nothing was accepted or the checks run at under half the speed of plain steps; (3) the server reads a mixture’s memory-mapped experts ahead (madvise(MADV_WILLNEED) / PrefetchVirtualMemory) once its sessions are made.
  • Measured on: a 4-core AVX-512 cloud VM shared with other builds (noisy); synthetic Q8_0 models with a 262,144-token vocabulary: Qwen3 4 layers of 256 (137M parameters, most of them the embeddings and the output layer) and Qwen3 MoE 8 layers of 512, 64 experts of 512, 8 per token; a Qwen3 MoE of 3.4 GB (16 layers of 1024, 128 experts) for the cold start. No GPU, no real model.
  • How: a Session with the server’s default sampling (temperature 0.8, top-k 40, top-p 0.95, min-p 0.05) and its default speculation, four answers of 200 tokens in a row, the binaries before (main at 98ad7a6) and after alternated, three rounds; inga serve with /v1/chat/completions (200 tokens, streamed and not); for the cold start, the page cache dropped, inga serve, 5 s, then a 1028-token prompt and a second, different one.
  • Result: the bare forward pass (bench’s tg) 740–800 tok/s on the dense model. Session, per answer: dense 279 / 313 / 325 / 348 → 519 / 551 / 562 / 609 tok/s; without speculation 387–456 → 572–642 (sampling alone); greedy with speculation unchanged (460–627 → 501–611). MoE 89 / 107 / 107 / 137 → 125 / 140 / 139 / 135 (forward pass 163–169, without speculation 127–153 → 146–154). inga serve: 280–430 → 520–630 tok/s. Per-token streaming (SSE) costs about 0.05 ms. Cold start: first prompt 3.8 s against 2.6–3.0 s warm → 2.6–2.7 s; the load 0.5 s either way (starting the reads during the load slowed it to 1.8 s: the load’s own reads waited behind them).
  • Verdict: adopted
  • Why: on the CPU the sampler’s 1 ms is as much as a decode step of a small model; on a GPU decode step of 50 ms it is 2 %. Speculation’s checks cost 3–4 plain steps here (the 262,144-wide output layer for 9 rows on the CPU, the experts of 9 tokens); a measure of 16 checks that accept nothing cost the first answers 30 %. How much of the 2x on the reporter’s GPU each part explains is to measure there: bench neither samples nor drafts, so inga serve with and without run.speculative=false on the same chat tells the share of the drafts.
  • Could work when: always; the early end of a measure matters most where a check is dear (mixtures with CPU experts, GPU batched passes).

A 4-bit KV cache with a Hadamard rotation

Section titled “A 4-bit KV cache with a Hadamard rotation”

  • Source: the feature survey of 2026-10-13, rank 3 (llama.cpp’s PR 21038; QuaRot, ik_llama.cpp) (spec).

  • Date: 2026-10-13 · Inga version: 0.26.5+ (branch feat/kv-q4-hadamard)

  • Idea: --cache-type q4_0|q5_0|q4_k, each head’s keys and values rotated by a Walsh-Hadamard transform before they are quantized, so an outlier channel no longer sets the scale of its block; the flash attention rotates the queries once and the output back once, instead of every key and value it reads.

  • Measured on: a 4-core AVX-512 cloud VM shared with about twenty other builds (load average 5–25 while measuring: the speeds are noisy, the instruction counts are not); SmolLM2-135M-shaped synthetic Q8_0 (smol-q8_0.gguf: Llama, 30 layers, 9 heads / 3 KV heads of 64, random weights); no real model was available.

  • How:

    1.   • Date: 2026-10-09 · Inga version: 0.22.1-dev
  • Idea: sample on the GPU; submit step n+1 with the sampled token copied on the device, before the CPU reads it back, so the GPU never waits for the host.
  • Built (CUDA, first half): kernels/sampling.cu draws on the GPU what Sampler::sample_at draws on the CPU ((b)): sample_top_k_slices keeps the k best logits (by total_cmp, then lower id) of each slice of 4096 tokens — a thread keeps its own best and only the thread whose best was taken scans again — and sample_draw keeps the k best of those, then thread 0 computes the softmax, min-p, top-p and the Gumbel-max draw with Philox4x32-10. The two passes are checked step by step against the CPU’s sampler here (crates/inga-cuda/src/kernels.rs, 6 vocabularies up to 20 000 tokens with ties, NaN, infinities and signed zeros), and the whole path (GpuHead::sample, Model::forward_sampled, Session) on HostOps (crates/inga-gpu/tests/host.rs); the kernels themselves only on the GPU runner (crates/inga-cuda/tests/sampling.rs).   • Source: uzu (automatic hazard tracking).
  • Idea: track the buffer ranges each dispatch reads and writes, and put a barrier only where a read meets an earlier write, instead of after every dispatch.
  • Built (0.31.0, spec 2026-10-14-vulkan-barriers-design.md): whole buffers by handle, the written bindings from the SPIR-V (crates/inga-vulkan/src/hazard.rs, pipeline.rs), on by default; --vk-barriers all / --ab debug.vk_barriers=all go back.
  • Result (lavapipe, indicative only): a synthetic 28-layer Qwen3-shaped Q8_0 model (barriers_speed): a decode step 758 commands, 760 barriers before, 675 after (-11 %); a prompt chunk of 128 tokens 762 barriers before, 676 after. The speed did not move beyond lavapipe’s noise (decode 2.9-4.4 tokens/s on both sides across two ABAB rounds, the prompt 13.8-14.8). On the 3-layer test models a decode step drops 9 % (Llama Q4_K), 12 % (Qwen3 Q8_0) and 23 % (Gemma 3 F16): the quantized products each quantize their input into one shared buffer, which orders them; the F16 ones read it as it is, so Q, K and V, gate and up, overlap.
  • Verdict: pending the P1000 and RX 9060 XT measures (inga bench -p 512 -n 128 -r 3 --ab debug.vk_barriers=all); on lavapipe the bits are the same and the synchronization validation reports no hazard. Part 2 (spec §8) quantizes a norm’s output once for the products that read it (Q, K, V; gate, up; a shared expert’s; one token’s routed experts’ gate and up): the 28-layer model’s decode step drops to 112 quantizations (196 before), 535 barriers (675) and 674 commands (758), the same bits (norm_outputs_are_quantized_once, shared_input_speed); lavapipe’s speed stays within its noise. Real GPUs are still to be measured.
  • Could work when: a decode step records many small dispatches in one command buffer (Vulkan V3), on GPUs where barriers stall the queue.
