A code execution sandbox: runcode on WebAssembly

Status: proposed for 0.33.0 (decided 2026-10-14). First proposal (agents); asked by the maintainer on 2026-10-14, after docs/comparison.md (Part 2, §4) listed the code sandbox as “not planned: no external programs”. Nothing built. The plugins spec (2026-10-14-plugins-design.md) runs on the same runtime (§12).

0. Decisions and open questions (2026-10-14)

Section titled “0. Decisions and open questions (2026-10-14)”

The maintainer, 2026-10-14: every question about the sandbox’s distribution is postponed (1, 2, 4, 5, 6: what ships in the executable, how the Python runtime is built and what it holds, and the rules it would bend). Question 3 is decided by the spec’s proposal.

  1. Python on first use or inside the executable? Proposed: JavaScript (QuickJS, about 1.5 MB) inside, Python (about 30 MB) downloaded once, on the user’s consent, pinned by checksum (§4.3). Status: open — postponed by the maintainer on 2026-10-14.
  2. Who builds python.wasm? Proposed: Inga’s own CI, in a small repository of its own, reproducible from CPython’s tag and wasi-sdk (§4.3); a third-party build is faster to start with and harder to trust. Status: open — postponed by the maintainer on 2026-10-14.
  3. Approval of the model’s runs: decided 2026-10-14 — ask before each run (as workspace writes); --sandbox-approve scratch lets scratch-only runs go without asking.
  4. Charts in part 1: wait for part 2’s real matplotlib, or ship a small pyplot-compatible subset written in Python that draws SVG (§7)? Status: open — postponed by the maintainer on 2026-10-14.
  5. Binary size: wasmtime adds about 13.5 MB to a stripped executable (measured, §10). Acceptable in every build, or a Cargo feature left out of some builds (mobile, the Docker image)? Status: open — postponed by the maintainer on 2026-10-14.
  6. The rules (AGENTS.md): this spec reads “no external programs” as “no program of the operating system”: WebAssembly run inside Inga’s process is not one. And wasmtime 49 compiles one small C file of its own (helpers.c, 50 lines, §2.1): a second exception to “pure Rust” after ring. Agreed? Status: open — postponed by the maintainer on 2026-10-14.

1. Why

Section titled “1. Why”

Open WebUI runs code (a Python interpreter and terminals), Unsloth Studio runs sandboxed code, LibreChat and Lobe Chat run code for their agents. A model that can compute stops guessing arithmetic, dates and statistics, reads a CSV of the workspace, and draws a chart. Inga’s agent tools today read and write files (the workspace, 0.30.0), fetch pages, search, remember, ask the user, call MCP servers and load skills; none of them computes. The one place that runs code, skill scripts (--allow-skill-scripts, 0.27.0), starts a host interpreter with the user’s rights: fine for a reviewed skill, wrong for code a model just wrote, perhaps steered by a page it fetched.

The constraint: one file, nothing to install, no external programs. The code runs inside Inga’s own process, in WebAssembly, with no access to anything it is not given.

2. The options

Section titled “2. The options”
Embedded WASM runtime, WASI CPython / QuickJS Pyodide in the browser A host Python
Where it runs the server (every client: web UI, APIs, inga run, schedules) the web UI’s tab only the server
Nothing to install yes (Python downloaded once by Inga) yes (Pyodide downloaded by the browser) no: Python must be there, in the right version
Isolation WASM: no files, no network, no system calls unless given the browser’s WASM and worker sandbox none of its own; the OS would have to provide it (containers, seccomp, AppContainer) per platform
Limits (time, memory, output) exact: epochs or fuel, a memory cap, capped pipes a worker can be killed; memory not capped OS-specific
Packages the standard library; numpy and matplotlib built for WASI in part 2 (§7) numpy, pandas, matplotlib, scipy ready anything installed, and pip
Speed close to native with a JIT (Cranelift): about 1.5–2× slower than native CPython ❓ about 1.5–3× slower ❓ native
Offline yes, once installed only if Inga serves Pyodide (about 25 MB plus packages) yes
Model’s tool (run_code) yes, in the server’s tool loop only through the open tab (the server waits for the browser) yes
Cost to Inga the runtime in the executable (§10) none in the executable, a second Python world in the web UI none, and no guarantee
Fits “no external programs” yes yes no
  • A host Python is rejected: it breaks the principle, its version and packages differ on every machine, and isolating it is a different project on each OS. Skill scripts already cover “run the user’s own interpreter, approved”.
  • Pyodide is the best Python for charts, but it lives in one browser tab: the APIs, inga run, scheduled tasks and other clients would have no sandbox, the server’s tool loop would depend on a tab staying open, and serving it offline means 25 MB or more of files kept by Inga. Kept as a possible later addition for the web UI’s Run button only (not planned).
  • An embedded runtime is recommended: one engine for every client, exact limits, WASI capabilities as the whole permission model, and the same engine for plugins.

2.1 wasmtime or wasmi

Section titled “2.1 wasmtime or wasmi”
wasmtime (Bytecode Alliance) wasmi
Execution Cranelift JIT; Pulley interpreter where a JIT is not allowed (iOS) interpreter
CPython speed close to native about 5–20× slower: seconds to start CPython ❓
Limits fuel and epoch interruption; ResourceLimiter for memory fuel; memory limits
WASI preview 1 and 2 (wasmtime-wasi) preview 1 (wasmi_wasi)
Component model (WIT) yes no
Security fuzzed continuously, a security process and advisories, used by Fastly, Shopify, Microsoft smaller user base
Size (measured, §10) +13.5 MB +2.2 MB
Licence Apache-2.0 WITH LLVM-exception MIT OR Apache-2.0

wasmtime with Cranelift. CPython in an interpreter is too slow to start for a chat, and plugins need the component model (plugins spec §4). The Pulley interpreter, built into wasmtime, is the path for the mobile builds (2026-10-09-mobile-builds-design.md), where iOS forbids a JIT.

C in wasmtime (checked on 49.0.2, 2026-10-14): its build script compiles src/runtime/vm/helpers.c (50 lines: the debug built-ins’ entry point and a check for libunwind) with cc on every supported OS, and its cache feature pulls zstd-sys (the zstd C library). AGENTS.md asks for pure Rust crates (only ring excepted): the first is a small exception for the maintainer to approve (open question 6; the build already needs a C compiler for ring); the second is avoided by leaving the cache feature out and keeping compiled modules with Inga’s own code (§4.2).

3. What runs

Section titled “3. What runs”
  • JavaScript: QuickJS (quickjs-ng, MIT) built for wasm32-wasip1, about 1.5 MB, inside the executable (gzipped, as KaTeX is): works offline from the first run. Plain ECMAScript with a console; no Node APIs, no fetch, no require; files through a small std/os module QuickJS has, confined like Python’s.
  • Python: CPython 3.14 built for wasm32-wasip1 (tier 2 in CPython), its standard library in a zip (zipimport), about 30 MB in all, downloaded on first use (§4.3). No pip from the network (no network); pure-Python wheels the user puts in the scratch folder or the workspace can be imported from there.
  • Each run is a fresh instance: nothing in memory survives between runs; files in the chat’s scratch folder do (§5). A stateful session, as Jupyter’s, is part 2’s question (§13).

4. The runtime

Section titled “4. The runtime”

A new crate, crates/inga-sandbox: the engine, the limits, the file system and the languages. inga-server and the CLI call it; nothing else depends on wasmtime.

4.1 Limits

Section titled “4.1 Limits”
Limit Default How Setting
Time 30 s per run epoch interruption: a ticker thread increments the engine’s epoch every 10 ms, each store’s deadline is the run’s time; cheaper than fuel (a few % against 10–30 %) --sandbox-time
Memory 512 MiB StoreLimits: linear memory, tables, one instance; a memory.grow past the cap fails (Python raises MemoryError) --sandbox-memory
Output 1 MiB captured per stream, 16 KiB of stdout and 8 KiB of stderr to the model capped pipes (MemoryOutputPipe); past the cap the run is stopped and marked output --sandbox-output
Disk 64 MiB per scratch folder the ticker thread sums the folder every 100 ms and stops the run past it; checked again at the end --sandbox-disk
Runs at once 2 a semaphore; others wait in the request’s queue (admission control applies) --sandbox-jobs

Fuel is kept for the tests (deterministic counts) and for plugins’ small calls (plugins spec §6). A run stopped by a limit says which, with the number, to the model and the user (“stopped after 30 s: the time limit of the sandbox, --sandbox-time”).

4.2 Compiled modules

Section titled “4.2 Compiled modules”

Cranelift compiles python.wasm in several seconds. The compiled module is kept in $INGA_HOME/sandbox/cache/ (Module::serialize, read back with deserialize_file; keyed by the module’s SHA-256, wasmtime’s version and the CPU’s features; not wasmtime’s cache feature, which links zstd’s C code), so later runs start in about 100–300 ms ❓ (measured in S1). The cache is listed by inga data and cleared with it.

4.3 Getting Python

Section titled “4.3 Getting Python”
  • The first run_code in Python with no runtime installed tells the model and the user “Python is not installed in the sandbox (about 30 MB): install it from the Server tab or with inga sandbox install python”. The web UI shows Install in place; the CLI asks. Never downloaded without the user’s consent; refused with --offline (then the folder can be copied from another machine: inga sandbox install python --from FILE).
  • The archive: python-3.14.x-wasi-inga-N.zip (Inga reads zips already, for skills) from a release of a repository of Inga’s (open question 2), built by its CI from CPython’s tag with wasi-sdk, holding python.wasm, the standard library zip, the licences and a BUILD.txt (the sources’ commits). Its URL and SHA-256 are compiled into Inga: another checksum is refused. Inga N.M takes one runtime version; a new Inga may name a new one, and the old is removed after the new one is installed.
  • Kept in $INGA_HOME/sandbox/python/<version>/; inga sandbox status and the Server tab show what is installed, its size and its source.
  • Left out of the build: readline and anything else under the GPL, ssl (no network), tkinter, ctypes (no dynamic loading in WASI).

5. Files

Section titled “5. Files”
Inside the sandbox On the disk Access
/scratch (the working directory) $INGA_HOME/sandbox/chats/<chat>/ read and write, the disk limit
/workspace the server’s workspace (--workspace, 0.30.0) read-only, only when the request has inga_workspace: true
/usr/lib/python3.14 the runtime’s folder read-only
  • Nothing else exists: no home folder, no /tmp outside /scratch, no environment variables but HOME=/scratch, PYTHONHASHSEED, LANG=C.UTF-8, TZ (the server’s, read by tz.rs), MPLBACKEND=Agg in part 2.
  • WASI preopens are capabilities: a path outside them cannot even be named, and .. out of a preopen is refused by wasmtime-wasi (cap-std). Symbolic links in the workspace that point out are refused as the workspace tools refuse them.
  • The chat’s folder: the web UI sends its chat id (inga_code: {"chat": "ID"}, [A-Za-z0-9_-]{1,64}); another client may send any id it keeps, or none (then a temporary folder, removed after the answer). Folders not used for 30 days are removed; inga data list sandbox lists them, inga data rm removes one; deleting a chat in the web UI removes its folder.
  • Into the workspace: the code cannot write it (read-only). A file the run made is copied in only through write_file (approved, as in 0.30.0) or the web UI’s Save to workspace on the file (the same approval). Part 2 mounts the workspace writable over an overlay, each changed file approved after the run (§13).

6. The model’s tool

Section titled “6. The model’s tool”

  • Offered in the server’s tool loop (websearch::generate, beside web search, fetch_url, the workspace, memory, skills, MCP and ask_user) when the request asks with "inga_code": true (or {"chat": "ID"}), the server has the sandbox, and the model takes tools. python is in the enum only when Python is installed. A client that defines its own run_code runs it itself.

  • The result given to the model, as text:

    with stderr when not empty, “(cut: 120 KB more)” when cut, and the limit that stopped the run. At most 4 runs per round, 20 per answer.

  • Images to the model: a model with vision gets the images of the run as image parts of the tool’s result (part 2: the tool-result images every API needs).

  • The stream: inga_tool deltas as the other tools’ (name, language, the code’s start, the result’s start), and a new inga_code delta with the whole run: code, stdout, stderr, files with their URLs (§8), the limit hit.

6.1 Approval

Section titled “6.1 Approval”

Each run the model asks for goes through the approvals’ stream (inga_approval, skills::Approvals), kind: "code_run", with the language, the code, the mounts and the limits: Run, Don’t run, Always run in this chat (scratch-only runs; a run that mounts the workspace asks again). Five minutes without an answer, or a refusal, is told to the model (“do not try again”). The setting --sandbox-approve ask|scratch (decision 3): scratch runs scratch-only code without asking, the workspace still asks.

  • Scheduled tasks have no one to approve: a task may use run_code (--code, the Schedules page’s Code box) only with --sandbox-approve scratch and no workspace.
  • API clients see the approval as skill scripts’ and workspace writes’ are (GET /api/inga/approvals, POST /api/inga/approvals/{id}); --sandbox-approve scratch serves clients that cannot answer.

7. Charts and images

Section titled “7. Charts and images”
  • Any file the run writes in /scratch comes back: images (png, jpg, gif, webp, svg) are shown in the chat, other files are links (download, Save to workspace).
  • Part 2, matplotlib: numpy and matplotlib (Agg backend: freetype, libpng, kiwisolver, contourpy, Pillow) built for WASI and statically linked into a second python.wasm (WASI has no dynamic loading), offered as the “scientific” runtime (about 60 MB ❓, inga sandbox install python-sci). A sitecustomize.py makes plt.show() save each open figure to /scratch/figure-N.png, so the code models usually write draws in the chat as it does in a notebook. pandas follows if its build works (its C extensions, open). These builds exist in other projects (componentize-py’s WASI wheels for numpy ❓); matplotlib’s is the uncertain one, to be tried before part 2 is promised.
  • Part 1 without matplotlib (open question 4): either the models are told in the tool’s description “no matplotlib: write SVG or PNG files” (stdlib only: SVG is text, PNG through zlib), or Inga ships a small module, MIT, in the runtime, that covers plot, bar, scatter, hist, title, labels, legend and savefig and draws SVG, importable as matplotlib.pyplot. The second helps small models, which write matplotlib by reflex; it is also a subset that will surprise them.
  • SVG files are shown in an <img> (scripts in an image do not run) and served with Content-Security-Policy: sandbox.

Web UI

12. Security

Section titled “12. Security”

What is protected: the user’s files outside the mounts, the network (the LAN and the cloud metadata address above all), the server’s secrets (API keys, the encrypted API-node keys, $INGA_HOME), other chats’ scratch folders, and the machine’s CPU, memory and disk.

The attacker: the code is written by a model, and a model can be steered by anything in its context (a fetched page, a document, a skill, an MCP result, another user’s shared chat). Treat every run as hostile code.

Why WASM isolation is enough here

  • WASM code reaches the outside only through the functions the host gives it. Inga gives WASI preview 1 with: the preopened folders of §5, clocks, random numbers, stdin, stdout, stderr, arguments and the variables listed. No sockets (preview 1 has none; the p2 socket interfaces are not linked), no processes, no signals, no dlopen.
  • Memory is bounded and checked: a WASM module cannot read the host’s memory; wasmtime reserves guard pages and checks every access.
  • Limits stop a loop, an allocation storm, an output flood and a disk filler (§4.1).
  • One fresh instance per run: no state shared between chats or users; each chat’s folder is its own preopen.

What it does not cover, and what is done about it

  • A bug in wasmtime or Cranelift (a miscompilation that escapes the sandbox has happened: CVE-2023-26489, x86-64, 2023). Mitigations: wasmtime kept current (Renovate, its security advisories followed: a patched wasmtime is a patch release of Inga), only the features needed enabled (no threads, no SIMD beyond what CPython needs ❓, no GC proposals). Part 2, defence in depth: runs moved to a child process of Inga itself (inga sandbox-worker, the same executable: no external program) with the OS’s own restrictions (seccomp and Landlock on Linux, a restricted token and a job object on Windows, sandbox_init on macOS), so an escape from WASM lands in a process with no files and no network.
  • Side channels (Spectre) between runs: a concern for a server shared by users (Users U1–U3); wasmtime’s mitigations (bounds-check spectre guards) stay on.
  • The output reaches the model, which may be steered by it: the same risk as a fetched page, said in the tool’s description; the user sees every run.
  • Files the run writes are shown and served with the types above; HTML files are offered as downloads, never rendered on Inga’s origin.

So: stronger than skill scripts (a host program with the user’s rights) and than MCP programs; enough for a local, single-user server with approval on; with users and --sandbox-approve scratch, part 2’s worker process is recommended before it is the default.

13. Phases

Section titled “13. Phases”

Part 1 (0.33.0)

  • S1, the runtime: crates/inga-sandbox (wasmtime, epoch ticker, StoreLimits, capped pipes, preopens, the disk watcher, the compiled-module cache), QuickJS inside, inga sandbox run and status. Measure: the binary’s growth, a cold and a warm CPython start, a loop’s speed against native. Gate: ≤ 14 MB, a warm start ≤ 0.5 s.

Part 2 (later)

  • numpy and matplotlib (python-sci), plt.show() to images, images given to vision models.
  • The workspace mounted writable over an overlay, each changed file approved after the run (a diff, as write_file’s preview).
  • The network, off by default, per run: an allow-list of hosts through a host function that applies fetch_url’s policy (public addresses only, size and time caps), e.g. for urllib through a small shim; never raw sockets.
  • Skill scripts in the sandbox: a skill’s .py and .js scripts run on this runtime instead of the host (no --allow-skill-scripts needed for them; scripts in other languages keep the host path).
  • The worker process (§12); stateful sessions (one instance kept per chat for a few minutes, as a notebook); more languages that build for WASI (Lua, Ruby ❓).
