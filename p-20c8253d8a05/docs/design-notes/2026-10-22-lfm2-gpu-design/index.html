LFM2 on the GPU: the short convolutions

Status: built on feat/lfm2-gpu (2026-10-21; see As built), checked against the CPU on lavapipe and on by default on Vulkan; on by default on CUDA from compute capability 8.0 since the A100’s run of 2026-10-22, off below it and on HIP (debug.cuda_short_conv) until the GPU suites and the measures on those cards pass. Decided by the maintainer on 2026-10-21 for issue #802 (Dario’s LFM2.5-24B-A2B on a Radeon RX 9060 XT, about 20 tokens/s with Inga 0.32.0, only the output layer on the card), for 0.35.0. This is part 2’s LFM2 half of 2026-10-14-hybrid-prompts-on-gpu-design.md (§4 there gives it a paragraph; this spec designs it). The chunked Mamba-2 scan, the other half of part 2, stays in the backlog. Code: crates/inga-model/src/model/shortconv.rs (plain_shortconv), crates/inga-model/src/model.rs (plain_attention), crates/inga-gpu/src/ops.rs (GpuOps::short_conv), crates/inga-gpu/src/{layers,host}.rs, crates/inga-vulkan/shaders/short_conv.comp, crates/inga-cuda/kernels/shortconv.cu (also HIP’s bundle), src/commands/placement.rs.

1. Today (main, 2026-10-21)

Section titled “1. Today (main, 2026-10-21)”

An LFM2 layer is either grouped-query attention (with per-head Q/K norms and RoPE) or a gated short convolution (shortconv::forward):

The state of a convolution layer is the last l_cache - 1 = 2 values of b * x per channel ([d, 2], oldest first: the layout of DeltaNet’s conv_step state). The feed-forward networks are dense SwiGLU (LFM2), or routed experts after the leading dense layers (LFM2-MoE: sigmoid routing with a selection bias, no shared expert).

Model::plain_attention refuses every layer of a model that has one convolution layer (“the GPU does not run short convolution (LFM2) layers yet”), so the planner puts only the output layer on the GPU.

2. Design

Section titled “2. Design”
  1. One fused operation, GpuOps::short_conv(bcx, rows, w, l_cache, past, out): out[t, ch] = c[t, ch] * Σ_i w[ch, i] · v_i, v the past values then b * x of the rows, the taps summed in order in f32 as the CPU’s conv_seq, and the last l_cache - 1 values of b * x left in past. One thread per channel, the tokens in order (a prompt chunk is 16 to 4096 tokens of a few multiply-adds per channel: the two products around it dominate). No intermediate buffer: b * x is recomputed from bcx for each tap. The same operation for one token and for a prompt’s chunks. Vulkan: short_conv.comp; CUDA: short_conv_f32 in kernels/delta.cu (loaded with the DeltaNet module, optional as the chunked rule’s kernels: a PTX or HIP bundle without it keeps the convolutions on the CPU); HIP: the same source in delta.hipfb.gz; HostOps: the CPU’s arithmetic. The default (Metal, WebGPU) returns Error::Unsupported.
  2. Model::plain_shortconv(l) -> PlainConv: the block’s norm, in_proj, the taps ([d, l_cache], as f32), out_proj and l_cache; refused with LoRA adapters, post-norms or scaled residuals (none in LFM2’s files). plain_attention refuses the convolution layers themselves, no longer the whole model.
  3. Mix::Conv in GpuAttentionStages, as DeltaNet’s block: its state a Cache::State (the past inputs; no matrices) with its checkpoint, read back, copied and loaded as the CPU’s (KvLayer::recurrent, the same values), so the prefix cache, --kv-disk and rollbacks work as for Qwen3.5. Decode steps are recorded as graphs as before; batched decode steps of several sessions wait, as for DeltaNet.
  4. The planner: LFM2 becomes attention_only (the mixing blocks placed one by one, then the feed-forward networks beside them, then a mixture’s routed experts), and the dense LFM2 takes the hybrid dense rule (hybrid_layers: the first layers whole on the CPU when that makes a step faster). A convolution block counts like an attention block: its weights and its state for each session. The gpu: line says “short convolutions of layers …, attention of layers …”. A device without the kernel (Metal, WebGPU, an old module) keeps the convolution layers on the CPU, their attention layers still on the GPU (refused, with the reason).
  5. No new flag.

3. Tests

Section titled “3. Tests”
  • Vulkan on lavapipe, CUDA and HIP in the GPU suites (#[ignore], INGA_VULKAN=1, INGA_CUDA=1 / INGA_HIP=1): short_conv against HostOps at LFM2.5’s widths (2048 channels; 1, 16, 31, 100 and 517 rows on one carried state); synthetic LFM2 and LFM2-MoE models whose layers are all on the device (F32 and Q8_0) against the CPU, a prompt in chunks, single tokens, a rollback to the checkpoint and to the start (1e-3 of the largest logit in F32, as the hybrid tests); prompts of 1 to 100 tokens with and without the layers in one call; the cache read back and the prefix cache’s copy (inga_gpu::testing).
  • crates/inga-gpu/tests/host.rs: the same models on HostOps give the CPU’s greedy tokens.
  • src/commands/placement.rs: an LFM2 and an LFM2-MoE model put their layers on the GPU; a device without the kernel keeps the convolutions on the CPU.

4. Measures (left to the cards)

Section titled “4. Measures (left to the cards)”

On #802’s RX 9060 XT (Dario) and the maintainer’s A100 (Colab): inga bench -p 512 -n 128 on LFM2.5-24B-A2B and LFM2-1.2B, before and after, against llama.cpp on the same card. No CUDA or AMD card in the development container.

As built

Section titled “As built”

Built on 2026-10-21 (branch feat/lfm2-gpu). Where the code differs from the design above, the code is described here.

The operation runs in two passes, not one thread per channel. A thread per channel walking the tokens gives a prompt chunk of 4096 tokens 2048 threads of 4096 dependent steps each. The output of token t needs only the inputs t - 2 .. t (and the state for the first two), so the outputs go one thread per token and channel, reading past only; a second pass (one thread per channel) then leaves the last l_cache - 1 values of b * x in past. Vulkan: one shader, short_conv.comp, dispatched twice with a phase push constant (the hazard tracker puts the barrier between them, the shader writing past in its second phase). CUDA and HIP: short_conv_f32 and short_conv_state_f32, two launches (recorded in the decode step’s graph as the other launches), in a module of their own, kernels/shortconv.cu (not delta.cu, as §2 said: delta.ptx and delta.hipfb.gz, which run the DeltaNet layers on CUDA and HIP today, stay byte for byte as they were). The module is optional, as the DeltaNet and Mamba2 ones: a driver that refuses it keeps the convolutions on the CPU.

Off on CUDA and HIP by default. Nothing here could run the CUDA and HIP kernels, so until they pass the GPU suites and are measured on real cards, debug.cuda_short_conv (default false, CUDA and HIP alike) keeps LFM2’s convolution layers on the CPU there: Gpu::short_conv refuses the operation, check_short_conv fails, and the planner keeps those layers (with their networks and experts) on the CPU, LFM2’s attention layers on the GPU, the gpu: line saying why. debug.cuda_short_conv = true (inga.toml, or --set debug.cuda_short_conv=true) runs them on the GPU. Vulkan runs them by default (checked on lavapipe). The CUDA and HIP tests turn the setting on; tests/short_conv_off.rs checks that it is off otherwise.

The state is a Cache::State with no matrices (mats_len 0): the copies, writes and reads of the matrices are skipped when there are none (no zero-length device copy reaches a driver). The activations (b, c, x and the gated output, 4 d floats a row) are allocated only in the sessions of a model with convolution layers, so the other models’ sessions make no more allocations than before (the hardware profiles count them).

The planner: inga_gpu::attention_only includes LFM2, so its mixing blocks are placed one by one (layer_bytes: a convolution block is its two projections, its taps and norm, and its state with a checkpoint, 4 · 2 · 2 d bytes, whatever the context); the dense LFM2 takes the hybrid dense rule (hybrid_layers). GpuPlan::conv lists the convolution layers placed, for the gpu: line (“short convolutions of layers 0,2,…, attention of layers 1,3,…”) and the placement table (“(6 full, 10 short convolutions)”, from LayerParts::conv). Before the upload, inga_gpu::check_short_conv runs the operation on one channel of zeros: a device that refuses it (Metal, WebGPU, an old module) keeps the convolution layers, their networks and their routed experts on the CPU (conv_on_cpu: refused and cpu_why say so), its attention layers on the GPU. A layer split across several GPUs refuses LFM2 as it refuses the other hybrid models (split_refused: “a hybrid model (LFM2’s short convolutions)”).

The kernels’ builds. shortconv.ptx was built as part 1 built delta.ptx: clang 18 (-x cuda --cuda-device-only --cuda-gpu-arch=sm_61 -S -O3, CUDA 12.4’s headers from tools/setup-nvcc.sh’s conda packages, an empty curand_mtgp32_kernel.h for clang’s wrapper, no libdevice: the kernels call no math function), with the first line tools/build-ptx.sh --check reads; ptxas 12.4 builds it for sm_61, sm_80 and sm_89 without spills (about 30 registers). tools/build-ptx.sh with nvcc 12.4 on the runner rebuilds it as the other modules. shortconv.hipfb.gz was built by tools/build-hsaco.sh with clang 18.1.3: the script’s nine other bundles came out byte for byte as committed, so the toolchain is the one CI checks.
