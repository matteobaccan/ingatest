One server for every model: chat, images, voice and video without a restart

Asked by the maintainer on 2026-10-28: “se passo da un modello chat a uno immagine a uno voce o a uno video non voglio riavviare” (switching from a chat model to an image, voice or video model must not need a restart). Placed in 0.40.0 on 2026-10-28, when the maintainer asked for the new items by release; moved to 0.41.0 on 2026-10-28, when the maintainer swapped 0.40.0 and 0.41.0 (docs/todo/0.41.0.md); planned for 0.43.0 by the maintainer on 2026-10-30 (docs/todo/backlog.md, “Many users, faster”), 0.44.0 since 2026-10-31; M1 (images in the chat server) shipped in 0.40.0.

Status: M1 (images in the chat server) built on synthetic models, branch feat/one-server-images (“As built” at the end); M2 (video) built on branch exp/0.43 for the web UI’s Videos page (“As built (M2)” at the end), save inga serve VIDEO, which still serves the model alone; M3–M4 open. The open questions took the spec’s defaults (below).

Why

Section titled “Why”

Today inga serve is one of four servers, chosen at start by the model given (src/commands/serve.rs, serve):

The model given What runs What it answers
a language model, or none the chat server (inga_server::serve): a pool of models loaded and unloaded from the web UI, the least recently used unloaded for room (router.rs, --idle-unload, keep_alive, --vram-evict) chat, completions, embeddings, rerank; speech too, with --whisper / --tts or the models chosen in the web UI, loaded at first use (voice.rs)
an image model (is_image_model_at, --diffusion-model) serve_images: that model alone /v1/images/generations, /v1/images/edits, the web UI’s image mode
a video model (is_video_model_at) serve_videos: that model alone /v1/videos
a speech-to-text model (is_speech_model) serve_speech: that model alone /v1/audio/transcriptions, /v1/audio/translations

So a user chatting who wants a picture must stop the server and start it again with the image model. The web UI says so on the Images page (“Servi questo modello per disegnare … Fermalo e avvialo con il modello”), and that is what the maintainer does not want. Voice already works without a restart in the chat server (voice.rs: the models chosen in the settings, loaded at the first request); images and video do not.

Goal

Section titled “Goal”

One inga serve, started with any model or none, answers every kind of request. Each kind’s model is loaded when it is chosen or first asked for, without a restart. When memory is short, models no request is using are unloaded to make room. The web UI never asks for a restart to change kind.

Out of scope: the mesh and the API nodes, which keep serving language models only; image and video generation on the GPU, which is its own item (#919, P1); two drawings at the same time.

Design

Section titled “Design”

§1 One slot for each kind beside the language models

Section titled “§1 One slot for each kind beside the language models”

The chat server keeps the language models’ pool as it is. Beside it, one slot for each of the other kinds holds at most one model:

Slot Kind Loaded from Routes
image image models: SD 1.x / 2.x / XL, Flux, Qwen-Image, SD 3.5, kits a library entry, a path, hf://, kit:// /v1/images/generations, /v1/images/edits; the web UI’s Images page
video video models: Wan 2.1 the same /v1/videos
transcription, speech, vocoder speech already there (voice.rs) /v1/audio/*

The image and video slots are built like voice.rs’s Voice. A model is chosen through the settings (image_model, video_model in /api/inga/settings) or named by a request (model of /v1/images/generations). It is loaded at the first request that needs it, or ahead of use with POST /api/inga/media/load, and replaced when another is chosen. GET /api/inga/media says which model each slot holds, its state (empty, loading with its progress, ready, failed with the error) and its memory.

ImageServer and VideoServer (images.rs, videos.rs) become the slot’s content instead of a server of their own. Their request handlers keep their code, so answers do not change. serve_images, serve_videos and serve_speech remain as thin starts: the chat server with the model given preloaded in its slot. inga serve IMAGE therefore keeps working and can then load a chat model too.

§2 One memory budget for every kind

Section titled “§2 One memory budget for every kind”

A load of any kind asks the same question first: is there room in RAM, and on the GPU it would use? If there is none, models that no request is using are unloaded, least recently used first, from any kind and any slot. Models kept forever (keep_alive: -1) are never unloaded. The rules are the existing ones extended to the slots:

  • inga_engine::HeavyJobs already queues a load while an image is drawn. A slot’s load goes through it too (HeavyKind::Load).
  • --idle-unload / keep_alive apply to a slot’s model too. Default: unloaded after 5 minutes idle, as the language models.
  • The language model’s prompt caches are kept when it is unloaded for an image model (Router::park, --kv-disk), so the conversation resumes without its prompt read again.
  • What was unloaded and why is said where unloads already say it: stderr, the load’s progress and /health.

On a machine where the chat model and the image model fit together, both stay loaded and switching costs nothing. Where they do not fit, switching costs a load, never a restart.

§3 One drawing at a time

Section titled “§3 One drawing at a time”

A slot’s model serves one request at a time (ImageServer’s busy lock today). Further requests wait in a queue, each told its place on the stream (progress events), with the existing time limit. Chat requests do not wait for a drawing unless memory forces an unload (§2).

§4 The web UI

Section titled “§4 The web UI”
  • Models page: Load works for every kind. An image model loads into the image slot, a chat model into the pool. The card’s line says which slot and memory it takes.
  • Images page: the model picker lists the image models of the library. Choosing one loads it, with the load’s progress on the page. The card “Servi questo modello per disegnare” and its command line go away. The recommended models’ Download button sees downloads in progress (the 2026-10-28 list, item 1).
  • Chat: when the model chosen in a chat is an image model, the chat says so and offers to open the Images page. Its prompt can also be drawn in the chat itself (the “Send to chat” path, the other way round). This was asked on 2026-10-25.
  • Voice and video pages: the same picker and load as Images.
  • The library classifies models by their used field (image, video, speech, chat), not by the diffusion capability. DiffusionGemma, a text model that generates by diffusion, stays a chat model (the 2026-10-28 list, item 1).

§5 The command line

Section titled “§5 The command line”
  • inga serve with no model, with a chat model, or with an image, video or speech model starts the same server, the given model preloaded in its pool or slot.
  • --image MODEL and --video MODEL preload a slot beside a chat model, as --whisper and --tts already do for speech. With --diffusion-model / --vae / --clip-l / --t5xxl, the parts of an image model are given as today.
  • inga serve --like ollama:... stays for language models only, as today.

§6 Errors

Section titled “§6 Errors”
  • A model that cannot be loaded (an unsupported format, such as ComfyUI’s FP8 Flux, issue #930) fails its slot’s load with the reason. The reason is shown on the page that asked for it and in GET /api/inga/media. The chat model is not touched.
  • A request for an image when no image model is chosen gets OpenAI’s error with the hint to choose one (model_not_found), not the advice to restart.
  • A request naming a model of another kind (an image request naming a chat model) gets an error saying which kind the model is.

Steps

Section titled “Steps”

Each step is one PR, measured and landed before the next:

  1. M1, images in the chat server: the image slot (§1), its routes, /api/inga/media, the budget’s unload of an idle language model for it (§2), the Images page without the restart card (§4); inga serve IMAGE starts the chat server (§5).
  2. M2, video: the video slot, the same way.
  3. M3, speech as the main model: inga serve WHISPER starts the chat server with the transcription slot filled, and serve_speech’s own server goes away.
  4. M4, the chat side: an image model chosen in a chat (§4), --image / --video (§5).

Tests

Section titled “Tests”
  • Server tests on the synthetic image model of inga-diffusion’s tests. Load an image model into a server holding a chat model, draw, chat again, all without a restart. Check that GET /api/inga/media shows each state.
  • The budget: with a memory limit that holds one model, loading the image model unloads the idle chat model and says so; a chat request reloads it.
  • Two drawings at once: the second waits and is answered after the first.
  • inga serve IMAGE answers /v1/images/generations as before, with the same bytes for the same seed.
  • Not measured here: load times and memory with real models (SD-Turbo with Qwen3-8B on the maintainer’s PC and on the A100); to do at M1’s PR.

Open questions for the maintainer

Section titled “Open questions for the maintainer”
  • How long a slot’s model stays idle before it is unloaded: the language models’ 5 minutes, or longer, since an image model is slow to load on a CPU?
  • When a chat model and an image model do not fit together, should the chat model be unloaded automatically (§2), or should the web UI ask first?

As built (M1)

Section titled “As built (M1)”
  • The slot is crates/inga-server/src/slots.rs (ImageSlot, after voice.rs): ImageServer is its content; images.rs keeps only the handlers (generations, edits, unchanged in what they answer) and serve_images’ own server is gone. The loader is MediaLoader (ServerCfg::media_loader, built in src/commands/serve.rs): a path, an hf:// reference, kit://NAME (its transformer, then its other files by their option) or the key of the command line’s model and parts. A request’s model loads a model only when it is a reference (hf://, kit://, ms://, an existing path); another name (OpenAI’s dall-e-2) is drawn by the model chosen; a language model’s name gets a 400 saying its kind (§6).
  • Routes: /v1/images/generations and /v1/images/edits on the chat server; GET /api/inga/media (image: model, source, id, state empty / loading / ready / failed, load as /health’s, error, bytes, idle_s, keep_s, unloaded, made_room, about; memory: limit, budget, available, language_bytes); POST /api/inga/media/load {"kind": "image", "model"?}, which answers once the load ends (the page polls GET /api/inga/media for the progress). /v1/models lists the slot’s model while it is loaded ("type": "image", inga.slot, inga.reference, inga.source); /health has image and is ok with only an image model ready.
  • The budget (§2): before an image model loads, need = its files’ bytes (known only when they are on this machine; a model still to download is not budgeted) + a 512 x 512 drawing’s (images::image_bytes, 384 MiB). Room = --mem-limit minus what the language models loaded hold (Router::ram_held: their weights and experts not on a GPU, their KV caches), else the RAM the system reports available. While room < need, Router::unload_idle_for unloads the least recently used language model with no request and not kept forever, as --vram-evict does (the same Router::evict: prompt caches parked, the reason in /health’s evicted, stderr, the load’s queued phase); without --mem-limit it stops when an unload frees no RAM the system counts (weights mapped from their file). Before a language model loads again (its size known from its last load), the router’s hook (Router::set_room) unloads an idle image model when the two do not fit. The slot’s load goes through HeavyJobs as HeavyKind::Load.
  • Idle unload (open question 1, the spec’s default): the slot follows the language models’ rule, the server’s --idle-unload (by default never) and a request’s keep_alive / ttl; Inga’s language models have no 5-minute default of their own (that is Ollama’s keep_alive default), so the slot has none either.
  • No prompt (open question 2, the spec’s default): the idle chat model is unloaded automatically and said; the Images page shows what was unloaded (“To make room, Inga unloaded: …”).
  • The command line (§5): inga serve IMAGE (or --diffusion-model ...) loads the image model before listening, as before, then starts the chat server with it in the slot (ServerCfg::image); its start line names the image model and its routes. Other models may be named beside it; --like works.
  • The web UI (§4, the Images page): the picker lists the slot’s model and this machine’s image models (a kit’s transformer whose files are here as kit://NAME); choosing one loads it, with the load’s line and percent on the canvas; Load for the one chosen last; a failed load shows its reason with Try again; the restart card and ig.serve* are gone. The chat enters its image mode only when the slot’s model came from the command line and no chat model is loaded, and leaves it when one is.
  • Tests: tests/images.rs (a chat server loading an image model, drawing and chatting again, GET /api/inga/media’s empty / failed / ready; the budget with --mem-limit; two drawings at once; inga serve IMAGE’s same bytes as inga image), the web UI’s webui::images (Load, its progress, what was unloaded, a failed load).
  • Not done in M1: the Models page’s Load for image models, the queue’s place told on the stream (§3: drawings already wait one at a time in HeavyJobs), the measures with real models (SD-Turbo with Qwen3-8B, docs/todo/real-world-checks.md).

As built (M2)

Section titled “As built (M2)”
  • The slot is crates/inga-server/src/video_slot.rs (VideoSlot, after the image slot): VideoServer is its content, loaded by MediaLoader::video (a diffusers folder, a path, kit://NAME with its files by role, as the image loader), its size by MediaLoader::video_bytes. The jobs are videos.rs’s Jobs, shared with inga serve VIDEO’s own server: one worker thread of the chat server (video_slot::worker) runs them one at a time, loading the chosen model first when it is not (the job’s stage loading). A request’s model that is a reference chooses it, a language model’s name gets a 400; no model chosen is a 404 model_not_found with the hint.
  • Routes: /v1/videos on the chat server; POST /api/inga/media/load {"kind": "video"} (kept as video_model); GET /api/inga/media’s and /health’s video; /v1/models lists the slot’s model while it is loaded ("type": "video", the defaults of a clip, multiple, frame_step, max_frames, max_side, and sizes: 480p for a transformer 1,536 wide, 480p and 720p for one 5,120 wide, as Wan-AI’s cards say).
  • The budget: before a video model loads, need = its files’ bytes (no clip counted); the room is made as for an image model (slots::make_room, its kind said). A language model loading again unloads the idle video model when the two do not fit, never while a clip is queued or generated; the idle model goes after --idle-unload with no clip queued (no keep_alive for clips).
  • Jobs: a job says its stage (inga.stage: queued, loading, waiting, text, steps, decoding, done, failed), its step (inga.step) and when it started; DELETE of a clip being generated stops it before its next step (inga_diffusion::VideoModel::generate_until) instead of a 409.
  • Left: inga serve VIDEO as a thin start of the chat server (§5), --video MODEL, the memory of a clip counted before it runs (the worker admits it through HeavyJobs with working_set, as before), a clip’s speed recorded per model.
