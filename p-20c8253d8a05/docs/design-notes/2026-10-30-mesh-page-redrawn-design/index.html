The Mesh page redrawn around the model

Status: phases 1, 2 and 4 and most of 3 built for 0.41.0 (feat/mesh-flow, see “As built” at the end); Rebalance now, the measured factor and the animation for the site left. Asked by the maintainer on 2026-10-30 (“occorre migliorare e di parecchio la grafica che presentiamo per mostrare la rete mesh”: the mesh’s pictures must get much better). He reviewed a prototype with simulated data with us the same day and liked it. He asked one thing in particular: how to tell how each node performs. He decided the item for 0.40.0, then moved it to 0.41.0 the same day to make room for the pictures on the GPU (docs/todo/0.41.0.md on docs/plan-040-adoption). This spec takes in what is left of the map’s spec (M3 and M4, see §2.10).

Code:

  • the API: crates/inga-dist/src/mesh.rs (NodeInfo, to_txt / from_announce, Mesh::to_json, Mesh::event), crates/inga-dist/src/stages.rs (MeshStage::forward, MeshStages::plan, recover), crates/inga-dist/src/worker.rs (Worker::forward), crates/inga-dist/src/place.rs (share, Candidate), src/commands/mesh.rs (the satellite’s and the server’s refresh, inga mesh show), crates/inga-server/src/nodes.rs (mesh_json), crates/inga-server/src/lib.rs (the re-plan thread), docs/api/inga.yaml;
  • the page: crates/inga-server/webui/js/mesh.js, two new files js/mesh-flow.js and js/mesh-perf.js, css/models-mesh.css, i18n/mesh.json and the new files’ i18n, html/pages.html (#mesh-view);
  • the pictures: tools/screenshots/shots.cjs (MESH), docs/images/webui-mesh.png, a new docs/images/mesh-flow.svg, site/src/pages/index.astro, README.md.

The starting point is the prototype the maintainer reviewed (mesh-prototype.html, HTML and JavaScript with simulated data, kept outside the repository). Every number in it is made up. This spec keeps its look and says, for each part, where the real number comes from.

1. Why

Section titled “1. Why”

Today’s Mesh page (js/mesh.js, 614 lines) shows the machines but not the model:

  • The map draws the PCs, not the work. It shows boxes around the master (meshMapDraw), links coloured by round trip, a “Who runs what” bar under it (#mesh-models) and the cards under that (#mesh-nodes). Nothing shows a token going through the layers, PC by PC, and back.
  • Nothing says how each PC performs. GET /api/inga/mesh gives each node’s measured speed at start (speed, bytes of weights per second) and a tok_s that is always null (Mesh::to_json). The model gets the plan’s tok_s, an estimate. No measured time per PC, per link or per token reaches the page. The plan is never compared with what the mesh then does: B2 of the mesh bench spec is not built (§2.1).
  • The choices are in a text log. A PC left out, a link that is too slow, layers moved mid-answer: Mesh::event keeps each one as a sentence (64 kept, EVENTS), and the page lists them at the bottom. The map does not show them.
  • The pictures are out of date. docs/images/webui-mesh.png (2026-10-13, commit ee434d8) still says “No encryption”. The screenshot fixture (tools/screenshots/ shots.cjs, MESH) writes “11.8 tokens/s measured” and “a satellite’s GPU does not run mesh layers yet”. The first number was never measured, and the second has not been true since 0.27.0.

What Inga takes from them:

  • each PC’s measured time against the plan’s estimate (GPUStack #1070, exo #11);
  • each link’s bandwidth and its share of a token (exo TODO.md);
  • “slower with more PCs” said in one sentence, with what would fix it (exo #553): §2.5.

None of these tools draws the model itself, layer by layer, across the PCs. The Flow view (§2.3) is the prototype’s own idea. Public pages say what the page does, never how others do it.

2. What it does

Section titled “2. What it does”

2.1 What /api/inga/mesh gives today, and what the page needs

Section titled “2.1 What /api/inga/mesh gives today, and what the page needs”

Today (Mesh::to_json, then nodes::mesh_json, which adds load and the API nodes):

  • for each node: id, name, role, state, os, cpu, isa, threads, ram_total, ram_free, cpu_use (whole machine, %), speed, prefill_speed, devices[], runs[] (layers: [from, to)), the cache fields, the version fields, load (spec L3), and tok_s: null;
  • for each device: device, name, backend, memory, free, speed, used, reason;
  • links[]: a (the master), b, rtt_ms, mbit_s;
  • models[]: id, n_layers, tok_s (the plan’s estimate), split[] (node, from, to), sent[], suggested;
  • alone[], replans[], and events[] (at, text).

Some of it does not mean what the page needs:

  • The links form a star. A token’s hidden state goes from the master to a satellite and back to the master: RemoteStage::forward sends Msg::Forward, then waits for Msg::Hidden. Then it goes to the next satellite. No link joins two satellites, so the page draws none. The master is the one that measures the links: set_link is called from MeshStages::plan with the Hello round trip, and with the push’s mbit_s when parts were sent. They are not measured again while tokens run.
  • A GPU’s free is measured once. It comes from the start (about → placement::mesh_devices). Neither refresh closure in src/commands/mesh.rs reads it again.
  • The hidden state travels as f32 (Msg::Hidden { hidden: Vec<f32> }): 4 bytes × n_embd per token, each way, per satellite, plus the frame and Noise’s tag. The prototype counted f16.

New fields. All of them are null when their source does not say:

Field (new) What it is Where it comes from
nodes[].perf.ms_token its part of a token: the median over the last 20 generated tokens, in ms a satellite: the master times each MeshStage::forward of one token (n == 1) and takes away the compute time the satellite reports (compute_ms). The master: the time from the last stage’s return for token t to the first stage’s call for token t + 1, in the same session. That is its own layers, the output layer and the pick of the next word. It is counted only between consecutive positions (pos0 == len), so a pause between answers is never counted. New: a Timing in stages.rs’ Shared
nodes[].perf.compute_ms a satellite’s own time on its layers for one token, median new: Worker::forward timed with Instant for n == 1, kept by the worker per run, and announced (below)
nodes[].perf.est_ms the plan’s estimate for that part place::share(...).secs for the node’s range, worked out in MeshStages::plan, where share is already called (devices). New: kept in ModelSplit.split
nodes[].perf.ms_layer ms for one layer the page divides ms_token by the node’s layer count. Not a field
nodes[].perf.busy the share of the last 10 s the node spent on mesh layers, % a satellite: new, the worker’s summed Forward time over the wall time, announced. The master: its Timing
nodes[].perf.history the last 40 values of its part of a token, in ms the master’s Timing. For a satellite this is the round trip as the master sees it, so the link is included; the label says so
nodes[].perf.factor measured ÷ estimated, the median over the last 20 answers (B2) B2 is not built. No $INGA_HOME/mesh/measured.json exists, and neither do inga mesh show --measured or inga mesh forget. §2.6 builds the part the page needs
nodes[].devices[].util, temp_c, mem_used, power_w each GPU now NVIDIA: NVML (inga_cuda::gpu_stats: nvmlDeviceGetUtilizationRates, GetTemperature, GetMemoryInfo, GetPowerUsage), on Linux and Windows. AMD on Linux: sysfs (inga_engine::sysfs_gpus). Everything else gets the free memory only. The three are merged by src/commands/system.rs gpu_stats (the System page’s source), which goes through gpu_runtime::Last::probe, so a busy GPU is not asked. Matched to the mesh’s devices by label, as merge does
nodes[].cpu_temp_c the hottest CPU sensor inga_engine os::temps: Linux only (hwmon). Windows and macOS give none
nodes[].devices[].free refreshed the same probe, read again in refresh
models[].split[].gpu_bytes, ram_bytes the model’s part in each node’s GPU and RAM place::Share.gpu and .ram from the plan (new, kept beside est_ms)
links[].ms_token a satellite’s link cost per token, there and back the master’s round trip less the satellite’s compute_ms
links[].bytes_token bytes per token, both ways 2 × n_embd × 4 plus the frame (from ModelCheck.n_embd)
models[].generating tokens are being generated now the router’s activity (in_flight), read in mesh_json
models[].tok_s_now the measured generation speed over the last 10 s the master’s Timing
models[].stand_in the satellite recover would try first if a stage fails, and its free room mesh.satellites() in recover’s order, without the failed and left-out ones (new helper Mesh::stand_in)
events[].kind, events[].node join, leave, back, plan, left_out, moved, replan, master, security, network; the node’s id new: Mesh::event_of(kind, node, text). event stays for the rest as kind: "note"

What a satellite must report, and how. It reports in its announcement (mDNS TXT, signed with the mesh key, every HEARTBEAT of 2 s), not in the worker protocol. New keys, each under 255 bytes:

  • st=MODEL@FROM-TO:COMPUTE_US:N;…: the median compute time per token of each run, and the tokens counted;
  • busy=PCT;
  • gs0=UTIL:TEMP:USED_MIB:FREE_MIB per GPU (the same order as gpu0, …);
  • ct=TEMP.

from_announce reads them, and an older node simply leaves them out. VERSION stays at 9. Peers of another protocol leave each other out (MeshStages::plan skips a node whose same_protocol() is false). Adding the timing to Msg::Hidden would bump VERSION to 10, and every satellite would have to be updated at once until V2 of the versions spec (MIN_VERSION, also planned for 0.41.0) lands. The cost of the announcement is precision: a median every 2 s, not each token. That is enough for a page refreshed every second. The context window’s spec C2 (its §2) wants each answer’s exact split, so it will need the protocol field. It can come with V2.

A satellite on an older Inga shows “—” with “this PC’s Inga does not report it: update it” (the update link of V1).

inga mesh show prints the same figures as a table (--json: the same fields). The terminal and the page say the same things.

2.3 The Flow view (new, js/mesh-flow.js)

Section titled “2.3 The Flow view (new, js/mesh-flow.js)”

  • The model is a ribbon from the prompt to the answer. It runs through the PCs that hold layers, in layer order (models[].split). Each PC’s part is in its colour, with “layers 14–23 · 10/24”. The ends are “prompt” and “next word, on the master”.

  • A light for each token. While generating, a dot runs along the ribbon and each card’s part lights up in turn.   • The empty state (a mesh with no other node): “Add a PC to this mesh”, the steps, and the command with a Copy button (inga satellite --mesh NAME; mesh.none today has it in a sentence). “It appears here within a few seconds. If it does not, this page says why”: the connection errors already say so (inga mesh doctor, the events). “A second PC would let you load a model larger than this one’s N GB” uses this node’s ram_total and devices.

2.5 How each PC performs (new, js/mesh-perf.js)

Section titled “2.5 How each PC performs (new, js/mesh-perf.js)”

This is the part the maintainer asked about.

  • A table, one row per PC:

    • device;

  • A click on a row or a card opens its detail:

    • a larger sparkline;

      • slower than the plan (factor above 1.12): “DESKTOP-1VFB0M9 runs 18 % slower than the plan expected.” The temperature is added when it is reported. “It may be throttling” is said only when the temperature is reported and at or above 80 °C: the reason is not read from the driver (NVML’s throttle reasons are not loaded today, nvml.rs).   • Where a token’s time goes:

    • its legend;

    • otherwise nothing. No sentence is given for a balanced mesh. “A pipeline adds memory, not speed” is said once, in the empty state and in the guide, not on every visit.

2.6 “N layers fewer at the next load”, and Rebalance now

Section titled “2.6 “N layers fewer at the next load”, and Rebalance now”

Today’s re-plan path (spec mesh robust R2, shipped):

  1. Mesh::due_replans marks a model due when satellites that joined after its plan would make it REPLAN_GAIN (1.1×) faster, or would let it fit.
  2. The server’s thread polls it every REPLAN_TICK (2 s), in crates/inga-server/src/lib.rs.
  3. It calls Router::unload_between_requests, which returns Busy while a request holds the model.
  4. It calls router.load again, which runs MeshStages::plan from scratch.
  5. replan_done says how it ended.

Only a join triggers it. Nothing can ask for it.

Asking it today would give the same plan. The plan weighs each node by the speed it announced at start. A node that turns out slower keeps the same layers. So the advice needs a minimal B2 first:

  • The factor (new): measured ÷ estimated per node and model, the median over the last 20 answers, from §2.1’s Timing.
    • It is kept in $INGA_HOME/mesh/measured.json, keyed by the node’s name and the model, as B2 says.
    • MeshStages::plan divides the node’s Candidate.speed (and gpu.speed) by it.
    • The plan’s line says so: “expected 6.1 tok/s (measured on 37 answers; the raw estimate was 4.2)”.
    • The fingerprint rule of B2 (CPU, GPU, RAM changed: the factor is dropped) comes with it.
    • inga mesh show --measured and inga mesh forget are B2’s and are not part of this spec.
  • “N layers fewer at the next load” comes from running place_layers with the factor applied, not from a rule of thumb. Nothing is shown when the result is the same plan.
  • Rebalance now (new: POST /api/inga/mesh/replan {"model": M}, admin like /api/inga/mesh/handover, in docs/api/inga.yaml):
    • it puts a Replan in waiting with the note “asked from the Mesh page”;
    • the existing thread runs it;
    • the button turns into the replan’s state (replans[]).

What Rebalance now costs, said before the button acts:

  • It waits for the requests in flight to end (Busy).
  • The model is unloaded. The open chats’ KV caches on the master and the satellites are dropped, and their next turn reads its prompt again (unless --kv-disk keeps them).
  • The plan runs again:
    • each satellite’s round trip;
    • the parts each satellite lacks, sent (cached by hash, so a node that keeps its range or shrinks gets nothing new);
    • each node loads its layers from its disk cache.
  • The confirmation gives an upper bound of the bytes to send: the layers new to each node, over its last mbit_s. It also says the model is unavailable meanwhile.
  • None of these times has been measured on a LAN (group C), and the page gives no duration.

5. Risks

Section titled “5. Risks”
  • A median every 2 s hides spikes within one answer. The sparkline is the master’s own per-token view, so it shows them for every node, but with the link included.
  • The master’s gap also counts the server’s own work between tokens (streaming, sampling). It is labelled as “its layers, the output layer and the next word”.
  • Refreshing the GPUs’ figures every heartbeat on a satellite calls NVML every 2 s. Last::probe returns the last figures while a GPU is busy, so a load is never slowed. This is not measured on a satellite.
  • The thresholds (20 %, 1.5×, 30 %, 1.12, 80 °C) are chosen, not measured. The first LAN run may move them.
  • Rebalance now drops the open chats’ caches. The confirmation says so.

As built (0.41.0, feat/mesh-flow)

Section titled “As built (0.41.0, feat/mesh-flow)”

Built with the 0.40 batch as base (the new style #1022, the reorganised page #1019: the Inga nodes, the routes, then the API nodes’ boxes, kept in that order and unchanged).

The API (phase 1, inga_dist::timing).

  • Timing (per model, in stages.rs’ Shared, handed to ModelSplit.timing): the master records each MeshStage::forward of one token (n == 1) as the node’s round trip, its own part through Gap (the last stage’s return for token t to the first stage’s call for t + 1, counted only at the next position and for one token; a prompt or a truncation clears it), and each token at the last stage. A step that had to move its layers first is not counted. Medians of the last 20, history of the last 40, the busy share and tok_s_now over 10 s, generating while a token passed in the last 2 s (from the timing, not the router’s in_flight as §2.1 said: the mesh does not see the router).
  • The satellite: Running holds a StageClock; Worker’s Msg::Forward is timed and recorded by the connection’s run. The refresh (src/commands/mesh.rs) announces me.stage_times (st=MODEL@FROM-TO:COMPUTE_US:N;..., last in the TXT strings so a full announcement drops it first; the last 4 ranges are kept, after their session ends too) and me.busy (busy=). VERSION stays 9; an older satellite gives none.
  • nodes[].perf: a satellite’s ms_token is its announced compute_ms (its own part, so that the PCs and the links add up to a token); links[].ms_token is the master’s round trip less it. §2.1’s table read as if the satellite’s ms_token were the round trip less the compute time, which is the link’s figure. The master’s ms_token is its Gap. history is the master’s view (the round trip for a satellite, history_round_trip). factor is null (B2 not built).
  • links[].bytes_token: 2 × n_embd × 4 + 58 (the frames’ headers and Noise’s tags, about). models[].split[] carries gpu_bytes, ram_bytes, est_ms from place::share (PartPlan, ModelSplit.planned); a stage moved by recover has none.
  • models[].stand_in (Mesh::stand_in: the first of satellites() not in the split and not left out; the stage’s failed list is not seen from there).
  • Events: Mesh::event_of(kind, node, text), event is note. Kinds given: join, leave, back (saw, sweep), master, security, network (--peers silent or back, a stage failing), plan, left_out (MeshStages::plan), moved (recover, about the node that failed; its text now names both: “moved to nas (from MINI-PC)”), replan.
  • Not built: the GPUs’ util, temp_c, mem_used, power_w, the refreshed free and cpu_temp_c (the cards show the memory the announcement has); inga mesh show’s table.
  • Tests: timing.rs’ unit tests (median, busy, the gap rule, ranges kept), the TXT round trip with the new keys and an older node giving none, a full announcement (four GPUs, runs, times and links) kept whole in one signed frame, and crates/inga-dist/tests/mesh.rs’ each_node_and_link_is_timed_a_token_and_a_move_is_an_event (a master and two satellites in process: compute times announced, link costs, bytes, a moved event naming the failed node).
