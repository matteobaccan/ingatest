One configuration file: inga.toml

Status: proposed for 0.31.0 (decided 2026-10-14: its break lands at the start of the release); C1 built (feat/config-file-c1), C2 and C3 built (feat/config-file-rest; see “As built” at the end); C4–C6 not built (asked by the maintainer on 2026-10-14; revised the same day after his decision: one single file, and the INGA_* settings variables removed; revised again on 2026-10-15: removed outright, with no transition, decision 3). Code it touches: src/cli.rs (the hand-written parser, USAGE, every_user_facing_variable_is_in_the_help), src/completions.rs, src/main.rs, src/commands/mod.rs (mem_limit, cpu_cfg), src/commands/bench.rs (--ab), src/commands/service/, crates/inga-core/src/env.rs (EnvCell), crates/inga-hub/src/local.rs (inga_home), crates/inga-hub/src/download_dir.rs, crates/inga-server/src/settings.rs, crates/inga-engine/src/variants.rs, crates/inga-engine/src/learned.rs, crates/inga-server/src/webui.html, docs/api/inga.yaml, README.md, Dockerfile, docker/release.Dockerfile, .github/workflows/*.yml. New: src/config/ (the key table, the loader, inga config), docs/config.md (generated), tests/config_file.rs. Folds in the TODO.md item “A server presets file: inga serve --presets FILE”.

Decisions (2026-10-14)

Section titled “Decisions (2026-10-14)”
  1. toml_edit: accepted (pure Rust, MIT / Apache-2.0, with winnow, indexmap, toml_datetime), justified in §4.1.
  2. Where the file lives by default: ~/.cache/inga/inga.toml, next to everything else Inga keeps (§3.1) (the maintainer, 2026-10-14).
  3. Removed variables: removed outright, with no deprecation period and no error naming the replacing key: Inga is still in development and does not need backward compatibility, and nobody uses its environment variables (the maintainer, 2026-10-15, replacing his decision of 2026-10-14 of an error for 0.30 and 0.31). A removed variable that is still set is ignored like any other unknown variable (§11.2). The CHANGELOG lists the main ones with their keys; no table of the removed variables is kept in docs/config.md or elsewhere.
  4. --presets FILE: dropped; per-model presets are [models."NAME"] tables of the one file (§4.4). The shareable model settings spec keeps only the export, import and share link of one model’s settings.
  5. settings.json: split (preferences into inga.toml, machine state stays, §8), and a copy of the moved values is kept in settings.json for a downgrade.
  6. Secrets by environment reference (api_key = { env = "MY_VAR" }): allowed, for secrets only (§10).

New switches in other specs. Specs written the same day that proposed new INGA_* switches (Vulkan barriers, Vulkan memory blocks, the integrated GPUs’ shared pool, the hybrid prompts on the GPU, the cross-model KV transfer) now name keys of this file instead, under [gpu] or [debug]; inga bench --ab takes those keys.

1. What is asked

Section titled “1. What is asked”

The maintainer asks why Inga has some 70 INGA_* environment variables and no documented configuration file. His decision: one single configuration file; every user and debug setting lives only in inga.toml or on the command line; the INGA_* user and debug variables are removed, a hard break said in the CHANGELOG (on 2026-10-15: with no transition at all, decision 3).

The design must also: keep the file’s documentation in sync automatically; give tools to see where each value comes from and to change it; decide what becomes of settings.json and the other JSON files; keep secrets out of the file in clear; fold in the per-model server presets of TODO.md; and plan the migration so that main stays green.

2. What main does today

Section titled “2. What main does today”

Settings live in four places:

  • Command-line options, about 445 lines of USAGE in src/cli.rs. Note: they are not defined with clap — src/cli.rs is a hand-written parser (parse_* functions filling RunArgs, ServeArgs, GpuOpts, MeshOpts, …) with the help text as one constant. src/completions.rs keeps a table of every command’s options, and its test the_table_and_the_help_text_name_the_same_options checks the table against USAGE. The generated template (§6) follows that pattern, not clap’s.
  • Environment variables: the environment: section of USAGE and README’s “Environment variables” table. every_user_facing_variable_is_in_the_help (src/cli.rs) scans src, crates and tests for INGA_* names and fails on one that is neither in the help nor in INTERNAL_VARS.
  • $INGA_HOME/settings.json, written by the web UI (POST /api/inga/settings) and by inga download-dir: web_search, search_services, embedding_model, transcription_model, speech_model, vocoder_model, optimize_auto, memory, workspace, download_dir (crates/inga-server/src/settings.rs, crates/inga-hub/src/download_dir.rs), and the engine’s per-model state variants, variant_tips, variant_pending, variant_machine, expert_tips (crates/inga-engine/src/variants.rs, learned.rs). The saved values win over defaults and lose to --no-web-search, --search-backends, --workspace; HF_HUB_CACHE and HF_HOME win over download_dir.
  • Other files in $INGA_HOME (README, “Where does Inga keep its files and settings?”): model-dirs.json, nodes.json, secrets.json + secret.key, routes.json, mcp.json, mcp-approvals.json, schedules.json, measured.json, keys-usage.json, the --api-keys FILE, the service records (service/NAME.json).

How values reach the code today: INGA_DEVICE, INGA_MEM_LIMIT, INGA_THREADS*, INGA_ISA are read once in src/cli.rs / src/commands/mod.rs; the GPU, Vulkan, Metal and MoE toggles are read deep in the crates, many through inga_core::EnvCell (crates/inga-core/src/env.rs), which re-reads after env_changed() so that inga bench --ab NAME=VALUE can flip a variable between runs on one loaded model without allocating in a decode step. INGA_HOME is read in three places (inga_hub::inga_home, expert_cache.rs, profiles.rs) and set by 33 .env("INGA_HOME", ...) calls in the tests.

3. The inventory and the exceptions

Section titled “3. The inventory and the exceptions”

The code names 70 INGA_* variables (src, crates, tests, the .cjs test drivers; __INGA_VERSION__ is a text placeholder in the service worker, not a variable). They fall in four groups:

Group Count Becomes
User settings 14 a key of inga.toml and a flag; the variable removed
Developer and diagnostic toggles 16 a [debug] key; the variable removed
Test-only 33 unchanged: environment only, never in the file
Build-time, child process, examples 7 unchanged (not settings)

The shell scripts under tools/ and the workflows also use INGA_BIN, INGA_PORT, INGA_OPT: variables of those scripts, never read by inga; they stay. docs/experiments.md and docs/performance.md name INGA_OP_OFFLOAD, which no code reads any more: the migration fixes those lines.

3.1 INGA_HOME

Section titled “3.1 INGA_HOME”

The file lives in the home, so the home cannot come from the file in the usual way. Recommendation: remove INGA_HOME; the home is found without it:

  1. --home DIR, a global option (before or after the command, as --offline);
  2. else home = "DIR" at the top of the configuration file in use (§4.2);
  3. else the OS default, ~/.cache/inga (%USERPROFILE%\.cache\inga on Windows), as today.

The configuration file is found by --config FILE, else ~/.cache/inga/inga.toml, else /etc/inga/inga.toml (Unix; %ProgramData%\Inga\inga.toml on Windows) — the first that exists, never merged (one file). A home set in the default file moves the data, not the file: the file stays where it was found, a pointer to the data. Without any file, everything is a default and nothing is written until a setting is saved.

Reasons: one flag replaces the variable for the cases where it mattered (tests, a second instance, a service, a container), and a moved home is written once in the file instead of in every shell. Cost: the 33 test call sites pass --home instead (a helper does it), and inga_hub::inga_home() reads a process-wide value set once by main (inga_hub::set_home), with an override for library tests.

3.2 Docker and services

Section titled “3.2 Docker and services”

Containers usually configure through the environment. Recommendation: no environment layer; a generic override flag and a file:

  • --set KEY=VALUE (repeatable, global): any key of the file, e.g. inga serve --set gpu.device=vulkan --set cpu.threads=8 MODEL. It is the flag layer, so it wins over the file. Every key gets this form for free, including the ones without a dedicated flag (the [debug] keys).
  • The images ship /etc/inga/inga.toml with home = "/data/inga" and comments; users mount their own file over it (-v ./inga.toml:/etc/inga/inga.toml:ro) or pass flags after the image name (the ENTRYPOINT is already inga). Compose files and Kubernetes manifests write the same flags in command:/args:, or mount a ConfigMap as the file.
  • INGA_CONTAINER=1 (set by both Dockerfiles) becomes mesh.container, detected automatically (/.dockerenv, /run/.containerenv, the cgroup) and settable with --set mesh.container=true. ENV HF_HOME=/data/huggingface stays (§3.4).
  • inga service install stops copying INGA_* variables into the service record (copied() in src/commands/service/mod.rs); it records --config FILE and --home DIR in the serve arguments when they were given, and still copies the third-party variables it copies today.

Reasons: one way to configure on every platform; a flag shows in ps and in the service record, a variable does not; the file is what Inga’s own tools edit.

3.3 Secrets

Section titled “3.3 Secrets”

INGA_API_KEY, INGA_MESH_KEY, the API nodes’ keys (key-env=VAR, the key store), the search services’ keys (key store, BRAVE_API_KEY), and the named keys’ key_env (--api-keys FILE). Recommendation: a secret key of the file takes one of:

Form Meaning
{ secret = "NAME" } the encrypted store (secrets.json + secret.key)
{ file = "PATH" } a file holding only the key (Docker and Kubernetes secrets)
{ env = "VAR" } a variable the user names (CI, a secrets manager)
{ sha256 = "HEX" } server keys only: the hash it checks against

A string in clear is refused with an error naming these forms (inga config set serve.api_key reads the value from the terminal and stores it encrypted). The mesh key keeps its own file (~/.cache/inga/mesh/NAME.key), the default of mesh.key.

Environment references stay allowed for secrets only: the variable is named by the user in the file, not owned by Inga, so it is not a hidden setting; and secrets are exactly what CI systems and secret managers hand over as variables. key-env= of --api-node, key_env of the named keys and --key-env of inga node add stay as they are.

3.4 Third-party standard variables

Section titled “3.4 Third-party standard variables”

Keep honouring them: Inga does not own them, other tools set them for everyone, and ignoring them would break the shared setups they exist for.

Variable Why it stays
HF_HOME, HF_HUB_CACHE the cache shared with huggingface_hub; win over download_dir
HF_TOKEN, HF_ENDPOINT, HF_HUB_OFFLINE Hugging Face’s own; the token is a secret
HTTP(S)_PROXY, ALL_PROXY, NO_PROXY read by ureq; the network’s, not Inga’s
CUDA_VISIBLE_DEVICES read by the NVIDIA driver, before Inga sees a GPU
NO_COLOR not read today; honoured if coloured output comes
LMSTUDIO_MODELS, OLLAMA_MODELS where those apps keep models
OTEL_EXPORTER_OTLP_ENDPOINT OpenTelemetry’s; serve.otlp_endpoint beside it
HOME, USERPROFILE, XDG_RUNTIME_DIR, TZDIR, D-Bus the OS’s

inga config show lists the ones set, as the source of the values they decide.

3.5 Test-only variables

Section titled “3.5 Test-only variables”

They stay environment variables, as they are. They are read by cargo test code (and a few test hooks in src), set by the workflows and by hand; a test cannot take command-line flags, and a test configuration file would be one more file for the same job. They never appear in inga.toml, the template or docs/config.md. They stay listed in INTERNAL_VARS and documented in docs/development.md, not in docs/config.md. The two bench --ab test knobs (INGA_TEST_AB_PERTURB, INGA_TEST_NOTHING) become hidden keys test.ab_perturb, test.nothing (§5.2), since --ab now takes keys.

3.6 Build-time variables

Section titled “3.6 Build-time variables”

INGA_GIT_COMMIT, INGA_BUILD_DATE, INGA_TARGET, INGA_PROFILE are read by env! at compile time (crates/inga-server/build.rs, version.rs): unaffected. __INGA_VERSION__ is a placeholder replaced in the service worker’s text: unaffected. INGA_SKILL is set by Inga for a skill script (skills.rs), an interface to the script: unaffected. INGA_CI_KEY and INGA_X are names in examples (keys.rs, the --ab examples); the --ab examples change to keys.

4. The format: TOML

Section titled “4. The format: TOML”

4.1 TOML or INI

Section titled “4.1 TOML or INI”
TOML INI
Specification one (TOML 1.0) none: each parser differs on quotes, comments, escapes
Types strings, integers, floats, booleans, arrays, tables strings only
Per-model tables [models."hf://org/repo:Q4_K_M"] names with / and : are ambiguous
Lists models_dir = ["/a", "/b"] repeated keys or a separator, per program
Rust Cargo.toml, rustfmt.toml, clippy.toml no convention
Editing with comments toml_edit (what Cargo uses) by hand
Looks like INI for simple files —

Recommendation: TOML. A simple inga.toml reads as an INI file, and the rest (types, lists, per-model tables, one specification) is what INI lacks. toml_edit parses and rewrites keeping comments, order and spacing; it is pure Rust and statically linked, so it fits AGENTS.md’s dependency rule; the toml crate is not needed (reading goes through toml_edit::DocumentMut too). Writing a comment-keeping TOML editor by hand is possible (tests/api_specs.rs reads YAML by indentation) but is weeks of edge cases for no gain.

4.2 Location, sections and an example

Section titled “4.2 Location, sections and an example”

The file: §3.1. Sections:

Section Holds
top level home
[run] what loads and runs a model: run, serve, bench, info, … (ctx, sampling, mem_limit, speculative, offline, …)
[cpu] threads, threads_decode, isa, ram_gbps
[gpu] device, gpu_layers, gpu_split, max_load, experts_on, …
[serve] host, port, api_key, parallel, models_max, branding, …
[web_search] enabled, services (from settings.json)
[mesh] name, key, peers, roles, container, …
[client] url, api_key: what schedule, connect, mcp serve talk to
[models."NAME"] per-model presets (§4.4)
[debug] the developer toggles

[client] is added to the sections the maintainer listed: INGA_URL and the client side of INGA_API_KEY belong to no other.

A key is named after its flag, without the dashes (--threads-decode → cpu.threads_decode); a --no-X flag is X = false. Options that describe one invocation (-p, --image, --json, -o, the command’s files) have no key.

4.3 Precedence

Section titled “4.3 Precedence”

Flag (including --set) > file > default, per key. There is no environment layer any more, but for the third-party variables of §3.4 that already win today (HF_HUB_CACHE over download_dir), which keep their place and show as source env.

Errors: a value of the wrong type or out of range stops the command with exit 2, naming FILE:LINE, the key and what it takes (the same Error::Usage the flags use). An unknown key or section is a warning naming the closest known key, so that a file written by a newer Inga still runs an older one; inga config check makes warnings errors (for CI and for the web UI’s save).

4.4 Per-model presets (TODO.md’s --presets FILE)

Section titled “4.4 Per-model presets (TODO.md’s --presets FILE)”

[models."NAME"] replaces the presets file of TODO.md: the server’s models, their aliases, context, sampling, placement, LoRA and autoload in the one file that describes the server (as llama.cpp’s --models-preset, LocalAI’s per-model settings, KoboldCpp’s configs).

  • NAME is the name clients ask for. source is the file or reference (hf://..., ollama://..., a path); without it, NAME itself is the reference.
  • aliases = [...] are more names for it in /v1/models and requests.
  • autoload = true loads it at start (the models given on the command line still load too); the others load on first request, as the web UI’s library does today.
  • Any key the key table marks per-model may appear: from [run] (ctx, temp, top_p, chat_template, think, reasoning_effort, lora, variant, cache_type, quantize, …) and [gpu] (device, gpu_layers, gpu_split, experts_on). Others are refused with the section they belong to.
  • For a model: flag > its table > the section > default. A request’s own sampling fields win over all of these, as they win over the flags today.

--presets FILE is dropped (decision 4). The variants state of settings.json stays state; variant = "q4_k_m" in a model table pins one.

5. How the settings reach the code

Section titled “5. How the settings reach the code”

5.1 One resolved value per key

Section titled “5.1 One resolved value per key”

src/config/keys.rs holds the key table, the one source for everything else:

main reads the file once (src/config/load.rs), applies --set, and the parser fills RunArgs, ServeArgs, GpuOpts, … from flag, else file, else default — the places that read INGA_DEVICE, INGA_MEM_LIMIT, INGA_THREADS*, INGA_ISA read the resolved values instead (device_from_env, mem_limit, cpu_cfg lose their environment branch). Each resolved value remembers its source, for inga config show.

5.2 The debug toggles: inga_core::tunables

Section titled “5.2 The debug toggles: inga_core::tunables”

The [debug] keys are read deep in the crates, at each layer or product, and inga bench --ab flips them between runs on one loaded model. They become typed process-wide tunables in crates/inga-core/src/tunables.rs, replacing env.rs’s EnvCell: one static atomic per key (tunables::VK_TILES.get()), lock-free and allocation-free (the decode step’s alloc.rs test still holds), set once by main from the resolved [debug] values, and by tunables::set(key, value) for --ab and tests (no more std::env::set_var racing other threads). A reader replaces std::env::var("INGA_VK_TILES") with tunables::VK_TILES.get().

inga bench --ab KEY=VALUE takes a key (--ab debug.vk_tiles=false, --ab gpu.max_load=50), checked against the key table. The two test knobs are hidden keys test.ab_perturb and test.nothing.

6. Keeping the documentation in sync

Section titled “6. Keeping the documentation in sync”
  • inga config init [--force] [FILE] writes the template: every non-hidden key, grouped by section, commented out, with its help, its flag and its default. Generated from the key table, so it cannot drift.
  • docs/config.md, generated from the same table: one table per section (key, flag, default, meaning), the secret forms, the precedence, the lookup order, and the other programs’ variables Inga reads. A test compares it with what the table makes and fails with a diff; INGA_BLESS=1 cargo test --bin inga config_doc writes it again (the pattern of src/commands/placement/hardware_profiles.rs). Its tables obey tests/doc_tables.rs’s width limit like every other file.
  • Tests that tie the table to the rest (src/config/ and tests/config_file.rs, in the style of src/completions.rs and tests/api_specs.rs):
    • every option of USAGE’s run, serve, mesh, satellite, worker, schedule, connect sections has a key, or is in NO_KEY with its reason (per-invocation); every key with a flag names an option of USAGE;
    • every_user_facing_variable_is_in_the_help becomes no_inga_variable_is_read_but_tests: an INGA_* name in the code must be in INTERNAL_VARS (test and build-time); a new user variable fails CI with “add a key to src/config/keys.rs instead”;
    • the template parses, holds every key, and loads to the defaults; a file setting every key to a valid value loads, and inga config show names it as the source;
    • the environment: section of USAGE lists only the third-party variables.

7. Tools

Section titled “7. Tools”
  • inga config show [--json] [KEY|SECTION]: each key’s effective value and its source — default, file (PATH:LINE), flag (--threads, --set), env (only the third-party ones), detected (mesh.container) — and the file in use and the home, and which third-party variables are set. Secrets show their form, never their value.
  • inga config get KEY: the effective value alone (for scripts).
  • inga config set KEY VALUE and inga config unset KEY: checked against the table, written with toml_edit keeping comments; a secret’s value is read from the terminal and stored encrypted. A running server is told to apply live keys (POST /api/inga/config) when it answers; others say “restart needed”.
  • inga config path, inga config check (exit 1 on any warning), inga config init (§6).
  • The web UI’s Server page (Developer → Server): each setting with its value, its source (a badge: default, file, flag, env) and its help; a setting fixed by a flag is read-only with “set by –X”. Saving sends POST /api/inga/config {key: value} (admin keys), which validates, writes the file with toml_edit and answers which keys were applied and which need a restart. GET /api/inga/config serves the same list as inga config show --json. Both routes go into docs/api/inga.yaml (tests/api_specs.rs), the texts into I18N (webui_i18n.rs). /api/inga/settings stays, writing its preference keys to inga.toml (§8).

8. settings.json

Section titled “8. settings.json”

Recommendation: split it. The user’s preferences move into inga.toml; what Inga learns stays in settings.json as machine state.

settings.json key Becomes
download_dir download_dir (top level)
workspace serve.workspace
memory, optimize_auto serve.memory, run.optimize_auto
web_search, search_services web_search.enabled, web_search.services
embedding_model, transcription_model serve.embedding_model, …
speech_model, vocoder_model serve.speech_model, serve.vocoder_model
variants, variant_*, expert_tips stay: machine state

Reasons: the preferences are what a user writes, copies to another machine and wants to see in inga config show; the variant and tip state is written per model while models run, is meaningless on another machine, and would churn the user’s file.

Migration: at start, when settings.json holds a preference key, Inga writes it into inga.toml (creating the file from the template if missing, with toml_edit), unless the file already sets it, then removes it from settings.json and adds "moved_to": "inga.toml"; it says so once on the terminal. Done once; the settings.rs and download_dir.rs readers then read the resolved configuration. A copy of the moved values stays in settings.json (decision 5), so an older Inga run afterwards still sees them. model-dirs.json (folders added from the page) moves the same way into serve.models_dir, beside --models-dir.

As built

Section titled “As built”

C1 (feat/config-file-c1)

Section titled “C1 (feat/config-file-c1)”

What is in: src/config/keys.rs (the key table, 91 keys), src/config/load.rs (the loader, on toml_edit 0.25 with only its parse and display features), src/config/doc.rs (the template and docs/config.md), src/config/mod.rs (the global options, the lookup, the precedence, inga config), src/config/tests.rs and tests/config_file.rs. Where the code differs from the text above:

  • How the values reach the code in C1. A key that replaces a variable is handed to the code through that variable: main sets it from the file when it is not set (a variable set still wins over the file, the C1 precedence of §12), and always from --set or --home (Reach::Env). A key with a flag and no variable is given to the command as its flag when the command line does not give it (Reach::Flag; inserted before a --, else at the end); a parse error caused by such a flag names the key. So every value goes through the code path the variable or the flag takes today; C2 replaces the debug variables with inga_core::tunables and C3 the user ones with the resolved values. Booleans whose variable any value turns on (INGA_CUDA_SYNC, INGA_DIRECT_READS, INGA_VK_VALIDATE, …) are left unset for false.
  • The key struct is not §5.1’s: flag is Flag::Value / On / Off (a --no-X flag is X = false), also holds the short and opposite spellings, reach says how the value travels, example is a valid value (the template’s line and the tests’), commands limits a flag (and the two api_key keys’ shared INGA_API_KEY) to the commands that take it. per_model, live and hidden come with C6, C5 and C2 (no key is hidden yet: the test.* keys come with --ab on keys).
  • Not every option is a key. The keys are the 14 user and 16 debug settings of §3 (31 keys: INGA_API_KEY is serve.api_key and client.api_key) and 60 common settings of run, serve, the GPU and the mesh. Every other option of the run, serve, satellite, worker, mesh show, schedule and connect sections of USAGE is in NO_KEY with its reason: one invocation’s, a model’s own (C6), a settings.json preference (C4: [web_search], serve.memory, the speech models), or a detail kept as a flag. The test fails on an option in neither. [web_search] and [models."NAME"] are not sections yet: a file using them gets a warning.
  • The file in the home. When the home is given (--home DIR, or INGA_HOME until C3), the file looked for is DIR/inga.toml instead of ~/.cache/inga/inga.toml: a second instance or a test with its own home then never reads the user’s file. Then /etc/inga/inga.toml (%ProgramData%\Inga\inga.toml), as §3.1.
  • Global options are taken anywhere before a bare --, but merge --config (a recipe), service host --config (the Windows service’s record) and eval --set (a question set) after their command stay theirs; before the command they are global. --opt=value is accepted for the three.
  • Secrets: { env = "VAR" } and { file = "PATH" } work; { secret = "NAME" } and { sha256 = "HEX" } are refused with “comes with a later Inga” (C4, with the key store and inga config set). A string in clear is refused.
  • mesh.container is a plain key (INGA_CONTAINER); detecting the container comes with C3, when the variable goes.
  • inga config show sources are default, file PATH:LINE, flag --set, flag --home and env INGA_X (a variable of the table that is set, since it wins in C1); the third-party variables set are listed by name. A dedicated flag of another command (--threads) is not seen by inga config show. path and init work with a broken file; show, get, check and every other command stop on it (exit 2). check exits 1 on warnings.
  • inga service install records --config, --home and --set (paths made absolute) with the serve arguments, and no longer copies into the service the variables main set from the file or --set: the service reads the file itself.
  • Tests: the §6 tests but the two that belong to C3 (no_inga_variable_is_read_but_tests and the environment: section with third-party variables only): every_option_of_the_settings_sections_has_a_key_or_a_reason, every_flag_of_the_table_is_in_the_help, every_flag_given_from_the_file_is_taken_by_its_commands (each flag key injected into each of its commands, parsed), the_template_holds_every_key_and_loads_to_the_defaults (and, uncommented, to every example), config_doc_is_made_from_the_key_table (INGA_BLESS=1 cargo test --bin inga config_doc); the loader, --set, the precedence, the variables planned and the flags given; and tests/config_file.rs end to end (a key of the file read by inga version through INGA_ISA, the lookup in the home, --config, --home, --set, errors with FILE:LINE, warnings and check).

C2 and C3 (feat/config-file-rest)

Section titled “C2 and C3 (feat/config-file-rest)”

What is in: crates/inga-core/src/tunables.rs (replacing env.rs and its EnvCell), every reader of a removed variable moved to the resolved configuration, --ab on keys, the tests and the documents. Where the code differs from the text above:

  • Three ways a value reaches the code (Reach in src/config/keys.rs): Flag (given to the command as its flag, as in C1), Main (the binary’s own readers ask config::text(KEY) or config::secret(KEY) of the configuration main installed: run.mem_limit, cpu.threads, cpu.threads_decode, gpu.device, serve.branding, serve.api_key, client.url, client.api_key, mesh.key, debug.cuda_split, and ollama.token), and Tunable (a process-wide value of inga_core::tunables that main sets: gpu.max_load, run.speculative, cpu.ram_gbps, mesh.container, every [debug] key but debug.cuda_split and debug.vk_barriers, and the hidden test.ab_perturb and test.nothing; cpu.isa and home are tunables::Text, read when a command starts). The variant sets the tunable, the default unsets it, the end restores what the configuration had set.

  • inga connect‘s variable. INGA_API_KEY was also the default name of the variable inga connect reads the server’s key from and names in the tools’ settings (Codex’s env_key, opencode’s {env:...}, pi’s apiKey, the shell lines); left as it was, inga connect would read an INGA_* variable. The default is now LOCAL_LLM_API_KEY (not an Inga setting: a name for the tools, as --key-env VAR gives another), with client.api_key of the file when it is not set; the web UI’s API examples say $LOCAL_LLM_API_KEY. Confirmed by the maintainer.
  • The Metal test keeps its environment switch: INGA_METAL=simdgroup (a value of the test variable INGA_METAL) runs metal_everything with the M3 kernels on, as INGA_METAL_SIMDGROUP=1 did; tools/mac-test.sh passes --set debug.metal_simdgroup=... to inga and that value to the test.
  • Tests: no_inga_variable_is_read_but_tests (src/cli.rs: a quoted INGA_* name in src, crates or tests must be in INTERNAL_VARS, but in src/config/ and tests/config_file.rs, which name the removed ones to refuse them; the help’s environment section holds only config::THIRD_PARTY); the_file_reaches_the_process_wide_settings, ab_takes_the_keys_read_while_a_model_runs (src/config/tests.rs); in tests/config_file.rs an_inga_variable_changes_nothing (old variables set: the command runs and no value comes from them), the_debug_keys_and_the_home_reach_the_code, the_images_file_loads_without_a_warning and the_guides_name_no_variable_but_the_developers (an INGA_* name in the README, docs/*.md, docs/use-cases, docs/integrations, docs/api or examples must be one of docs/development.md’s tables; the specs, plans and research are the design’s history and keep the old names, as the CHANGELOG does).
