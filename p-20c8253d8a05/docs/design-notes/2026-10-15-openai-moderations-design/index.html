OpenAI's Moderations API on a local guard model

Status: proposed for 0.32.0 (decided 2026-10-15). First proposal (asked by the maintainer on 2026-10-15, the drop-in set). Nothing is built. Family moderations of the API families. Code: crates/inga-engine/src/session.rs (Engine::classify), crates/inga-engine/src/decide.rs (decide_with), crates/inga-server/src/lib.rs (classify), the guardrails’ classifier of the local guardrails spec (0.33.0), whichever lands first. New: crates/inga-server/src/moderations.rs, docs/api/moderations.yaml, [api.moderations] in inga.toml.

1. What the user sees, and what it is worth

Section titled “1. What the user sees, and what it is worth”

Apps that call POST /v1/moderations before or after a model (chat front ends, bots, LibreChat’s and Open WebUI’s moderation options, LangChain’s OpenAIModerationChain; to check each) keep working against Inga when the server has a moderation model:

Without one, the route answers 503 naming the setting — it never pretends (flagged: false with no check would be the worst answer: an app would believe the text was checked).

Honest about quality, in the docs and in every answer (inga_note): OpenAI’s omni-moderation is a model trained and calibrated for these 13 categories; a guard model (Qwen3Guard, Llama Guard) has its own categories, mapped onto OpenAI’s by a table, and its probabilities are not OpenAI’s scores. Thresholds that an app tuned on OpenAI’s scores need tuning again. Categories the guard model does not have are reported as not flagged with a score of 0 and listed in inga_unmapped.

2. The protocol (OpenAI’s API reference; to verify against the official docs)

Section titled “2. The protocol (OpenAI’s API reference; to verify against the official docs)”

POST /v1/moderations:

Answer:

One result per input string (for the multi-modal list, one result for the whole list).

3. Mapping onto Inga

Section titled “3. Mapping onto Inga”
  • The model: [api.moderations] model (a key of inga.toml, --moderation-model on the command line), loaded on first use like any model of the router (it counts in --models-max). The request’s model (omni-moderation-latest, text-moderation-latest) is accepted and ignored; the answer’s model is the local model’s name.
  • The check: for a guard model with its own chat template (Qwen3Guard, Llama Guard 3), the input rendered as a user turn and the verdict read from the logits with Engine::classify over the model’s own label tokens (safe / unsafe, then the category codes such as Llama Guard’s S1…S14), giving a probability per category. A plain chat model is accepted too, with an instruction listing OpenAI’s 13 categories and decide_with per category (13 typed yes / no answers; slower, and said so).
  • The mapping table (moderations.rs, to verify each guard model’s category list against its model card):
OpenAI Llama Guard 3 Qwen3Guard
violence, violence/graphic S1 violent crimes Violent
illicit, illicit/violent S2 non-violent crimes, S9 indiscriminate weapons Non-violent illegal acts
sexual S12 sexual content Sexual content
sexual/minors S4 child sexual exploitation (in sexual content; to verify)
self-harm, /intent, /instructions S11 suicide and self-harm Suicide and self-harm
hate, hate/threatening S10 hate (unethical acts; to verify)
harassment, harassment/threatening — (unmapped) — (unmapped)

A guard category with no OpenAI equivalent (Llama Guard’s S6 specialised advice, S7 privacy, S8 intellectual property, S13 elections, S14 code interpreter abuse; Qwen3Guard’s PII, politically sensitive topics, copyright, jailbreak) is returned in inga_categories beside OpenAI’s, so nothing the model found is hidden.

  • flagged: any mapped category over its threshold, [api.moderations] threshold (default 0.5), per category overridable.
  • Images: image_url parts are checked when the moderation model reads images (Llama Guard 3 Vision; to verify a GGUF exists that Inga runs); otherwise a 400 naming the model’s lack, never skipped silently.
  • Shared with the guardrails: the classifier call and the table are the same code the local guardrails use (guardrails.rs); the first of the two to be built writes it.

4. Errors and auth

Section titled “4. Errors and auth”
  • 503 moderation_model_not_configured: “no moderation model: set [api.moderations] model in inga.toml (or –moderation-model); see docs/api/moderations.yaml for the models Inga supports”. With the family switched off: the families spec’s 404.
  • 400 for an empty input or an image the model cannot read; 413 past the model’s context (the input is not cut: a moderation of half a text is not a moderation).
  • Auth: the chat group, as OpenAI’s.

5. Tests

Section titled “5. Tests”

tests/server.rs: 503 without a model (the message names the setting); a synthetic guard model (a tiny model whose template answers unsafe\nS1, built by the tests’ synthetic-model helper) flags violence with the expected probability; the unmapped categories are false with score 0 and listed; a list of inputs gives one result each; inga_categories. A real-world check on Qwen3Guard-Gen-0.6B and Llama Guard 3 1B with a small labelled set (ten safe, ten unsafe prompts per category from the models’ cards), the agreement recorded in the spec’s “As built” (TODO.md group A).

6. OpenAPI, phases, open questions

Section titled “6. OpenAPI, phases, open questions”

New docs/api/moderations.yaml. One phase, Low if the guardrails’ classifier exists, Medium if this spec builds it.

  1. A default moderation model offered by the first-run setup or the Models page (a download of ~0.6–1 GB)? Proposed: offered, never automatic.
  2. Should a 0.5 threshold be the default when the model’s probabilities are known to be skewed (guard models answer with high confidence)? To measure in the real-world check.
