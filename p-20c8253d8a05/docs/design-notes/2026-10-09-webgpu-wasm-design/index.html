WebGPU / WebAssembly build — design and work plan

Status: proposed, 2026-10-09; postponed out of 0.27.0 by the maintainer on 2026-10-11; reopened by the maintainer on 2026-10-14, proposed for 0.36.0 or later; reviewed against the code of 2026-10-14 in §8, “Revised 2026-10-14”, which takes precedence over §1–§6 where they differ. W0–W1 (the CPU part) built as an experiment on 2026-10-14, then its SIMD128 kernels and threads (W2’s Isa::Simd128, W4’s threads) the same day: see §8.7, “As built”. On 2026-10-15 the browser’s answers became the native engine’s again, token for token: the transcendental functions were the difference, not the SIMD128 kernels (see “Same tokens: the math functions”). Then the layers read from OPFS while the model runs (a model larger than the tab’s memory, branch exp/wasm-opfs-stream), and on 2026-10-15 the embeddings read by row, the output layer in parts and a model refused before it loads (see “The embeddings by row”). W3 (the layers on the GPU through WebGPU) built as an experiment the same day on branch exp/wasm-webgpu: see §8.8. The same day SIMD128 kernels for the i-quants and the other K-quants were built (see “SIMD128 for the other weight types”). Then both experiments on one page, the GPU’s first layers beside the CPU’s and storage within one memory limit, and the GPU’s optimizations (one read per step, inputs quantized once, bind groups reused, sampling on the GPU), on branch exp/wasm-unified: see §8.9; then the page’s tokens drawn on the GPU, shader-f16 kernels, kernels per adapter for Apple GPUs and a GPU benchmark button for the phone (built, not measured on a GPU: see “The page’s draws on the GPU”). Was the 0.27.0 item “WebGPU / WebAssembly build (in the browser)”. The WebAssembly CPU part needs no special hardware; the WebGPU part runs in Chrome / Edge on the maintainer’s P1000 (D3D12 or Vulkan underneath). Fifth in the suggested order (README.md).

1. Goal and scope

Section titled “1. Goal and scope”
  • Inga as a WebAssembly module that loads a GGUF model in a web page and generates text with no server: the same tokenizer, templates, model code and samplers as the native build.
  • WebGPU runs the layers on the user’s GPU from the browser; the CPU path (wasm SIMD128) is the fallback.
  • A demo page (web/) built from the existing web UI (inga-server/src/webui.html) in a “local” mode, published with the GitHub Release as a static folder.
  • Out of scope: the HTTP server, inga-hub downloads with ureq, distributed inference, image/audio decoding in the first phases, Node.js packaging.

2. What the maintainer needs

Section titled “2. What the maintainer needs”
  • Rust target wasm32-unknown-unknown; build tools (not linked into inga): wasm-bindgen-cli (same version as the wasm-bindgen crate), optionally wasm-opt (Binaryen) for size.
  • Chrome or Edge ≥ 113 with WebGPU (Windows D3D12 on the P1000), Firefox ≥ 141 / Safari 26 for coverage.
  • Crates, only in the new crates/inga-wasm, which the inga executable does not depend on: wasm-bindgen, js-sys, web-sys (MIT/Apache-2.0, pure Rust, the standard way to call browser APIs) and wgpu (MIT/Apache-2.0, pure Rust; WebGPU in the browser, Vulkan/Metal/D3D12 natively). Justification: the browser build has no other way to reach JavaScript and WebGPU; the native executable keeps its dependency list.

3. Design

Section titled “3. Design”

3.1 Making the core crates build for wasm32

Section titled “3.1 Making the core crates build for wasm32”

inga-core, inga-quant, inga-tokenizer, inga-model, inga-engine (without inga-hub and the server) must compile for wasm32-unknown-unknown:

  • Memory mapping: no mmap in the browser. Weights come in as Storage::Owned (Arc<Vec<u8>>) from an ArrayBuffer; a new loader GgufFile::from_bytes (or a Read + Seek source) in inga-formats avoids memmap2 on wasm (cfg).
  • Threads: std::thread does not exist on wasm32-unknown-unknown without the atomics target feature and a rebuilt standard library (nightly). Phase W1 runs the ThreadPool (crates/inga-cpu/src/pool.rs) with zero workers (the calling thread only); multithreading through Web Workers and SharedArrayBuffer (cross-origin isolation headers) is phase W4, when it works on stable Rust.
  • SIMD: a new Isa::Simd128 with kernels in crates/inga-cpu/src/kernels/wasm.rs (core::arch::wasm32: i32x4_dot_i16x8, and the relaxed-SIMD int8 dot where the toolchain has it stable), built with -C target-feature=+simd128; scalar fallback for browsers without SIMD (all current ones have it).
  • Memory: wasm32 linear memory is limited to 4 GB (browsers cap lower, often 2–4 GB); memory64 lifts it but costs speed. With WebGPU the weights go straight into GPU buffers and are not kept in wasm memory (§3.3), so a 4B Q4 model fits.
  • Instant / time: web-time style shim in inga-wasm for the samplers’ seeds and the stats (performance.now()).

3.2 API exposed to JavaScript

Section titled “3.2 API exposed to JavaScript”

Models are fetched with HTTP range requests (Hugging Face serves CORS), cached in the Origin Private File System (OPFS) by file hash so a reload does not download again, and parsed tensor by tensor (no full copy in wasm memory).

3.3 The WebGPU backend

Section titled “3.3 The WebGPU backend”

WgpuOps implements inga_gpu::GpuOps (CUDA spec §7) over wgpu; GpuLayers<WgpuOps> is the stage. Shaders in WGSL (crates/inga-wasm/shaders/*.wgsl, embedded), semantics as the CUDA kernel table, each tested against RefBackend:

  • quantized matvec: WGSL’s dot4I8Packed (packed 4×8 integer dot, a core WGSL feature) on Q8_1-quantized activations, as __dp4a on CUDA;
  • shader-f16 feature used for storage when present; arithmetic in f32;
  • subgroups feature for reductions when present, else workgroup memory;
  • limits: request the adapter’s maxBufferSize and maxStorageBufferBindingSize (defaults are 256 MB / 128 MB); large tensors split by rows across bindings.
  • The whole decode step is one command encoder and one queue.submit; reading the logits back is the only mapAsync per token (async: the JS API is async anyway).

Because wgpu also runs natively, the same backend is testable outside the browser (§5); it is not offered by the native inga executable (Vulkan / Metal / CUDA are better there).

4. Phases

Section titled “4. Phases”
  1. W1 — wasm CPU. Core crates build for wasm32, from_bytes loading, single thread, inga-wasm with load / generate. Acceptance: SmolLM2-135M-Instruct and Qwen2.5-0.5B Q4_K_M generate in Chrome the same greedy text as native inga run (32 tokens); .wasm ≤ 4 MB gzipped.
  2. W2 — SIMD128 and the demo page. Isa::Simd128, OPFS cache, the web UI’s local mode. Acceptance: Qwen2.5-0.5B decode ≥ 50 % of native single-thread speed.
  3. W3 — WebGPU. WGSL kernels, WgpuOps. Acceptance: Llama-3.2-1B Q4_K_M in Chrome on the P1000 gives the CPU’s greedy text; decode ≥ 60 % of Inga’s native Vulkan backend on the same card, and ahead of llama.cpp’s WebGPU build (ggml-webgpu through its wasm/browser build) if one is available to compare; Llama-3.2-3B loads within the browser’s limits.
  4. W4 — threads and size. Web Workers + SharedArrayBuffer for the CPU path, wasm-opt, release packaging (inga-web-<version>.zip).

5. Test plan

Section titled “5. Test plan”
  • CI: cargo build --target wasm32-unknown-unknown -p inga-wasm and cargo clippy for it; the core crates’ unit tests under wasm-bindgen-test in Node (CPU path, no browser) on the Linux job; wgpu natively on lavapipe (software Vulkan, as the Vulkan spec) runs every WGSL kernel test and the synthetic end-to-end test on every PR.
  • Headless browser (optional CI job): wasm-bindgen-test --chrome --headless with SwiftShader WebGPU for the W3 kernel tests, if stable on the runner.
  • Maintainer: Chrome/Edge on Windows with the P1000 (chrome://gpu shows WebGPU hardware), the demo page served by python -m http.server or inga serve (with cross-origin isolation headers for W4); timings in docs/performance.md.

6. Risks and open questions

Section titled “6. Risks and open questions”
  • Browser memory limits vary (tabs killed above ~4 GB on some systems): the demo page states the largest tested model per browser.
  • WebGPU limits on integrated GPUs (storage buffers per stage, buffer sizes) may force smaller tiles; keep them as specialization (override) constants.
  • wgpu versions move fast (a breaking release every few months): pin one, upgrade on purpose.
  • Open: ship the web build as a separate release asset, or embed it in inga serve (the web UI then offers “run in this browser”)? The second is attractive: the server hands out the model file, the browser runs it.

8.0 Open questions for the maintainer

Section titled “8.0 Open questions for the maintainer”
  1. Separate asset or served by inga serve? (§6’s open question, still open.) Proposed: a separate release asset inga-web-<version>.zip first (W2), then, if wanted, inga serve --webgpu serving it at /webui/wasm/ beside the KaTeX and Mermaid files of /webui/lib/ (0.30.0), so the web UI can offer “run in this browser” with the model file handed out by the server. Embedding it in the executable costs its size (§8.6).
  2. Generated or hand-written WGSL? Proposed: generated from the committed SPIR-V by naga at development time (§8.2), committed like the SPIR-V, hand-written only where the translation fails. Agreed?
  3. Which models must run in W3? Proposed: the dense attention models (Llama, Qwen2.5 / 3, Gemma 3) with F16, Q8_0, Q4_K and Q6_K weights; DeltaNet, Mamba-2 and MoE kernels later (W5), since browser memory limits rule out most of those models anyway.

8.1 What the code looks like now

Section titled “8.1 What the code looks like now”
  • The core crates already build for wasm32-unknown-unknown, checked on 2026-10-14 with cargo check --target wasm32-unknown-unknown: inga-core, inga-quant, inga-tokenizer, inga-formats and inga-cpu compile unchanged (memmap2 compiles there; mapping a file would fail at run time, so §3.1’s GgufFile::from_bytes is still needed). inga-model fails only on read_some (crates/inga-model/src/experts.rs, written for Unix and Windows: the experts read from disk), which needs a wasm fallback or a cfg on the disk experts. inga-engine fails on getrandom (it needs its wasm_js feature on wasm) and pulls inga-hub (ureq, rustls): the hub goes behind a default feature that inga-wasm turns off. std::thread::spawn compiles but panics at run time on this target, so W1’s zero-worker pool stays.
  • GpuOps grew from the CUDA spec’s table to about 46 operations (crates/inga-gpu/src/ops.rs): buffers and weights, the KV cache (kv_cache, kv_truncate, kv_store, kv_read), positions, capture and replay (CUDA graphs), rope tables, norms and activations (rms_norm, swiglu, geglu, sigmoid_mul, relu2, group_norm, swiglu_clamp), attention, matvec, matmul and the quantized prompt products (quantize_rows, matmul_quantized, swiglu_quantized), DeltaNet (delta_gates, conv_step, delta_step), Mamba-2 (ssm_conv, ssm_scan), grouped experts (scatter_add, groups_products, add_bias_rows, moe_sum) and sampling on the device. GpuLayers<O> (layers.rs, about 2.9k lines) and the split across devices (split.rs) are generic over it, and HostOps tests them without a device. WgpuOps implements the same trait: capture / replay become “record the step into one command encoder” (WebGPU has no graphs, and needs none: one submit per step is already the design of §3.3); has_sampler returns false at first (logits read back, sampled on the CPU).
  • Four backends implement it (CUDA, Vulkan, Metal, HIP through CUDA’s code); Metal’s MSL kernels are checked on a CPU emulator on Linux (crates/inga-metal/src/emu.rs).

8.2 The Vulkan shaders as the source of the WGSL

Section titled “8.2 The Vulkan shaders as the source of the WGSL”

crates/inga-vulkan/shaders holds 96 GLSL files (72 compute shaders and their includes), compiled by tools/build-spv.sh to the 72 committed SPIR-V files. What they use, and its WGSL counterpart:

Vulkan shaders Count WGSL
Quantized blocks read as 32-bit words (no 8- or 16-bit storage extension) all array<u32>, the same unpacking
Push constants 25 sources a uniform buffer per dispatch (browsers have no push constants)
Specialization constant BLOCK (common.glsl) all override BLOCK: u32
Workgroup memory (reductions, matmul tiles) 22 var<workgroup>; the tiles’ size to check against the 16 KB default limit
Subgroup sums (*_sg, and SUBGROUP_SUM in the *_dot ones) 14 + 16 the subgroups feature (Chrome 134+); without it the plain variants, which already exist
4 x 8-bit integer dot (INT_DOT, GL_EXT_spirv_intrinsics) matvec.glsl, matmul_tile.glsl dot4I8Packed (WGSL’s packed_4x8_integer_dot_product)
Storage buffers per shader at most 6 within the default limit of 8
Cooperative matrices none —

So the shaders map onto WGSL without redesign. The WGSL is generated, not re-written: tools/build-wgsl.sh runs naga (wgpu’s shader translator, MIT / Apache-2.0, a development tool like glslangValidator, never linked into inga) on each committed .spv, then a small rewrite moves the push-constant block into a uniform binding; the output is committed under crates/inga-webgpu/wgsl/ with a sources.sha256 like spv/, and CI checks it is up to date. Shaders naga refuses (the spirv-intrinsics integer dot is the likely one) are written by hand in WGSL from their GLSL, and their plain variants used until then.

SIMD128 and threads (second step, 2026-10-14).

  • Isa::Simd128 (crates/inga-cpu/src/kernels/wasm.rs, name SIMD128, which the page shows: “SIMD128 kernels on 1 thread”). SIMD128 is a property of the module, not of the CPU: .cargo/config.toml builds wasm32-unknown-unknown with -C target-feature=+simd128, and a browser without it would refuse the whole module (none of the targets: Safari 16.4, Chrome 91, Firefox 89 have it), so there is no run-time detection and one SIMD module is built (SIMD128=0 still builds the scalar one, for comparisons). Standard SIMD128 only, no relaxed SIMD (not in Safari).
    • Kernels (the other weight types since 2026-10-15, see “SIMD128 for the other weight types”): the Q8_0, Q4_K and Q6_K dot products, Q4_0 (dot_more), Q8_0 four weight rows against one token (decode, rows4), one weight row against four tokens for Q8_0, Q4_K and Q6_K (prefill, dot4: the weight unpacked once for four tokens), the Q8_0 and Q8_K activation encoders, the float matrix product of the attention (gemm, two tokens per load of the weights), axpy and dot. The F16 / BF16 / F32 weight dots, the softmax (its exp) and the key transpose stay the scalar ones.
    • No 8-bit dot product in SIMD128: i16x8.extmul_{low,high}_i8x16 multiply bytes into 16-bit products (smull / smull2 on aarch64), added in 16 bits while they cannot overflow (Q4_K: four products of at most 15 · 127; Q8_0 and Q6_K: two), then widened by i32x4.extadd_pairwise_i16x8, or by i32x4.dot_i16x8_s against the block’s scale (which multiplies and widens at once).
    • Bit for bit the scalar kernels, a choice that keeps the browser test exact: a block’s integer sums are exact in any order, and each block’s float arithmetic and the sum over blocks follow inga_quant::vec_dot_ref’s order; where four rows or four tokens run together each lane holds one of them and adds its own blocks in order (the four sums of a block gathered by one transpose of i32x4 vectors). The encoders round with f32x4.nearest (ties to even, as the scalar nearest), gemm and axpy add in the scalar order; only dot (f32 · f32, the sparse attention’s, the lightning indexer’s and the partial attention’s of a KV cache on disk, none of which the browser runs) sums in four lanes. Natively, browser_cpu() is still Isa::Scalar on one thread, and on wasm32 Isa::best(). The same kernels did not make the same tokens alone: the engine called the C library’s exp, powf and sin_cos, which round differently natively and in the browser, and a four-layer model answered differently by one token; with inga_core::math the native engine on the scalar kernels gives the browser’s tokens exactly (see “Same tokens: the math functions”).

Weights read from OPFS while the model runs (branch exp/wasm-opfs-stream, 2026-10-14). On the iPhone 16 Pro, Safari ended the tab with a 4B model (2.5 GB in Q4_K_M): every weight lived in WebAssembly memory. The maintainer chose to try streaming: keep part of the weights in memory, read the rest from OPFS at every token, and measure.

  • The same design as natively, without a mapping. Natively, a dense model larger than the RAM streams its layers from the memory-mapped file (Plan::stream_layers, Model::stream_layers: the next layer Storage::prefetched while one runs, the layer evicted after it; “SSD (read while running)”). The browser has no mapping, so inga_core::Storage gains a variant, Streamed(Arc<StreamPool>, group, range) (crates/inga-core/src/stream.rs): a view of one of two buffers (slots) the size of the largest streamed layer. Group (layer) g is read into slot g % 2 by prefetch, or when one of its weights is first read (bytes()), from a ReadAt (a file read at an offset). The model’s layer loop is unchanged but for one line: it already prefetches layer l + 1 while l runs, and now also layer 0 before the first (as its other loop did); evict does nothing to a slot, which the layer two on overwrites. A layer’s tensors close together in the file (256 KiB apart at most, the norms between them) are read in one request. Storage::len gives a weight’s size without reading it; Weight::rows of a streamed weight is a view of the same slot; CpuBackend::repack leaves streamed weights alone (the browser does not repack anyway).
  • What stays in memory (inga_engine::LayerSplit, next to Plan in plan.rs): the token embeddings and the output layer (as natively: a token’s logits read the whole output layer, which Llama 3.2 and Qwen3 tie to the embeddings), every norm and bias (the 1-D tensors), the KV cache, and the first layers whose matrices fit the budget together with the two slots (one when a single layer streams); the matrices of the others stream. Under a budget too small for that, every layer streams and the info says the budget is exceeded. The budget is for weights only: the KV cache and scratch come on top. (Changed on 2026-10-15, below: the tables are read by row, the output layer is counted like a layer, the budget covers everything and a model that cannot fit is refused.)
  • Reading the file. inga_formats::read_model reads the GGUF header from a ReadAt (growing reads until it parses), then each tensor kept in memory straight into its buffer (no chunk is copied twice, unlike GgufStream‘s pushes), and makes the streamed tensors’ views (GgufFile::with_streamed); Engine::from_source plans the split from the header and turns Model::stream_layers on. inga_wasm::Runner::from_source wraps it, and JavaScript calls openModel(name, size, read, budget, ctx, progress), where read(at, view) is FileSystemSyncAccessHandle.read(view, { at }) in the worker: view is a Uint8Array over WebAssembly memory (Uint8Array::view_mut_raw), so the bytes land in the slot with no copy, in reads of up to 64 MiB. The handle stays open while the model is loaded. In the threaded module the reader refuses calls from another thread than the one that loaded the model (JavaScript values belong to one thread); the layers are read on that thread, before the pool’s threads use them.
  • info() adds streamed_layers, stream_read_per_token (the bytes a pass reads, norms between matrices included), stream_buffers, resident_weights and within_budget; a generation’s statistics add stream_read_bytes and stream_read_secs.
  • The page (contained in a few places of app.js, worker.js and index.html): Settings → Memory for weights, Auto / All in memory / Limit in MB. Auto is 1 GB for weights on iOS (an iPhone, iPad or iPod user agent, or a MacIntel platform with a touch screen: a heuristic) and 2 GB elsewhere, applied only to a file larger than that; starting points, to tune. A model within its budget loads as before (all in memory, from Loader.push); a larger one from OPFS through openModel (the worker’s load message gains budget). A picked file larger than the budget is first copied into OPFS (import: the quota checked first with navigator.storage.estimate(), the copy’s progress shown), then loaded from there. The load line says how many layers are read at every token and how many bytes; the answer’s line how much was read, in how long. Disk speed test (under Stored models) writes 256 MiB to OPFS in 8 MiB pieces, reads it back through a sync handle, reports MB/s, deletes the file (and refuses without 320 MiB free). The download and the copy now check what each OPFS write wrote: in Playwright’s default context, whose OPFS quota was under 1 GiB, a 2.6 GB download had been marked complete with a third of the file.

Same tokens: the math functions (2026-10-15)

Section titled “Same tokens: the math functions (2026-10-15)”

A four-layer model with SmolLM2-135M’s widths (the browser test’s, with n_layers: 4) gave a different answer in the page and natively: the 24 greedy tokens decoded to gggg in Chromium and ggggg in the native engine on the scalar kernels (most of the synthetic vocabulary decodes to nothing). The two-layer model of the test matched.

  • Not the SIMD128 kernels. A probe run in Node.js (wasm32-wasip1 with +simd128) compared the scalar and the SIMD128 tables inside one module on that model, the prompt in one pass then 24 tokens one by one, with the residual stream entering every layer tapped (Scratch::set_taps): the logits and every layer’s input were the same bits at every step. The same probe built natively (x86-64, glibc) gave those bits too.
  • The math functions. The page is wasm32-unknown-unknown, which has no C library: there the standard library’s f32::exp, powf, sin_cos, … are compiler_builtins’ port of musl’s functions (the libm crate), and natively glibc’s (wasm32-wasip1’s wasi-libc agreed with glibc on this model). On 2^20 arguments each, glibc’s and the browser’s expf (on [-20, 20]) differ on 9.8 % of them, powf(10000, y) (y in [-1, 0]) on 9.7 %, sincosf (on [0, 2048]) on 1.3 %, and 6 of the 64 RoPE frequencies 10000^(-2i/64); the libm crate built natively gives exactly the browser’s values. SiLU, softmax and RoPE go through these tens of thousands of times a token, and on four layers the last-bit differences moved a greedy choice.
  • The fix: inga_core::math, one set of functions written in Rust, used by every number the CPU computes for a model: exp is Inga’s own (a table of 2^(i/32), double-precision arithmetic, a Taylor polynomial of degree 3; correctly rounded on all but 0.016 % of the floats of (-104, 89), never more than 0.51 units in the last place off, where glibc’s expf misrounds 0.008 % and libm’s 0.86 %), the others (ln, log2, powf, sin_cos, sin, cos, tanh, and exp, ln, cos in double precision) are the libm crate’s (MIT, pure Rust). inga-core, inga-cpu and inga-model call them everywhere (the layers, the attention, RoPE and YaRN, the samplers, the synthetic test models), and their clippy.toml disallows the standard methods; inga-engine’s diffusion steps call them too. Checked: a digest of exp on all 2^32 floats and of the others on 2^24 arguments each is the same natively (x86-64) and in wasm32-unknown-unknown (Node.js, V8); inga-core’s test math::tests::give_the_same_bits_on_every_target fixes it for the platforms of the test job. The native engine’s numbers change in the last bits against earlier versions (they used glibc’s on Linux, and each system’s own on macOS and Windows, which now give Linux’s bits for these functions too).

Section titled “SIMD128 for the other weight types (2026-10-15)”

  • The types that matter. llama.cpp’s IQ2_M mix (inga-engine’s quantize.rs copies it) uses IQ2_S for most matrices. It uses IQ3_S for attn_output and for the first eighth of the ffn_down matrices. attn_v is Q4_K when there are four or more query heads per key/value head, and IQ3_S otherwise. The real Gemma file could not be downloaded here, so its exact mix was not checked.

  • Kernels (crates/inga-cpu/src/kernels/wasmq.rs, through dot_more):

    • IQ2_XXS, IQ2_XS, IQ2_S, IQ3_XXS, IQ3_S, IQ1_S, IQ1_M, IQ4_XS, Q2_K, Q3_K and Q5_K against Q8_K activations, each with a four-token kernel for prompts. Kernels gains dot4_more for these; the other tables leave it None.
    • IQ4_NL, Q5_0, Q4_1 and Q5_1 against Q8_0 / Q8_1 activations, one token at a time. Prompts on IQ4_NL and Q5_0 already ran as Q8_0 rows (to_q8_0).
    • Neither the NEON nor the AVX2 module has i-quant grid kernels to copy (AVX2 has Q2_K, Q3_K, Q5_K, IQ4_NL and IQ4_XS). These follow wasm.rs’s Q4_K and Q6_K instead.

  • How they work. A weight block is rebuilt once, for the one or four tokens, as its 256 signed quants in 16 vectors, plus its integer scales:

    • For an i-quant, two grid entries a vector (u64x2 of the 8-value IQ2 / IQ1 entries, u32x4 of the 4-value IQ3 ones) take their signs from a 256-entry table of byte masks ((g ^ m) - m). For IQ2_XXS, IQ2_XS and IQ3_XXS the table is of ggml’s ksigns_iq2xs.
    • IQ4_NL and IQ4_XS look their values up with i8x16.swizzle.
    • The K-quants combine their bit planes with shifts and masks.
    • The products are wasm.rs’s: extmul into 16 bits, then two (one scale per 16 values) or four (one scale per 32) products added while they fit, then i32x4.dot_i16x8_s with the scale. IQ3_XXS’s grid reaches 62, so four products are at most 4 · 62 · 127 = 31,496 < 2^15.
    • IQ1_M’s shifts are a second vector of ±1 against the same activations. IQ1_S’s shifts come from the activation sums, as in the reference. IQ4_XS keeps its eight sums of 32 apart, because the reference adds one float product per 32 values.

  • Bit for bit the scalar kernels, as wasm.rs. Integer sums are exact in any order. The float arithmetic follows inga_quant’s reference kernels (iq.rs, legacy.rs): the same order and the same initial 0.0 (not the -0.0 of an iterator’s sum), and the final 0.125 / 0.25 factor applied last.

Blockers and limits found.

  • Threads need a nightly toolchain (-Z build-std) until the standard library ships prebuilt with atomics for wasm32-unknown-unknown or build-std is stable; the pinned date has to be moved by hand (tools/build-wasm.sh, build.yml). The threaded module is not linted by cargo clippy (stable clippy cannot build it).
  • The threaded module’s shared memory declares a 4 GiB maximum; a browser that cannot reserve it (possibly iOS Safari) fails to start it, and the page falls back to one thread (checked only in Chromium).
  • Spinning workers: the pool’s threads spin 5 ms after each job before parking, as natively; on a phone that costs battery during an answer (not measured).
  • A generation is one synchronous call in the worker, so the page stops it only through a shared flag (isolated pages) or by ending the worker (the others).
  • wasm32’s 4 GB address space and the browsers’ lower limits per tab (unknown on iOS Safari here): with the weights in WebAssembly memory a 1B Q4 model takes about 0.9 GB; larger models need W3’s GPU buffers, or the layers read from OPFS at every token (above), slowly.
  • Streaming reads synchronously on the thread that runs the model: the next layer is read before the current one runs, not during it, so reads and compute add up.

Speculative decoding with a resident draft model (2026-10-15)

Section titled “Speculative decoding with a resident draft model (2026-10-15)”

A pass of a model whose layers are read from OPFS reads those layers whatever the number of tokens it runs; a draft model guessing several tokens lets one pass read them once for every token it accepts. Built on the native engine’s speculative decoding, with no second implementation:

  • The engine (inga-engine): DraftModel (the draft-model path of inga run --draft, speculative.rs) runs behind Session::set_gated_speculation_with and a SpecGate. DraftModel::set_batch makes it catch up with a prompt in passes of STREAM_BATCH tokens, so its activations are those planned (natively one pass, as before). same_vocabulary checks two tokenizers token by token. SpecGate::timed is the gate without MIN_ACCEPT: it already decides by the clock (the tokens per second of its checks, the draft’s guesses and the reads included, against those of plain steps measured first, PLAIN_PROBE), and a measure that accepts nothing still ends early (EARLY, and at once when its checks cost more than two plain steps); the fixed share of 10 % is left out because a streamed pass is so dear that a lower share can pay. The rest is unchanged: WINDOW 16, pauses of 64 to 1,024 plain steps. GenStats gains draft_checks, decode_passes and the bytes read from the file after the prompt (decode_read_bytes, decode_row_bytes, read from the model’s StreamPool). Engine::plan_source plans a model from its header (inga_formats::read_header) before any weight is read.
  • The check is one pass: Model::forward_all runs the token and its guesses together, layer by layer (run_layers), so each streamed layer is read into its buffer once per check, and the output layer’s parts compute the logits of every row of the pass while each part is loaded. Tested: the bytes read after the prompt are, pass by pass, every streamed item once (but one still in its buffer), for plain steps and checks alike, and the reads per token fall with a draft that agrees.
  • inga-wasm: Runner::from_sources(model, Some((draft, n)), ctx, budget, …) reads both headers first; it refuses a draft of another vocabulary, and one whose planned memory held whole (weights, KV cache for the context, activations), plus the model’s logits for the n - 1 extra rows of a check, exceeds the budget; the model is then planned within what is left, and its refusal says the draft’s share was taken out. The draft is loaded whole after the model. n defaults to 4 (DEFAULT_DRAFT). openModel takes draftName, draftSize, draftRead, draftTokens; info() adds draft (name, layers, bytes, KV cache, activations, memory planned, tokens); an answer’s statistics add draft_tokens, draft_accepted, draft_checks, accepted_per_check, draft_paused, decode_passes, decode_read_bytes, read_per_token and read_per_pass.
  • The page: Settings → Draft model (None or a stored model, kept in localStorage by name); a load with a draft goes through openModel with both files’ sync access handles open (a picked file is stored first); the load line names the draft and its memory; the answer’s line adds the guesses and the bytes read per token.
  • Tests. inga-engine: a draft catching up in passes of 1 and 3 tokens guesses as one in a pass; plain decoding counts a pass per token; a draft of another vocabulary is refused; the timed gate keeps a draft accepting 6 % that pays by the clock (the default gate pauses it) and pauses a slower one and one that accepts nothing. inga-wasm: greedy decoding with a draft gives plain decoding’s tokens with the model all in memory and under seven budgets (its layers streamed), a draft that agrees (the model itself) and one that rarely does (another model), 1, 3 and 6 guesses; the reads after the prompt are as reported, pass by pass; with an agreeing draft fewer passes and fewer bytes per token than plain decoding; a draft of another vocabulary, one too large for the limit, and one leaving the model too little are refused after the headers alone. 8.8 WebGPU, as built (experiment, 2026-10-14)

Section titled “8.8 WebGPU, as built (experiment, 2026-10-14)”

W3 brought forward as an experiment on branch exp/wasm-webgpu (from exp/wasm-cpu), to answer two questions on the maintainer’s iPhone 16 Pro: how fast the layers run on the GPU against the CPU path (53 tok/s SmolLM2-135M, 25 Qwen3-0.6B, about 13.5 Llama-3.2-1B in 879 MiB there), and whether a model larger than the tab’s WebAssembly memory runs with its weights in GPU buffers (a 4B model, about 2.5 GB, makes iOS kill the tab on the CPU path). Tested in headless Chromium on Linux (SwiftShader, a software Vulkan device) and natively on lavapipe only: no real GPU, no phone, no Safari. The page shows what the phone needs to answer both.

Design.

  • crates/inga-webgpu (new; not a dependency of inga): WebGpu, an inga_gpu::GpuOps device over wgpu 30.0.1, so GpuStages / GpuLayers run a model’s layers on it unchanged (the same layer loop as CUDA, Vulkan and Metal). Why wgpu rather than raw web-sys bindings: the same code runs natively on wgpu’s Vulkan backend, so every kernel and the whole layer loop are tested against the CPU on lavapipe (INGA_VULKAN=1), with no browser; in the browser only its WebGPU backend is built (no wgpu-core, no naga: the WGSL goes to the browser as it is), and the module grows from 4.61 MB to 5.54 MB (1.48 to 1.64 MB gzipped; the WGSL text is 0.6 MB of it). Native builds use pollster (MIT / Apache-2.0) to wait for the device in the tests and the example.
  • The WGSL is generated (§8.2’s plan): tools/build-wgsl.sh takes the Vulkan backend’s committed SPIR-V, portable builds only (no subgroup arithmetic, no 8-bit integer dot product), sets and folds the specialization constants with spirv-opt (BLOCK 256; the matrix-vector kernels with LANES 32 and NR 8, and a one-token build with NR 1), drops the NonReadable / Restrict decorations, moves a second variable on the same binding (GLSL’s uint / uvec4 aliases of one buffer) to binding 10 + n, and translates with naga 30.0.1 (cargo install naga-cli@30.0.1). Then a rewrite of the text: the push constants become a uniform buffer at binding 20 (one 256-byte slot per dispatch in an arena written before each submission); the workgroup size, a specialization constant naga leaves at 1, becomes 256; in the kernels with barriers, the workgroup’s id and count, which naga copies into private variables, go through workgroup variables read with workgroupUniformLoad (Chromium’s Tint, stricter than naga, otherwise refuses the barriers as non-uniform); -infinity, refused by WGSL as a constant, is read from a private variable. 43 kernels: add, add_bias, rms_norm, swiglu, geglu, sigmoid_mul, relu2, rope, kv_store, attention, quantize_q8_1; matvec_* of F32, F16, Q8_0, Q4_0, Q4_1, Q5_0, Q5_1, IQ4_NL, Q2_K, Q3_K, Q4_K, Q5_K, Q6_K, IQ4_XS (two builds each); the tiled prompt products matmul_* of Q4_0, Q8_0, Q4_K, Q6_K. None is written by hand; every one translates, passes naga’s validation and compiles in Chromium (checked by creating each pipeline). The output is committed (crates/inga-webgpu/wgsl/, with sources.sha256: per kernel the hash of its SPIR-V, constants and the script) and tools/build-wgsl.sh --check runs in spv.yml next to the SPIR-V check, so a shader change without the WGSL generated again fails CI.
  • Reading results back without blocking. WebGPU maps a buffer asynchronously and a browser runs the mapping’s callback only after the calling code has returned to the event loop; the engine’s decode loop is synchronous, and nothing can wait inside it (JSPI is not in Safari; Atomics.wait would block the very event loop the mapping needs). So a step runs again: with deferred reads (always in the browser), a read whose result is not known yet submits the work recorded so far, starts the mapping and fails; the device counts its operations, the forward pass rolls the cache back as for any error, the page awaits the mapping (model.ready()), and the same step runs again from its start: the operations up to the last read already done are skipped (their work is on the GPU), each read already done returns its result again, and the step goes on to the next read. A decode step has two reads (the hidden state after the layers, the logits after the output layer), so three runs; the CPU’s share (the embedding, the final norm) runs again each time, the GPU’s work once. The step is one token: Runner::begin / step in inga-wasm call Session::generate for one token at a time (the KV cache keeps the conversation), each token’s id read from its log-probability record, its text decoded by whole characters and split into reasoning and answer as the CPU path does. Natively the same deferred mode is tested (WebGpu::set_deferred, finish_pending), and without it reads wait as usual.
  • Submissions. The dispatches of a step go into one compute pass; a write (the hidden state going in) submits what is recorded first, since WebGPU’s writes run before the commands of the next submission; a read submits too. A decode step is three to four submissions, not §3.3’s one.
  • Large weights. The device is created with the adapter’s own limits (maxBufferSize, maxStorageBufferBindingSize, …). A weight larger than one binding is split into buffers of whole rows, each but the last a multiple of 64 rows (its share of the output then starts at a 256-byte offset, as WebGPU requires); a product with one token runs on each part (decode, and the output layer, which is the only matrix that large in the models above). Tested with a binding limited to 64 KiB.
  • Weights straight from the stream into GPU buffers (question 2): inga_formats::GgufStream::route sends the tensors a TensorSink wants to it chunk by chunk instead of keeping them; inga_webgpu::GpuSink writes them into their GPU buffers (whole 32-bit words: the bytes that do not make one wait for the next chunk), and the model’s Weights for them are Storage::Elsewhere (a new variant in inga-core: their size, no bytes; Storage::len). upload_weight finds them by name. The browser build routes the layers’ matrices and output.weight; the token embeddings, the norms and the other vectors stay in WebAssembly memory (the CPU looks tokens up there; a tied output layer is uploaded from them as well). Since the weights are gone from the CPU side, a model whose layers cannot run on the GPU (§ below) fails with a message to load it on the CPU; there is no fallback after the fact.
  • Placement. Every layer and the output layer go on the GPU (GpuStages::new(0..n) .with_head); a partial split is not offered (the CPU would need the weights the stream sent away).

What runs where. On the GPU: the layers of the plain attention models GpuStages takes (tested: Llama, Qwen2, Qwen3, Gemma 2, Gemma 3: norms, RoPE, the f16 KV cache, attention with windows / soft-capping / sinks, SwiGLU / GeGLU, gated attention), all the weight types above, and the output layer; prompts through the tiled products for Q4_0 / Q8_0 / Q4_K / Q6_K and eight tokens at a time through the matrix-vector kernels for the others. On the CPU: tokenizer, chat template, the token embeddings, the final norm, sampling. Not on the GPU (reported as Error::Unsupported when a model needs them): DeltaNet and Mamba-2 layers, grouped expert products, sampling on the device, CUDA-style graphs, reading the KV cache back (the prefix cache, --kv-disk). Parity: crates/inga-webgpu/tests/layers.rs runs synthetic Llama, Qwen2, Qwen3, Gemma 2 and Gemma 3 models in F32, F16, Q8_0, Q4_K and Q6_K through three layers and the output layer, prompts and single tokens, with immediate and deferred reads, against the CPU’s logits within the Vulkan tests’ tolerances and with the same top token at every step; weights streamed and weights split give the CPU’s logits too.

The page (web/, small changes): Settings → Device: CPU (the default) or GPU (WebGPU, experimental), disabled with the reason when navigator.gpu is missing; GPU info shows the adapter (vendor, architecture, device, description) and its maxBufferSize, maxStorageBufferBindingSize, maxComputeWorkgroupStorageSize, maxStorageBuffersPerShaderStage, shader-f16 and subgroups, read in the page itself; after a load and after each answer the page shows the WebAssembly memory and the GPU’s bytes (weights, and the other buffers made: KV cache, activations). No binding limit, split weight or missing kernel failed: on lavapipe, whose binding limit is 128 MiB, the 4B shape and the Llama-3.2-1B shape ran whole. It was memory. Now:

  • A device takes the first layers that fit its budget: each layer’s matrices, norms and f16 KV cache, plus its activations (device_scratch_bytes: a session’s buffers for 1 to 8 rows and the powers of two up to the prompt chunk, the quantized inputs, the output layer’s logits), and the output layer when it holds every layer. The rest is split on the CPU as §8.7 splits a model (embeddings by row, the output layer in parts, the last layers read at every token), its KV cache only the CPU layers’. The GPU’s bytes count against “Memory for the model” with WebAssembly memory: fewer layers go to the GPU when the CPU’s share would not fit what is left; when nothing fits the model is refused before any weight is read, as on the CPU.
  • The GPU’s tensors go from OPFS straight into GPU buffers, 8 MB at a time (StreamChoice::device, read_model’s sink, Storage::Elsewhere); a tied output layer is uploaded from the token embeddings, read in pieces when they are read by row (upload_weight through Storage::read).
  • The load line names the split and why the GPU holds no more (gpu_note: its budget, the limit, a layer kind it does not run, a weight type without a kernel). A model kind the GPU stages do not take (gpu_runs: mixtures of experts, MLA, DeltaNet, Mamba-2, short convolutions, Gemma 4, the streamed architectures) gets no GPU layer and runs on the CPU; a model refused when its layers are set up loads again on the CPU, the reason on the load line. A draft model drafts on the CPU only.

Measured on lavapipe with tools/bench_model.py’s Qwen3-4B Q4_K_M shape (2.62 GB): with a GPU budget of 1024 MB and a limit of 1600 MB, 13 of 36 layers on the GPU (the 14th would take 1065 MiB), 20 read from the file at every token, 1.55 GiB planned (1.0 GiB of it the GPU’s); 0.37 tok/s (lavapipe and the scalar kernels, no meaning for a phone). Tests: LayerSplit::plan_device; on lavapipe, a six-layer model for nine GPU budgets and eight limits (the CPU’s greedy tokens, F32 weights; every limit kept, the GPU holding no more than planned, gpu_note given), a Gemma 4 E shape at 1600 MB / 1 GiB in proportion (the CPU, within the limit); in Chromium on SwiftShader, the page splitting a model between the GPU and the CPU.

The GPU’s optimizations (§8.8’s next steps), each switchable for measurements (WebGpu::set_head_in_stage, set_quantize_once, set_reuse, set_sampling; Gpu.tune("head,qonce,reuse,sampling") in JavaScript; off= in the native example and browser.cjs bench-gpu):

  • One read per step. A stage holding every layer and the output layer runs the final norm and the output layer in the layers’ pass (RemoteLayers::forward_head, GpuOps::runs_head_in_stage, copy_from): only the logits come back, or the token. A prompt reads nothing but its last token’s logits (before: the hidden state of every chunk, then the logits). A step runs twice in the browser instead of three times for a token, and instead of chunks + 2 times for a prompt.
  • No replayed work but bookkeeping. The design keeps one deferred read per step: its second run skips every GPU operation and repeats the CPU’s embedding row and the session’s bookkeeping. Measured natively on lavapipe (Qwen3-0.6B Q8_0 shape, 46 prompt tokens and 16 answer tokens): the second runs took 37 ms for 16 steps (2.3 ms each), against 65 ms for 34 before (1.9 ms each). A state machine resuming after ready() would save those milliseconds but split the session’s generation; not done.
  • Bind groups reused. A dispatch’s bind group is kept by kernel, buffers, offsets and parameter slot, and used again by the next token’s same dispatch; the cache is emptied when a buffer is freed (a bind group keeps its buffers alive). other_bytes now counts freed buffers out.
  • Inputs quantized once (#624’s method on WebGPU): quantize_input / matvec_input, the same kernels so the same bits.
  • Sampling on the GPU. The Vulkan sampler (sample_prep, sample_top_k, sample_draw) translated by build-wgsl.sh: sample_draw computes Philox’s 64-bit products from 16-bit halves (WGSL has no umulExtended) and frexp from the bits; sample_top_k reads its workgroup’s id once at the start (the translation reads it through a barrier, which must not sit in its loops). The same tokens as the CPU’s sampler (greedy, top-k / top-p / min-p, penalties, Gemma’s soft-capping), on lavapipe for WebGPU and for Vulkan. The browser’s steps generate one token per call, whose first token comes from the prompt’s logits, so the page did not draw on the GPU; the native decode loop did. Now it does (“The page’s draws on the GPU”).
  • A split weight runs prompts (it returned Unsupported): one piece at a time into a buffer of its rows, copied into each token’s columns.
  • Not done then: shader-f16, tiles and workgroup sizes for Apple. The quantized kernels read 8-bit activations (quantize_q8_1), so f16 would only touch the attention and F16 / F32 weights; the kernels’ workgroup storage is at most 14 KiB (the tiled products), under Apple’s 32 KiB. Either change needs the phone to measure: the software renderers here cannot rank them. Built since, with switches and a benchmark button for the phone (next section).

Numbers on lavapipe (native example, Qwen3-0.6B Q8_0 shape, 181 prompt tokens, 16 answer tokens, two runs each, tok/s prompt / answer): before (all off) 5.35 / 0.756 and 6.24 / 0.752; inputs quantized once 6.49 / 0.741 and 6.58 / 0.764; and bind groups reused 6.08 / 0.738 and 6.50 / 0.790; and one read per step 7.23 / 0.826 and 6.37 / 0.734. Within lavapipe’s noise (about 10 %): it runs on this machine’s CPU, waits nowhere for an event loop, and makes bind groups cheaply. The page’s draws on the GPU, shader-f16 and kernels for Apple GPUs (2026-10-15)

Section titled “The page’s draws on the GPU, shader-f16 and kernels for Apple GPUs (2026-10-15)”

Same branch. Four changes, for the phone to measure; tested on lavapipe (natively) and on SwiftShader (headless Chromium) only, which cannot rank kernels: both run on this machine’s CPU, and SwiftShader offers no shader-f16 here.

The page’s tokens drawn on the GPU. The page’s steps call Session::generate for one token, so each token was the prompt’s first token, drawn by the CPU from logits read back (600 KiB for Qwen3’s 151,936 tokens, 1 MiB for Gemma’s 262,144). Now the session draws a prompt’s first token where the output layer runs, as the decode loop draws the others: prefill takes a DeviceDraw for its last pass (Model::forward_sampled; the position after the prompt, the prompt as the penalties’ history) when the sampler’s settings allow it (SamplerCfg::device_sampling) and nothing else needs the logits (no grammar, log-probabilities, batcher or reasoning budget; no drafter reading hidden states). The token goes to the loop’s queue as a device-drawn token does, and counts in GenStats::device_sampled. Natively it saves the first token’s logits too (CUDA, Vulkan, WebGPU). The page learnt each step’s token from its log-probability record, which turned the device’s draw off; it now reads Session::generated (the ids the last generation emitted). What the GPU sampler does not do falls back to the CPU from the logits: logit bias, DRY, XTC, mirostat, typical-p, top-n-sigma, top-k above 128, grammar and log-probabilities. With every layer and the output layer on the GPU a step reads back 4 bytes; with layers split between the GPU and the CPU the output layer is the CPU’s and so is the draw. answer_stats gains gpu_sampled; the page’s stats line says “N drawn on the GPU”.

Running the sampler in the browser found that Chromium had never compiled it (the page never dispatched it): Tint refused sample_prep and sample_draw (+infinity as a constant, bitcast<f32>(0x7f800000)) and sample_top_k (a barrier after a branch on the radix select’s state, read from workgroup memory). build-wgsl.sh now reads +inf from a private variable as it does -inf, and reads radix_state through workgroupUniformLoad (each read a barrier, at points where every invocation is already in step). Same draws: the_gpu_draws_the_tokens_the_cpu_draws_from_its_logits runs the page’s steps on lavapipe with the GPU’s sampler on and off (off: the same GPU’s logits read back, drawn by the CPU’s sampler) for greedy, top-k 3 / 40 / 128 with top-p and min-p, and a repetition penalty: the same text, every token drawn on the GPU, and none with a logit bias (the CPU’s fallback, the same text again). shader-f16. WebGpu::new asks for shader-f16 where the adapter has it (GpuInfo::shader_f16, on the “GPU info” line) and then runs f16 builds where they apply; the f32 kernels stay, for adapters without it and for f16=off. The variants are generated by build-wgsl.sh from the GLSL, not written by hand: a source NAME+DEFINES is compiled by glslangValidator with those defines (here SHADER_F16), then goes through the same steps; naga writes enable f16;, which the script moves before the private variables it adds. --check hashes their GLSL (every header and the .comp) instead of a SPIR-V file. The SHADER_F16 branches in attention.comp and matvec_f16.glsl change no Vulkan build: the SPIR-V is byte for byte the same (only spv/sources.sha256 changes, as it hashes the headers).

  • attention_h16: the f16 KV cache read as f16 values, a key’s two at a time (f16vec2), the values one at a time, instead of 32-bit words unpacked; the sums stay f32, in the same order. Used when the head size is even.
  • matvec_f16_h16 / _1: F16 weights read natively, four at a time, instead of unpackHalf2x16; the products and sums stay f32.
  • f16 arithmetic is not used. Tried in matvec_f16_h16 (f16 products of 4 summed in f16, accumulated in f32): the F16 Llama shape’s logits were off by 1.97e-3 for a largest logit of 1.74 (1.1e-3 relative), over the 1e-3 the Vulkan tests allow for F16; reverted. The quantized kernels gain nothing from f16: their inner products are integer (activations quantized to 8 bits), and their scales are a few multiplies per block. The KV cache store keeps its own f16 rounding (f16_bits, the CPU’s bits): a native f16 conversion’s rounding is not specified the same way.

The i-quants on the GPU, a load that cannot hang, Markdown (2026-10-15)

Section titled “The i-quants on the GPU, a load that cannot hang, Markdown (2026-10-15)”

From the real devices: on the P1000, Gemma 4 E4B IQ2_M with Device GPU loaded on the CPU (GPU layers 0 of 42) at 0.55 tok/s; on the iPhone 16 Pro the same with Device GPU (or Auto) stayed on “Loading” for ever, where 22fb2e2 loaded it on the CPU at 1.3 tok/s.

The i-quants with grids (IQ1_S, IQ1_M, IQ2_XXS, IQ2_XS, IQ2_S, IQ3_XXS, IQ3_S): the Vulkan and WebGPU kernels read IQ4_NL and IQ4_XS only. Each now has a matrix-vector shader in the Vulkan GLSL (matvec_iq*.glsl on matvec_b256.glsl: lane k of a block’s eight takes values 32k..32k+32 as two halves of 16 signed 8-bit values and their scales), built three ways (.comp, _sg, _dot) and translated to WGSL (matvec_iq* and _1). ggml’s grids (iq_tables) are one buffer of 8448 words, bound fifth (matvec_iq_grid.glsl, inga_quant::iq_tables::gpu_grids and GPU_GRID_AT, a test checks both agree): GLSL constant arrays come out of naga as a copy of the whole array into a function variable at every read, and five storage buffers stay within the six every kernel keeps to. The signs are applied four bytes at a time (signed4: the grid values are 1..127); IQ1_S’s and IQ1_M’s shift of +-1/8 is folded into the values, read as 8 * grid +- 1 with the scale divided by 8 (exact in 8 bits). Prompts take the same kernels eight tokens at a time (matmul falls back to them: no tiles for these types). Tested: matvec_matches_the_dequantized_weights (inga-vulkan, every build lavapipe runs; a swapped kernel fails it), i_quants_match_the_dequantized_weights (inga-webgpu, the WGSL through wgpu’s Vulkan backend: Gemma 4 E4B’s width 2560 and 6912, 1, 8 and 12 tokens), i_quant_layers_give_the_cpus_logits (a Llama-shaped model of IQ2_XXS, IQ2_S, IQ3_XXS, IQ3_S: the CPU’s logits within 2 %, the same greedy tokens; seed 11, as seeds 42 and 7 of IQ3_S have near ties at the top that the activations’ blocks of 32 here and 256 on the CPU part), Chromium compiling every kernel. No real GPU has run them; their speed is not measured.

Gemma 4 E4B stays on the CPU all the same: gpu_runs refuses Gemma 4’s layers in the browser (per-layer embeddings, shared caches; W5) before their types are looked at, which is what the P1000’s 0 of 42 was. the_gpu_plan_reads_the_layers_types_from_the_header checks it on a Gemma 4 E-shaped model of IQ2_S: no layer for its kind, every layer’s tensors taken by the kernels once the kind is set aside. A Llama- or Qwen-shaped IQ2_M model now plans its layers on the GPU.

A load that cannot hang. With Device GPU the worker opened the GPU and ran openModelGpu, which loaded a model the GPU runs none of on the CPU beside the GPU device; on iOS a worker that passes the tab’s memory is ended without an error event, and the page waited. Now:

  • before the GPU is opened, gpuPlan (inga_wasm::gpu_layers, Engine::device_layers: the layers’ kind and their tensors’ types and shapes from the header, inga_webgpu::kernels_take) says how many of the first layers the GPU could run; with none, the model loads on the CPU at once and the load line says why (“the GPU would run none of its layers (…), so it was not opened”);
  • when the GPU refuses the model while it loads, the worker frees the model, destroys the device (Gpu.destroy, WebGpu::destroy) and posts retry: the page starts a fresh worker (an empty WebAssembly memory, which never shrinks) that loads it on the CPU with the reason; a model loaded with no layer on the GPU (its budget) drops the device too;
  • the page watches a load: the worker’s error and messageerror events, or 45 s with no message (progress comes every 8 MiB), end it with “The browser stopped the model’s worker (probably memory …); try Device CPU or a lower limit”, and a new worker starts (?watchdog_ms=N shortens it for the tests).

Device Auto on iOS keeps a model that needs storage on the CPU (unchanged), and Device GPU there keeps the 1024 MB GPU budget within the one limit of 1600 MB. Whether the iPhone loads Gemma 4 E4B again (on the CPU, from the header’s answer, the GPU never opened) is to be checked there. The Standard test’s line ends with fallback: ... (the load’s note, or the plan’s reason) when the CPU ran a model the GPU was asked for.

Subgroups in the browser, kernel times, the load log (2026-10-15)

Section titled “Subgroups in the browser, kernel times, the load log (2026-10-15)”

From the P1000 (Chrome on Windows, Qwen3-4B Q4_K_M all on the GPU): the benchmark’s subgroup rows said “no 32-wide subgroups on this adapter” with no widths, while the GPU info line (the page’s own adapter.features) listed subgroups; Qwen3-4B decoded at about 5.6 tok/s, about 15 GB/s of weights on a card of about 80 GB/s (Llama 3.2 1B: about 28 GB/s), and the tiles and rows variants changed nothing (prompt 32.4 / 32.3 / 32.0, answer 5.5 / 5.6 / 5.7 tok/s).

Why the subgroups never ran. wgpu 30’s WebGPU backend maps 16 WebGPU features to its own (FEATURES_MAPPING in backend/webgpu.rs) and subgroups is not one of them: adapter.features() never has SUBGROUP in a browser, and a device asked for with it is made without it (the request lists only the mapped features). The adapter’s widths do come through (GPUAdapterInfo.subgroupMinSize / subgroupMaxSize, Chrome 134 on). The worker now wraps GPUAdapter.prototype.requestDevice before the module makes its device (requestSubgroups): every request gets subgroups where the adapter has it. The module reads the device’s own features (Device::as_webgpu, GPUDevice.features) for GpuInfo::subgroups. The WGSL already gets enable subgroups; in a browser (kernels::for_device).

Any width. The _sg kernels take a segment of 32 lanes for one subgroup: right only where every subgroup is 32 wide. Chrome reports what the driver allows, not what it picks: on D3D12, Dawn reports WaveLaneCountMin to 128 (32 to 128 on NVIDIA), on Vulkan the driver’s range (AMD 32 to 64, Intel 8 to 32), SwiftShader 4, lavapipe 8. So the _sg kernels would still not run on the P1000. New builds, matvec_*_sgx and _sgx_1 (F16, F32, Q8_0, Q4_0, Q4_K, Q6_K; WEBGPU_ANY_SUBGROUP in matvec.glsl‘s store_rows), work for any width WebGPU allows (powers of two from 4 to 128), read in the kernel (subgroup_size). Each lane adds the lanes at distances 16, 8, 4, 2 and 1 with subgroupShuffleXor, the result kept only where the distance is under the width (a select, so every shuffle runs in uniform control flow). That sums the segment where the width is 32 or more, and the subgroup where it is narrower. The narrower subgroups’ first lanes then write their sums to shared memory (8 x 64 floats); after a barrier the segment’s first lane adds its 32 / width of them; a second barrier keeps Q4_K’s second row from overwriting them. Both builds assume that a subgroup is made of consecutive invocations, as every driver lays out a workgroup of one dimension; WGSL does not promise it. The device picks (GpuInfo::subgroup_kernels, SubgroupKernels): _sg where the adapter reports exactly 32 to 32, _sgx for any other range within 4 to 128, or none told, and none without subgroups. Correctness comes first: the shuffles and barriers of _sgx are not free, and the shared-memory build stays the default (sg=off). The GPU benchmark’s subgroup rows run whichever build applies, the row saying which. Generated by build-wgsl.sh; the Vulkan SPIR-V is byte for byte the same (only spv/sources.sha256 changes). 24 subgroup kernels now (105 in all).

Checked: naga validates them (and refuses them without its subgroup capability). Chromium (Tint) compiles all 105 on SwiftShader, whose subgroups are 4 wide: the benchmark’s two subgroup rows run _sgx and give the first row’s greedy text. lavapipe (8 wide) runs _sgx in every_tuning_gives_the_cpus_logits (sg=on, f16 on and off) with the CPU’s logits. No device here has 32-wide subgroups, so _sg has still run nowhere. The module grew to 7.01 MB (1.86 MB gzipped).

What the page shows. The GPU info line says shader-f16, subgroups (yes with the widths, “widths not told”, or no; the older minSubgroupSize limits where GPUAdapterInfo has no widths) and timestamp-query. The benchmark’s header says the device’s subgroups, their widths and which kernels run with them, and timestamp-query. GpuInfo::line has both too.

Kernel times (“Kernel times” beside “GPU benchmark”; WebGpu::start_profiling, profile, profile_in_flight, profile_mode; Gpu.profileStart, profile, profileInFlight). A warm-up run, then the benchmark’s prompt with the page’s kernels: the prompt’s step is not timed, every later step is (steps: each commit, so a step that ends the answer counts too). Every dispatch is tagged with what it computes. A product is tagged “matvec Q4_K attn_q 2560x4096”, or “output layer (matvec Q6_K 2560x151936)” for output.weight or tied token_embd.weight, with its weight’s bytes (each piece’s buffer). The other kernels are tagged by name: attention, rms_norm, rope, add, swiglu, kv_store, quantize_q8_1, sample_prep / top_k / draw. Two ways:

  • timestamps where the device has timestamp-query, which wgpu does map and now requests: each dispatch in a compute pass of its own, with timestamps at its beginning and end (a query set of 4096, flushed when full), resolved and copied with the submission and read back once mapped, never waited for. Chrome quantizes the timestamps (to 100 µs unless its WebGPU developer features are on). The sums over many dispatches stay right on average; single short dispatches do not.
  • fences otherwise: each dispatch is submitted alone with a 4-byte copy to a buffer that is then mapped. Its time runs from the submission to the mapping’s callback, less the median of 15 empty round trips measured at the start. Natively it waits at once. In the browser it is a read of the step: the step runs again up to the next dispatch, so a token takes as many runs as it has dispatches. Coarse.

The page’s table: kernel, build, calls per token, ms per token, share of all kernels, and GB/s for the products (weight bytes / their time), then a line for all kernels with the products’ GB/s. The caption gives the mode, the subgroups, and the profiled steps’ wall time, which timing slows (one pass, or one submission, per dispatch): the benchmark’s answer tok/s stays the real speed. Natively, on wgpu’s Vulkan backend (lavapipe), kernel_times_name_every_kernel_and_keep_the_logits times two decode steps with fences (direct, and through the deferred reads as in the browser), with timestamps, and with auto deferred. It checks each product’s calls and bytes, attention, the norms and the output layer, the steps counted, and the logits the CPU’s. In Chromium (SwiftShader: timestamp-query yes) the_page_benchmarks_the_gpu presses the button and checks the table: two calls per token of each layer’s products for the model’s two layers, one of the output layer, GB/s for the products, the shares adding to 100 %. The P1000’s own split (which products, at what GB/s, how much attention and the sampler take) is for the device to tell: press Kernel times there. Inga’s own Vulkan backend (inga bench) has no such table yet.

The load log. The worker posts a step for each stage of a load: the module, the GPU check of the header, the device, the model file, the weights, the model handed to the page. The page lists them with their times under the status line, from “load asked” to its own “ready to chat”. onMessage is wrapped: an error of the page while it handles a message is logged and shown, the page no longer busy. The browser test checks that the log of each chat ends with “ready to chat”. The load watchdog stopped at the loaded message, so a worker that Safari ends silently during the first answer left the page waiting with no word. With no message for 60 s during an answer (?quiet_ms=N), the page now says the worker may have been stopped, and logs it; it does not end the worker, since a long prompt on a phone’s CPU may take that long. The iPhone’s hang after a load (v13: Qwen3-0.6B too, CPU or GPU, page responsive, no watchdog message) was not found in the code. Two candidates are now visible: a throw in the loaded handler (which would leave exactly that state, now caught and shown) and a worker ended during the answer (now said after 60 s). The load log on the iPhone will tell which.
