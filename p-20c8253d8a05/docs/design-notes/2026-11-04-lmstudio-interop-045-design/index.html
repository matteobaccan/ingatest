Coming from LM Studio: its MCP servers, its chats, its REST API v1

Status: proposed on 2026-11-04; moved to the backlog by the maintainer on 2026-11-05 (“troppo lavoro per importare poca roba, la riragioniamo più avanti”), to be proposed again for 0.50.0; nothing in it is built. The three LM Studio items the maintainer decided on 2026-11-04 for 0.45.0 (all High) in docs/todo/0.45.0.md: LM Studio’s MCP servers offered in the web UI (§2), LM Studio’s chats offered for import (§3), LM Studio’s REST API v1 beside today’s /api/v0 (§4). One spec because the three share what finds LM Studio on the machine (§1), the privacy rules (§5) and the tests’ fixtures (§6).

What is verified and what is not. Read on 2026-11-04:

  • LM Studio’s documentation from its source, lmstudio-ai/docs at commit 8c7159b (2026-10-20): the MCP pages (0_app/2_mcp/), the chat page (0_app/1_basics/chat.md), the v1 REST pages (1_developer/2_rest/), MCP via the API (1_developer/0_core/mcp.mdx), authentication and the server’s settings (1_developer/0_core/), the API changelog. lmstudio.ai itself could not be reached from the session that wrote this spec (the network allowed GitHub only); the repository is what the site is built from.
  • lmstudio-python (lmstudio-ai/lmstudio-python, MIT) at commit 1679683 (2025-10-27): how the SDK reaches LM Studio, its token format, its chat-history schema (sdk-schema/lms.json).
  • Inga’s code on exp/0.44 at c0e85ad.

Not verified (marked ❓ where used): the inside of LM Studio’s conversation files (no real file was read, and LM Studio’s own page says “It is NOT recommended to edit them manually, nor to rely on their structure”), where LM Studio keeps the pictures attached to a chat, a pointer file that moves LM Studio’s home folder, the permissions an LM Studio API token can carry (the documentation shows them only in screenshots), the error body of a non-streamed v1 request. Every estimate is labelled so.

1. Finding LM Studio on this machine

Section titled “1. Finding LM Studio on this machine”

Today crates/inga-hub/src/local.rs finds LM Studio’s models folder (lmstudio_dir: LMSTUDIO_MODELS, else downloadsFolder of ~/.lmstudio/settings.json or of the older ~/.cache/lm-studio/.internal/app-settings.json, else ~/.lmstudio/models, else ~/.cache/lm-studio/models). The models folder can be anywhere (downloadsFolder); mcp.json and the conversations are in LM Studio’s home folder, so a second function is added beside it:

What macOS and Linux Windows Source
LM Studio’s home ~/.lmstudio/ %USERPROFILE%\.lmstudio\ the docs (conversations, presets, models pages)
Before 0.3 ~/.cache/lm-studio/ %USERPROFILE%\.cache\lm-studio\ Inga’s local.rs (models); for mcp.json ❓ (MCP came with 0.3.17)
MCP servers <home>/mcp.json <home>\mcp.json the todo’s path; the docs say only “the app’s mcp.json”, edited in the app (Program tab, Install, Edit mcp.json) ❓
Conversations <home>/conversations/ <home>\conversations\ the docs, 0_app/1_basics/chat.md
One chat <id>.conversation.json, <id> 13 digits same a third-party plugin’s documentation found by a web search (not read in full) ❓
Folders of chats sub-folders of conversations/ ❓ same the docs say chats are managed “in folders”; how on disk ❓
A chat’s pictures <home>/user-files/ ❓ same from memory, to be read on a real install
  • INGA_LMSTUDIO_HOME exists for the tests and for a moved home; it is read the way LMSTUDIO_MODELS is. A pointer file that moves LM Studio’s home (a ~/.lmstudio-home-pointer holding the path) is remembered from LM Studio’s forums, not seen ❓: C0 (§3.1) checks it on a real install; if it exists, lmstudio_home reads it first.
  • Finding a folder is a stat: no file is opened before the user asks (§5).

2. LM Studio’s MCP servers on the MCP page

Section titled “2. LM Studio’s MCP servers on the MCP page”

2.1 What LM Studio’s mcp.json holds

Section titled “2.1 What LM Studio’s mcp.json holds”

LM Studio “follows Cursor’s mcp.json notation” (0_app/2_mcp/index.mdx): the mcpServers object Inga already reads (crates/inga-mcp/src/config.rs: “in the format Claude Desktop and LM Studio read”), each server either a program (command, args, env) or a URL (url, headers), type as Cursor and VS Code write it. The documentation’s example is a URL with a token in a header:

LM Studio’s “Add to LM Studio” links (lmstudio://add_mcp?name=NAME&config=BASE64) add one entry of this shape. LM Studio-only keys, if any, are not documented ❓; Inga’s parser ignores keys it does not know, so they do no harm.

2.2 What the user sees

Section titled “2.2 What the user sees”

On the MCP page (webui/js/mcp.js), above the servers, when LM Studio’s mcp.json exists on the server’s machine and the user has not dismissed the card:

LM Studio’s MCP servers — LM Studio keeps MCP servers in ~/.lmstudio/mcp.json. Inga can add them to its own list (~/.cache/inga/mcp.json): you choose each one, and nothing is started. Show them · Not now

  • Show them reads the file (only now, §5) and lists every server as a card:
    • its name, how it is reached (stdio, http, sse), and the command line in full (npx -y @playwright/mcp@latest, each argument quoted as ServerSpec::target quotes it) or the URL, the working folder;
    • the names of its variables and headers, never their values (“Variables (values not shown): GITHUB_TOKEN”);
    • a warning when a value is still a placeholder (<YOUR_HF_TOKEN>, a value that is <...> or empty): “the header Authorization still holds a placeholder: edit mcp.json after the import”;
    • its state against Inga’s file: new; already in Inga (same name, same entry: nothing to do); name taken (same name, another entry: left as it is, the todo’s rule; the card shows both command lines so the user sees why); not readable (the entry Inga’s parser refuses, with the parser’s message);
    • for a new server, a checkbox, off by default; the dialog’s Add the chosen servers asks once more for the programs among them (“These programs will be listed in Inga’s mcp.json. They run with your permissions when you approve them and use them; nothing runs now:” and each command line).
  • After the import the card says “2 servers added, 1 already in Inga, 1 name taken (not changed)”; the new servers appear in the page’s list as any other: a program not approved (“Approve this command”, the existing button and its confirmation in mcp.approve.confirm), and without --allow-mcp-commands the existing reason (“programs are not allowed on this server”). The import never approves a command, never connects a server, never calls a tool.
  • Not now hides the card for this profile (kv/lmstudio.mcp.dismissed, §1.1 of the profile spec); the card comes back when LM Studio’s file changes (its size and time kept with the dismissal) or from a “Look for LM Studio’s servers” link under the list.
  • inga mcp import-lmstudio [--yes NAME...] [--dry-run] does the same in the terminal: the table of servers and states, then asks for each new one (y / n), --dry-run writes nothing.

2.3 What is written

Section titled “2.3 What is written”
  • Into the file the server’s MCP host reads (Host::file(): --mcp FILE, else ~/.cache/inga/mcp.json), created when missing. The chosen entries are copied as LM Studio wrote them (their JSON object, keys Inga ignores included: LM Studio may read them if the user points it at this file one day), under their own names; the rest of Inga’s file is kept, key order included (serde_json’s preserve_order is on in the workspace’s Cargo.toml).
  • Before writing, the whole new file is parsed with Config::parse; a file Inga could not read is not written. Written to mcp.json.tmp, then renamed over the old one; the old one is kept once as mcp.json.bak (the last import’s); owner-only (0600) on Unix as mcp-approvals.json is, the user’s own profile folder on Windows.
  • Inga’s MCP host reads mcp.json once, at start (Host::new in crates/inga-mcp/src/host.rs). So the import needs Host::reload(config): the servers of the new file are compared with the running ones by name; a removed or changed server is disconnected (its process stopped), an unchanged one keeps its connection, a new one starts Idle (or Off with its reason). McpTools holds the host behind a lock so a reload does not cross a running call (the call finishes on the old slot). Without the reload (if the maintainer prefers, open question 2) the card says “restart the server to use them”.

2.4 The API

Section titled “2.4 The API”

Admin routes (/api/inga/*), in docs/api/inga.yaml (tag mcp):

Route What
GET /api/inga/mcp/lmstudio without opening the file: {"found": true, "file": "/home/u/.lmstudio/mcp.json", "bytes": 812, "modified": 1730700000}, found: false and the folders looked in otherwise
GET /api/inga/mcp/lmstudio?read=1 the file read: {"file", "servers": [{"name", "transport", "target", "command", "args", "env": [names], "url", "headers": [names], "cwd", "state": "new" | "same" | "taken" | "invalid", "reason", "placeholders": [names], "inga": {...}}]} (inga: Inga’s entry of that name, as GET /api/inga/mcp shows it, when taken)
POST /api/inga/mcp/lmstudio/import {"servers": ["playwright", "github"]}: {"added": [...], "same": [...], "taken": [...], "invalid": [{"name", "reason"}], "file"}, then the page reads GET /api/inga/mcp again; a name not new is reported, never written

The values of env and headers never leave the server (as ServerSpec::to_json today); the import reads them from LM Studio’s file on the server itself.

The hypothesis, from LM Studio’s SDK (verified: sdk-schema/lms.json’s chatHistoryData, the shape LM Studio’s server and SDKs exchange) and from memory of the files (❓):

What is verified in that shape: a message part is {"type": "text", "text"} or {"type": "file", "name", "identifier", "sizeBytes", "fileType"} with fileType one of image, text/plain, application/pdf, application/word, text/other, unknown, and a file is named by an identifier that LM Studio resolves to a file it keeps. 3.2 What the user sees

Section titled “3.2 What the user sees”
  • When lmstudio_home()/conversations/ exists and holds *.conversation.json files (counted by name, not opened), the chats’ column shows once a card, and the Storage page a line: “LM Studio’s chats were found on this server’s machine (34 chats). Show them · Not now”.
  • Show them opens a dialog that reads the files (now, §5) and lists each chat: its title, date, model, how many messages and pictures, the folder it is in, and a mark: ready, already imported (§3.4), partly (what will be left out, “2 PDF files, 1 tool call”), cannot be read (why). A checkbox per chat, all the ready ones on; a search box; “Select all / none”.
  • Import writes the chosen chats into the server’s profile and says what was done: “31 chats imported (412 messages, 18 pictures); 2 already imported; 1 skipped: 1758816879741.conversation.json is not valid JSON”. The same report is kept in the server’s log (inga serve’s terminal) with the file names, and in the dialog until closed, with Copy the report.
  • An imported chat looks like any other, with a small “from LM Studio” mark in its menu’s details (the import field, §3.3); deleting it in Inga deletes nothing in LM Studio. LM Studio’s files are never changed or deleted.
  • inga chats import-lmstudio [--dry-run] [--all | ID...] does the same in the terminal, into the profile of --home (no server needed).

3.4 Duplicates and a second import

Section titled “3.4 Duplicates and a second import”
  • A chat whose lms-<digits> id is already in the profile is already imported: skipped, whatever its content, unless LM Studio’s file changed since (its sha256 differs): then it is offered as changed in LM Studio and, when chosen, imported as a new chat lms-<digits>-2 titled “… (LM Studio, 4 Nov)”, the first copy kept (the user may have continued it in Inga).   • A chat imported, then deleted in Inga, is offered again as ready.

4.2 Where they go in Inga

Section titled “4.2 Where they go in Inga”
  • crates/inga-server/src/lmstudio.rs answers /api/v0/* today; v1 goes beside it as lmstudio_v1.rs (chat, models, load), sharing quantization, model_info and the API nodes’ listing with v0.
  • The KoboldAI family owns /api/v1/* today (families.rs: ("* /api/v1/*", "kobold", &[]); lib.rs sends every other GET /api/v1/... to kobold::info, a 404 there). The paths do not collide (Kobold’s are /api/v1/model, /api/v1/generate, /api/v1/info/version, /api/v1/config/*; LM Studio’s /api/v1/chat and /api/v1/models[/...]), so LM Studio’s are named before Kobold’s wildcard in ROUTES (* /api/v1/chat, * /api/v1/models, * /api/v1/models/* → lmstudio), and lmstudio::route already runs before the big match. --like lmstudio (port 1234, families lmstudio and openai) serves them; --like kobold does not; requests::family names them lmstudio in the log.
  • Keys: GET /api/v1/models is a model list (is_model_list: only the key’s models) and POST /api/v1/chat a chat route; load, unload and download are admin (as Ollama’s /api/pull is, keys::group). LM Studio’s tokens look like sk-lm-XXXXXXXX:YYYYYYYYYYYYYYYYYYYY (lmstudio-python’s _LMS_API_TOKEN_REGEX, verified) and are sent as Authorization: Bearer; Inga takes any key string, so an LM Studio token can be put in Inga’s keys file as it is and clients keep their LM_API_TOKEN.
  • LM Studio’s permission keys: a token is created with “the desired permissions” (authentication.mdx); which permissions exist is shown only in screenshots ❓. Inga’s named keys already restrict by route group (chat, admin) and by model (models), which covers “this token may chat with these models” and “this token may load and unload”. The one LM Studio permission Inga has no group for is “use the servers of mcp.json” (its setting “Allow calling servers from mcp.json”, which needs authentication on): proposed, a third group mcp for named keys, needed by a request whose integrations name a server of mcp.json (§4.6); open question 8.

4.3 GET /api/v1/models

Section titled “4.3 GET /api/v1/models”

The same models as GET /api/v0/models (the router’s, then the API nodes’), in v1’s shape:

  • type: llm, or embedding for an embedding model; Inga’s image, video and speech models are not listed (LM Studio has no type for them).
  • key is Inga’s model id (what model takes everywhere); display_name the file’s general.name, else the file name. quantization.name is quantization() of v0, bits_per_weight the file’s bits per weight (an exact figure where LM Studio rounds; LM Studio’s example shows 4 for Q4_K_M).
  • loaded_instances: one per loaded model, its id the key (Inga has one instance per model; LM Studio’s key:2 never appears); config only what Inga knows (context_length, parallel = the slots); flash_attention, eval_batch_size, num_experts, offload_kv_cache_to_gpu are llama.cpp’s options and left out.
  • format: gguf, mlx for an MLX folder, null for safetensors and API nodes.
  • capabilities.trained_for_tool_use from the chat template (Inga’s modelTools); reasoning from the model’s thinking switch.
  • inga: Inga’s own state and details (as v0’s API nodes carry inga).
  • LM Studio lists every downloaded model, loaded or not; Inga’s v0 lists the router’s. Proposed: the same as v0 (open question 10).

4.4 Load and unload

Section titled “4.4 Load and unload”

POST /api/v1/models/load {"model", "context_length"?, "eval_batch_size"?, "flash_attention"?, "num_experts"?, "offload_kv_cache_to_gpu"?, "echo_load_config"?}: Inga’s /api/inga/load for model (from the router’s models; a path or hf:// reference as /api/inga/load takes them). context_length sets the model’s context for this load (POST /api/inga/ctx’s rule: at most the model’s training context, said in the answer if lowered). The llama.cpp options are accepted and ignored, said so in docs/api/lmstudio.yaml. Answer:

(load_config only with echo_load_config: true.) A model already loaded answers at once with load_time_seconds: 0. Errors: 404 (model_not_found) for an unknown model, 409 when a load is under way, the router’s memory errors as they are.

POST /api/v1/models/unload {"instance_id"}: router.unload; {"instance_id"}, 404 when it is not loaded.

4.6 Stateful chats and MCP

Section titled “4.6 Stateful chats and MCP”
  • The store: a response is kept in memory as the conversation it ends (system prompt, messages, model, the key that made it), under resp_ and 48 random hex digits; previous_response_id continues it (its messages, then the new input), and a new id is answered, so any earlier id is a branch point (LM Studio: “This allows you to branch conversations”). Bounded: at most 1,000 responses or 256 MiB of text, the least recently used dropped (estimates, constants, open question 12); a response is lost at a restart. An id made with another key is a 404, as an unknown one ({"error": {"type": "invalid_request", "message": "no response resp_...", "param": "previous_response_id"}}). store: false keeps nothing and answers no id.
  • The same store can serve /v1/responses’ previous_response_id, refused today (responses.rs): in this item (proposed, small once the store exists) or not, open question 13.
  • integrations: "mcp/NAME" or {"type": "plugin", "id": "mcp/NAME", "allowed_tools": [...]} is the server NAME of Inga’s mcp.json with only those tools; the calls run as an API client’s do today ("inga_mcp": ["NAME"]): only the calls of --mcp-auto-approve and the “always” answers run, any other is refused and the model told why (an API request cannot ask the person). Needs a named key with the mcp group when the server has named keys (§4.2). {"type": "ephemeral_mcp", "server_label", "server_url", "headers", "allowed_tools"}: a server reached by URL for this request only; LM Studio has it behind “Allow per-request MCPs”, off by default; Inga refuses it (not_implemented) unless [api.lmstudio] ephemeral_mcp = true, open question 14. Other plugins (lmstudio/...): 400 plugin_connection_error naming them.

4.7 Streaming

Section titled “4.7 Streaming”

"stream": true: Server-Sent Events with event: names, in LM Studio’s order: chat.start (model_instance_id), model_load.start / .progress / .end when the request loads the model (from the router’s LoadJob, progress 0 to 1), then prompt_processing.start / .progress / .end (from Inga’s prefill progress, prefill.rs), reasoning.start / .delta / .end, tool_call.start / .arguments / .success / .failure, message.start / .delta / .end, error ({"error": {"type", "message", "code"?, "param"?}}, the types LM Studio lists: invalid_request, model_not_found, mcp_connection_error, not_implemented, internal_error, …), and always chat.end with the whole answer of §4.5 as result.

Errors without streaming: the HTTP status and {"error": {"type", "message", "code", "param"}}, the event’s object; LM Studio’s own body for a non-streamed error is not documented ❓ and is checked in A2 against a real LM Studio if the maintainer has one (open question 15); OpenAI’s clients read error.message either way.

4.8 What is not done

Section titled “4.8 What is not done”
  • LM Studio’s SDKs (lmstudio-js, lmstudio-python) do not use the REST API. The todo asks for the routes “tested with LM Studio’s own client libraries … against inga serve --like lmstudio”; lmstudio-python’s source (verified) probes GET /lmstudio-greeting for {"lmstudio": true} on its default ports (41343, 52993, 16141, 39414, 22931, or the host given) and then speaks a WebSocket protocol on ws://HOST/llm, /embedding, /system… (_ws_impl.py, the channels and RPCs of sdk-schema/lms.json); lmstudio-js is the same protocol (the schema is generated from it). Serving the SDKs is a second protocol, much larger than v1 (estimate: L, several weeks), so it is not in this spec: the REST routes are tested with LM Studio’s documented requests (§6), and the SDKs are open question 1.
  • LM Studio’s catalog ids in download (openai/gpt-oss-20b resolved through lmstudio.ai): Inga does not ask lmstudio.ai (A5 takes Hugging Face links and Inga’s references only, and says so).
  • LM Link, LM Studio’s Anthropic routes (Inga has /v1/messages), presets.

5. Security and privacy

Section titled “5. Security and privacy”
  • Nothing leaves the machine. Finding LM Studio is a stat; its files are opened only when the user clicks Show them (or runs the command), on the server’s own disk; they are converted on the server and written into Inga’s files on the same disk. No file and no part of one is sent to any service, any API node, the project, a report (One step from the project’s reports name neither path nor content of an import). The page shows titles and counts before the import, never a chat’s text.
  • The routes that read LM Studio’s files are admin routes; on a server without keys that listens beyond 127.0.0.1 (--host 0.0.0.0), anyone on the network could read the list of a user’s chats’ titles and import them. Proposed: the three GET routes and the imports answer only a request from this machine (loopback) or with an admin key, and say so in the 403 (open question 7).
  • MCP programs: an imported server is listed, never started: the command is shown whole before the import and again on the existing approval, programs need --allow-mcp-commands, the approval is tied to the command, arguments, folder and variable names (mcp-approvals.json), a changed entry needs a new approval. No Connect, no tool list is fetched by the import.
  • Secrets in mcp.json: LM Studio’s file keeps tokens in env and headers in plain text; the import copies them into Inga’s file, also plain text, written owner-only. The page and the API show only their names; the log line of an import names the servers, never a value. Placeholders are flagged (§2.2).
  • Conversation files are data: a chat’s text, a file name, a picture are parsed as JSON and copied, never run, never rendered as HTML (the page’s Markdown renderer sanitizes as for any chat); a file name from LM Studio is never used as a path (pictures are found by identifier inside the pictures’ folder only, a .. or an absolute identifier refused).
  • REST v1: a stored response belongs to its key; integrations cannot reach a server of mcp.json without the mcp group; ephemeral servers off by default; load, unload and download are admin.
