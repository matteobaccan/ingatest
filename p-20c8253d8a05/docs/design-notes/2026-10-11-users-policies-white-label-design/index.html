Users, policies and white-label: Inga for a company

Status: decided by the maintainer on 2026-10-11. Phase U1 (logins, roles, HTTPS, allowed networks) is in 0.26.5, where TODO.md schedules “Users with a login and roles” and “HTTPS built in”; phases U2–U5 in 0.29.0. Phase W built for 0.29.0 (branch feat/white-label, which carries the first slice of feat/branding-acme with it; see §8.5 As built); U1–U5 not built yet. Builds on the named API keys (crates/inga-server/src/keys.rs, #382), the API nodes (the local-only tag, costs and budgets), the memory and documents store, the shared chats (crates/inga-server/src/shared.rs), scheduled tasks, skills and the local data rule.

1. Why

Section titled “1. Why”

Today inga serve is one person’s server: one --api-key, or named keys (--api-keys FILE) with route groups, allowed models, requests per minute, tokens per day and usage per key. A company that wants to give a local model to its staff needs more, and today the answer is “put Open WebUI in front” (docs/comparison.md, Part 2, §6):

  • people, not keys: a login in the web UI, roles, keys that belong to a person;
  • groups and policies: who may use which model and which feature, with what limits;
  • an administrator’s view: the users, what they used, an exportable audit log;
  • the company’s identity provider: single sign-on, groups mapped from it;
  • content rules: nothing personal leaves for a cloud provider, some groups never leave the machine, a terms-of-use banner;
  • its own name on it: a company or a reseller ships Inga as its own product (white-label), within the MIT licence and without implying the maintainer’s endorsement.

Everything stays in one executable, with no database server: accounts, groups, policies and the audit log live in $INGA_HOME as the keys and their usage do now.

2. What others do (surveyed 2026-10-11)

Section titled “2. What others do (surveyed 2026-10-11)”
Project Accounts and roles Groups and permissions SSO Audit, retention Branding
Open WebUI admin / user / pending; sign-up on or off; the first account is the admin groups with permissions per feature (web search, image generation, code execution, file upload, tools…) and per model (model access lists) OAuth / OIDC (Google, Microsoft, generic OIDC), LDAP, trusted header, SCIM 2.0 chats kept on the server (its database); admin can see chats; feedback and usage name (WEBUI_NAME), custom CSS, banners; logo changes reserved by its licence’s branding clause for deployments above a size, or an enterprise licence
LM Studio none in the app (enterprise: SSO and an org) permission keys for the server: which endpoints and models a key may use enterprise — —
LiteLLM (proxy) internal users, teams, organizations; admin UI per team / key: allowed models, max_budget, budget_duration, tpm_limit, rpm_limit SSO in its enterprise edition spend logs per key / user / team its enterprise edition (logo, colours)
AnythingLLM admin / manager / default, multi-user mode workspaces per user — event logs white-label in its paid editions
Inga today — named keys: routes (chat, admin), models, requests per minute, tokens per day; a user field reserved — usage per key (keys-usage.json in $INGA_HOME); chats in the browser only —

Lessons:

  1. Permissions per feature, not only per model (Open WebUI): web search, images, tools are what an administrator wants to turn off.
  2. Budgets per team (LiteLLM): a group’s tokens and cost per day or month.
  3. Chats on the server are a liability as much as a feature: they make the server a store of everything the staff typed. Inga keeps them in the browser unless an admin decides otherwise, with a retention period (§5.3).
  4. Branding behind a paid licence is what Inga does not do: Inga’s code is MIT, so white-label is free; only the name and logo are protected (§8.4).

3. U1 — Logins, roles, HTTPS, allowed networks (0.26.0)

Section titled “3. U1 — Logins, roles, HTTPS, allowed networks (0.26.0)”

Already in TODO.md (0.26.0, “Users with a login and roles” and “HTTPS built in”); this spec fixes the details so that U2–U5 build on it.

3.1 Accounts

Section titled “3.1 Accounts”
  • Kept in $INGA_HOME/users.json (name, display name, role, groups, password hash, created, last login, suspended, the identity provider for SSO accounts). Passwords hashed with Argon2id (the argon2 crate, pure Rust; parameters from OWASP’s current recommendation, upgraded on the next login when they change).
  • inga user add|list|passwd|suspend|remove on the machine (the first admin is created this way or by the web UI’s first-run page, which only answers on loopback).
  • No accounts: Inga behaves as today (keys or nothing). The first account turns logins on for the web UI.

3.2 Roles

Section titled “3.2 Roles”
Role May
admin everything: models, folders, devices, settings, users, groups, policies, the audit log
user the web UI’s chat (and what its group’s policy allows), its own keys, its own data
api API calls only, through its keys; no web UI login

A role is the coarse switch; the policy of the user’s groups (U2) refines it.

3.3 Sessions and keys

Section titled “3.3 Sessions and keys”
  • Web UI sessions by cookie: a random 256-bit id, HttpOnly, Secure over HTTPS, SameSite=Strict, an idle timeout and an absolute lifetime (both settable), kept in memory and in $INGA_HOME/sessions.json (hashed) so a restart does not log everyone out. State-changing requests from the web UI carry a CSRF token.
  • Login attempts limited per account and per address (a growing delay, then a lock the admin can lift), and said so in the answer and the log.
  • The named keys gain an owner: the user field of keys.rs (kept and reported as is since #382) now names an account; a user creates and revokes its own keys in the web UI (Settings → API keys, the secret shown once), an admin any key. A key never has more rights than its owner; a suspended user’s keys stop working at once.
  • --api-key (the single unnamed key) keeps working, as an admin key.

3.4 HTTPS built in

Section titled “3.4 HTTPS built in”

As TODO.md describes: --tls-cert / --tls-key, --tls self-signed (generated once and kept in $INGA_HOME/tls/), --tls acme --domain D (Let’s Encrypt over ACME, renewed by the server itself), on rustls (already in the tree). With logins on and a non-loopback --host, Inga says at start when it serves without TLS (cookies and passwords in clear on the network).

3.5 Allowed networks and the loopback default

Section titled “3.5 Allowed networks and the loopback default”
  • inga serve keeps binding 127.0.0.1 by default (this machine only); serving the LAN takes an explicit --host. This is the documented default and stays so.
  • --allow-from CIDR[,CIDR...] (and allow_from in the server settings): addresses outside the list are refused before any parsing (the connection closed, a line in the log with the address). IPv4 and IPv6, single addresses or CIDR ranges; loopback is always allowed so the admin cannot lock themselves out.
  • A non-loopback --host with no accounts, no keys and no --allow-from refuses to start (decided by the maintainer, 2026-10-11), naming the risk (anyone on the network could use the models and the admin routes) and the ways out: accounts, keys, --allow-from, or --open-network to serve the network open on purpose (then a warning at start and on the web UI’s Server page).
  • Per-role networks: admin routes may be limited to a narrower list (--admin-from, default loopback plus --allow-from).

3.6 What U1 shows

Section titled “3.6 What U1 shows”

The Server page lists the accounts signed in, the bound address, TLS (certificate, expiry, renewal), the allowed networks; /api/inga/users (admin) and /api/inga/me. A refused request says why (401 no session or key, 403 role, network or model, 429 limit with Retry-After), in the API, the log and the web UI.

4. U2 — Policies per group (0.29.0)

Section titled “4. U2 — Policies per group (0.29.0)”

4.1 Groups

Section titled “4.1 Groups”

A group is a name with a policy; a user belongs to zero or more groups; the built-in group everyone holds every user. Groups are created by an admin (Users page, inga group add|list|remove, $INGA_HOME/groups.json) or mapped from the identity provider (U4).

4.2 What a policy holds

Section titled “4.2 What a policy holds”
  • models: allowed models (the keys’ * prefix syntax), local, mesh and API nodes’.
  • features: web search, documents, memory, image generation, MCP tools, scheduled tasks, cloud API nodes; each off hides the control in the web UI and refuses the request with a 403 naming the feature.
  • max_context: a ceiling on the context a request may use (the prompt is cut or refused as context_length_exceeded, as today).
  • quota (per user: each member of the group has the group’s quota; a pool shared by the whole group comes later): requests and tokens per minute / day / month; cost per day / month once API nodes report costs (A4); per user, with an optional pool for the whole group.
  • hours: when the group may use the server (a time zone, days, a window); outside it a 403 that says when it opens.
  • local_only: the group’s requests carry local-only (U5, §7.3).

4.3 Combining

Section titled “4.3 Combining”

A user in several groups gets the union of allowed models and features and the largest limits (the most generous group wins), except local_only, content rules and hours, where the strictest wins. A key is limited by its own limits and by its owner’s policy, whichever is lower. The effective policy is shown per user (Users page, inga user show NAME), with the group each line comes from.

4.4 One limit engine

Section titled “4.4 One limit engine”

The counters, sliding windows, UTC day rollover, Retry-After and the usage file of keys.rs are generalized into one limit engine keyed by subject (key, user, group), with months and costs added. Usage moves from keys-usage.json to usage.json (read once from the old file). Every refusal says which subject and which limit.

5. U3 — Users page, audit log, chats on the server (0.29.0)

Section titled “5. U3 — Users page, audit log, chats on the server (0.29.0)”

5.1 The Users page

Section titled “5.1 The Users page”

Admins only: the users (role, groups, last login, usage today and this month, suspended), create, suspend / resume, reset a password (a one-time link or a temporary password that must be changed), assign groups, see the effective policy, revoke keys and sessions. A Groups tab edits groups and their policies, with a preview of who is affected.

5.2 The audit log

Section titled “5.2 The audit log”
  • One JSON line per event in $INGA_HOME/audit/YYYY-MM.jsonl: time, user, key, address, action (login, logout, failed login, request, refusal, model load, setting changed, user / group / policy changed, data deleted, export), model, node (local, mesh, which API node), tokens, cost, status. Never the prompt or the answer.
  • Shown on the Users page (filters by user, action, model, date) and exported as CSV or JSON Lines (inga audit export --from --to, /api/inga/audit).
  • Kept for a settable time (default 365 days), then deleted; listed and deletable as audit in inga data and the Storage page (the local data rule), deletion itself audited.
  • The audit log can be turned off entirely; it is on by default once accounts exist.

5.3 Chats on the server, off by default

Section titled “5.3 Chats on the server, off by default”
  • By default chats stay in the browser (as today): the server keeps nothing of what people typed.
  • An admin may turn on server-side chat storage (chat_storage: {"enabled": true, "retention_days": 90, "groups": [...]}): a user’s chats are then kept in $INGA_HOME/chats/<user>/, follow the user across browsers, and are deleted after the retention period. The web UI says so on every chat (a line under the input) and in the terms of use (U5).
  • Users see and delete their own stored chats; admins see sizes and counts, not the contents, unless a separate chat_review switch is also on (said to the users).
  • Shared chats (/shared/{id}) are unchanged; with accounts on, creating a link may be turned off per group.

6. U4 — Single sign-on with OIDC (0.29.0)

Section titled “6. U4 — Single sign-on with OIDC (0.29.0)”
  • OpenID Connect authorization code flow with PKCE, tested against Microsoft Entra ID, Google Workspace, Keycloak and Authentik; any compliant provider configured by its issuer URL (discovery from /.well-known/openid-configuration), client id and a client secret from an environment variable or the encrypted store.
  • ID tokens verified in pure Rust: the provider’s JWKS fetched and cached (re-fetched on an unknown kid), signatures checked with ring (already in the tree under rustls; RS256, PS256, ES256, EdDSA), iss, aud, exp, nbf, iat and nonce checked with a small clock skew. Approved by the maintainer as the one place ring is used directly.
  • Accounts created on first login (or only pre-created ones, a setting); the role and groups taken from a claim (groups, roles, or one named in the settings) through a mapping: company group → Inga group, with a default for the unmapped.
  • Local accounts keep working beside SSO (at least one local admin, for when the provider is down); an admin may turn local logins off for everyone else.
  • Logout ends the Inga session; the provider’s logout endpoint is offered when present.

7. U5 — Content rules (0.29.0)

Section titled “7. U5 — Content rules (0.29.0)”

7.1 Blocked words and patterns

Section titled “7.1 Blocked words and patterns”

Per group: words and regular expressions (the regex crate, linear time) checked on the request (and optionally on the answer). A match refuses the request (403 with the rule’s name, not the matched text, in the audit log) or replaces the text, as the rule says.

7.2 PII masking before a cloud provider

Section titled “7.2 PII masking before a cloud provider”

Before a request leaves for a cloud API node (and, for a group whose policy says pii_local: true, before a local or mesh model too, so that chats and logs never hold the originals), the group’s masks replace personal data with placeholders ([EMAIL_1], [PHONE_1]…) and put the originals back in the answer: emails, phone numbers (international and Italian formats), IBAN (with the check digits), Italian codice fiscale (with its check character), credit card numbers (Luhn), IP addresses, and custom patterns. Masks run in the server, are listed in the answer’s footer (“2 emails masked before OpenAI”) and the audit log (counts only).

7.3 Forced local-only

Section titled “7.3 Forced local-only”

A group with local_only: true has every request tagged local-only; the API nodes’ router (A3) already never sends such a request to a cloud node, and fails it rather than fall back to one. Cloud models are hidden from those users in the web UI and /v1/models.

7.4 Terms of use

Section titled “7.4 Terms of use”

An admin sets a terms-of-use text (Markdown, per language); each user accepts it at first login and again when it changes (the version and time in the audit log). An API key works only for an owner who has accepted.

8. W — White-label (0.29.0)

Section titled “8. W — White-label (0.29.0)”

8.1 Runtime branding

Section titled “8.1 Runtime branding”

--branding DIR (or $INGA_HOME/branding/) holds branding.json and its assets; nothing is rebuilt.

  • The web UI: name in the title, header, splash, PWA manifest (app.rs); logo, favicon and PWA icons; colours and the default theme; extra CSS loaded after the built-in one; the About text; help and support links in the menu.
  • Strings overridable in the six languages, by the keys of the I18N table; a key that does not exist is reported at start (inga-server/tests/webui_i18n.rs checks the built-in table as today).
  • The APIs: owned_by in /v1/models (today "inga"), the Server response header, the User-Agent of outgoing requests (downloads, web search, API nodes; today inga/<version>).
  • “Powered by Inga”: a line in the footer and in About, visible by default, removable with "powered_by": false.
  • Licence notices always reachable: About → Open source licenses shows Inga’s MIT licence and THIRD-PARTY-NOTICES.md (built into the executable). Branding cannot remove this entry: the MIT licence and the third-party licences require the notices to travel with the software. The CLI gains inga licenses, which prints the same text.
  • Assets are checked at load (size, type: PNG, SVG, ICO, WebP); SVGs are served with the same sandboxing headers as other static files.

8.2 No build-time branding

Section titled “8.2 No build-time branding”

Decided by the maintainer on 2026-10-11: the product is never rebuilt for a brand. White-label is runtime only — a stylesheet and the files of §8.1 — so a company runs the official release executables (and their updates) unchanged:

  • CSS first. The web UI’s look is driven by documented CSS custom properties (colours, fonts, radii, spacing, the header and the splash) and stable class names, so extra.css alone can restyle every page; the themes are built on the same properties. What CSS cannot reach (the page title, the PWA manifest, the strings, the API’s owned_by / Server / User-Agent) comes from branding.json.
  • The executable, its name, inga service’s service names, $INGA_HOME and the Docker image stay Inga’s; a company that wants another file name renames or wraps it itself (TRADEMARKS.md).
  • There are therefore no Windows version resources per brand, no INGA_BRAND_DIR, no branded build workflow.

8.3 What never changes

Section titled “8.3 What never changes”

The licence text and the third-party notices (§8.1), the inga_* fields of the APIs (inga_warning, inga_sources…: clients rely on them), the /api/inga/* paths, the file formats in the data folder (a branded build reads an Inga data folder and back).

9.1 Legal notes

Section titled “9.1 Legal notes”
  • Personal data and the GDPR. Accounts (names, emails, password hashes), sessions, the audit log, quotas’ usage and, when enabled, chats stored on the server are personal data. The organisation that runs Inga is the controller; Inga gives it the means: data kept only in $INGA_HOME (no third party), retention periods for the audit log and stored chats, inga data to list, export and delete a user’s data (access and erasure requests), server-side chats off by default, the audit log recording actions and counts, never prompt text.
  • Informing users. The terms-of-use page (U5) is where the organisation states what is recorded and why; the first-run page reminds the admin to write it when the audit log or server-side chats are on.
  • PII masking is a help, not a guarantee. Patterns can miss personal data; the docs say so and recommend local_only groups for data that must not leave.
  • Branding and trademarks. A brand applied with --branding must use names and logos its owner has the right to use: Inga’s own marks follow TRADEMARKS.md, and the example brand (ACME, an original anvil logo) uses a generic fictional name and no third-party artwork. “Powered by Inga” may be removed; the licence notices may not.

10. Decisions (the maintainer, 2026-10-11)

Section titled “10. Decisions (the maintainer, 2026-10-11)”
  • U1 stays in 0.26.0 with what TODO.md already holds, plus allowed networks and the loopback-only default.
  • U2–U5 and W go to 0.29.0, the last release of the roadmap.
  • Chats stay in the browser by default; server-side storage is an admin’s choice, with a retention period.
  • OIDC ID tokens are verified with ring directly (approved).
  • White-label is free (the code is MIT); “Powered by Inga” is on by default and removable; the licence notices are not removable; the name and logo are covered by TRADEMARKS.md.
  • The answers to the open questions (2026-10-11):
    • a non-loopback --host with no accounts, keys or --allow-from refuses to start, --open-network overrides (§3.5);
    • the audit log is on once accounts exist;
    • U2 has per-user quotas only; a pool shared by a group comes later;
    • PII masking applies to cloud nodes by default, and to local models too for a group that asks (pii_local: true in its policy);
    • white-label never rebuilds the product: CSS and runtime files only (§8.2), so the Windows resources and the executable name questions are gone.
