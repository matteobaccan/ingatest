Experts larger than the RAM: precision by use, quantized once

Status: proposed, 2026-10-10 (asked by the maintainer, after looking at ds4). Phases E1–E3 (planned for 0.22.1) shipped in 0.22.2: E1 (#290), E2 (#293), E3 (#294), checked on synthetic models; E3’s acceptance on the maintainer’s machine (§4) is left. E4 shipped in 0.25.0 (§3.7, checked against llama.cpp itself); E5 built for 0.27.0 (§3.6 “As built”, branch feat/experts-ram-3), checked on synthetic models; its acceptance on the maintainer’s machine is left.

1. The problem

Section titled “1. The problem”

A mixture of experts whose experts do not fit in RAM streams them from disk (Model::stream_experts, an LRU of whole experts read with pread). On the maintainer’s machine (32 GB of RAM, one NVMe SSD) Qwen3.6-35B-A3B Q4_K_M keeps part of its 18.3 GiB of experts in RAM and reads the rest per token. The models announced next are far larger: a 1000B mixture with about 50B active parameters is ~560 GB at 4 bits, ~280 GB at 2 bits; at 4 bits a token reads up to ~28 GB, seconds on one SSD.

What Inga has: the LRU cache, router-lookahead prefetch, pinned hot experts from usage counts kept in $INGA_HOME/experts (--pin-experts N), --mirror (reads spread over several disks), experts on other machines (--expert-nodes, 0.8.0), and --quantize-experts TYPE (at every load, and only when the experts are in RAM).

2. What ds4 does, and what Inga takes from it

Section titled “2. What ds4 does, and what Inga takes from it”

ds4 (DeepSeek V4 on a laptop): the routed experts at about 2 bits (IQ2_XXS gate and up, Q2_K down), the shared experts, attention and router at 8 / 16 bits; a profile of expert use per layer, sorted by hits per byte, decides which experts stay in RAM; the others are read from the SSD into a bounded cache. Inga takes: the asymmetric types (already possible: --quantize-experts iq2_xxs with a down type), the use profile (Inga has the counts), the hot list sized to a budget. What is new for Inga: the conversion done once and kept, hot and cold experts at different precisions, and an importance matrix.

3. Design

Section titled “3. Design”

3.1 Converted experts kept on disk (E1)

Section titled “3.1 Converted experts kept on disk (E1)”

--quantize-experts TYPE writes what it converts to $INGA_HOME/cache/experts/<key>/, <key> = SHA-256 of the model file’s header and tensor table, its size and the target types. The next load maps the converted experts from there (same mmap and pread paths as the GGUF), with no conversion. One file per layer, laid out expert after expert, so a streamed expert is one contiguous read. inga data list|rm|clear experts (2026-10-10-local-data-design.md) shows each model’s converted experts with their size and deletes one or all; the cache is a cache: deleting it only costs one conversion.

The conversion also works when the experts are streamed (today it refuses): layer by layer, reading each expert once from the model file and writing it converted, in bounded memory. A 1000B model is converted once, overnight.

As built (inga-engine/src/expert_cache.rs, inga-model/src/model/expert_cache.rs):

  • <key> hashes the cache format, the model’s size, its GGUF version and metadata (in key order), its tensor table (name, shape, type, offset) and the two target types (--quantize-experts, --quantize-down). The tensor data is not hashed: a model rewritten in place with the same header and size would need its entry deleted.
  • layer-NNN.bin, one per MoE layer: expert after expert, each its gate, up and down matrices (converted, or copied as stored when their type stays), every matrix at a multiple of 32 bytes, zeros in between. No header: the layout follows from the model and the types, and the loader computes it.
  • manifest.json: format, key, model name, source file and size, types, each layer’s file and exact size, total, creation time. The entry is written in <key>.partial-<pid>/, the manifest last (a temporary name, then renamed), then the directory is renamed to <key>/.
  • An entry is used only if its manifest parses, has this format and key, lists the layout the model expects and every file has the listed size; otherwise it is deleted and rebuilt. If the cache cannot be written (no home, a read-only disk), the experts are converted in memory as before, with a note.
  • The conversion runs on the CPU threads, at most one expert per thread in memory at a time; the model file’s pages are dropped after each layer. A streamed expert of the cache is read with one pread.

3.2 Use profile and importance matrix (E2)

Section titled “3.2 Use profile and importance matrix (E2)”

The usage counts become a profile per model ($INGA_HOME/experts/<model>.profile):

  • per (layer, expert): uses, and the router weight they carried (an expert picked with weight 0.02 matters less than one picked with 0.4);
  • per expert input column: the sum of the squared activations, what llama-imatrix collects, gathered while the model runs (one add per routed row, off the critical path in the pool’s idle time) or by inga profile MODEL --text FILE over a calibration text.

The profile is the basis of E3 and the importance matrix of E4.

As built (inga-model/src/profile.rs, inga-engine/src/profiles.rs, src/commands/profile.rs):

  • The profile file, $INGA_HOME/experts/<file name>-<size>.profile, is text: the line inga expert profile 2, then layer expert uses weight per expert used. A missing profile starts from the usage file of earlier versions beside it (.txt, inga expert usage 1, layer expert uses: no weights), which is deleted once the profile is written. Uses count routed rows (tokens), the weight is the final routing weight (after renormalization and scaling), both added by every MoE step of every mixture of experts that run or serve loads (one lock and k adds per row and layer, no allocation), written every 65 536 rows and when the model is dropped.
  • The importance matrix is kept beside it (.imatrix) in llama.cpp’s imatrix GGUF format (tools/imatrix/imatrix.cpp, --output-format gguf): general.type = imatrix, imatrix.datasets, imatrix.chunk_count, imatrix.chunk_size, and per matrix, sorted by name, <tensor>.in_sum2 (F32, [cols, n_mat]) and <tensor>.counts (F32, [1, n_mat]); llama.cpp’s own files read back (their .in_sum and .stats tensors are ignored, and not written). As in llama-imatrix, every matrix product of the layers is collected (attention, routers, dense and shared networks, each expert of a tensor of experts by the rows routed to it), the output and the embeddings are not, and the products of fewer than 16 rows by matrices that are not experts are left out.
  • Collection is a backend wrapping the model’s in Model::layer_forward, installed only when collecting (Model::collect_imatrix): off, the forward pass is unchanged. On, each product’s input rows are added once, outside the product’s kernels; after every tensor has been seen, nothing is allocated. --collect-imatrix adds to the file kept (written every five minutes by another thread and when the model is unloaded); inga profile starts a new one, runs each chunk of the text in one pass on the CPU (Model::hidden_states, the first token replaced by BOS as llama-imatrix does) and writes it. Layers run on a GPU or by other machines are not collected.
  • Checked against a reference tally of the backend’s own products on synthetic models (inga-model/tests/profile.rs): uses and router weights per expert, and the sums of squares and counts of every matrix (llama.cpp does not build here, so not against llama-imatrix itself). Inga adds an expert’s rows token by token, llama-imatrix slot by slot, so the sums agree to within f32 rounding; the counts are equal.

3.3 Precision by use (E3)

Section titled “3.3 Precision by use (E3)”

Experts sorted by uses × weight / bytes (ds4’s hits per byte):

  • hot — kept at the model’s own precision, in RAM (pinned, never evicted);
  • warm — converted to a smaller type (Q4_K by default, Q2_K / IQ2 with E4), in RAM;
  • cold — the smaller type, streamed from the E1 cache on disk.

Every expert of a GGUF layer shares one tensor and one type, so the mixed layout lives only in the E1 cache, never in a GGUF file: the original stays untouched and llama.cpp still reads it.

3.4 Budget (E3)

Section titled “3.4 Budget (E3)”

--experts-precision auto sizes the three groups to the free RAM (the planner’s mem_info, minus the KV cache and --mem-limit’s margin): as many hot experts as fit after the warm ones, the cold ones on disk; the plan printed as today (“experts: 112 hot Q4_K, 3 968 warm Q2_K in RAM, 1 040 cold on disk”).

3.5 Quality and the default

Section titled “3.5 Quality and the default”

Converting weights changes the output, and Inga’s promise so far is llama.cpp’s output. So:

  • off by default. When the experts do not fit and would stream, Inga prints a suggestion with the estimated speed: “experts streamed from disk; --experts-precision auto would keep them in RAM at about 2.8 bits (measured on this model: KL 0.08)”;
  • the cost is measured, not guessed: inga perplexity --kl-base against the original for each type, and the result kept in the profile and shown in the suggestion;
  • never converted to a type of more bits than the source, and a warning when the source is already 4 bits or less (errors add up: a Q4_K_M file taken to 2 bits loses more than the same model quantized from BF16; the best source is a Q8_0 or BF16 file);
  • attention, routers, shared experts, norms and the output layer are never converted by this option.

Rough expectations, to be replaced by measurements: Q8_0 → Q4_K of the experts, a few percent of perplexity; to Q2_K without an importance matrix, large losses on small models, smaller on large mixtures (each expert is a small share of a token’s compute); IQ2 with an importance matrix, between the two.

As built (inga-engine/src/precision.rs, inga-model/src/model/expert_cache.rs; --experts-precision auto|off, --experts-warm TYPE, --experts-cold TYPE in run, serve, bench and perplexity; not with --quantize-experts nor across machines):

  • The rank is the router weight an expert carried (the profile’s sum, so uses × mean weight; the uses for a usage file without weights) divided by its bytes as stored, ties by layer and expert. The budget is Engine::prepare’s: the available memory capped by --mem-limit, less the other weights (as --quantize leaves them), the KV cache and the planner’s overhead. Every expert warm if they all fit; else the best ranked warm and the rest cold, after room for a cache of 2 × n_expert_used cold experts; then, best ranked first, the experts whose own size still fits are hot. Without a profile, no expert is hot and a note says so. Nothing is done (with a note) when the experts fit as stored, when no type has fewer bits, without a home directory or when the memory is unknown.
  • The converted experts are an E1 cache entry; the layout gives each expert its own types (inga_model::ExpertTypes: warm types, cold types, the cold experts, and no_upgrade, which leaves a matrix as stored rather than give it more bits), and the manifest lists each expert’s offset and types (EXPERT_CACHE_FORMAT 2; entries of format 1 are rebuilt). The hot experts are in the entry too, at the warm type, but read from the model’s file (Model::map_expert_cache’s keep), so the entry does not depend on them; when the cold type is the warm one, it does not depend on the cold experts either (the same entry as --quantize-experts q4_k with no_upgrade). With a cold type of its own, an entry written for the same model and types (the manifest’s base key) is reused while its warm experts fit, so a profile that moves on does not convert the model again; entries it replaces are deleted.
  • In RAM: with no cold experts, the hot ones mapped from the model file and the warm ones from the entry; with cold experts, the experts are streamed (Model::stream_experts) and the hot and warm ones read once into the cache and pinned (Model::pin_experts), the rest of the cache holding the cold ones as they are used. The MoE forward pass needed no change: each expert’s three matrices are their own weights with their own types, and the products dispatch on each. The plan printed: “experts: 112 hot Q4_K (own), 3 968 warm Q4_K in RAM, 1 040 cold Q2_K on disk (6% of the routed use), about 4.6 bits per weight in RAM”, the types as converted (Q8_0 for rows that are not whole K-quant blocks).
  • Off, when the planner streams the experts, one line: “note: experts streamed from disk; –experts-precision auto would keep them in RAM at about 4.5 bits per weight (measured on this model: KL 0.0800) (it converts them, which changes the output)”, or “keep N of M”. The KL is the last one inga perplexity --kl-base measured with --experts-precision auto (and without --quantize or LoRA) for these types, kept in $INGA_HOME/experts/<model>.quality (inga expert quality 1, then types kl same_top tokens; q4_k, or q4_k+q2_k with a cold type of its own); inga data lists it with the profiles.
  • Fixed after 0.24.1, following the maintainer’s run (Qwen3.6-35B-A3B Q4_K_M, 32 GB, Windows): the default warm type was Q4_K whatever the source, so a Q4_K_M file had its Q6_K down projections taken to Q4_K (5 120 matrices, 272 s, 4.8 → 4.7 bits). Now a conversion must save MIN_SAVING (one bit per weight on average): without --experts-warm, the first of WARM_TYPES (Q4_K, Q3_K, Q2_K) that does; when none does, or the type given does not, nothing is converted and a note says so. The hot experts are left out of the entry (ExpertTypes::kept, zero bytes in the files, read from the model’s file; manifest kept, part of the key when not empty): with the profile’s hot experts, most of a large model is neither read nor converted. A new entry leaves out the experts hot with 1/16 less memory, and an entry is reused while its cold and left-out experts fit (ExpertLayout), so small changes of the free memory do not convert again. The conversion drops each expert’s source pages once written (Storage::evict, now also on Windows through VirtualUnlock). The hot and warm experts are read through the expert cache (Model::stream_experts with room for all of them; pinned when cold experts share it) rather than mapped: the maintainer’s run read them through the mappings, a page fault at a time with no read-ahead on Windows, and decoded at 1.18 t/s against 3.86 t/s streamed without the option. The GPU plan does not depend on the option (the 0.24.0 run had 106 MiB less free VRAM, so 5 attention layers and, with them, the shared experts stayed on the CPU; a test now plans both ways).
  • Checked on synthetic MoE models: groups for crafted profiles and budgets (precision.rs), logits equal to the same conversion done by hand expert by expert (hot experts kept, warm and cold types mixed in a layer, streamed or not), the second load converting nothing, the option off giving the same output as before, the suggestion and its KL, no type of more bits (inga-engine/tests/expert_precision.rs, the unit tests of inga-model/src/model/expert_cache.rs, tests/cli.rs). The acceptance on Qwen3.6-35B-A3B with 32 GB could not be run here: it is left to the maintainer’s machine.

3.6 Reading faster (E5)

Section titled “3.6 Reading faster (E5)”
  • LFRU eviction: the LRU becomes recency weighted by the profile’s frequency, so a burst of rare experts does not evict the hot ones.
  • Prefill by layer: a long prompt runs layer by layer for all its tokens (the --batch chunk), so each expert is read once per chunk instead of once per token, with the next layer’s experts read while this one computes (two buffers).
  • Experts striped over several disks (--experts-dir DIR, repeated): the E1 cache spread over the disks expert by expert, each disk holding a different share, so N NVMe drives read N times faster without N copies (--mirror keeps a whole copy per disk: fine for a 20 GB model, not for a 300 GB one).
  • Reads that bypass the page cache (O_DIRECT on Linux, F_NOCACHE on macOS, FILE_FLAG_NO_BUFFERING on Windows) for the streamed experts, so the OS does not keep a second copy of what Inga’s cache holds.

As built (0.27.0, branch feat/experts-ram-3; inga-model/src/experts.rs, inga-model/src/model/expert_cache.rs, inga-engine/src/expert_cache.rs, inga-engine/src/plan.rs):

  • Found first: the RAM the GPU frees (the maintainer’s bench of 2026-10-12, Qwen3-30B-A3B Q4_K_M, 17.3 GiB, on the P1000 runner with --device vulkan:0: “SSD (read while running): routed experts of layers 0-43, 14.9 GiB”, “experts on disk, cache of 4672 experts (13.31 GiB)”, with 32 GB of RAM). Windows reported about 15 GiB available on that machine, as every report from it did (the GPU mesh spec’s “~15 GB free” on ISAIA): the RAM reading is right, half the RAM was in use by other programs. Two planner faults made it worse:
    • The memory plan is made before the GPU, and only a GPU running every layer had it redone (#419). Here the card took the attention, the KV cache, the output layer and the routed experts of 4 layers (2.2 GiB the plan had kept room for in RAM). Plan::after_gpu plans the experts the CPU runs again within the same budget once the GPU holds its share (placement::gpu_share; only for cards with memory of their own, CUDA and discrete Vulkan devices, not integrated GPUs or Metal, whose memory is the RAM), and Engine::plan_after_gpu resizes the cache (or maps the experts when they now fit). The tip’s “N of M experts” and “more free RAM” count the CPU’s experts.
    • The cache was counted in experts at the largest expert’s size (a Q6_K down projection: 2.92 MiB, against 2.53 MiB for the Q4_K ones). It is now bounded by its bytes (the plan’s), and counted at the mean size; the hit rate follows the bytes.
    • On the hardware profiles suite (p1000-windows-vulkan__qwen3-30b-a3b-q4_k_m): 14.5 GiB of the 15.3 GiB of experts the CPU runs stay in RAM (95 %, was 82 %); with 16 GiB available, all of them (no disk read). The AMD RX 9060 XT profile (Ornith-1.5 Q6_K, 26 GiB available) now keeps every expert in RAM (1 GiB per token read from the disk before).
  • LFRU: an entry’s rank is its last use plus up to the cache’s capacity, in accesses, for its uses against the most used expert’s (Lru::rank); the lowest rank leaves first. The uses are the profile’s ($INGA_HOME/experts, seeded at load by Model::use_expert_history, beside the pinned experts) plus each use this run, kept when an expert leaves the cache. The experts the step running uses leave last; pinned experts never. An expert as used as the most used one outlives a full cache of experts used once since it ran; without a profile it is an LRU.
  • Prefill by layer, two buffers: Inga already ran a prompt chunk layer by layer, grouped by expert, so each expert was read once per chunk (the MoE prefill by expert spec). What went wrong with a cache smaller than the experts a chunk uses: chunk after chunk the LRU, used in the same order, evicted exactly the experts the next layers were about to use (nothing found, everything read again), one expert at a time. Now a prompt step (more than one row) whose missing experts the cache cannot take without evicting goes through two buffers (ExpertIo::staged): the cached experts run first while the first buffer is read (up to 8 threads), then buffer after buffer, the next read while one runs; once this layer’s reads are done, the experts the next layer’s router picks for these rows (router lookahead) and the cache lacks are read into a buffer for it. A buffer holds a sixteenth of the cache’s bytes (256 MiB at most, two experts at least); room for the two is made in the cache first (the lowest ranked leave). The experts read are kept only where the cache has room beyond the two buffers: a prompt no longer evicts the experts decoding uses (the read-ahead of a prompt step on the old path also fills only free room). ExpertStats::staged counts the experts read and dropped.
  • Reads past the page cache: INGA_DIRECT_READS=1 (read at each read, so inga bench --ab INGA_DIRECT_READS=1 compares both on one load): the streamed experts are read from a second handle opened with O_DIRECT (Linux), F_NOCACHE (macOS) or FILE_FLAG_NO_BUFFERING (Windows), whole 4 KiB blocks into an aligned buffer, the expert copied out; a file system that refuses them (tmpfs) falls back to the page cache for that file. Off by default until measured on a real NVMe.
  • Striped over several disks: --experts-dir DIR (repeatable; run, serve, bench) writes, once, an entry <DIR>/<key>/ in each directory with its stripe of every layer (expert e of a layer in the e % n-th directory, layer-NNN.bin and a manifest naming the stripe; the key counts the stripes), the experts copied as stored or converted with --quantize-experts / --quantize-down; the next loads read them from there (Model::map_expert_stripes), mapped or streamed, each expert from its own disk. A damaged stripe is rebuilt. Not with --experts-precision (refused) nor across machines.
  • Checked on synthetic models: the eviction (experts.rs unit tests: a burst of rare experts against hot ones, frequencies learned while running, the step running kept, pinned experts, the byte bound, offers that never evict), the logits of prompts through the two buffers equal to the mapped experts’ for caches of 1 to 40 experts and one bounded by bytes, and the experts of two decode steps all still cached after a 40-token prompt (inga-model/tests/forward.rs), aligned reads past the page cache (ext4 here), striped experts equal to the mapped ones, copied or converted, streamed from three files (expert_cache.rs unit tests, inga-engine/tests/expert_cache.rs), the planner (plan.rs tests, the hardware profiles suite).
  • Left: the acceptance run on the maintainer’s machine (prompt speed of a streamed model ≥ 3× today’s, decode not slower; inga bench --ab INGA_DIRECT_READS=1), the reads past the page cache on by default once measured, --experts-dir with --experts-precision, and inga data listing the striped entries (they live in the directories given, not under $INGA_HOME).

3.7 The i-quants with the importance matrix (E4)

Section titled “3.7 The i-quants with the importance matrix (E4)”

As built (inga-quant/src/iq_quant.rs, weighted.rs; inga-engine/src/quantize.rs; src/commands/profile.rs):

  • inga_quant::quantize_row_with(type, row, importance) is llama.cpp’s ggml_quantize_chunk for one row: IQ2_XXS, IQ2_XS, IQ2_S, IQ3_XXS, IQ3_S, IQ4_NL and IQ4_XS (quantize_row_iq*_impl, quantize_iq4_*), their grids and the neighbours of the points off them computed once as iq2xs_init_impl / iq3xs_init_impl do (from the dequantization tables, the same points), and the _impl quantizers of Q2_K … Q6_K and Q4_0 … Q5_1 that weigh each column’s error by the importance; without one, llama.cpp’s reference quantizers. Every operation in f32 in llama.cpp’s order (its ggml-base is built without FMA), so the bytes are the same; IQ2_XXS and IQ2_XS refuse to run without a matrix, as llama.cpp asserts. IQ1_S and IQ1_M are not written.
  • The importance of a column is llama-quantize’s: the sum of the squares over the rows seen, per expert, divided by that expert’s count (1 for an expert no row reached; Imatrix::importance, inga_model::Importance).
  • inga quantize --imatrix FILE writes llama-quantize’s file types IQ2_XXS, IQ2_XS, IQ2_S, IQ2_M, IQ3_XXS, IQ3_XS, IQ3_S, IQ3_M, IQ4_NL, IQ4_XS and Q2_K_S with its mixes (the rules of llama_tensor_get_type_impl, has_imatrix included), its fallbacks (the 256-value i-quants to IQ4_NL), its refusal without a matrix (tensor_requires_imatrix), the matrix of a tensor of experts sliced per expert, and the quantize.imatrix.file, .dataset, .entries_count and .chunks_count keys at the end of the metadata.
  • inga imatrix MODEL -f TEXT [-c N] [--chunks N] [-o OUT] is E2’s inga profile without the use profile: chunks of -c tokens (default 512) starting with BOS, the matrix kept for the model in $INGA_HOME/experts/ and written to -o OUT.
  • At load, --quantize, --quantize-experts / --quantize-down and the warm and cold types of --experts-precision auto take the i-quants (Model::set_importance): the matrix of --imatrix FILE, else, for an i-quant, the one kept for the model (noted on stderr); IQ2_XXS and IQ2_XS without one are refused, and a matrix the importance does not cover (the embeddings, the output) takes Q2_K for them, as llama.cpp’s IQ2 mixes give those. The E1 cache key includes the matrix’s values, so experts converted with another matrix (or none) are not reused.
  • The model variants (2026-10-10-model-variants-design.md §3) propose IQ4_XS, IQ3_M, IQ3_XXS, IQ2_M and IQ2_XXS from a 16- or 32-bit original once a matrix is kept for it, and make them with that matrix.
  • Checked against llama.cpp aa94f20, built here: llama-quantize with and without --imatrix (the matrix llama-imatrix made) on synthetic Llama (8 layers, 256-wide), Qwen3 (four query heads per KV head, tied embeddings), Qwen3-MoE (8 experts, 256-wide) and Llama with 288-value rows (the fallbacks), in Q2_K, Q2_K_S, Q3_K_M, Q4_K_M, Q5_K_M, Q6_K, Q4_0, Q5_0, Q8_0 and the ten IQ file types: 120 files, all byte-identical (the_files_are_those_llama_quantize_writes, ignored, tools/oracle-models.md), and the row quantizers on random rows with zero blocks and outliers. The SHA-256 of llama-quantize’s files for a synthetic model and a matrix from a formula are fixtures (the_i_quant_files_are_those_llama_quantize_writes). inga imatrix against llama-imatrix on the same models and text (-b of one chunk): the same counts on the dense models, the sums within 3e-4 relative (f32 sums in another order); on the MoE models one routed row per layer goes to another expert (a near-tie of the router).

5. A model much larger than the RAM

Section titled “5. A model much larger than the RAM”

For a 1000B mixture on one PC with 32 GB, E1–E5 reduce the reads but do not remove them: decode stays bound by the SSD (one disk at 3–7 GB/s, ~14 GB per token at 2 bits less what the hot experts save). The other levers, already in Inga or planned: a second SSD (--mirror), the experts of other PCs (--expert-nodes, and the mesh in 0.24.0, which adds their RAM to the budget of §3.4), and the hybrid layers on the GPU (2026-10-10-gpu-hybrid-layers-design.md) for the attention and the output layer.
