Images: Edit by instruction, then Reference

Status: proposed on 2026-11-04, to be approved by the maintainer; nothing in it is built. The 0.44.0 item (High, third by the maintainer’s priority) in docs/todo/0.44.0.md: “an edit by instruction with Qwen-Image-Edit, then a reference picture; a short spec first, with the memory and the time measured”. It continues group C of 2026-10-14-image-generation-part3-design.md (§4, “Qwen-Image-Edit (2509 / 2511)”), on the Qwen-Image of 2026-10-12-qwen-image-design.md.

What is measured and what is estimated: the file names, sizes and revisions below were read from the Hugging Face API on 2026-11-04; the pipeline’s behaviour from diffusers’ main the same day. No time and no memory in this spec is measured: every one is an estimate from the shapes, labelled so, and §7 is the plan that measures them. Qwen-Image itself has not been timed on real files yet either (docs/todo/real-world-checks.md, “Qwen-Image (0.28.0) on the real files”).

1. What the user sees

Section titled “1. What the user sees”

  • Edit by instruction (phase 1): a picture and a sentence, “make the sky purple”, “remove the man on the left”, “write OPEN on the sign”; the rest of the picture is kept. No mask, no strength.

    The line before the drawing says what runs: editing photo.jpg (1600x1200) by instruction with Qwen-Image-Edit-2511 at 1184x896: the picture seen by Qwen2.5-VL at 448x320 and given to the transformer as 4,144 latent tokens; 40 steps at guidance 4 (the numbers of that example follow §3’s rules).

  • Reference (phase 2): up to three pictures and a sentence that names them, “the cat of picture 1 sitting on the sofa of picture 2”, a new picture of any size. --ref-image FILE (repeatable) beside, or instead of, --init-image.

  • inga serve kit://qwen-image-edit: OpenAI’s POST /v1/images/edits with image (phase 2: image[] up to three times), prompt, size (auto by default), n, and Inga’s steps, cfg_scale, seed, negative_prompt.

  • The web UI’s Images page: a tab Edit by instruction (the picture as Transform takes it, no brush, no strength, the prompt box labelled “Instruction”), then a tab Reference with three picture slots. The Models page’s “Edit by instruction” filter and quick choice, which today find no kit (Mode::Instruct: “none yet”), list qwen-image-edit.

2. What exists today

Section titled “2. What exists today”
  • The transformer is Qwen-Image’s (qwen_image.rs): 60 double-stream blocks, 3072 wide, on DiffusionOps (CPU, and CUDA behind debug.image_gpu). The three edit models have the same transformer/config.json as Qwen-Image (60 layers, 24 heads of 128, in_channels 64, joint_attention_dim 3584, rope axes 16 / 56 / 56); 2511 adds "zero_cond_t": true.
  • The text encoder is Qwen2.5-VL-7B’s language model, read through --llm (llm.rs, Template::QwenImage), text only: the final norm’s rows from the user’s turn on, at most 1024. The text_encoder/ folders of Qwen-Image, Qwen-Image-Edit, -2509 and -2511 hold the same four shards (their LFS sha256 match, read 2026-11-04), so the kit’s Qwen2.5-VL-7B-Instruct-Q8_0.gguf serves the edit models unchanged.
  • The vision tower exists for chat: inga_vision::Clip reads Qwen2.5-VL’s mmproj (qwen2.5vl_merger, windowed attention), and inga_model::Model::forward_image places image rows with M-RoPE’s 3-D positions. The image path is not wired into LlmEncoder, and forward_image gives logits’ inputs, not the final norm’s rows that the encoder needs.
  • The VAE is Wan 2.1’s, decoder only (wan_vae.rs; the video module’s video/wan_vae.rs is a decoder too). So ImageModel::load_qwen sets encoder: None and Qwen-Image cannot Transform, Touch up or Extend (kits.rs: “Qwen-Image’s VAE has no encoder in Inga: it creates only”; the use case edit-images.md, §5). Comfy-Org’s qwen_image_vae.safetensors holds the encoder (encoder.conv1, encoder.downsamples.*, encoder.middle.*, encoder.head.*, conv1: its header read 2026-11-04); the edit repositories’ vae/ is byte for byte Qwen-Image’s (same LFS sha256).
  • The edit path (edit.rs) is image to image and inpainting: Edit { image, mask, strength }, the picture’s noised latents as the start (edit_steps, latent_mask), Extend as an inpainting. An instruction edit is a different thing: the sampler starts from noise and the picture is a condition, tokens beside the noisy ones, never noised.
  • Interfaces: inga image --init-image, --strength, --mask, --extend (src/cli/image.rs, src/commands/image.rs); /v1/images/edits (images.rs, edits) reads the first image / image[] and refuses a model without a VAE encoder; the kits’ Mode::Instruct and Mode::Reference (kits.rs) and the Models page’s edit_by_instruction / reference filters with their translations exist; the Images page’s tabs are create, edit, inpaint, extend, upscale (js/images.js, IG_MODES).

3. What Qwen-Image-Edit needs beyond Qwen-Image

Section titled “3. What Qwen-Image-Edit needs beyond Qwen-Image”

The references: diffusers’ pipeline_qwenimage_edit.py (QwenImageEditPipeline, the first Edit) and pipeline_qwenimage_edit_plus.py (QwenImageEditPlusPipeline, 2509 and 2511, as their model_index.json says), transformer_qwenimage.py; ComfyUI’s comfy/ldm/qwen_image/model.py and model_detection.py; stable-diffusion.cpp’s docs/qwen_image_edit.md.

3.1 The picture through the vision tower and the prompt template

Section titled “3.1 The picture through the vision tower and the prompt template”

The prompt is encoded with the picture in it. The Plus template (2509, 2511):

with one Picture N: <|vision_start|><|image_pad|><|vision_end|> per picture, in order, before the prompt. The first Edit’s template has no Picture 1: and one picture. <|image_pad|> stands for the picture’s rows from the vision tower (one per 28 x 28 pixels after Qwen2-VL’s smart_resize: multiples of 28, between 3,136 and 12,845,056 pixels, the processor’s preprocessor_config.json). The language model runs the whole sequence (text tokens embedded, the picture’s rows in place of the pads, M-RoPE positions: the picture’s 3-D grid, the text after it from its largest position plus one), and the rows of its final norm are kept after the first 64 tokens (prompt_template_encode_start_idx; Qwen-Image’s is 34). Unlike Qwen-Image the rows are not cut at 1024: the picture’s rows are part of them.

What the vision tower sees: 2509 / 2511 resize each picture to an area of 384 x 384 at its ratio, sides rounded to 32 (CONDITION_IMAGE_SIZE); about 196 rows for a square picture. The first Edit gives it the picture at 1024 x 1024’s area (about 1,369 rows for a square: a heavier text encoding, see §6).

In Inga: Template::QwenImageEdit { plus: bool } in llm.rs; LlmEncoder gains the projector (inga_vision::Clip) and encode_with(be, prompt, pictures), which needs a Model entry point that takes mixed rows (tokens and image rows with their grid) and returns the final norm’s hidden states (today hidden_states takes tokens only and forward_image returns into the logits’ path). The 64 is checked in a test against what the template’s start tokenizes to with Qwen’s vocabulary, as Qwen-Image’s 34 is.

3.2 The picture through the VAE, as tokens beside the noisy ones

Section titled “3.2 The picture through the VAE, as tokens beside the noisy ones”

Each picture is also resized to 1024 x 1024’s area at its ratio (VAE_IMAGE_SIZE, sides rounded to 32), encoded by the Wan VAE’s encoder (the distribution’s mean, sample_mode="argmax"), normalized (z - mean) / std with the per-channel constants wan_vae.rs already has, and cut into 2 x 2 patches as the noisy latents are. At every step the transformer reads [noisy patches, picture 1's patches, ...] in the image stream and only the first n outputs (the noisy ones) are kept.

  • The Wan encoder for one frame (new, wan_vae.rs): encoder.conv1, the downsamples (residual blocks and resamplers; their temporal time_conv skipped on the first frame, as Wan’s feat_cache does), middle, head, then conv1 (the quant conv, 32 channels: mean and log-variance). As the decoder, a causal 3 x 3 x 3 kernel on the first frame is its last temporal slice. It implements ImageEncoder, so load_qwen sets encoder: Some(..).
  • A side effect: with that encoder, Qwen-Image itself can Transform, Touch up and Extend through the existing path; the qwen-image kits gain those modes once the tests below pass.

3.3 The transformer

Section titled “3.3 The transformer”
  • Positions: the noisy patches at frame 0, each picture i at frame i (1, 2, …), each grid centred on itself (scale_rope); the text rows start after the largest max(h / 2, w / 2) of all the grids. qwen_image::positions takes the list of grids.
  • 2511’s zero timestep (zero_cond_t): the timestep embedding is computed for t and for 0; in every block the image stream’s modulation (shift, scale, gate, both halves) uses t‘s for the noisy patches and 0’s for the pictures’ patches; the text stream and norm_out use t’s. Without it 2511’s edits degrade (stable-diffusion.cpp’s docs: “image editing quality will degrade significantly”). The files say which: ComfyUI’s 2511 checkpoints carry an empty tensor __index_timestep_zero__, and so does unsloth’s qwen-image-edit-2511-Q4_K_M.gguf (both headers read 2026-11-04; the 2509 GGUF has none). Inga reads the marker, where stable-diffusion.cpp needs --model-args qwen_image_zero_cond_t=true.
  • The schedule is Qwen-Image’s (the three scheduler_config.json are the same as Qwen-Image’s: max_shift 0.9 at 8,192, shift_terminal 0.02), with mu from the noisy patches only (image_seq_len = latents.shape[1]), not the pictures’.
  • Guidance: diffusers runs the negative prompt only when one is given; the cards give negative_prompt=" " and true_cfg_scale=4.0. Inga’s default negative for these models is " ", so --cfg 4 runs both passes, rescaled per token as qwen_image::guide does; the negative is encoded with the pictures too.
  • Defaults: 40 steps for 2509 and 2511 (their cards), 50 for the first Edit; Euler. The output’s size: 1024 x 1024’s area at the (last) picture’s ratio, sides rounded to 32, then to 16 (diffusers’ calculate_dimensions); --width / --height or size override it.
  • Which pipeline: the shapes of the first Edit and of 2509 are the same, so the tensors cannot tell them apart. Proposed: the kit says it; a lone file by its name (2509, 2511; Qwen_Image_Edit- alone is the first Edit) and the GGUF’s general.name when present; 2511 by its marker; else the Plus pipeline, said on the line. Open question 2.

In Inga: qwen_image::Variant { Generate, Edit, EditPlus { zero_cond_t } }, as z_image::Variant does; QwenImage::forward takes the conditioning patches and their grids; GenParams gains refs: Vec<RgbImage> (the pictures, kept apart from edit, which stays image to image); ImageModel::check refuses edit (strength, mask) on an edit model and refs on any other model, each with what to use instead.

6. Memory and time: estimates, to be measured

Section titled “6. Memory and time: estimates, to be measured”

All estimated from the shapes, none measured.

  • Weights: about 22.6 GB mapped with the kit’s files (12.8 GB transformer in Q4_K_M, 8.1 GB language model, 1.35 GB projector, 0.25 GB VAE); the smallest machine the kit promises (its need_bytes) follows from these and the activations, and is confirmed by §7.

  • Activations: by device::flux_activations’ rule (about 40 rows of 3,072 f32 per token), which must count the pictures’ tokens (today it counts the noisy ones and 1024 text rows):

    Output Pictures’ tokens Tokens (estimate) Activations (estimate)
    Qwen-Image, 1024 x 1024 none 4,096 + 1,024 text about 2.0 GB
    Edit, 1024 x 1024, one picture 4,096 about 8,420 about 3.3 GB
    Edit, 512 x 512, one picture at diffusers’ 1024² area 4,096 about 5,350 about 2.1 GB
    Edit, 512 x 512, the picture at the output’s area 1,024 about 2,280 about 0.9 GB

    (text rows about 230 after the 64 dropped: the picture’s 196 at 384² and a short prompt.) Each further picture of phase 2 adds about 4,096 tokens at 1024²’s area.

  • Time: about 2 x 20e9 x tokens operations per transformer pass for the matrices, plus 4 x 60 x 3,072 x tokens² for attention: about 3.9e14 per pass at 1024 x 1024 with one picture, about 2.2 times Qwen-Image’s at the same size with a short prompt (about 1.8e14). With guidance two passes a step, so 40 steps at 1024² are about 3.1e16 operations: about 8.6 hours at one sustained TFLOP/s, about 26 minutes for a 4-step Lightning run without guidance. At 512² with the picture at the output’s area: about 9.5e13 a pass, about 2.1 hours for 40 guided steps and about 6 minutes for 4 Lightning steps at one TFLOP/s. These are arithmetic, not timings: how many TFLOP/s Inga’s quantized products sustain on a given CPU is what §7 measures.

  • Encoding, once per drawing: the vision tower on about 784 patches (about 1e12 operations), the language model on about 300 rows twice (prompt and negative, about 9e12), the Wan encoder on a 1024² picture (to be measured; expected of the order of the decoder’s). The first Edit’s vision input at 1024² makes about 1,450 rows (about 4.4e13 for both prompts).

  • The CUDA transformer (debug.image_gpu, the GPU spec’s P2) runs the edit’s longer sequence unchanged; its memory adds the activations above to the 12.8 GB of weights.

8. Phase 2: Reference

Section titled “8. Phase 2: Reference”

10. Open questions for the maintainer

Section titled “10. Open questions for the maintainer”
  1. Which variants get a kit: only 2511 (proposed), or also 2509 and the first Edit? All three would be read as files either way.
  2. Telling the first Edit from 2509: their tensors have the same shapes. Proposed: the kit, then the file name and general.name, then the Plus pipeline by default, said on the line. Or a flag (--edit-pipeline edit|plus)?
  3. The projector’s flag: --mmproj (Inga’s chat name, proposed) or stable-diffusion.cpp’s --llm_vision (as --llm is its name), or both?
  4. The pictures’ size on a CPU: diffusers encodes every picture at 1024²’s area whatever the output’s size (2.1 GB of activations at 512², §6). Keep diffusers’ rule (proposed as the default, so the pictures match its), or encode the pictures at the output’s area when it is smaller (about 0.9 GB and about 2.5 times less work at 512²), with a flag?
  5. A Lightning kit for 2511 (4 steps, 850 MB more) in phase 1? On a CPU it is the difference between hours and minutes (§6, estimates).
  6. Reference beyond Qwen-Image-Edit: is Reference only 2509 / 2511’s multi-picture path (proposed), or should a smaller model (SDXL with an IP-Adapter) follow for machines that cannot hold 22 GB?
  7. The measurements: which machines (the table of §7.1 on a CPU only is enough?), and does the item wait for them, given that AGENTS.md says measurements on real hardware do not hold a release?
  8. The web UI: two more tabs (seven in all, proposed), or Edit by instruction as a switch inside Transform?
  9. Qwen-Image’s Transform / Touch up / Extend, which the new encoder makes possible: in this item (proposed: E1, with its tests), or a separate one?
  10. The default guidance: the cards’ cfg 4 with the " " negative (two passes a step, proposed), or stable-diffusion.cpp’s examples’ 2.5, or cfg 1 on a CPU by default (half the work)?
