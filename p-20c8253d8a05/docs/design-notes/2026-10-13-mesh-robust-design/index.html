Mesh tests without timing assumptions, and satellites that join late

Status: built for 0.28.0 (branch fix/mesh-robust; see §9, As built). Asked by the maintainer on 2026-10-13: make the mesh’s end-to-end tests reliable on the CI runners without nextest retries, and fix the product weakness behind them. Code: crates/inga-dist/src/{mesh,place,stages}.rs, src/commands/{mesh,serve}.rs, crates/inga-server/src/{lib,router}.rs, the mesh tests, .github/workflows/stress.yml.

1. Why

Section titled “1. Why”

Three failures of the mesh tests on the Windows and macOS runners (2 threads), all from a timing assumption:

  • crates/inga-dist/tests/mesh.rs a_load_shows_each_satellite_receiving_then_ready took the first receiving heartbeat (50 %) for the one that reports every byte (fixed in #553: it waits for 100 %).
  • tests/mesh.rs a_mesh_of_processes_answers_like_one_and_survives_a_satellite_leaving: inga serve --mesh --mesh-wait 6 waits 6 s, then plans with the nodes it heard. On macOS, sat-a measured its machine (CPU speed, the Metal probe) before it joined, and missed the window: two nodes instead of three (worked around in #555 by a test helper, announced(), that listens on the master’s port until both satellites announce, before the server starts).
  • Earlier, the Windows mapped files and the prefill gate (fixed).

The second one is a product weakness too: a user’s slow satellite is ignored until the model’s next load, which, in a server, may be never.

2. What changes, in short

Section titled “2. What changes, in short”
Before After
The wait before the first plan always the whole --mesh-wait ends as soon as the nodes expected are there, measured (R1); --mesh-wait stays the bound
A satellite that joins after the plan used at the model’s next load weighed at once; the model placed again between requests when it pays (R2)
A satellite’s first announcement after it measured its machine as soon as its port is bound; the measure follows (R3)
The mesh tests fixed sleeps and waits, the first event that arrives the exact condition, a generous timeout, the mesh’s JSON on failure (R4)
Before a release — stress.yml runs the mesh tests N times on Linux, Windows and macOS (R5)

3. R1. The wait ends when the nodes expected are there

Section titled “3. R1. The wait ends when the nodes expected are there”
  • The rules (Mesh::wait_for, wait_over):
    • every --peers entry answered (when there are --peers);
    • and/or --mesh-expect N: at least N other nodes alive (new option of inga serve and inga mesh show);
    • and, for either, every node heard has sent its measure (R3);
    • with both --peers and --mesh-expect, both must hold;
    • with neither, only the bound ends the wait, as before;
    • --mesh-wait stays the upper bound (default 3 s).
  • Nodes remembered from the last run: the master’s store keeps no list of the nodes ($INGA_HOME/cache/mesh holds a satellite’s parts and a master’s chunk hashes), so this rule is not built; --peers and --mesh-expect cover it.
  • Said: the event at the start (waiting up to 6 s for the other nodes (--mesh-wait), less once 2 are there (--mesh-expect), each with its measure), the load’s waiting phase (with the nodes still measuring), and the event at the end, which names the rule: the wait for the other nodes ended after 1.3 s: the 2 other nodes expected (--mesh-expect) are there, or … after 6.0 s: its bound (--mesh-wait) passed; no measure yet from sat-a: weighed when it arrives, and the model placed again between requests if it pays.

4. R2. A satellite that joins after the plan

Section titled “4. R2. A satellite that joins after the plan”
  • What the master keeps (Mesh::set_placed, Placed): for each model it placed, the satellites it weighed, the name the server serves it under, and the placement’s inputs (Estimate: what each layer weighs, the KV cache per layer, the candidates, the master first). A model that runs on the master alone because no satellite could take part of it is kept without an estimate.
  • The decision (Mesh::due_replans, every 2 s on the server): a satellite alive, measured and of this protocol, not weighed yet for a model and not left out of it, is weighed once:
    • without an estimate (the model ran alone for want of a satellite): placed again;
    • otherwise the placement code runs twice (place::replan_gain): the candidates of the plan in place, and the same plus the new satellites (seen from their announcements: free RAM less the reserve, measured speed, cache room, GPU; their round trip counted as the slowest of the plan’s, 1 ms at least). The model is placed again when that is 10 % faster (REPLAN_GAIN), or when it now fits the mesh’s memory and did not.
    • Either way it is said: sat-c joined after q.gguf was placed: placing it again between requests (about 14.2 tok/s with it against 9.8 now), or …: the plan stays (about 9.9 tok/s with it against 9.8 now: less than 10 % faster).
  • Between requests, never in the middle of an answer: the server asks Router::unload_between_requests, which unloads the model only when no request holds it, no session is busy and no load is under way (the loaded lock taken without waiting, so no request can take the model meanwhile); otherwise it asks again 2 s later. Once unloaded, the server loads it again: the load plans with every satellite there (the satellites’ caches keep the layers they had: only what they lack travels). The model’s conversations in RAM start over, as after any reload.
  • Said and shown: the events, a note: line on the console, and GET /api/inga/mesh’s new replans (model, satellites that joined, when, waiting / done / dropped, the tok/s before and expected, a note). A model that is not loaded any more when its turn comes is dropped: its next load places it anyway.
  • Only the master decides; a door that is not the master does not.

5. R3. A satellite announces itself before its measure

Section titled “5. R3. A satellite announces itself before its measure”
  • inga satellite binds its port, joins the mesh, then measures its machine (its CPU’s speed, its prompt speed, its GPUs: seconds on a slow machine, the Metal probe above all), and sends the measure at once (Mesh::announce) instead of waiting for the next heartbeat.
  • A satellite whose measure has not arrived (speed 0) is not a satellite for the master yet (NodeInfo::measured, Mesh::satellites): it is never planned on, and the wait of R1 does not end on it. The master says found sat-a …; it measures its machine, its measure follows, then sat-a sent its measure: 3.2 GB/s of weights; it may be planned on now. GET /api/inga/mesh gives each node’s measured.
  • A satellite measured after the first plan is a satellite that joins late (R2).

6. R4. Tests

Section titled “6. R4. Tests”
  • Rule: no fixed sleep, no fixed wait that a slow runner can outlast, no “first event that arrives”: each test waits for the exact condition it checks, with a generous timeout (60 s in the crates’ tests, 120 s for the processes), and on failure prints the mesh as the master sees it (to_json, GET /api/inga/mesh).
  • The servers of tests/mesh.rs start with --mesh-expect N --mesh-wait 120: the plan waits for the satellites, however long they take to measure; the announced() helper of #555 is gone.
  • Pure logic in deterministic unit tests, where it was covered end to end only:
    • the election’s ranking (elect: priority, the master in place, a model, the RAM in whole GiB, the lowest id);
    • the wait’s rules (wait_over);
    • the re-plan decision (replan_gain, Gain::worth_it) and its bookkeeping (due_replans, replan_done), with announcements handed to the node directly (no socket, no clock);
    • a satellite not measured is not a satellite;
    • the new master’s claim sent at once after a goodbye: checked without a clock (the goodbye handed to the node directly; the claim is in the old master’s socket when that returns), instead of “agreed within a second”. elect now sends the claim before it releases its lock, so whichever thread made the claim, it is on its way.
  • New tests: R1 and R3 (unit), R2 in crates/inga-dist/tests/mesh.rs (a model placed with one satellite that holds half of it, a second one joins, the next plan uses both, the same logits) and end to end in tests/mesh.rs (a server started with no satellite, one joins, the model moves to it between requests, the same answer).

7. R5. The stress workflow

Section titled “7. R5. The stress workflow”
  • .github/workflows/stress.yml, workflow_dispatch only. Inputs: the number of runs in a row (default 30), the runners (default ubuntu-latest,windows-latest,macos-latest) and nextest’s --test-threads (default 2, as the runners).
  • It runs the mesh tests (the mesh group of .config/nextest.toml) with nextest’s stress mode (--stress-count N, nextest 0.9.146 as CI), stops at the first failure, and names the failing test in the job’s summary.
  • No retries in .config/nextest.toml: a flaky test is a bug to fix, not to hide.
  • AGENTS.md and docs/RELEASING.md: it is run before a release tag when the mesh code changed.

Section titled “8. Files”

  • crates/inga-dist/src/place.rs: REPLAN_GAIN, Gain, replan_gain.
  • crates/inga-dist/src/stages.rs: MeshSetup::served, the placement recorded at every end of MeshStages::plan, weigh.

  • src/cli.rs, src/completions.rs: --mesh-expect.
  • src/commands/mesh.rs: the satellite measured after it joins, settle with the rules, the model alone recorded for R2; src/commands/serve.rs: the served name and the re-plans wired to the server.
  • The tests named in §6; .github/workflows/stress.yml; AGENTS.md, docs/RELEASING.md, README.md, docs/use-cases/run-a-model-on-a-mesh.md, docs/api/inga.yaml, CHANGELOG.md, TODO.md.

9. As built

Section titled “9. As built”

As specified above. On the development machine (4 cores, Linux), the 42 tests of the mesh group (the inga-dist mesh and placement unit tests, crates/inga-dist/tests/mesh.rs and tests/mesh.rs) ran 30 times in a row pinned to two cores (taskset -c 0,1) with nextest’s --stress-count 30 --test-threads 2 --fail-fast, as stress.yml runs them: 30 of 30 passed, about 40 s per run (20 minutes in all). The end-to-end test of a mesh of processes takes about 9.5 s, the wait for its two satellites about a second instead of a fixed 6 s. stress.yml on the three hosted runners is the maintainer’s to start (manual only).
