API nodes: remote and frontier models in the mesh, with routing and fallback

Status: decided, 2026-10-10 (asked by the maintainer: “add servers from the command line and, from the GUI, a list of remote nodes reached through their API, that we put in our network of nodes; they hold whole models, not parts, and the master uses them; being APIs, they can also be frontier models; then routing and fallback rules”). The open choices of §9 were decided by the maintainer on 2026-10-10, each as recommended. A1–A2 shipped in 0.26.0 (#406); A0 (the web UI’s remote mode, brought back from 0.27.0) shipped in 0.26.3; A3–A4 and part 2 (A5–A7) are scheduled in 0.26.5, with the mesh and router part 1 (TODO.md). On 2026-10-11 the maintainer approved the additions taken from free-claude-code (§2.4): provider presets, client model mapping, reasoning translation, a global fallback list and inga connect. A1–A2 are built (see “As built” at the end); in 0.26.5, A3 and A5 (without budgets) and the rules and failover: "continue" of A6 (see “As built: routes”); A4 and A7 are not.

Related specs, not repeated here:

  • Inga mesh: discovery, satellites, groups, the elected coordinator, the Mesh page. An API node is a fourth kind of member next to the master, satellites and doors (§3.1 below).
  • Inga router: how a door picks an Inga node for a request (eligibility, prefix-cache score, affinity). Its §3.4 (virtual models, external engines, cloud fallback) is specified here: this spec replaces that sketch with the full design.
  • Local data: inga data lists what Inga keeps; the node list and the key store join it (§4.4).

1. The idea

Section titled “1. The idea”

Inga today runs models itself, on one PC or split across several. An API node is a server that already answers an inference API: another inga serve, an Ollama or LM Studio on a colleague’s PC, a vLLM box, or a provider (OpenAI, Anthropic, Google, Mistral, Groq, OpenRouter, Together…). It joins the mesh as a node that holds whole models: the master never sends it layers, it sends it whole requests and streams back the answer.

What this gives the user:

  1. One catalog. /v1/models, the web UI’s model list and inga list --all show local models, mesh models and API models together, each with where it runs, its capabilities and its cost.
  2. One endpoint. Every client already pointed at inga serve (OpenAI, Anthropic, Ollama, LM Studio, KoboldAI APIs) reaches frontier models through it, with the protocol translated by Inga when the node speaks another one.
  3. Rules. Which model answers which request, what happens when it fails, what may never leave the machine, and how much may be spent.

The local-first goal stays: nothing is sent to an API node unless the user added it, and a request tagged local-only never is.

2.4 free-claude-code (surveyed 2026-10-11)

Section titled “2.4 free-claude-code (surveyed 2026-10-11)”

free-claude-code (Python, AGPL-3.0, ~57k stars) is a local proxy for coding agents (Claude Code, Codex, OpenCode, Aider, Cline…): it serves Anthropic’s Messages API and forwards to about 60 providers (OpenRouter, Groq, Cerebras, NVIDIA NIM, DeepSeek, Kimi, Z.ai, Bedrock, Vertex, Azure…) and to local servers (Ollama, LM Studio, llama.cpp). What it adds to the projects above:

  • Provider presets: a provider is picked from a list (base URL, wire format and prefix known); the user only pastes a key. Custom OpenAI-style endpoints are added by URL, key and format.
  • Models addressed as provider/model, and per-tier mapping for the client: MODEL_OPUS, MODEL_SONNET, MODEL_HAIKU, MODEL_FABLE send each Claude Code tier to any model, with MODEL as the default.
  • Reasoning control per tier: from the client, off, or a forced level (low … max), translated to each provider.
  • A global ordered fallback list tried after the retries, with the warning that a failed request may use credits at more than one provider.
  • Launchers (fcc-claude, fcc-codex) that start an agent with the right environment, and fcc-doctor for diagnostics.
  • Not taken: logins to personal subscriptions (ChatGPT, Copilot — terms of service), chat bots (OpenClaw covers them), its code (AGPL; ideas only).

2.3 Lessons for Inga

Section titled “2.3 Lessons for Inga”
  1. Aliases are the user’s handle (LiteLLM’s model_name, Open WebUI’s prefixes, llama-swap’s peer/model): clients ask for a name; the rules decide which node answers it.
  2. Eligibility first, then a score (OpenRouter’s require_parameters, LiteLLM’s pre-call context check, PAIR): a node that cannot take the request (context too long, no vision, no tools, a privacy tag) is removed before any strategy runs.
  3. Fallback by error class, not “any error” (LiteLLM’s three lists, Portkey’s on_status_codes): a context overflow goes to a longer-context model, a 429 to another node after its Retry-After, a 400 goes straight back to the client.
  4. Cooldown / circuit breaker per node (LiteLLM’s allowed_fails + cooldown_time, Portkey’s cb_config, Envoy’s outlier detection).
  5. Failover before the first token only by default (everyone); continuing a partial answer elsewhere is an explicit opt-in (LiteLLM’s mid-stream fallback, api7’s mode: continue).
  6. Keys server-side (Open WebUI, LiteLLM); env-var references in files (LiteLLM’s os.environ/, llama-swap’s ${env.}); listed redacted (Jan).
  7. Costs from a price table plus the usage each response reports; budgets per key (LiteLLM), token-based limits (Envoy).
  8. Privacy as routing input (OpenRouter’s data_collection / zdr), not a documentation footnote.
  9. Learned routing is a later layer on top of explicit rules (RouteLLM, NVIDIA LLM Router), and works best as “cheap vs strong” with a tunable threshold.
  10. Presets beat forms (free-claude-code, Jan): known providers come with their URL, wire format and prefix; adding one is choosing it and pasting a key.
  11. Map what the client asks for (free-claude-code’s tiers): coding agents send fixed model names (claude-opus-*, claude-sonnet-*, gpt-*); a mapping table turns them into Inga aliases, so the agent’s own configuration is left alone.
  12. Translate reasoning, not only messages: the client’s thinking controls become each provider’s own parameter (reasoning_effort, a thinking budget, Qwen’s on/off), and an alias may force a level.

3. Design

Section titled “3. Design”

3.1 What an API node is

Section titled “3.1 What an API node is”

An API node is a mesh member with the role compute (mesh §4.3) that

  • holds whole models only: it is never given layers, experts or slices, and never joins a split group (it may be the single member of a one-node group, mesh §4.6);
  • is reached over HTTP(S) with one of the APIs Inga already serves, as a client:
kind Endpoints used Model list Capability data
inga Inga’s own APIs /v1/models + /api/inga/model full: capabilities, context, placement, load (as satellites)
openai (default) /v1/chat/completions, /v1/completions, /v1/embeddings, /v1/responses when present /v1/models context length and modalities when the server adds them (vLLM’s max_model_len, OpenRouter’s catalog), else the table of §3.4

vLLM, SGLang, llama-server, LocalAI, TGI, Groq, Together, Mistral, Google’s OpenAI-compatible endpoint, Azure OpenAI (with a deployment map) and OpenRouter are all openai.

  • has a name (work-pc, openai, claude), used as the prefix of its models’ ids in the catalog (claude/claude-sonnet-4-5), and optional tags (cloud, lan, trusted, zdr) that rules match on.

An inga serve on another PC can be a satellite (it joined the mesh with the mesh’s secret, mesh §3.2) or an API node (added by URL and API key, without the mesh): the second is how a server outside the LAN, or owned by someone else, is used whole.

3.4 Capabilities when a node does not say

Section titled “3.4 Capabilities when a node does not say”

Most openai and anthropic endpoints list ids only. Inga fills the gaps from, in order: what the node reports (§3.1), a built-in table of well-known model families (context, vision, tools, reasoning, prices; shipped with Inga in crates/inga-server/src/api_nodes/catalog.json, dated, updated with releases), and the user’s overrides in nodes.json ("overrides": {"gpt-5": {"context": 400000}}). A capability unknown from all three is treated as absent for routing (a request with an image never goes to a model not known to read images) and shown as “unknown” in the web UI. A request that fails with a context or capability error corrects the entry for the session.

3.5 Forwarding a request

Section titled “3.5 Forwarding a request”
  • Same protocol: the request is forwarded as it came, with the node’s key and the node’s model id; the stream is passed through; the answer’s model field is the catalog id that answered.
  • Different protocol: Inga translates (OpenAI ⇄ Anthropic ⇄ Ollama), using the converters its server already has for its own APIs (messages, tools, images, reasoning, streaming events, usage). Fields with no equivalent are dropped with an inga.warnings entry (OpenAI’s logit_bias to Anthropic, for instance).
  • Inga-only features (grammars, n, DRY, watermark, LoRA per request) are refused with a clear 400 when the chosen node cannot honour them, unless the rule allows dropping them (drop_unsupported: true); eligibility (§5.2) prefers a node that can.
  • Server tools (web search; memory, documents and skills from 0.24.0) run on the master: the remote model sees the tool definitions and the master executes the calls, as for a local model.
  • Headers: the client’s API key for Inga is never forwarded; the node’s key is added; X-Inga-Node and X-Inga-Route (the rule that matched) are added to the response.

Section titled “3.6 Provider presets”

The first table: OpenAI, Anthropic, Google AI Studio, Mistral, Groq, Cerebras, DeepSeek, xAI, OpenRouter, Together, Fireworks, DeepInfra, NVIDIA NIM, Hugging Face Inference, Ollama, LM Studio, llama-server, vLLM, another Inga. 3.10 Legal notes

Section titled “3.10 Legal notes”
  • The user’s keys, the provider’s terms. An API node calls a provider with the user’s own key and account, so the provider’s terms of service and usage policies apply to the user. Inga says so where a node is added (inga node add, the Mesh page) and in docs/use-cases/use-external-models.md.
  • No circumvention. Inga never offers features whose purpose is to get around a provider’s limits or terms: no pooling of free tiers across accounts, no scraping of providers’ web interfaces. Presets point at official APIs only. A node may hold several keys the user is entitled to use (a pool, key pools), but for failover only: the next key is used when the current one is rate-limited, out of quota or rejected, never in turns to add up limits. When two keys of a pool answer for the same account, Inga warns that they share that account’s limits (decided by the maintainer on 2026-10-14).
  • Data leaves the machine. A request routed to a cloud node sends its content to that provider: the model’s badge (☁), X-Inga-Node / inga_route and the web UI’s footer say where each answer comes from, --no-cloud and local-only rules keep data local, and PII masking (users U5) is the stronger option for organisations.
  • Translation is interoperability. OpenAI’s and Anthropic’s wire formats are implemented from their public documentation, as other servers do; no client or provider code is copied.

4. Secrets

Section titled “4. Secrets”

4.1 Rules

Section titled “4.1 Rules”
  • Keys never reach the browser: the web UI sends a key once when a node is added and never reads it back; GET routes return "key": "set" or "key": "env:VAR".
  • Keys are never logged: the tracing layer and /metrics redact Authorization, x-api-key, api-key headers and any field named *key* / *token*; errors from a node are logged with the key replaced by *** if it echoes it back.
  • Keys are never on the command line (only key-env=), never in nodes.json in clear, and never in inga node list, inga data, bug reports or the OpenTelemetry spans.

4.2 Where a key lives (choice in §9.2)

Section titled “4.2 Where a key lives (choice in §9.2)”
  1. an environment variable named in the node (key-env), the default for servers and containers (Docker secrets, systemd LoadCredential, the service of 0.24.0);
  2. the key store $INGA_HOME/secrets.json: each key encrypted with ChaCha20-Poly1305 (ring, already a dependency through rustls) under a machine key in $INGA_HOME/secret.key, both files readable by the owner only (0600 on Unix, an owner-only ACL on Windows). This protects against a copied nodes.json, a backup or a screenshot, not against someone with the user’s account; the guide says so;
  3. later, the OS keychain (Windows Credential Manager, macOS Keychain, Linux Secret Service) when it can be reached without a C library.

4.3 In the mesh

Section titled “4.3 In the mesh”

Doors need the keys to call API nodes. The replicated state carries them encrypted with the mesh’s secret (mesh §3.5); a node that leaves the mesh keeps nothing in clear. A node with the role door only and the tag no-cloud never receives cloud keys.

4.4 inga data

Section titled “4.4 inga data”

inga data list gains nodes ($INGA_HOME/nodes.json: one entry per node, its name, kind and URL) and secrets ($INGA_HOME/secrets.json: the node names that have a stored key, never the keys). inga data clear secrets deletes every stored key after a confirmation.

5. Routing and fallback rules

Section titled “5. Routing and fallback rules”

5.1 Where rules live

Section titled “5.1 Where rules live”

In $INGA_HOME/routes.json (edited by hand, by inga route … or by the web UI’s Routes tab on the Mesh page), or --routes FILE. The router spec’s virtual models (router §3.4) are these rules.

A route is a name clients ask for, and an ordered list of targets with conditions; the first eligible target wins, the next ones are the fallback chain.

5.2 How a target is chosen

Section titled “5.2 How a target is chosen”

For each request the door does, in order:

  1. Resolve the name: a catalog id is a route with one target; an alias expands to its targets; a target may name another route ("hard": "chat"), depth ≤ 4, cycles refused when the file is loaded.
  2. Eligibility (each failing target is skipped, and the reason kept for X-Inga-Route and the web UI):
    • capabilities the request needs: images or audio in it, tools, a response_format / grammar, reasoning, embeddings;
    • context: the prompt’s tokens (counted with the local tokenizer when the model is local, otherwise estimated at 1 token per 3.5 characters, rounded up, plus max_tokens) within the target’s context; if.context_max / context_min;
    • privacy: the request’s tag (X-Inga-Privacy: local-only|lan-only, a per-key or per-user default, a per-chat switch in the web UI, or the route’s own privacy) against the target’s privacy (§3.3); local-only is enforced here, before anything is sent, and cannot be overridden by a rule;
    • cost ceiling: the estimated cost (prompt tokens × input price + max_tokens × output price) under if.max_cost_usd, and the node’s or key’s budget not spent;
    • availability: the node is up and not cooling down (§5.4), within its max_concurrency and rate limits, and the model loaded or loadable;
    • policies: allow / deny lists by API key, user (0.26.0), header.
  3. Strategy among the eligible targets of one step (a step is one target, or a list in "any": [...]): order (the default: the first eligible), least-busy, latency (lowest measured time to first token, moving average), cost (lowest estimated cost), weighted ("weight" per target), affinity (the router spec’s prefix-cache score, for local and mesh targets), classify (§6).
  4. Send; on failure, apply §5.3 and try the next eligible target.

5.3 Failures

Section titled “5.3 Failures”
What happened Default
connection refused, DNS, TLS, timeout before the first byte retry the same target with backoff (500 ms, then 4 s, ± 20 % jitter), up to retries, then the next target
HTTP 429 honour Retry-After (seconds or date; capped by max_wait, 10 s): wait and retry if within the cap, otherwise cool the node down for Retry-After and go to the next target
HTTP 500, 502, 503, 504, 529 (Anthropic “overloaded”) count a failure, next target
context too long (OpenAI context_length_exceeded, Anthropic invalid_request_error on length, Ollama’s message) mark the entry’s context (§3.4), next target with a larger context only
content refused by the provider (content_filter, a policy refusal) the error to the client, unless the route sets on_refusal: "next" (LiteLLM’s content-policy fallback)
HTTP 400, 401, 403, 404, 422 the error to the client (a bad key or request will not get better elsewhere); 401 / 403 mark the node down: key rejected in the web UI
the stream breaks after the first token §5.5

Every failure is recorded with the node, model, status and time, shown in the node’s details and counted in /metrics (inga_api_node_errors_total{node,code}).

5.4 Cooldown and circuit breaker

Section titled “5.4 Cooldown and circuit breaker”

Per node and model: after cooldown.fails failures (connection errors, 5xx, 429) in cooldown.window (60 s), the target is open for cooldown.seconds (60 s, doubled at each re-open up to 15 min); then half-open: one request is let through, success closes it, failure re-opens it. A health probe (the model list, every 30 s while open) can close it early. When every target of a route is open, the door tries the one that opened first rather than failing without a try (Portkey’s bypass).

5.5 Streaming: before and after the first token

Section titled “5.5 Streaming: before and after the first token”
  • Before the first token (the default failover: "before-first-token"): nothing has reached the client; the request is resent to the next target as if it were the first; the client sees a longer wait only. The door holds the response headers until the first token, then commits.
  • After the first token, by default the stream ends with the API’s error event (OpenAI: an error object in the last chunk, Anthropic: an error event, Ollama: {"error": ...}) and finish_reason: "error"; the partial answer is kept in the web UI’s chat with a Continue elsewhere button.
  • Opt-in failover: "continue": the door sends the next target the conversation plus the partial answer as an assistant prefill (Anthropic’s prefill, OpenAI’s continue_final_message on servers that take it, Inga’s own API natively) and splices the rest into the same stream. The answer may change voice at the splice; an inga.splice field in the final chunk says where and which node finished it. For split groups, the mesh’s replay (mesh §3.6) gives an identical continuation instead.

5.6 Rate limits of our own

Section titled “5.6 Rate limits of our own”

A node’s limits (rpm, tpm, max_concurrency) are enforced by the door before sending, so Inga does not hit the provider’s 429s in the first place; requests over the limit wait in the mesh’s shared queue (mesh §4.7) up to queue_timeout, then go to the next target.

5.7 The global fallback list

Section titled “5.7 The global fallback list”

Besides each alias’s chain, fallback in nodes.json is an ordered list of targets tried, after a request’s own chain and retries are exhausted, for every alias that does not opt out ("global_fallback": false). The same eligibility applies (a local-only request never leaves the machine). Every answer that came from a fallback says so in the footer and in inga_route (which targets failed and why), and the docs warn that one request may then use credits at more than one provider.

6. Learned routing (part 2)

Section titled “6. Learned routing (part 2)”

A classify route sends each request to a class’s target. Three ways, all local:

  1. Rules on the request (length, tools present, an image, keywords, the system prompt), cheap and explainable: the default.
  2. A small classifier with Inga’s own Engine::classify (0.15.0) on a small local model, as NVIDIA’s LLM Router v2 does with intent classes (simple, code, reasoning, creative, …) described in the route.
  3. A strong / weak router as RouteLLM: a score from a small model’s embeddings (Inga’s BERT encoders) and a threshold that sets the share sent to the strong model; trained offline on preference data, shipped as a small file, the threshold tuned with inga route calibrate on the user’s own past prompts (which stay local).

The decision and its reason are in X-Inga-Route and the web UI, so a user can see why an answer came from the cloud.

7. Usage and cost accounting

Section titled “7. Usage and cost accounting”
  • Every answer’s usage (prompt, cached, completion, reasoning tokens) is read from the node’s response (usage, Anthropic’s usage, Ollama’s prompt_eval_count / eval_count), or counted by Inga when the node gives none.
  • Cost = usage × the price of §3.4 (or the node’s own cost field, as OpenRouter returns it); local models cost 0 (an optional energy price per kWh is a later idea).
  • Kept per node, model, route, API key (0.24.0’s named keys) and day in $INGA_HOME/usage/ (one JSON-lines file per month; listed by inga data), shown in the web UI (Mesh page: spend today / this month per node; the chat’s answer footer: the node and the cost), /metrics (inga_api_node_tokens_total, inga_api_node_cost_usd_total) and inga node usage [--month].
  • Budgets: per node, route or API key, per day or month; a target over budget is ineligible (§5.2); at 80 % a warning in the log and the web UI.

8. The web UI and remote nodes

Section titled “8. The web UI and remote nodes”

8.1 Proxy mode (the default)

Section titled “8.1 Proxy mode (the default)”

The web UI always talks to its own inga serve. API models appear in its model picker with a badge (☁ cloud, 🖧 LAN) and their price; choosing one sends the chat to the local server, which forwards it (§3.5). So: no CORS, keys stay on the server, rules and privacy tags apply, usage is counted, and the chat looks the same whatever answers it. A chat can be marked local only (a lock in the composer), which sets X-Inga-Privacy: local-only on its requests.

8.2 Remote mode (A0, built in 0.26.3)

Section titled “8.2 Remote mode (A0, built in 0.26.3)”

The web UI served by one Inga can point at another Inga server (Settings → Server: URL and API key), for a PC with the models and a laptop with the browser: the page then calls that server’s APIs directly (it must allow the page’s origin with --cors, and the key is kept in the browser’s storage for that origin, as the API tester does today). This is useful without any mesh, and it is the first step of A0 (§10).

As built (0.26.3): Settings → Server (and Server… at the top of the Models tab, where a server with no model opens) asks for the address and the key; Test and Connect probe GET /v1/models with the key and GET /api/inga/version, and say which of these it is: the server cannot be reached (a request without CORS fails too), it answers but does not allow the page’s origin (a no-cors request succeeds where the CORS one fails: start it with --cors ORIGIN), it needs a key, the key is refused (401) or may not list the models (403), or it is not an Inga server. Connected, the address and the key are kept as inga.remote in the browser’s storage for the page’s origin, and the page reloads: every request to a path of the APIs (/v1/..., /api/...) goes to that server with its key, so the chat, the model menu and the Models, Server, API (its curl lines and base URL too), Memory, Schedules and Storage tabs are the other server’s; the chats stay in the browser. A bar across the top names the server, turns red with the reason when a request cannot reach it or its key is refused, and has Change… and Back to this server (which forgets the address and the key). No server change: --cors already answered the preflight and put Access-Control-Allow-Origin on every response, 401s included.

8.3 Direct mode (optional, later)

Section titled “8.3 Direct mode (optional, later)”

A switch to let the browser call an OpenAI-compatible endpoint itself (Open WebUI’s “direct connections”), for a user’s own key on a public server: off by default, with a warning that the key is stored in the browser and that rules, privacy tags and usage accounting do not apply. Only if users ask for it (§9.6).

9. Decisions (decided 2026-10-10)

Section titled “9. Decisions (decided 2026-10-10)”

The maintainer approved every recommendation below on 2026-10-10 (marked Decided); the other options are kept to show what was weighed.

9.1 The node file format

Section titled “9.1 The node file format”
  • A. JSON (nodes.json, routes.json): what settings.json and model-dirs.json already use, serde_json already a dependency. Decided.
  • B. TOML: nicer to edit by hand, comments; needs the toml crate (pure Rust).
  • C. Both, TOML read and JSON written by the GUI: two formats to keep in step.

9.2 Where keys live

Section titled “9.2 Where keys live”
  • A. Environment variables only: simplest, nothing on disk; the GUI cannot add a key.
  • B. Environment variables, plus the encrypted key store of §4.2 for keys added in the GUI or with --key-stdin. Decided: the GUI works, the file is not readable if copied.
  • C. B plus the OS keychain from the start: the strongest, but three platform APIs to reach through FFI without C libraries; better later.

9.3 Where the rules live

Section titled “9.3 Where the rules live”
  • A. In nodes.json with the nodes.
  • B. A separate routes.json, the same file the router spec’s virtual models use. Decided: nodes say where models are, routes say which one answers.
  • C. In the model presets of the web UI only: no CLI, no file.

9.4 Failover after the first token

Section titled “9.4 Failover after the first token”
  • A. Never by default; failover: "continue" per route as an opt-in (§5.5). Decided: honest by default, useful when wanted.
  • B. Never: the client retries.
  • C. Always continue elsewhere: answers change voice silently.

9.5 Cloud nodes and the “local first” goal

Section titled “9.5 Cloud nodes and the “local first” goal”
  • A. Cloud nodes only as the last fallback of a route (router spec’s first idea).
  • B. Cloud nodes as first-class targets, but nothing cloud in the default routes, a ☁ badge everywhere, and local-only enforced before any send. Decided: the maintainer asked for frontier models as nodes.
  • C. A build or a flag (--no-cloud) that disables cloud kinds entirely, for companies: cheap to add on top of B; decided with B (a --no-cloud flag).

9.6 The web UI and remote servers

Section titled “9.6 The web UI and remote servers”
  • A. Proxy mode only for API nodes (§8.1), plus the remote mode to another Inga (§8.2). Decided.
  • B. A plus direct mode for any OpenAI endpoint from the browser (§8.3).
  • C. Direct mode only: simplest, but keys in the browser and no rules.

9.7 Learned routing

Section titled “9.7 Learned routing”
  • A. Rules first (0.24.0), Engine::classify intent classes in 0.25.0, the RouteLLM-style strong / weak score after measuring A and B. Decided.
  • B. Rules only.
  • C. Ship a RouteLLM-style router at once: needs training data and a model Inga does not have yet.

9.8 An inga API node vs a satellite

Section titled “9.8 An inga API node vs a satellite”
  • A. Both exist: a satellite for PCs in the mesh, an inga API node for a server reached by URL and key (another owner, another network). Decided.
  • B. Only satellites; outside servers join the mesh over the internet (0.25.0).
  • C. Only API nodes; satellites are for split groups.

11. Out of scope

Section titled “11. Out of scope”
  • Splitting a model across API nodes, or giving them layers: they hold whole models.
  • Hosting a public gateway for others (accounts, billing, payments): Inga is for the user’s own machines and keys. Named keys (0.24.0) and users (0.26.0) are as far as it goes.
  • Provider-specific APIs beyond the four protocols of §3.1 (Bedrock’s and Vertex’s native APIs: use their OpenAI-compatible endpoints or a LiteLLM in front).
  • Semantic caching of answers, guardrails and prompt rewriting (Portkey’s, Kong’s): possible later, not part of routing.
  • Fine-tuning or batch jobs on providers.

A1–A2 (0.26.0, crates/inga-server/src/api_nodes/, nodes.rs, src/commands/nodes.rs; merged with main on 2026-10-11, after the mesh part 1, named API keys and scheduled tasks):

Privacy: the tags cloud, lan, local, else the address (loopback local, private ranges and .local names lan). The openai kind’s URL is the API base (/v1 included); a bare http://host:port gets /v1.
  • keys.rs: the key store as §4.2, the node’s name as the associated data (a key moved under another name does not open). On Unix both files are 0600; on Windows the owner-only ACL is not set yet (no FFI in this crate): the files rely on the profile’s permissions.
  • presets.rs: the 19 presets of §3.6 (no prices), tested to parse. Since widened to 113 in three groups (cloud providers, gateways, servers), with -anthropic presets for providers’ Anthropic-compatible endpoints, {NAME} placeholders in URLs filled from the variable NAME (or asked for by inga node add), lists_models asking for --models, aliases for other tools’ provider names, inga node presets --search; the list and its sources in docs/api-node-presets.md.
  • client.rs: ureq with no redirects, a connect timeout of 10 s, the node’s timeout (300 s) for the head of an answer, bodies capped (64 MiB whole, 512 MiB streamed, 16 MiB lines); errors a node echoes the key in are redacted. Model lists: OpenAI’s (with OpenRouter’s catalog fields and vLLM’s max_model_len), Anthropic’s, LM Studio’s /api/v0/models, Ollama’s /api/tags plus /api/show for the first 64 models.
  • catalog.rs / catalog.json: the dated table of §3.4 (globs on the id’s last segment), then the node’s overrides.
  • forward.rs (same protocol): OpenAI routes go to every kind but anthropic (Ollama, LM Studio and Inga serve them), /v1/messages to anthropic and inga, /api/chat|generate|embed|show to ollama and inga; requests that use the server’s web search, memory or documents are not passed through. web_search and inga_memory are removed for nodes that are not Inga. The answer’s "model":"…" is rewritten textually, nothing else.
  • wire.rs (different protocol): State::generate sends any other request — from any client API, and the web search loop — as OpenAI chat completions or Anthropic Messages, streamed, and reads the text, reasoning, tool calls and usage back as a local generation’s; images are re-encoded as PNG (the pixels Inga decoded); audio, video, grammars, LoRA, log-probabilities and /infill are refused with a 400. Token counts the node does not give are estimated (3.5 characters per token) and the answer says so (inga_route.estimated_usage).
  • The GUI (merged into the Mesh page by the maintainer’s decision of 2026-10-11): the Mesh page shows every node in one list of cards — the machines of the mesh when the server is in one (graph, split, decisions as before), then the API nodes with their API, address, where the key is, state, latency, requests and failures, models, and Test, Disable / Enable, Remove (nodes of --api-node: Test only); under the list, the add form (preset or URL, kind probed, key or variable, tags, Test, Add), the model_map and Read the model lists again. The page is always in the menu (before, only in a mesh); a saved view nodes opens it. Routes /api/inga/nodes, /test, /remove, /enable, /refresh (nodes.rs).
  • The mesh’s view: GET /api/inga/mesh adds the API nodes to nodes, in a mesh or not (api_nodes::with_api_nodes): "kind": "api", "role": "api", the id api:NAME, the API in api, the fields of /api/inga/nodes (never a key); the mesh’s machines get "kind": "inga". inga mesh show adds the nodes saved on its machine (their lists not read) and prints them after the machines.
  • Clients (the maintainer’s decision of 2026-10-11): the server’s named API keys of --api-keys (keys.rs), no key mechanism of the nodes’ own; the provider keys of §4.2 are only what Inga sends to the providers. /api/inga/nodes* and /api/inga/mesh are admin routes (keys::group); a key’s models check the model that answers — a node’s catalog id NODE/MODEL, after model_map (State::model_id) — so claude/* allows a node and qwen3* never matches work-pc/qwen3...; requests per minute count a node’s request as a local one, and the tokens of tokens per day and the usage are the node’s: a translated request’s (State::generate_remote), a passed-through answer’s usage (OpenAI, the Responses API, Anthropic’s message_start / message_delta, Ollama’s counts; whole or streamed, kept when the client leaves early), else estimated at 3.5 characters per token from the request and the text that came back (forward::Tally). Tested by named_api_keys_govern_the_api_nodes (tests/api_nodes.rs).

As built: routes

Section titled “As built: routes”

A3, A5, part of A6 (0.26.5, crates/inga-server/src/api_nodes/routes.rs, crates/inga-server/src/routing.rs, src/commands/route.rs), with R2 of the network of models:

  • routes.json as §5.1, plus: defaults.max_wait (§5.3’s cap), defaults.cooldown.window, defaults.strategy, a route’s max_cost_usd (a ceiling for all its targets), retries, privacy (local-only / lan-only, as if every request said it), global_fallback: false, on_refusal: "next", {"any": [...], "strategy": S} groups; for classify and best-by-eval, rules ({"if": {keywords, min_tokens, max_tokens, tools, images, system, category}, "class"}), classifier (a local model, or {model, instruction, labels: {class: description}}), default, categories. A target is a string or {model, if: {privacy: not-local-only|not-lan-only, context_max, context_min, max_cost_usd}, weight}. Read when the server starts and again when the file changes (looked at every 2 s, with nodes.json); a file with a mistake is refused, named on stderr and in GET /api/inga/routes, and the routes stay as they were. budget policies are read and not applied (said once): budgets come with the named API keys’ part 2.
  • Resolution: a route’s name shadows a model of the same name (its targets may name that model); model_map may map a client’s name to a route; a model named directly is a route of one target, with the global fallback list after it when the list is not empty (then only privacy, the policies and the key’s models are checked for it: the model says itself what it cannot do).
  • Eligibility as §5.2, in this order: privacy (X-Inga-Privacy, the route’s), the target’s if.privacy, the policies (labels local, lan, cloud, mesh = local or LAN, api, a node’s name or node:N, tag:T, model:GLOB; matched by header Name: value (* any), api_key (a glob) and route), the API key’s models (the admission check is skipped for a route: its targets are checked here), capabilities (an image, audio, tools, embeddings: unknown is absent for an API node, tried for a local model not loaded, whose inputs are known once loaded), context (the prompt estimated at 3.5 characters per token plus max_tokens), the cost ceiling (output tokens: max_tokens, else 4096; a price unknown is never under a ceiling), the node disabled or its key refused, the target’s breaker, max_concurrency. The per-key and per-user privacy defaults and the web UI’s per-chat lock are not built (a key policy with deny: ["cloud"] does the first).
  • Strategies as §5.2 step 3: with a strategy other than order, a route’s single targets form one step ranked by it; any groups are steps of their own. latency: an exponential moving average (0.3) of the time to the first text, unmeasured targets first; weighted: sampling without replacement; affinity: rendezvous hashing (FNV-1a) of the conversation’s key (the client’s user or metadata.user_id, X-Inga-Session, else its first two messages) with each target — no prefix-cache score (the router’s part 1 is not built). classify: the route’s rules, then its classifier (Engine::classify on a model of this server, loaded if needed), then the built-in rules (an image → vision, tools → tools, inga_engine::prompt_category → code / math / writing, 2000 prompt tokens or more → hard, else general, simple, the route’s default, its first class); the class’s target first, then the route’s own targets as its fallback.
  • Running a plan (routing::generate, and routing::pass_through for requests passed through as they came, until a target needs the request translated or run here; the rest of the chain is then answered by generate, the targets tried skipped): §5.3 as written, with a context error read from the message (context_length_exceeded, “maximum context”, “prompt is too long”, …), the next targets limited to larger known contexts; a request a node cannot take (audio, a grammar, LoRA, …) goes to the next target; this server’s models: a 5xx (a load failure) goes on, a 4xx to the client. Breakers per target as §5.4, in memory (no health probe while open: the half-open request is the probe). Passed-through answers are committed at the node’s status line, so a stream that breaks after a 200 but before its first token is not failed over (a translated one is).
  • failover: "continue" (A6): for translated requests (a route with it is never passed through); after the first text, the next target that is an API node gets the conversation plus the partial answer (trailing spaces trimmed) as a last assistant message — Anthropic’s prefill, continue_final_message: true and add_generation_prompt: false for the other kinds (vLLM’s parameters); this server’s models cannot continue a partial answer yet and are skipped. The answer is the two parts joined; inga_route.splice is {at_chars, from, to}.
  • What the answer says: X-Inga-Route (passed through) and inga_route.route: route NAME [class by how] -> TARGET (why), (global fallback) when it came from the list; inga_route adds name, class, failed (each target tried and why), fallback and splice; answers of this server’s models through a route get an inga_route too (kind: "local", node empty). The response’s model is the route’s name on translated answers, the target’s id on passed-through ones.
  • GET /api/inga/routes (file, text, error, routes, fallback, each target’s measures, the best-by-eval score tables, the last 50 decisions), PUT /api/inga/routes (checked, then written), POST /api/inga/routes/explain; inga route list | show NAME | check [FILE] | explain NAME -p TEXT (offline: the saved nodes’ lists read now, names no node has taken for local models, nothing measured); the Mesh page’s Routes section (the targets’ measures and breakers, the score tables, the last decisions, a request explained, the file edited as JSON).
  • The key’s budgets (the named API keys’ part 2): a target whose estimated cost is above what is left of the request’s key’s budgets (Pass::budget_left_usd) is ruled out, with the reason; a local model and a price unknown cost nothing to them.
  • Not built: budgets per node and per route (§7), A4 (usage files, inga node usage, the /metrics counters, the footer’s cost), our own rpm / tpm limits and the shared queue (§5.6; max_concurrency is enforced as eligibility, without waiting), the RouteLLM-style strong / weak router and inga route calibrate (A7), the router’s prefix-cache affinity for mesh nodes, the per-key / per-user privacy defaults and the web UI’s local-only lock, the web UI’s Continue elsewhere button, splices by this server’s own models, a form editor for the Routes tab (it edits the JSON).
