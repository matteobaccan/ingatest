Design specs

Listed in the order of TODO.md. “0.27.0” names the release its features belong to: the v0.27.0 tag’s build failed, so 0.27.0 was not published and 0.27.1 is its release.

GPUs (0.22.0 onwards) and other devices (0.27.0)

Section titled “GPUs (0.22.0 onwards) and other devices (0.27.0)”

Every GPU and device item of TODO.md has a spec. Shipped: Vulkan V1–V3 and the GPU by default (0.22.0); CUDA graphs G1, sampling on the GPU and the first part of Vulkan V4 (0.22.1); hybrid models on the GPU, H1–H2 (0.23.0); Mamba-2 layers (H3) and the routed experts on the GPU (0.24.0); Metal M1–M2 (0.25.1); Metal M3’s kernels, off by default (0.26.0); ROCm / HIP built without an AMD card, the layer split across GPUs (S1), MTP drafts and NEON i8mm (0.27.0). Open, in TODO.md’s 0.33.0 (moved from 0.31.0 on 2026-10-15): CUDA part 2 (with the KV offload’s K3–K4 and CUDA graphs G2–G3), the rest of the GPU prefill (Vulkan V4 and V5), the layer split for hybrid models; the devices with no hardware here (Metal M3–M4, NPUs, phones, RDMA, tensor parallelism) are in its Later. They share three decisions:

  • A device is a stage. The Backend trait works on host Act buffers; a GPU (or NPU) runs a range of layers as a RemoteLayers stage held by the KvCache, exactly as a pipeline worker does (0.7.0). Only the hidden state crosses to it per step.
  • One layer engine, many devices. After CUDA P4, the stage logic moves into crates/inga-gpu (GpuOps trait + GpuLayers<O>); each backend implements only buffers and kernels, and CI tests the stage logic with HostOps (CUDA spec §7).
  • Only the driver. Device APIs are loaded at run time with libloading (CUDA driver, Vulkan loader, HIP runtime, libibverbs, Level Zero) or are OS frameworks (Metal); kernels/shaders are committed in compiled or source form (PTX, SPIR-V, HIP code objects, MSL/WGSL sources). Building Inga never needs a vendor SDK.

Suggested order for one Quadro P1000 owner

Section titled “Suggested order for one Quadro P1000 owner”
  1. CUDA backend, P1–P7: everything else on the GPU builds on it. Introduce StepParams in the decode kernels (CUDA graphs §3.1) and the common.cuh portability header (HIP spec §3.2) while writing them, and extract inga-gpu after P4.
  2. CUDA graphs: small, measurable on the P1000 (Windows launch overhead).
  3. KV offload: K1–K2 need no GPU and can even be pulled earlier; K3 is what makes long contexts usable on 4 GB.
  4. Vulkan backend: the same card through another API, compared with CUDA on the same machine; lavapipe gives it real CI coverage. It also covers AMD and Intel.
  5. WebGPU / WebAssembly: reuses the inga-gpu engine with WGSL; Chrome on the P1000.
  6. EAGLE-3 / MTP: no GPU needed, only real checkpoints; can be done any time, gains on the CPU and the GPU alike.
  7. Multi-GPU layer split, then tensor / expert parallelism: develop with logical devices on the P1000 (INGA_CUDA_SPLIT=2), finish when a second card is available. A heterogeneous test (CUDA + Vulkan) needs only the P1000 and an iGPU.
  8. Video generation: after 0.20.0’s image generation and CUDA P5; small clips on 4 GB.
  9. Hardware to acquire, by usefulness per euro: an Apple Silicon Mac M2+ (Metal, NEON i8mm, iOS — three items), an Android phone with i8mm (mobile, NEON, later QNN), an AMD GPU (ROCm, Vulkan coverage), two used ConnectX-4 Lx NICs (RDMA), cloud hours on a 2-socket machine (NUMA), a Snapdragon X / Core Ultra laptop (NPU, last: the most uncertain item).

Each spec lists what CI checks without the hardware (mock devices, lavapipe, ARM runners, Soft-RoCE, fake NUMA, emulators) and what runs only on the maintainer’s machine (#[ignore] tests with INGA_CUDA, INGA_VULKAN, INGA_METAL, INGA_HIP, INGA_NPU, INGA_RDMA, INGA_NUMA_TESTS and INGA_MODELS).
