MCP host: tools from MCP servers for local models

Status: built for 0.27.0 (decided by the implementation, 2026-10-11, to be reviewed by the maintainer; scheduled in 0.27.0 by the maintainer on 2026-10-12, TODO.md). Part 2 (§11: OAuth, resources and prompts offered, sampling, MCP tools in skills, changed lists followed) built for 0.28.0 on feat/mcp2-schedules2 (2026-10-13), to be reviewed by the maintainer. Crate inga-mcp; the server side in crates/inga-server/src/mcp.rs, the command line in src/commands/mcp.rs.

1. What it is

Section titled “1. What it is”

The Model Context Protocol (MCP) lets an application (the host) use tools offered by servers: a filesystem, a database, a calendar, a browser… Claude Desktop, LM Studio, Open WebUI and Unsloth Studio are hosts. Inga becomes one: the tools of the MCP servers the user lists are offered to the models that call tools, in inga run, inga serve (the web UI and the API) — and every call is approved before it runs.

2. Configuration

Section titled “2. Configuration”
  • mcp.json in the format Claude Desktop and LM Studio read, so the same file can be copied: {"mcpServers": {"NAME": {"command", "args", "env", "cwd"} | {"url", "headers"}}}. Also read: "type": "stdio" | "http" | "sse" (VS Code’s and Cursor’s key; sse forces the older HTTP+SSE transport), "disabled": true, and Inga’s own "timeout" (seconds per call). Unknown keys are ignored.
  • Read from $INGA_HOME/mcp.json, or the file of --mcp FILE (run, serve, mcp). At most 64 servers, a file of at most 1 MiB; a malformed file is an error that names the server and the field.
  • inga serve reads it at start and lists its servers (--no-mcp: none); servers are connected when a request first uses them, or from the Tools page.
  • inga run offers the tools with --mcp-tools (the default file) or --mcp FILE: a chat that does not ask gets no tool definitions in its prompt.

3. Transports

Section titled “3. Transports”

All by hand on serde_json and the HTTP client already in the tree (ureq), JSON-RPC 2.0, protocol version 2025-06-18 asked (older versions the server answers with are accepted):

  • Streamable HTTP (default for url): each message is a POST with Accept: application/json, text/event-stream; the answer is JSON or an event stream read until the response arrives; Mcp-Session-Id and MCP-Protocol-Version are sent back; a DELETE ends the session.
  • HTTP+SSE (protocol 2024-11-05): when the POST of initialize is refused with 400, 404 or 405 (or with "type": "sse"), a GET opens the event stream, its endpoint event (same origin only) receives the POSTs, the responses come on the stream.
  • stdio (command): a program started by Inga, one JSON message per line on its standard input and output. Lines that are not JSON (a banner) are skipped and counted; the last 4 KiB of its standard error are kept for error messages.

Every message is bounded (4 MiB); larger ones are refused with the server’s name.

4. stdio servers: the second exception to “no external programs”

Section titled “4. stdio servers: the second exception to “no external programs””

AGENTS.md says Inga runs no external programs. Skill scripts are one exception (2026-10-09-skills-design.md); stdio MCP servers are the second, on the same terms:

  • Off by default. Without --allow-mcp-commands (run, serve, mcp), a stdio server is listed with why it does not start; HTTP servers work without it.
  • Shown in full and approved once. The command, its arguments, the working directory and the names of its environment variables (never their values) are shown — on the web UI’s Tools page with an Approve button, in the terminal by inga mcp approve NAME or by the prompt of inga run / inga mcp test — and the approval is kept in $INGA_HOME/mcp-approvals.json (owner-only). A server whose command, arguments, working directory or variable names change needs a new approval. inga mcp revoke NAME and the page’s Revoke take it back; inga data lists the file (kind settings).
  • A clean environment. The program gets only the variables a program needs to start (PATH, HOME, the locale, the temporary directory, Windows’ system variables) and the server’s own env; Inga’s API key and tokens are not passed.
  • A time limit per call (--mcp-timeout, default 60 s; the server’s timeout): a call that takes longer is cancelled (notifications/cancelled) and reported to the model as failed. The program is stopped when the server stops or is restarted.

The file that spawns it is crates/inga-mcp/src/stdio.rs; it has no unsafe.

5. Tools offered to the model

Section titled “5. Tools offered to the model”
  • Each connected server’s tools (tools/list, followed page by page, at most 128 per server) are offered as SERVER__TOOL (letters, digits, _ and - only, 64 characters at most), their description starting with the server’s name, next to the client’s tools, web search and the memory’s tools. Descriptions are cut at 1000 characters, schemas larger than 16 KiB replaced by an open object (and said so).
  • The calls run in the server-side tool loop of web search (websearch::generate): at most 8 MCP calls per round, 3 rounds, then the model answers without tools.
  • A result is bounded: its text (text parts, embedded text resources, structured content, a line per image or audio part with its type and size) is cut at 16 000 characters with a note saying how much was cut. isError results and JSON-RPC errors go back to the model as failures it can explain.

6. Every call approved

Section titled “6. Every call approved”
  • Web UI (requests with "inga_mcp": {"approval": "ask"}, which need "stream": true): the stream sends inga_mcp {"stage": "approval", "id", "server", "tool", "arguments"}, the page shows a prompt with them, POST /api/inga/mcp/approve {"id", "allow", "always"} answers. No answer in 120 s is a refusal. “Always” allows that tool of that server until the server stops.
  • API clients and scheduled tasks ("inga_mcp": true, or a list of servers: ["github"], what a task’s mcp / mcp:SERVER sends): only the calls in the --mcp-auto-approve SERVER[:TOOL] allow-list (repeatable or comma-separated; off by default) run; any other call is refused, and the model is told why.
  • inga run: a y / n / a (always, for this chat) prompt on the terminal with the server, the tool and the arguments; without a terminal only --mcp-auto-approve calls run.
  • Every stage is reported: inga_mcp events while the answer streams (approval, running, done with the size and time of the result and a preview, refused with the reason), the list of calls in the answer’s inga_mcp, stderr lines in inga run.

7. Resources, prompts, sampling

Section titled “7. Resources, prompts, sampling”
  • resources/list and prompts/list are read (read-only, when the server announces them) and shown by inga mcp tools, GET /api/inga/mcp and the Tools page; part 2 offers them to the model (§11.2).
  • Part 1 announced no client capability. Part 2 announces sampling (§11.3); roots and elicitation still get JSON-RPC error -32601 with the feature’s name, and the server’s state notes it. ping is answered.

8. Interfaces

Section titled “8. Interfaces”
  • inga mcp list (the servers of the file, their transport, command or URL, approval; nothing is started), inga mcp test [NAME] (connects: protocol, server name and version, time, tools, notes), inga mcp tools [NAME] (tools with their arguments, resources, prompts), inga mcp approve NAME, inga mcp revoke NAME; --json.
  • GET /api/inga/mcp (servers, state, tools, notes, settings), POST /api/inga/mcp/connect {"server"} (connect or reconnect), POST /api/inga/mcp/approve (a call), POST /api/inga/mcp/servers {"server", "approve": true|false} (a stdio server’s command).
  • The web UI: a Tools page (each server, its transport, state, notes, tools, the full command and Approve / Revoke, Connect), a Tools button per chat (the wrench icon, shown when servers are configured), the approval prompt and the calls under the answer. Six languages.

9. As built

Section titled “9. As built”
  • Crate inga-mcp: config.rs (Config, ServerSpec; servers in the order of their names, as serde_json keeps them), approvals.rs, rpc.rs (messages, the answers to a server’s requests, notes), stdio.rs, http.rs (Streamable, Legacy), sse.rs, client.rs (Connection, render), host.rs (Host: lazy connections in parallel, a failed server retried after 30 s, one call at a time per server, the approval broker ask / wait / answer), testing.rs (the mock server, test support as inga_engine::testing).
  • The server: crates/inga-server/src/mcp.rs (McpTools, the server’s inga_server::ToolHost that serve puts in ServerCfg::tool_host, shared with skills and scheduled tasks; wanted, run_tool, the routes, which reach the host through ToolHost::as_any), websearch::Event::Mcp; the stream’s inga_mcp is one stage, the answer’s inga_mcp_calls every call. With --offline, servers reached by URL that are not on this machine are disabled.
  • Tests: crates/inga-mcp/tests/host.rs (a harness of its own: the test binary started again with INGA_MCP_MOCK=stdio is the stdio server), mcp_tools_run_once_approved_and_are_refused_otherwise in tests/server.rs (grammar-forced calls, the allow-list, the approval prompts answered from another connection, “always”), mcp_lists_tests_and_approves_servers and run_offers_mcp_tools_and_runs_the_approved_calls in tests/cli.rs; crates/inga-server/tests/webui_mcp.rs (Playwright, webui_mcp.cjs: the Tools page, a command approved, a call allowed and one refused against a fake server whose event stream waits for POST /api/inga/mcp/approve, Italian, 375 px).

11. Part 2 (0.28.0)

Section titled “11. Part 2 (0.28.0)”

11.1 OAuth for servers reached by URL

Section titled “11.1 OAuth for servers reached by URL”

The MCP authorization specification (2025-06-18): OAuth 2.1, the authorization code with PKCE, by hand on ureq, serde_json and the sha2 and getrandom crates already in the tree (crates/inga-mcp/src/oauth.rs).

  • When: a server answers 401 (Fail::Auth, with WWW-Authenticate’s resource_metadata and scope); the connection fails with “wants you to sign in: inga mcp login NAME, or Sign in on the Tools page”, and the server’s auth.needed is set. A token in headers (Authorization) still works and wins.
  • Discovery: the protected resource’s metadata (RFC 9728: the 401’s URL, else /.well-known/oauth-protected-resource{path} then /.well-known/oauth-protected-resource on the server’s origin) names the authorization server; its metadata comes from /.well-known/oauth-authorization-server{path} (RFC 8414) or /.well-known/openid-configuration (both forms). A server without metadata (protocol 2025-03-26) is its own authorization server, at /authorize, /token, /register. A server that lists code_challenge_methods_supported without S256 is refused.
  • The client: "oauth": {"clientId", "clientSecret", "scope"} in mcp.json for a client registered by hand (servers without dynamic registration); otherwise Inga registers itself once (RFC 7591: client_name Inga, public, no secret, authorization_code and refresh_token), kept per authorization server and redirect address.
  • The authorization: PKCE S256 (a 32-byte random verifier), a random state, the resource parameter (RFC 8707: the server’s URL), the scope (the 401’s, else mcp.json’s, else the metadata’s scopes_supported). Inga starts no browser (no external programs): the address is shown. The browser comes back to
    • inga mcp login NAME: http://127.0.0.1:PORT/callback, a port opened for the sign-in (10 minutes at most);
    • inga serve (the Tools page’s Sign in, POST /api/inga/mcp/login {server, redirect_base} → {url}): GET /api/inga/mcp/oauth/callback, public (the browser brings no API key; only a state this server started, less than 10 minutes old, is taken), which shows “Signed in” or why not.
  • The tokens: $INGA_HOME/mcp-tokens.json, owner-only as mcp-approvals.json, per server and URL (a server whose URL changes signs in again); sent as Authorization: Bearer; refreshed a minute before they expire and once after a 401; never shown (the status has signed_in, expires_at, scope). inga mcp logout NAME, the page’s Sign out and POST /api/inga/mcp/logout forget them. Every OAuth address must be https, or http on this machine.

11.2 Resources and prompts offered to the model

Section titled “11.2 Resources and prompts offered to the model”
  • A connected server that lists resources gets one more tool, SERVER__read_resource {uri} (resources/read), whose description names its resources (40 at most); one that lists prompts gets SERVER__get_prompt {name, arguments} (prompts/get, the arguments as text). A tool of the server’s own with the same name wins.
  • They are calls like the others: approved, reported, bounded (text contents, a line per binary content; a prompt’s messages as role: text). In the allow-list they are SERVER:resources/read and SERVER:prompts/get; a rule for the whole server (--mcp-auto-approve SERVER) covers them.
  • GET /api/inga/mcp gives resources_tool and prompts_tool (the names offered), the prompts’ arguments; the Tools page says “offered to the model as …”.

11.3 Sampling, answered by the chat’s model

Section titled “11.3 Sampling, answered by the chat’s model”
  • Inga announces {"sampling": {}}. A server’s sampling/createMessage during a tool call (the only time a model is at hand) goes to the call’s sampler (Host::call_with, inga_mcp::Sampler); outside a call it is refused, with a note.
  • The request is read and bounded (SamplingRequest): text messages (user, assistant; 64 000 characters at most; images and audio counted, not passed), the system prompt, maxTokens (at most 4096), the temperature, the stop sequences.
  • Approved like a call, under the name sampling/createMessage: --mcp-auto-approve SERVER:sampling/createMessage (a rule for the whole server does not cover it: sampling runs the model), an “always” answer (per server), or the person: the web UI’s approval shows the messages (“The MCP server X asks the model to write”), inga run asks y / n / a on the terminal. API requests without ask and scheduled tasks refuse it unless allowed. A refusal is JSON-RPC error -1 with the reason.
  • Answered by the request’s model (mcp::sample: the request’s model and sampler settings, the sampling’s messages alone, no tools); inga run uses its session. The result names the model and says maxTokens when it stopped there. The stream sends inga_mcp {stage: "sampling"}; the call’s done report counts sampled.
  • The wait for an answer starts again after each request of the server’s (stdio, HTTP+SSE); over Streamable HTTP the call’s time limit includes the sampling.

11.4 MCP tools in skills

Section titled “11.4 MCP tools in skills”
  • A skill names the MCP tools it uses in its SKILL.md header: Claude Code’s allowed-tools entries mcp__SERVER (every tool of a server) and mcp__SERVER__TOOL (the others, Claude Code’s own tools, are passed over), a YAML list or a line; and Inga’s mcp: SERVER, SERVER:TOOL (Skills::mcp_tools).
  • When the model loads such a skill (load_skill) in a request with skills, those tools are offered from the next round, even if the request did not ask for MCP; the answer of load_skill names them (or says why none is available: no MCP host, none connected, none allowed unattended). Their calls are approved as the request’s MCP calls are (inga_mcp’s approval), or, without inga_mcp, by the person when the answer streams (as skill scripts) and by the allow-list otherwise; a scheduled task (skill:NAME) offers only the tools allowed unattended.

11.5 Changed lists followed

Section titled “11.5 Changed lists followed”
  • notifications/tools/list_changed, resources/list_changed and prompts/list_changed mark the lists; the next use of the host (Host::ensure, every request with MCP tools) lists them again without reconnecting. Messages that came between two requests are read then (stdio, HTTP+SSE); over Streamable HTTP, where no GET stream is kept open, a change is seen in a response’s event stream. A server busy with a call is listed again the next time.
