Splitting the hot files

Status: proposed (asked by the maintainer on 2026-10-16), to land at the end of the 0.32.0 cycle, after the merge queue has drained. Nothing is moved yet: this document is the analysis and the plan. CHANGELOG.md is out of scope (its fragments are a separate change). Since built step by step, each with its As built paragraph; the web UI’s eight steps (W0–W7) are all built, W6 last (2026-10-22, §5.5).

The five files that most pull requests touch, and so the five that cause most merge conflicts, measured on origin/main at c754f2c (678 commits in the last 30 days, which is the whole history: the first commit is from 2026-10-07):

File Lines Commits touching it (30 days)
TODO.md 888 381 (56 %)
src/cli.rs 7,790 184
crates/inga-server/src/webui.html 31,847 122
tests/server.rs 7,641 87
tests/cli.rs 3,588 72

The plan splits each file into files that follow the lines along which the pull requests already divide (a release, a command, an API, a page of the web UI). Every step moves code only, so a reviewer checks that the bytes moved and nothing else changed. The order is TODO first, then the tests, then cli.rs, then the web UI (§6).

1. How the estimates were made

Section titled “1. How the estimates were made”

For every commit of the last 30 days that touched a file, its diff’s hunks (git show -U0, the line numbers of the old side) were mapped onto the proposed new files, with the boundaries computed on that commit’s parent version of the file. The boundaries are markers that survive edits: headings in TODO.md, the item names (fn parse_mesh, struct ServeArgs) in cli.rs, the #[test] fn names in the tests, and the // ---- … ---- banners, the CSS comments and the I18N languages in webui.html. An insertion is counted in the part that holds the line before it.

Two figures per file:

  • commits touching more than one new file: the pull requests that would still touch several files after the split (they can still conflict with more pull requests than one file’s worth, but only where they overlap);
  • pairs of commits sharing a file: out of all pairs of pull requests that touched the old file (each pair is a possible conflict, since both edit one file), how many would still share at least one new file. It is a proxy for the chance of a conflict: a real conflict also needs both pull requests open at the same time and hunks that touch or are adjacent.

The figures are approximate (a few hunks fall on the wrong side of a marker), but the order of magnitude is reliable. The script is not committed; it is described here so it can be run again: for each commit, git show C^:FILE gives the boundaries and git show -U0 C -- FILE the hunks.

2.2 The target

Section titled “2.2 The target”

Each release file starts with the source header comment, # 0.32.0 — the web UI for daily use, a one-line back link to TODO.md, then its items unchanged. Headings become # in their own file (### A. becomes ## A. in real-world-checks.md).

TODO.md becomes the index:

  • the intro (lines 3–5) without the “Last update” line: that line was rewritten by 37 of the 381 commits only to change the date, and git log docs/todo/ tells the same;
  • one line per file: the release, its title, its link, how many items are open (the count is written by the release script, not by each pull request);
  • the rules of “Feature releases” (lines 663–684, they hold for every release) and the “1.0.0 follows” note;
  • a ## Real-world checks heading with one line that points to docs/todo/real-world-checks.md, so the links to TODO.md#real-world-checks from outside the repository (issues, old pull requests) keep working; the links inside it are updated anyway (§2.5).

2.3 The rule at a release

Section titled “2.3 The rule at a release”

Text for docs/RELEASING.md, step 6 (it replaces the current step), and the same in short for AGENTS.md (the TODO.md bullet, lines 20–25, and “Next:”, line 529):

  1. Update the TODO list (the index ../TODO.md, the files of todo/). The release’s file (docs/todo/X.Y.Z.md) is closed: run python3 tools/todo-release.py X.Y.Z NEXT (NEXT is the next planned release): it removes the items marked done, moves every item still open to the top of docs/todo/NEXT.md marked “(moved from X.Y.Z)”, deletes docs/todo/X.Y.Z.md and its line in the index. Then schedule every feature newly seen elsewhere into a future release’s file, keeping the rule of 1 high-, 2 medium- and 3 low-effort features per release (fill open slots first). Add what the release could not check as bullets in the right group (A–E) of todo/real-world-checks.md, tagged (X.Y.Z) and [runner] or [manual]; remove the checks that passed.

Between releases nothing changes for the pull requests: an item that ships is removed from its release’s file; a pull request that ships an item of 0.32.0 touches docs/todo/0.32.0.md and nothing else.

Why one inline script, the JS files concatenated in order. The page’s code is one classic script: its 478 function declarations are hoisted over the whole script and its 293 top-level const / let share one scope. Concatenating the files back into the same single <script> keeps that exactly, so the page the browser gets is byte for byte the page of today. The alternatives were rejected:

  • ES modules would need an import / export for each of the ~770 shared globals, change the timing (defer), and, inline, cannot import one another without URLs: that is a rewrite, not a move;
  • one <script> per file breaks hoisting across files (a top-level call in an earlier script to a function declared in a later one fails), so the order would become a constraint to maintain by hand;
  • serving the files separately (<script src>) adds routes, entries to the service worker’s cache and requests per page load, for no gain to the user.

The browser still gets one HTML document, inline CSS and JS, no request out: the page works offline as today, and the brand’s replacen anchors are where they were. If a CSP is added to the page later, one inline script and one inline style need one hash each, which the build script can compute.

5.5 The strings, by area

Section titled “5.5 The strings, by area”

W5 alone does not reduce the conflicts: a pull request that adds a string adds it to all ten languages, so it would touch ten files instead of one. The gain comes from grouping the strings by area (the JS file that uses them): i18n/chat.json, i18n/mesh.json, i18n/schedules.json…, each holding its keys in the ten languages ({"en": {…}, "it": {…}, …}), and i18n/common.json for the keys used by several files. The assignment is mechanical: a script finds, for each key, the JS files where t("key" or data-i18n="key" appears; one file → that area; several → common.

The build script merges the areas back into today’s const I18N = { en: {…}, … } layout, in the order of the areas, so the page’s format and the parsers (webui_i18n.rs, branding.rs‘s i18n_keys and i18n_langs) do not change. The keys’ order inside each language changes (it follows the areas), which has no effect on the page; the pull request proves it by comparing the I18N object parsed from the page before and after (same languages, same keys, same texts). The i18n test keeps checking that every language has every key, and gains one check: each key is in exactly one area file.

As built, W6 (2026-10-22, one pull request): the 1,972 keys of each language in 29 area files, i18n/common.json (146 keys) and one per JS file that uses strings (core.js and boot.js use none), from settings.json (34) to palette.json (24), the largest downloads.json (182) and shell.json (158); page.html names them in a run of <!-- @include-i18n i18n/AREA.json --> lines, common first, then the JS files’ order. The assignment script looked, for each key, for the files where the key appears as a quoted string (t("key", data-i18n…="key", a key in a table such as ["nav.chat", …]), the markup counting for the JS file of its page (html/shell.html → shell, html/models.html → models, developer.html’s Server, API, Developer, Apps and Logs → system, api-docs, developer, apps, logs, pages.html‘s Memory → chat-options, Leaderboard → apps, Storage → developer, Tools → mcp, the others by their name); a key built at run time (t("cap." + k), `lp.${s}`) by the file that builds its prefix (the sampling settings’ p.*, state.* and mcp.state.* are built in two files: common); four keys no file uses (nav.about.t, where.remote, in.noread, in.images) went with their prefix’s siblings. An area file is { / "LANG": { / "key": "text", (no comma after a language’s last) / }, ( } for the last language) / }, every language in each area in the order en, it, fr, de, es, zh, pt, ru, ja, hi, its keys in the order of the old en.json. webui_assemble::i18n_blocks merges a run of areas line by line (no JSON parser), as i18n_block did: per language of the first area, LANG: {, each area’s entries with their comma, },; the build fails on an area whose languages are not the first one’s in that order and on a key twice in a language (two areas, or one twice), besides the malformed lines it refused before. tools/js-check.py (with each line’s origin) and tools/screenshots/page.cjs merge the same way. 5.7 Risks

Section titled “5.7 Risks”
  • Shared globals. Every file reads globals of the others; a file is not a module and does not run alone. The order of the includes is the order of today and must stay so for the top-level statements (a const read at load time before its file is included is a ReferenceError). boot.js is last, as the start of the page is today. Editors’ linters see undefined names in each file: an /* global */ line or a project-level globals list keeps them quiet; not needed for the build.
  • The order of the files is in page.html only; moving code between files later (for example the API nodes’ cards next to mesh.js) is a separate change, tested by the browser tests, never part of a move.
  • The i18n checks run on the assembled page, so they keep working; W6 is the only step that changes the page’s bytes and has its own proof (§5.5). A string added to one language only fails webui_i18n.rs as today.
  • Brand rendering relies on exact strings of the page; the byte-identical steps keep them, and branding.rs’s tests (b.render(crate::WEBUI)) run on the assembled page.
  • Build time: the build script copies 2 MB once per change under webui/; nothing measurable.
  • build.yml’s list of browser tests (the -E 'not binary_id(…)' filter, line 119, and the webui job’s steps) is itself a small hot spot: every new browser test adds itself in two places. Not part of this plan; a glob (binary_id(inga-server::webui_*)) would end it.
