Vulkan barriers only where reads and writes meet

Status: part 1 built for 0.31.0 (branch perf/vulkan-barriers; see §7, As built); part 2’s shared quantized input built (branch perf/vulkan-shared-act-quant; see §8, As built); the measures on real GPUs open. Decided 2026-10-14. TODO.md 0.22.1: “Candidate (uzu) — Vulkan barriers only where the read / write ranges overlap (automatic hazard tracking)”; docs/experiments.md (c). Code: crates/inga-vulkan/src/device.rs (barrier, Inner::{begin, record, flush, dispatch_on, upload}, Queue), crates/inga-vulkan/src/pipeline.rs (the shader table: (Shader, name, spv, bindings)), new crates/inga-vulkan/src/hazard.rs.

Decisions (2026-10-14)

Section titled “Decisions (2026-10-14)”
  1. On by default once the P1000 and lavapipe show no regression, with debug.vk_barriers = "all" in inga.toml (or --ab debug.vk_barriers=all) to go back.
  2. The RX 9060 XT’s reporter (#401, #489) for an --ab run: to be asked: Status: open — postponed by the maintainer on 2026-10-14.

1. Goal

Section titled “1. Goal”

Inner::record puts a full memory barrier (ALL_COMMANDS → ALL_COMMANDS, every write made visible to every read and write) after every dispatch and copy. A decode step of a 28-layer model records a few hundred dispatches, so it gets a few hundred barriers. Many of them sit between independent dispatches: the Q, K and V products of one layer, or the gate and up products. A barrier drains the GPU between them, and on small kernels the drain costs as much as the work.

The barrier should go only where a dispatch reads what an earlier one wrote since the last barrier, or writes what an earlier one read or wrote. Results do not change: the same dispatches run in the same order with every true dependency kept. debug.vk_barriers = "all" (a key of inga.toml, the configuration file) restores today’s behaviour for comparison (inga bench --ab debug.vk_barriers=all) and for a driver that misbehaves. No CLI, API or web UI change.

2. Design

Section titled “2. Design”

2.1 What each binding does

Section titled “2.1 What each binding does”

Every shader binds whole buffers (DescriptorBufferInfo with offset 0 and WHOLE_SIZE), so a vk::Buffer handle names its whole range. The suballocator gives each buffer a range of its own in a block, and no two live buffers overlap. Handle identity is therefore enough: no byte ranges are needed.

Which bindings a shader writes comes from its SPIR-V, read once when the pipelines are built (pipeline.rs). A storage buffer whose block members are all decorated NonWritable (GLSL readonly) is read-only. Any other binding counts as written, writeonly and read-write alike. The scan walks OpDecorate / OpMemberDecorate (Binding, NonWritable) and OpVariable’s pointer types, about 80 lines with no dependency. The result is a written: u8 mask per pipeline (MAX_BINDINGS ≤ 8), beside bindings.

2.2 The tracker

Section titled “2.2 The tracker”

hazard.rs: struct Pending { reads: [vk::Buffer; 32], writes: [vk::Buffer; 32], .. }, fixed arrays with their lengths, so the hot path does not allocate (no new dependency); when one fills, a barrier is placed. One Pending lives in Queue, beside the command buffer.

  • Before recording a dispatch with reads R and writes W: a barrier is needed if R ∩ writes (read after write), W ∩ writes (write after write) or W ∩ reads (write after read, an execution dependency) is not empty. Then Pending is cleared.
  • After recording it, R and W are added.
  • Copies (cmd_copy_buffer, cmd_update_buffer, cmd_fill_buffer) are tracked the same way: source as a read, destination as a write. Their barrier keeps TRANSFER in its stage masks, as today’s ALL_COMMANDS covers it.
  • begin keeps its barrier (ordering after earlier submissions; the fence already waits for them) and resets Pending. flush keeps its barrier to HOST.

The barrier placed is the same global MemoryBarrier as today, only less often. Per-buffer barriers are not worth their cost here, since a global one is no more expensive to the driver.

Inner::record(q, sets, record) takes the access lists from its callers: dispatch_on(shader, single, bufs, push, grid) knows bufs and the pipeline’s mask; upload, copy and read know their buffers. The trailing barrier(...) in record becomes hazard.after(...).

2.3 Two models on one device

Section titled “2.3 Two models on one device”

Today each model opens its own device. If the shared device of 2026-10-14-vulkan-memory-blocks-design.md lands, two models record into the same queue under its lock. Their buffers are distinct, so the tracker stays correct. Only a buffer freed and recycled inside one recording could alias, and that does not happen: a buffer submits the recording before it is destroyed (DeviceBuffer’s drop).

3. Tests

Section titled “3. Tests”
  • hazard.rs unit tests: RAW, WAW and WAR each place a barrier; independent dispatches do not; a full set places one; begin resets.
  • pipeline.rs: for every shader, the SPIR-V mask agrees with the GLSL source’s readonly qualifiers. The test reads shaders/*.comp and checks that every buffer declared without readonly is in the mask, so a shader edited without the qualifier fails CI.
  • The Vulkan test suite on lavapipe (INGA_VULKAN=1 in CI) passes unchanged, once with the tracker and once with debug.vk_barriers = "all". Every layer test compares against the CPU, so a missing barrier shows as wrong numbers.
  • debug.vk_validate = true (INGA_VK_VALIDATE=1 until the configuration file lands) with synchronization validation (VK_LAYER_KHRONOS_validation, validate_sync) on one decode step and one prompt chunk of a synthetic model: no hazard reported.
  • A count: a Gpu::barriers() counter, read by the Vulkan layer tests and by an #[ignore] timing test on a synthetic model, gives the barriers per decode step before and after (the expected drop is from about one per dispatch to about half).

4. Measures

Section titled “4. Measures”

On the P1000 runner (Vulkan) and, if available, the RX 9060 XT: inga bench -p 512 -n 128 -r 3 --ab debug.vk_barriers=all on Llama-3.2-1B Q4_K_M, Qwen3-0.6B Q8_0 and Qwen3.6-35B-A3B Q4_K_M. Following the rule of docs/performance.md: the same tokens and no regression above 3 %. The verdict goes in docs/experiments.md (c).

5. Phases

Section titled “5. Phases”
  • Part 1: the SPIR-V scan and its test, the tracker, debug.vk_barriers, the counter, lavapipe and the validation layer.
  • Part 2: the measures. The default stays on only if no device regresses; otherwise the tracker ships off by default and the entry in experiments.md says where it helps.

6. Risks

Section titled “6. Risks”
  • A missed dependency produces wrong numbers on some drivers and not others. The validation layer’s synchronization checks and the CPU comparisons are the guard, and debug.vk_barriers = "all" is the escape.
  • A dispatch that reads a buffer through a binding without readonly is counted as a write. That is safe; it only costs a barrier.

Effort: S (about 300 lines with tests), plus the runner’s measures.

7. As built (part 1, perf/vulkan-barriers)

Section titled “7. As built (part 1, perf/vulkan-barriers)”
  • The scan (pipeline.rs, written_bindings): as §2.1. A binding is read only when its variable is decorated NonWritable or every member of its block is; several variables at one binding (W and W4) write it if any does; a binding no variable has counts as written. Pipeline::written holds the mask of the SPIR-V actually loaded (the subgroup and dot-product builds are scanned too, and a test checks they agree with the base build). The test written_bindings_agree_with_the_glsl expands the #includes of every shaders/*.comp and checks that the mask equals the GLSL’s (every buffer without readonly), both ways: nothing written is missed, and no barrier is placed that the qualifiers allow to save.
  • The tracker (hazard.rs, Pending): as §2.2, 32 buffers per list, each buffer once. Every binding of a dispatch counts as read, the written ones as written too. cmd_update_buffer writes its destination; copies read their source and write their destination (the staging buffer included). begin keeps its barrier and clears the lists; flush keeps its barrier to the host.
  • The switch: the configuration file had not landed, so debug.vk_barriers is, for now, inga_vulkan::set_barrier_mode(Barriers) for the process and Gpu::set_barrier_mode(Option<Barriers>) for one device (read at each command, so it can change between runs); --vk-barriers tracked|all on run, serve and bench (no new INGA_* variable); and inga bench --ab debug.vk_barriers=all (the key form --ab will take for every setting; the only key it knows yet). Under all a barrier follows every command, as before. The Cargo feature vk-barriers-all makes all the default, to run the whole Vulkan suite as before (cargo test -p inga-vulkan --features vk-barriers-all -- --include-ignored).
  • The counters: Gpu::barriers() (every pipeline barrier recorded: between commands, at the start of a recording, before the host reads) and Gpu::commands().
  • Validation: INGA_VK_VALIDATE=1 now also turns on the synchronization checks (VkValidationFeaturesEXT with SYNCHRONIZATION_VALIDATION, when the layer offers VK_EXT_validation_features). The whole Vulkan suite under it on lavapipe (validation layer 1.3.275) reports no error and no SYNC-HAZARD. With the tracker’s barriers removed (a local check, not committed) the same test reports 4,296 read-after-write and 1,752 write-after-read hazards, while lavapipe still gave the right numbers: on a software device the CPU comparisons alone would not catch a missing barrier, and the validation layer does. It is not a CI test (the layer’s messages go to stdout, and CI’s lavapipe job has no layer).
  • Tests: hazard.rs’s unit tests (§3); barriers_go_only_where_reads_and_writes_meet (Llama Q4_K, Qwen3 Q8_0, Gemma 3 F16: the same bits under both modes, the CPU’s logits, fewer barriers for the same commands); barriers_speed (#[ignore], a 28-layer synthetic model). The Vulkan suite passes on lavapipe in both modes.
  • Measured on lavapipe (indicative only; real GPUs are part 2): a decode step of the 28-layer Q8_0 model records 758 commands and 675 barriers instead of 760 (-11 %), a prompt chunk of 128 tokens 676 instead of 762; the speed did not move beyond lavapipe’s noise. The 3-layer models drop 9 % (Q4_K), 12 % (Q8_0) and 23 % (F16) per decode step. That is far from §3’s “about half”: here the code differs from the spec’s premise. Each quantized product first quantizes its input into the one ActScratch that every product shares (quantize_q8_1, then the product reading it), so the next product’s quantization writes what the previous one read. That is a write-after-read barrier, and Q, K and V (gate and up) stay ordered. Only F16 / F32 weights, read without quantizing, overlap. Quantizing a norm’s output once for the products that read it would remove both the barriers and the repeated quantizations. It changes the dispatches, so it is left for a follow-up (TODO.md).

8. As built (part 2, the shared quantized input, perf/vulkan-shared-act-quant)

Section titled “8. As built (part 2, the shared quantized input, perf/vulkan-shared-act-quant)”

§7’s follow-up: a norm’s output is quantized to 8 bits once, into a buffer of its own, and every quantized product that reads it reads that copy.

  • The operations (inga_gpu::GpuOps, all with defaults that keep the old path): quantizes_inputs_once() (asked when a session’s scratch is made), reads_quantized_input(w) (asked at each product), quantize_input(x, values, s) and matvec_input(s, rows, w, out). On Vulkan (layer.rs) matvec_input runs the dispatches matvec (up to eight rows) or matmul (more: the tiles where matmul takes them, else the matrix-vector shaders) would run, less the quantization: product now quantizes and then calls the same quantized_product that matvec_input calls, so both paths share one dispatch. HostOps takes the shared path too (its “quantized” input is a copy in f32), so the CPU tests of inga-gpu walk the new loop. CUDA and Metal keep the defaults.
  • The layer loop (inga-gpu/src/layers.rs, Input): after each norm, the products of s.x go through Input::mul, which quantizes x into Scratch::xq before the first product that reads quantized activations and reuses it for the others; a product by F16 or F32 weights reads x as before. It covers the attention’s Q, K, V and gate, DeltaNet’s qkv, z, beta and alpha, Mamba2’s z, xBC and dt, the feed-forward network’s gate and up (or up alone), and a shared expert’s gate, up and gate logits (after the down projection: xq still holds x). The routed experts’ eight-row path (expert_chunk) keeps ExpertScratch::xq and whether it holds the x on the device: a decode step’s token (x_there) is quantized once for every expert’s gate and up. The products of the other inputs (wo, down, DeltaNet’s and Mamba2’s out) still quantize their own into act. The routed experts of a prompt chunk were already quantized once (Grouped::sx, GPU prefill P4).
  • Not shared: a shared expert and the routed experts read the same normalised activation, but the routed experts get it from the host (the router runs on the CPU) in another call, so each quantizes its own copy.
  • The switch: Gpu::set_shared_input(bool) (on by default; read when a session makes its scratch, and at each product). No CLI option or INGA_* variable: the results are the same bits, so it only serves the comparisons of the tests. Gpu::quantizations() counts the quantize_q8_1 dispatches.
  • Memory: Scratch::xq holds the model’s width for each chunk size (1 to max_rows, the powers of two of prompts), ExpertScratch::xq the width for 1 to max_rows rows: a byte and a half per value (the 8-bit values and four floats per block of 32). scratch_bytes counts both, on every device (CUDA does not allocate them: a few MiB counted in excess there). The placement profiles’ activations grow by 1-3 % (tests/profiles, blessed again); no layer or chunk choice changed.
