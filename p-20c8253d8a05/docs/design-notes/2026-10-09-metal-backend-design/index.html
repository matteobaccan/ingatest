Metal backend (Apple Silicon GPU) — design and work plan

Status: M1–M2 shipped in 0.25.1 (#389; see As built); M3’s prefill and attention kernels shipped in 0.26.0 (#397), experimental and off by default (INGA_METAL_SIMDGROUP=1), unverified on a real GPU (see M3); every GGUF block type read without a conversion, and every M2 and M3 kernel checked on a CPU emulator, in 0.27.0 (Every GGUF block type); M3’s checks on a GPU and M4 (the speed against llama.cpp on a real Mac) in 0.27.0 (TODO.md; brought forward by the maintainer after the CI probe of §5). Builds on the shared layer engine inga-gpu (CUDA spec §7). M1–M2 are tested on GitHub’s macos-15 runners; M3–M4 need a real Apple Silicon Mac, which the test kit of docs/mac-testers.md (tools/mac-test.sh, #398) asks testers for.

1. Goal and scope

Section titled “1. Goal and scope”
  • inga run / serve on macOS run every layer on the Apple GPU by default (--device auto = Metal on Apple Silicon), as llama.cpp and Ollama do: on a Mac the GPU is the fast path for both prefill and decode.
  • Zero-copy weights: Apple Silicon has unified memory; the memory-mapped model file is wrapped as Metal buffers (newBufferWithBytesNoCopy) instead of copied, so a model uses its file size once, not twice.
  • Same correctness rules (greedy text = CPU’s for 32 tokens, perplexity within 0.5 %); speed close to llama.cpp’s Metal backend on the same Mac.
  • iOS / iPadOS reuse it (2026-10-09-mobile-builds-design.md).
  • Out of scope: Intel Macs with AMD GPUs (Vulkan through MoltenVK is not planned either), the Apple Neural Engine (see the NPU spec: not reachable without Core ML), MLX interop.

2. What the maintainer needs

Section titled “2. What the maintainer needs”
  • A Mac with Apple Silicon: M1 is enough to develop (Metal 3, simdgroup_matrix); M2 or later for bf16 in shaders; 16 GB+ to run 8B models. macOS 14+.
  • Xcode command-line tools only for the Rust toolchain’s linker; no Xcode project and no offline metal compiler: shaders are compiled at run time (§3.3).
  • Rust target aarch64-apple-darwin (already a release target).

Crate choice and the no-runtime-dependencies rule

Section titled “Crate choice and the no-runtime-dependencies rule”
  • Metal.framework and Foundation.framework are part of macOS and iOS (like libSystem, which every macOS program links): linking them adds no dependency the user has to install. They are linked normally, not loaded with libloading.
  • Bindings: planned as objc2, objc2-foundation, objc2-metal (MIT/Apache-2.0/ Zlib, pure Rust, generated from Apple’s headers). As built: no crate at all: the forty-odd messages Inga sends (a device’s properties, buffers, a library compiled from source, pipelines, one command queue, compute encoders) are typed by hand over objc_msgSend in one file, crates/inga-metal/src/sys.rs, the crate’s only unsafe code; libobjc, Metal.framework and Foundation.framework are linked as system libraries on macOS, nothing is added to the allowed list of the design spec §2. The older metal crate (gfx-rs) is in maintenance mode, and objc2-metal would have brought three crates and thousands of generated bindings for those few calls.

3. Design

Section titled “3. Design”

3.1 Plug-in point

Section titled “3.1 Plug-in point”

MetalOps implements inga_gpu::GpuOps; GpuLayers<MetalOps> is the stage. Because memory is shared, the stage can also take the embedding lookup and the output head (and the samplers’ inputs stay readable by the CPU without a copy). --gpu-layers defaults to all on Metal.

3.2 Weights without a copy

Section titled “3.2 Weights without a copy”

Storage::Mmap(Arc<Mmap>, Range) (crates/inga-core/src/weight.rs) holds the file mapping. newBufferWithBytesNoCopy needs a page-aligned pointer and length (16 KB pages on Apple Silicon): the stage wraps the whole mapping (or 1 GB page-aligned windows of it, under maxBufferLength) in a few buffers and addresses each tensor by (buffer, offset). Tensors converted at load (--quantize, safetensors BF16 → another type, LoRA-merged) live in Storage::Owned and are copied once into shared buffers. Storage::Mmap keeps the map alive as long as the buffers (the Arc is held by the stage). Streamed layers (Model::stream_layers) keep working: the OS pages the mapping in for the GPU as for the CPU.

3.3 Shaders compiled at run time

Section titled “3.3 Shaders compiled at run time”

The MSL sources are embedded and compiled with newLibraryWithSource:options:error: at the first use (~0.5–1 s for the full set; llama.cpp embeds its .metal source the same way by default). Pipelines cached per (function, function constants). A cache of compiled libraries (MTLBinaryArchive in $INGA_HOME/metal/) is optional, phase M4.

Kernels: the CUDA spec §4 list, written for Apple GPUs:

  • decode matvec_<type>: SIMD groups of 32 threads, each over rows of quantized blocks, f32 activations in threadgroup memory (Apple GPUs have fast f16/f32; no int8 dot instruction: dequantize to half/float in registers as llama.cpp’s kernel_mul_mv_q4_K_f32 does);
  • prefill matmul_<type>: simdgroup_matrix<float, 8, 8> (or half) tiles, weights dequantized into threadgroup memory;
  • attention: decode with split-K over the cache and a reduction, prefill as flash attention with simdgroup_matrix tiles; sliding window, sinks, soft-capping;
  • rms_norm, rope, element-wise, gated_delta_net step and chunks.

3.4 Execution

Section titled “3.4 Execution”

One MTLCommandBuffer per step with one compute encoder; dispatches in order with memoryBarrierWithScope:buffers between dependent ones (or a serial dispatch type); the CPU waits with waitUntilCompleted only when it needs the logits. Per-step scalars in a small shared StepParams buffer, so encoding stays allocation-free. Optional: encode the next step’s command buffer while the GPU runs (llama.cpp splits a graph across several command buffers encoded on threads).

3.5 Memory budget

Section titled “3.5 Memory budget”

recommendedMaxWorkingSetSize of the device is the VRAM-equivalent budget; the planner treats Metal as a tier sharing the RAM budget (mem_info), not adding to it.

4. Phases

Section titled “4. Phases”
  1. M1 — devices and element-wise. objc2-metal setup, inga devices on macOS, library compilation, no-copy buffers, element-wise/norm/rope kernels vs RefBackend.
  2. M2 — decode. matvec for F32, F16, BF16, Q8_0, Q4_K, Q6_K, decode attention, GpuLayers<MetalOps> with all layers, head and embeddings. Acceptance on an M1/M2: Llama-3.2-1B and Qwen3-0.6B Q4_K_M greedy text equal to the CPU’s; decode ≥ 80 % of llama-bench (Metal build, default) on the same Mac.
  3. M3 — prefill and coverage. simdgroup_matrix matmul and flash attention, the other weight types, MoE (experts as no-copy buffers too), Gemma / gpt-oss options, DeltaNet. Acceptance: pp512 ≥ 70 % of llama.cpp Metal; perplexity within 0.5 %.
  4. M4 — polish. Binary archive cache, double-buffered encoding; auto defaults, docs. Acceptance: Qwen3-30B-A3B Q4_K_M on a 32 GB Mac decode ≥ 80 % of llama.cpp.

5. Test plan

Section titled “5. Test plan”

  • CI: the macOS ARM runner builds and lints inga-metal on every PR. Probed on 2026-10-11 (a Swift compute kernel, MTLCreateSystemDefaultDevice):

    • macos-15: an “Apple Paravirtual device” — unified memory, 9.5 GiB recommended working set, 7 GiB largest buffer, a vector add right, a 4096 x 4096 F16 matrix-vector product in 0.53 ms (63 GB/s); it reports no Apple7 / Apple8 family, so simdgroup_matrix and other Apple-GPU features must not be assumed there.
    • macos-14: no Metal device.

    macOS runners cost money (the maintainer, 2026-10-11: as few Metal runs as possible, one test gathering everything). So there is no Metal job of its own and no Metal run on ordinary PRs:

    • the Metal checks are one test, metal_everything in crates/inga-metal/tests/, which compiles every shader, runs every kernel against RefBackend and the synthetic end-to-end models in a single process (one device, one library compilation), and prints one table of results;
    • it runs inside the existing macOS step of build.yml, the one already run for the release PR (chore(release)), its merge and the tag, with runs-on: macos-15 pinned (it has the paravirtual device) and INGA_METAL=1; without a device it reports why and is skipped;
    • while M1–M2 are written, at most one manual run per Metal PR (workflow_dispatch of the same workflow on that branch), never on every push;
    • ordinary PRs build inga-metal only on Linux (cargo check of the shared code; the Objective-C calls are behind cfg(target_os = "macos")).

    M3’s simdgroup_matrix paths and every speed figure need a real Mac and are not run in CI.

  • MSL compiles: a test compiles every embedded shader through newLibraryWithSource when a device exists, so a syntax error fails fast.

  • Maintainer (INGA_METAL=1, cargo test -p inga-metal -- --ignored), end to end with INGA_MODELS; Xcode’s Metal debugger / GPU frame capture for profiling.

6. Risks and open questions

Section titled “6. Risks and open questions”
  • No Mac today: M1–M2 are checked for correctness on the CI’s paravirtual device only; M3–M4 wait for a real Mac (a used M1 Mac mini, or one as a self-hosted runner as the P1000 is).
  • newBufferWithBytesNoCopy on a file mapping: the mapping must stay valid and read-only for the buffers’ lifetime; GPU page faults on a model larger than RAM are slow but correct (to measure).
  • Open: f16 vs f32 accumulation in matvec (llama.cpp uses f32 for accumulation, half for some intermediates); decided by the perplexity check.

8. As built (M1–M2, 0.25.1)

Section titled “8. As built (M1–M2, 0.25.1)”

Next (approved by the maintainer on 2026-10-11): every GGUF block type on Metal without conversion and GPU-resident generation with megakernels, after mlx-serve-gguf and lithos-metal, are open items in TODO.md under 0.27.0, beside M3–M4 (M3 merged off by default in 0.26.0, unverified).

  • Crate inga-metal: lib.rs (probe, devices, DeviceInfo: name, registry id, unified memory, recommendedMaxWorkingSetSize, allocated bytes, largest buffer, threadgroup memory, the MTLGPUFamily values supported), sys.rs (the Objective-C calls, macOS only; stub.rs elsewhere, where every type is uninhabited, so the crate builds and is linted on Linux), library.rs (the kernels’ sources and names), shapes.rs (shape checks and dispatch sizes, tested without a device), ops.rs (MetalOps, the inga_gpu::GpuOps device). src/commands/devices.rs lists the Metal devices on a Mac (inga devices, --json’s metal, /api/inga/devices); inga_engine::DeviceApi::Metal, DeviceSel::Metal (--device metal[:N], INGA_DEVICE, POST /api/inga/device); --device auto tries CUDA, then Metal, then Vulkan; src/commands/placement.rs opens MetalOps (OpenGpu::Metal) and prints gpu: Metal 0 ...: kernel files compiled ..., weights ... wrapped ... without a copy (GpuPlan::device_note). A device without unified memory (an Intel Mac’s AMD GPU) is listed as not usable.
  • Shaders: five files (shaders/elementwise.metal, norm.metal, matvec.metal, attention.metal, recurrent.metal), each compiled with shaders/common.metal put before it, as a library of its own, the five at once on threads of their own, with fast math off (the CPU’s exp, divisions, square roots); a file that does not compile names itself. Only the baseline feature set: threadgroup memory and barriers, no SIMD-group functions (the CI’s paravirtual device reports no Apple7 family); the threadgroup size is the largest power of two up to 256 the pipeline allows, read back from it, the threadgroup memory sized by the host. The kernels: copy, add, bias, SwiGLU, GeGLU (ggml’s f16 GELU table), squared ReLU, sigmoid gates, the clamped SwiGLU and the scatter of routed experts, the f16 KV store (rounded as the CPU’s cache), RMS and grouped norms, RoPE (YaRN, NeoX or pairs; Cephes’ sine and cosine as the Vulkan shaders), the matrix-vector products of F32, F16, BF16, Q8_0, Q4_K and Q6_K on f32 activations (dequantized in registers, a segment of 32 threads per output row, eight tokens at a time, prompts through the same kernels), causal attention over the f16 cache (one threadgroup per head and token, an online softmax over tiles; window, soft-capping, sinks; heads up to four times the threadgroup), and the gated DeltaNet and Mamba-2 kernels (gates, convolutions, the delta rule, the selective scan), ported from the Vulkan shaders. So beyond M2’s list, MoE experts, DeltaNet and Mamba-2 layers run on Metal too (the shared layer engine needs every GpuOps operation), checked as the rest.
  • Weights without a copy: a weight whose bytes are in a file mapping (Storage::Mmap, or Storage::Packed rearranged from one) is wrapped with newBufferWithBytesNoCopy over the whole pages around it, one buffer per tensor (not 1 GB windows: simpler, and a tensor never straddles two buffers), the buffer keeping the mapping alive; a weight not starting on 16 bytes, or not mapped (converted at load), is copied once into a shared buffer. MetalOps::weight_bytes counts both.
  • Execution: one command buffer with one compute encoder (its dispatches run one after the other), committed and waited for when the host reads or writes a buffer (or after 4096 dispatches); per-dispatch numbers through setBytes, so recording allocates nothing. No graphs (begin_capture is false), no sampling on the GPU yet.
  • Memory: the planner’s budget is the working set less what the process allocated; the RAM-sharing tier of §3.5 and the embedding lookup on the GPU are not done: the token embeddings stay on the CPU, as with CUDA and Vulkan (on unified memory the rows are read from the same mapping).
  • Tests: crates/inga-metal/tests/metal_everything.rs, the one test of §5: the devices, the five files compiled one by one, every kernel against HostOps (the reference backend behind GpuOps) including the wrapped weights, synthetic Llama, Qwen2, Qwen3, Gemma 2 and 3 models in F32, F16, BF16, Q8_0, Q4_K and Q6_K, and Qwen3.5, Qwen3-Next, Nemotron-H, Qwen3 MoE and gpt-oss in F32 and Q8_0, with every layer and the output layer on the GPU: the logits of 32 greedy steps against the CPU’s (the same token at every step but near ties, where the CPU’s two best are within the tolerance: the CPU quantizes the activations of quantized weights to 8 bits, the GPU does not) and the engine’s greedy text against the CPU’s. It prints one table and adds it to the job summary; harness_on_the_host runs the same checks with the CPU in the GPU’s place on every system, so the harness itself is tested on ordinary PRs. build.yml’s macOS job runs on macos-15 with the step “🍏 Metal checks” (INGA_METAL=1), and a manual run with the input only: metal runs that job alone. The acceptance on real models and a real Mac (Llama-3.2-1B, Qwen3-0.6B greedy text, decode against llama-bench) is M3–M4’s.
  • What the runner found (2026-10-11, two manual runs): Apple’s compiler refuses a kernel whose position and size attributes mix scalars and vectors (the local syntax check had passed them): the threadgroup’s size is now a uint3 like the others (GROUP_ARGS / GROUP_INIT in common.metal), and metal_everything then passed on the paravirtual device. With Metal working, --device auto put on it runs whose options a GPU’s layers cannot serve yet (--image / --video, --prompt-cache, --collect-imatrix): under auto those runs now stay on the CPU and say why (LoadOpts::cpu_only); a GPU named by --device still runs them, with a warning. The Metal step runs even when the rest of the macOS suite fails, so one paid run always gives its table.

M3 (unverified, off by default in 0.26.0)

Section titled “M3 (unverified, off by default in 0.26.0)”

Written on 2026-10-11 by the maintainer’s decision, as code only, kept on the branch feat/metal-simdgroup, then merged off by default (the maintainer, 2026-10-11: the release binaries carry it, testers turn it on with INGA_METAL_SIMDGROUP=1; off, its file is not even compiled and the M1–M2 path is unchanged): simdgroup_matrix needs MTLGPUFamilyApple7 (an M1) or later, and GitHub’s macOS runners expose a paravirtual device that reports only Apple1–5 and Mac2. None of these kernels has run on a GPU. What is written:

  • Detection: DeviceInfo::simdgroup_matrix (the supportsFamily: answers already probed for families): Apple7 to Apple10, or Metal3; otherwise “the device lacks Apple7 (it reports …)”. The M3 kernels run only with INGA_METAL_SIMDGROUP=1; without it the gpu: Metal ... line says “experimental, off”.
  • A file of its own, shaders/simdgroup.metal (library::SIMDGROUP, kernels library::Tile): compiled only on such a device, on a thread of its own beside the five M2 files, as one more library made of common.metal, matvec.metal, attention.metal, norm.metal (whose decoders, parameter structs and tanh_exp it reuses) and itself. A device without simdgroup_matrix never compiles it; a kernel of it that does not compile (or a SIMD width other than 32, or fewer than 128 threads per threadgroup for the tiles) leaves that operation on the M2 kernel and the reason in the summary, and does not fail MetalOps::new. The M1–M2 shader files are unchanged.
  • Prefill products mm_f32, mm_f16, mm_bf16, mm_q8_0, mm_q4_k, mm_q6_k (structure after llama.cpp’s kernel_mul_mm, MIT, credited in the file): one threadgroup of 4 SIMD groups (128 threads) per tile of 64 outputs x 32 tokens; per step of 32 values, the first 64 threads dequantize one weight row each into threadgroup memory (as half for F16 and the quantized types, as float for F32 and BF16, whose values half would round; zeros past the row or past n_out), the other 64 stage the activations as float (zeros past the last token); each SIMD group accumulates 2 x 4 simdgroup_float8x8 blocks (16 tokens x 32 outputs) with simdgroup_multiply_accumulate, the weights loaded transposed; full tiles are stored straight to the output, edge tiles through threadgroup memory. 16–20 KiB of threadgroup memory.
  • Flash attention for prompts flash_h<D> for heads of 16, 32, 64, 80, 96, 112, 128, 192 and 256 values (structure after llama.cpp’s kernel_flash_attn_ext): one threadgroup of 4 SIMD groups per (head, 32 queries), 8 queries per SIMD group held as float 8 x 8 matrices with their output; the keys the block’s queries see (from the first query’s window to the last query’s position, shapes::flash_key_span) go by blocks of 32 keys (16 above 128 values) through threadgroup memory as half, K and V shared by the SIMD groups, zeros past the last key (nothing past the cache’s positions is read); per block S = Q K^T, an online softmax a row at a time with one key per lane (simd_max, simd_sum; the causal mask, the window, the scale, soft-capping), the output rescaled by a diagonal matrix of the corrections, O += P V; sinks start the softmax as in attention.metal; grouped-query heads by h / (n_head / n_head_kv). Other head sizes stay on the M2 kernel. At most 21 KiB of threadgroup memory.
  • SIMD-group reductions in the decode kernels: matvec_<type>_simd (a SIMD group per output row, simd_sum instead of the threadgroup-memory sum and its barriers), attention_simd and rms_norm_simd (simd_max / simd_sum in each SIMD group, then one value per group through threadgroup memory, instead of the log2(threads) tree).
  • Host (ops.rs): prompts of MetalOps::tile_rows tokens or more (32 by default, INGA_METAL_TILE_ROWS, set_tile_rows) go to mm_* and flash_h* when they compiled (shapes::plan_tiles, plan_flash); every other product, attention and RMS norm to the SIMD-reduction kernels when they compiled, else to the M2 kernels. The gpu: Metal ... line (MetalOps::summary, prefill_note) ends with “prefill on simdgroup_matrix tiles (prompts of 32 tokens or more; …), decode kernels with SIMD-group reductions” or “prefill on matrix-vector kernels: the device lacks Apple7 (it reports …)”.
  • Checked here (Linux, no Apple GPU): cargo fmt, cargo clippy for the workspace and for inga-metal’s library on aarch64-apple-darwin; the shape functions as unit tests (every output of every tile covered once, edge tiles, the grid limits, the threadgroup memory of every instantiation under 32 KiB, every key a query sees inside the block’s span and nothing past the cache); and, outside the repository, the Metal sources compiled with clang++ against a shim mapping MSL to C++ that runs each threadgroup’s threads as CPU threads (barriers, simd_sum / simd_max, simdgroup_* as whole 8 x 8 matrices): every mm_* against a plain product (float types) and against the M2 matvec_* (quantized decoders), the matvec_*_simd against the M2 kernels, flash_h* and attention_simd against a reference attention for every head size, windows, soft-capping, sinks, grouped-query heads, prompts after earlier positions and edge blocks, and rms_norm_simd agreed (95 checks). That emulation checks the indexing and the algorithm, not Apple’s compiler nor how a real GPU runs simdgroup_load / simdgroup_multiply_accumulate.
  • Waiting for a Mac (an M1 or later): metal_everything compiles simdgroup.metal and, with prompts from 9 tokens put through the tiles, checks every mm_* (every weight type, edge tiles), every flash_h* (head sizes, windows, soft-capping, sinks, chunks) and the synthetic models end to end against the CPU, beside the M2 rows (whose products and attention then run on the SIMD-reduction kernels); on the paravirtual device one row says why they are skipped. Then speed against llama.cpp (pp512 ≥ 70 %) and the default tile_rows.

Every GGUF block type, and the kernels on a CPU emulator (0.27.0)

Section titled “Every GGUF block type, and the kernels on a CPU emulator (0.27.0)”

Branch feat/metal-m3-m4 (the TODO items “Metal: every GGUF block type without conversion” and M3’s checks), still without a Mac.

  • Every block type read as stored. library::WEIGHTS lists the 26 types of inga_core::DType with their three kernels (matvec_<t> in matvec.metal, matvec_<t>_simd and mm_<t> in simdgroup.metal); Kernel::Matvec(DType) and Tile::Mm(DType) / Tile::Matvec(DType) replace the six variants per kernel family, reads_weights and shapes::matvec_block (a row of whole blocks) follow the list, so the placement, inga fit and the hardware profiles’ simulated Mac see the new types without a change of their own. Each new decoder (decode_q4_0 … decode_q2_0) gives the 32 values of a unit (a block of 32, or a quarter, half or eighth of one) as ggml’s dequantize_row_* does (inga-quant’s legacy.rs, iq.rs, fp4.rs), in the same order of operations; 32-bit fields at 2-byte offsets (Q5_0’s qh, the i-quants’ words) are read as two 16-bit loads, MXFP4’s 17-byte blocks byte by byte. The tables (ksigns_iq2xs, the IQ2 / IQ3 / IQ1 grids, kvalues_iq4nl, kvalues_fp4: 3,840 64-bit and 768 32-bit entries) are written into the Metal source from inga-quant’s own (library::tables_source, now pub in inga_quant::iq_tables), before matvec.metal wherever it is compiled, so they cannot drift from the CPU’s. M3’s tiles stage the decoded values as half, but MXFP4’s as float (an E8M0 scale reaches 2^127). Nothing is converted at load and nothing copied: a weight of any type is wrapped from the file mapping as before. Not done: the 16-byte aligned payloads split at load and the scratch-free decoders of the TODO item (speed, to be measured on a Mac); the units are already decoded once for up to eight rows.
  • The emulator (src/emu.rs, emu/metal_shim.h, emu/driver.cpp): the full source of simdgroup.metal‘s library (common, the tables, matvec.metal, attention.metal, norm.metal, simdgroup.metal) compiled as C++20 by clang++ (INGA_MSL_EMU_CXX), with three rewrites (no metal_stdlib, no [[...]] attributes, a threadgroup array declared in a kernel made static); the shim maps the address spaces to nothing, half to _Float16, the threadgroup barrier to a std::barrier of the threadgroup, simd_sum / simd_max / simdgroup_barrier to the 32 threads of the SIMD group, and gives each thread a whole simdgroup_matrix (8 x 8 values; simdgroup_load, _store by one lane, _multiply_accumulate in float). The driver runs the threadgroups one after the other, each one’s threads at once on a pool, with the grids of shapes.rs (plan_matvec, plan_tiles, plan_flash) and threadgroup memory filled with garbage. One test, kernels_on_the_cpu_emulator, builds it once and checks, against inga-quant’s dequantize_row and an f64 attention: every type’s matvec_<t> (1, 3 and 11 rows, threadgroups of 256 and 64), matvec_<t>_simd (1 and 8 rows) and mm_<t> (edge tiles, 9 to 33 rows; 895-value float rows, 544 or 512 for the blocks), on random blocks (every bit pattern decodes; the scales set to finite values), within 1e-5 of the sum of the products’ magnitudes (1.5e-3 for the half-staged tiles); flash_h<D> for the nine head sizes and six more cases (a window, soft-capping, sinks, one or as many KV heads, 21 and 50 earlier positions) and attention / attention_simd on the last three rows of each. On a machine without a compiler, or with INGA_MSL_EMU=0, it says why and passes; it runs on Linux only (the macOS job has the real compiler).
  • What it does not check: Apple’s compiler (what it refuses, as in §8’s “What the runner found”), the real simdgroup_* semantics and timing, and speed. The M2 kernels of the new types run on the CI’s paravirtual device in metal_everything (every type’s products against HostOps, Llama models in Q4_0, Q4_1, Q5_0, Q5_1, Q2_K, Q3_K, Q5_K, IQ4_NL and IQ4_XS end to end): build.yml’s manual run with the input only: metal on this branch. M3’s need an Apple7 GPU (docs/mac-testers.md).
  • GPU-resident generation (the indirect command buffer and the megakernels of the TODO item) is not started: without a Mac it can be neither measured nor checked.
