GPUs in the mesh, and the master Inga suggests

Status: built for 0.27.0 (G1–G4, M1, M3, and M2 by --priority) and 0.28.0 (part 2: M2’s handover and the Mesh page’s banner with Make master, uptime and the door in the suggestion, a node’s layers across its GPUs, satellites reading prompts on their GPU, a satellite’s GPU caches for the master’s sessions, a satellite whose GPU fails placed again on its CPU, mesh profiles in the placement suite; see “As built” and “As built, part 2”). Remaining: the handover sending the model’s file and the conversations (the new master must hold the file; the conversations start over), the door’s address kept on the old node with requests forwarded, and the checks on the maintainer’s machines. Asked by the maintainer on 2026-10-12: “can Inga suggest which node should be the master from their characteristics? Write a spec to do GPU mesh”. It lifts the limit of the mesh spec (2026-10-09-inga-mesh-design.md §5: “CPUs only, GPUs and VRAM later”). Code: crates/inga-dist/src/mesh.rs (the announcement), place.rs (the placement), stages.rs (MeshSetup, MeshStages), worker.rs; src/commands/mesh.rs (inga satellite, the master’s engine, today gpu_notes = ["not with --mesh yet"]); crates/inga-gpu (GpuLayers, reserve, budget); the placement suite (src/commands/placement/hardware_profiles.rs); the web UI’s Mesh page.

1. What happened (2026-10-12)

Section titled “1. What happened (2026-10-12)”

inga serve Qwen3.6-35B-A3B-Q4_K_M --mesh home on ISAIA, with three machines:

Node CPU RAM GPU Free RAM
ISAIA (master) 8 threads, AVX-512 31 GiB Quadro P1000, 4 GB ~15 GB
CYBERSPACE 4 threads, AVX2 15 GiB — 8 GB
DESKTOP-1VFB0M9 8 threads, AVX2 31 GiB GeForce GTX 1070, 8 GB, CUDA 24 GB

  • No GPU was used.

    • The master set its own P1000 aside: GPU: not used (not with --mesh yet). Without --mesh the same model kept every layer’s attention on it.
    • DESKTOP-1VFB0M9’s GTX 1070 was not seen at all: the announcement carries CPU, threads, RAM and a measured speed, nothing about GPUs.

  • The plan expected 0.9 tok/s. ISAIA alone with its GPU is very likely faster.

  • The master was wrong. DESKTOP-1VFB0M9 is the better machine for this model. It has the bigger GPU, and 24 GB of free RAM that hold all of the model’s experts (18.2 GB). ISAIA had to read them from its SSD.

    The election chose ISAIA because it “holds a model” and has the most RAM. Nothing compared what each machine would do with the model.

  • The placement costs a token as all of its layers’ bytes over the node’s speed (place.rs). For a mixture of experts that is wrong. A token of an A3B model reads its attention, its shared experts and the 8 experts it routes to, not all 128 or 256. The 0.9 tok/s estimate was too low for that reason too.

2. GPUs in the mesh

Section titled “2. GPUs in the mesh”

G1. Each node announces its devices

Section titled “G1. Each node announces its devices”

  • The announcement gets a devices list. Per GPU:

    • backend (CUDA, Vulkan, Metal);
    • name;
    • VRAM total and free (the driver’s budget, as inga devices reads it);
    • its measured speed in bytes of weights per second.

    The speed comes from a short matrix-vector run at the satellite’s start, as the CPU’s is measured today.

  • The announcement’s size: TXT records are short, so the list is compact: gpu0=cuda;GTX 1070;8192;7700;310 (backend; name; VRAM MiB; free MiB; GB/s). Several gpuN keys for several GPUs.

  • inga satellite’s start line names them: 4 threads AVX2, 9.5 GB/s; CUDA 0 GeForce GTX 1070 (8 GB, 310 GB/s).

  • --device on a satellite (auto, cpu, cuda:0, vulkan:0) chooses as for inga serve. --device cpu keeps a satellite on the CPU.

G2. The placement plans each node like a single machine

Section titled “G2. The placement plans each node like a single machine”

Today a node is one tier: bytes over speed. It becomes the same plan Inga makes on one machine, for the layers it is given:

  • A node’s tiers: VRAM (its GPU’s budget less inga_gpu::reserve), RAM, disk. Each tier has its own speed.
  • For a range of layers on a node, its cost per token is what the single-machine planner (Plan, the placement profiles) computes:
    • the GPU’s share at the GPU’s speed;
    • the CPU’s share at the CPU’s speed;
    • disk reads for what fits nowhere.
  • For a mixture of experts, the bytes a token reads are the active ones: attention, shared experts, and k of n routed experts. They are not the layer’s whole size. The memory needed is still the whole layer’s.
  • The layers’ order across nodes stays contiguous ranges, the dynamic program of place.rs, with this per-node cost function in place of bytes over speed.
  • Round trips: with GPUs a node’s share of a token can be milliseconds, so the round trip (hop) weighs much more than today.
    • The dynamic program already adds one hop per satellite used. It will choose fewer nodes when the link is slow.
    • A link above 2 ms gets a note: “CYBERSPACE is 7.9 ms away (Wi-Fi?): each token pays it once; a wired link would help”.
  • The plan’s line names the devices: this machine layers 0-19 (attention on CUDA 0 P1000, experts in RAM), DESKTOP-1VFB0M9 layers 20-39 (all on CUDA 0 GTX 1070 + RAM): expected 14 tok/s.

G3. A satellite runs its layers on its GPU

Section titled “G3. A satellite runs its layers on its GPU”

  • A satellite loads the parts it receives as a model of its own range. It then uses the same engine path as inga serve on one machine:

    • GpuLayers for the layers or attention the plan puts on its GPU;
    • the CPU for the rest;
    • the routed experts in RAM.

  • The worker protocol does not change: activations in, activations out. The KV cache of a GPU layer lives on that GPU.

  • The satellite’s VRAM is held under the same rules as on one machine:

    • the reserve;
    • the Vulkan suballocator;
    • the shrink-and-retry fallback of 0.26.2.

    A satellite that cannot place what the plan gave it answers with an error. The master then plans again without that GPU (the satellite errors’ S2).

G4. The master keeps its GPU

Section titled “G4. The master keeps its GPU”
  • gpu_notes = ["not with --mesh yet"] goes. The master’s own range is planned and run with its GPU like any node’s.
  • --mesh-local N still caps the master’s layers.

G5. Where the layers come from, and their size on the GPU

Section titled “G5. Where the layers come from, and their size on the GPU”
  • The satellite receives the GGUF’s chunks as today, then uploads to its GPU what the plan gives it.
  • Repacking at load (Q4_K, Q8_0…) happens on the satellite, as on one machine.
  • The transfer is the same, but a GPU satellite is worth sending more layers to. The first load of a big model on a slow link can take minutes. The load’s progress (2026-10-12-serve-early-and-load-progress-design.md) shows it, and the parts are cached by hash on the satellite (--cache), so the next load sends nothing.

3. The master Inga suggests

Section titled “3. The master Inga suggests”

M1. Which node would be the best master for this model

Section titled “M1. Which node would be the best master for this model”

When a model loads in a mesh, the master simulates the plan with each node in turn as the first stage. It uses the announced devices and memory, and the measured links. It then compares the expected tokens per second.

What decides it, in order of weight:

  1. The expected tok/s of the whole plan.
  2. Which nodes hold the model file. The master needs it to send the parts. A node without it would first receive the whole file once, an extra cost shown in the suggestion.
  3. The door role: where the users connect. A suggestion never moves the API’s address silently.
  4. How long the node stays up (uptime, announced). A laptop that comes and goes is a poor master.

The suggestion appears when another node beats the current master by more than 20 %:

  • an event and a stderr line: DESKTOP-1VFB0M9 as master would run Qwen3.6-35B-A3B-Q4_K_M at about 14 tok/s, against 0.9 here (GTX 1070 8 GB, all experts in its 24 GB of free RAM; it does not have the model file: 19 GB to send once);
  • on the Mesh page, a banner with the comparison table and a Make master button.

M2. How a suggestion is acted on

Section titled “M2. How a suggestion is acted on”
  • Today, by hand. Start that node with --priority 10, the existing rule that wins the election, and give it the model. The suggestion prints the exact command.
  • With the handover of the mesh spec §4.5 (inga mesh handover NODE, planned):
    • the Make master button sends the plan and the state to the new master;
    • the model’s file goes there if it lacks it, with the progress shown;
    • the button waits for the new master’s confirmation, then steps down;
    • the door’s address can stay on the old node, which forwards requests (the router of the API nodes).
  • Never automatic. Moving the master moves a model file and maybe the API’s address: the user decides.

M3. inga mesh show --suggest

Section titled “M3. inga mesh show --suggest”
  • Prints, for a model, the plan with each candidate master and its expected tok/s.
  • Prints the best single machine alone, which is often the honest answer: “this model runs fastest on DESKTOP-1VFB0M9 alone (14 tok/s): a mesh adds nothing here; use it as an API node”.
  • The comparison covers the mesh against each machine alone, so the user can see when the mesh is not worth it.

4. Tests

Section titled “4. Tests”

  • The placement suite gets meshes. A profile names several machines (CPU, RAM, GPUs with their VRAM and speeds, the links) and a model. The expected plan is checked like the single-machine profiles (tests/profiles/), on simulated GPUs (SimGpu).

    The first profiles are the maintainer’s three machines with Qwen3.6-35B-A3B Q4_K_M:

    • the best master is DESKTOP-1VFB0M9;
    • the P1000 is used for the master’s attention;
    • a 7.9 ms link gives fewer stages than a 0.6 ms one.

  • The MoE cost: a mixture’s per-token bytes in the plan are the active ones. The expected tok/s of a single-node plan matches inga bench on the same machine within 30 % (checked on the maintainer’s machines and recorded in docs/performance.md).

  • The announcement: gpuN keys round-trip through the TXT records. An old node without them is planned as CPU-only.

  • A satellite with a GPU (the CUDA runner, in-process) runs its layers there. The output equals the single-machine run’s within the backends’ tolerance.

  • The suggestion: three simulated nodes where the second is 3× faster as master give the event and the command. One 10 % faster gives nothing.

5. Order

Section titled “5. Order”
  1. G1 and G4: the announcement, and the master keeping its GPU.
  2. G2: the per-node cost, with the MoE correction.
  3. G3: satellites on their GPU.
  4. M3: the comparison, which shows at once whether a mesh pays.
  5. M1: the suggestion.
  6. M2: the handover.

As built (0.27.0)

Section titled “As built (0.27.0)”
  • G1. inga_dist::GpuInfo (device as --device names it, name, memory, the bytes free for weights, speed). In the announcement gpuN=cuda:0;GeForce GTX 1070;8192;7700; 210.0 (the device rather than the backend alone, so a node with two GPUs of one API tells them apart; memory and free bytes in MiB, the speed in GB/s with one decimal); in the worker protocol’s Welcome (version 7). The free bytes are the node’s own budget (inga_gpu::budget: the driver’s free memory less the reserve), so the planner needs no rule of the other node’s system. The speed is inga_gpu::measure_speed: a 64 MiB Q8_0 matrix-vector product, warm, for a quarter of a second at most (placement::mesh_devices). On lavapipe: 330 MB/s. The master announces its GPUs too, from inga serve --device.
  • G2. place::place_layers takes a LayerCost per layer (dense bytes, routed experts’ bytes, the share a token reads) and a GpuTier per candidate. A node’s cost for a range is a closed form, not the single-machine Plan: its GPU takes the dense weights and the KV cache first, then experts, in proportion; each share at its speed. The dynamic program is unchanged (ranges, one hop per satellite, the master’s disk overflow). A GPU not measured counts 8 times its CPU. The output layer runs on the master: compare adds it (on the master’s GPU when it has room). mesh::layer_costs reads them from Model::parts and MoeSpec. The 2 ms note is an event per satellite, (Wi-Fi?) above 5 ms. The plan’s line: pc-gpu layers 0-3 (all on CUDA 0 Sim), attention on …, experts in RAM, 3.1 GB on …, the rest in RAM.
  • G3. Worker::with_gpu(attach, devices): attach is the binary’s placement::attach_range(model, --device, ctx, layers, head = false), the single-machine planner and upload (with its shrink-and-retry) limited to the layers given (GpuPlanner::within: the last of the range first; a satellite never takes the output layer, which its model lacks). The stages are kept per model and range, freed with the model; each connection opens its KV cache there. Model::hand_over moves layers of a fresh cache (a layer cache too) to the device’s stages or attention. Under auto a GPU that cannot take them leaves them on the CPU, said on the satellite’s console; one named by --device makes the Load fail, which the master handles as any satellite failure (it leaves the satellite out and places again, rather than planning again without its GPU).
  • G4. The master’s GPU: attach_range(…, local layers, head = true) and MasterStages (the GPU’s stages, attention and output layer, then the satellites’); Engine::new_cache hands the satellites’ stages over beside a GPU’s attention; Engine::remote_layers keeps “part of the model on other machines” in the placement’s line. The planner of the mesh weighs the master’s GPU from its announcement.
  • M1. place::compare and better_master (more than 20 %); round trips from the present master’s measures (a node’s trip to the new master is the larger of the two nodes’ trips to the present one). The event says the tok/s, the GPU, whether what its GPU does not hold fits its RAM, whether it lacks the model file, how fast it would be alone, and the --priority 10 command. Uptime and the door are not weighed yet.
  • M3. inga mesh show --suggest MODEL (--json: suggest), the model read from this machine (its header and tensor table only).
  • Map (mesh map spec M3). The node’s devices in GET /api/inga/mesh carry backend, memory, used (the first GPU of a node that runs layers) and reason, which the existing chips read; a VRAM bar per GPU shares the RAM bar’s row.
  • Tests. Protocol and announcement round trips (protocol.rs, mesh.rs), the placement with simulated GPUs and the maintainer’s three machines (place.rs: ISAIA’s P1000 holds the attention of the layers it keeps, DESKTOP-1VFB0M9 is the fastest master, a 7.9 ms link gives fewer stages, a node 3 times faster behind a slow link is suggested and one 10 % faster is not), the range-limited GPU plan (placement.rs), a satellite whose layers run on a simulated GPU (HostOps) in the mesh’s end-to-end test (crates/inga-dist/tests/mesh.rs), and, gated by INGA_CUDA=1 / INGA_VULKAN=1 (gpu.yml), the GPU a node announces and a master’s and a satellite’s layers on the GPU against the CPU’s logits (dense and MoE; passed on lavapipe).

As built, part 2 (0.28.0)

Section titled “As built, part 2 (0.28.0)”
  • M2, the handover. Mesh::hand_over(node, wait): only the master; the node (id or name) must be alive, may coordinate (an inga serve --mesh, not a satellite) and speak this protocol. The master announces ho=<id>; the node named by a master that claims its place takes a priority above every node’s (follow_handover, on each election), which wins the election as --priority would and stays; the old master forgets ho once the mesh elects the node (“handed the master’s place over to …”). inga mesh handover NODE finds the master by listening (--mesh, --peers, --mesh-wait) and calls its POST /api/inga/mesh/handover (--api-key), which waits up to 10 s for the election. Each inga serve --mesh watches whether it is the master (MeshView’s fourth member) and, once a change has lasted 10 s, unloads and loads its models again: the new master splits them across the mesh, the old one runs its own alone. Not built: the model’s file sent to a new master that lacks it (the handover is offered only to a node that holds it), the conversations passed on, and the door’s address kept on the old node.
  • The banner. ModelSplit::suggestion is a Suggested (the node, its tok/s and this master’s, whether the handover can make it the master, the command, the reasons, the table of each node as master and alone); GET /api/inga/mesh gives it as the model’s suggested beside the text. The Mesh page’s #mesh-suggest draws it with Make master, or the command for a node that cannot take the place (webui_mesh_map.cjs: suggest-*). Strings in every language block.
  • Uptime and the door (M1). place::better_master_weighed(compared, standing): a node up for less than STEADY_UPTIME (an hour) needs NEW_NODE_MARGIN (50 %), the others MASTER_MARGIN (20 %); among the plans within DOOR_CLOSE (10 %) of the fastest, a door’s wins. The event says a short uptime and “it serves no API now: the users would connect to … instead”.
  • A node’s layers across its GPUs. inga_gpu::split_span(sizes, span, devices, head): [split_layers] of a span that need not end at the last layer, the output layer only when allowed (None on a satellite) and every layer of the span is on the devices. plan_split takes the planner’s within and no_head (layer sizes from layer_sizes_in), so attach_range with --device cuda:0,cuda:1 gives a DeviceStages of the node’s range; the 0.27.0 refusal is gone.
  • Prompts on a satellite’s GPU. inga satellite gives its worker a prefill loader (unless --device cpu): the mesh: model opened whole from the parts received, its KV type set, attach_range(0..n, head = true), and a GpuPrefill whose caches hand the layers and the output layer over. inga_gpu::measure_prefill (64 tokens by an 8 MiB Q8_0 matrix, the CPU probe’s shape) gives placement::mesh_prefill; a node announces the larger of its CPU’s and its first GPU’s prompt speed.
  • The master’s sessions on a satellite’s GPU. Protocol 8: Load carries sessions and gpu. MeshSetup has the server’s ctx and sessions; the satellite’s GpuAttach plans Need { ctx, sessions }, its GPU stages kept per model, range and sessions.
  • A satellite whose GPU fails. After sending a satellite planned with a GPU its parts, MeshStages::plan loads its layers there at once (Node::load_on, the master’s sessions). A failure that a CPU-only load does not repeat marks the node’s GPU out (no_gpu), and the model is placed again with its CPU only; both failing leaves the satellite out as before. The stages’ later Loads say gpu: false for it.
  • A mixture’s output layer first on the master’s GPU. The single-machine planner puts the output layer on a GPU before attention blocks alone (the largest product of a token for the least memory); the mesh’s placement now does too: for a mixture of experts, MeshStages::plan and compare (place_with_head) take the output layer from the master’s GPU tier first and run it at the GPU’s speed, where 0.27.0 counted it on the CPU whenever the layers filled the GPU (20 ms a token on ISAIA).
  • Mesh profiles. hardware_profiles.rs: mesh_run plans a ghost model on a mesh of profiles (their GPUs announced from the simulated devices by devices_of, assumed speeds: CPUs 20 and 9.5 GB/s, the P1000 70 GB/s, the GTX 1070 210 GB/s), the real place_layers, each node’s range on its own simulated GPU by attach_span, and each node as master; golden files tests/profiles/mesh-home-{0.6,7.9}ms__qwen3.6-35b-a3b-q4_k_m.txt. With these speeds DESKTOP-1VFB0M9 is the fastest master (38.7 tok/s against ISAIA’s 34.0) but by 14 %, under the 20 % of a suggestion; CYBERSPACE is used in neither plan (DESKTOP-1VFB0M9 holds every layer ISAIA does not), so its link only changes its own plan as master. The files also show where the mesh’s cost model and the GPU planner differ: the cost model gives ISAIA’s P1000 routed experts that the planner, with 1.1 GB of CUDA budget and its reserve for experts, does not put there.
  • Tests. split.rs (spans), placement.rs (a node’s range across two hosts, its hidden state as the CPU’s), place.rs (uptime and the door), mesh.rs (the handover between three nodes), crates/inga-dist/tests/mesh.rs (the sessions a GPU satellite is planned for; a failing GPU placed again on the CPU, the logits of one machine), cli.rs, the browser test; gated by INGA_CUDA=1 / INGA_VULKAN=1 in gpu.yml’s mesh steps: a satellite reading a prompt on its GPU against the CPU’s logits, the GPU’s prompt speed, and (CUDA’s step) a satellite’s range split across CUDA 0 and Vulkan 0.
