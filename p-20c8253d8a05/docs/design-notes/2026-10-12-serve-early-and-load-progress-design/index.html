The server up at once, and the load seen while it happens

Status: proposed (asked by the maintainer on 2026-10-12: “until the models are sent to the nodes I see nothing: from the GUI I should see that the satellites are starting, their state, etc.”); the release is decided by the maintainer (proposed: L1, L6 and L7 in 0.26.3 with the satellite errors’ S2, the rest after). L1, L6 and L7 shipped in 0.26.3; L2 and L3 built after it, with the small parts of L4 and L5 (see “As built (L2, L3)” at the end; what is left is listed there). Code: src/commands/serve.rs, src/commands/mesh.rs (join, inga satellite), crates/inga-server/src/lib.rs (serve_with), crates/inga-server/src/router.rs, crates/inga-server/src/models.rs, crates/inga-dist/src/mesh.rs (the announcement, to_json), crates/inga-dist/src/parts.rs and stages.rs (sending), the web UI (crates/inga-server/src/webui.html: the Chat header, the Mesh page).

1. What happens today

Section titled “1. What happens today”

inga serve MODEL --mesh home does these steps in order, and nothing is served until the last one is done:

  1. Join the mesh and wait --mesh-wait (3 s) for the other nodes (commands::mesh::join).
  2. Bind the port. serve_with binds it, but does not accept connections yet.
  3. Load the first model (state.router.get(None) before on_listen). With satellites this means:
    • measuring them;
    • planning the layers;
    • sending each one the chunks it lacks: gigabytes over the LAN, minutes;
    • each satellite loading its part.
  4. Print serving … on http://… and only then accept connections.

So for minutes:

  • the browser waits on a connection that is never accepted;
  • the Mesh page, which already draws nodes, splits, bytes sent and events (/api/inga/mesh), cannot be opened;
  • the only trace is the console’s lines, some glued to the spinner’s.

If the load fails, the process exits, so the GUI never shows the error at all. That happened on 2026-10-12 with CYBERSPACE’s full disk.

2. The fixes

Section titled “2. The fixes”

L1. Serve at once, load in the background (for 0.26.3)

Section titled “L1. Serve at once, load in the background (for 0.26.3)”
  • Accept connections right after the bind. Joining the mesh and loading the first model run on a background thread, as the web UI’s own POST /api/inga/load already does on an empty server.
  • The console says both moments:
    • listening on http://127.0.0.1:8080 (loading Qwen3.6-35B-A3B-Q4_K_M; the web UI shows the progress);
    • then ready: Qwen3.6-35B-A3B-Q4_K_M on http://127.0.0.1:8080 (…).
  • The release notes say that scripts waiting for the old serving line should poll /health instead.

L2. A load is a job with phases

Section titled “L2. A load is a job with phases”
  • The router keeps, for a model being loaded, its phase, the time in it, a progress where one is known, and the error if it failed.
  • The phases:
    1. waiting for nodes (--mesh-wait, with the nodes found so far);
    2. measuring (each satellite’s speed and round trip);
    3. planning (the split, and why);
    4. sending (per satellite, below);
    5. loading (the master’s own part: mapping, repacking, the GPU upload, with its bytes);
    6. ready, or failed.
  • Where it is read:
    • GET /api/inga/models gives each model’s state (as now) and load: {phase, since_s, done_bytes, total_bytes, nodes: […], error};
    • /health gives the same phase while it answers 503.

L3. Each satellite’s state, as it happens

Section titled “L3. Each satellite’s state, as it happens”

The states a satellite goes through, for a model:

State What it shows
found the node, its CPU, RAM, free cache space (from the satellite errors spec, S3)
measured speed and round trip
planned its layers, with the reason
offering what it already holds and what it lacks
sending percentage, bytes sent of bytes to send, MB/s, time left (L5)
loading the satellite maps the parts it received
ready
running with its share of each token’s time once requests come

The other outcomes:

Outcome When
failed with the satellite’s own error (S5’s wording)
left out with the reason: unreachable, no room, too slow
left it stopped announcing

Who knows what:

  • The master knows its side: the plan and the bytes it sent. parts.rs already counts them (Sent), but only at the end. They are counted as they go.

  • The satellite knows its side:

    • bytes written;
    • disk space left;
    • “loading”, then “loaded … from the parts received”, which today is only printed on the satellite’s own console.

    It adds them to its announcement (phase=receiving 2.1/4.5GB, phase=loading, phase=ready), so the master and the GUI see them within one heartbeat. The announcement grows by one short field.

  • GET /api/inga/mesh gives per node a load object: the state, bytes, speed, time left, the error. It also gives a phase at the top.

L4. The GUI shows it

Section titled “L4. The GUI shows it”

  • The Chat page. While the model loads, the header reads:

    • “Loading Qwen3.6-35B-A3B-Q4_K_M — sending layers to CYBERSPACE, 2.1 of 4.5 GB, 1 min left”;
    • a progress bar;
    • a link to the Mesh page.

    The message box stays usable: a question typed now waits for the model, and says so.

  • The Mesh page.

    • Live: it polls every second while a load runs, every 5 s otherwise.
    • One row per node:
      • its state with an icon (⏳ found, 📏 measured, 📤 sending, 💾 loading, ✅ ready, ⚠️ left out, ❌ failed);
      • a progress bar for the bytes, with the percentage, the speed and the time left (the same numbers as the consoles, L5);
      • its layers;
      • the reason when it is left out or failed;
      • a short tip from the errors specs, for example “firewall: TCP 9090” or “–cache on a drive with room”.
    • The events list grows as the load goes, newest first, with the phase each belongs to.
    • The split drawing shows the planned layers greyed out until their node is ready.

  • Actions while loading:

    • cancel the load;
    • leave this node out, which re-plans without it;
    • retry a failed node.

  • After a failed load:

    • the error and the “report” button of the error reports (2026-10-11-error-reports-design.md);
    • retry, retry without the failed nodes, and load another model.

L5. The console says the same, on both machines

Section titled “L5. The console says the same, on both machines”

The maintainer, on 2026-10-12: “the master is sending chunks to the satellite: from the master I see what happens, from the satellite I don’t see data arriving. And I have no idea how long it will take or what percentage of the data is sent”. Both ends show the same numbers, live, during every transfer.

  • The total is known before the first chunk. It is the size of the chunks the satellite lacks, from the offer’s answer. The percentage is bytes done over that total, never over the whole model.

  • The speed is the average of the last 10 s, so a slow start does not stay in it. The time left is the bytes left over that speed. It is shown as “about 2 min”, and “estimating…” for the first 3 s.

  • The master’s console, one spinner line per transfer: sending CYBERSPACE layers 31-39: 47 % (2.1 / 4.5 GB), 38 MB/s, about 1 min left. With several satellites it adds a total line.

  • The satellite’s console gets the same line, from its side: receiving Qwen3.6-35B-A3B-Q4_K_M from ISAIA (layers 31-39): 47 % (2.1 / 4.5 GB), 38 MB/s, about 1 min left · 7.9 GB free on D:. Then loading layers 31-39… and ready: layers 31-39 of Qwen3.6-35B-A3B-Q4_K_M.

    Today the satellite prints nothing until the end. A satellite on another desk is then indistinguishable from one that is stuck.

  • When nothing arrives for 15 s in the middle of a transfer, both sides say so: “no data from ISAIA for 15 s (network, or the master busy)”. This is not an error until the transfer’s timeout.

  • A transfer that resumes (chunks already held, cached) says how much was skipped: 4.5 GB to send, 1.2 GB already here.

Also:

  • Each phase change and each satellite’s change of state is a line on stderr, through the spinner’s writer (2026-10-12-load-messages-design.md).
  • The console tells the same story as the GUI.

L6. A failed load does not stop the server (for 0.26.3)

Section titled “L6. A failed load does not stop the server (for 0.26.3)”
  • When the first model fails to load, the server stays up. The model’s state is failed with its error, and the GUI offers the actions of L4.
  • The process exits only when it cannot serve at all: the port cannot be bound, or a usage error in the options.
  • Exit 1 for a failed load stays available with --exit-on-load-error, for scripts that relied on it.

L7. Requests during the load (for 0.26.3)

Section titled “L7. Requests during the load (for 0.26.3)”
  • /health answers 503 {"status": "loading", "phase": …} until a model is ready, as now. Docker and orchestrators that read it are unchanged.
  • A chat or completion request for the model being loaded waits for it up to --load-wait (default 120 s). Then it gets 503 with Retry-After and a body naming the phase. It never hangs on an unaccepted connection.
  • A request for a model that failed gets 503 with the error.
  • /v1/models lists the model being loaded, with Inga’s state field, as it already does for an unloaded one.

3. Tests

Section titled “3. Tests”
  • L1: with a model whose load is held by a test hook, GET / (the web UI) and /health answer at once: 200, and 503 loading. The ready line comes after the hook releases.
  • L2: the phases come in order for a mesh load with an in-process satellite. done_bytes grows while chunks are sent.
  • L3:
    • the satellite’s announcement carries receiving, loading, ready in turn;
    • a satellite failing at a write turns failed with its error;
    • one unreachable turns left out.
  • L4: the Mesh page’s rendering of each state from fixture JSON, in the web UI’s existing test style. The cancel and leave-out actions reach their endpoints.
  • L6:
    • a load that fails leaves the server up;
    • /api/inga/models shows the error;
    • a second POST /api/inga/load of another model works;
    • with --exit-on-load-error, the process exits 1.
  • L7: a chat request during a held load waits and then answers once the hook releases. With --load-wait 1 it gets 503 and Retry-After.

4. Order

Section titled “4. Order”
  1. L1, L6 and L7 together: they change the same function (serve_with) and come with the satellite errors’ S2.
  2. L2 and L3, which are the data.
  3. L4, the GUI.
  4. L5, the console, after the load messages fix.

As built (L1, L6, L7, 0.26.3)

Section titled “As built (L1, L6, L7, 0.26.3)”
  • L1: serve_with calls its on_event with Started::Listening right after the bind and loads the first model on a thread of its own (Router::load), then Started::Ready or Started::Failed. inga serve joins the mesh before the bind (binding its UDP port) and waits --mesh-wait in the first load (mesh::settle, once).
  • L6: a failed load is kept in the router (Status::failed, ModelState::Failed) with its error; /health answers 503 failed when nothing is loaded or loading. POST /api/inga/load, a changed context, device or variant try again. A first load failing on a usage error (400) still exits 2; --exit-on-load-error exits 1.
  • L7: a request locks the loaded models for at most --load-wait (Router::lock_loaded), then gets 503 with Retry-After: 10, set through a thread-local of the connection (http::set_retry_after). /health’s phase is loading until L2 brings the phases.

As built (L2, L3, and parts of L4 and L5)

Section titled “As built (L2, L3, and parts of L4 and L5)”
  • The job: inga_core::progress::LoadJob keeps a load’s phase (waiting, reading, measuring, planning, sending, loading, starting, ready, failed), its detail, the time in it, the phases gone through with their seconds, its bytes (with the speed over the last 10 s and the time left after 3 s), each node’s state (found, measured, planned, sending, loading, ready, failed, left_out, with why and the states it went through) and the error. Once ready or failed it no longer changes.
  • Who reports: the router (Router::lease) makes one per load (mark_loading too) and enters it on the loading thread and on the model’s worker thread (whose sessions load the satellites’ layers); the code reports to progress::current(): mesh::settle (waiting, the nodes found), load_engine (reading, then loading before Engine::prepare), mesh::load and MeshStages::plan (measuring, each satellite found, measured or left out; planning, their layers; sending, the bytes of push as each chunk is answered, the total being the part’s chunks less those the satellite holds), Router::start (starting), MeshStage::open (each satellite loading, then ready). The router ends it ready or failed.
  • The satellite’s side: Running keeps a SatPhase the worker updates (Offer: receiving, with the bytes it lacks; Chunk: the bytes written; Load: loading, then ready or failed); the announcement carries it as ph=recv:DONE:TOTAL, load, ready or fail (NodeInfo::phase), shown by GET /api/inga/mesh as each node’s load (mesh::phase_json).
  • The API: GET /health gives the phase and the load (the last one when nothing loads); GET /api/inga/status (the spec’s /api/inga/models) each model’s load; GET /api/inga/mesh the phase, the load and each node’s load, the master’s view (from: master) with the satellite’s announcement inside (satellite) (nodes::with_load). Documented in docs/api/inga.yaml (Load, NodeLoad).
  • The console: inga serve shows the job (serve::show_load): on a terminal one spinner line, loading MODEL: sending the satellites their parts · pc-a layers 31-39: 47 % (2.1 GB / 4.5 GB), 38.0 MB/s, about 2 min left; otherwise a line at each change of phase or of a node’s state and at each quarter of the bytes. The ready line waits for it. inga satellite shows its side (mesh::show_receiving): receiving MODEL: 47 % (2.1 GB / 4.5 GB), 38.0 MB/s · 7.9 GB free, then loading layers 31-39 of MODEL….
  • The web UI: a line above the message box (drawLoad) while a model loads: the phase, each satellite receiving, a bar for the bytes, a link to the Mesh page, the phases in its tooltip; the error once the load failed; read every second while a load runs. On the Mesh page each node’s box says its state in the load instead of what it runs (meshLoadText), its card the same with the reason, and the split’s section the load’s line.
  • Tests: the job’s state machine (inga-core progress::tests), the router’s job (router::tests::a_load_is_a_job_whose_phases_the_api_reads), a mesh load on 127.0.0.1 whose satellite goes found → measured → planned → sending → loading → ready and announces receiving, then ready (inga-dist/tests/mesh.rs a_load_shows_each_satellite_receiving_then_ready), and the web UI in Chromium with a mocked API (inga-server/tests/webui_load_progress.rs).

Left for later:
