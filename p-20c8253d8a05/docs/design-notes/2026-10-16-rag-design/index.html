Retrieval over documents, code and wikis: best-in-class RAG in Inga

Status: proposed, 2026-10-16 (asked by the maintainer: “Inga’s RAG as good as possible”). Phases R1–R4 scheduled at the head of 0.33.0 with a UX review (R-UX), R5–R11 in 0.34.0, the doubtful ideas in TODO.md’s Experiments (§12). It extends memory and documents (M2: readers, chunks, collections, reranking, built in 0.25.0 and 0.26.5) and builds on the ingestion survey of PR #719 (docs/research/rag-ingestion-2026-10.md, “the survey” below), which compares about fifteen apps on folders, incremental re-index and progress. This spec adds what the apps and the literature do after ingestion: chunking, hybrid retrieval, reranking, graphs, agentic retrieval, citations, evaluation and the index store.

Code it touches: crates/inga-docs (readers, chunk.rs), crates/inga-engine/src/store.rs and collections.rs (the store), a new crates/inga-engine/src/rag/ (index, BM25, fusion, graph, jobs), crates/inga-server/src/collections.rs and documents.rs (API, grounding), src/commands/ (inga docs, inga eval rag), the web UI’s Documents page, docs/api/inga.yaml.

0. Decisions (2026-10-16)

Section titled “0. Decisions (2026-10-16)”

The maintainer’s priorities, which order everything below:

  1. Search must be fast and precise. Query latency and retrieval quality come first.
  2. Indexing speed is secondary. After the first full pass, ingestion is a continuous trickle of a few changed files; only the first run is slow, and it needs a good progress display, not more speed.
  3. Therefore compute is spent at index time to buy query-time precision and speed: richer chunks and metadata, several representations (dense, BM25, link and symbol graph), an LLM-written context per chunk, summaries per file and section, parent/child links, a document-level vector for a two-stage search. Each is computed once per changed chunk or file.
  4. The query path makes no LLM call by default. Query rewriting, multi-query and HyDE stay optional, per request.
  5. Ingestion never blocks or slows a query: it runs on its own low-priority threads and yields to the chat model on the CPU and the GPU (§7.4).
  6. Everything stays in the executable: no database, no C library; the index is Inga’s own files, in RAM under a memory budget and memory-mapped above it (§8).
  7. Before designing a feature, survey how the others do it (the maintainer’s standing rule, now in AGENTS.md): §2 and §3 are that survey.

1. Goals and non-goals

Section titled “1. Goals and non-goals”

Goals

Section titled “Goals”
  • Precision: on Inga’s own evaluation sets (§10), recall@10 and nDCG@10 at least as good as the best configuration the literature reports for the same technique, and measured before and after every phase.
  • Latency targets (warm, CPU, 100k chunks; targets, to be measured by inga eval rag, §10): retrieval before rerank p50 ≤ 20 ms, p95 ≤ 50 ms excluding the query’s embedding; the query’s embedding ≤ 30 ms on a CPU (cached for repeated questions); the rerank of the top N=32 ≤ 150 ms on a GPU and ≤ 1 s on a CPU with a small reranker.
  • The two real cases: folders of source code and an “LLM wiki” (an Obsidian-like Markdown folder, possibly written by an LLM), plus PDFs and Office documents.
  • Incremental: a changed file updates the vectors, the BM25 index and the graph in place, in seconds; full rebuilds only on a change of encoder or chunker version.
  • Exact citations: file, page, section anchor or line range, opened in the web UI.
  • Same surfaces as today: every chat API (inga_documents), the web UI, the CLI, the OpenAI-compatible /v1/embeddings and /v1/rerank, and MCP for agents.
  • Multilingual: Italian questions over Italian and English documents work as well as English ones (§11.1).

Non-goals

Section titled “Non-goals”
  • A general vector database or a server product (RAGFlow’s MySQL + Redis + MinIO + Elasticsearch): Inga stays one executable.
  • A parser per language (tree-sitter’s grammars are C): the symbol graph comes from tokensave over MCP (§6.6); Inga’s own code chunker is heuristic.
  • Cloud connectors (Confluence, Notion, Drive): Open WebUI’s oikb and AnythingLLM cover them (the survey §5, P7). A git repository and a website by URL stay possible later.
  • Chunk-size knobs in the UI (the survey, “what not to copy”): one tested default per kind (prose, Markdown, code).
  • Full GraphRAG entity extraction by default (§6.5): too costly for a local model, and doubtful; an experiment.

3. What the literature does (techniques)

Section titled “3. What the literature does (techniques)”

Each line: what it is, the evidence, how dated, and the verdict for Inga (build, experiment, no). arXiv and docs.rs could not be reached from the research machine on 2026-10-16: papers were read through their HTML mirrors, ACL Anthology pages, the authors’ blogs or search summaries, and the numbers marked (secondary) are from those.

3.1 Chunking

Section titled “3.1 Chunking”
  • Heading-aware chunks with the heading path. Khoj splits Markdown and Org by heading and prepends the ancestry, recursing when a section is too long; Open WebUI splits on Markdown headers then merges tiny sections (survey §2). No paper needed: the heading path is the cheapest context a chunk can carry. Build (R2).
  • Semantic chunking (breakpoints where neighbouring sentences’ embeddings diverge). Qu, Tu, Bao, Is Semantic Chunking Worth the Computational Cost? (NAACL Findings 2025): on realistic data fixed-size chunks did as well or better; gains only on artificially stitched documents. Experiment (§12), not the default.
  • Parent/child, small-to-big. Embed small children, hand the model the larger parent: LlamaIndex’s auto-merging retriever (levels 2048 / 512 / 128 tokens, a parent returned when enough of its children match), LangChain’s parent document retriever, sentence-window retrieval. Widely used; little controlled evidence. Build (R2) as section → chunk links, the parent given when several of its chunks are hits (it suits Inga’s “whole when it fits”).
  • Late chunking (Jina). Embed the whole document with a long-context encoder, pool per chunk after the transformer: each chunk’s vector sees its document. Günther et al., 2024; about +2.7–3.6 % relative nDCG@10 on BEIR with jina-embeddings-v2-small (secondary: alphaXiv). No extra model; needs an encoder with a long context and mean pooling: BGE-M3 takes 8,192 tokens (but pools by CLS), nomic-embed-text v1.5 is held to its 2,048 trained positions by Inga as by llama.cpp (inga-formats/src/encoder.rs). Experiment (§12): cheap to try, small gain, and neither of Inga’s encoders is the kind it was shown on.
  • Contextual retrieval (Anthropic, 2024-09-19: dated but the reference). An LLM reads the whole document and writes 50–100 tokens situating each chunk; the prefix is embedded and indexed by BM25. On their sets (codebases among them), the top-20 retrieval failure rate fell 35 % with contextual embeddings, 49 % with contextual BM25 too, 67 % with a reranker over the top 150 on top. Cost: about $1.02 per million document tokens with prompt caching. In Inga the “cost” is local compute at index time, which the maintainer’s priorities accept. Build (R7), after the eval can confirm it on Inga’s sets and with a small local model (the paper used Claude 3 Haiku).
  • Summaries per file and section, a tree of summaries (RAPTOR). Sarthi et al., ICLR 2024: recursive clustering and summarising; QuALITY 82.6 % with GPT-4 against 62.3 % before. A full tree is costly to keep incremental. Build (R7) one level (a summary per file and per top-level section, with its own vector); the recursive tree is an experiment.

3.2 Retrieval

Section titled “3.2 Retrieval”
  • Hybrid BM25 + dense with reciprocal rank fusion (RRF, Cormack et al. 2009). Elastic on BEIR: RRF of BM25 and its learned sparse encoder +18 % nDCG@10 over BM25 alone and +1.4 % over the encoder alone, never worse than BM25, insensitive to its parameters (Elastic, 2023: vendor blog, dated). Anthropic’s numbers above show BM25 adding to dense on top of context. Exact identifiers (embed_missing, an error code, a name) are what dense search misses, and they are most of the questions on code and wikis. GPT4All, Open WebUI, RAGFlow, Kotaemon, Cursor all do it. Build (R3).
  • Doc-level vectors, two-stage search. A vector per file (its summary, §3.1) finds the files first; chunk search then runs within them and globally, fused. Cheap at query time; useful on many small files (wikis). Build (R7), measured.
  • Multi-vector / late interaction (ColBERT). A vector per token, MaxSim scoring. ColBERTv2 stores 20–36 bytes per token vector after residual compression, 6–10× less than before (Santhanam et al.; PLAID): for 500-token chunks that is still 10–18 KB per chunk, ten times a single f16 vector. BGE-M3 has a multi-vector head too (its model card), but the GGUF conversions Inga reads carry only the dense output (to be checked). Experiment (§12).
  • Query rewriting, multi-query (RAG-Fusion), HyDE. HyDE embeds an LLM-written hypothetical answer (Gao et al., 2022); it beat unsupervised Contriever, but depends on the LLM’s own knowledge, a weakness on private corpora (Jedidi et al., 2024). Each costs an LLM call per query: against decision 4. Optional per request ("rewrite": "multi" | "hyde", R9); the default stays off unless the eval shows a large gain (experiment, §12).
  • Metadata filters. Path globs, tags and front matter keys, file kind, date: applied before scoring (a bitmap per value). Build (R2, R3).
  • Conversational query. The last user message alone misses “and what about the second one?”: the query is the last message plus the previous user turn’s text, cut to the encoder (no LLM call). Build (R3).

3.3 Reranking

Section titled “3.3 Reranking”
  • Cross-encoders. Inga already reranks the 32 closest chunks with any loaded reranker (/v1/rerank; bge-reranker-v2-m3, Qwen3-Reranker). Anthropic’s 67 % needs a reranker; Open WebUI, Khoj, RAGFlow, AnythingLLM rerank. Cost grows with N: reported timings for bge-reranker-v2-m3 vary from ~240 ms per query to 80–120 ms for 100 candidates on a mid-range GPU (MemReranker, a vendor estimate: secondary, hardware unclear). Build (R3): rerank only the fused top N (default 32, rerank_n per request and in inga.toml), skip it when the fused list is already confident (the top hit far above the second, measured).
  • LLM listwise rerank (RankGPT). Competitive with cross-encoders on TREC-DL and BEIR but “much slower than a cross-encoder” on 100 candidates; sliding windows of 20, stride 10 (RankLLM). An LLM call per query. Experiment (§12).

3.4 Graphs

Section titled “3.4 Graphs”
  • GraphRAG (Microsoft): LLM-extracted entities and relations, community summaries, “global” questions over the whole corpus. Indexing is the cost: entity extraction is most of it; LazyGraphRAG defers the LLM to query time and claims indexing at 0.1 % of GraphRAG’s (Microsoft Research). Experiment (§12): a local model extracting entities from 10k files is days of compute, and Inga’s two cases already have explicit graphs (links, symbols).
  • LightRAG (Guo et al., EMNLP Findings 2025): a lighter entity graph, dual-level (entity / theme) retrieval and incremental updates. Experiment, same reason.
  • Wiki-link graphs. [[Page]], [[Page#Section|alias]], relative links and backlinks: free, exact, already written by the author (or the LLM maintaining the wiki). Karpathy’s “LLM wiki” pattern (April 2026; summary, secondary) relies on the LLM following its own index pages and links. Build (R6): a link table, one-hop expansion of the best hits, reranked with the rest.

3.5 Agentic retrieval

Section titled “3.5 Agentic retrieval”

The model calls search tools in a loop instead of receiving fixed excerpts. Coding tools moved there: Claude Code uses Grep, Glob and Read with no embedding index; its lead said an early vector-RAG version was beaten by agentic search (report, secondary); Continue deprecated @Codebase for agent exploration; Cody’s enterprise embeddings were replaced by Sourcegraph search in 5.3 (survey §2). But Cursor measured the opposite on its own benchmark: semantic search with grep gave agents 12.5 % higher answer accuracy on average (6.5–23.5 % by model) and more retained code on repositories of 1,000+ files (Cursor, November 2025). The lesson: an index is a tool the agent calls, beside grep, not a replacement. Open WebUI’s knowledge tools do the same for documents. Build (R9): search_documents, read_document, list_documents, follow_links as tools (and over Inga’s MCP server), the workspace’s search_files (grep) beside them.

3.6 Code

Section titled “3.6 Code”
  • AST chunking. cAST (Zhang et al., EMNLP Findings 2025): split oversized syntax nodes, merge small siblings under a size limit: +4.3 Recall@5 on RepoEval, +2.67 Pass@1 on SWE-bench over line chunks. Inga cannot link tree-sitter (C); the same split-and-merge over a heuristic item finder (indentation, braces, a table of declaration starts per language: the survey §4.1) gets most of it. Build (R5).
  • Symbol graphs. aider’s repo map: tree-sitter definitions and references, a graph ranked by personalised PageRank, cut to a token budget (1,024 by default) (pattern write-up, secondary); tokensave: a symbol graph of 50+ languages over MCP, no embeddings (survey §2). Build (R5) only a lexical identifier table (definitions found by the item finder, references by identifier match: approximate, no parser); the precise graph stays tokensave’s, documented as the MCP companion.
  • Identifiers in BM25: snake_case and camelCase split, the whole identifier kept too. Build (R3).

3.7 Answering

Section titled “3.7 Answering”
  • Citations with exact anchors: page (PDF), section anchor (Markdown, DOCX headings), line range (code, text), shown and opened by the web UI. Build (R2, R10).
  • Attribution check. ALCE (Gao et al., EMNLP 2023) scores citation recall (do the cited passages entail the sentence?) and precision (is each needed?) with an NLI model; even the best models lacked full support 50 % of the time on ELI5. Inga can check each cited sentence against its passage with the loaded reranker as a cheap entailment proxy and mark unsupported sentences. Build (R10) as an option; its value measured by §10’s faithfulness.

3.8 Evaluation

Section titled “3.8 Evaluation”
  • RAGAS: faithfulness (claims supported by the context), answer relevancy, context precision (useful chunks ranked high), context recall (against a reference answer); LLM-judged (definitions).
  • IR metrics on a labelled set: recall@k, MRR, nDCG@10 (BEIR style); they need no LLM and are stable: the main gate for every phase.
  • Task benchmarks for code: Cursor Context Bench (questions with known answers in codebases), SWE-bench (Pass@1); Inga’s own is §10.2.

3.9 Operations

Section titled “3.9 Operations”
  • Embedding models. Inga runs nomic-embed-text v1.5 (English) and BGE-M3 (multilingual, 100+ languages, 8,192 tokens). Newer: Qwen3-Embedding (0.6B / 4B / 8B, MMTEB mean 64.3 / 69.5 / 70.6 (secondary), report) and EmbeddingGemma (308M, MMTEB 69.7 at 768 dimensions, paper); the embeddings part 2 spec plans EmbeddingGemma. No Italian-specific ranking was found: Inga measures it (§10.1).
  • Quantized vectors. Binary (one bit per dimension, 32× smaller, Hamming distance) and int8 with rescoring of the top candidates by full-precision vectors: a 2026 benchmark over 33 models put the nDCG@10 loss at ~6.5 points for binary and ~2 for int8 alone, and ~0.9 and ~0.1 after rescoring the top 100 (HAKARI-Bench); sentence-transformers reports “up to ~96 %” kept for binary + rescoring (docs). Build (R3).
  • ANN on disk. DiskANN: compressed vectors in RAM guide a graph search; the full vectors on SSD rerank; a billion points with 64 GB of RAM, under 3 ms mean latency at 95 % 1-recall@1 on 16 cores (Subramanya et al., NeurIPS 2019). The pattern of §8.

5.4 Chunking (R2, R5)

Section titled “5.4 Chunking (R2, R5)”

One chunker per kind, all producing Chunk { text, page, heading_path, anchor, lines, parent, kind, meta }, sized in encoder tokens (today’s 500, 64 overlap for prose):

  • Prose (PDF, DOCX, HTML, text): paragraphs as today, the heading path (Report › 3 Costs › 3.2 Energy) instead of the last heading, a new chunk at every heading of level ≤ 2.
  • Markdown / wiki: by section, recursing to the next heading level when too long (Khoj), tiny sections merged with the next (Open WebUI’s minimum); front matter (title, tags, aliases, date) parsed into meta, not embedded as text; links recorded for the graph (R6); anchors as GitHub and Obsidian make them.
  • Code (R5): split-and-merge over top-level items found by indentation, braces and a per-language table of declaration starts (cAST’s algorithm over a heuristic tree); the heading path is path › impl Store › fn search; line ranges kept; generated and minified files skipped (one line over 1,000 characters, @generated).
  • Parent/child: every chunk records its section (parent); a section small enough (≤ 1,500 tokens) is the unit given to the model when two or more of its chunks are hits.
  • What is embedded: heading path + context prefix (R7) + text; what BM25 indexes: the same plus the file path and the identifiers split.
  • A chunker version in the index: a change re-chunks (and re-embeds) only what changed in output, by chunk content hash (§7.2).

5.5 Enrichment (R7), at index time

Section titled “5.5 Enrichment (R7), at index time”

Computed once per changed chunk or file, in idle time (§7.4), by a local chat model the user picks ([docs] enrich_model, default: the smallest loaded or configured chat model; off when none):

  1. Context prefix per chunk, Anthropic’s prompt adapted: the document (or, when it is longer than the model’s context, its section plus its summary) and the chunk; 50–100 tokens. The prompt’s document part is the same for every chunk of a file, so Inga’s prefix cache makes each extra chunk cost only its own tokens.
  2. Summary per file and per top-level section (≤ 120 tokens), embedded as its own vector (doc-level search, §5.7) and shown in inga docs search results.
  3. A chunk is searchable before it is enriched (plain embedding first); enrichment replaces its vector and BM25 entry when done. The status reports both counts.

When a file changes, only the chunks whose text changed get a new prefix; the others keep theirs and are marked stale, refreshed in idle time (a prefix depends on the whole document, but a small edit rarely changes it).

5.6 Index (R3, R6, R8)

Section titled “5.6 Index (R3, R6, R8)”

Per collection and encoder, in ~/.cache/inga/store/rag/COLLECTION/ (the JSON-lines store keeps the memory and the file list):

  • Vectors: append-only segments: bin (1 bit/dim), f16 (full precision for rescoring) and, optionally, i8 (§8); a tombstone bitmap; ids are dense u32.
  • BM25: segments (Lucene-like): a term dictionary (sorted, front-coded) and postings (doc-id deltas, varint, term frequencies); per segment stats; a new segment per sync, merged in the background; deletions are tombstones until a merge. Analyzer: Unicode word split, lowercase, ASCII folding, identifiers split (embed_missing → embed, missing, embed_missing), a light stemmer per language (English, Italian) behind the analyzer version, no stop-word list (BM25’s IDF handles them).
  • Graph (R6, R5): an edge table (from_chunk_or_file, to_file, to_anchor, kind) with kinds link, backlink (derived), defines, references (code identifiers).
  • Chunk store (T3): text, heading path, anchor, lines, meta; one file per segment, read by offset.
  • ANN graph (R8): HNSW over the binary or int8 vectors, only when the exact scan misses the latency target (§8.3).

5.7 Retrieval (R3, R6, R7)

Section titled “5.7 Retrieval (R3, R6, R7)”
  1. Query: the last user message (plus the previous user turn when short), cut to the encoder; its vector from a query embedding cache (LRU of 1,024, keyed by text and encoder); its BM25 terms through the same analyzer.
  2. Filters (where: path globs, tags, kind, date) to a bitmap.
  3. Dense: Hamming scan over the binary vectors (or HNSW, R8) → top 200 → rescore with f16 → top 100.
  4. BM25: top 100 (term-at-a-time with a heap; WAND later if needed).
  5. Two-stage (R7): the file summaries’ vectors pick the top 20 files; their chunks get a small RRF bonus (not a hard filter, so a good chunk in another file still wins).
  6. Graph (R6): the files linked from and to the top 10 hits add their best chunk for this query (one hop, at most 20 candidates).
  7. Fusion: RRF (k = 60) of dense, BM25, graph and doc-level lists; weights per kind tuned by the eval, never by hand.
  8. Rerank the top N (default 32) with the loaded reranker; skipped when none is loaded (the report says so) or when the fused top is confident.
  9. Optional, per request (R9): rewrite: "multi" (three rewrites by the chat model, fused) or "hyde"; never on by default.

5.8 Context assembly and citations (R2, R10)

Section titled “5.8 Context assembly and citations (R2, R10)”
  • Hits of the same section merged into their parent when two or more (§5.4); neighbours joined when adjacent; ordered by file and position (not score) inside the budget, so the model reads coherent text; the budget is today’s (a share of the context).
  • Each excerpt is numbered and carries its anchor: report.pdf p. 12, wiki/rust/ownership.md#borrowing, src/store.rs:776-845. The answer’s inga_documents report gives each excerpt’s source, anchor, which retrievers found it (dense, bm25, graph, doc), its fused rank and rerank score.
  • The web UI opens a citation at the page, the anchor or the lines (a viewer for text and code with the lines highlighted; PDFs at the page).
  • Attribution check (R10, option check_citations): after the answer, each sentence with a citation is scored against its cited passage by the reranker; sentences below a threshold are marked “not supported by [n]” in the report and the UI.

Section titled “7.1 Jobs and progress (R1)”

A sync is a server-side job (POST /api/inga/documents/sync → {"job"}); its events over SSE (GET /api/inga/documents/jobs/{id}): scan (found, to do, unchanged), file (name, n of m), chunks (embedded of total), enrich (R7: enriched of total), error (file, reason), done (added, changed, removed, failed, seconds). The web UI shows a bar per collection (42 % · 312 of 1,204 files · 5,210 of 12,400 chunks · reading src/store.rs · ~6 min left), errors under it, Cancel. The ETA from the chunks per second measured so far. A failed file is reported and skipped.

7.2 Incremental updates in place (R1, R3)

Section titled “7.2 Incremental updates in place (R1, R3)”
  • Chunk content hash (SHA-256 of chunker version + text + prefix): an unchanged chunk keeps its vector, BM25 postings and enrichment; only new hashes are embedded.
  • Vectors: removed chunks become tombstones; new ones are appended to the open segment; a segment whose tombstones pass 25 % is compacted in the background.
  • BM25: a new small segment per sync; deletes as tombstones; segments merged by size tiers; global statistics (N, average length) kept incrementally.
  • Graph: the edges of a changed file are replaced as a unit.
  • HNSW (R8): inserts in place; deletions are tombstones (skipped in results, still used for navigation); a rebuild when tombstones pass 20 % or after a chunker or encoder change, in the background, the old graph serving until the new one swaps in.
  • Every write goes to new files then an atomic rename of the segment list: a crash leaves the last good index.

7.3 Readers never wait

Section titled “7.3 Readers never wait”

The searchable state is an immutable snapshot (Arc of the segment list); a sync builds new segments and swaps the Arc. A query never takes a lock held by ingestion.

7.4 CPU and GPU contention with the chat model

Section titled “7.4 CPU and GPU contention with the chat model”
  • Ingestion runs on its own thread pool, at low OS priority (nice 10 on Unix, THREAD_PRIORITY_BELOW_NORMAL on Windows), sized to half the cores by default ([docs] ingest_threads).
  • Embedding batches yield: while a chat request is in prefill or decode on the same device, the ingestion job pauses between batches (a shared “busy” counter of the scheduler); on the GPU it uses the batched embeddings of the high-throughput item (H4) only when the queue is idle.
  • Enrichment (LLM calls) runs only when no chat request is waiting, and is the first thing paused; with --models-max 1 it is skipped while another model is in use, never forcing a model swap.
  • The query path has priority on everything: the query embedding jumps the embedding queue; the reranker runs on the request’s thread.

8. Memory tiers: RAM below a budget, the disk above it

Section titled “8. Memory tiers: RAM below a budget, the disk above it”

8.1 Tiers

Section titled “8.1 Tiers”
Tier Holds Where Read when
T1 binary vectors, ANN graph, BM25 dictionary + hot postings, doc vectors always RAM every query
T2 f16 vectors (and i8 if kept) RAM under budget, else mmap rescoring top ~100
T3 chunk text, meta, summaries, graph edges, cold postings disk (mmap) final top-k only

Per chunk at 768 dimensions (BGE-M3’s 1,024: ×1.33 for vectors): binary 96 B, int8 768 B, f16 1,536 B; HNSW graph at M = 16 about 128–160 B (“roughly M * 8-10 bytes per stored element”, hnswlib); BM25 postings ~1 KB compressed for a 500-token chunk (~250 distinct terms × 3–4 B, estimate); chunk text and meta ~2.5 KB. So T1 is ~0.35 KB per chunk (binary + graph + dictionary share), T2 1.5 KB, T3 ~3.5 KB.

mmap makes the OS page cache the “RAM if it fits” layer for free; the budget decides what Inga pins or prefetches (madvise(WILLNEED) / reading once at open, mlock never) versus what it leaves to the OS.

8.2 The budget

Section titled “8.2 The budget”

inga.toml: [docs] memory_budget = "auto" | "512M" | "4G". auto is a fraction of the RAM free at start (25 %), minus what the loaded and configured chat models need (the fit planner already knows it), never under 64 MiB. The rule:

  • index ≤ budget → (a) everything in RAM (all tiers read in at open);
  • index > budget → (b) T1 in RAM, T2 and T3 mmapped, T2 prefetched while it fits the rest of the budget;
  • T1 alone > budget → (c) everything mmapped, with a warning in inga docs status (“the index needs X MB of RAM to be fast; budget Y”).

Disk kind matters: on a rotating disk (detected from /sys/block/*/queue/rotational on Linux, IOCTL_STORAGE_QUERY_PROPERTY on Windows, or measured: a random 4 KiB read over 5 ms) case (b) rescores with int8 kept in RAM instead of f16 on disk (HAKARI-Bench: ~0.1 nDCG point lost after int8 rescoring) and keeps BM25 postings in RAM if they fit.

8.3 Trade-offs (estimates and literature; to be measured by inga eval rag)

Section titled “8.3 Trade-offs (estimates and literature; to be measured by inga eval rag)”

Memory, 768 dimensions, at 10k / 100k / 1M chunks:

Configuration RAM 10k RAM 100k RAM 1M Disk
(a) all in RAM ~55 MB ~550 MB ~5.4 GB same
(b) T1 in RAM ~4 MB ~35 MB ~350 MB ~5 KB/chunk
(b) on HDD, + i8 ~11 MB ~110 MB ~1.1 GB ~5 KB/chunk
(c) all on disk ~1 MB ~5 MB ~50 MB ~5 KB/chunk

Query latency before rerank, 100k chunks, one query, exact binary scan (no HNSW):

Configuration NVMe warm NVMe cold HDD warm HDD cold
(a) all in RAM ~3–8 ms n/a ~3–8 ms n/a
(b) T1 in RAM ~3–8 ms ~5–10 ms ~3–8 ms ~0.3–1 s
(b) on HDD, + i8 n/a n/a ~3–8 ms ~0.1–0.2 s
(c) all on disk ~3–8 ms ~20–50 ms ~3–8 ms several s

Where the numbers come from: the binary scan of 100k × 96 B (9.6 MB) is about 1 ms at memory bandwidth; BM25 for a short query a few ms; rescoring reads 100 × 1.5 KB = 150 KB: microseconds in RAM, ~0.5–1 ms of parallel 4 KiB reads on NVMe, ~100 random reads × ~10 ms on an HDD (sorted by offset, 0.3–1 s); the final top-k text (8–20 chunks) adds the same per read. “Cold” is the first query after a reboot. At 1M chunks the binary scan is ~10 ms: that is where HNSW (R8) may pay, which is why R8 is gated by the eval.

Recall: (a) and (b) are identical (same candidates, same f16 rescoring); binary + f16 rescoring of the top 100 loses ~0.9 nDCG point against f32 exact (HAKARI-Bench), int8 + rescoring ~0.1; HNSW adds its own miss rate (tuned by ef). (c) only changes latency. Default: (a) under the budget, (b) above it.

The two reference corpora, estimated (to be replaced by inga eval rag’s real counts): Inga’s repository, ~20 MB of code and Markdown, is ~10–12k chunks, ~60 MB in (a); the maintainer’s wiki, 12 MB of pages cut into sections and ~21,000 timeline bullets plus 18 MB of raw sources, is ~40–50k chunks, ~250 MB in (a), ~18 MB of T1 in (b). Both sit well under 100k chunks: the exact binary scan with f16 rescoring serves them, and HNSW (R8) is for larger collections only.

Whatever tier Inga picks, it says so with the reason, as every placement decision (AGENTS.md, “be informative”): inga docs status, the start-up line of inga serve, GET /api/inga/documents (tier, ram, budget, disk: "ssd" | "hdd") and the Documents page (“Wiki: 41,210 chunks · 18 MB in RAM, f16 rescoring from the SSD · budget 512 MB”).

10.1 inga eval rag

Section titled “10.1 inga eval rag”

inga eval rag --corpus DIR --questions FILE [--config FILE] [--json] indexes a corpus folder into a throw-away collection (or reuses one by name) and runs a questions file against it. Corpus and questions can live anywhere: the public sets ship in the repository, private ones (the maintainer’s wiki) stay outside it and are never committed. A questions file is TOML:

An answer counts as a hit when a retrieved chunk overlaps the expected line range, holds the symbol’s definition (the item chunker’s names, R5) or carries the anchor.

Set Corpus Questions Where
inga-code Inga’s own checkout 50–100 tests/rag/inga-code.toml
wiki-synth a synthetic wiki, same shape ~40 tests/rag/wiki-synth/
docs Inga’s docs/ as a wiki ~60 tests/rag/inga-docs.toml
pdf public-domain PDFs, DOCX ~40 fetched by hash
beir-scifact BEIR SciFact its own fetched by hash
wiki-private the maintainer’s wiki ~100 outside the repository
  • inga-code, the code reference (the maintainer’s choice): questions about Inga’s own code with the ground truth as a path plus a symbol or line range, e.g. “where are bench’s options parsed?” → src/cli.rs::parse_bench; “which function logs a model loaded?” → crates/inga-server/src/requests.rs::model_changes; “where is the OPFS read-only handle opened?” → web/worker.js. A mix of exact identifiers, concepts (“how does the GPU memory planner decide layers?”), cross-file questions and questions in Italian. Symbols are preferred to line ranges because they survive edits: CI runs the set against the checkout itself, and a test checks that every expected symbol still exists (a renamed function fails that test, not the eval); commit pins the line-range labels, and inga eval rag --relabel proposes new ranges for moved symbols for a person to review.
  • wiki-synth: a few hundred generated pages with front matter, timelines of dated bullets with source markers, wikilinks and Italian text (made by a script in tools/, deterministic, no real news), for CI: filters, dates, links, Italian.
  • wiki-private: the real target; inga eval rag --corpus ~/wiki --questions ~/wiki-eval.toml, results reported in pull requests as numbers only.
  • SciFact checks the pipeline against published BM25 and dense numbers.
  • The memory tiers (§8) are validated on inga-code: Inga’s repository is ~650 .rs files (16 MB), the web UI’s files and ~300 Markdown pages (4.5 MB): roughly 5–6M tokens, ~10–12k chunks (an estimate); inga eval rag prints the real chunk count and the bytes per tier after indexing, which replace §8.3’s estimates.

Measured: recall@5/10/20, MRR@10, nDCG@10 (retrieval, per set and per question kind); query latency p50/p95 split into embed, dense, BM25, fusion, rerank; RAM of the index; answer faithfulness and citation precision/recall (ALCE-style, judged by a configured local model, reported but not a gate: judges drift); first-pass ingestion time reported separately and only for the first pass. The output is a table plus JSON; CI runs inga-code and wiki-synth (small, a few minutes on CPU with a small encoder) for regressions; the full sets run on the maintainer’s runner.

The rule: a phase ships when its eval shows no regression on any set over 1 point of recall@10 and no p95 over the targets of §1; a technique stays only if it gains on the sets it is meant for. Every result goes into docs/experiments.md. Questions are written with the maintainer, some proposed by a model and reviewed; half of each set is held out while tuning.

13. Risks

Section titled “13. Risks”
  • Enrichment cost on a CPU: a context prefix per chunk with a 4B model over 10k chunks is hours (estimate; the prefix cache cuts the document part). Mitigation: idle time only, searchable before enriched, off without a model, measured gain required.
  • Latency targets on weak machines: the query embedding on an old CPU may exceed 30 ms; the cache helps repeated queries only. Mitigation: a small encoder suggested by inga docs status when p95 is high.
  • Heuristic code chunker misplaces boundaries on unusual formatting: costs a little recall, not correctness; measured on inga-code.
  • Eval sets written by the people who build the system overfit it. Mitigation: SciFact as an outside check, questions proposed by a model and reviewed, a held-out half not looked at while tuning.
  • Index format churn: versioned segments; an unknown version is rebuilt, never misread.
  • Paths from the API: limited to [docs] roots; symlinks out of a root not followed.
  • Contention: ingestion pausing for chat may never finish on a busy server; the status says “paused for chat” and --full-speed exists for the first pass.
  • Secondary sources: several numbers here are from summaries (marked); the eval replaces them with Inga’s own.

As built: R1 and R4’s harness (2026-10-17)

Section titled “As built: R1 and R4’s harness (2026-10-17)”

R1, folders kept in sync (crates/inga-engine/src/rag/, crates/inga-server/src/docsync.rs, src/commands/docs.rs), on the collections of 0.26.5 rather than a new store:

  • A folder is an entry of the store’s collection document-sources (its path; in meta its collection, include and exclude globs, every, watch, last sync and the binary files it holds, by size and time). Its files are the collection’s files, named by their path relative to the folder, whose meta adds the folder’s id, mtime (nanoseconds) and sha256: that is the manifest. Uploads are files without a folder.
  • The scan (rag/scan.rs, rag/glob.rs) reads the folders’ entries only: globs and ignore files with .gitignore’s rules (anchored and unanchored patterns, **, classes, !, folders only with a trailing /, the last match wins, an excluded folder is not entered), .gitignore and .ingaignore per folder, the default excludes of §5.1 (an include glob under one takes it back), a list of binary extensions never opened, files above 64 MiB skipped and reported, symbolic links not followed (so nothing outside the folder is read), at most 200,000 files per folder.
  • A sync (rag/sync.rs): unchanged size and time, not opened; a changed time with the same SHA-256, only the manifest updated; new and changed files read by inga-docs, chunked and embedded as uploads are, the old version removed once the new one is embedded; a file that is binary or has no text remembered and skipped until it changes; files gone removed with their chunks. (Part 2 below: a changed file’s unchanged chunks keep their vectors.)
  • Jobs (docsync.rs): one worker thread runs them one at a time; a job per collection (all its folders, one progress bar over the bytes to read); events kept in the job and replayed to each SSE client; between files the sync waits while the server’s generation counter (/metrics’ requests in flight) is above zero and says paused. The ticker looks every 5 seconds: a periodic folder is queued when every has passed since its last sync; a watched folder is planned from sizes and times and queued once the same change is seen twice in a row. (OS priority: R1’s low-priority part below.)
  • The API adds folders only under --docs-root (docs.roots); the command line adds any folder (it is the local user). Both write the same store; the server reads it again when it changes. (Part 2 below: a CLI sync and a server sync of the same folder wait for each other.)

R4, the harness (rag/eval.rs, inga eval rag in src/commands/docs.rs): a questions file (TOML: corpus, commit, include, exclude, [[q]] with text, kind, expect) indexed into a throw-away store by R1’s sync (or --collection used as it is), each question asked through fit_query and search_collections with the retrieval chats use today (dense, exact, no reranker), 100 chunks grouped by file; recall@5/10/20, MRR@10, nDCG@10 (binary relevance) per kind and overall, the search’s p50 / p95 (the question’s embedding included, the first search, which builds the index, not timed). Answers are matched by file: the chunks carry no symbols, lines or anchors yet. tests/rag/inga-code.toml (22 questions, model-proposed, to be reviewed with the maintainer) and tests/rag/wiki-synth/ (8 hand-written pages, 12 questions, every name invented) ship; tests/cli.rs checks that every expected file and symbol exists and runs the harness on the synthetic wiki with a tiny random encoder (its scores mean nothing).

First measure (2026-10-17, inga eval rag --questions tests/rag/inga-code.toml): all-MiniLM-L6-v2 (sentence-transformers’ weights, from Chroma’s ONNX export converted back to a safetensors folder; Inga’s embeddings matched ONNX Runtime’s at cosine 1.000000 on three sentences), mean pooling, chunks of up to 500 tokens (the model’s max_position_embeddings is 512, while sentence-transformers truncates it at 256), dense exact search, no reranker; the corpus is this branch’s src/**/*.rs and crates/*/src/**/*.rs: 452 files, 10,795 chunks, 11.6 MiB. R1, part 2 (2026-10-18; rag/sync.rs, collections.rs, store.rs, docsync.rs, src/commands/docs.rs):

  • Chunks that did not change keep their vectors (§7.2, simplified): when a file is read again (a folder’s changed file, --full, an upload of the same name), its new chunks are matched with the old file’s by the SHA-256 of the text the vector was made of (heading and text, Store::reuse_vectors); a match embedded by the same encoder (Engine::kv_key) gets the old vector, the others are embedded. The hash is computed when needed, not stored: identical text gives the same vector whatever the chunker’s version, so no version is part of it. Another encoder reuses nothing. The report says reused beside chunks (embedded). BM25 is unchanged (a chunk added is indexed). Not built: tombstones and segments (the store’s file stays one append-only log).
  • Waiting for the chat between chunks: the embedding loop calls the sync’s control before each chunk (Store::embed_missing_paced), so a long PDF no longer holds the CPU for minutes while a chat waits; Cancel is heard there too, and the half-added file is removed (the old version stays).
  • A CLI sync and a server sync kept apart: a sync takes locks/folder-ID.lock in the store’s folder with File::try_lock (an OS lock released when the process ends, so no stale lock); folder-ID.who says who holds it (inga serve, pid N, inga docs, pid N: Windows keeps a locked file’s bytes from other readers). The second process sends waiting with the holder once and polls every 250 ms (Cancel heard), then plans again, so it does only what is left. inga docs rm removes both files.
  • inga docs search NAME[,NAME] QUESTION [--k N] [--explain] [--json]: the chats’ search (SearchOpts::configured, docs.reranker loaded when set), the passages with file, heading, page and a snippet; --explain adds each passage’s dense and BM25 rank (Passage::dense_rank, bm25_rank), cosine, rerank score and the steps’ times. --where is not built (chunks have no tags yet).
  • inga docs add NAME FILE...: the files read and added as uploads (add_document); the folder options are refused with files, and a folder among files too.
  • Not built yet: the GPU’s batched embeddings when idle, the folder’s globs, period and watch in the web UI (R-UX).

R1, low priority (2026-10-18; priority.rs, inga-cpu’s pool.rs, docsync.rs, src/commands/docs.rs; the unsafe calls approved by the maintainer on 2026-10-18):

  • Not its own pool, the encoder’s: the embedding runs on the encoder’s CPU pool, so the pool’s threads are the ones lowered. inga_engine::priority::lower_current_thread lowers the calling thread: on Linux setpriority(PRIO_PROCESS, 0, 10) (on Linux the calling thread only; nice 10, as §7.4 says; a thread already above it is left) and ioprio_set to the lowest best-effort level (7) for its reads, on x86-64 and ARM64 (the system call has no C wrapper and its number differs per processor); on macOS pthread_set_qos_class_self_np(QOS_CLASS_BACKGROUND); on Windows SetThreadPriority(GetCurrentThread(), THREAD_MODE_BACKGROUND_BEGIN) (CPU, disk and memory; stronger than §7.4’s THREAD_PRIORITY_BELOW_NORMAL, and the one that also lowers the disk); elsewhere nothing. Not SCHED_IDLE nor the idle disk class: they give no CPU or disk at all while anything else runs, so a sync on a busy computer would never end, where nice 10 still gets a share. lower_pool runs it once on every thread of a pool (ThreadPool::on_every_thread) and the caller’s. A failure is never an error: the sync goes on at normal priority and says why.
  • [docs] ingest_threads (default half the logical CPUs, at least 1; --set docs.ingest_threads=N): inga docs sync and docs add load their encoder with that many threads and lower them all; --full-speed loads it as every command does (cpu.threads) at normal priority. Both say the mode once on stderr and on each folder’s report line (low priority (nice 10, disk best-effort 7), 4 threads, full speed, 8 threads).
  • inga serve: its encoder is shared with the searches, so a sync lowers that encoder’s threads and the sync worker’s, and caps the pool’s jobs at ingest_threads while the job runs (ThreadPool::cap); the job says it in a mode event and in progress.mode, and logs once when the priority could not be lowered. The lowered threads stay so while the model is loaded: an ordinary user cannot raise a thread’s nice value again on Linux (RLIMIT_NICE), and macOS and Windows are kept the same for simplicity. It only matters while the computer is busy with something else: a search then embeds its question more slowly. The server has no full speed.
  • Measured: nothing yet. The tests check that the call returns on every OS, and on Linux that each thread’s nice value reads back as 10 or more. The macOS and Windows code was written on Linux and not run there by its author; CI builds and runs those tests on macOS and Windows (the call returns), and nothing reads the priority back there.

As built: R3, hybrid search (2026-10-17)

Section titled “As built: R3, hybrid search (2026-10-17)”

What R3 built, on R1’s store rather than the segments of §5.6 (crates/inga-engine/src/rag/: analyze.rs, bm25.rs, search.rs; the store’s indexes in store.rs):

  • The analyzer (§5.6, §11.1; one function for chunks and questions, version 1): runs of letters and digits joined by _ - . / : are one run; a run gives itself whole, its parts between / : . that hold more than one word, and its words (camelCase split too), so store.embed_missing gives store.embed_missing, embed_missing, stor, embed, missing, and dates (2025-03-14) and codes (MRV-3) stay exact tokens; apostrophes split (l'azienda); words are lowercased and their accents folded; Italian and English stop words and single letters are dropped (unlike §5.6, which had none: the questions’ function words matched every chunk of a hub page), except acronyms (two or more capitals: PUE, CI), kept as they are; words without digits are stemmed for both languages at once (Harman’s English S-stemmer, then Savoy’s light Italian stemmer on words of five letters or more, as Lucene’s ItalianLightStemmer), so no language detection is needed (the per-collection language of §11.1 is not built). Elisions are split; accents are folded for matching only (the chunks keep them).
  • BM25F (Robertson and Zaragoza, 2009): five fields per chunk, its text (weight 1, b 0.75), its heading (2, 0.5), its file’s title (front matter’s title, else the first # heading: 3, 0.5), path (2, 0.5) and front matter’s values (1.5, 0.5); k1 1.2; IDF over the live chunks. The index is in memory, per collection, built at the collection’s first lexical search (10,696 chunks of Inga’s sources: 1.1 s on the shared container, 13.5 MB in memory) and kept in step by the store: a chunk added is indexed, a chunk removed is a tombstone, compacted once tombstones pass 64 and a quarter of the chunks. When another process changes the store’s file the store reads it again and the index is built again at the next search. Not built: segments on disk, a background merge, WAND (a term-at-a-time scan of a short question’s postings takes under a millisecond at 10k chunks).
  • Dense: unchanged (exact, f32), but its index is kept per collection and made again only when that collection changed (a generation per collection), where before any change of the store (a memory added) dropped it. Not built: binary vectors with f16 rescoring, the memory tiers of §8, docs.memory_budget.
  • Hub pages: each retriever’s scores are lowered by hub_penalty · σ · √(2 ln n) (n the file’s chunks, σ the spread of that list’s scores: the expected best of n draws stands about σ√(2 ln n) above their mean), then each list keeps at most per_file chunks of a file, and the fused list too. Pages that only list others are better excluded with the folder’s globs (documented).
  • Fusion: Σ w / (k + rank) with k = 60 and w = 1 for dense, docs.bm25_weight (2) for BM25; a passage carries the retrievers that found it, its fused rank and its cosine (computed for the chunks BM25 alone found too).
  • Rerank: the first rerank_top (32) fused chunks, each as file name, heading, text, scored by Engine::rerank; replace (default) or fuse (RRF of the two orders). The server’s reranker is docs.reranker (loaded when first needed), else a loaded one; ground no longer reranks passages the search reranked, and gives the passages in their search order, taken in turn with the attached files’ chunks.
  • Query cache: the last 1,024 questions’ unit vectors, by encoder, pooling and text.
  • Settings: [docs] search, rrf_k, bm25_weight, candidates, per_file, hub_penalty, reranker, rerank_top, rerank_mode (process-wide values of inga_core::tunables, so --set works for every command); inga eval rag --mode dense|bm25|hybrid|hybrid+rerank [--rerank-model M], with each step’s median time.
  • Folders remember their embedding model (embed_model and the encoder’s key in the folder’s meta): inga docs sync without --embed-model uses it, and a sync with nothing to read loads no model (it failed with “no embedding model” before); another model given is said, with the --full command that embeds everything again.

As built: R2, part 1 — chunks with structure (2026-10-18)

Section titled “As built: R2, part 1 — chunks with structure (2026-10-18)”

What R2’s first half built (crates/inga-docs/src/chunk.rs, front.rs; crates/inga-engine/src/rag/filter.rs, search.rs, read.rs, sync.rs, collections.rs); the Models page’s RAG roles (§9.5) are part 2, not built:

  • Chunker version 2 (inga_docs::CHUNKER_VERSION, kept in each file’s meta as chunker; a file without it is version 1). A page is cut into blocks first: paragraphs (Markdown’s fenced code kept whole and never read for headings), heading lines (# to ######, up to three spaces before; not in plain text and code, where # comment is no heading) and dated bullets. A heading of level 1 or 2 always starts a chunk (a chunk holding only headings joins the next: # Title and ## Intro stay with the intro), a deeper one once the chunk holds a quarter of the maximum (as before). The sizes, the overlap of a short last paragraph (only for a cut made for size) and the split of a too long block (whole lines first, then sentences, words, characters) are R1’s.
  • Each chunk’s structure in its meta: heading is the heading path (Report › 3 Costs › 3.2 Energy, the front matter’s title as its root when the file has no # heading), embedded before the text and indexed as BM25’s heading field; anchor (GitHub’s: lowercase, letters, digits, -, _, spaces as -, a repeated title -1, -2); section (one more at each heading of level 1 or 2: the parent); lines ([a, b], from 1, both included) for text and Markdown files, whose chunks’ text is now those lines as written (blank lines, indentation kept; a piece of a long line is the one exception, its lines [n, n]); date for a dated bullet. HTML and DOCX give their headings as Markdown’s (paths and anchors from them; HTML’s own ids are not read), PDFs only pages (no headings in a text layer).
  • Front matter (inga_docs::front_matter): the YAML wikis write (key: value, [a, b], - item lists; nested mappings skipped; a byte-order mark before it allowed), typed: YYYY-MM-DD (a time after it dropped) and YYYY-MM as dates, numbers, true/false, the rest text. It is no longer chunk text: the file’s meta keeps front (typed JSON), front_text (for a read by lines) and title (front matter’s, else the first # heading), and BM25’s title and front matter fields come from there.
  • Dated bullets (§6.2, 2): a list item (-, *, +, 1., 1)) whose text starts with YYYY-MM-DD, YYYY-MM or YYYY/MM/DD (after **, _, [ or a backtick) is a chunk of its own with its continuation lines, its date in meta.date; the section’s heading joins the first bullet (a chunk of headings alone joins the next). A list item without a date ends it.
  • Filters (where, §5.7 step 2; rag::filter): KEY=VALUE, !=, <, <=, >, >=, separated by ,, ; or and; keys path (a .gitignore glob over the file’s path), kind, title, heading (a part of the path), date (a bullet’s, else the front matter’s) and any front matter key. Values compare typed: dates at the filter’s precision (the field cut to the value’s length, so date<=2026-08 keeps August 31st), numbers as numbers, the rest ignoring case; a list matches by item; a missing key fails all but !=. The kept chunks are a set given to both retrievers (Store::dense_search_where, lexical_search_where) before scoring. Exposed as inga docs search --where (repeatable), where in an inga_documents collection entry (per collection: SearchOpts::filters) and in documents_search; not in the web UI (R-UX).
  • The dates of a question (analyze::question_dates): ISO dates and months, a month’s English or Italian name (or English short name) with its year and maybe a day (December 2025, 14 dicembre 2025, Dec 3, 2025); a year alone is not taken (too wide), nor a month’s name without a year (may, march). In hybrid mode, the dated chunks of those dates (at the coarser precision of the two) make a third list of the RRF (weight 1, date among the retrievers, date_rank in --explain): ordered by BM25 among them, then in the files’ order. Not in dense or bm25 mode (one list, ordered by its own scores). A recency term (“latest”) is R6’s.
  • Sections as parents (§5.4): after the search (and the reranker), two or more passages of one section of a file become that section once, at the best one’s rank, its chunks put together without their overlaps (rag::read::assemble), when it is at most 1,500 tokens of the encoder (PARENT_TOKENS); its place is the section’s heading, its lines the section’s, section: true. SearchOpts::parents turns it off (tests); no [docs] key yet.
  • Citations (documents::Place): Markdown and HTML by anchor (wiki › models/x.md#timeline), text and code by lines (notes › todo.txt:12-40), others by their last heading (§7 Prices), and the page when there are several (p. 4): the excerpts block the model reads, cite, heading, anchor, lines, date and section in inga_documents, inga run’s note, inga docs search and documents_search (whose next document_read asks for the #anchor, the heading, the lines or the page).
  • Reads by the file’s own lines (rag::read): when every chunk of a file knows its lines, the file is put back line by line at those numbers (the front matter at the top, uncovered lines blank, a long line’s pieces joined), so document_read’s lines, documents_grep’s path:line and a citation’s :12-40 are the file’s. Sections are also found by GitHub’s anchor (#32-energy).
  • Re-indexing (§5.4’s chunker version): a folder’s sync plans the files of an older chunker as to read even when their size and time did not change (Plan::rechunk), the scan event says so (rechunk, and a note: “N files are read again: Inga’s chunker changed …”), the file is read and chunked again even when its SHA-256 is the manifest’s, and the report counts it as rechunked; R1 part 2’s vector reuse (same heading and text) keeps what it can: a chunk whose path is one heading and whose text did not change keeps its vector; the others (a nested path, front matter gone, a bullet now alone) are embedded again. inga serve does it at the next periodic or watched sync; for a folder synced by hand, inga docs status says “re-index needed” (and outdated in GET /api/inga/documents, a line on the Documents page, a note before inga docs search); an uploaded file cannot be read again (its bytes are not kept) and is to be added again.
