Document tools: list, search, read and grep the collections a prompt names

Status: built in 0.33.1 (§11, “As built”); proposed for 0.33.0 (decided by the maintainer on 2026-10-17); needs RAG R3’s hybrid search for documents_search. It is the tool half of RAG R9 (RAG §3.5) brought forward from 0.34.0, under the names below (R9 keeps follow_links, which needs R6’s graph, the tools over Inga’s MCP server, and query rewriting / HyDE). It replaces the “read_document as a tool” part of the “Chat with documents and memory, part 2” item. Part of the scheduled agent specs; the collections it works on are those named in the prompt, in its tool mode. Code: a new crates/inga-server/src/doctools.rs (the four tools in the loop of websearch::generate, as memory.rs and workspace.rs), crates/inga-engine/src/collections.rs and crates/inga-engine/src/rag/ (search, the chunks of a file in order, grep), docs/api/inga.yaml.

1. Goal

Section titled “1. Goal”

Give a tool-calling model what coding agents have for files, over the collections the prompt names: see what is there, search it, read a whole document or the span around a hit, and find an exact name or code. Grounding by excerpts (one look, before the answer) misses what the question does not say; an agent looks again.

2. Today

Section titled “2. Today”
  • inga_documents grounds once (documents::apply, crates/inga-server/src/documents.rs): the closest chunks go into the prompt, the model cannot ask for more.
  • The model’s tools in the loop of websearch::generate: web_search, fetch_url, the memory’s, the workspace’s list_files / read_file / search_files / write_file, skills, MCP tools, ask_user. None reads the store.
  • inga_engine::read_document is the reader of uploaded files (PDF, DOCX, HTML, Markdown, text), not a tool; hence the tool’s name document_read below.
  • The store keeps each file’s chunks with their page (search_collections’s Passage: collection, document, page, score, text); R2 adds heading paths, anchors and line ranges.

3. What others do

Section titled “3. What others do”

From their documentation as remembered on 2026-10-17, not re-checked:

  • Gemini CLI: read_file (a path, with an offset and a limit in lines for large files), search_file_content (a regular expression, ripgrep when present), glob, list_directory.
  • opencode: read (offset and limit), grep, glob, list.
  • Claude Code: Read (a path, offset and limit, about 2,000 lines by default), Grep (ripgrep), Glob; its team reported agentic search beating an early vector index (RAG §3.5, a secondary source).
  • Cursor: semantic search with grep, 12.5 % more accurate answers on its own benchmark (Cursor, November 2025, cited in RAG §3.5).
  • Open WebUI: knowledge tools for the model over the attached collections.

The common shape: list, search, read a span, grep. Read is what makes the others useful: a hit is a pointer, the answer is around it.

4. Design

Section titled “4. Design”

Four tools, offered when a prompt names at least one collection in tool mode. Each works only on the named collections (the reference is the permission). Each result is text for the model, numbered as sources ([n], shared with web_search and fetch_url in one answer), and an inga_tool event for the web UI and the log.

4.1 documents_list()

Section titled “4.1 documents_list()”

The named collections: for each, its sources (folders by their last path component, and “uploads”), the number of files and chunks, the last sync and its state (synced, syncing 40 %, failed), and the encoder. No file list (a collection may hold 100,000 files); documents_grep and documents_search find files.

4.2 documents_search(query, collection?, k?)

Section titled “4.2 documents_search(query, collection?, k?)”

R3’s hybrid search (dense and BM25 fused by RRF, the reranker on the top N), over one named collection or all of them (fused across collections as the collections spec §4.3 says). k defaults to 8, at most 20. Each hit: its number, collection › path, its anchor (page, section, lines), a snippet of at most 600 characters, and the file and section (or lines) to pass to document_read.

4.3 document_read(file, section | lines)

Section titled “4.3 document_read(file, section | lines)”
  • file: collection › path as a hit or documents_list shows it (or the path alone when one named collection holds it).
  • section: a heading anchor (#revisione-prezzi, §7) or a page (p. 3); lines: 120-180. Neither: the whole document if it fits the limit, else its outline (headings with their line ranges and pages) and its first part, with “ask for a section or lines”.
  • The text comes from the store, the file’s chunks in order with their overlaps removed: what was indexed is what is read, for uploads and folders alike, and for a file deleted from its folder since the last sync (said). Sections and lines need R2’s heading paths and line ranges; before R2 a document reads by pages.
  • At most 12,000 characters per call (docs.read_chars in inga.toml), cut at a line with “(cut: lines 1-240 of 610; ask for lines 241-…)”.

4.4 documents_grep(text | regex, collection?)

Section titled “4.4 documents_grep(text | regex, collection?)”

Exact matches over the chunks’ text of the named collections: text (literal, case-insensitive unless it has a capital) or regex (fancy-regex, already a dependency, with its backtracking limit; a pattern over 200 characters refused). At most 50 matches, each collection › path:line (or page) and its line cut to 300 characters; “N more matches in M files” past the limit. For names, codes, numbers: what an embedding misses.

4.5 Limits

Section titled “4.5 Limits”
  • At most 8,000 characters per result except document_read (12,000), 3 calls of one tool per round, the loop’s TOOL_ROUNDS per answer (as skills and MCP tools).
  • The tools count against the context like any result; a run near its end is compacted as today (--compact-at).

5. A worked example

Section titled “5. A worked example”

All names, files and contents below are invented. The chat names two collections: contratti (supplier contracts, PDFs) and wiki (the company’s wiki, Markdown).

User: #contratti #wiki Can supplier Rossi raise prices in January? Who follows it here?

The trace, as the web UI shows it under the answer:

Answer: Yes, but within limits. The contract lets Rossi raise prices once a year from 1 January, by no more than the ISTAT inflation of the previous year, and only if it says so in writing at least 60 days before, so by early November [1]. A January increase without that notice, or above the ISTAT figure, is not allowed by §7. Here, Marta Bianchi of Purchasing follows Rossi; the wiki also notes that the contract renews on 31/12/2026 [4][5].

Sources: [1] contratti › fornitori/rossi-forniture-2025.pdf §7 (p. 4) · [4] wiki › fornitori/rossi-forniture.md · [5] wiki › persone/marta-bianchi.md

The search found the clause, document_read gave the whole clause (the snippet stopped before the 60 days), and grep found the person, a name an embedding of the question would not have looked for.

6. Interfaces

Section titled “6. Interfaces”
  • Chat (any API, the web UI, inga run): offered by inga_documents_mode: "tool" with inga_documents, or the prompt’s references in tool mode. A client that defines a tool of the same name runs its own.
  • Scheduled tasks: documents:NAME in tools, tool mode by default.
  • HTTP: no new route; POST /api/inga/documents/search (RAG §9.2) is the same search for programs.
  • Web UI: each call as a tool line (name, arguments, the first line of the result), the hits in Sources grouped by collection, a citation opening the document at its section (R10’s viewer when it lands; the file’s text until then).

7. Security

Section titled “7. Security”
  • Only named collections, checked on the server for every call (§4); a path is matched against the store’s names, never opened on the disk, so ../ reads nothing.
  • A regular expression is bounded (length, backtracking limit, time per call 2 s).
  • Document text is data: it goes to the model as a tool result, never as instructions to Inga, and a #name in it references nothing.

8. Tests

Section titled “8. Tests”
  • Each tool on a store in a temporary home with a tiny encoder: list counts; search returns hits of the named collections only; read by section, page, lines and whole, the cut and its note; grep literal, case, regex, the 50-match limit and the backtracking limit.
  • Permission: a call naming a collection not referenced is refused; a path with .. is “no such file”.
  • The loop: a synthetic chat model forced (by grammar, as fetch_url_refuses_local_addresses in tests/server.rs) to call search then read; the sources’ numbering shared with web_search.
  • The worked example as a fixture (two tiny collections, the invented texts above): the trace’s three calls return the hits shown.

9. Out of scope

Section titled “9. Out of scope”
  • follow_links (R9, after R6), the tools over MCP (R9, the MCP gateway), rewriting and HyDE (R9).
  • Writing to a collection from a tool.
  • The workspace’s file tools (they read a folder on disk, not the store).

10. Phases and effort

Section titled “10. Phases and effort”

One part, M, after R3: documents_list, documents_grep and document_read can be built before it on today’s store; documents_search waits for R3’s search.

11. As built (0.33.1)

Section titled “11. As built (0.33.1)”
  • Where: the four tools in crates/inga-server/src/doctools.rs (tool_defs, run, shared with inga run; wanted and run_tool for the server), run in the loop of websearch::generate like the workspace’s tools (TOOL_ROUNDS rounds, at most CALLS_PER_ROUND = 3 calls of one tool per round); the files’ text and grep in crates/inga-engine/src/rag/read.rs (file_text, collection_texts, grep, Pattern).
  • When they are offered (doctools::wanted): inga_documents names collections, inga_documents_mode is tool, tool_choice is not none, the client defines no tool of the same names, and the model’s chat template names tools (inga_engine::takes_tools, what the model’s card calls tools). Otherwise tool falls back to context and the answer’s inga_documents says why (documents_mode_asked, documents_mode_note; a scheduled run’s warning); a client with its own tools of those names runs them (neither tools nor excerpts from the server, said in the note). In tool mode no excerpt goes into the prompt; the report is {"mode": "tool", "documents_mode": "tool", "tools": [...], "files": [...]}. Scheduled tasks get them through the same request (run_body), unattended.
  • Reading: a file’s text is its chunks in the store’s order, a chunk’s leading paragraph dropped when it is the previous chunk’s last one (inga_docs::chunk’s overlap). Lines are the lines of that text (a blank line between paragraphs), the same numbers for document_read and documents_grep; until R2 they are not the file’s own line numbers. A section is found among the Markdown headings (by anchor, title, or the start of the title: §7 and 7 find 7 Revisione prezzi) and runs to the next heading of its level; a file without headings (a PDF) gives the first line that starts with the mark and the 60 lines after it. section: "p. 3" and page: 3 read a page. A folder’s file missing from the disk since the last sync is said (a stat of its path; its text is never read from the disk).
  • Numbering: one number per file (collection › path is the source’s url and title, via: "documents" in inga_sources), shared with web_search and fetch_url; the worked example’s two hits of one PDF share a number.
  • Search: rag::search::search over the collection asked or all the named ones (fused by rank), docs.reranker (or a loaded reranker) applied, the server’s embedding model as the encoder (inga run: as its context mode). A hit points to document_read with its heading as section, else its page.
  • List: each folder by its last path component with its files and state (syncing 40 % from the running job, else the last sync’s time, failures or stop), uploads, and the encoder (the folders’ embedding model, else the files’ encoder key).
  • Grep: smart case for text; regex with fancy-regex’s backtracking limit (100,000 steps a line: a line that hits it is counted and left out), 200 characters at most, 2 seconds a call; 50 lines, then “N more matches in M+ files”, the result within 8,000 characters.
  • docs.read_chars (default 12,000) bounds document_read; an over-long document read whole gives its outline (headings or pages, 3,000 characters at most) and its start, cut at a line with the lines to ask for next.
  • Terminal: the server logs each call (inga: documents_search({...}) -> Hits for ..., target documents); inga run prints [documents_search {...}] and the result’s first line on stderr, and the files under the answer with the web’s sources.
  • Tests: rag::read’s unit tests (overlap, sections, pages, pattern bounds), doctools’s on a store with the worked example’s files (permission refusals, .., search, read by section / page / lines / whole, grep literal / case / regex, one number per file, the bounds of read and grep), and tests/server.rs’s document_tools_search_read_and_refuse_in_tool_mode (a synthetic model whose template names tools, forced by grammar to call each tool).
  • Not built: the web UI’s tool lines exist (inga_tool) but its Sources are not grouped by collection and a citation does not open the document at its section (the collections spec’s part 2, R10’s viewer); heading paths, anchors and line ranges of R2; an integration test of the numbering shared with web_search in one answer (the unit tests check the numbering).
