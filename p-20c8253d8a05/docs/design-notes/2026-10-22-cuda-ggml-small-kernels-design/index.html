llama.cpp's CUDA kernels for generation, the rest: the small kernels and the routers

Parts 2 and 3 of 2026-10-22-cuda-ggml-mmvq-design.md (“The parts”), the 0.37.0 roadmap’s “llama.cpp’s CUDA kernels for generation, the rest”: ported as MMQ (2026-10-19-cuda-ggml-mmq-design.md), MMVQ and flash attention (2026-10-22-cuda-ggml-fattn-design.md) were: ggml’s kernels unchanged, compiled to PTX by tools/build-ggml-ptx.sh from llama.cpp b11489, launched as ggml’s host code launches them, Inga’s own kernels kept as the fallback and the default until a GPU measures them.

Why

Section titled “Why”

The Colab A100 runs of 2026-10-19 put the small kernels around a decode step’s products (the norms, RoPE, the activations’ quantization) at about 1.3 ms a token on Qwen3-8B, and Qwen3-30B-A3B generates at 0.21 of llama.cpp’s speed with its routers and their top-k on the CPU: every MoE layer reads the hidden state back, multiplies it by the router, picks the experts, and sends the token back.

What

Section titled “What”

The kernels (kernels/ggml/small.cu)

Section titled “The kernels (kernels/ggml/small.cu)”

One file includes ggml’s norm.cu, rope.cu and topk-moe.cu; the build script compiles it once per architecture (sm_61, sm_75, sm_80) with llama.cpp’s flags (-use_fast_math -extended-lambda, as ggml-cuda/CMakeLists.txt gives every CUDA source: the approximate rsqrtf, powf, sinf, cosf, expf are llama.cpp’s arithmetic) and keeps of the PTX the 30 kernels Inga launches, every other .entry left out and nothing else changed (ptx/ggml/small.smARCH.ptx.z, .visible .entry blocks handled too):

  • rms_norm_f32<256 | 1024, do_multiply = true, do_add = false, do_scale = false>: the RMS norm fused with the multiplication by its weight, 256 threads below 1024 values a row and 1024 from there, as rms_norm_mul_f32_cuda picks.
  • rope_norm and rope_neox<forward = true, has_ff, float, float>: the original and NeoX layouts, with and without frequency factors.
  • topk_moe_cuda<n_experts, has_bias> for the twelve numbers of experts ggml instantiates (1 to 576).

Their launch configuration is ggml’s constants (block sizes, CUDA_ROPE_BLOCK_SIZE, TOPK_MOE_ROWS_PER_BLOCK), so there is no table to print: small.rs writes them as ggml’s host code has them, and its unit tests check each kernel’s parameters (24, 23 and 9, RoPE’s corrections and the top-k’s flags by value) and launch bounds in the PTX. ptx/ggml/SOURCES hashes small.cu too. The existing PTX is unchanged byte for byte (rebuilt with the same nvcc and the same llama.cpp checkout path, which ggml’s asserts embed).

Where they run (src/device/ggml/small.rs, hooks in device.rs)

Section titled “Where they run (src/device/ggml/small.rs, hooks in device.rs)”

Behind debug.cuda_ggml_small (default false); the module is loaded when the GPU opens with the setting on (never while a decode step is recorded as a graph); Gpu::set_ggml_small for tests and comparisons.

  • RMS norm: Gpu::rms_norm (every norm of the layer loop: the blocks’ inputs, the Q/K norms per head, the post-norms) takes ggml’s fused kernel, in place (each thread reads its values before writing them), the weight one row (fastdiv(1) for its row, channel and sample counts). The residual add ggml fuses after a post-norm and its rms_norm_mul_rope (Qwen3’s Q/K norms with RoPE) need the layer loop and the attention to change: not in this step.
  • RoPE: Gpu::rope for up to eight tokens (a decode step, a batched one) takes rope_norm or rope_neox with ggml’s parameters, built by Gpu::rope_table (GgmlRope: the frequency factors uploaded, theta_scale = powf(base, -2 / n_rot) on the host as ggml computes it, YaRN’s attn_factor without the 1 + 0.1 ln(factor) that ggml’s rope_yarn applies itself). ggml reads one int32 position per token, so a Position made with the setting on also holds the positions of eight consecutive tokens, written by set_position (outside any graph, as the hidden state is). Prompts, rope_shift, M-RoPE (sections) and tables or positions made with the setting off keep Inga’s kernel.
  • The activations quantized once: with debug.cuda_mmvq on too, the CUDA device answers GpuOps::quantizes_inputs_once (the layer loop already asks it, for Vulkan): quantize_input records the norm’s output, the first product of llama.cpp’s matrix-vector kernels that reads it quantizes it to block_q8_1 (ggml’s quantize_q8_1, already in the MMVQ modules) and the next ones of the same shape (the attention’s Q, K and V, the output gate; the feed-forward’s gate and up; a decode token’s experts) read it as it is. matvec_input gives what matvec or matmul give bit for bit: the other types, prompts (matmul’s tiles) and ggml’s MMQ choice for a few K-quant tokens on Volta, Orin and Blackwell take their own paths from the same input. The scratch remembers the tokens and width it quantized for (ActScratch::held), reset by every quantize_input and every plain matvec on it.

A mixture’s routers on the GPU (debug.cuda_moe_router)

Section titled “A mixture’s routers on the GPU (debug.cuda_moe_router)”

Its own setting, default false, so that it is measured apart (it changes where the engine computes, not only which kernel runs); it loads the same module.

  • Model::plain_router(l) hands a layer’s router over where plain_experts(l) hands its experts: the weight, DeepSeek V3’s selection bias, the gating (softmax, the softmax of the k chosen logits, sigmoid, sqrt-softplus), the normalization and the scale. Not handed over: routers with a bias (gpt-oss), groups of experts (DeepSeek), Gemma 4’s (it reads its own norm of the residual), hashed routing (DeepSeek V4).
  • GpuAttentionStages::add_experts uploads it with the experts (inga-gpu/src/router.rs, DeviceRouter; expert_bytes counts it when the setting is on) when the device runs its top-k (GpuOps::runs_topk).
  • RemoteAttention::route (default: false, the router stays on the CPU): the CPU’s moe_forward asks the device that runs the layer’s experts first; the device writes the token rows, multiplies them by the router (matvec, or matmul past eight tokens), runs GpuOps::topk_moe and reads back only each token’s k experts and weights, which go to RemoteAttention::experts as before. Out of memory there, the CPU routes.
  • CUDA’s topk_moe is ggml’s topk_moe_cuda (one warp a token, eight tokens a block): the softmax or sigmoid or sqrt-softplus of the logits, the selection on the scores plus the bias, the k best by repeated arg-max (the lower index wins a tie, as on the CPU), ggml’s delayed softmax for the softmax of the chosen logits, the normalization clamped at the CPU’s 6.1e-5, the scale. The numbers of experts ggml instantiates only; a normalized delayed softmax (which ggml asserts against) stays on the CPU.
  • HostOps (the CPU behind GpuOps) runs the CPU’s own top-k, so the layer loop’s router path is tested without a GPU.

This leaves the token’s layer going back to the CPU once per MoE layer (the routes, then the experts’ sum): the hidden state no longer does, nor the router’s product. Keeping the whole layer on the device (ggml’s MUL_MAT_ID products reading the ids on the device) changes the routed experts’ loop that H1 (batched decode) is changing too, and is the next step.

Checks

Section titled “Checks”
  • Without a GPU (cargo test -p inga-cuda, -p inga-gpu): each architecture’s module has the 30 kernels and no other, their parameters and launch bounds as launched; the top-k’s flags for each gating and what it refuses; the positions of a step; tests/router.rs (inga-gpu): Qwen3-MoE, OLMoE, Qwen2-MoE and Qwen3.5-MoE synthetic models give the CPU’s logits with their routers “on the device” (HostOps), which ran them (at least once per layer and forward), and gpt-oss’s router stays on the CPU.
  • On a GPU (INGA_CUDA=1 cargo test -p inga-cuda --release --test small -- --ignored), each test listing every failing case before it fails, every row of the inputs its own:
    • llama_cpp_rms_norm_matches_ggml_s_arithmetic_and_inga: rows of 896, 1024, 4096, 5120 (both block sizes) and per-head norms of 128 and 64, 1 to 33 rows, against x * w / sqrt(mean(x²) + eps) in f64 (1e-5 of the largest) and Inga’s kernel;
    • llama_cpp_rope_matches_ggml_s_arithmetic_and_inga: the original layout with and without frequency factors, NeoX with and without YaRN, a partial rotation, 1 to 8 tokens at positions up to 297, against ggml’s angle p * theta_scale^i / ff with ggml’s f32 theta_scale and rope_yarn’s ramp and magnitude in f64, the tolerance that of the fast-math powf, sinf, cosf (positions within the hundred turns where sin.approx is specified), and Inga’s kernel; twelve rows keep Inga’s kernel;
    • llama_cpp_top_k_matches_the_cpu_s_router: 8, 32, 64, 128, 256 experts, each gating, normalized and not, a scale and a selection bias, 1 to 37 tokens, against the CPU’s routing in f64: the same experts (another one only where the scores tie to a millionth) and weights within 2e-5;
    • inputs_quantized_once_give_the_bits_of_each_product: Q4_K, Q8_0, Q6_K and F32 products of one input, widths of 1024, 896 and 4096, 1 to 8 tokens and 40, equal to matvec’s and matmul’s bits.
  • The speed: inga bench -p 0 -n 128 --set debug.cuda_mmvq=true --set debug.cuda_ggml_small=true|false on Llama-3.2-1B and Qwen3-8B Q4_K_M, and --set debug.cuda_moe_router=true|false on Qwen3-30B-A3B Q4_K_M, with llama-bench’s tg128 beside them, on the A100 (Colab) and the P1000, with the rule of docs/performance.md.

As built

Section titled “As built”

On branch feat/cuda-ggml-gen-rest (2026-10-22):

  • The PTX was built here with nvcc 12.4.131 (conda’s nvidia/label/cuda-12.4.1 packages, unpacked) against llama.cpp b11489; the same nvcc rebuilt every committed MMQ, MMVQ and flash-attention module byte for byte. Three modules: 107 KB (sm_61), 138 KB (sm_75, sm_80) compressed, about 0.8 and 1.0 MB of PTX.
  • Built and unit-tested without a GPU; not run on a GPU yet: the four GPU tests and the speed wait for the maintainer’s Colab A100 and the P1000.
  • Shipped off: debug.cuda_ggml_small = false and debug.cuda_moe_router = false; with both off nothing changes (no module loaded, no positions buffer, no ggml parameters in the RoPE tables, quantizes_inputs_once false, the routers on the CPU).
  • Measured on a GPU on 2026-10-23 (A100-SXM4-40GB, sm_80, Colab, driver 580.82.07, Inga main de9d9485, llama.cpp b11489; tokens/s, 3 repetitions, every layer on the GPU): tests/small.rs 4 passed. tg128 with debug.cuda_ggml_small off / on / llama.cpp (debug.cuda_mmvq on, as by default there), Llama-3.2-1B-Instruct Q4_K_M 430.9 / 461.9 / 517.3 (1.07×), Qwen3-8B Q4_K_M 125.6 / 137.0 / 141.1 (1.09×, 0.97 of llama.cpp’s). So debug.cuda_ggml_small is on by default on CUDA GPUs of compute capability 8.0 and newer (inga_cuda::measured_setting: unset means “auto”, true or false wins either way), off below 8.0 (the P1000, not measured) and on HIP. The shared quantization needs MMVQ as well (quantizes_inputs_once), on by default from the same compute capability.
  • debug.cuda_moe_router measured with no gain: Qwen3-30B-A3B Q4_K_M tg128 off / on / llama.cpp 40.4 / 39.7 / 175.8 (0.23 of llama.cpp’s). With the router on the GPU the layer still returns to the CPU once per MoE layer for the experts’ ids; it stays off, and the experts on device ids (MUL_MAT_ID, below) are the backlog’s High item.
  • Not in this step: the residual add fused after a post-norm, rms_norm_mul_rope, MMVQ’s fused gate/up with SwiGLU (has_fusion), MUL_MAT_ID for the experts on device ids (see above), M-RoPE, HIP.
