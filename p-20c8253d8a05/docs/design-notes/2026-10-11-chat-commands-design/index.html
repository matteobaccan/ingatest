Commands of the terminal chat (inga run)

Status: built in 0.26.3 (asked by the maintainer on 2026-10-11; first proposed for 0.26.5). See “As built” at the end. Code: src/commands/run.rs (the chat loop of inga run MODEL without -p), src/commands/chat.rs (the parser), src/commands/interrupt.rs (Ctrl-C).

1. Why

Section titled “1. Why”

inga run MODEL opens a chat in the terminal. Today it knows seven commands, each matched by hand in the loop:

Command What it does
/exit ends the chat
/think on|off the reasoning of thinking models on or off for the next answers
/image FILE, /audio FILE, /video FILE attaches a file to the next message
/save FILE, /load FILE saves the conversation as JSON, loads one (as --history)

What is missing, against Ollama’s and llama.cpp’s chats:

  • No list of the commands. The banner only names /exit; the others are in the README’s option rows (--think, --image, --history).
  • An unknown command goes to the model. /help or a typo such as /sav x.json is sent as a user message.
  • No way to start over, to undo or to retry an answer, to change the sampling or the system prompt, or to see the model, its settings and its speed without leaving.
  • One line per message. A pasted block of code is cut into several messages.

2. Rules

Section titled “2. Rules”
  • A command is a line whose first character is /, followed by a known name. The name is matched case-insensitively and may be shortened to any unambiguous prefix (/sa is /save; /s is ambiguous and lists the candidates).
  • An unknown or ambiguous command is never sent to the model. It prints unknown command /xyz: /help lists them and the chat goes on.
  • To send a message that starts with /, double it: //usr/bin is… sends /usr/bin is….
  • Arguments follow the name, separated by spaces. A path may hold spaces and may be quoted (/image "my photo.png"). A wrong argument prints the command’s usage line and changes nothing.
  • Every command answers on stderr in one or two lines saying what changed. The answers of the model stay on stdout, so inga run ... > chat.txt keeps only the conversation.
  • Commands are English, like the rest of the command-line interface.
  • The parser is one pure function, chat_command(line) -> Option<Result<Command, String>>, in src/commands/chat.rs. run.rs executes the Command, and the parser is unit-tested without a model.

3. Commands

Section titled “3. Commands”

3.1 Kept as they are

Section titled “3.1 Kept as they are”

/exit (also /quit, /bye as in Ollama), /think on|off, /image, /audio, /video, /save, /load.

3.2 New

Section titled “3.2 New”
Command What it does
/help (also /?) the commands, one line each, and the multi-line and // rules; /help NAME shows the command’s usage and an example
/clear starts a new conversation. The system prompt (--system or /system), the settings and the loaded model are kept; the attached files and the cache are dropped. Prints conversation cleared (system prompt kept)
/undo removes the last exchange (your message and its answer); repeated, it goes further back
/retry asks the last message again, for a new answer with the current settings (a new seed when sampling)
/system TEXT sets the system prompt for the rest of the chat; /system alone shows it, /system off removes it
/set NAME VALUE changes a setting for the next answers: temperature, top-p, top-k, min-p, repeat-penalty, presence-penalty, frequency-penalty, seed, max-tokens, ctx-shift on|off. The names and ranges are those of the matching command-line options, checked the same way. /set alone lists them with their current values; /set NAME default restores the model’s recommended value or Inga’s default, and says which
/show the model (file, architecture, size, quantization), where it runs (the placement line, as at load), the settings in effect and where each comes from (option, model recommendation, /set), thinking on or off, web search on or off, the system prompt (first line), the context used (1,834 / 8,192 tokens), the files waiting for the next message
/stats the last answer’s numbers: prompt tokens, generated tokens, time to the first token, prompt and generation speed (tokens/s), the context used; and the same summed over the chat
/web on|off web search for the next answers, when the chat started with a search backend (--web-search, --search-url); otherwise it says how to start one
/files the files attached to the next message; /files clear drops them

3.3 Multi-line input

Section titled “3.3 Multi-line input”
  • A line made only of """ starts a block. The lines up to the next """ line are one message, as in Ollama. The prompt changes from > to . inside a block.
  • A line ending with \ continues on the next line (the backslash is removed).
  • Pasted text that arrives with several lines at once is not split: text that arrives within a few milliseconds of the previous line is joined to it. This “bracketed paste” detection is a time window on the reads, not a terminal library.

3.4 Keys

Section titled “3.4 Keys”
  • Ctrl-C while an answer is written stops that answer, keeps what was written in the history (marked as stopped) and returns to the prompt.
  • Ctrl-C at the prompt clears the line; a second one, or Ctrl-D, ends the chat as today.
  • No line editor and no command history with the arrow keys: these need a terminal library, and Inga takes no runtime dependency. The shell’s own history works when the input is piped.

3.5 The banner

Section titled “3.5 The banner”

At start, the banner names the model and adds: /help lists the commands; """ starts a multi-line message.

4. Out of scope

Section titled “4. Out of scope”
  • Switching the model inside the chat (/model NAME): a load takes the time and the memory of a new run, so /exit and a new inga run say the same thing more clearly.
  • The same commands in the web UI’s chat box: the web UI has buttons and menus for all of this. It may later read a leading / the same way, sharing the parser’s table of names.
  • Tab completion and a persistent command history: they need a line editor (see §3.4).

5. Tests

Section titled “5. Tests”
  • Parser (unit):
    • every command, its prefixes and aliases, case-insensitivity;
    • ambiguous prefixes, unknown names, and // escaping;
    • quoted paths, wrong arguments and the usage lines;
    • /set names and ranges against the command-line options’ table, so the two cannot drift apart.
  • tests/cli.rs, the chat fed on stdin with a synthetic model:
    • /help lists every command, and an unknown command is not sent to the model;
    • /clear and /undo change what the next greedy answer sees;
    • /retry with a seed set by /set seed gives the same text as a fresh run;
    • /set temperature 0 makes answers deterministic, and /show reports the values and their sources;
    • /stats prints numbers after an answer;
    • a """ block and a \ line reach the model as one message;
    • stdout holds only the answers.
  • Ctrl-C: a test sends SIGINT to the process (Unix) during a long answer and checks that the chat goes on. Windows uses the console control handler, tested the same way where CI allows it.

6. Docs

Section titled “6. Docs”
  • README: a “Chat commands” table in the command-line reference, next to inga run.
  • Use-case guides: keep-long-conversations.md (/clear, /undo, /save) and use-thinking-models.md (/think) point to it.
  • inga run --help: the commands’ summary lines.

7. As built (0.26.3)

Section titled “7. As built (0.26.3)”
  • The parser is chat::chat_command(line) -> Option<Result<Command, String>> as planned, with the table chat::COMMANDS (name, aliases, usage, summary, example) that /help prints. Prefixes count for aliases too (/q is /quit).
  • /set‘s settings are chat::SETTINGS; their values go through the command line’s own cli::set_sampler_option (and cli::num for seed and max-tokens), so both accept and refuse the same values with the same message; a unit test checks it for every setting. The command line checks the sampling options’ types, not ranges, and so does /set. temp (the option’s name) and prefixes such as max also name a setting.
  • /retry keeps the seed set by /set seed, so a retry gives the same answer as a fresh run with that seed; otherwise, when sampling, it draws a new one from the clock. A retry does not take the files waiting for the next message.
  • /clear keeps the session’s KV cache: the next prompt shares only the system prompt with it, so the rest is processed again, as with a dropped cache.
  • The seed’s source in /show is --seed or the clock (the command line does not record which).
  • Lines are read on a thread of their own, so the prompt can watch Ctrl-C; pasted text is the lines arriving within 15 ms of each other, on a terminal only (a pipe sends every line at once). A block’s or a pasted message’s text is never read as a command.
  • Ctrl-C: SIGINT through the C library’s signal on Unix and SetConsoleCtrlHandler on Windows, installed for the chat only (-p keeps the default). An answer stopped by it stays in the history as written; the report line says cancelled. A press during the prompt’s processing stops the answer at its first token. The SIGINT test of §5 is not written: CI feeds the chat through a pipe, and Ctrl-C is a manual check (TODO.md).
