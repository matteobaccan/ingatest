Image generation on the GPU

Status: proposed, not built beyond P0. The maintainer asked for it on 2026-10-25 (“prepare the GPU path of image generation now, so the optimization starts as soon as the first A100 numbers are in”). On 2026-10-30 he decided the first version for 0.40.0 (“mi piacerebbe dare la prima versione delle immagini da gpu nella 40”, docs/todo/0.40.0.md, “Pictures on the GPU, the first version”):

  • 0.40.0 ships P0 and P1 on CUDA for SD 1.x / 2.x, SD-Turbo, SDXL and SDXL-Turbo. The UNet and the VAE run on the GPU. The text encoders stay on the CPU.
  • It is done when those models run on the A100 with their PSNR against the CPU (§3.4) and their times next to the reference’s CUDA times (§5).
  • If the kernels take longer, 0.40.0 ships P0 and P1a, and P1b and P1c move to 0.41.0.
  • P2 to P5 come later: the text encoders, Flux / SD 3 / Qwen-Image, Vulkan / HIP / Metal, and Wan video.

1. Why

Section titled “1. Why”

1.1 Where it stands (origin/main 92c195f, 2026-10-30)

Section titled “1.1 Where it stands (origin/main 92c195f, 2026-10-30)”
  • Only the CPU draws today. inga image (crates/inga-diffusion) covers SD 1.x / 2.x, SDXL, SD-Turbo, SD 3.x, Flux.1 and Qwen-Image, with image to image and inpainting; inga video covers Wan 2.1. All of it runs on the CPU:
    • the crate depends on inga-cpu and on no GPU crate;
    • every operation takes a &CpuBackend (ops.rs);
    • the command never reads gpu.device / --device.
  • inga image has no --device flag. It does read the global --set KEY=VALUE (src/cli.rs, global options).
  • Image generation has never been measured.
    • docs/performance.md and docs/experiments.md have no row for it.
    • docs/performance.md’s open list has the item “Image generation, never measured yet”.
    • docs/todo/real-world-checks.md lists the per-stage baseline as open.
    • The Colab cell that compares the per-stage times (§5) has not reported yet.
    • So every number below that is not a file size or a shape is a goal, not a result.
  • The LLM side already runs on CUDA, Vulkan, HIP and Metal behind one interface, inga_gpu::GpuOps, with HostOps (crates/inga-gpu/src/host.rs, the CPU behind the same interface) for tests without a GPU. crates/inga-cuda holds Inga’s own PTX kernels and ggml’s MMQ, MMVQ, flash attention and small kernels, ported unchanged.

1.2 What users ask

Section titled “1.2 What users ask”

Image generation in the same tool as chat is one of the most-wanted features of the engines people use: ollama/ollama#786 “Image generation models”, 112 reactions (the maintainers’ survey of 2026-10, issues-ollama-llamacpp.md). A picture drawn only on the CPU takes minutes. A user with a GPU expects seconds, and expects Inga to find the GPU by itself.

1.3 How comparable engines do it

Section titled “1.3 How comparable engines do it”

stable-diffusion.cpp:

  • Read on 2026-10-25 at master 0f76bf5 (the sources and docs/backend.md), and again on 2026-10-30 at tag master-1028-37bc88b (docs/build.md, docs/performance.md, examples/common/common.cpp, src/pipeline/image.cpp).
  • One ggml graph per module: the text encoders te, diffusion and vae. Each module has its own backend: --backend te=cpu,vae=cuda0,diffusion=vulkan0. Where the weights live is set apart from where they run (--params-backend, which can be disk). There is a per-device budget, --max-vram cuda0=6. --auto-fit on (the default) places the weights on the compute GPU, then the RAM, then another GPU, then the disk, by the free memory. --offload-to-cpu keeps the weights in RAM and copies them to the GPU as needed. --clip-on-cpu and --vae-on-cpu are deprecated aliases of --backend te=cpu / vae=cpu.
  • Convolutions use ggml_conv_2d (im2col then a matrix product) or ggml_conv_2d_direct, chosen per module (conv_direct_mode on/off/auto; auto probes each backend once).
  • Attention goes through ggml_flash_attn_ext when the backend supports it:
    • --flash-attn on|off|auto (default auto), per module (auto,te=off);
    • keys and values cast to F16; F32 accumulation;
    • on CUDA, heads below 64 are padded to 64 (2026-10-25 read, src/core/ggml_extend.cpp);
    • its docs/performance.md says flash attention in the diffusion model saves about 1400 MB on SD2 at 768 x 768 (its claim).
    • The 2026-10-30 tag also has native CUDA SageAttention (--sage-attn) and a patched ggml that uses CUTLASS for INT8 GEMM and CuTe attention (docs/build.md).
  • GroupNorm, LayerNorm and the timestep embedding are ggml’s own operations.
  • The VAE is decoded in tiles when asked (--vae-tiling). The guidance’s two passes run as one batch (--batched-cfg, on by default).
  • Its CUDA products are ggml’s: MMQ for quantized weights, and cuBLAS for F16 / F32 with many rows (below, “ggml-cuda”).
  • Its stage lines, logged at INFO (src/pipeline/image.cpp, src/model_loader.cpp at master-1028-37bc88b):
    • get_learned_condition completed, taking X.XXs;
    • sampling completed, taking X.XXs (all the steps);
    • decode_first_stage completed, taking X.XXs;
    • generate_image completed in X.XXs;
    • loading tensors completed, taking X.XXs (...).

The reference build for the measurement (§5) is stable-diffusion.cpp at tag master-1028-37bc88b (commit 37bc88b5e97a213821949732ea66c58ae8ffc784, 2026-10-30):

  • Fetch: git clone --recursive https://github.com/leejet/stable-diffusion.cpp, then git checkout master-1028-37bc88b && git submodule update --init --recursive. That brings its patched ggml at 7b2b435 and the CUTLASS headers its CUDA build needs.

  • CUDA build: cmake -S . -B build-cuda -DCMAKE_BUILD_TYPE=Release -DSD_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=80 -DCMAKE_CUDA_COMPILER=$NVCC, then cmake --build build-cuda -j$(nproc). This is its documented -DSD_CUDA=ON plus the A100’s architecture.

  • CPU build: cmake -S . -B build-cpu -DCMAKE_BUILD_TYPE=Release -DSD_CUDA=OFF.

  • Run: its own defaults, except the sampler, given explicitly so that both programs use the same one:

    • Defaults left as they are: --flash-attn auto, --batched-cfg on, --auto-fit on, --rng cuda.
    • A second CUDA run adds --backend te=cpu: the same split as P1 (text encoders on the CPU).
    • The CPU build runs with -t $(nproc).

diffusers (read on 2026-10-30, docs/source/en/optimization/memory.md on main):

  • enable_model_cpu_offload keeps the one model of the pipeline that is running on the GPU, the others on the CPU; the UNet stays on the GPU until it is done.
  • enable_sequential_cpu_offload moves submodules back and forth (“extremely slow”, its words).
  • enable_group_offload moves groups of layers, at block or leaf level.
  • enable_slicing / enable_tiling decode the VAE per image / in tiles (“may have some tone variation from tile-to-tile”).

ComfyUI: not read for this spec. The idea that it loads and frees whole models between stages is from memory.

ggml-cuda at b11489 (the pin of tools/build-ggml-ptx.sh, read in a checkout on 2026-10-30):

2. What it does

Section titled “2. What it does”

2.1 How the CPU code is laid out

Section titled “2.1 How the CPU code is laid out”

  • ops.rs holds the building blocks on Fmap ([batch][y][x][channel], pixel-major: a pixel is a row of channels) and on Vec<f32> rows:

    • Linear, Conv and Norm (group_norm, layer_norm);
    • attention / attention_ext over strided Cols;
    • geglu, silu, add, add_rows, upsample, concat and pad_after.

    Each one takes &CpuBackend and returns a new buffer.

  • The networks:

    • unet.rs: ResBlock, the spatial transformers, the timestep embedding;
    • vae.rs: the KL VAE’s encoder and decoder;
    • clip.rs, t5.rs, flux.rs, sd3.rs, qwen_image.rs with wan_vae.rs;
    • llm.rs: a language model used as text encoder;
    • video/: Wan 2.1.

  • pipeline.rs (ImageModel) runs the conditioning, the schedule and the sampler (sampler.rs), the guidance mix and the edit’s blending on the host. It calls the denoiser once per step, then decode. Progress reports Text, Encode, Step(i, n) and Decode.

2.3 P1a: the seam, with the CPU’s output unchanged

Section titled “2.3 P1a: the seam, with the CPU’s output unchanged”

  • DiffusionOps (new, crates/inga-diffusion/src/device.rs) is a trait with:

    • type Buf, type Linear, type Conv;
    • one method per row of §2.2, with the shapes and names of §2.4;
    • upload_linear(&self, &Linear) -> Result<Self::Linear> and upload_conv(&self, &Conv) -> Result<Self::Conv>;
    • outputs written into caller-owned buffers taken from a pool per pass (no allocation per operation).

  • CpuOps wraps CpuBackend and today’s ops.rs, unchanged: its Linear and Conv are ops::Linear and ops::Conv, the taps reordered at load as Conv::new does now.

  • What becomes generic: unet.rs (Unet<O: DiffusionOps>) and vae.rs (Decoder<O>, Encoder<O>). clip.rs, t5.rs, flux.rs, sd3.rs, qwen_image.rs and video/ stay on CpuBackend as they are; they become generic in P2 / P3.

  • pipeline.rs holds the parts as boxed objects (all new):

    • dyn Denoiser: forward(latents, t, cond) -> latents, read back each step;
    • dyn ImageDecoder / ImageEncoder;
    • the text encoders as they are.

    The sampler, Progress and GenParams do not change.

  • OnDevice<G: GpuOps> (new, same file) implements DiffusionOps over a GpuOps. inga-diffusion gains a dependency on inga-gpu. In P1a, OnDevice<HostOps> runs in tests only.

  • Exit: the same bytes as today. The goldens of crates/inga-diffusion/tests/oracle.rs (tests/data/*-sdcpp.png) and tests/images.rs do not change, and the CPU slows by at most 3 % (inga image --timings, SD-Turbo 512 1 step and SD 1.5 512 20 steps, machine A, before and after).

2.4 P1b: the new GpuOps operations

Section titled “2.4 P1b: the new GpuOps operations”

They go in crates/inga-gpu/src/ops.rs. Each has a default of Err(Error::Unsupported(..)), as short_conv did in 0.35.0, so Vulkan, HIP and Metal fill them in their own time (P4). They are implemented by HostOps (on the CPU, in f32, as ops.rs computes them) and by CUDA’s Gpu. The shapes are in values and checked by the implementation, as for the existing operations.

Reused, unchanged: alloc, write, read, copy, upload_weight, act_scratch, add, add_bias and matmul (MMQ for GGUF types).

On CUDA:

  • The new kernels go in files of their own: kernels/diffusion.cu → ptx/diffusion.ptx (built by tools/build-ptx.sh with the pinned nvcc 12.4) and src/device/diffusion.rs. They do not go in batch.cu, attention.cu or the hot paths of device.rs, which the LLM work changes often.
  • diffusion.cu holds: the group norm (two passes, f32 sums per image and group), the layer norm, SiLU, the GEGLU of a fused row, upsample, concat, pad, the per-image add, im2col on pixel-major maps, a strided F16 cast for attention, the attention for heads of 512, and the F16 product.

2.5 What CUDA code is reused (crates/inga-cuda, read on main 92c195f)

Section titled “2.5 What CUDA code is reused (crates/inga-cuda, read on main 92c195f)”
  • Flash attention: Gpu::flash_attention (src/device/ggml/fattn.rs). It is ggml’s tensor-core kernel flash_attn_ext_f16 on sm_75 / sm_80 and the tile kernel on sm_61, ported for heads of 64, 128 and 256 (HEADS, ptx/ggml/fattn-d{64,128,256}.sm{61,75,80}.ptx.z). It reads F16 keys and values from a DeviceKv, takes a mask, and reads keys in tiles of 256 (KQ_STRIDE). attention_full reuses it as follows:
    • Keys and values: cast to F16 by the strided cast kernel into a scratch DeviceKv (Gpu::kv_cache(cap, kv_dim) with cap = nk rounded up to 256, zeroed).
    • A non-causal mask (new, beside fattn::mask): 0 for the nk real keys, -inf for the padding. It is built once per shape, as the causal one is.
    • A new entry, flash_attention_full: the same launch as flash_attention. AttnOpts::full stays refused by Gpu::attention, the LLM path, which does not change.
    • Heads by model (SD 1.x: 8 heads over 320 / 640 / 1280 channels; SD 2.x, SD-Turbo, SDXL: heads of 64):
      • 64: native;
      • 40 → padded to 64, 80 → 128, 160 → 256, with zero columns: the dot products do not change and the scale stays 1 / sqrt(d) of the real d;
      • 512 (the VAE’s mid-block, one head) → diffusion.cu’s own blocked attention (f32 scores, a block of queries at a time, as ops::attend), because ggml takes 512 only with grouped queries.
    • Later: porting ggml’s own heads of 40 and 80 (b11489 has them) means adding them to tools/build-ggml-ptx.sh’s modules. That is a measured change of its own, after P1.
    • Fallback: where flash attention does not run (debug.cuda_fattn = false, the default below compute capability 8.0, or a GPU older than Pascal), attention_full uses the blocked kernel.
  • MMQ: Gpu::matmul → mmq (src/device/ggml.rs), reused unchanged for GGUF UNets:
    • Q4_0, Q8_0, Q4_K, Q5_K and Q6_K by default; the others behind debug.cuda_ggml_new_types;
    • from MIN_ROWS = 9 rows, weights’ rows a multiple of 128 (ROW_MULTIPLE);
    • activations quantized to Q8_1 as ggml does.
  • The F16 products: today’s matmul_f16 (kernels/matmul.cu, the MATMUL(f16, T_F16) tiles, f32 FMA) stays as matmul_wide’s fallback and as the reference of its tests.
    • Neither Inga’s kernels nor the vendored ones have a tensor-core product for many rows (no mma.sync outside kernels/ggml/fattn.cu’s instantiations).
    • ggml’s mmf stops at 16 columns (§1.3).
    • So the new product is Inga’s own, in diffusion.cu: mma.sync.m16n8k16 F16 x F16 → F32, the activations cast to F16 tile by tile.
    • It is entered only from matmul_wide, so the LLMs’ F16 prompts do not change. Opening it to them later is its own measured change.
  • Elementwise: add_f32 and add_bias_f32 (kernels/elementwise.cu) through add / add_bias, and the GELU table of gelu_f32 / geglu_f32, passed to geglu_rows so it matches the CPU’s.
  • Not reused:
    • GpuOps::group_norm (Mamba-2’s RMS norm per group);
    • attention_rows_f16 / flash_decode_f16 (batch.cu: causal, over a session’s cache);
    • ggml’s NCHW im2col, norm, upscale and concat (Inga’s maps are pixel-major).

2.6 P1c: the plan, the setting, the line

Section titled “2.6 P1c: the plan, the setting, the line”

  • The plan per part:

    • Each part’s weight bytes are counted from Tensors (new: ImageModel::part_bytes()).
    • F32 weight matrices (SD 1.5’s and SD-Turbo’s published files are F32) are converted to F16 when uploaded, and this is said on the line.
    • The activations of the size asked are computed from the shapes (the VAE decoder’s last level at 1024 x 1024: maps of 1024 x 1024 x 128 values, 512 MiB each in f32).
    • The budget is the LLM side’s inga_gpu::budget(free, total); the load goes under gpu_runtime::uploading().
    • The UNet is placed first (it runs every step), then the VAE. A part that does not fit runs on the CPU, and the line says so.
    • No VAE tiles in P1. Above the budget the VAE stays on the CPU, said so; tiles are P3’s.

  • The VAE’s activations stay in f32. SDXL’s original VAE overflows in F16; that is the reason for the guides’ fp16-fix VAE. So the VAE’s products use matmul (f32 activations, F16 weights), not the F16 tensor-core path, until a test shows F16 is safe.

  • The setting:

    • gpu.device / --device (the existing key, Kind::Device, default auto) is honoured by inga image and by inga serve with an image model, as inga run honours it. inga image gets the --device flag.

    • New key, declared as debug.cuda_fattn is:

      with pub static IMAGE_GPU: Tunable = Tunable::new("debug.image_gpu"); in crates/inga-core/src/tunables.rs.

    • Default: off in the release that ships P1c. After the A100 run passes (§3.4, §5), the default becomes auto: on for compute capability 8.0+ through inga_cuda::measured_setting(&IMAGE_GPU, api, cc), as debug.cuda_fattn went. That is a change of its own, with its numbers.

    • false keeps every part on the CPU whatever the device. A value the user set is never changed silently.

  • The line, printed once on stderr before the prompt’s encoding (and by inga serve when it loads the model). Its exact texts:

    • on the GPU: drawing on cuda:0 (NVIDIA A100-SXM4-40GB): the UNet (4.8 GiB, F16) and the VAE (160 MiB, F16); the text encoders on the CPU (not on the GPU yet)
    • with F32 weights converted, the size part becomes: the UNet (1.6 GiB, F16 from the file's F32)
    • the setting off, with a CUDA GPU present: drawing on the CPU: pictures on the GPU are off until measured (--set debug.image_gpu=true tries cuda:0)
    • a part that does not fit: drawing on the CPU: the UNet (4.8 GiB) does not fit in cuda:0's 3.1 GiB free or, the UNet placed: drawing on cuda:0: the UNet (4.8 GiB, F16); the VAE on the CPU (its 6.2 GiB of activations at 1024 x 1024 do not fit in the 2.0 GiB left)
    • another family: drawing on the CPU: Flux.1 draws on the CPU only for now (the GPU draws Stable Diffusion 1.x, 2.x and SDXL)
    • another kind of device: drawing on the CPU: vulkan:0 cannot draw pictures yet (CUDA can)
    • --device cpu: drawing on the CPU (--device cpu)

    The model’s name, the sizes and the device are the real ones. The first line’s numbers are SDXL’s. --timings’ heading changes from timings (CPU, N threads): to timings (UNet and VAE on cuda:0, text encoders on the CPU with N threads):.

6. Risks

Section titled “6. Risks”
  • The F16 product. Without cuBLAS, the UNet’s products need Inga’s own tensor-core kernel. If it is slower than the reference’s cuBLAS, everything above it is too. It is measured first, alone, in P1b’s third part. If it falls short, P1 can still ship on matmul_f16 with honest numbers, or the maintainer may choose to port CUTLASS-style tiles (§7).
  • F16 overflow. The VAE keeps f32 activations (§2.6). F32 weights converted to F16 can lose range (SD 1.5’s and SD-Turbo’s files): the PSNR gate catches it.
  • Padded heads waste work: up to 60 % more attention FLOPs for SD 1.x’s heads of 40 → 64 (computed from the shapes, not measured).
  • Memory. The VAE’s activations at 1024 x 1024 have no tiles in P1. On cards smaller than the A100 the VAE may stay on the CPU (said on the line). In inga serve the GPU is shared with LLMs (gpu_runtime::uploading()).
  • The same image for a seed: the GPU’s picture is close to the CPU’s, not identical (§3.4).
  • Concurrent CUDA work: the LLM kernels change often (#911, #926). The diffusion kernels go in files of their own.
  • The schedule: P1b’s three kernels are the long part. The roadmap’s fallback (P0 and P1a in 0.40.0) keeps the release from waiting on them.

7. Open questions for the maintainer

Section titled “7. Open questions for the maintainer”
  1. The PSNR thresholds of §3.4 (30 / 35 / 45 dB on real models): accept them as gates, or set them after the first A100 run?
  2. F32 files (SD 1.5, SD-Turbo) converted to F16 at upload (half the memory, the tensor cores), or kept in F32 on the GPU (matmul_f32’s tiles, slower)?
  3. The tensor-core product: Inga’s own kernel (the proposal), or vendoring ggml’s mma.cuh tile primitives unchanged as a base (a new vendored file and its SOURCES entry)?
  4. Heads of 40 and 80: padding first (the proposal), or port ggml’s d40 / d80 flash-attention modules from the start?
  5. Does inga serve show the line in the web UI’s Images page too (the “Be transparent” rule), in P1c or later?

  • F32 files (SD 1.5, SD-Turbo): converted to F16 when their weights go to the GPU; the file on disk and the CPU path stay F32.
