Video input, part 2: MP4 and WebM

Status: proposed for 0.34.0 (decided 2026-10-14: H.264 only in the browser, no ffmpeg). Nothing is built. The TODO.md item (Extra, asked by the maintainer): MP4 / WebM files, once a pure-Rust decoder is chosen (rav1d for AV1; H.264 and VP9 have no pure-Rust decoder yet), sampled as part 1 samples GIF and MJPEG · llama.cpp (mtmd), vLLM.

Decisions (2026-10-14)

Section titled “Decisions (2026-10-14)”
  1. The web UI first: yes. The browser already decodes every MP4 / WebM it can play; part 1 makes the web UI send the sampled frames, with no decoder in Inga, for 0.34; the AV1 decoder in Inga (part 2) after it.
  2. rav1d without its assembly: accepted. The decoder stays pure Rust, slower (to be measured, §6), with no nasm at build time.
  3. H.264 is decoded only in the browser. There is no pure-Rust decoder, and openh264 builds Cisco’s C source whose patent licence covers only Cisco’s own binaries. The CLI and the API accept AV1 (MP4, WebM) or frames already extracted (a frame list, a directory of frames, GIF, MJPEG). No ffmpeg at all: Inga never runs one, not even when found on PATH (§4.4).

1. Why

Section titled “1. Why”

Part 1 (0.23.0) reads animated GIF, MJPEG and directories of frames (crates/inga-vision/src/video.rs, Video::decode). It samples them with the rules of Qwen2-VL / Qwen2.5-VL, Qwen3-VL and SmolVLM2 (SamplingRule). The videos people actually have are MP4 (H.264, HEVC, AV1) and WebM (VP8, VP9, AV1). Today these are refused with “MP4 and WebM are not yet: extract their frames as images”.

2. What the user sees

Section titled “2. What the user sees”
  • Web UI (part 1): the 🎬 Video button (#attach-video in crates/inga-server/src/webui.html) accepts video/*. A GIF or MJPEG file goes to the server as it does today. Any other file is opened in a hidden <video> element. The page seeks to the times the model samples and draws each frame on a canvas. It sends the frames as JPEG data URLs in the part {"type": "video", "video": [...], "fps": F}, which openai.rs already reads (VideoSource::Frames). The chip shows “12 frames of 0:48”. A file the browser cannot play says so (“this browser cannot play HEVC: convert it to MP4 H.264 or WebM”).
  • CLI and API (part 2): inga run --video clip.mp4, and a video_url holding data:video/mp4 or data:video/webm, work for AV1 (in MP4 or WebM). Other codecs get a precise error: “clip.mp4: H.264 video; Inga decodes AV1 (MP4, WebM), GIF and MJPEG, or takes the frames as images; attach it in the web UI, which lets the browser decode it, or convert it to AV1 with a tool of your choice”.
  • inga info / GET /v1/models keep video as a capability. The web UI’s tooltip (attach.video.t, in all ten languages) names the formats.

3. Part 1: frames sampled by the browser

Section titled “3. Part 1: frames sampled by the browser”
  • The page needs the model’s sampling: fps and max_frames from Clip::video_sampling (crates/inga-vision/src/clip.rs). GET /v1/models adds "video": {"fps": 2, "max_frames": 768} to models that takes_video().
  • The browser picks the times as the server would. A small JS port of Sampling::indices for a source of duration * 30 frames is enough. The server then keeps every frame it receives, because the count is at most max_frames and they come at the model’s fps.
  • Each frame is drawn at its natural size, capped at the image limit (image::check_size), and encoded with canvas.toBlob("image/jpeg", 0.92). Seeking uses requestVideoFrameCallback where it exists, and seeked otherwise.
  • There are no server changes beyond the /v1/models field. Videos sent as frame lists already work for API clients (vLLM’s form).

4. Part 2: decoding in Inga

Section titled “4. Part 2: decoding in Inga”

4.1 Containers (no new dependency)

Section titled “4.1 Containers (no new dependency)”

crates/inga-vision/src/video/ becomes a module folder: mod.rs (today’s video.rs), mp4.rs and webm.rs.

  • MP4 / MOV (ISO-BMFF): the boxes ftyp, moov/trak/mdia (mdhd timescale, hdlr = vide), stbl (stsd with av01 + av1C, avc1, hvc1, vp09; stts, ctts, stss, stsz, stsc, stco / co64). Fragmented files (moof / trun) are also read. The output is the sample table: offset, size, presentation time, and whether the sample is a keyframe.
  • WebM / Matroska: EBML, Segment/Info (TimestampScale, Duration), Tracks (CodecID V_AV1, V_VP9, V_VP8, V_MPEG4/ISO/AVC), Cues when present, and Cluster / SimpleBlock / BlockGroup. The output is the same table.
  • Both readers check every size against the file length before they slice. A file over media::MAX_VIDEO_BYTES (100 MiB) is refused, as are more than MAX_SOURCE_FRAMES samples.

4.2 Sampling before decoding

Section titled “4.2 Sampling before decoding”

Video::decode picks the kept indices from the table (the frame count and duration come from the container) with Sampling::indices, as for GIF. Only those frames become pixels. For each kept frame, decoding starts at the last keyframe at or before it. Kept frames that share a group of pictures are decoded in one pass, so a 10-minute video at 2 fps decodes about 1,200 frames plus the frames in between up to each one.

4.3 AV1 with rav1d

Section titled “4.3 AV1 with rav1d”
  • The rav1d crate (BSD-2-Clause, a port of dav1d), built without its asm feature. Inga wraps it in video/av1.rs. dav1d’s C API (dav1d_open, dav1d_send_data, dav1d_get_picture) is called from Rust, with no C compiler involved. The wrapper takes the av1C / CodecPrivate sequence header and the OBUs of each sample.
  • Pictures are 8-bit or 10-bit 4:2:0 / 4:4:4. The wrapper converts them to RGB with the BT.601 / BT.709 matrix the sequence header names (limited or full range) into inga_vision::Image.
  • Behind a cargo feature video-av1, on by default. A build without it says “this Inga was built without the AV1 decoder”.

4.4 Other codecs (decision 3)

Section titled “4.4 Other codecs (decision 3)”
  • H.264, HEVC, VP8 and VP9 are refused on the CLI and the API with the message in §2: the web UI decodes them in the browser (part 1), and API clients send AV1 or the frames.
  • There is no ffmpeg route: Inga never runs an ffmpeg (AGENTS.md: no external programs), never downloads one, and has no option for it (decided 2026-10-14).

4.5 The audio track

Section titled “4.5 The audio track”

It is not read in this item. Feeding it to an omni model (Qwen2.5-Omni’s use_audio_in_video) needs AAC or Opus decoding. That is left for later.

5. Tests

Section titled “5. Tests”
  • crates/inga-vision/tests/video.rs: tiny MP4, fragmented MP4 and WebM files written by the test, with containers built byte by byte around AV1 samples. The AV1 samples are a 64 x 64 clip of 8 frames, encoded once with aomenc and checked in under tests/data/ (a few KB). The tests check the kept indices against Sampling::indices, the times, and the pixels against the PNGs that dav1d writes for the same clip.
  • Corrupt files: truncated boxes, sizes past the end, 2^32 sample counts. Each returns Error::Format without panicking. A short cargo fuzz target is added for both readers.
  • tests/cli.rs: inga run --video x.mp4 with an H.264 file gives the message in §2.
  • Web UI (Chromium, crates/inga-server/tests/webui_video.rs): a WebM attached in the page reaches the server as a frame list of the right length.

6. Risks and size

Section titled “6. Risks and size”
  • Speed: rav1d without assembly is about 2-3 times slower than dav1d. On 1080p that is still tens of frames a second on a laptop core, enough for sampling. Measure it before release.
  • Binary size: rav1d is about 1-1.5 MB. The container readers are small.
  • Licence: rav1d is BSD-2-Clause; add it to THIRD-PARTY notices. AV1 is royalty-free (AOMedia).
  • Most phone videos are H.264 or HEVC. Part 2 helps mainly with WebM and AV1 downloads; part 1 (the browser) covers phones, and API clients extract frames themselves.

7. Phases and effort

Section titled “7. Phases and effort”
  • Part 1: the web UI samples in the browser, and /v1/models gives the sampling. S.
  • Part 2: the MP4 / WebM readers, AV1 through rav1d, and the messages. M.
