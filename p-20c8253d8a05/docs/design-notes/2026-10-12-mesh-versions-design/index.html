Mesh, nodes of different versions

Status: V1 built in 0.26.3; V2 and V3a built for 0.41.0 (see As built, V2 and V3). V3b, the Update button, waits for signed releases (SHA256SUMS.sig, Q1): the maintainer’s decision of 2026-10-31, “badge only, no button”; its code is kept on branch feat/mesh-remote-update. The maintainer asked for them on 2026-10-12, one of the mesh improvements proposed that day. On 2026-10-30 he placed them in 0.41.0 with the new Mesh page (docs/todo/0.41.0.md, “The mesh’s versions, V2 and V3”) and asked: “la rete mesh riporta la versione di inga del nodo? in modo da suggerire upgrade?” (does the mesh report each node’s Inga version, so that it can suggest an upgrade?). The release stays the maintainer’s decision. This spec was rewritten on 2026-10-30 against origin/main 92c195f (Inga 0.38.1). Code: crates/inga-dist/src/mesh.rs (NodeInfo::same_version, same_protocol, version_note, update, version_cmp, asset_url, update_text, Mesh::satellites, Mesh::master), crates/inga-dist/src/protocol.rs (VERSION, Msg), crates/inga-dist/src/secure.rs (the preamble), crates/inga-dist/src/worker.rs (Hello), src/commands/mesh.rs (inga mesh show), crates/inga-server/webui/js/mesh.js and i18n/mesh.json (the Mesh page), crates/inga-server/webui/js/settings.js (openAbout), .github/workflows/build.yml (the release job), tools/install.sh.

1. Why

Section titled “1. Why”

The maintainer’s question has two parts: does the mesh report each node’s version, and can it suggest an upgrade? It reports the version (V1). It suggests an upgrade only when the node is left out. A node one release behind, which is still used, gets an amber line on its card and nothing to click. Every protocol change since 0.7.0 also left every older node out, even when the change only added something. And updating means walking to each machine.

With three or more machines updated by hand, one of them is always behind after a release.

1.1 Today, in the code

Section titled “1.1 Today, in the code”

  • NodeInfo::same_version (mesh.rs) is true when the node’s announced version equals this process’s CARGO_PKG_VERSION and its protocol equals VERSION. same_protocol compares only the protocol. That one decides use:

    • Mesh::satellites and Mesh::master filter on n.protocol == VERSION;
    • secure::client and secure::server refuse a preamble of another version;
    • Worker answers a Hello of another version with an Error.

  • VERSION (protocol.rs) is 9. It has changed 8 times. Measured with git log -G 'pub const VERSION' and git show TAG:crates/inga-dist/src/protocol.rs on every tag:

    Protocol First release What changed (commit) Kind
    1 0.7.0 pipeline parallelism (a95ac66) —
    1 0.8.0 LoadExperts / Experts (tags 10–11) added without a bump (deed9a5) new messages
    2 0.9.0 Load gains kv (a639c81) a field added
    3 0.18.0 LoadSlice / Slice (10b9429) new messages
    4 0.19.0 Truncated / Checkpoint (a927233) new messages
    5 0.25.1 Offer / Want / Chunk, the mesh (cad084b) new messages
    6 0.26.5 Offer reshaped into pieces; CacheClean / Cleaned (1849f22); Prefill / Prefilled / KvPart in the same release (c97b72d) breaking (Offer)
    7 0.27.0 (published as 0.27.1) Welcome gains devices (d9ff7a5) a field added
    8 never released the preamble, Noise, signed announcements (8113b9d) breaking (transport)
    9 0.28.0 Load gains sessions and gpu (783c3f9) fields added

    Protocol 9 has held from 0.28.0 to 0.38.1, 17 releases (tags). Of the 8 bumps, three only added messages and three only added fields at the end of a message. Two broke the wire: the Offer reshape and the transport. The decoder (Msg::decode) refuses trailing bytes and a field that runs past the payload. So an added field breaks an older peer unless the newer side leaves it out.

  • The Mesh page (mesh.js):

    • meshBanner puts up a banner only for nodes with version_used === false (another protocol), with update.asset (or update.docker) and update.release (mesh.version.banner / mesh.version.banner.self in i18n/mesh.json, eight languages).
    • A card whose version_ok is false adds one line: amber mesh.version.used (“Inga {0} (protocol {1}), this node {2} (protocol {3}): another version, the same protocol: used”), or red mesh.version.unused.
    • The used node’s card has no link, no “older/newer” and no action, although GET /api/inga/mesh already gives it an update. NodeInfo::update answers for any other version, not only another protocol.

  • inga mesh / inga mesh show (src/commands/mesh.rs):

    • it prints · Inga 0.38.1 (another version, the same protocol: used) on the node’s line;
    • under it, version_note with update_text: Inga 0.38.1 against this node's 0.40.0, the same protocol 9: used: update it to 0.40.0, https://…/inga-linux-arm64-0.40.0.tar.gz. The terminal already suggests the update. The page does not. The “found” event (mesh.rs, about line 2436) adds the update only for another protocol.

  • Comparing versions: version_cmp splits on . and - and compares the numbers. A part that is not a number counts as 0, and a longer list is greater. So 0.41.0-rc.1 counts as newer than 0.41.0, which is wrong under semver. Inga has published no pre-release so far.

  • The newest release: neither the CLI nor the server checks it. The one check is in the browser. openAbout (settings.js) fetches https://api.github.com/repos/matteobaccan/inga/releases/latest each time the About dialog opens and says about.newer / about.latest. That request is not opt-in. It is not said before it is sent, and it contradicts “Be transparent” (AGENTS.md). See the open question Q5.

  • SHA256SUMS: the release job (build.yml, “Flatten release artifacts”) already publishes it, the SHA-256 of every archive. tools/install.sh checks it. The previous text of this spec said “today it publishes none”, which is no longer true. It is not signed: anyone who can change the release, or stand between the download and the user, can change both. It hashes the archives, not the inga binary inside them.

  • Signing:

    • macOS: Developer ID signing and notarization are written in build.yml but off. The secrets do not exist (docs/RELEASING.md), so the Mac binaries are signed ad hoc by the linker.
    • Windows: there is no Authenticode signing.
    • Releases: Inga has no signing key of its own.

  • Sizes, measured from the v0.38.1 release (2026-10-25, GitHub API): 28,030,432 B (inga-linux-arm64) to 29,131,230 B (inga-macos-x86_64); Windows 28,535,605 B. MAX_CHUNK is 16 MiB, so an archive is two chunks of the existing Chunk message.

  • A node’s id is a hash of the start time, the process id, the port and the host name (Mesh::start). It is new at every start, so a node that restarts appears as a new card and the old one is left after GONE_AFTER (6 s).

1.2 How others do it (read on 2026-10-30)

Section titled “1.2 How others do it (read on 2026-10-30)”
  • llama.cpp’s RPC (ggml/include/ggml-rpc.h, ggml/src/ggml-rpc/ggml-rpc.cpp, raw.githubusercontent.com, master): RPC_PROTO_MAJOR_VERSION 8, MINOR 0, PATCH 1. The client accepts a server with the same major and a minor not greater than its own (response.major != RPC_PROTO_MAJOR_VERSION || response.minor > RPC_PROTO_MINOR_VERSION fails “RPC server version mismatch”). The idea: a version range, with the newer side speaking down.
  • Kubernetes’ version skew policy (kubernetes/website, content/en/releases/version-skew-policy.md): “kubelet must not be newer than kube-apiserver” and “may be up to three minor versions older”. The idea: a stated, tested window, and the coordinator is never the older side.
  • Syncthing’s upgrade (lib/upgrade/upgrade_supported.go):
    • the archive carries a release.sig, verified against a key built into the binary, over the archive’s name and the binary;
    • the binary is renamed to .old, the new one renamed in, and the old one put back if that fails. The idea: a signature, not only a hash; rename, then replace.
  • Tailscale’s clientupdate (clientupdate/clientupdate.go):
    • it updates itself only for install methods it knows;
    • it refuses NixOS, pacman on Arch, the Mac App Store and custom builds, and says what to do instead. The idea: never replace a binary something else manages.
  • From the maintainers’ research of 2026-10-30 (scratchpad issues-multi-machine.md, localai-issues.md):
    • exo’s README says devices of different versions “don’t join each other”;
    • GPUStack’s most-commented open issue is a broken distributed upgrade (#2647, 23 comments), and “upgrades break deployments” is one of its themes (~6 issues);
    • in LocalAI, an automatic upgrade broke backends (#11720). The idea: upgrades are the step users fear. Never automatic, and always reversible.

V2. MIN_VERSION: an additive change does not leave older nodes out

Section titled “V2. MIN_VERSION: an additive change does not leave older nodes out”

The rule. Starting at V2, the newer peer adapts to the older one.

  • protocol.rs keeps VERSION (the newest it speaks) and a new MIN_VERSION (the oldest).
  • A node announces both: TXT p= as today and a new pmin=. A node without pmin= has pmin = p.
  • Two nodes can work together when their ranges overlap. A connection runs at min(p_a, p_b), its session version.
  • The planner works per connection, not at “the lowest version in the mesh” (what this spec said before): one older satellite does not take a feature away from the others.

Speaking down needs nothing from the older node. An older node refuses any preamble other than its own VERSION (secure::server). So the newer master opens with the node’s version: it knows it from p=.

  • secure::client gets the session version to write in the preamble, and Hello carries the same number.
  • The older node sees its own version and accepts.
  • A newer satellite accepting an older master answers with the master’s version, if it is at least its MIN_VERSION.
  • Noise’s prologue already holds both preambles, so the agreed version is authenticated.
  • Mesh::satellites and Mesh::master filter on the overlap instead of n.protocol == VERSION.
  • version_used becomes “the ranges overlap”.

Message by message. New: Msg::encode_for(v) and Msg::decode_for(v), with one rule for each change. Applied to this history (as if V2 had existed), a master of the newer protocol talking to the older:

Change What the newer master must not send / must accept
A new message (3, 4, 5, LoadExperts, Prefill, CacheClean) Not send it below the version that added it. Leave out the feature on that connection and say so in the plan: “pc3 (protocol 4) takes no tensor-parallel slices: Inga 0.18.0 or later”.
Load.kv (2) Not encode it below 2. Below 2, the worker’s cache is f16. A q8_0 KV cache cannot be placed there, so leave that node out with the reason.
Welcome.devices (7) Accept a Welcome without it (the worker sends it) and read it as “no GPU announced” (mesh.dev.unknown.t already says so).
Load.sessions, Load.gpu (9) Not encode them below 9. Below 9, the worker plans for one session and cannot be told “your CPU, not your GPU”. Plan its layers for one session, and leave it out where the CPU-after-GPU-failure path is needed.
Offer reshaped (6), the transport (8) Cannot be spoken down: MIN_VERSION rises to the new VERSION.

At first MIN_VERSION = 9 = VERSION. Protocol 8 was never released, and 7 has no encryption: speaking it would be a downgrade attack. So V2 changes nothing for today’s nodes. It pays off from the next protocol change on. That is said in the release notes.

Rules for the next change (written in protocol.rs’s doc and in AGENTS.md):

  • a new field goes at the end of its message and is read only when the session version is at least the one that added it;
  • a new message is sent only from its version on;
  • anything else raises MIN_VERSION;
  • the release notes say “mesh protocol N, works with nodes of protocol M and later”, or “breaking: update every node”.

The breaking case on the page. When a node is below this node’s MIN_VERSION, the banner says it: “pc3 runs Inga 0.27.1 (protocol 7); this node needs protocol 9 or later (encrypted connections). Update it:”, followed by the asset as today.

Not in V2:

  • a newer node working with an older master, without an older-master code path in the older release (impossible by construction);
  • protocol 8 or older.

V3a. An older node says so, even when it is used

Section titled “V3a. An older node says so, even when it is used”

This answers the maintainer’s question. No new data leaves any machine.

  • The card (one line, amber, under the versions): “Inga 0.38.1 · newest in this mesh 0.40.0 — used; an update is available” with the asset’s link and “release 0.40.0”. V3b adds the Update button. A used node gets no banner: the banner stays for nodes that are left out.
  • inga mesh show: on the node’s line, · Inga 0.38.1 (older, used). Under it:
    The second form comes with V3b.
  • The “found” event gets the update for a used older node too.
  • GET /api/inga/mesh: update adds newest (the version) and older: true|false. New, additive.

V3b. The Update button

Section titled “V3b. The Update button”

The flow.

  1. The page. The user clicks Update on pc3’s card. The page asks, in a dialog:
    • what will happen: “pc3 will get Inga 0.40.0 (inga-linux-arm64-0.40.0.tar.gz, 28 MB), checked against the release’s signed checksums. pc3 stops its part of any model, restarts as 0.40.0 and comes back. If 0.40.0 does not start, pc3 goes back to 0.38.1.”;
    • when the master must download the asset: “This PC downloads it from github.com/matteobaccan/inga/releases (28 MB)”. Clicking is the opt-in.
    • a model running with pc3 that has no spare: “The model now loses its 12 layers on pc3 until it is back”. This uses the page’s existing ask(), as Clean does. Nothing happens without that click.
  2. POST /api/inga/mesh/update {"node": ID} (new). An admin route of the named keys, like /api/inga/mesh/clean. The master checks:
    • the mesh has a key (security.keyed);
    • the node is a satellite of an overlapping protocol and is older than the target;
    • the target is the master’s own version, never older than the node’s (no downgrade);
    • the node can update itself (below). Otherwise it answers 409 with the reason, which the page shows.
  3. The asset. The master needs the archive for the node’s OS and architecture (asset_url), plus SHA256SUMS and SHA256SUMS.sig (Q1) of its own version:
    • from its cache ~/.cache/inga/releases/V/ (new, listed in Local data);
    • else from the release, which the dialog said. When the node’s OS and architecture match the master’s and the master runs a release binary, the master may send its own binary: SHA256SUMS gains a line for each bare binary (inga-linux-x86_64-0.41.0/inga, new in build.yml). A local build is not in it, so the master downloads instead. Offline and nothing cached: the Update is unavailable, with why, and the link stays.
  4. The transfer, over the worker protocol in the mesh’s encrypted channel. New messages, from the protocol version that adds them:
    • UpdateOffer {version, asset, size, sha256, sums, sums_sig};
    • the node answers with Want (as today);
    • Chunk in 1 MiB pieces for this transfer (not 16 MiB), so the page can show progress;
    • Updating from the node, at each phase. The page shows “receiving 12 / 28 MB”, then the phases. The time is estimated from the link the master measured (links, Mbit/s). Not measured on a real LAN yet.
  5. The node checks, before touching anything:
    • SHA256SUMS.sig against the public key built into Inga (Q1);
    • the archive’s SHA-256 against SHA256SUMS;
    • the name and version in SHA256SUMS against what was offered;
    • the version newer than its own. Then it extracts inga / inga.exe (zip: the existing inga_docs::zip::unzip; tar.gz: flate2, already a dependency, and a small ustar reader, new) and checks its line in SHA256SUMS. It runs NEW --version in a temporary folder next to the binary: the output must be inga 0.40.0 and the exit code 0. This catches the wrong architecture, a missing C library and a binary the OS kills. Any failure: Updating {failed: why}, the old binary untouched, nothing restarted.
  6. The swap and the restart.
    • The node stops its part (unloads its layers, closes its ports).
    • It renames the running binary to inga.old (inga.old.exe) and renames the new file into its place, in the same folder: never written over in place.
    • It starts the new binary with its own arguments and a hidden --update-handoff FILE (new). The file holds the node’s mesh id, the old version and a deadline.
    • The old process stays as a small waiter. It forwards Ctrl+C and the exit code, so the terminal still owns the satellite. It waits for the new process to say it is ready (bound, first announcement sent) by writing to the handoff file.
  7. Rollback. The new process exits, or is not ready within 60 s: the waiter renames inga.old back and runs it (on Unix with exec). It announces “the update to 0.40.0 failed: <the new process’s last error line>; back on 0.38.1”, and the master’s page shows it. inga.old is removed when the next start finds no handoff.
  8. The page follows the node. The new process keeps the old mesh id (from the handoff file), so the same card goes “updating → restarting → Inga 0.40.0”. No “left” card and no new card. The master re-plans it as it does a satellite that joins late (2026-10-13-mesh-robust-design.md).

Who confirms: the user at the master’s page, not at the node. A satellite has no web UI and usually nobody in front of it. Being at the master’s page is the reason to want the button. The node’s own terminal or log prints each step (“update to 0.40.0 asked by pc1 (the master), checked, restarting”), and the node can refuse for good with inga satellite --no-remote-update or mesh.remote_update = false (new key in src/config/keys.rs). Under Q2, the node’s owner opts in instead.

Where it must not replace itself, with what is shown instead:

The node Detected by The card says
In a container container (TXT ctr, already announced) docker pull ghcr.io/matteobaccan/inga:0.40.0, then recreate the container (as V1)
Run by inga service (today inga serve; inga satellite once R1 of 2026-10-12-mesh-always-ready-design.md is built) new: the running binary matches the exe of a service record (<dir>/<name>.json) “pc3 runs as a service: on pc3, inga service stop, install the asset (or sh install.sh), then inga service start”
A binary in a folder it cannot write, or one a package manager owns (/usr/bin, /nix/store) new: a write test of the folder; the path “pc3 cannot update itself (its Inga is in /usr/bin): update it there” with the asset
--no-remote-update new TXT upd=0 the asset only, no button

The node announces the reason (new TXT upd= with a short code), so the page knows it before the click and shows no button that would fail.

Windows. A running .exe cannot be written over or deleted, but it can be renamed. So the flow is: rename inga.exe to inga.old.exe, put the new inga.exe in place, start it, and the waiter (the old process) keeps running from the renamed file. Not run on Windows yet. Antivirus software may hold the new file for a scan. The NEW --version step shows it as a failure with Windows’ error, not as a hang. There is no Authenticode signature: SmartScreen does not apply to a file Inga writes itself (no Mark of the Web). That is not verified on a real machine.

macOS.

  • The binary is renamed, never written over: overwriting a running signed binary in place gets the process killed by code signing. That is known behaviour of macOS, not checked with Inga.
  • A file Inga writes itself carries no quarantine attribute, as with tools/install.sh’s curl download, so Gatekeeper does not stop it. Not verified on the Mac here.
  • Today’s binaries are signed ad hoc. When Developer ID signing is on (docs/RELEASING.md), the node also runs codesign --verify --strict on the new binary before the swap.

Security. A master that pushes executables is the largest trust step in the mesh.

  • Today: a node holding the mesh key can join and take part in the election and the handover. Through the worker protocol it can send satellites models, which are untrusted data with checked parsers, and ask them to clean their caches. It cannot run code on them.
  • With V3b and only SHA256SUMS: the master supplies the checksums too, so any holder of the key can run any program on every satellite that accepts updates. The key becomes root on the LAN.
  • With a signed SHA256SUMS (Q1): the master is only a carrier. A rogue master, or someone who has the key, can at most install a genuine, newer Inga release on a satellite, after a click at a master’s page. Downgrades are refused, so it cannot push an older release with a known bug. What remains: whoever controls the release-signing key (the maintainer’s GitHub secret) controls updates. That is the same trust as downloading a release by hand, without the man in the middle.
  • Always:
    • a keyless mesh refuses Update (security.keyed), because its pre-shared key is public;
    • the route is admin-only when the server has keys;
    • nothing is automatic: there is no update on a schedule or at join;
    • every update is logged on both nodes with who asked.
  • Default (Q2): on for satellites in a keyed mesh, asked each time at the master’s page, only with signed checksums. Without the signing key, V3b is not built: V3a gives the link.

Size and progress. About 28 MB per update (see 1.1), sent once per node. A node that asked recently reuses the chunks it already has (Want lists only the missing ones). Two nodes of the same platform: the master’s cache serves both from one download.

5. Risks

Section titled “5. Risks”
  • The waiter keeps the old process alive for the satellite’s whole life after an update, until its next manual restart. Its memory once the layers are unloaded is not measured. The alternative, exec without a waiter on Unix, has no rollback.
  • An update during an answer: the node’s part goes away. The dialog says it, and the master re-plans as for a satellite that leaves (spare or fewer layers).
  • The protocol’s two code paths (V2) add surface. The frozen frames and the previous-release job keep it honest. A breaking change stays possible: it raises MIN_VERSION.
  • A lost release key means no updates through the mesh until a new key ships in a release installed by hand. Key rotation is not designed here.

6. Open questions for the maintainer

Section titled “6. Open questions for the maintainer”
  • Q1. A release signing key (Ed25519; the private key a GitHub secret, the public key in the source). Recommended: without it, the mesh key would be enough to run code on every satellite. If no, V3b is not built and V3a gives the link.
  • Q2. The default for V3b. Recommended: on for satellites in a keyed mesh, signed checksums required, asked each time at the master’s page, and refusable per node (--no-remote-update). The cautious alternative: off until the node’s owner starts it with --remote-update once. It is safer against a stolen key with signed releases too, but it adds a step on every machine.
  • Q3. The window of V2. Is MIN_VERSION kept as low as the code allows, or capped (as Kubernetes does) at, say, the last three releases with a protocol change? Recommended: as low as the code allows, with the previous-release CI job only for N-1.
  • Q4. Who may press Update when the server has named keys: admin keys only (recommended, like Clean and Make master), or any key with mesh access?
  • Q5. The About dialog’s GitHub check (openAbout, settings.js) runs on every opening without asking. Recommended: make it opt-in. Show “Check for a newer version (asks github.com)” as a button, or a setting updates.check, default off. Then V3a may also say “0.41.0 is available” once the user has turned it on.

V2.

  • VERSION = 10, MIN_VERSION = 9. Protocol 10 adds messages only (LogQuery, LogLines, Request, and tags 21 to 25 reserved for V3b’s update) and two fields at the end of Welcome (os, arch, written only on a connection of 10). So 0.41.0 works with every node of 0.28.0 to 0.40.x (protocol 9), the first protocol change that leaves no node out. Release notes: “mesh protocol 10, works with nodes of protocol 9 and later”.
  • The handshake. A node announces p= and pmin= (none: pmin = p). The newer side opens at the lower p (it knows it from the announcement); the answering side repeats any version it speaks, and Noise’s prologue holds both preambles. A worker not announced (inga worker, --workers) is opened at VERSION; an older one answers with its version, which this node speaks, and the connection opens again at it (secure::peer_speaks). A newer node opening at a version an older one does not speak is not reported as a refusal on the older one.
  • Messages a lower peer does not know are refused before they are sent (encode_for: “LogQuery needs mesh protocol 10 (Inga 0.41.0 or later); the peer speaks 9”), and the feature that needs them says so for that node: “log not available on Inga 0.40.0”.
  • Use. Mesh::satellites, Mesh::master, the handover and Clean cache use the overlap (NodeInfo::speaks_with); version_used is the overlap; session is the connection’s version. A node below MIN_VERSION is left out with the banner “pc3 runs Inga 0.27.1 (protocol 7); this node needs protocol 9 or later (encrypted connections). Update it:”.
