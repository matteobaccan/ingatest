Object detection with dedicated models: RT-DETR, D-FINE, YOLO

Status: proposed for 0.34.0 (decided 2026-10-14). First proposal (reopened by the maintainer on 2026-10-14: it was “not planned: not a language model” in docs/supported-models.md); proposed for 0.34.0 (voice and media). Nothing built. Code (planned): crates/inga-detect (new), crates/inga-formats/src/detect_hf.rs, crates/inga-formats/src/torch_pt.rs, crates/inga-engine/src/locate.rs, crates/inga-server/src/locate.rs, crates/inga-server/src/detect_tool.rs, crates/inga-server/src/webui.html, src/commands/locate.rs.

0. Decisions (2026-10-14)

Section titled “0. Decisions (2026-10-14)”
  1. YOLO’s licence (the maintainer, 2026-10-14): RT-DETR and D-FINE first (Apache-2.0), the suggested models. YOLO comes later (D4): its files are read when the user downloads them, the web UI never suggests one, and its licence (AGPL-3.0, YOLO-World GPL-3.0) is shown at load (§9).
  2. PyTorch .pt files: a restricted reader that never runs code (§4.3, shared with the omni talker’s spk_dict.pt), in D4, refused for anything but tensors and plain values.
  3. One endpoint: POST /api/inga/locate and inga locate take a detector as well as LocateAnything; a /v1/detect alias only if a client asks.
  4. A crate of its own: crates/inga-detect, using inga_diffusion::ops; a shared inga-nn crate once three users exist.

1. Why

Section titled “1. Why”

inga locate (0.28.0, use case) runs LocateAnything-3B: open vocabulary, but a 3B language model that writes about 6 tokens a box and spends tens of seconds per picture on a CPU. Dedicated detectors are 20–80M parameters, answer in a fraction of a second on a CPU, give a score per box and are what people mean by “object detection” (COCO’s 80 classes, or a fine-tune of their own). They also cover the layout model of docling (docling-layout-heron is an RT-DETRv2: document layout spec), so the first architecture serves two items.

2. Which models

Section titled “2. Which models”
Family Architecture Weights Licence Phase
RT-DETR, RT-DETRv2 ResNet-vd backbone, hybrid encoder (AIFI + CCFF), deformable-attention decoder, no NMS HF safetensors: PekingU/rtdetr_r{18,34,50,101}vd(_coco_o365), PekingU/rtdetr_v2_r{18,34,50,101}vd; transformers’ RTDetrForObjectDetection, RTDetrV2ForObjectDetection Apache-2.0 D1
D-FINE (and DEIM’s checkpoints) RT-DETR’s skeleton, HGNetv2 backbone, fine-grained distribution refinement of the boxes HF safetensors: ustc-community/dfine-*; DFineForObjectDetection Apache-2.0 D3
YOLOv8, YOLO11 CSP backbone (C2f / C3k2, C2PSA), SPPF, PAN neck, anchor-free decoupled head with DFL, NMS Ultralytics .pt; GGUF by Asher-1/yolo-gguf (ultralytics-ggml: f32, f16, q8_0) AGPL-3.0 D4
YOLO26 YOLO11’s layout, end-to-end head (no NMS) as YOLO11; in Asher-1/yolo-gguf AGPL-3.0 D4
YOLO-World YOLOv8 + CLIP ViT-B/32 text encoder, RepVL-PAN, contrastive head: classes given as words Ultralytics .pt; GGUF in Asher-1/yolo-gguf (YOLOv8-World) GPL-3.0 / AGPL-3.0 D4
  • GGUF: none for RT-DETR or D-FINE was found; for YOLO only the ultralytics-ggml files above (their tensor names and keys to be read from that converter before D4). Inga reads the safetensors as stored (F32 / F16 / BF16; no conversion), presented as a GgufFile as cohere_hf.rs does; inga optimize can write a Q8_0 GGUF later, but at 20–80M parameters a quantized file saves little.
  • ONNX: no. An ONNX file is a graph of operators, not weights of a known architecture: reading it means an ONNX interpreter (protobuf, ~150 operators), a second engine inside Inga. Every model above has safetensors or a GGUF.
  • Open-vocabulary alternatives with permissive licences, for later: OWLv2 (Owlv2ForObjectDetection, Apache-2.0) and Grounding DINO (Apache-2.0). LocateAnything stays the open-vocabulary answer Inga already has.

3. What the user sees

Section titled “3. What the user sees”

3.1 CLI

Section titled “3.1 CLI”
  • The same command as LocateAnything; a detector adds the score column. QUERY is optional for a detector: without it every class above the threshold is printed; with it ("person, car") only those classes (a name the model does not have is an error that lists the model’s classes, --classes prints them). For YOLO-World the query is the vocabulary.
  • --threshold 0.5 (default 0.5, YOLO 0.25 as Ultralytics), --max-detections 100, --iou 0.7 (NMS, YOLO only), --json, -o boxes.png (as today), and --size 640 (the input side; the model’s preprocessor_config.json by default).
  • A directory or a list of pictures: one block per picture, the model loaded once.

3.2 API

Section titled “3.2 API”

POST /api/inga/locate keeps its body (image, query, model); a detector’s answer has the same detections with a score, plus the model’s classes and the threshold used; text, prompt_tokens and gen_tokens are absent:

threshold, max_detections, iou are optional fields of the request. images (an array) runs a batch. The OpenAPI file (docs/api/inga.yaml) and the API tab document both kinds.

3.3 Web UI

Section titled “3.3 Web UI”
  • The chat: with a detector chosen as the chat’s model, a picture sent is answered by the picture with the boxes drawn (the code that draws LocateAnything’s boxes), a legend of the classes with their counts and a threshold slider that filters the boxes already found (no new run). The answer’s text is the table of detections.
  • The detection model in Settings (a picker like the embedding model’s, kept in settings.json as detector): the model the tool of §3.4 uses. The Models page shows detection as a capability and suggests RT-DETRv2-R18 (80 MB) and R50.
  • The Documents page is untouched here; the layout model has its own picker (next spec).

3.4 A tool for the chat model

Section titled “3.4 A tool for the chat model”

detect_objects beside web_search and fetch_url, offered when a detection model is chosen (and turned on per chat, like web search): arguments image (the 1-based number of a picture in the conversation, default the last), classes (optional list) and threshold (optional). The server runs the detector on that picture and returns compact JSON (label, score, box in pixels, counts by class) to the model; the web UI draws the boxes under the tool call. Any chat model can use it, even one that sees no images: “how many cars are in this photo?” is answered from the counts. The MCP server of 0.28.0 (/mcp) offers the same tool.

4. The code

Section titled “4. The code”

4.1 crates/inga-detect (new)

Section titled “4.1 crates/inga-detect (new)”

Depends on inga-core, inga-cpu, inga-formats, inga-vision (image decoding and resizing) and inga-diffusion (ops::{Fmap, Conv, Linear, Norm, attention}).

  • lib.rs: Detector (an enum over the families), Detection { label, score, bbox }, Options { threshold, max_detections, iou, size }, Detector::open(&GgufFile), detect(&Image, &Options) -> Vec<Detection>, classes().
  • backbone/resnet_vd.rs: ResNet-vd (the three-convolution stem, average-pool shortcuts), batch norm folded into the convolutions at load. backbone/hgnetv2.rs (D3), backbone/csp.rs (YOLO’s C2f / C3k2 / C2PSA / SPPF, D4).
  • rtdetr/encoder.rs: the hybrid encoder: one transformer layer on the last level with 2D sin-cos positions (AIFI), then the top-down and bottom-up fusion of RepVGG / CSP blocks (CCFF).
  • rtdetr/decoder.rs: query selection (the encoder’s top-K anchors by class score, K = num_queries, 300), six decoder layers of self-attention and multi-scale deformable attention (sampling offsets and weights per head, level and point, bilinear sampling of the feature maps: the one new kernel, deform_attn.rs), box refinement per layer; RT-DETRv2’s per-level point counts and its discrete sampling option; D-FINE’s distribution refinement (D3).
  • post.rs: sigmoid scores, top-k over queries x classes, cxcywh to corners in the picture’s pixels; NMS per class for YOLO; the threshold.
  • yolo/head.rs (D4): anchor points per level, DFL (softmax over 16 bins per side), YOLO26’s one-to-one head; yolo/world.rs: the text side through inga_diffusion::clip::TextEncoder (CLIP’s text transformer, already used by Stable Diffusion; ViT-B/32’s sizes come from the file), class embeddings cached per query.
  • preprocess.rs: RT-DETR’s plain resize to 640 x 640 and rescale by 1/255 (no normalization, as its image processor), YOLO’s letterbox (grey 114) — read from preprocessor_config.json when present.

Cost: RT-DETRv2-R18 is about 20M parameters and 60 GFLOPs at 640 x 640, R50 about 42M and 136 GFLOPs. The convolutions go through CpuBackend::gemm as the VAE’s do: expected 0.2–0.6 s per picture on an 8-core AVX2 CPU for R18 (to measure).

4.2 Files (crates/inga-formats/src/detect_hf.rs)

Section titled “4.2 Files (crates/inga-formats/src/detect_hf.rs)”

A Hugging Face directory whose config.json has model_type rt_detr, rt_detr_v2 or d_fine (or the matching architectures) is presented as a GgufFile with general.architecture = rtdetr | rtdetr_v2 | dfine, the configuration as keys (encoder_hidden_dim, num_queries, decoder_layers, decoder_n_points, num_feature_levels, feat_strides, backbone_config.*, id2label as an array) and the tensors under their own names (no copy). Today’s refusal (RTDetrV2ForObjectDetection is not a language model) becomes “an object detector: use inga locate” for inga run, and supported (object detection: inga locate) in inga list, inga scan and the Hub’s search. The ultralytics-ggml GGUF files are recognised by their general.architecture (to read from that converter).

4.3 crates/inga-formats/src/torch_pt.rs (D4)

Section titled “4.3 crates/inga-formats/src/torch_pt.rs (D4)”

A PyTorch checkpoint (a ZIP with data.pkl and data/N) read by a restricted unpickler: the opcodes of protocols 2–5 that build plain values, GLOBAL allowed for the tensor rebuild functions, storages and collections.OrderedDict only; any other class becomes an inert object whose state is kept as a dictionary (so a whole pickled model yields its state_dict by path); REDUCE of anything else is an error. Nothing is ever executed. Bounds as inga-docs’ readers (sizes, depth). Also used by the omni talker’s spk_dict.pt (omni spec).

4.4 Engine, server, CLI

Section titled “4.4 Engine, server, CLI”
  • crates/inga-engine/src/locate.rs: Locator becomes an enum (Generative for LocateAnything, Detector); Detection gains score: Option<f32>.
  • crates/inga-server/src/detect_tool.rs (new, beside websearch.rs, where web_search and fetch_url are defined): detect_objects (definition, argument check, result JSON); the server’s tool loop passes the conversation’s pictures to it.
  • crates/inga-server/src/locate.rs: the new fields; a loaded detector stays in the model pool like an embedding model (small: never counted against --models-max’s large models? see §7’s open point).
  • src/commands/locate.rs: the score column, --threshold, --classes, many pictures.
  • crates/inga-server/src/webui.html: legend, slider, the Settings picker, the tool’s drawing.

5. Tests

Section titled “5. Tests”
  • Synthetic weights (crates/inga-detect/src/testing.rs, as the other models’): a tiny RT-DETRv2 (2-block ResNet-vd, 32 channels, 2 decoder layers, 8 queries, 3 classes) written as safetensors with transformers’ names.
  • Reference: tools/rtdetr_oracle.py runs transformers’ RTDetrV2ForObjectDetection on the same synthetic weights and picture and writes the logits and boxes; the Rust test compares within 1e-4 (the backbone’s features, the encoder’s output, each decoder layer’s boxes, the final detections). The same for RT-DETR v1 and D-FINE.
  • Kernels: deformable attention against a plain loop in f64; batch-norm folding; NMS on hand-made boxes; the letterbox’s coordinates back to the picture.
  • Files: the HF directory read without copying; refusals (unknown model_type, a missing tensor, an unsafe pickle: a GLOBAL of os.system must fail).
  • CLI and server: tests/locate.rs with the synthetic detector (--json, --classes, a query naming an unknown class, many pictures), the API’s fields, the tool’s round trip in crates/inga-server/tests/.
  • Real files (real-checks.yml, group A): PekingU/rtdetr_v2_r18vd on COCO’s 000000039769.jpg (the two cats) against transformers’ boxes within 1 pixel; later YOLO11n from Asher-1/yolo-gguf against Ultralytics.

6. Phases

Section titled “6. Phases”
  1. D1 — RT-DETR and RT-DETRv2 on the CPU (M): inga-detect, the HF directory, inga locate, /api/inga/locate, the chat’s drawing and slider. Acceptance: the real check above; R18 under 1 s per picture on the maintainer’s CPU.
  2. D2 — the tool and the picker (S): detect_objects, Settings’ detection model, the MCP server’s tool.
  3. D3 — D-FINE (S–M): HGNetv2 and the distribution refinement.
  4. D4 — YOLO (M): CSP backbone, DFL head, NMS, YOLO26’s head, YOLO-World’s text classes; the GGUF files and the restricted .pt reader (§0.1 and §0.2: decided yes, 2026-10-14).
  5. D5 — GPU and video (M): conv2d (im2col into the existing matmul) and deform_attn in GpuOps (CUDA, Vulkan, Metal), batches of video frames (inga locate --video, a track per object is out of scope).

7. Binary size, licences, limits

Section titled “7. Binary size, licences, limits”
  • Size: no new dependency. inga-detect is about 3–4k lines with YOLO; expected +300–500 KB in the executable (to measure on the release build). No model is embedded.
  • Licences: Inga’s code is written from the papers and transformers’ Apache-2.0 implementation (read as the reference, as llama.cpp’s code is for the language models); Ultralytics’ AGPL code is not copied. Model licences are shown at load and in the model card (inga info): RT-DETR, D-FINE, DEIM Apache-2.0; YOLO AGPL-3.0 with a one-line warning (“its licence is AGPL-3.0: read it before using its results in a product”); YOLO-World GPL-3.0.
  • Open point for D1: whether small models (detectors, embedding models, rerankers) get a pool of their own outside --models-max.
  • Not here: segmentation masks (YOLO-seg, SAM), pose, tracking, classification-only models (ViT, *ForImageClassification stay refused).
