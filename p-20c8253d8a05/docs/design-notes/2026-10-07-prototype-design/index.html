Inga — First prototype design

Date: 2026-10-07 Status: approved; a living document, kept up to date with each release (latest: 0.26.0, 2026-10-11) License: MIT Background: docs/research/local-inference-landscape-2026-10.md (landscape research), docs/comparison.md (feature comparison with other engines, maintained)

1. Goal

Section titled “1. Goal”

A local LLM inference engine written in Rust from scratch, shipped as a single executable with no runtime dependencies, that runs dense Llama-like and MoE models on CPU and NVIDIA GPUs, fetches them straight from Hugging Face, exposes OpenAI and Anthropic APIs, and can split a model across several machines on a LAN.

Prototype success criterion: works end-to-end (coherent text, greedy output matching llama.cpp, APIs usable by real clients). Performance is measured but is not an acceptance criterion.

Design principles

Section titled “Design principles”
  1. No runtime dependencies. The executable needs no DLLs, CUDA Toolkit, runtimes or installed libraries. Statically compiled Rust crates are allowed, few and statically linked (see §2). The only system library used is the NVIDIA driver (nvcuda.dll / libcuda.so), loaded dynamically only if present.
  2. No hard limits: when resources are short the engine slows down, it does not fail. Any model size runs on any amount of RAM, as long as the file fits on disk and a minimal working RAM is available (activations + one layer). Weights are placed on a memory hierarchy VRAM → RAM → disk (streaming with prefetch) → remote nodes, and the engine states the expected speed up front.
  3. Architecture extensibility. Variants of a known architecture are added declaratively (ModelSpec + tensor-name mapping); new architectures are composed from existing blocks plus, if needed, new Backend operations. Anything unsupported is rejected at startup with a precise message, never executed silently wrong.
  4. “Where” is separate from “what”. Model code does not know about devices: it asks the placement plan for weights and calls the matching backend. CPU, CUDA, disk and remote nodes are interchangeable from this point of view.
  5. The scalar CPU backend is the correctness reference for every other kernel.

Out of scope for the prototype

Section titled “Out of scope for the prototype”
  • Metal, Vulkan, ROCm, WebGPU, NPU backends.
  • Continuous batching, concurrent users, PagedAttention, prefix caching.
  • Speculative decoding, grammar-constrained output, LoRA.
  • Tensor parallelism across machines.
  • MLA, linear/hybrid attention, SSM/Mamba, vision, diffusion architectures.
  • KV cache quantization.
  • GGUF types other than F32, F16, BF16, Q8_0, Q4_K, Q6_K (Q4_K_M also uses Q6_K for some tensors, so Q6_K is included).

2. Project layout

Section titled “2. Project layout”

Cargo workspace with internal crates and a single inga binary.

Every new crate needs an explicit justification, must be statically linked and must not load dynamic libraries. System libraries every program of the platform has are not dependencies: on macOS inga-metal links Metal.framework, Foundation.framework and the Objective-C runtime (as every macOS program links libSystem) and calls them through its own bindings (crates/inga-metal/src/sys.rs), no crate added. Pure Rust is preferred; the only accepted exception is the cryptographic backend of rustls (ring, which compiles C/assembly into the executable at build time).

Deliberate choices:

  • In-house tokenizer (the tokenizers crate depends on onig, which is C).
  • Synchronous HTTP server on std::net, one thread per connection, no tokio. Enough for one user at a time; moving to async is deferred to batching.
  • Errors: one shared Error enum in inga-core, no thiserror/anyhow.

Build dependencies

Section titled “Build dependencies”
  • Stable Rust toolchain.
  • For 0.27.0: nvcc to compile .cu kernels to PTX. The generated PTX is committed to the repo, so building without the CUDA Toolkit still yields CUDA support.

3. Core abstractions

Section titled “3. Core abstractions”

Tensors

Section titled “Tensors”
  • Weight: immutable, possibly quantized dtype (F32, F16, BF16, Q8_0, Q4_K, Q6_K), shape, residence (Vram(dev), Ram as mmap view or buffer, Disk with file offset, Remote(node)). From 0.21.0 a backend may hold the same weight rearranged for its kernels next to the bytes as stored (Storage::Packed: the CPU backend’s Q4_K, Q8_0, Q4_0, Q4_1, Q5_0, Q5_1 and IQ4_NL rows in groups of eight, made at load, the mapped pages dropped; --no-repack keeps the weights as stored).
  • Activation: f32 on CPU, f16/f32 on GPU; allocated from a per-step arena reused for every token, with no allocations in the hot loop. Exception: the scalar reference backend (RefBackend, used only to check the others) allocates small per-call scratch buffers; inner loops do not allocate. The CPU backend the engine runs on (CpuBackend, 0.2.0) reuses its buffers.

Backend trait (coarse-grained operations)

Section titled “Backend trait (coarse-grained operations)”

The backend picks the kernel by shape (matvec in decode, matmul in prefill) and may fuse operations internally. The trait is designed so that a future move to a ggml-style compute graph is an internal replacement.

ModelSpec

Section titled “ModelSpec”

Declarative description derived from GGUF (general.architecture, <arch>.* metadata) or config.json: number of layers, dimensions, n_heads/n_kv_heads, head_dim, rope_theta and scaling (linear/YaRN/llama3), norm eps, vocabulary, n_experts/n_experts_used, expert FFN size, router weight normalization, tied embeddings, QKV bias (Qwen2/2.5), QK-norm (RMSNorm on Q and K: per head in Qwen3, over the whole projection in OLMoE), etc. A mapping table translates GGUF and Hugging Face tensor names into internal roles.

Covered families: Llama 2/3.x, Mistral, Qwen 2/2.5/3, SmolLM (dense); Mixtral, Qwen MoE (1.5/2/3), OLMoE (MoE).

One step

Section titled “One step”
  • Prefill and decode share the same path.
  • KV cache: contiguous per layer, f16, preallocated for --ctx, on the same device as its layer (may move down the hierarchy, see §4).
  • Sampler (CPU; greedy and temperature with top-k up to 128, top-p and min-p also on the NVIDIA GPU that runs the output layer, from 0.22.1): greedy, temperature, top-k, top-p, min-p, repetition penalty, seed. The draw of the token at position p depends only on the seed and p (Philox4x32-10 keyed by the seed, Gumbel-max), from 0.22.1.

4. Placement plan and memory hierarchy

Section titled “4. Placement plan and memory hierarchy”

0.1.0 to 0.3.0 keep every weight in the memory-mapped file and only check that the KV cache fits. From 0.4.0, at startup the planner:

  1. Detects resources: free VRAM per GPU, available RAM, (0.7.0) remote nodes and their memory.
  2. Computes the memory needed by every tensor, by the KV cache for --ctx and by the arenas.
  3. Assigns tensors to tiers from fastest to slowest, putting higher those used on every token: embedding/output, attention and norms, then dense FFNs, then MoE experts. User options (--device, --gpu-layers, --experts-on, --nodes) are constraints the planner respects.
  4. Estimates decode speed as Σ (bytes read per token ÷ tier bandwidth) and prints it, naming the bottleneck (“~2.5 s/token, disk-bound”).

--mem-limit SIZE (or INGA_MEM_LIMIT) caps the budget the planner sees. In 0.4.0 the planner moves MoE experts to disk first (a cache of at least n_expert_used experts); when the rest does not fit either, the layers are streamed from disk (0.9.0, below). The bandwidths of the estimate are assumed (20 GB/s RAM, 2 GB/s disk), not measured.

Disk streaming (introduced in 0.4.0 for MoE experts, generalized in 0.9.0):

  • Disk-tier tensors are read into reusable RAM buffers with prefetch: while layer L is computed, the weights of layer L+1 are read; for MoE, reads start as soon as the router picks the experts, and an LRU cache keeps recent experts in RAM.
  • Experts use explicit I/O (not mmap page faults) to control block size and parallelism. Dense layers (0.9.0) stay memory-mapped: the next layer’s mapping is advised WILLNEED before the current layer runs and the current one DONTNEED after, so the kernel reads ahead in order and memory stays bounded (Linux and macOS; on Windows the operating system pages the mapping). The embeddings and the output projection stay resident.
  • Minimum RAM required: activation arenas + streaming buffers (2 layers or k experts) + the resident part of the KV cache.

Transfers between devices happen only at plan boundaries (device change between layers, experts on another tier). Remote (0.7.0–0.8.0) implements the same hand-off point over the network.

5. Backends

Section titled “5. Backends”

CPU (inga-cpu)

Section titled “CPU (inga-cpu)”
  • Scalar reference kernels for every operation and dtype (0.1.0, single-threaded).
  • From 0.2.0:
    • AVX2, AVX-512 (x86-64) and NEON, with and without dotprod (aarch64), SIMD kernels selected at runtime with is_x86_feature_detected! / is_aarch64_feature_detected! (the INGA_ISA environment variable forces another one); quantized dot products on activations encoded as llama.cpp does (Q8_0 for Q8_0 weights, Q8_K for Q4_K/Q6_K, F16 for F16, BF16 for BF16). Activation encoders are the same scalar code on every instruction set, so all of them encode bit-identically.
    • Persistent thread pool (not fork/join per operation), matmul rows partitioned across threads: threads - 1 workers plus the calling thread; tasks are handed out by an atomic counter; idle workers spin briefly, then park.

CUDA (inga-cuda, 0.21.0–0.22.0)

Section titled “CUDA (inga-cuda, 0.21.0–0.22.0)”
  • Dynamic loading of nvcuda.dll/libcuda.so via libloading; only the Driver API is used (cuInit, cuModuleLoadData, cuLaunchKernel, cuMemAlloc, streams).
  • No Toolkit libraries (cuBLAS, NVRTC, cuDNN): all kernels are ours, written in CUDA C, compiled to PTX at build time and embedded in the executable. The driver JIT-compiles the PTX for the installed GPU.
  • Kernels: matvec/matmul with dequantization for the supported dtypes, rms_norm, rope, attention (decode and prefill, no FlashAttention), swiglu, add, router top-k.
  • If the driver is missing or the GPU unsuitable: fall back to CPU with a warning, unless --device cuda was given explicitly, which is an error.

6. Formats, tokenizer, templates

Section titled “6. Formats, tokenizer, templates”
  • GGUF v2/v3: header, typed metadata, tensor descriptors, alignment; full validation before mmap. Tokenizer and chat template read from metadata.
  • safetensors (0.5.0): JSON header + data; config.json → ModelSpec; tokenizer.json + tokenizer_config.json (template). Dtypes F16/BF16/F32, with optional --quantize q8_0|q4_k at load time.
  • Tokenizer: byte-level BPE (GPT-2/Llama 3/Qwen, with the pre-tokenization regex lists of llama.cpp, selected by tokenizer.ggml.pre) and SentencePiece BPE (Llama 2/Mistral); since 0.20.0, for the BERT-family encoders, WordPiece (bert: Hugging Face’s BertNormalizer and BertPreTokenizer) and SentencePiece unigram (t5: the precompiled character map, Viterbi over the piece scores, as llama.cpp); special tokens; streaming decode that handles UTF-8 split across tokens.
  • Chat templates: Jinja rendering with minijinja plus the functions/filters used by current templates (e.g. raise_exception, tojson); the template is parsed once, at load, and one that does not parse is a startup error; an error raised while rendering a conversation (e.g. by raise_exception) is reported for that conversation.

Hugging Face integration (inga-hub, 0.3.0)

Section titled “Hugging Face integration (inga-hub, 0.3.0)”
  • Model references: <model> on the command line can be a local path or a Hugging Face reference hf://<org>/<repo>[@<revision>][:<quant>|/<file>], e.g. hf://bartowski/Llama-3.2-1B-Instruct-GGUF:Q4_K_M. :<quant> picks the GGUF file whose name contains that quantization tag (case-insensitive); ambiguity or no match is an error listing the available files. Without :<quant> or /<file> a GGUF repo defaults to Q4_K_M; a repository without GGUF files is an error until 0.5.0 (which loads safetensors).
  • Standard HF cache: files live in the Hugging Face hub cache ($HF_HUB_CACHE, else $HF_HOME/hub, else ~/.cache/huggingface/hub) with the same layout as huggingface_hub (models--org--repo/blobs, snapshots/<commit>, refs). Models already downloaded by other tools are reused, and ours are usable by them: no duplicated weights. Where symlinks are not available (Windows without developer mode) files are stored directly in the snapshot folder, as huggingface_hub does.
  • Download: repository file list from /api/models/<repo>/revision/<rev>, files from /<repo>/resolve/<commit>/<file> following redirects; resumable (HTTP Range on a .incomplete file); SHA-256 verified against the listing’s LFS hash; progress on stderr. A model whose files are all in the cache is used without contacting the Hub; pull always asks the Hub for the revision’s current commit. Split GGUF files (*-00001-of-0000N.gguf) are downloaded and loaded as one model.
  • Auth and environment: HF_TOKEN (or the token file huggingface-cli login writes) for gated models such as Llama; HF_ENDPOINT for mirrors; HF_HUB_OFFLINE=1 or --offline forbids network access; HTTPS_PROXY honoured.
  • run, info, bench, serve download a referenced model when missing, after printing its size; pull only downloads; list shows cached models.

7. CLI

Section titled “7. CLI”

<model> is a .gguf file (the first part, for split files), a directory with config.json, *.safetensors, tokenizer.json, or an hf:// reference.

8. Server (0.6.0)

Section titled “8. Server (0.6.0)”
  • HTTP/1.1 on std::net, one thread per connection, one generation at a time (concurrent requests wait in a queue).
  • OpenAI: POST /v1/chat/completions (SSE streaming and non-streaming), GET /v1/models.
  • Anthropic: POST /v1/messages (SSE streaming with message_start / content_block_* / message_delta / message_stop events).
  • Basic tool calling: tool definitions passed to the chat template; calls parsed from the output according to the model family’s format (e.g. Qwen <tool_call>, Llama 3.1+ JSON).
  • No authentication; binds to 127.0.0.1 by default.

9. Distributed inference (0.7.0–0.8.0)

Section titled “9. Distributed inference (0.7.0–0.8.0)”
  • The same executable started as inga worker becomes a node: it announces its memory and devices, receives from the coordinator the list of assigned tensors and loads them from its own copy of the model file (the file must be present on every node; transferring it is out of scope).
  • Protocol: length-framed binary TCP, versioned messages (Hello, Assign, Forward{layer_range, hidden}, Experts{ids, x}, Result, Error). No encryption or authentication in the prototype: trusted LAN only, documented as such.
  • Discovery: explicit --nodes list; optional automatic discovery (UDP broadcast).
  • 0.7.0 pipeline: the planner assigns layer ranges to nodes proportionally to their memory (--node-layers overrides it); the coordinator runs the first range, the embeddings and the output. Per token only the residual stream travels, as f32 (hidden_dim × 4 bytes) so that the output is bit-identical to one machine. Each node keeps the KV cache of its own layers; the coordinator’s KvCache holds the remote ranges as stages, one connection per cache. As built in 0.7.0 the messages are Hello/Welcome, Load/Loaded, Forward/Hidden, Truncate/Ok and Error; the worker resolves the model reference itself and checks it matches.
  • 0.8.0 MoE experts: the coordinator keeps attention and router; experts are spread across nodes; for each MoE layer each node receives only the tokens routed to its experts, in parallel, and the results are summed. As built in 0.8.0: each node runs the same range of experts in every MoE layer (--expert-nodes, --node-experts, else in proportion to available memory); the coordinator sends every worker its rows (LoadExperts, then Experts answered by Hidden), computes its own experts meanwhile, then combines; layer ranges and remote experts are not combined yet.
  • 0.18.0 tensor parallelism (--tp-nodes, --tp-split): every layer is split between the coordinator and the workers by key-value heads (with their query heads, their KV cache and the matching columns of the output projection) and by feed-forward columns (cut at multiples of 256 when the width allows, so a quantized down projection keeps whole blocks; otherwise its slice is kept as F32). For each layer the coordinator sends the normalized residual to every worker (Slice, answered by Hidden with the partial output), computes its own slice meanwhile and adds the partial outputs before the residual connection (and Gemma’s post-norms); two round trips per layer. Dense models only (not MoE, latent attention, DeltaNet or LoRA); TCP only (RDMA moved to 0.27.0). Protocol VERSION 3 adds LoadSlice and Slice.
  • Hybrid models (0.19.0): pipeline stages may hold DeltaNet layers. Their state can only go back to a checkpoint, so the coordinator forwards checkpoints (Checkpoint, answered by Ok) and Truncate is answered by Truncated with the positions the worker kept; the whole cache follows the furthest stage back. Protocol VERSION 4.
  • If a worker dies, the current generation fails with an explicit error.

10. Error handling

Section titled “10. Error handling”
Category Examples Behaviour
Unsupported model unknown architecture or dtype, template that cannot be rendered error at startup, before loading weights, naming what is missing
Resources model larger than disk + minimal RAM, CUDA missing, context too long planner checks before loading; CPU fallback with warning under --device auto
Network Hugging Face unreachable, 401/403 on gated models, interrupted download, checksum mismatch clear message (e.g. how to set HF_TOKEN); partial downloads kept for resume; corrupt files deleted
Runtime CUDA error, worker down, client disconnected ends the current session; the process stays alive under serve
  • Full file validation before mmap: a corrupt file is an error, not a crash.
  • unsafe limited to mmap, SIMD, CUDA FFI, the Vulkan FFI (inga-vulkan/src/), the CPU thread pool (inga-cpu/src/pool.rs: lending a borrowed task to the workers, which run outlives, and splitting an output into disjoint chunks), the CPU topology queries (inga-cpu/src/topology.rs: GetLogicalProcessorInformationEx on Windows, sysctlbyname on macOS) and the operating-system memory queries of the planner and the free-disk query of inga data (inga-engine/src/memory.rs: sysctl/host_statistics64 and statfs on macOS, statvfs on Linux, GlobalMemoryStatusEx and GetDiskFreeSpaceExW on Windows), the system monitor’s CPU, swap and pressure queries (inga-engine/src/system.rs: host_statistics, sysctlbyname and getloadavg on macOS, GetSystemTimes and GlobalMemoryStatusEx on Windows), the list of the mesh’s network interfaces (inga-dist/src/ifaces.rs: getifaddrs on Linux and macOS, GetAdaptersAddresses on Windows) and the sparse files of a mesh satellite’s cache on Windows (inga-dist/src/disk.rs: DeviceIoControl with FSCTL_SET_SPARSE, GetCompressedFileSizeW); every block documents its invariant.
  • No panic! reachable from external input (files, HTTP, network).

11. Testing

Section titled “11. Testing”
  1. Kernels against the reference: every SIMD/CUDA kernel compared with the scalar one on seeded random inputs, with per-dtype tolerance; (de)quantization verified bit-for-bit against vectors extracted from llama.cpp and stored in the repo.
  2. Synthetic models: a test utility writes GGUF and safetensors files with random weights and minimal architectures (dense, and MoE with 4 experts); covers loading, forward pass, KV cache, disk streaming, planner. Runs under cargo test. The Hugging Face client is tested against a local mock HTTP server (file list, redirects, Range resume, checksum failure, 401) and against a fixture cache directory; no real network in cargo test.
  3. Real models (#[ignore], downloaded separately): tokenizer identical to llama.cpp on a corpus of hard strings; greedy output identical for 32 tokens and logits within tolerance; server checks with OpenAI and Anthropic clients. llama.cpp is only a development oracle. On quantized weights llama.cpp also quantizes activations to 8 bits, so a greedy case may diverge at a near-tie between the two best logits; such a case records the diverging token (near_tie_at) and is compared only up to it, while an F32 copy of the same model (no activation quantization in llama.cpp) must match for all 32 tokens (tools/oracle-models.md).
