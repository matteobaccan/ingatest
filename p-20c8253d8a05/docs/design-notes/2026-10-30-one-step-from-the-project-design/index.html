One step from the project

Status: proposed for 0.40.0, not built. The roadmap item “One step from the project” was decided for 0.40.0 by the maintainer on 2026-10-30 (docs/todo/0.40.0.md on branch docs/plan-040-adoption), from the “Direction” paragraph of AGENTS.md written the same day. Which phases ship in 0.40.0 is for the maintainer to choose (§4).

  • crates/inga-server/src/report.rs (new): the report, its redaction and its link, for the terminal and inga serve;
  • src/main.rs (the last match result), src/commands/mod.rs (UNSUPPORTED_HELP);
  • crates/inga-core/src/error.rs (Error, the “what to do”);
  • crates/inga-server/src/lib.rs (ApiError), openai.rs (error_body), families.rs (body), branding.rs (powered_by), version.rs (details_for);
  • the web UI: webui/js/report.js and webui/i18n/report.json (new), js/palette.js (askBox, tell), js/core.js (api, headers), js/shell.js (store), js/markdown.js (save), js/chat.js, js/downloads.js (reportModel), js/export-share.js, js/developer.js (storage), html/shell.html;

1. Why

Section titled “1. Why”

AGENTS.md, “Direction” (the maintainer, 2026-10-30): “zero unjustified errors (an error says what happened, why, and what to do next); and reporting to the project one step away: where something fails, Inga offers to open a GitHub issue with the details already filled in (version, platform, command, model, the error), shown before it is sent”, and “the report Inga fills in is in the language of its page or terminal”.

What origin/main (92c195f) has today:

What Where What it does, what it lacks
A link after “not supported” UNSUPPORTED_HELP, src/commands/mod.rs:66, printed by src/main.rs (the Err(e @ Error::Unsupported(_)) arm) and twice by commands::mod for a projector a bare form link (?template=unsupported-model.yml), nothing filled in; every other error prints error: {e} alone
The Models page’s Report reportModel, crates/inga-server/webui/js/downloads.js:747 opens unsupported-model.yml with title, model, error, version filled; English only; no length check; no redaction pass on m.status or m.model; only for models that do not run
About’s copy aboutBuild, js/settings.js:410 copies inga version’s text for an issue, by hand
The browser page’s report web/report.js (the WebAssembly page, not the web UI) the closest to what this spec wants: every field filled, MAX_URL = 7500, the log cut from its start; opens a form on the public matteobaccan/ingatest
The issue forms .github/ISSUE_TEMPLATE/: idea.yml, test-report.yml, unsupported-model.yml, wasm-beta-report.yml (wasm-report.yml since the page left its beta) no form for an error; none says that any language is welcome
The error type inga_core::Error, crates/inga-core/src/error.rs: eight variants, each a String (Io wraps std::io::Error) the message says what happened and often why; no place for “what to do”
The server’s errors ApiError { status, message } (crates/inga-server/src/lib.rs:808), openai::error_body ({"error": {"message", "type", "code"}}), families::body for the other shapes about 137 calls of error_body; no link, no “what to do”
The web UI’s notices tell(message) (js/palette.js:183, the page’s <dialog id="ask">), api() (js/core.js:89) throws Error(data.error.message) OK only, no Report
The chats store.set("chats", chats) (js/markdown.js:54, :97; js/shell.js:375), store.set = try { localStorage.setItem(...) } catch {} (js/shell.js:139), generated pictures kept as data:image/png;base64,... (js/image.js:117) once the origin’s quota is full, nothing is saved and nothing is said
Credits CHANGELOG.md names issues (“(issue #848)”) never who reported them

Two facts found on main that the roadmap item does not say:

  • The repository is private: https://github.com/matteobaccan/inga answers 404 to a client that is not signed in (checked with curl on 2026-10-30; matteobaccan/ingatest answers 200). A pre-filled link to it works only for its collaborators until it becomes public (§6, question 1).
  • The 2026-10-11 spec Error reports (backlog) plans local report files, a Reports page and inga report. This spec takes from it the redaction rules (its §5) and the form (its §10), and leaves the local files to it.

1.1 How others do it (read on 2026-10-30)

Section titled “1.1 How others do it (read on 2026-10-30)”
  • VS Code’s issue reporter (MIT; src/vs/workbench/contrib/issue/browser/baseIssueReporterService.ts on main): a window that shows the issue’s text before anything opens; MAX_URL_LENGTH = 7500; past it, the text goes to the clipboard after a dialog and the URL’s body says, in the user’s language (localize('pasteData', ...)), “We have written the needed data into your clipboard because it was too large to send. Please paste.” Its redaction (src/vs/platform/telemetry/common/telemetryUtils.ts, anonymizeFilePaths, userDataRegexes) replaces file paths with <REDACTED: user-file-path> and matches tokens (GitHub, Slack, Google, JWT), key|token|secret|password values and e-mails. Taken: the length, the clipboard fallback with a localized line, showing first.
  • rustc’s crash message (MIT / Apache-2.0; compiler/rustc_driver_impl/src/lib.rs, DEFAULT_BUG_REPORT_URL): a terminal line with issues/new?labels=...&template=ice.md. Taken: a link as the last line. Not taken: labels= in the URL (below: GitHub refuses it to someone without the right).
  • human-panic (MIT / Apache-2.0; src/lib.rs of rust-cli/human-panic): writes a report file and says where; “we do not perform any automated error collection”. The local-file half is the 2026-10-11 spec’s.
  • GitHub’s documentation, “Creating an issue from a URL query” (the source of docs.github.com, content/issues/tracking-your-work-with-issues/using-issues/creating-an-issue.md in github/docs): “You must have the proper permissions for any action to use the equivalent query parameter” (labels, assignees), else 404; “If you create a URL that exceeds the server limit, the URL will return a 414 URI Too Long error page” (no number given); issue forms’ text fields can be filled by their id.
  • MDN, “Storage quotas and eviction criteria” (source in mdn/content): Web Storage “is limited to 10 MiB of data maximum on all browsers”, “up to 5 MiB of local storage”; IndexedDB shares a much larger origin quota (Chromium: up to 60 % of the disk); in private browsing “browsers may apply different quotas, and stored data is usually deleted when the private browsing mode ends”; navigator.storage.persist() exempts an origin from eviction (Firefox asks the user).
  • Chat front ends that hit the quota (seen only in search results, not opened: the pages were refused from this machine): big-AGI pull request #158 moved the chats from localStorage to IndexedDB, a reviewer asking to clear localStorage only after checking the copy; BetterChatGPT issues #588 (the setItem quota error) and #591 (IndexedDB); ChatGPT-Next-Web #4574 (quota full after image recognition, the advice being to clear the site’s storage, chats included); a commit of AXERA-TECH/lite_webui catching a silent QuotaExceededError from data URLs.
  • The maintainers’ survey (docs/research/user-pains-2026-10.md, branch docs/user-pains-survey): LocalAI #12562 (“silent failure is the worst kind”), #9125 (settings not saved), #1416 (“please improve error messages”); the pain “Writing in English to be heard”: Inga “no”.

1.2 GitHub’s limits, measured

Section titled “1.2 GitHub’s limits, measured”

Measured on 2026-10-30 from this session (through its HTTPS proxy, not signed in to GitHub) with curl on https://github.com/matteobaccan/ingatest/issues/new?body=...:

URL Answer
up to 8,195 characters 302 to the sign-in page
8,196 characters and more 414 URI Too Long
up to 7,662 characters of plain ASCII the 302 keeps the address (/login?return_to=..., 7,715 characters)
7,663 characters and more the 302 goes to /login with no return_to: after signing in, the filled form is gone
4,257 characters of %C3%A8 (è) return_to kept (7,110 characters)
4,857 characters of %C3%A8 return_to dropped

So for someone not signed in (most first reporters) the limit is the sign-in address: the issue URL with each %, :, /, ?, = and & counted three times (they are escaped again in return_to), plus 37, must stay under about 7,715. Text in Hindi or Chinese (6–9 characters per letter once encoded) fits about half as much as English. web/report.js‘s MAX_URL = 7500 counts characters once, so a long non-ASCII report from the browser page can lose its text at sign-in (not reproduced there; said here). Not measured: the limit for a signed-in user beyond the 414, other browsers’ own limits.

The budget of this spec: cost(url) = len(url) + 2 × count(%, :, /, ?, =, &) + 37 ≤ 7,500, about 200 characters under what was measured.

2. What it does

Section titled “2. What it does”

2.1 R1: a Report on every error

Section titled “2.1 R1: a Report on every error”

One helper per surface.

Surface Helper Builds
the terminal and inga serve inga_server::report (new, beside version.rs, which the CLI already calls for inga version) Report { fields, lang }, redact(&str) -> String, Report::url() -> (String, bool) (the bool: something was cut)
the web UI js/report.js (new, its // ---- Report ---- banner, its include line before palette.js) reportOf(err), reportUrl(fields), reportShow(report)

The browser page (web/report.js) keeps its own report; it adopts the budget of §1.2 later (not in this spec).

The fields (each an id of the new form, filled verbatim):

Field What From
language the language of the page or terminal, e.g. it (Italiano) §2.3
what one line in that language: “What were you doing when it happened? Write in your language: we answer in it.” The reporter writes below it report.json
error the error’s whole text and, from phase 4, its “what to do” the error
version inga X.Y.Z, commit, build date, target and profile version::info
system OS and architecture, the CPU’s instruction set (isa, isa_source), the RAM version::info, inga_engine::memory
gpu each device found, as inga version’s backends lines version::info(Some(&report)) (commands::devices::report(), the server’s cfg.devices)
command the command line, redacted (below) std::env::args, or the API route (POST /v1/chat/completions)
model the model’s file name, architecture, quantization and size set once a model is open (a process-wide report::Context, new)
where terminal, web UI (page NAME[, remote mode]) or API the helper

The template: a new form, .github/ISSUE_TEMPLATE/error-report.yml (“Error report”, label error report, title "Error: "), with these ten ids, what required, the others render: text. “Not supported” errors keep unsupported-model.yml, now filled by the same helper (its ids model, error, info, version, plus a new language input). No labels, assignees or projects in the URL: the form sets the label, and GitHub answers 404 to a reporter without the right to set them (§1.1).

The title: in the language of the page or terminal, “Errore: “ + the error’s first line, cut to 80 characters.

Redaction (report::redact, one function, run on every field; the 2026-10-11 spec’s §5, extended):

What Becomes
the home folder (HOME, USERPROFILE, inga_core::tunables::user_home), with / or \ ~
any other absolute path …/ + its last component (…/Qwen3-8B-Q4_K_M.gguf)
the user name (USER, USERNAME; the home’s last component), as a whole word <user>
the host name (HOSTNAME, COMPUTERNAME, /proc/sys/kernel/hostname, /etc/hostname, as inga_dist::mesh’s private hostname() reads it: made one shared function), and NAME.local <host>
a URL’s user and password, and its query string removed, [removed] left
a URL’s host, except the sources Inga itself reads (huggingface.co, hf-mirror.com, modelscope.cn, ollama.com, registry.ollama.ai, github.com, the API node presets’ hosts) <host>
an IPv4 or IPv6 address outside loopback and the private ranges (10/8, 172.16/12, 192.168/16, fc00::/7) <ip>
e-mail addresses; sk-…, hf_…, ghp_…, github_pat_…, xox…, AIza…, JWTs, Bearer …; the values of key, token, secret, password [removed]

in command: a Path value as a path above

What is not found is not redacted: on macOS neither HOSTNAME (not exported by the shell) nor /etc/hostname exists, so the host name is not known there; NAME.local is caught, a bare host name in an error is not. This is why the report is always shown before it is opened.

The length (§1.2): over budget, the helper cuts, in this order, until it fits: gpu to its devices’ names, command to its first 200 characters, error from its middle (its first and last 600 characters kept, [… cut …] between). Still over (a very long error in Hindi), the fields but language, what and the title are replaced by one line in the user’s language, “The details did not fit in the link: paste them here (they are in your clipboard)”, as VS Code does; the web UI copies them, the terminal prints them above the link.

The terminal. On an error that ends the command (exit status 1: the last arms of main’s match result), after error: …:

The line before the link shows what the link carries, with its values: that is what “shown before it is opened” means in a terminal, where nothing opens by itself. That line stays in English, as the whole command line does; the issue’s title and what are in the terminal’s language (§2.3). A typical link is short: about 820 characters for the example above in Italian, 920 in Chinese (computed with Python’s urlencode on 2026-10-30, not a measure of a real run). UNSUPPORTED_HELP keeps its first line (the list of models) and its second becomes the filled unsupported-model.yml link. Not given a link: usage errors (exit status 2: a wrong flag, inga setup without a terminal), a broken pipe, and Ctrl-C.

inga serve’s error bodies. Every error body made from an inga_core::Error (ApiError::from) carries the link beside the message, where the shape has room (families::body’s rule): error.report_url in the OpenAI and Anthropic shapes, report_url at the top in the others. Its language is the request’s Accept-Language (§2.3). It is left out:

  • of the key refusals (write_refusal: 401, 403, 429) and the family gate (families::refuse: 404, 501): they are the operator’s settings, not Inga’s faults;
  • for a branded server whose brand turned “Powered by Inga” off (Brand::powered_by false): its users report to the brand, not to Inga’s tracker;
  • of its version, system and gpu fields for a client that may not see the build details (version::details_for: --hide-version, a non-admin key): the link then carries the version only, which GET /api/inga/version gives everyone anyway.

The ~137 openai::error_body(&e.message) calls become e.body(req) (one method of ApiError, which reads the request’s language and the server’s settings), a mechanical change. The OpenAPI files (docs/api/) gain the optional report_url (and, from phase 4, todo) in their error schema.

The web UI.

  • api() keeps the server’s whole error object on the Error it throws (err.server).
  • tell(message) also takes an Error: the dialog shows its message (and, from phase 4, its “what to do”) and a third button, Report, an ingaLink (hidden on a brand without “Powered by Inga”, as the side bar’s links are). The 41 tell(e.message || e) calls become tell(e).
  • A chat answer that ended in an error (reply.error = true, js/chat.js:1037–1040) gets a Report icon among its tools.
  • Report opens <dialog id="report"> (new, html/shell.html): the title, each field as it will be sent, where it goes (“github.com/matteobaccan/inga, in a new tab”), and “Opening it sends this text to GitHub in the page’s address; the issue is created only when you submit it there.” Buttons: Open on GitHub, Copy, Close.
  • The fields: the server’s, decoded from err.server.report_url, when it has one; else (the server did not answer, an older Inga in remote mode, an error of the page itself) reportOf builds them from GET /api/inga/version (as reportModel does today), the browser’s name and platform, and the error, with reportUrl applying the same budget. The page’s own redaction is small: the remote server’s address becomes <server>, the page’s origin is never included.
  • reportModel (downloads.js) becomes a call of reportOf with the unsupported-model.yml template.
  • Offline: Open on GitHub opens a tab that does not load, and the dialog says, when navigator.onLine is false, “No connection now: copy the text and paste it into a new issue later” (Copy is always there). The terminal’s link is text and keeps.
  • Remote mode (Settings → Server, remote in js/shell.js): the report is the remote server’s (its version, its GPU), since the error came from it; where says “remote mode”.

2.2 R2: every user-facing error says what happened, why and what to do

Section titled “2.2 R2: every user-facing error says what happened, why and what to do”

Size of the work (counted on 92c195f with a script that skips test files and the #[cfg(test)] part of each file; rough):

Sites
Error::Usage( 1,211
Error::Format( 535
Error::Shape( 451
Error::Unsupported( 288
Error::Device( 82
Error::Tokenizer( / Template( 24 / 8
total (without Io), in 276 files 2,599
matches on a variant (Error::X(_) =>, matches!, e @ Error::X) about 117
the web UI: tell( calls / places that show e.message / its own error strings (*.err*, *fail* keys) 41 / 122 / 42

Biggest crates: inga-engine 416, inga-model 387, the inga binary 299, inga-vision 235, inga-formats 199, inga-diffusion 190.

The structure. Error keeps its eight variants and gains one (new):

  • Error::todo(self, what: impl Into<String>) -> Error (new) wraps an error; a site writes Err(Error::Usage(format!(…)).todo("free some space, or --home elsewhere")).
  • Error::kind(&self) -> &Error (new) is the error without its advice; the ~117 matches move to match e.kind(), and is_out_of_memory, is_kv_pool_full look through it.
  • Error::advice(&self) -> Advice (new): the site’s todo, else a default by kind:
    • Shape, Template of Inga’s own templates, and a panic: “This is a bug in Inga: please report it (the link below)”;
    • Device out of memory: “a shorter context (--ctx), fewer layers on the GPU (--gpu-layers) or --device cpu”;
    • Unsupported: the list of models and the request form (today’s UNSUPPORTED_HELP);
    • Io by io::ErrorKind: not found (“check the path”), permission denied, storage full, address in use (“another program uses the port: --port”);
    • no default for Usage, Format and the rest: those sites say their own.
  • Display is unchanged for a plain error and adds \nwhat to do: … for an advised one.
  • The terminal prints what to do: … under error: … (the default when the site gave none); the server adds todo beside message in the error body and appends it to message too, for clients that show only the message; the web UI shows it under the message in its notice.

Not chosen: a struct in place of the enum, or a String payload made a new type (every one of the 2,599 sites would change at once); a convention inside the message text (nothing could test it).

The review plan, by where users meet the errors first, one pull request per row, each adding its files to the test’s reviewed list:

Batch Files Sites (about)
1 src/main.rs, src/cli*, src/commands/mod.rs, src/commands/serve*, crates/inga-server/src/lib.rs the CLI’s and the server’s start
2 loading a model: inga-formats, inga-engine’s load and placement, inga-hub (downloads, hf://, ollama://) ~700
3 the GPUs: inga-cuda, inga-vulkan, inga-metal, inga-hip, inga-gpu ~310
4 the server’s routes and the web UI’s 42 own error strings ~200
5 the rest (vision, diffusion, docs, mcp, dist) the remainder

A message is reviewed with three questions: does it say what happened in the user’s words; why (the value, the limit, the file); what to do (a flag, a command, a setting, or “report it” when only a fix in Inga helps). Internal invariants (most Shape errors) keep their text and get the “report it” default.

The test that fails (tests/error_advice.rs, new, the shape of no_inga_variable_is_read_but_tests):

  • it scans the reviewed files’ code (not their #[cfg(test)] part) for each construction of Error::Usage(, Unsupported(, Device(, Format(, Tokenizer(, Template(, and fails when its expression has no .todo( and its line no // no todo: WHY comment (an error no user sees, or covered by the default);
  • it counts the same constructions in the files not yet reviewed and fails when the count grows past the number written in the test (a ratchet: lowered by each batch);
  • tests/cli/ runs five common failures (a missing model file, an unknown hf:// model with --offline, a damaged GGUF, a port in use, an unsupported architecture’s synthetic file) and checks that stderr has what to do:;
  • crates/inga-server/tests/webui/i18n.rs fails on a page error string (*.err*, *fail*) without its KEY.todo, or outside an allowlist.

2.3 R3: in the user’s language

Section titled “2.3 R3: in the user’s language”

The words of the report are one file, crates/inga-server/webui/i18n/report.json (new), in the ten languages (en, it, fr, de, es, zh, pt, ru, ja, hi) as every area of the page: the title’s “Error”, the what line, the language’s own name, the “did not fit” line, the dialog’s texts. The page reads them as usual (I18N); the build script (crates/inga-server/build.rs, which already parses the area files in src/webui_assemble.rs) also writes them as a Rust table for report.rs. One source; webui_i18n.rs checks them as any other area. The fields’ data (the error, versions, devices, the command) stay as Inga printed them, in English.

How each surface knows the language:

  • the web UI: lang (js/core.js: the choice in inga.lang, else browserLang()); headers() adds Accept-Language: <lang> (a CORS-safelisted header: no new preflight in remote mode), so the server’s report_url is in the page’s language too;
  • inga serve for any client: the first tag of Accept-Language that is one of the ten, else English;
  • the terminal: today the CLI does not know the user’s language at all (no read of LANG or of the system’s locale outside the environment cleared for MCP servers and skill scripts). New: a top-level key language (auto, en, it, …; flag none), auto reading LC_ALL, then LC_MESSAGES, then LANG (POSIX’s order; C and POSIX are English). On Windows these are rarely set: the system’s language needs kernel32’s GetUserDefaultUILanguage, a new unsafe block, so until the maintainer approves it Windows reports are in English unless language is set (§6, question 3). macOS’s Terminal sets LANG by default (not verified here).

“Write in your language: we answer in it”, from the reporter’s side:

  • the top markdown block of each of the five forms;
  • README.md where it asks for issues (the “Open an issue and tell us” note), and CONTRIBUTING.md’s first list;
  • the site’s footer beside Issues (site/src/pages/index.astro);
  • the what line of every pre-filled report, and its language field, so the answer’s language is known even when the reporter adds nothing.

2.4 R4: credits in the changelog

Section titled “2.4 R4: credits in the changelog”
  • The convention (changelog.d/README.md): an entry for a fix or a feature an issue asked for ends its bold lead with the issue and its reporter, in the style the changelog already has: - **Chats saved again when the storage is full** (issue #990, reported by @login): …; several: (issues #990 and #991, reported by @a and @b). The reporter is the issue’s author; the maintainer’s own issues are not credited.
  • The check (tools/changelog.py check, tested in tools/changelog_test.py): reported by must be followed by one or more @login (GitHub’s login rule: letters, digits and single hyphens, at most 39) inside a parenthesis that names an issue; and an @ followed by a word outside backticks anywhere else in a fragment is refused. The release body is the changelog’s section (build.yml, “Extract release notes from CHANGELOG.md”), and GitHub notifies every @login in it: only reporters may be named.
  • The procedure (docs/maintaining.md, “The loop”): a pull request that fixes an issue someone else opened reads its author (the GitHub tool, or the issue page) and credits them in its fragment; the answer on the issue, in its language, says in which release the fix ships.

2.5 R5: the web UI’s chats no longer lost in silence

Section titled “2.5 R5: the web UI’s chats no longer lost in silence”

Step 1, a warning (phase 2):

  • store.set returns whether it saved; on a refusal it calls storageRefused(key, e) (new) instead of saying nothing.
  • e.name === "QuotaExceededError" (Firefox before 2020 also used NS_ERROR_DOM_QUOTA_REACHED): a bar at the top of the page, once per visit and key, for the chats: “Your chats are no longer being saved: this browser’s storage for this page is full (4.9 MB of chats, 3.6 MB of them pictures). Export them now, then delete pictures or old chats.” Buttons: Export every chat (the Export menu’s all, which writes the chats held in memory: nothing is lost while the tab is open), Delete pictures (new: removes the generated and attached images of chats older than the current one, after ask(…, true), keeping their text and a “picture removed” note), Report.
  • Any other refusal (storage blocked, a private window that refuses it): “This browser keeps nothing for this page: your chats last until you close the tab. Export them to keep them.”
  • Before it is full: save() measures the chats JSON’s length; past 4 MiB (80 % of MDN’s 5 MiB) the Storage page and the chats’ column say how much is used. The browsers’ real limits were not measured.
  • The Storage page (storage(), js/developer.js) gains a line for “Chats in this browser: N chats, X MB, Y MB of pictures”, beside the server’s stores.

Step 2, IndexedDB (phase 5):

  • A database inga-webui with two stores: chats (one record per chat, its id as key, as web/chats.js does on the browser page) and media (each picture, audio or video of a message as a Blob, a random id as key; the message holds inga-media:ID and the page shows it through URL.createObjectURL). A random id and not a hash: crypto.subtle is missing outside secure contexts, and inga serve on a LAN address is plain HTTP.
  • save() writes the chat that changed, not the whole list; Export and Share put the media back as data: URLs, so the files stay the same format (and the browser page’s backup, web/chats.js VERSION = 1, still reads them).
  • The move from localStorage, once, at load: every chat and its pictures written, read back and compared (count and ids), then chats_v = 3; the old inga.chats value is kept untouched for one release, so an older Inga put back still finds the chats as they were (the survey’s “go back by putting the old one back”), and deleted by the release after (§6, question 4). A failed move leaves everything in localStorage and says so with Report.
  • A private window: Chromium’s incognito and recent Firefox and Safari give IndexedDB in memory, wiped when the window closes (MDN: “usually deleted”; not checked browser by browser here). Where indexedDB.open fails, the page keeps today’s localStorage path and step 1’s warning.
  • navigator.storage.persist() is not called by itself (Firefox would show a prompt at load): the Storage page offers “Keep these chats even when the disk is low”, which calls it and says the browser’s answer.
  • Remote mode: whose storage? The browser’s, for the origin of the page, not the server it talks to: in remote mode the chats made with server B live in the storage of server A’s address in this browser, as today (the chats were never on a server; “chats on the server” is the backlog’s U3). The warning and the Storage line say “kept in this browser for <the page’s address>”; switching the remote server does not move them. Several tabs of the same address share the database; today the last tab to save wins for every chat, with one record per chat it wins only for the chat it changed.

5. Risks

Section titled “5. Risks”
  • The repository is private: every link fails for non-collaborators until it is public (§6, question 1).
  • A leak the redaction misses (a folder named after a person, a host name on macOS): the report is shown before it opens, and the fixtures grow with each case found.
  • The terminal’s output changes: tests and scripts that read stderr’s last line; the tests/cli/ ones that expect error: … alone are updated in phase 2.
  • Error bodies grow by up to 7.5 KB; clients that read message are unaffected.
  • The review’s size: 2,599 sites; the ratchet keeps new ones from adding to it, the batches take releases.
  • The move to IndexedDB loses chats: written, read back and compared before the version changes, the old value kept a release; the test covers it with pictures.
  • Delete pictures is lossy: asked first, in red, the export offered beside it.

6. Open questions for the maintainer

Section titled “6. Open questions for the maintainer”
  1. Until the repository is public, where do the links point: matteobaccan/inga (works for collaborators only, nothing to change later), or matteobaccan/ingatest as the browser page does (anyone can report, the issues moved later)?

  5. This spec takes the 2026-10-11 Error reports spec’s form and redaction and leaves it the local files, the Reports page and inga report: confirm, and its status row.
  6. Which phases go into 0.40.0 (§4).

7. Not verified

Section titled “7. Not verified”
  • GitHub’s limits were measured once, not signed in, through this session’s proxy; a signed-in user’s limit beyond the 414 and other browsers’ URL limits were not.
  • The size of the reports’ links (about 820 and 920 characters) is computed, not taken from a real run.

Decisions (the maintainer, 2026-10-30)

Section titled “Decisions (the maintainer, 2026-10-30)”
