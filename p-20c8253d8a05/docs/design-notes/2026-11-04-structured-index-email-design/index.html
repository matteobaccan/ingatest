Structured index: email and tickets

Status: approved by the maintainer on 2026-11-05 (§14). For 0.45.0 (the item Structured index: email and tickets of docs/todo/0.45.0.md, moved there from the backlog by the maintainer on 2026-11-04: “the file types to index by their structure, beside tree-sitter and the text chunker”). It builds on R11’s F2 reader (EML / MBOX, the RAG spec §5.3, the backlog’s RAG R11: more formats), which is not built: this spec builds it, and goes past it.

It follows the pattern of the structure of code (T1–T3 as built on exp/0.44-ts2): the structure of a file is kept in the store beside its chunks, a file’s indexing says how it was read, and the model gets tools over the structure beside documents_search. Where code has items and references, mail has messages and threads.

No code is written by this spec; every number below is an estimate unless it says measured, and every claim about a crate or a vendor’s export is from memory and unverified until the work starts.

1. What the user gets

Section titled “1. What the user gets”
  • A mailbox (MBOX), a folder of messages (.eml) or a ticket export (CSV, JSON, JSON lines) added to a collection, by upload or as a folder source (R1’s sync).
  • Threads rebuilt across files: a reply in one .eml and its original in the MBOX are one thread.
  • Fields to filter on: sender, recipients (To, Cc), date, subject, thread, has attachments, answered or not; for tickets also status, priority, assignee, requester, the ticket’s id.
  • Only what each message adds is embedded: quoted replies and signatures dropped, so a thread of twenty messages is not twenty copies of the first.
  • Attachments as documents of their own (a PDF in a message is read by the PDF reader), linked to their message and found with it.
  • Tools for “what did X ask in October” (find_messages), “the whole exchange” (get_thread) and “tickets without an answer” (find_messages with unanswered).
  • The Documents page says “email · MBOX, 340 threads” in the file’s Indexing column.

Non-goals

Section titled “Non-goals”
  • Reading a mail server (IMAP, JMAP, Microsoft Graph, Gmail’s API): files only. A connector is a later item; it would write the same structure.
  • Sending, replying, moving mail: Inga reads.
  • A ticketing system’s API (Zendesk, Jira, Freshdesk): their exports, through one generic mapping (§4), no vendor code.
  • Spam and phishing detection; classification by urgency and department is the email case of ingausecase (§12), done by the chat model, not by the index.
  • The browser page (crates/inga-wasm): it has no folder sync; the reader may build there, but nothing is promised.

2. Inputs

Section titled “2. Inputs”
Format What it is Reader Phase
EML (.eml, RFC 5322 + MIME) one message per file Inga’s MIME reader (§3) E1
MBOX (.mbox, mbox, Thunderbird’s extensionless folders) messages one after the other, each after a From line split on From lines (mboxrd and mboxo quoting undone), then EML E1
Maildir (cur/, new/, tmp/) a folder of EML files without extension the folder sync, names sniffed as EML E1
Ticket export: CSV, JSON, JSON lines a row or object per ticket or per comment the mapping of §4 E3
Outlook MSG (.msg) one message in a Compound File Binary cfb + MAPI properties (§2.1) E4, if approved
Outlook PST / OST a whole mailbox in Outlook’s own database §2.1: not proposed now —

A file is an email by its extension, or by sniffing for files without one (the first lines are Header: value with From: and one of Date:, Message-ID:, Subject:; a From line followed by headers is an MBOX). Sniffing is bounded to the first 8 KiB.

2.1 Outlook: MSG and PST

Section titled “2.1 Outlook: MSG and PST”
  • MSG is feasible in pure Rust. The format is a Compound File Binary (the old Office container) holding MAPI properties as streams (__substg1.0_0037001F the subject, ..._1000001F the body, ..._1013* the HTML body, __recip_version1.0_#N the recipients, __attach_version1.0_#N the attachments). Candidates, all unverified:
    • cfb (MIT, pure Rust, small: a few thousand lines): the container only; the property streams read by Inga (estimate: 400–700 lines). The RAG spec already plans cfb for DOC and MSG (§5.3, F4), so one approval covers both.
    • msg_parser (MIT, on top of cfb): a ready reader; its upkeep and its handling of Unicode against ANSI property types to check.
    • Recommended: cfb plus Inga’s own property reader, as DOCX is Inga’s own reader on its own unzip.
  • PST / OST is a large format (the NDB layer, the LTP heap-on-node and table contexts, the messaging layer; Microsoft’s [MS-PST] is over 200 pages). A pure-Rust crate exists, outlook-pst (published by a Microsoft developer, MIT as far as known; unverified: its licence, its maturity, whether it reads OST and compressible encryption, its size). Not proposed for 0.45.0: the advice is “export the folder as MBOX or EML from Outlook or Thunderbird’s import”, written in the use-case guide; a PST reader is open question 3.

3. Reading a message

Section titled “3. Reading a message”

A new module crates/inga-docs/src/mail.rs (the documents crate, where the other readers are; no engine type in it), hostile input as every reader: bounded headers (256 KiB a message), bounded MIME depth (16), bounded parts (1,000), bounded decoded size (the crate’s MAX_INFLATED).

  • Headers: RFC 5322 folding, RFC 2047 encoded words (=?UTF-8?B?...?=, =?iso-8859-1?Q?...?=), RFC 2231 parameters (filename*=UTF-8''...). Kept: From, Sender, Reply-To, To, Cc, Bcc (when present, as in Sent folders), Date, Subject, Message-ID, In-Reply-To, References, X-Mozilla-Status / Status (read or not, ignored for now), and the list headers (List-Id) as a field.
  • Addresses parsed into {name, address}, the address lowercased, the display name decoded; groups (undisclosed-recipients:;) read as empty.
  • Dates: RFC 5322 dates with their offset, the obsolete zone names (EST, CET read as RFC 5322 says: only the North American ones are defined, the rest as +0000 with a note), stored in UTC with the original offset kept for display. A message without a date takes the MBOX From line’s date, else the file’s mtime, and says so.
  • MIME: multipart/* walked; multipart/alternative takes text/plain when it is real text, else text/html through Inga’s HTML-to-text (inga_docs already has it); an HTML-only message is common (newsletters, Outlook) and goes the HTML way, with its <blockquote> and known quote containers marked for §5.
  • Transfer encodings: base64, quoted-printable, 7bit, 8bit, binary.
  • Charsets: UTF-8 and US-ASCII by hand; ISO-8859-1 / -15 and Windows-1252 by small tables; the rest (ISO-2022-JP, Shift_JIS, GB18030, KOI8-R, …) through encoding_rs (MIT OR Apache-2.0, pure Rust). encoding_rs 0.8.44 is already in Cargo.lock (through ureq and gix-filter); whether it is linked into the release executable today is to check (cargo tree -e normal -i encoding_rs). If it is not, it is a new crate to approve (its tables add about 1–2 MB to the executable: an estimate). A wrong charset label (very common: iso-8859-1 on Windows-1252 text) is read as Windows-1252, as browsers do.
  • TNEF (winmail.dat, Outlook’s rich text in a mail): its attachments listed by name, not unpacked (open question 6).

3.1 Why not a mail crate

Section titled “3.1 Why not a mail crate”
  • mail-parser (Stalwart Labs; Apache-2.0 OR MIT as far as known, pure Rust, no required dependency, its own charset tables behind a feature; unverified): the RAG spec’s §5.3 named it for F2. It is complete (RFC 5322, MIME, 2047, 2231, many charsets) and fuzzed upstream (their claim).
  • mailparse (0BSD; depends on charset, data-encoding, quoted_printable; unverified).
  • The choice proposed: Inga’s own reader, as DOCX, XML, ZIP and PDF are Inga’s own, with encoding_rs for the charsets. The reader is smaller than a general mail library (estimate: 1,200–1,800 lines with its tests’ fixtures apart), and its bounds are Inga’s. mail-parser is the fallback if the fixtures of §11 show the hand-written reader is far behind (open question 2).

4. Tickets: one generic mapping

Section titled “4. Tickets: one generic mapping”

A ticket export is a table (CSV) or a list of objects (JSON, JSON lines), at one of two grains: a row per ticket (the description and maybe the last comment) or a row per comment (a ticket’s id repeated). Inga maps columns to roles, never to a vendor:

Role Meaning Names it recognises by default (case and spaces ignored)
ticket the ticket’s id (a thread) id, ticket, ticket id, key, issue key, number, #
subject its title subject, title, summary
body the text of the row description, body, comment, text, content, message
from who wrote the row requester, reporter, author, from, created by, user
assignee who handles it assignee, agent, owner, assigned to
date when the row was written created, created at, date, submitted, opened
updated its last change updated, updated at, modified, last update
status open, pending, closed… status, state
priority as the tool says it priority, urgency, severity
public a comment the requester sees public, is public, internal (negated)
tags labels tags, labels, components

  • Detection: the header’s names (CSV) or the first object’s keys (JSON; nested keys as a.b, comments[].body for a list of comments inside a ticket) matched to the table; a role found once. A file whose ticket and body roles are not found is read as an ordinary CSV or JSON (the tables item’s reader, beside this one in 0.45.0), and the Indexing column says why.

  • Override: a mapping written by the user, in the source’s settings (the Documents page’s source dialog, inga docs add ... --as tickets --map body=Descrizione,from=Autore) or in a file beside the export, NAME.tickets.toml:

  • Known shapes are data, not code: a small table of presets (column names of common exports: Jira’s CSV, GitHub’s gh issue list --json, Zendesk’s JSON, Redmine’s CSV, osTicket’s CSV, Freshdesk’s CSV) only adds names to the recognised list. Each preset is unverified until checked against a real export, and each one is said in the Indexing column when it matched (“tickets · CSV, 1,204 tickets, columns as Jira’s”).

  • Dates: ISO 8601 and RFC 3339 by default, DD/MM/YYYY and MM/DD/YYYY told apart by a value above 12 in the file, else the mapping’s format, else the collection’s locale (and the Indexing column says the dates were ambiguous).

  • A ticket is a thread; its rows are its messages, with from, date, body; the same structure as mail from here on, so §5–§9 hold for both.

5. Threads, quotes and signatures

Section titled “5. Threads, quotes and signatures”

5.1 Threads

Section titled “5.1 Threads”

Jamie Zawinski’s threading algorithm (the one Netscape, Thunderbird and most clients use; public description at https://www.jwz.org/doc/threading.html), over every message of a collection (not of a file: threads cross files):

  1. Each message’s Message-ID is a node; its References (in order) then In-Reply-To link parents to children, a link never creating a loop.
  2. Messages without any of them, or whose parents are not in the collection, are roots; roots with the same normalised subject are grouped (the fallback):
    • prefixes stripped repeatedly, in the languages of the web UI and the common clients: Re:, RE:, Fw:, Fwd:, R: and I: (Italian Outlook), RIF:, AW: and WG: (German), SV: and VS: (Nordic), TR: (French), RV: (Spanish), Antw:, 回复:, 答复:, 转发:, Ответ:, also with a count (Re[2]:) and list tags ([team] Re:);
    • only within 60 days of each other (a “Report” every month is not one thread);
    • a subject of fewer than 4 characters after stripping is never a fallback key.
  3. A missing Message-ID gets a stable one from the message’s own hash (so the index is stable across syncs).
  4. Duplicates (the same Message-ID in the Inbox and in Sent, or a message saved twice) are kept once, the first file’s copy, its other places listed.

Each thread gets an id (the root’s Message-ID hashed), a subject (the root’s, normalised), its participants, first and last date, message count, and:

  • answered: a thread is unanswered when its last message is not from one of the collection’s own addresses. The own addresses are given (--me a@x.it,b@x.it, the source’s settings) or guessed: the most frequent From of the messages found in a folder named like Sent (Sent, Inviata, Posta inviata, Gesendet, Envoyés, Enviados, …), shown to the user as a guess to confirm. Without own addresses, unanswered means “the last message has no reply”, and the tool says which meaning it used.
  • For tickets: unanswered when the status is not closed and the last public message is from the requester (or, without public, the last message is not from the assignee or an agent); the status mapping of §4 decides “closed” and “waiting”.

5.2 Quoted text

Section titled “5.2 Quoted text”

What each message adds is its text without what it quotes. The rule: drop a quote only when the quoted message is in the index; a quote of a message the collection does not have is kept (it may be the only copy of that text), marked as quoted in the chunk’s meta.

  • Plain text: the > lines at the end or interleaved; the attribution line before them (“On Mon, 3 Oct 2026, Rossi wrote:”, “Il giorno lun 3 ott 2026 alle 10:12 Rossi ha scritto:”, “Am … schrieb …:”, “Le … a écrit :”, “El … escribió:”); Outlook’s blocks (“—–Original Message—–”, “—–Messaggio originale—–”, “From: … Sent: … To: … Subject: …” and its translations “Da: … Inviato: … A: … Oggetto: …”), recognised as a header block of three or more known header names.
  • HTML: <blockquote type="cite">, Gmail’s div.gmail_quote, Outlook’s #divRplyFwdMsg / #appendonsend and the border-top separator of its replies, Apple Mail’s blockquote[type=cite], Thunderbird’s moz-cite-prefix.
  • Forwarded messages (“––––– Forwarded message ———”, “Inizio messaggio inoltrato:”) are not quotes: their text is new to this thread and kept, with the forwarded headers read as a nested message when they parse.
  • Interleaved replies (answers between quoted lines): the quoted lines dropped, a marker […] left so the answer still reads in order; the full text is one get_thread call away (quoted: true).

5.3 Signatures

Section titled “5.3 Signatures”
  • The RFC 3676 delimiter -- (with its space) on its own line: everything after it.
  • Mobile footers (“Sent from my iPhone”, “Inviato da iPhone”, “Von meinem iPhone gesendet”, “Get Outlook for Android”, …): a list in the reader, per language.
  • Without a delimiter: a repeated tail — the same last lines (3–15 of them, after whitespace is normalised) in three or more messages from the same sender is that sender’s signature, learnt per collection, dropped. Legal disclaimers (“This e-mail and any attachments are confidential…”, “Ai sensi del D.Lgs. 196/2003…”) are caught the same way, as the same tail across senders of one domain.
  • A dropped signature’s phone numbers and roles are not lost: the signature of each sender is kept once, in the participant’s entry (§6), so “what is Rossi’s phone number” still has an answer.

Each message records what was dropped (quoted_lines, signature_lines) so the Indexing column and the eval can see it, and so a bad cut can be reported.

6. What the store keeps

Section titled “6. What the store keeps”

The same shape as code’s (T1, rag::code::code_of): the chunks stay in the collection; the structure is in a side collection of the store, mail/NAME, written with the file and removed with it (remove_file, remove_collection).

  • The file’s entry in documents carries meta.mail: {"format": "MBOX" | "EML" | "Maildir" | "MSG" | "tickets-csv" | "tickets-json", "messages", "threads", "attachments", "duplicates", "reader": MAIL_READER (1), "preset"?, "errors": [first 20 messages not read, with why]}.
  • One entry per message in mail/NAME: its text is the subject; its meta: message_id, thread, parent, file (and the byte offset in an MBOX), date (UTC), utc_offset (the original zone), from {name, address}, to, cc, subject, attachments (names, types, sizes, the id of each attachment’s document), quoted_lines, signature_lines, list_id, and for tickets ticket, status, priority, assignee, public, tags.
  • One entry per thread: subject, participants, first and last date, messages, the root, answered, and for tickets status.
  • One entry per participant (an address): names seen, messages from and to, first and last date, the signature learnt.
  • Threads are rebuilt for the whole collection after a sync that changed mail (a message added in one file can join a thread of another); the threads’ and participants’ entries are rewritten, the messages’ entries only when their thread changes. A collection of 50,000 messages rethreads in under a second (estimate: the algorithm is linear with a hash map; to measure).
  • Searchable without the structure: the chunks carry the fields too (below), so documents_search with where works on every client, tools or not.

6.1 Chunks

Section titled “6.1 Chunks”

One chunk per message (more when a message’s new text is over the encoder’s chunk size: cut at paragraphs, as prose), never two messages in one chunk:

  • Heading: Thread: Offer › 2026-10-03 Rossi — the thread’s subject, then the message’s date (in the collection’s time zone) and its sender’s display name (else the address’s local part); for a ticket Ticket 4512: Printer › 2026-10-03 Rossi.
  • Embedded and in BM25: the heading, then a short header block (From: Mario Rossi <m.rossi@example.com> / To: ... / Subject: ... / Attachments: offerta.pdf), then the message’s new text. Addresses go to BM25 as whole tokens and split (m.rossi@example.com → m, rossi, example, com), so “Rossi” finds them.
  • Section (the parent of R2): the thread, so two hits in one short thread bring the whole thread (§5.8 of the RAG spec, its 1,500-token rule).
  • Anchor: Archivio.mbox#msg=<Message-ID>; the citation reads Archivio.mbox › 2026-10-03 Rossi.
  • where keys added to the filter (rag::filter): from, to (To and Cc), participant (any of them), date (the message’s: the filter’s date precision already works, date=2026-10), subject, thread, attachment (a name glob, or attachment=yes), answered=yes|no, list, and for tickets ticket, status, priority, assignee. An address matches by substring of the address or the name, ignoring case (from=rossi).

6.2 Attachments

Section titled “6.2 Attachments”
  • Each attachment of a supported kind (PDF, DOCX, text, Markdown, HTML, and what R11 and the tables item add) becomes a document of its own in the collection, named Archivio.mbox › 2026-10-03 Rossi › offerta.pdf, with meta.parent_message and the message’s from, date and thread copied, so where from=rossi finds the PDF Rossi sent too.
  • Its chunks’ heading starts with the message’s (Thread: Offer › 2026-10-03 Rossi › offerta.pdf › 2 Prices).
  • Inline images and unsupported kinds: listed by name, type and size in the message, not read (images wait for the OCR spec). Nested messages (message/rfc822) are messages of the thread.
  • Bounds: attachments over the reader’s MAX_INPUT (64 MiB) listed and skipped; a ZIP attachment goes through R11’s bomb guard when that exists, else is listed only.
  • The same attachment sent twice (the same bytes’ SHA-256) is indexed once, its other messages listed.

7. Tools for the model

Section titled “7. Tools for the model”

Offered with the document tools (doctools::offered, doctools::is_tool) when a named collection holds mail or tickets, in the chat APIs, inga run and Inga’s MCP server (as the code tools are, with collection required over MCP). Results numbered as sources, bounded like the document tools’ (SEARCH_K, READ_CHARS).

  • find_messages — the structured query, no embedding needed:
    • parameters: collection, query (optional: text ranked by the hybrid search within the matches), from, to, participant, after, before (dates, the filter’s precision: 2026-10), subject, has_attachment (bool or a name glob), unanswered (bool), thread, limit (default 20), and for tickets status, priority, assignee;
    • answers: per message the thread’s subject, date, from, to, a 200-character excerpt of its new text, its attachments, answered, the anchor to cite; or, with group: "thread", one line per thread (subject, participants, dates, count, last sender, answered);
    • “What did Rossi ask in October?” is find_messages(from: "rossi", after: "2026-10", before: "2026-11") and a reading of the excerpts; “tickets without an answer” is find_messages(unanswered: true, group: "thread").
  • get_thread — collection, thread (an id, or a message’s anchor), quoted (default false): the messages in order, each with its header block and new text, bounded to READ_CHARS (the oldest messages summarised to their header and first lines when the thread is longer, said so).
  • documents_search keeps working, with the where keys of §6.1; document_read of a mailbox reads one message by its anchor.
  • Each answer says the meaning of unanswered it used (own addresses given, guessed, or none) and how many messages were read.

8. Privacy

Section titled “8. Privacy”

Mail is the most personal data a collection can hold: addresses, names, signatures with phone numbers, health and pay matters in an HR mailbox. Email addresses are personal data under the GDPR (art. 4(1)); a mailbox may also hold special categories (art. 9). Inga runs locally; this spec keeps it so, and says so.

  • Local only: the mailbox, its index and its attachments stay in the store on this machine (~/.cache/inga/store/..., deleted with the collection, listed in the local data view). No telemetry, no error report with an address in it (the redaction of one step from the project gains a rule for addresses: m.rossi@example.com → <email>).
  • A collection holding mail is marked personal (meta.personal: true on the collection, set by the reader). Its tools and its search results are not sent to a remote model (an API node, state.is_remote): the chat says “this collection holds mail; it is not sent to remote models” and the request goes on without it, unless the collection’s owner turns on “allow remote models” for it, with the provider named in the warning. Today the document tools serve API nodes’ models too (doctools.rs); this is the one change to that.
  • The Documents page shows addresses only locally: the page served to the loopback address shows them; served to another address (the LAN, the web UI’s remote mode) it shows display names and masked addresses (m•••@example.com) unless the viewer is an admin of U1’s logins (when that ships). The API (GET /api/inga/documents/mail) does the same masking, by the request’s address; the model’s tools read the full text (they run here).
  • Logs: the sync’s lines name files and counts, never addresses or subjects.
  • Forgetting: removing a message from the mailbox and syncing removes it, its chunks, its attachments’ documents and its participant’s counts; a participant with no message left is deleted.
  • MCP: the mail tools are listed to MCP clients only with an API key (the server’s rule for the memory service) and only for collections the key may read.

9. Surfaces

Section titled “9. Surfaces”
  • Documents page (js/documents.js, i18n/documents.json):
    • the Indexing column: {"method": "email", "format": "MBOX", "threads": 340, "messages": 2112, "attachments": 87} read “email · MBOX, 340 threads” (the tip: the messages, attachments, duplicates, the own addresses used, the messages not read and why); tickets: “tickets · CSV, 1,204 tickets” (the preset or mapping in the tip); an attachment: “attachment of Archivio.mbox › 2026-10-03 Rossi”;
    • the state column as today (indexed, outdated with why: "mail" when MAIL_READER changes, queued, indexing);
    • a Threads view of a mail collection: threads by last date, filters (from, to, dates, has attachment, unanswered), a thread opened as a conversation; the “own addresses” box (given or guessed) on the collection;
    • a citation Archivio.mbox › 2026-10-03 Rossi opens that message in the thread view.
  • HTTP: GET /api/inga/documents/mail?collection=C (the status: formats, counts, own addresses), &threads=1 with the filters of find_messages as query parameters, &thread=ID, &message=ANCHOR; PUT /api/inga/documents/sources/{id} gains mail: {me: [...]} and tickets: {map: {...}}. In docs/api/inga.yaml.
  • CLI: inga docs add C FILE --as tickets [--map role=column,...], --me ADDR,...; inga docs threads C [--from X] [--to X] [--after D] [--before D] [--unanswered] [--attachments] [--json]; inga docs thread C ID [--quoted]; inga docs status --files shows the Indexing line.
  • MCP: find_messages and get_thread on /mcp and inga mcp serve, as in §7.
  • Docs: a use-case guide, docs/use-cases/search-your-email.md (export from Thunderbird, Outlook, Gmail’s Takeout as MBOX; the own addresses; privacy; the tools; what is not read), and the RAG guide’s formats table.

10. i18n

Section titled “10. i18n”
  • Web UI: every new string in crates/inga-server/webui/i18n/documents.json, ten languages (en, it, fr, de, es, zh, pt, ru, ja, hi), checked by tests/webui/i18n.rs.
  • The reader’s language tables (subject prefixes, attribution lines, Outlook’s header blocks, mobile footers, Sent folder names, ticket column names): one table per kind in mail.rs, with at least en, it, fr, de, es, pt, nl, the Nordic languages, ru, zh, ja. Each entry is tested by a fixture line; a missing language means a quote kept, never text lost.
  • Dates in headings in the collection’s locale order (ISO 2026-10-03 by default, as the heading in the item says), times in the collection’s time zone (the server’s, or the source’s setting).

11. Tests

Section titled “11. Tests”

Fixtures written by hand in crates/inga-docs/tests/fixtures/mail/ (people and companies invented, as ingausecase’s), each with its expected structure as a golden JSON file (INGA_BLESS=1, read by hand):

  • Threading: a thread whose middle message is missing (the parent known only through References); In-Reply-To without References (old clients); a reply with a changed subject; two unrelated monthly “Report” threads 30 days apart (grouped) and 90 days apart (not); a References loop; a duplicate in Inbox and Sent; a message without Message-ID; a thread across an MBOX and two .eml files.
  • Encodings: RFC 2047 subjects in UTF-8 B and ISO-8859-1 Q, split across folded lines; RFC 2231 filenames; a Windows-1252 body labelled ISO-8859-1 (the “€” and the quotes); ISO-2022-JP; quoted-printable with soft breaks; a base64 body with CRLF; 8bit without a declared charset; a malformed encoded word kept as typed.
  • HTML: an HTML-only message (Outlook’s), a Gmail reply with gmail_quote, an Apple Mail blockquote type=cite, a newsletter with tables; the text compared.
  • Quotes and signatures: bottom posting, top posting with Outlook’s Italian header block, interleaved answers, a forward (kept), a quote of a message not in the index (kept), -- signatures, a repeated signature without delimiter (learnt after three messages), a disclaimer across a domain.
  • MBOX: From lines quoted mboxrd-style (>From ) and mboxo-style, a body line starting From that is not a separator, CRLF files, a truncated last message.
  • Attachments: a PDF and a DOCX indexed as their own documents with the message’s fields; an inline image listed only; a message/rfc822; the same attachment twice; an attachment over the size limit.
  • Tickets: a CSV per ticket and one per comment, a JSON with nested comments, a JSON-lines file, Italian column names with the .tickets.toml mapping, ambiguous dates, the status mapping and unanswered.
  • Hostile input: MIME nested 100 deep, 10,000 parts, a header of 10 MB, a base64 bomb (small input, the bound reached), invalid UTF-8 everywhere: bounded errors, no panic (AGENTS.md: no unwrap() reachable from files). A fuzz target for mail.rs in the nightly job, as tree-sitter’s spec plans.
  • Engine and server: the store’s mail/NAME entries replaced on change and removed with the file; rethreading after a new file; where from=..., date=2026-10; find_messages and get_thread (crates/inga-server), the MCP listing, the masking of addresses for a non-loopback request, the refusal to send a personal collection to a remote model; inga docs threads end to end (tests/cli/docs.rs); the Documents page’s Indexing text (tests/webui/).

12. Measurement: ingausecase’s email case

Section titled “12. Measurement: ingausecase’s email case”

The case today (cases/email, read 2026-11-04): 40 synthetic Italian messages (messaggi.json: testo, urgenza, reparto), classified one by one with structured output by qwen3-4b; the score is the mean of the urgency and department accuracies. It measures triage by the chat model, not retrieval, and needs no index: it stays as it is.

A second part, email-archivio (a new case beside it, so the first’s history is not broken), sketched here and written in ingausecase when E2 is built:

  • Data: a mailbox generated once and committed (archivio.mbox, fixed): the 40 messages of messaggi.json as first messages of threads, from invented senders, dated September–November 2026; replies written by hand for about 25 of them (some top-posted with Outlook’s Italian block, some bottom-posted, a few HTML-only), 5 forwards, 8 attachments (PDF offers, a DOCX contract), 3 duplicates, 2 threads whose subject changed, a signature with a disclaimer. About 120 messages. A JSON file of the expected threads (thread per Message-ID) and of the answered ones.
  • Questions (domande.json, 30, with expected answers and the message ids that support them): by sender and month (“cosa ha chiesto Marco del magazzino in ottobre?”), unanswered (“quali richieste non hanno ancora risposta?”: a set, scored by precision and recall), by attachment (“chi ha mandato un’offerta in PDF?”), by thread (“com’è finita la contestazione dell’ordine 45821?”), and five whose answer is only in a quoted part of a message whose original is missing (the “keep a quote we do not have” rule).
  • Runs: the same model (qwen3-4b, then qwen3-8b) in three modes: (a) the mailbox read as plain text (today’s behaviour if the file is renamed .txt); (b) the structured index with documents_search only; (c) with find_messages and get_thread.
  • Scores: the threads rebuilt against the expected ones (pairwise F1 over message pairs); the unanswered set (precision, recall); answers judged against the expected ones (exact for sets and names, the judge of inga eval for prose) and cited messages against the supporting ids (recall@5); prompt and completion tokens per question.
  • The bar, an estimate to confirm with the first run: (c) at least 15 points over (a) on the answers, threads F1 ≥ 0.95, unanswered recall ≥ 0.9.

13. Phases

Section titled “13. Phases”
  1. E1 (M): read mail. mail.rs (EML, MBOX, Maildir; headers, MIME, encodings, HTML-only), the charset decision (§3), per-message chunks with headings and the header block, meta.mail on the file, the Indexing column, the fixtures of §11. Without threads, quotes are kept: usable on its own (R11’s F2 done).
  2. E2 (M): the structure. Threading over the collection, quotes and signatures, attachments as documents, mail/NAME, the where keys, find_messages and get_thread in the APIs, inga run and MCP, the privacy rules of §8, inga docs threads; ingausecase’s email-archivio run.
  3. E3 (S–M): tickets. The mapping, its detection and override, the presets as data, unanswered by status.
  4. E4 (S–M), if approved: Outlook MSG through cfb; TNEF’s attachments; then the web UI’s Threads view if E2 left it.

Each phase usable on its own, as AGENTS.md asks of a release’s items. Effort labels are estimates.

14. Decisions of the maintainer (2026-11-05)

Section titled “14. Decisions of the maintainer (2026-11-05)”

The maintainer accepted every proposal (“ok, vanno bene tutte”):

  1. encoding_rs as a direct dependency of inga-docs (if it is not in the executable already) for the charsets beyond Latin-1 and Windows-1252.
  2. Inga’s own MIME reader, not mail-parser.
  3. Outlook: MSG through cfb in 0.45.0 (E4); no PST reader (“export as MBOX”).
  4. Privacy: a mail collection is never sent to remote models unless allowed per collection; transcripts (the sibling spec) follow the same rule.
  5. Addresses masked on a page served to another address than the loopback, until U1’s logins.
  6. TNEF (winmail.dat): listed only.
  7. The own addresses guessed from a Sent folder and confirmed by the user.
  8. The email-archivio case written in ingausecase now, before E2, its plain-text baseline measured on 0.44.0.
