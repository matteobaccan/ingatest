Structured index: tables kept as tables, and a tool that queries them

Status: approved by the maintainer on 2026-11-05 (§15); for 0.45.0 (the item “Structured index: tables” of docs/todo/0.45.0.md, moved from the backlog by the maintainer on 2026-11-04). Nothing built.

It follows the pattern of the tree-sitter spec: a file’s structure kept in the store beside its chunks, tools for the model over that structure, and what became of each file said in the Documents page (the State and Indexing columns built in 0.44.0). It takes the spreadsheet part of R11’s F1 (the RAG spec §5.3: “CSV; XLSX / XLS / ODS: rows as records, sheet as page; calamine”) and goes further: rows are not only text to embed, they are a table to filter, sum and group. The tables inside PDFs join later, through the layout spec (§10); OCR and layout are not designed here.

Figures marked (estimate) are guesses to be measured; facts marked (unverified) were not checked against a source on 2026-11-04.

1. Why

Section titled “1. Why”

A question over a spreadsheet is rarely “which passage is closest”. It is “how much did Rossi Srl spend in 2025”, “how many orders in March from Bergamo”, “which agent sold the most in the second quarter”. Today:

  • CSV is read as plain text (inga_docs::detect finds it text, Kind::Text), cut into chunks of paragraphs: a CSV has no blank lines, so a chunk is a run of rows without their header, and a sum needs every row in the prompt.
  • XLSX and ODS are refused (“a ZIP archive that is not a DOCX file”, crates/inga-docs/src/lib.rs unsupported); XLS too (“the old Office format”).
  • Tables in DOCX and HTML become lines with cells joined by | (docx.rs, text.rs): readable, not queryable.
  • A local model of 4B parameters cannot add 12 400 numbers it reads in excerpts, and even a large one should not: the answer must be exact and must say which rows it came from.

Every desktop RAG app in the survey of the RAG spec §5.3 reads CSV and XLSX as text (Jan with calamine, AnythingLLM, Open WebUI, PrivateGPT). None of them, as far as the survey read, queries the rows (unverified for the apps read from search results only).

2. Goal

Section titled “2. Goal”
  • Formats: CSV and TSV (any delimiter, the common encodings), XLSX (Excel, LibreOffice, Google Sheets’ and Numbers’ exports), ODS; the tables of DOCX and HTML files (§10, T4); the tables of PDFs after the layout item (§10).
  • Each table’s schema (columns, types, units, header rows, totals rows, what was guessed) and its rows, kept in the store beside the file’s chunks, replaced with the file and removed with it.
  • Chunks still made for semantic search: a schema chunk per table, its rows in groups, the values of its text columns (§5), so documents_search and the context mode find the table and small lookups keep working without tools.
  • Two tools for the model, beside the document tools: table_schema and query_table (filters, count, sum, average, min, max, distinct count, groups, sorting), read-only, bounded, each result a numbered source that cites file, sheet and rows (§6).
  • The Documents page says per file: table · XLSX, 3 sheets, 12 400 rows, with the sheets, the guesses and the warnings as its tooltip and a Schema view (§8).
  • The same tools in the chat APIs, inga run, Inga’s MCP server, the CLI and the HTTP API (§7).

Non-goals

Section titled “Non-goals”
  • No SQL text from the model run by an engine, and nothing that reaches the filesystem: the query is a small JSON shape Inga evaluates itself (§6.3, §11).
  • No formulas evaluated: a cell’s value is the one the spreadsheet saved.
  • No joins between tables in the first version (open question 6).
  • No editing: the tools read; a table changes only when its file does.
  • No OCR, no layout: PDF tables wait for the layout item (§10).
  • XLS (BIFF), XLSB, Numbers’ own format, Parquet: not in the first version (§3.1, open question 3).

3. Formats and detection

Section titled “3. Formats and detection”

3.1 What is read, and by what

Section titled “3.1 What is read, and by what”
Format Detected by Reader Notes
CSV, TSV extension .csv, .tsv, .tab, or text whose first lines split into the same number of fields (≥ 2) by one delimiter Inga’s own, in inga-docs (§3.2) the delimiter sniffed among , ; \t |; Excel’s sep=; first line honoured
XLSX, XLSM ZIP with xl/workbook.xml Inga’s own: the ZIP reader and XML tokenizer inga-docs already has (zip.rs, xml.rs) macros (.xlsm) never read
ODS ZIP with mimetype = application/vnd.oasis.opendocument.spreadsheet Inga’s own, the same ZIP and XML pieces content.xml only
XLS (BIFF8) the OLE header D0 CF 11 E0 and a Workbook stream not in v1: refused as today, “save it as XLSX” calamine reads it (open question 3)
DOCX, HTML tables the existing readers the existing readers, emitting cells (T4)
PDF tables the layout item §10

Everything stays under inga-docs’ existing bounds (MAX_INPUT 64 MiB, MAX_INFLATED 256 MiB for every ZIP entry together, the ZIP bomb guard) plus the table limits of §4.4.

3.2 Text: encodings and dialects

Section titled “3.2 Text: encodings and dialects”
  • Encoding: UTF-8 (a byte-order mark dropped), UTF-16 after its mark (Excel’s “Unicode text” export is UTF-16 with tabs), else Windows-1252 when the bytes are not valid UTF-8 (Italian Excel’s CSV: Quantità in 1252). Today’s text::decode replaces invalid bytes; a 128-entry table for 1252’s upper half is enough, no crate.
  • Delimiter: the one among , ; \t | that gives the same field count (≥ 2) on most of the first 50 records, quotes respected. ; with comma decimals is the norm of Italian, German and French exports.
  • Quotes: RFC 4180 ("" inside quotes, line breaks inside quoted fields); a malformed quote ends at the line’s end and is counted as a warning, never an error.

3.3 The header row, title rows and regions

Section titled “3.3 The header row, title rows and regions”

For each sheet (a CSV is one sheet):

  1. Regions. Non-empty cells are grouped into rectangles separated by at least two empty rows or one empty column: a sheet with a summary block beside the data gives two tables, Ordini and Ordini (2). A single non-empty cell, or a region of one row, is not a table: it is text (a note), kept as text in the chunks.
  2. Title rows. Rows above the header with one non-empty cell (or one cell merged across the region) are the table’s caption (Vendite 2025 — dati provvisori), kept in the schema and the schema chunk.
  3. Header. Within the region’s first 20 rows, the first row whose cells are mostly non-empty text and below which at least one column changes type (text above, numbers or dates below). Multi-row headers: consecutive text rows above the body where the upper ones have merged or blank cells are joined with › (2025 › Aprile).
  4. No header found (every row of the same types): the columns are named by their letters, as the spreadsheet shows them (A, B, C), and the schema says “no header row: columns named by letter”.
  5. Names are trimmed and kept as written; duplicates get (2); an empty header cell over a filled column is named by its letter.

3.4 Types

Section titled “3.4 Types”

Per column, over its non-empty body cells. A column is of a type when at least 95 % of them read as that type (threshold to tune on the fixtures); the rest stay as their text and are counted (3 cells are not numbers: "n.d.", "-", "circa 20").

Type Kept as Read from
integer i64 XLSX numbers without decimals; CSV 1234, 1.234 / 1,234 per the column’s locale
decimal(s) i64 scaled by 10^s, s ≤ 6 numbers with at most 6 decimals: sums exact to the cent
number f64 the rest (scientific notation, many decimals)
percent decimal of the fraction XLSX % formats, ODS percentage, CSV 20%, 20 %
date, datetime days, seconds since 1970 XLSX serials with a date format (built-in ids 14–22, 45–47, custom ones with d, m, y), the workbook’s 1904 flag; ODS date-value; CSV ISO, dd/mm/yyyy, dd.mm.yyyy, mm/dd/yyyy
time, duration seconds h:mm, ODS time-value
boolean bit XLSX t="b", TRUE/FALSE, sì/no, yes/no
text dictionary index everything else
  • Empty values: "", -, —, n.d., N/A, NA, null, #N/A and the other spreadsheet errors (#DIV/0!, #VALUE!) are null; errors are counted apart.
  • Number locale per column: 1.234,56 and 1,234.56 are told apart by the column’s values (a comma followed by one or two digits, a dot every three digits) and by the delimiter (; suggests comma decimals). A column where both readings stay possible (1.234 alone) is read as the file’s other columns are, and the schema says “ambiguous: read as 1234”.
  • Date order: dd/mm and mm/dd are told apart by a value above 12 in either place; when no value decides, day first (the order of most of Inga’s languages), and the schema says “ambiguous day and month order: read day first”.
  • XLSX’s typed cells (t="n", s, str, inlineStr, b, e, d) are trusted over guessing; a text cell that holds a number ('00123, a code) stays text when the column is mostly text (product codes keep their leading zeros).

3.5 Units

Section titled “3.5 Units”
  • From the header: Importo (€), Peso [kg], Prezzo EUR, Sconto %, Durata (h).
  • From the cell format: XLSX number formats with a currency symbol or %, ODS office:currency.
  • From the cells: 12 kg, € 1.200,00, 1.200,00 € (the same unit on 95 % of the column), the number kept and the unit moved to the schema.
  • Never converted: two currencies in one column make it text with a warning; a sum is in the column’s unit and the result says it.

3.6 Merged, hidden, formulas, totals

Section titled “3.6 Merged, hidden, formulas, totals”
  • Merged cells (XLSX <mergeCells>, ODS number-columns-spanned / number-rows-spanned and covered cells): in a header, the merged name heads each column under it (§3.3’s ›); in the body, a vertical merge fills its value down to every row it covers (a region name over its rows), and the schema says which columns were filled; a horizontal merge keeps the value in its first column.
  • Hidden sheets, rows and columns are read (they are data) and marked hidden in the schema; table_schema says so. (Open question 5.)
  • Formulas: the cached value the file saved; a formula cell without one (a file written by a program that does not compute) is null and counted (“12 formulas without a saved value”).
  • Totals rows: a row whose first text cell starts with Totale, Totali, Total, Subtotale, Subtotal, Somma, Sum, Gesamt, Summe (a list per language of the web UI), or whose numeric cells are XLSX formulas SUM(...) over the column above, is a totals row: kept, shown in the schema with its values, and left out of queries unless the call asks for it (include_totals), so a sum never counts the total twice.

3.7 Very large files

Section titled “3.7 Very large files”
  • Inside inga-docs’ 64 MiB input and 256 MiB inflated: a sheet’s XML is tokenized as it is inflated today, rows written to the table as they come; nothing holds the whole DOM.
  • Limits (§4.4): beyond them the table is cut, never refused, and the cut is said in the schema, the Indexing column and every query result (“the first 1 000 000 rows of 1 312 004 were kept”).
  • An XLSX <dimension ref="A1:XFD1048576"> is not trusted for allocation; ODS’s number-columns-repeated / number-rows-repeated (LibreOffice writes 16384 repeated empty columns) are expanded only for non-empty cells and within the cell budget.
  • The sync reads at low priority as today (priority.rs); speed is to be measured (a 12 400-row XLSX read in well under a second (estimate)).

4. The table store

Section titled “4. The table store”

4.1 Where

Section titled “4.1 Where”

The store (store.rs) is one JSON-lines file replayed into memory, with texts of at most 4 000 bytes (MAX_ENTRY_BYTES): right for schemas, wrong for a million rows. So, as code keeps its tables in the collection code/NAME:

  • The schema is a store entry per table in the collection tables/NAME (rag::table::table_of): its name (vendite.xlsx › Ordini) as the text, the schema in meta (columns with type, unit, nulls, distinct count, min / max, a few examples; header and title rows; totals rows; warnings; the source file’s id and sha256; the reader’s version TABLE_READER). Listing a collection’s tables reads only these entries.
  • The rows are in one file per table beside the store, store/tables/<entry id>.itab, written once by the sync and replaced with the file. The Local data list (D2) counts them under the documents; remove_file and remove_collection delete them with the entries.

4.2 The rows file (.itab, version 1)

Section titled “4.2 The rows file (.itab, version 1)”

A columnar file, small and simple, written and read by Inga only:

  • a magic INGATAB1, a JSON header (the schema’s column order, the row count, the reader’s version);
  • per column a null bitmap and its values: i64 (integer, decimal, dates, times), f64 (number), a bitmap (boolean), u32 indexes into the column’s dictionary of strings (text);
  • the source row numbers (u32 per row): the row numbers the spreadsheet shows (a CSV’s line numbers, header on line 1), for citations.

Read whole into memory on a table’s first query and kept in an LRU cache bounded in bytes (docs.table_cache_mb, default 256 (estimate)); a 12 400 × 9 table is well under 1 MB (estimate). A memory map (memmap2, already used for models) only if the measures ask for it. No database crate (§11).

4.3 When it changes

Section titled “4.3 When it changes”
  • Folders: the sync of RAG R1 reads a changed file again; a file indexed before tables existed (a CSV cut as text) or by an older TABLE_READER is outdated (why: "table", as why: "code" today) and read again by the next sync; its unchanged chunks keep their vectors.
  • Uploads are read as tables too (unlike code, which only a folder’s sync parses: no child process here, the readers are pure Rust in the server’s process like the PDF reader). An upload indexed before is outdated with “upload it again”.

5. Chunks for semantic search

Section titled “5. Chunks for semantic search”

The table store does not replace the chunks: a question still has to find the table, and the context mode (the default, DocumentsMode::Context) has no tools. Each table gives:

  1. A schema chunk: vendite.xlsx › Ordini — 12 400 rows (rows 4–12 403), header row 3; caption "Vendite 2025"; columns: Data (date, 2024-01-02 … 2025-12-30), Cliente (text, 312 values, e.g. Rossi Srl, Bianchi SpA), Importo (decimal, €, 12.50 … 98 000.00), …; totals row 12 404. Its section is the table, so the whole-section rule of the fusion can bring it with its rows.
  2. Row groups: each row as Row 57 — Data: 2025-03-04; Cliente: Rossi Srl; Importo (€): 1200.00; … (the header repeated in every row: a small encoder embeds “Cliente: Rossi Srl” better than a bare cell (estimate, to be measured in the case of §12)), rows grouped up to the encoder’s chunk size, the heading path vendite.xlsx › Ordini › rows 57–80. Only the first docs.table_rows_indexed rows of a file are cut into chunks (default 20 000 (estimate: about 1 000 chunks to embed)); the rest are reached by query_table only, and the schema chunk says so.
  3. Value chunks: for each text column with at most 1 000 distinct values, one chunk listing them (vendite.xlsx › Ordini › Cliente: Rossi Srl, Bianchi SpA, …), so BM25 and the vectors find “Rossi Srl” even in rows past the cap.

A small table (the whole file within a third of the context, today’s rule in documents.rs) goes into the prompt whole, as a Markdown table with its header: no tool needed. document_read on a table file reads this same text, as it reads any file from its chunks (rag/read.rs). The file’s kind is CSV, XLSX or ODS; its pages are its sheets (a citation’s “page 2” is said “sheet 2, Clienti”).

6. The tools for the model

Section titled “6. The tools for the model”

6.1 When they are offered

Section titled “6.1 When they are offered”

Like the code tools (codetools.rs): they join the document tools in doctools::offered when a named collection holds tables (rag::table::holds_tables), counted with them per round (CALLS_PER_ROUND), named in doctools::ALL_TOOLS. The reference is the permission, as for the document tools: a call sees the tables of the collections the prompt names and no other.

In the default context mode the model gets excerpts and no tools. A question that needs a sum is then answered from rows in excerpts, which is the problem of §1. Proposal: when a named collection holds tables and the model’s template takes tools, the two table tools are offered beside the excerpts in context mode too (open question 1).

6.2 table_schema

Section titled “6.2 table_schema”
  • Without table: the tables of the named collections (name, rows, columns, caption), at most 50.
  • With table: its schema as §4.1 keeps it, its first five rows, its totals rows, its warnings and guesses (ambiguous dates, filled merges, cut rows), and the line “Row numbers are the spreadsheet’s own”.
  • A table may be given as its name, its file alone when the file has one table, or the n of a previous result; an ambiguous one is refused with the candidates.

6.3 query_table

Section titled “6.3 query_table”
  • where: conditions joined by AND; op one of =, !=, <, <=, >, >=, between, in, contains, starts_with, is_null, not_null. Text compares without case and accents (= after trimming); dates as ISO strings; numbers as JSON numbers in the column’s unit. OR only through in (open question 7).
  • select: the columns of the rows listed, when nothing is aggregated (default: all, cut by the result’s size).
  • group_by: columns, or a date column by year, quarter, month, day.
  • aggregate: count, count_distinct, sum, avg, min, max; on a decimal column, sum and avg are exact (§3.4) and rounded to the column’s scale (avg to two more places).
  • order_by: a column or an aggregate’s name, desc; limit: default 20, at most 50.
  • include_totals: false by default (§3.6).
  • Column names are matched without case and accents, and by their name before a unit (Importo finds Importo (€)); an unknown column is refused with the table’s columns and the closest one (“no column Imorto: did you mean Importo (€)?”), so the model can retry in the same round.

6.4 The result

Section titled “6.4 The result”
  • Numbers without thousands separators, a dot for decimals, the unit in the header: unambiguous for the model, whatever the file’s locale.
  • A source per call, numbered with the document tools’ and web_search’s ([n], one number per file); inga_sources gains sheet, rows (up to 20 ranges, then a count) and the query, so the web UI’s source chip says “vendite.xlsx › Ordini, 214 rows” and opens the rows.
  • Bounds: RESULT_CHARS (8 000) per result, at most 50 rows or groups shown and 1 000 cells; at most 100 000 groups computed (beyond: “too many groups: add a filter or a coarser by”); 2 s per call (GREP_TIME’s), checked every 65 536 rows; the answer says when any bound cut it.
  • Every result restates the filter as applied, the rows matched of the total, the totals rows left out and the table’s cut (§3.7): the model can say what its number covers.

6.5 Safety

Section titled “6.5 Safety”
  • No SQL, no paths: the query is the JSON of §6.3, checked against a schema and evaluated by Inga’s own code over the rows file; a table is named among the store’s tables of the collections the prompt names, never by a path; nothing in a query reaches the filesystem, a network or a program.
  • Read-only: no tool writes a table; a table changes only with its file.
  • Bounded CPU and memory: §6.4’s limits per call, CALLS_PER_ROUND per round, the table cache’s budget (§4.2); a query is a scan with a fixed set of operators, no recursion, no user-defined functions, no regular expressions (contains is a substring).
  • Cells are data: a cell that says “ignore your instructions” reaches the model in a tool result, as a document’s text does today; nothing in a cell is run. A cell starting with = is shown as text (no formula, here or in any export of results, open question 8).
  • Hostile files: the readers keep inga-docs’ rules (no unwrap on input, bounded inflation, depth limits) and §4.4’s limits; fuzz targets on the three readers (T0).

7. Surfaces

Section titled “7. Surfaces”

10. Tables inside documents: DOCX and HTML in T4, PDF after the layout item

Section titled “10. Tables inside documents: DOCX and HTML in T4, PDF after the layout item”

All readers emit the same thing, an inga_docs::Table (a grid of cells with their spans, their text or typed value, a header guess, a page or sheet, a caption), and everything after it (types, units, the store, the chunks, the tools) is shared:

  • DOCX and HTML (T4, this release): docx.rs already walks w:tbl / w:tr / w:tc and the HTML reader <table>; they emit their grids (w:gridSpan, w:vMerge, colspan, rowspan) as tables beside today’s | text. Tables of fewer than two body rows stay text only (a layout table).
  • PDF (after the layout item): the layout spec’s TableFormer (§4.4 there) gives rows, columns and spans; its assembler (§4.6 there) emits an inga_docs::Table with the page and the table’s caption instead of only a Markdown table. Until then a PDF’s tables are text, and contratti’s questions about them are answered from excerpts (§12).
  • Citations of such tables are Contract.pdf, page 12, table 2, row 4.

11. Dependencies: own readers and an own query, not a database

Section titled “11. Dependencies: own readers and an own query, not a database”

AGENTS.md: new crates must be justified, statically linked and pure Rust, each approved by the maintainer. Checked on crates.io on 2026-11-04 (versions, licences and the direct dependencies of the latest version; sizes are estimates):

Candidate Version, licence Direct dependencies Brings Cost
Own readers (CSV, XLSX, ODS) — none new (zip.rs, xml.rs, miniz_oxide already there) exactly what §3 needs, Inga’s bounds about 1 500–2 000 lines with tests (estimate); binary +0.1–0.3 MB (estimate)
csv 1.4.0, Unlicense / MIT csv-core, itoa, ryu, serde_core a fast RFC 4180 reader small; sniffing and encodings are still Inga’s
calamine 0.38.0, MIT quick-xml, zip, encoding_rs, codepage, byteorder, atoi_simd, fast-float2, log, serde (chrono optional) XLSX, XLSM, XLSB, XLS, ODS quick-xml, zip and codepage are new to Cargo.lock; a second ZIP reader beside Inga’s; +0.5–1.5 MB (estimate)
sqlparser 0.63.0, Apache-2.0 (parser only) SQL text → an AST still needs an executor

Proposal:

  • Own readers for CSV, XLSX and ODS in inga-docs: Inga already has a hardened ZIP reader, an XML tokenizer and the inflation budget, and needs a reader that follows its limits and reports its guesses; XLSX’s and ODS’s parts read are few (workbook.xml, sharedStrings.xml, styles.xml’s number formats, the sheets; content.xml). calamine stays the fallback if the own XLSX reader proves fragile on real files, and the candidate for XLS (open question 3).
  • An own query evaluator over the columnar rows (§6.3): a filter, a hash group-by and an aggregate over at most a million rows are a few hundred lines (estimate), every bound under Inga’s control, nothing that could reach a file. An SQL engine would bring joins, sub-queries and functions Inga would have to fence off again, megabytes of binary, and, for the SQLite rewrite, a dynamic-library loader. If §12’s numbers show that local models write SQL better than §6.3’s JSON, a SELECT subset can be parsed (own parser, or sqlparser) into the same plan, with no new executor (open question 2).

Section titled “13. Tests”
  • Readers (inga-docs): fixtures written by the tests themselves (a stored-ZIP XLSX and ODS writer in the test helpers, so each case is a few lines: merged headers, a 1904 workbook, shared and inline strings, a hidden sheet, a formula without a value, error cells, 16384 repeated columns), plus a few real files saved by Excel, LibreOffice Calc, Google Sheets and Numbers (small, checked in under crates/inga-docs/tests/fixtures/tables/), each with a golden schema JSON written with INGA_BLESS=1 and read by hand, as the code tags’ golden files.

15. Decisions of the maintainer (2026-11-05)

Section titled “15. Decisions of the maintainer (2026-11-05)”

The maintainer accepted every proposal (“ok, vanno bene tutte”):

  1. Context mode: table_schema and query_table are offered beside the excerpts in the default context mode when a named collection holds tables and the model takes tools, not only in tool mode.
  2. The query’s shape: §6.3’s JSON only; an SQL SELECT subset only if fogli shows local models write SQL better. No SQL engine.
  3. XLS (BIFF8): refused with “save it as XLSX”, as today.
  4. Own XLSX / ODS / CSV readers, no calamine nor csv.
  5. Hidden sheets, rows and columns: read and queried, marked hidden.
  6. Joins: none in v1; a single equal-key join to weigh after T2.
  7. OR conditions: only in.
  8. Exports: out of scope.
  9. Limits: §4.4’s figures as the start, revised once measured.
  10. The structured index family: one shape shared with the email and tickets spec (a collection KIND/NAME of store entries, a rows file beside the store, a method in indexing), aligned between the two specs.
