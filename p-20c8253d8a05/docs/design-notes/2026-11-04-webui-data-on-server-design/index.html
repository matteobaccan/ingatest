The web UI's data on the server, the page's settings in the browser

Status: built on 2026-11-04 in exp/0.44 for 0.44.0, as written here (decided by the maintainer on 2026-11-02, in place of the chats in IndexedDB; no migration from the browser, the maintainer’s decision); planned in docs/todo/0.44.0.md.

1. The problem today

Section titled “1. The problem today”

Everything the web UI remembers lives in the browser’s localStorage for the page’s address, under inga.* keys (store.get / store.set of js/shell.js): the chats with their pictures as data: URLs, but also the sampling settings, the presets, the prompt being written on the Images page, which project is open, the opt-ins the user accepted. Three costs:

  • about 5 MiB is all a browser gives a page (MDN, “Storage quotas and eviction criteria”, read 2026-10-30): a few pictures fill it, and the chats are no longer saved (0.42.0 added the bar that says so and Delete pictures, spec 2026-10-30-one-step-from-the-project-design.md, R5 step 1);
  • one browser, one profile: the same server opened from the phone and from the PC shows two different sets of chats; clearing the browser’s site data deletes them all;
  • the data is where the server cannot see it: a scheduled task, the memory, a project cannot read a chat; a backup of the server’s data folder holds no chat.

1.2 How others do it

Section titled “1.2 How others do it”

From what their repositories showed when they were looked at for docs/comparison.md (not re-read for this spec: from memory, to be checked when the comparison is next updated): Open WebUI keeps chats and settings in its database per user, the page caching nothing but the session; LibreChat the same in MongoDB, a message’s files as files; Jan and LM Studio, desktop apps, write one JSON file per thread in the app’s data folder with the thread’s files beside it. One file per chat in the data folder is the common shape for a local app; Inga does the same.

2. The design

Section titled “2. The design”

2.1 Where

Section titled “2.1 Where”

The server keeps a profile per user in its data folder, beside the memory (projects.rs’s root()): %APPDATA%\inga\profiles\default\ on Windows, ~/Library/Application Support/inga/profiles/default/ on macOS, $XDG_DATA_HOME/inga/profiles/default/ (else ~/.local/share/...) elsewhere. With --home DIR (or home in inga.toml), where Inga keeps its own files, the profile is DIR/profiles/default/ instead, so a server moved by hand, and every test’s server, has its own. Today, without authentication, every browser is the same user, default; separating users comes with the accounts (docs/todo/backlog.md). GET /api/inga/profile says the folder (where), as every choice of the server is said.

2.2 On disk

Section titled “2.2 On disk”
  • A chat’s id is the page’s (newId of js/markdown.js: base-36 digits); the server accepts [A-Za-z0-9_-]{1,64}, a kv name [A-Za-z][A-Za-z0-9_.-]{0,63} without ..; anything else is a 400 (the name is the file’s name).
  • Pictures as files: on a write, every string of the chat that is a data:image/... URL (a message’s images[], an edit’s painted mask, in every branch: the whole JSON tree is walked, so a new field with a picture needs no new code) is written to <id>.files/<hash>.<ext> and replaced by "file:<hash>.<ext>" in the JSON; on a read the file is inlined back as a data: URL, so the page and the API see the chat exactly as the page saved it. A media type the server does not name (not png, jpeg, webp, gif) stays inline. Files the new JSON no longer names are deleted with the write; the folder goes with the chat. The JSON stays readable and small, and a picture two versions of the conversation share is one file.
  • Atomic writes: a document is written to <file>.tmp then renamed over the old one (std::fs::rename replaces on every platform); the index the same, after the chat. A reader never sees a half file; a crash leaves at worst a .tmp, ignored.
  • The index is rebuilt from the files when missing or unreadable (a user may delete or copy chats by hand); a chat whose file is not valid JSON is skipped and named in the server’s log.
  • Limits, each said in the error (code and message, the numbers inside) and in GET /api/inga/profile’s limits: a document (a chat’s JSON without its pictures, a kv value) of at most 4 MiB (DOC_MAX, 413 profile_document_too_large: “the chat … is 5.2 MiB of text; a chat holds at most 4 MiB, its pictures apart”); the profile of at most 1 GiB in all, pictures counted (TOTAL_MAX, 413 profile_full: “the profile holds 1.0 GiB, its limit: delete chats or pictures”); a request body of at most 16 MiB (http::MAX_BODY, already there: a chat whose pictures weigh more cannot be sent, the page says so). The limits are constants today; keys of inga.toml when someone needs them.
  • One lock for the profile’s writes (Mutex), so two tabs saving at once do not cross.

2.3 The API

Section titled “2.3 The API”

Admin routes (/api/inga/*: an admin key when the server has named keys), documented in docs/api/inga.yaml (tag profile), JSON in and out, errors in the OpenAI shape:

Route What
GET /api/inga/profile the snapshot the page loads first: user, where, chats (count, bytes, pictures_bytes), bytes (the profile in all), limits (document_bytes, total_bytes, body_bytes), kv (every document by name)
GET /api/inga/profile/chats every chat, newest first (created, else updated), pictures inlined: {"chats": [...]}
GET /api/inga/profile/chats/{id} one chat; 404 when none
PUT /api/inga/profile/chats/{id} writes a chat (the body, a JSON object; its id set to the path’s): {"id", "bytes", "pictures", "pictures_bytes", "total_bytes"}
DELETE /api/inga/profile/chats/{id} deletes it and its pictures: {"deleted": id, "total_bytes"}; 404 when none
DELETE /api/inga/profile/chats deletes every chat: {"deleted": n, "total_bytes"}
GET /api/inga/profile/kv/{name} one document: {"name", "value"}; 404 when none
PUT /api/inga/profile/kv/{name} writes one: body {"value": ...}: {"name", "bytes", "total_bytes"}
PUT /api/inga/profile/kv writes several at once (the page’s debounced queue): body {"values": {name: value}}, all or none: {"saved": [names], "total_bytes"}
DELETE /api/inga/profile/kv/{name} deletes one: {"deleted": name}

2.4 The page

Section titled “2.4 The page”
  • js/profile.js (after core.js, before shell.js): the profile’s client.
    • The snapshot is read before the page’s scripts run, with one synchronous XMLHttpRequest to GET /api/inga/profile (the remote server’s address and key when the page is in remote mode: they are page settings, read from localStorage). The page’s files read their saved choices in top-level statements in some forty places (let params = …store.get("params"), the Images page’s prompt, the project open): a value that arrived later would be read too late. The answer is a few KB from a server on the same machine; the request is deprecated by the browsers but supported by all, and the only way a classic script waits. A server that does not answer fails the request at once (connection refused) and the page starts with its defaults, says so (below) and sends nothing until a reload shows the profile.
    • profile.get(k, d) and profile.set(k, v) serve the data keys of §1.1: store of shell.js sends those keys here (PROFILE_KEYS) and the page settings to localStorage, so the forty call sites do not change. A set queues the key; the queue is sent 400 ms after the last change as one PUT /api/inga/profile/kv.
    • The chats: save() of markdown.js calls profile.saveChats(chats), which compares each chat’s JSON with the last one sent and queues a PUT for each changed chat and a DELETE for each gone; current is a kv document. The list is read after the scripts ran, asynchronously (GET /api/inga/profile/chats: with pictures inlined it may be large); the chats’ column says “Loading your chats from the server” meanwhile, then draw(). A chat made before the list came (the user typed at once) is kept and saved.
    • Retries and the state shown: a request the server does not answer is tried again after 1 s, 2 s, 4 s … up to 30 s, and at once when the server is back (connUp of server-down.js); the #store-bar says what is not saved and why, with Retry and Export every chat, and “Your chats are saved again” when a retry succeeds. A 413 keeps the document aside (not retried until it changes) and the bar says the server’s limit and the figures, with Export and Delete pictures (the bar of 0.42.0, its text now the server’s). A 401 or 403 says the key is refused. When the page is closed with changes queued, they are sent at once with keepalive (bodies up to 64 KiB) and the browser asks before leaving when more is unsaved.
    • What stays in localStorage: the page settings of §1.1, and nothing else; a refusal there (a browser that blocks the storage) is said once, as before, but concerns only the page’s settings now.
  • No migration: the page starts from the server’s chats; the chats a browser kept before 0.44.0 are not read. The Storage page says so under its line for the chats (“Chats kept on the server in …: N chats, X, Y of pictures”), and, when this browser still holds chats of an older Inga, how many and an Export button for them (the existing Import reads that file, so a user who wants them back has two clicks; the page does it for nobody by itself).
  • The migrations of shell.js and markdown.js that rewrote old browser data (params_v, chats_v) go: the server’s profile starts empty and chatOk still normalizes every chat read.
  • The Storage page’s line and the chats’ column’s note (chatsNear, past 80 % of the server’s total limit) read the figures of GET /api/inga/profile and of each PUT’s answer, not the browser’s quota.

3. What is not done here

Section titled “3. What is not done here”
  • Separating users (profiles/<user>/) waits for the accounts; the API’s shape (/api/inga/profile/..., the user implied) does not change then.
  • A chat’s list loaded lazily (titles first, the messages when opened): the index is there for it; today the page loads every chat, as it did from localStorage.
  • Chats written by the server itself (a scheduled task’s answer into a chat).
  • A chat of several MiB of text split or compressed; a quota per user.
  • The .tmp files are not fsync’d before the rename: a power cut may lose the last write, never an older one.
  • The API key in localStorage (a candidate of docs/todo/0.44.0.md) is unchanged: it is how the page reaches the server.
