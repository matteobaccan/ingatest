The structure of code in Inga: tree-sitter inside the binary

Status: proposed for evaluation, 2026-11-01. Asked by the maintainer (“what if we integrated tree-sitter’s C part? licences? portability?”; “not in the browser”). No decision before the numbers: the tokensave case of ingausecase (Inga as an MCP host with tokensave’s tools, answers and tokens with and without them) says first how much a symbol graph is worth to a local model (§9). Until then this spec only lays out the options and their costs.

It extends the RAG spec §3.6 and §6.6, which chose today’s course: a heuristic item chunker and a lexical identifier table in Inga (R5), the precise symbol graph left to tokensave over MCP, because “Inga cannot link tree-sitter (C)”. This spec reopens that one point.

1. What tree-sitter is

Section titled “1. What tree-sitter is”

A parser generator and an incremental parsing library, written by Max Brunsfeld at GitHub (2018, for Atom), now used by GitHub’s code navigation, Neovim, Zed, Helix, Emacs and coding agents (aider’s repository map, tokensave). Per language a grammar (grammar.js) is turned by the generator (tree-sitter generate, written in Rust) into a parser.c: parse tables and a lexer, data more than code. A runtime in C (lib/src: the parser, the lexer, the subtree store, the query engine) walks those tables; it is incremental (an edit re-parses only what changed) and error-tolerant (code that does not compile still gives a useful tree). Some languages add an external scanner (scanner.c, written by hand) for what a grammar cannot say: Python’s indentation, JavaScript’s template strings, Rust’s raw strings, Ruby’s heredocs, YAML. The tree-sitter crate is a Rust wrapper around the C runtime. Licence of the core: MIT. (From the projects’ READMEs and repositories; sizes below are estimates to measure.)

2. Goal

Section titled “2. Goal”
  • For a folder of code added to a collection (the RAG’s folders, inga docs add):
    • chunks cut at syntax boundaries (functions, classes, impl blocks), split and merged under a size limit (cAST, the RAG spec §3.6);
    • definitions and references: where a symbol is defined, who calls it, what it calls;
    • line ranges in citations.
  • The graph is offered to models as built-in tools, beside search_documents: find_definition, find_references, callers, callees, outline. They go to the chat APIs, to inga run and to Inga’s MCP server, with the same names and shapes as the matching tokensave tools where they overlap, so a model’s habits carry over.
  • Incremental: a changed file is parsed again in milliseconds, in the folder sync of RAG R1, at low OS priority.
  • No new runtime dependency in the sense of AGENTS.md: still one executable, no dynamic library, no external program.

Non-goals

Section titled “Non-goals”
  • The browser page (crates/inga-wasm, web/): no tree-sitter there (the maintainer, 2026-11-01). The feature is compiled out of the WASM build.
  • Every language of tokensave’s 50+: a curated set first (§5).
  • Type-aware analysis (rust-analyzer, LSP servers): references stay syntactic, name-based, scoped by the grammar’s locals queries where they exist; precision is said, never implied.
  • Replacing tokensave: it stays the documented MCP companion for those who use it.

3. The options

Section titled “3. The options”
A. Link the C B. tree-sitter in WebAssembly, run by a pure-Rust interpreter C. Rust out of the generator, runtime in Rust D. Today’s course
What the tree-sitter crate and each grammar’s parser.c / scanner.c, compiled by cc and linked statically runtime + grammars compiled once to .wasm in CI, run by an interpreter such as wasmi; grammars fetched like models the generator’s renderer writes Rust tables; the runtime and every external scanner rewritten in safe Rust heuristic item finder and identifier table in Inga (R5), tokensave over MCP for the precise graph
Languages the curated set (§5) every grammar that builds to wasm those whose scanners are ported all of tokensave’s, outside Inga
C in the binary yes (second exception after ring) no no no
unsafe in Inga no (inside the crate) no no no
Speed native slower: interpreted wasm, perhaps 5–20× (unmeasured) native native (heuristic)
Binary size grows with each grammar (§6.4) unchanged; grammars downloaded grows like A unchanged
Effort small–medium medium large: the runtime is tens of thousands of lines of C, plus a scanner per language (estimate) R5 as planned
Risk memory safety on untrusted files (§6.3) interpreter maturity, speed upkeep against upstream precision

This spec details A, the one the maintainer asked about, with B as the fallback if §6’s costs turn out too high. C stays an idea for a separate crate (useful to others too), not for Inga’s roadmap. D is what happens if §9’s numbers say a symbol graph does not pay.

4. Design of option A

Section titled “4. Design of option A”
  • A crate of its own, crates/inga-code, behind a Cargo feature code:
    • on by default for the desktop targets: Windows x86-64, Linux x86-64 and ARM64, macOS ARM64 and x86-64;
    • off for wasm32 (crates/inga-wasm never enables it).
  • The grammars vendored like llama.cpp’s kernels: each parser.c / scanner.c / query files (highlights.scm not needed; tags.scm and locals.scm used) under crates/inga-code/grammars/<lang>/ at a pinned upstream commit, with its licence file, and a tools/vendor-grammars.sh that fetches and checks them (sha256), Renovate-style bumps reviewed by hand.
  • Parsing in a child process.
    • inga starts itself (inga __parse, a hidden subcommand), which is not an external program;
    • the parent sends files by path and gets back the tags as JSON lines;
    • the child is killed after a time limit per file (default 2 s) and over a memory limit, and is restarted after a crash;
    • the file is then marked “not parsed: ” and falls back to the heuristic chunker;
    • this is what tokensave does (a worker process per file, so a grammar crash does not stop the sync).
  • The data.
    • Per file: the items (kind, name, line range, parent) from tags.scm, and the references (name, line) from the tree.
    • In the store beside the RAG’s index (crates/inga-engine/src/rag/): a symbol table and a reference table keyed by name, updated with the file.
    • Callers / callees by name, scoped by locals.scm where the grammar has it.
  • The chunks. cAST’s split-and-merge on the syntax tree, replacing the heuristic chunker for the languages in the set (the heuristic stays for the rest).
  • Transparency. The Documents page and inga docs say, per folder:
    • the languages parsed with tree-sitter and those that fell back, with why;
    • the grammar versions;
    • that references are by name, not by type.

6. The costs, one by one

Section titled “6. The costs, one by one”

6.1 Licences

Section titled “6.1 Licences”
  • tree-sitter’s core: MIT, compatible with Inga’s MIT; an entry in THIRD-PARTY-NOTICES.md.
  • Each grammar is a project of its own:
    • the tree-sitter/ and tree-sitter-grammars/ organisations’ grammars are, as far as known, MIT;
    • community grammars vary (Apache-2.0, or no licence at all).
  • The rule:
    • a grammar is vendored only with a licence file that allows redistribution (MIT, Apache-2.0, BSD), recorded in THIRD-PARTY-NOTICES.md with its commit;
    • one without a licence is not taken.
  • The binary’s archives already ship THIRD-PARTY-NOTICES.md, so nothing changes in the release process.

6.2 Portability

Section titled “6.2 Portability”
Target Expected To check
Linux x86-64, ARM64 the cc crate builds portable C as it does for ring the ARM64 cross build in CI
macOS ARM64, x86-64 as above, with Apple’s clang none expected
Windows x86-64 (MSVC, static C runtime) tree-sitter builds on MSVC the C runtime flags must match Inga’s static CRT (+crt-static)
wasm32 (browser) excluded (no libc on wasm32-unknown-unknown) the feature compiled out, a CI check that inga-wasm does not pull inga-code

6.3 Memory safety

Section titled “6.3 Memory safety”
  • Inga is in Rust partly for memory safety on untrusted input (comparison, “Where Inga stands”, point 4). A C parser reading any folder brings that risk back.
  • tree-sitter is widely used and fuzzed upstream, but how solid it is today was not checked (no data in this spec).
  • The mitigation:
    • the child process of §4, with time and memory limits;
    • a fuzz target in CI on the vendored grammars (cargo fuzz over random and mutated files), run in the nightly job.
  • The server process never runs grammar code.

6.4 Binary size and build time

Section titled “6.4 Binary size and build time”
  • The generated tables are large: the big grammars (C++, TypeScript, C#) produce parser.c files of many MB.
  • To measure before deciding:
    • the size of inga with and without the feature (today about 63 MB on Windows);
    • CI’s build time on the release matrix;
    • one grammar at a time, so each language’s cost is known.
  • If the growth is too large, two ways out:
    • fewer languages;
    • option B’s downloaded grammars for the large ones.

6.5 The rules of AGENTS.md

Section titled “6.5 The rules of AGENTS.md”
  • “New crates must be justified in the PR, statically linked and pure Rust (only exception so far: ring)”: this needs the maintainer’s explicit exception, written into AGENTS.md with its scope (the tree-sitter crate and the vendored grammars of crates/inga-code, desktop targets only).
  • No new unsafe in Inga’s own code: the FFI lives inside the tree-sitter crate.

6.6 Upkeep

Section titled “6.6 Upkeep”
  • tree-sitter has ABI versions (13–15): the vendored grammars are regenerated or pinned to the runtime’s ABI, checked in CI.
  • Some grammars are slow to follow their language’s new syntax: the fallback to the heuristic chunker keeps such files usable, and says so.

7. Surfaces

Section titled “7. Surfaces”
  • Chat APIs and inga run: the code tools join search_documents when a request names a collection holding code (inga_documents, #name).
  • MCP: Inga’s MCP server offers them to other agents.
  • CLI: inga docs outline FILE, inga docs refs NAME [--collection C].
  • Web UI: the Documents page shows per folder the parsed languages and fallbacks, and a symbol’s definition and references next to a passage. Desktop only, since the browser page has no code feature.
  • Docs: a use-case guide, “Ask questions about a code base”, with tokensave as the alternative for the languages Inga does not parse.

8. Tests

Section titled “8. Tests”
  • Golden tests per language: small fixture files, their items and references, compared with tree-sitter tags run on the same files at the same grammar commit (an oracle run in CI, as the llama.cpp oracles are).
  • The child process:
    • a grammar that loops or crashes on a crafted file is stopped, reported and falls back;
    • the server keeps serving.
  • Incremental sync: an edited file updates its symbols and references only.
  • The WASM build has no inga-code in its dependency tree.

9. The decision gate: the numbers first

Section titled “9. The decision gate: the numbers first”

Before any code, ingausecase’s tokensave case runs on the release and on the trial branch, with the local models of models.json, and answers three questions:

  1. Do local models use code tools well? Right answers with tokensave’s tools against without, by model size (0.6B, 1.7B, 4B and, where the runner allows, larger).
  2. Do they save tokens? Prompt and completion tokens per question in both modes (the case reads them from the API’s usage; Inga’s usage counter keeps them too).
  3. Which tools matter? Which of tokensave’s tools the models call and which calls lead to right answers: the first set of §2’s built-in tools.

Then:

  • Clear gain with the tools:
    • option A for the curated languages, if §6.4’s measures are acceptable;
    • otherwise option B.
  • Small or no gain: option D (R5 as planned, tokensave documented), and this spec closes.

The same case, rerun with Inga’s own tools once built, compares them with tokensave’s.

  1. T0: the AGENTS.md exception, the vendoring script, crates/inga-code with two languages (Rust, Python), the child process, the golden tests; size and build time measured and written here.
  2. T1: the rest of §5’s set, the symbol and reference tables in the store, cAST chunks, the fallback said per file.
  3. T2: the built-in tools in the APIs, inga run and the MCP server; ingausecase’s case run with them.
  4. T3: the web UI’s per-folder status and the symbol view; the use-case guide.

Each part is usable on its own or invisible until complete, as AGENTS.md asks of a release’s items.

As built (T0, on the experimental branch exp/0.44-treesitter)

Section titled “As built (T0, on the experimental branch exp/0.44-treesitter)”

Built ahead of §9’s gate, on an experimental branch, so the gate’s numbers can be taken with Inga’s own parser too; nothing reaches main before the maintainer’s decision.

  • crates/inga-code: the types (Lang, Item, Ref, Tags), parse (the grammar’s tags.scm plus a few patterns of Inga’s own: an impl block as an item named by its type, a trait’s declared methods and calls through a path in Rust, a class’s bases and attributes in Python), qualified names (Signer.derive_key, Store::search) and the item each reference is in. Two languages, Rust and Python; a list of the other code extensions so a folder can say “not parsed: no grammar”.
  • The grammars are crates, not vendored files. tree-sitter 0.27.1, tree-sitter-rust 0.24.2 and tree-sitter-python 0.25.0 from crates.io, pinned with = in the workspace’s Cargo.toml (a test checks that the versions the status prints are the pinned ones); their parser.c / scanner.c and tags.scm come inside the crates, checked by Cargo.lock’s checksums, so §4’s grammars/<lang>/ folder and tools/vendor-grammars.sh are not needed for these two. A grammar without a crate would bring them back.
  • The feature is grammars of inga-code (on by default; §4’s code); the grammars are target dependencies of cfg(not(target_arch = "wasm32")), and a build without them has no language and says so. inga-wasm does not depend on the crate: a test (the_browser_page_has_no_tree_sitter) walks Cargo.lock from inga-wasm and fails if it reaches inga-code or a tree-sitter crate.
  • The child process. inga __parse (hidden, handled first in main, before the configuration is read) answers one JSON line a file on its standard input ({"lang", "text"} → {"tags"} or {"error"}). inga_code::Worker starts it on the first file and keeps it for the next; a reply waited for longer than 2 s kills the child, a child that stops is reaped with its exit status, and either way only that file is “not parsed: ” and the next file starts a new child. Files above 2 MiB are not sent. Not built: the memory limit (it needs a per-platform call such as setrlimit or a Job Object, a new unsafe block to approve) and the fuzz target.
  • Tests: golden files per language (crates/inga-code/tests/fixtures/*.tags.json, written with INGA_BLESS=1 and read by hand), a hanging and a crashing child (with /bin/sh, Unix only), the protocol, and inga __parse run end to end through the worker (tests/cli/docs.rs). The golden files are not compared with tree-sitter tags (§8’s oracle): the CLI is not in CI yet.
  • Sizes, estimated: the C compiled by cc in a dev build is 0.37 MB for the runtime, 0.53 MB for Python and 1.16 MB for Rust (static libraries, before linking); the release executable with and without them and CI’s build time are not measured yet.
  • Not wired yet (T1–T3): the symbol and reference tables in the RAG’s store, the cAST chunks, the tools for the models, inga docs outline / refs and the web UI.

As built (T1–T3, on the experimental branch exp/0.44-ts2)

Section titled “As built (T1–T3, on the experimental branch exp/0.44-ts2)”

Built on 2026-11-04 on top of T0, still ahead of §9’s gate; nothing reaches main before the maintainer’s decision.

  • No grammar in the engine. inga-engine is in the browser page’s build, so it never depends on inga-code (the test the_browser_page_has_no_tree_sitter still holds): it defines a CodeParser trait and the tags’ shape (rag::code::FileCode, the same JSON as inga_code::Tags), and the executable installs its parser at the start (src/commands/code.rs: an inga_code::Worker behind a mutex, the child started on the first source file). The server, inga docs and inga run share it; the server only reads the tables.
  • §5’s set: two languages, not twelve. Adding the other grammars needs the maintainer’s approval of their crates (AGENTS.md’s exception names tree-sitter-rust and tree-sitter-python only), so T1 kept Rust and Python; the others are “not parsed: no grammar for JavaScript in this build (Inga parses Rust, Python)”, per file.
  • The tables (T1). One store entry per parsed file in the collection code/NAME (rag::code::code_of): its path as the text, its items and references in meta, added once the file’s passages are embedded, replaced with the file and removed with it (remove_file, remove_collection). CodeIndex reads a collection’s entries into two maps keyed by name (items, references) for each question; no table is kept in memory between questions (a few thousand files read in milliseconds: not measured on a large repository).
  • The fallback, said per file (T1). Every source file’s entry in documents carries meta.code: lang, grammar, chunker (CODE_CHUNKER, 1), and either the items’ and references’ counts with syntax_errors, or fallback with why. A file indexed before, or by another grammar version, is read again once (rag::code::needs_parse, counted with the files of an older chunker; its unchanged passages keep their vectors). rag::code::summary gathers a folder’s: per language the files parsed and not, the grammar, the first 20 fallbacks with why, the runtime and the note on precision. Uploaded files (inga docs add NAME FILE..., the Documents page’s Add files) are not parsed: only a folder’s sync parses (the conservative choice; §2 speaks of folders).
  • cAST (T1). rag::code::cast_chunks: the item tree’s siblings (items, and the lines between them) merged while they fit in the encoder’s chunk size, an item larger than that split into its children and the lines between them, a leaf larger than that cut at whole lines; sizes in the encoder’s tokens, counted once per line and summed (an approximation: tokens across a line break are counted apart). The comment, attribute and decorator lines right above an item go with it. Each chunk’s heading is the path and the items it is in (src/store.rs › impl Store › fn search: each item’s signature up to its name, the visibility dropped), its lines the file’s own, its section the top-level item it starts in (so the fusion’s whole-section rule works per item), no overlap. The heuristic chunker of R5 is not built: files of other languages keep the plain-text chunker.
  • The tools (T2). crates/inga-server/src/codetools.rs: find_definition, find_references, callers, callees (symbol, optional collection) and outline (file). tokensave’s own tools are tokensave_callers, tokensave_callees, tokensave_node, tokensave_search, tokensave_module_api (its docs/guide/MCP-TOOLS.md, read 2026-11-04; their parameters are not documented there): the names of §2 were kept, and symbol as the argument. They join the document tools (doctools::offered, doctools::is_tool, counted per round with them) in the chat APIs and inga run when a named collection holds parsed code, and Inga’s MCP server (memory_mcp.rs) lists them when one does, with collection required (an MCP client has no prompt that names collections; the conservative choice: any collection holding code, by its name, under the server’s API keys). Every answer says that references are by name, not by type; results are numbered as sources and bounded like the document tools’. inga docs outline FILE and inga docs refs NAME (--collection, --json) answer from the same tables, and GET /api/inga/documents/code serves them (?collection= the status, &symbol= a symbol, &file= an outline).
  • The web UI (T3). The Documents page: each folder’s code line (languages, files parsed, grammar versions, the files cut as plain text, folded, with why), a Find symbol box in a collection holding parsed code, and a search hit’s Definition and references button (its symbol from the hit’s heading path).
  • Tests: the cAST cut, the labels, the tables and needs_parse (rag::code::tests), a folder synced with a fake parser (rag::sync), the code tools without code (codetools), the MCP listing, the CLI parser, the binary’s parser adapter, a folder of code end to end through inga docs (tests/cli/docs.rs) and through inga serve, /api/inga/documents/code and /mcp (tests/server/memory_docs.rs). Only cargo check was run on this branch (the release’s rule); the tests run in CI.
  • Not built: the other languages, locals.scm scopes, the parsing child’s memory limit and the fuzz target (T0’s), ingausecase’s case run with Inga’s tools, the web UI test of the new views.

As built (TypeScript, JavaScript, C#, Go and PHP, on the experimental branch exp/0.44-tslangs)

Section titled “As built (TypeScript, JavaScript, C#, Go and PHP, on the experimental branch exp/0.44-tslangs)”

Built on 2026-11-04 on top of the Java branch, the maintainer having approved tree-sitter-typescript, tree-sitter-javascript, tree-sitter-c-sharp, tree-sitter-go and tree-sitter-php the same day (AGENTS.md’s exception now lists the eight grammars); nothing reaches main before §9’s gate.

  • The grammars. From crates.io, each the latest published, pinned with = in the workspace’s Cargo.toml, target dependencies of crates/inga-code behind grammars, desktop targets only, run in inga __parse. Their parser.c ABIs are within the 0.27.1 runtime’s 13–15, and §5’s “external scanner” column holds for all five:

    Grammar Version parser.c ABI scanner.c Licence
    tree-sitter-typescript (LANGUAGE_TYPESCRIPT, LANGUAGE_TSX) 0.23.2 14 yes MIT, no licence file in the crate (in its repository at v0.23.2)
    tree-sitter-javascript 0.25.0 15 yes MIT
    tree-sitter-c-sharp 0.23.5 15 yes MIT
    tree-sitter-go 0.25.0 15 no MIT
    tree-sitter-php (LANGUAGE_PHP, PHP with its HTML; LANGUAGE_PHP_ONLY unused) 0.25.1 15 yes MIT

    Extensions: .ts, .mts, .cts are TypeScript (Lang::TypeScript), .tsx TSX (Lang::Tsx), .js, .mjs, .cjs, .jsx JavaScript (its grammar reads JSX), .cs C#, .go Go, .php PHP; the separator is . but for PHP (::, Circle::area). other_code keeps C, C++, Ruby, Kotlin, Swift, Scala, Lua and shell.

  • What is read (each grammar’s tags.scm plus Inga’s patterns in crates/inga-code/src/grammar.rs; TypeScript’s query is JavaScript’s tags.scm, TypeScript’s and the patterns of both):

    • TypeScript and JavaScript: functions (generators, and arrow functions or function expressions assigned to a name), classes, methods, constructors (constructor), a class’s fields (TypeScript’s parameter properties, private log: Logger, as the class’s fields), the module’s consts (constant); in TypeScript also interfaces and their members, type aliases (type), enums and their members, namespaces (module), abstract classes and method signatures. References: calls, new, extends (inherit), implements (impl), the imports (import { a as b } is a, a default or * as u import its local name, const x = require("x") is x, export { a } from "./m" is a), the names exported (export: export { a }, export default A), in TypeScript every type named (type), and in JSX and TSX the components used (<Button />: a call; a lowercase element is HTML, not a reference). An object’s methods are functions.
    • C#: namespaces (module; a file-scoped namespace A.B; holds the items after it), classes, structs (struct), interfaces, enums and their members, records and their positional properties, methods, constructors, properties (property), fields (int a, b; siblings), consts (constant), events (field), delegates (type). References: calls (plain, member and generic), new (generic and qualified too), a class’s, record’s and interface’s bases (inherit: the syntax does not tell a base class from an interface), a struct’s interfaces (impl), the usings (import, the last name; an alias’s target), the types named (type). Attributes on lines of their own are passed over in a signature ([Obsolete]).
    • Go: the package (module), functions, methods (their parent is their receiver type, Circle.Area, wherever the type is declared; cAST cuts them on their own lines, beside the type), structs (struct), interfaces and their methods, the other types (type), a struct’s fields, the file’s consts (constant) and vars (variable). References: calls, composite literals (Circle{...}: a call, as new), the types a struct or an interface embeds (inherit), the imports (the path’s last part: http), the types named (type; the predeclared int, error, any, … are not references).
    • PHP: namespaces (module; a braced one holds its items), classes, interfaces, traits (trait), enums and their cases, functions, methods, constructors (__construct), properties and promoted constructor properties (the class’s fields), constants. References: function, method, static and nullsafe calls, new, extends (inherit), implements (impl), the traits a class uses (inherit), the use imports (import, the last name, grouped uses too), the class of a static call and the types named (type; not self, static, parent). Attributes on lines of their own (#[Pure]) are passed over in a signature.

  • The shared changes. A reference’s name is its last part without type arguments (IComparable<Circle> → IComparable, \Countable → Countable, Base(X) → Base, "net/http" → http); a name being defined is not also a type reference (TypeScript’s class Circle, Go’s type Circle struct); two items of the same node and name keep the more specific kind (a PHP trait over tags.scm’s interface, a Go struct over its type, an arrow function over its const, a C# const over its field); a signature keeps the export, const, let, var, type words before its node on its line (export const total = (xs) => ..., type Circle struct {). The Rust, Python and Java golden files are unchanged.

  • Labels (rag::code::label): more modifiers dropped (C#’s internal, override, virtual, partial, extern; readonly; export), C#’s attributes dropped, and function, function*, func, var and namespace declare a name: shapes.ts › class Circle › method area, const total, Shapes.cs › namespace Example.Shapes › class Circle › method Area, shapes.go › func (c *Circle) Area, Shapes.php › class Circle › function area; a method or function whose signature starts with its name is method area. A parent that does not hold an item’s lines (a Go method’s receiver type) is not one when cAST cuts the file.

  • Tests: a golden file per language (shapes.ts, shapes.js, Shapes.cs, shapes.go, Shapes.php and their .tags.json in crates/inga-code/tests/fixtures/), a test per language of inheritance, imports and types (typescript_inheritance_imports_and_types, tsx_and_jsx_components_are_calls, csharp_inheritance_usings_and_types, go_receivers_embedding_and_imports, php_traits_promoted_properties_and_uses), the labels (rag::code::tests::typescript_csharp_go_and_php_labels) and a Go method cut beside its type (a_go_method_is_cut_beside_its_receiver_type); the_browser_page_has_no_tree_sitter checks the five crates too. The files that stood for “a language without a grammar” in the engine’s, the CLI’s and the server’s tests are Ruby now. The golden files are not compared with tree-sitter tags (§8’s oracle), and no real code base of these languages has been synced yet.

  • Size. The grammars’ parser objects, built with the release profile (size, text and data, cc’s output for each crate): C# 5.30 MB, TypeScript and TSX 2.85 MB (1.41 + 1.44), PHP 1.08 MB (the php parser; php_only’s, as large, is in the crate’s archive but nothing refers to it, so the linker should leave it out), JavaScript 0.41 MB, Go 0.22 MB: about 9.9 MB for the five (Java’s 0.41 MB, Rust’s 1.11 MB and Python’s 0.46 MB for comparison). Not measured as a difference of the release inga executable (the disk here was too small for a second release build).

  • Not built: the locals.scm scopes; Vue and Svelte files; PHP’s LANGUAGE_PHP_ONLY for files without <?php; C#’s base class told from its interfaces; Go’s generic type parameters as definitions; a real code base of each language (docs/todo/real-world-checks.md).
