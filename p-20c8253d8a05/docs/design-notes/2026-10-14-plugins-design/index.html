Plugins: WebAssembly components that extend Inga

Status: proposed for 0.33.0 (decided 2026-10-14). First proposal (agents), after the code sandbox’s S1; asked by the maintainer on 2026-10-14, after docs/comparison.md (Part 2, §4) listed plugins as “not planned”. Nothing built. It runs on the runtime of the code sandbox (2026-10-14-code-sandbox-design.md), §12.

0. Open questions for the maintainer

Section titled “0. Open questions for the maintainer”

Status of every question below: open — postponed by the maintainer on 2026-10-14. The plugins depend on the code sandbox’s runtime, whose distribution is undecided.

  1. The format: WebAssembly components with Inga’s WIT interfaces (proposed, §3), MCP staying as it is for tools from other programs. Agreed?
  2. Signatures: required for plugins of a catalogue, optional (with a warning) for a file or a URL the user gives (proposed, §9)? Or required everywhere?
  3. A default catalogue: a repository of Inga’s, each plugin reviewed by the maintainer before it is listed, or no default catalogue at first (only sources the user adds)?
  4. Filters on the stream (each token through the plugin) in part 1, or only on the whole request and the whole answer (proposed)?
  5. Pages (a plugin’s own page in the web UI) in part 3, or never?
  6. Python plugins: on the code sandbox’s shared CPython (part 3, small plugins), or only as components built with componentize-py (each carrying its own CPython, about 30 MB)?

1. Why

Section titled “1. Why”

LM Studio has Hub plugins (tools, prompt preprocessors and generators written in TypeScript); Open WebUI has functions (tools, filters, pipes, actions, in Python) and pipelines (the same in a separate server). Inga has two ways to extend a model today:

Skills (0.27.0) MCP (0.27.0) Plugins (this spec)
What it is instructions and files, read by the model a server’s tools, resources and prompts code inside Inga
Tools through run_skill_script (a host program, approved) yes yes, in a sandbox
Change a request before the model no no filters (inlet)
Change an answer after the model no no filters (outlet)
New models or providers no no pipes
Buttons on messages no no actions
Pages in the web UI no no pages (part 3)
Settings the user fills in no mcp.json a form from the plugin’s schema
Where the code runs the host (scripts) another program or another machine Inga’s process, WebAssembly

Skills and MCP stay as they are: a plugin is for what needs to sit inside Inga’s request path or web UI.

2. What a plugin can do

Section titled “2. What a plugin can do”
  • Tools: functions offered to the model as MCP and skill tools are, in the server’s tool loop (websearch::generate); a result is text, images and files.
  • Filters: inlet receives a request (the messages, the model, the parameters, in Inga’s internal shape, the same whatever API it came from) and returns it changed, or refuses it with a reason; outlet receives the finished answer and returns it changed, or adds a note. Uses: masking personal data before a cloud API node, a house style, translating in and out, citations, logging to a file of the plugin’s. Each filter has a priority; filters run in order.
  • Pipes: models of their own, listed in /v1/models as plugin/<id>/<model>; a pipe receives the request and streams the answer. Uses: a provider API nodes do not speak, a router over local models, an agent loop, a fixed workflow (retrieve, then answer).
  • Actions: buttons on a message (or the composer) that run the plugin with the message and the chat, and replace the text, add a message, show a result, or offer a file. Uses: “summarize this chat to a file”, “send to my notes”, “translate”.
  • Pages (part 3): a page of the plugin’s own in the web UI’s left bar, in a sandboxed frame, that talks only to its plugin.
  • Settings (“valves” in Open WebUI): a JSON Schema the web UI turns into a form; secret fields are stored encrypted, as API node keys are.

What a plugin cannot do: start programs, open sockets, read files outside its own folder and what the user granted, see requests it does not filter, change Inga’s own pages, or run when it is disabled.

3. The options

Section titled “3. The options”
WASM components (WIT) MCP servers plus a manifest Scripts in the code sandbox
Tools yes yes yes
Filters, pipes, actions yes, typed interfaces no: MCP has tools, resources, prompts and sampling only; Inga would add its own methods, which no MCP server implements yes, through a protocol of Inga’s over stdin / stdout
Isolation WASM, per plugin, the permissions enforced by the host functions a stdio server is a host program (--allow-mcp-commands); an HTTP one is another machine’s WASM, as the sandbox
Nothing to install yes stdio servers need their runtime (Node, Python, uv) Python downloaded once (the sandbox’s)
Languages Rust, C, Go (TinyGo), JavaScript (ComponentizeJS), Python (componentize-py), C# any Python and JavaScript
Size of a plugin 50 KB – 2 MB (Rust, Go), 8–30 MB (JavaScript, Python, which carry their interpreter) small small (source files)
Speed of a call microseconds once instantiated a process round trip an interpreter, warm: milliseconds
Portable one file for every OS and CPU per runtime yes
Typed contract and versions WIT packages with semver JSON Schema per tool Inga’s own

Recommended: WebAssembly components with Inga’s WIT world, with Python plugins added in part 3 as scripts on the sandbox’s CPython behind the same manifest (open question 6), and MCP left for tools that live in other programs. Reasons:

  • only components cover filters, pipes, actions and pages with a typed, versioned contract that can evolve (WIT packages and @since);
  • the isolation and the permissions are the host’s, not the plugin’s promise: a plugin reaches the network only through Inga’s http function, which checks the hosts granted;
  • one .wasm file runs on every platform Inga runs on, with the runtime Inga already carries for the code sandbox;
  • MCP as the format would keep stdio servers (external programs) as the common case and need Inga-only extensions for everything but tools;
  • scripts alone would make Python the only language and every call an interpreter’s, but they make authoring easy, so they come as a second entry kind.

Open WebUI’s functions cannot be run as they are (Python with any pip package and the network, in Open WebUI’s process); a plugin’s interfaces are close to theirs, so porting one is a rewrite of its glue, not of its logic.

4. The WIT interfaces

Section titled “4. The WIT interfaces”

Package inga:plugin@1.0.0, in crates/inga-plugins/wit/, published with each release for authors. Requests and answers cross as JSON text in Inga’s documented shape (docs/plugins/request.md), so new fields do not break the interface; the rest is typed.

A plugin targets a world of its own that imports host (and WASI’s filesystem, clocks and random interfaces) and exports any subset of the five. Inga reads the component’s exports at install and checks them against the manifest’s provides: an interface exported but not declared, or declared but not exported, refuses the install. Not imported, ever: WASI sockets, wasi:http (the network is host.http only), processes.

5. The manifest and the package

Section titled “5. The manifest and the package”

A plugin is a .ingaplugin file: a zip holding plugin.json, the component, its README.md, its LICENSE, optional web/ files for pages and icon.png, and optionally SIGNATURE (§9).

  • id: publisher.name, lowercase letters, digits, - and .; the key of every store. plugin_version: semver. inga: a semver range of Inga versions. world: the WIT world’s major and minor the component was built for.
  • entry.kind: component (part 1) or python / javascript (part 3: entry.path is a script run on the sandbox’s interpreter, §12).
  • applies_to of a filter: all (every request), web (the web UI’s), api (the APIs’), api-nodes (only requests that go to a cloud API node), models: [...].
  • icon of an action: a name among Inga’s own SVG icons, never markup of the plugin’s.
  • limits: at most what the server allows (--plugin-memory, --plugin-call-time).
  • At most 64 MiB unpacked, 200 files; no symbolic links; paths inside the package only.

6. Running plugins

Section titled “6. Running plugins”
  • crates/inga-plugins: the manifest, the store, the review, the host functions and the calls; it uses inga-sandbox’s engine (§12).
  • One warm instance per enabled plugin (InstancePre, instantiated on first use), its calls serialized; a plugin that declares "concurrency": N (at most 4) gets N instances. A pipe’s long answer holds its instance for the answer’s length.
  • Limits per call: the time (epochs; 5 s by default, 10 minutes for a pipe’s answer), the memory (64 MiB per instance), fuel for filters (a filter runs on every request: a budget of fuel per call keeps it from slowing all of them, measured in part 1), output of host.log capped.
  • Failures: a trap, a limit or an error is logged with the plugin’s name and shown (“the filter mask of PII mask failed: stopped after 5 s”). A failing inlet refuses the request with that reason, unless the filter is marked "on_error": "pass" (the user sees which). Five failures in a row disable the plugin, with the reason on the Plugins page.
  • Where filters sit: inlets after Inga reads the request into its internal shape and before routing (so applies_to: api-nodes knows the route), in priority order; outlets after the answer is complete. In a streamed answer an outlet sees the whole text at the end; its change arrives as an inga_replace event the web UI applies, and other clients get it in the final message of the Responses API and in non-streamed answers (said in the docs). Streaming filters, token by token, are open question 4.
  • Informative: every message a filter changed carries inga_filters: [{plugin, filter, changed}]; the web UI shows a small chip (“changed by PII mask”); the server’s log names each call with its time.

7. Permissions

Section titled “7. Permissions”

Asked for in the manifest, shown at install, granted by the user one by one; a permission not granted makes the matching host function return an error the plugin can report.

Permission What it allows Enforced by
network: ["api.example.com", "*.example.org"] host.http to those hosts, HTTPS only unless http:// is written; public addresses only (fetch_url’s is_public, after DNS and on every redirect) host.http
network: ["local"] private addresses too (a NAS, a LAN service) host.http
files.workspace: "read" | "write" the server’s workspace at /workspace; each write approved as write_file’s in part 2 WASI preopens
(always) its own folder at /data ($INGA_HOME/plugins/<id>/data, 256 MiB) WASI preopen, a size check
models: true | ["qwen3-8b", ...] host.chat and host.embed on local models (and API nodes if "api-nodes" is listed) the host
code: true host.run-code in the sandbox, with the sandbox’s own limits the host
sees: ["requests", "answers", "chats"] what filters and actions receive; said plainly at install (“sees every message you send”) the host passes nothing else
  • Tools ask before each call by default when the plugin has network, files.workspace: write or code; the user may choose “run without asking” per plugin at install or later.
  • A new version asking for more permissions asks for the new ones at its update; the old ones stay granted.
  • With users (U1–U2): only an admin installs plugins and grants permissions; groups’ policies allow plugins one by one.

8. Install, catalogues, versions

Section titled “8. Install, catalogues, versions”

From a file or a URL

As skills are: nothing is installed without the review. The review shows the manifest, the README, every file with its size, what the component exports and imports, the permissions with a box each, the licence, the signature (§9) and the SHA-256; --yes installs with every permission asked for (scripts, CI). In the web UI: Plugins → Add (a file or a URL) or the Browse tab, then the same review.

Catalogues reuse the skills’ store (skill_catalog.rs, generalized to a catalogue of kinds): sources are git repositories (every folder with a plugin.json and a built package), or a plugins-index.json:

Listings kept in $INGA_HOME/plugins/.catalog/ and refreshed after six hours, with ETags, as the skills’ are; --offline searches the kept listings. A package whose SHA-256 differs from its listing is refused.

Kept: $INGA_HOME/plugins/<id>/<plugin_version>/ (the package, unpacked), <id>/data/ (its folder), and plugins.json (enabled, the granted permissions, the approval choice, the settings’ non-secret values, the pinned SHA-256 and key, the previous version). Secrets go to the encrypted store of the API node keys.

Versions and updates

  • Never updated by itself. The Plugins page and inga plugin list show Update when a catalogue lists a newer plugin_version that this Inga can run (inga range, world).
  • An update goes through the review, which shows what changed: the version, the files, the permissions added (unticked until the user ticks them), a new signing key.
  • The previous version is kept: inga plugin rollback ID and the page’s Roll back.
  • The settings carry over; keys the new schema drops are removed, new ones take their defaults.
  • The WIT world: Inga runs plugins built for inga:plugin@1.x with x up to its own; a minor version only adds (new functions in host are imports a plugin may ignore, new interfaces are optional exports). A @2.0 keeps @1 loadable for at least two Inga releases, through an adapter, and the page says which plugins need a new build.
  • A plugin whose inga range excludes the running Inga is kept but disabled, with the reason.

9. Signatures

Section titled “9. Signatures”
  • A package may carry SIGNATURE: a minisign signature (Ed25519) of files.sha256, the list of every other file’s SHA-256, signed by the publisher’s key. Verified with ring’s Ed25519, already in Inga (no new crate).
  • The key is given by the catalogue’s entry (key) or the manifest’s key field; at install it is pinned for the plugin (trust on first use). An update signed by another key is refused unless the user accepts the new key in the review, which says it in red.
  • Unsigned packages install from a file or a URL with a warning (open question 2); catalogues may require signatures ("require_signatures": true in an index; the default catalogue would).
  • Inga’s own signing of its releases (TODO.md, signed releases and an SBOM) uses the same format, so one verifier serves both.

10. Web UI

Section titled “10. Web UI”
  • Plugins in the left bar: Installed (each plugin: name, version, author, what it provides, the permissions granted, on / off, Settings, Update, Roll back, Remove, its last errors and calls) and Browse (the catalogues, as the Skills page’s: cards, search, Install, Installed / Update).
  • Settings: a form generated from the schema (text, number, boolean, choice, list, secret as a password field never shown back).
  • In the chat: a Plugins button beside Skills and Tools offers the enabled plugins’ tools (remembered per chat, inga_plugins: true | [ids]); filters work by themselves and show their chip; pipes appear in the model pickers with the plugin’s name; actions are buttons on each message’s toolbar (Inga’s icons, the plugin’s label) with their result in place, in a dialog, or as a download.
  • Pages (part 3): an entry under Plugins in the left bar; the page is the package’s web/ files served at /plugins/<id>/ inside an <iframe sandbox= "allow-scripts"> (no same origin, so no cookies and no Inga API), with a CSP that allows only its own files; it talks to the web UI by postMessage, which relays to pages.call of that plugin only.
  • Texts in the ten languages; a plugin’s own labels are shown as text, never as HTML.

12. One runtime for the sandbox and the plugins

Section titled “12. One runtime for the sandbox and the plugins”
  • One engine, one ticker thread, one cache ($INGA_HOME/sandbox/cache/), one set of limits’ code; the component model is a feature of the same wasmtime.
  • --no-sandbox turns off code runs; plugins have --no-plugins; both off removes every WASM use. A build without the sandbox feature has neither.
  • host.run-code lets a plugin use the sandbox, with its permission.

13. Security

Section titled “13. Security”
  • The attacker: a plugin’s author, or whoever took over their account or key; and, as for every tool, content that steers a model into calling a plugin’s tool.
  • Isolation: the code sandbox’s (spec §12), per plugin: its own instance, memory, folder and store; no sockets; the network only through host.http, which applies the granted hosts and the public-address policy on every redirect.
  • What a plugin sees is what its role needs and the user granted (sees): a tool sees its arguments; a filter the requests and answers it applies to; an action the chat it is pressed in. A filter with network can send what it sees to its hosts: the review says so in those words.
  • Supply chain: the review, the pinned SHA-256, signatures with pinned keys, updates never automatic, permissions added only by the user.
  • The web UI: no plugin markup on Inga’s pages; pages in a sandboxed frame with no same origin; icons from Inga’s set.
  • Availability: the per-call limits, fuel for filters, disabling after repeated failures, --no-plugins to start without any.
  • Secrets: encrypted at rest with the API node keys, given only to their plugin, never returned by the API.

14. Licences and size

Section titled “14. Licences and size”
  • No crate beyond the sandbox’s: the component model, bindgen! and the WIT parser are part of wasmtime (Apache-2.0 WITH LLVM-exception); Ed25519 through ring.
  • No size of their own: the sandbox’s measure (+13.5 MB, its §10) already includes wasmtime’s component-model feature.
  • Plugins are not Inga’s code: each shows its licence at install. A catalogue of Inga’s (open question 3) lists only plugins under an OSI licence, and does not host their files.

15. Tests

Section titled “15. Tests”
  • crates/inga-plugins, with test components committed under crates/inga-plugins/tests/plugins/ (their Rust source beside them, rebuilt by tools/test-plugins.sh and checked by a CI job that has the wasm32-wasip2 target) and small components written in WAT for the host’s edge cases:
    • the manifest: every field checked; provides against the exports; a missing or extra export refuses; sizes, paths, symbolic links;
    • each interface: a tool’s call and result; an inlet passing, changing, refusing; an outlet changing an answer; filters’ order by priority; applies_to; a pipe streaming text and reasoning; an action’s four results;
    • permissions: host.http to a host not granted, to a private address, by a redirect to one (a local HTTP server, as fetch_url’s tests); /workspace without the grant; host.chat without models; kv over its size;
    • limits: an endless loop in a filter stopped, the request refused with the reason (and passed with on_error: pass); memory; five failures disable;
    • signatures: a good one, a file changed after signing, another key at an update, unsigned with and without require_signatures;
    • install and update: from a file, a URL (local server), a plugins-index.json and a git source; the checksum refused; the permission diff; rollback; the world’s version refused or accepted.
  • crates/inga-server: a synthetic model calling a plugin’s tool; a filter changing a request on the OpenAI and the Anthropic routes alike; inga_filters in the answer; a pipe’s model in /v1/models and answering a chat; the routes with and without the admin’s key; tests/api_specs.rs.
  • Web UI: webui_i18n.rs for the keys; a headless-Chromium test installing a test plugin from a file, pressing an action, and seeing a filter’s chip.
