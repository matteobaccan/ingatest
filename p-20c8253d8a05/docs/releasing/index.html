Release process

Versioning: every release bumps the minor version (0.1.0, 0.2.0, …); patch versions (0.1.1) are for fixes only. 1.0.0 is released once the engine is complete enough for everyday use. The planned content of each release is in the design spec (§12) and in TODO.md, the index of todo/ (one file per planned release). 0.0.1 only exercised the pipeline.

Pipeline

Section titled “Pipeline”

Adapted from FastTail (spec §14):

  • .github/workflows/build.yml: tests on Linux for every pull request (a newer push cancels the run still going) and every night on main, and on Linux, Windows and macOS for the release pull request (chore(release): x.y.z or Release x.y.z); no tests on a push to main (a pull request lands up to date with main and green, tools/land.sh) nor on the tag, whose commit is the release pull request’s merge; on a v* tag it builds the release archives (Windows x86-64, Linux x86-64, Linux ARM64, macOS ARM64, macOS x86-64 (Intel), plus -symbols archives) and publishes the GitHub Release, whose body is the downloads grid followed by the CHANGELOG.md section of the version, with a SHA256SUMS file (the SHA-256 of every archive; tools/install.sh checks the archive it downloads against it) and the one-line installers install.sh and install.ps1 from packaging/, listed in SHA256SUMS too (install.md). The macOS binaries are signed and notarized when the signing secrets exist (below); without them they are built as before, signed ad hoc by the linker. Since 0.13.0 it also pushes the Docker image ghcr.io/matteobaccan/inga:<version> and :latest (x86-64 and ARM64, from the Linux archives; docker/release.Dockerfile).
  • .github/workflows/release-tag.yml: when Cargo.toml changes on main, tags v<version> if the tag does not exist and CHANGELOG.md has a ## [<version>] section (written by the release pull request from the fragments), then starts build.yml on the tag. It needs the repository secret RELEASE_TOKEN (a fine-grained token on this repository with Contents and Workflows write access) whenever the release changed files under .github/workflows: GitHub refuses the workflow’s own token then, by push and by the REST API alike. Without the secret, tag by hand (git tag vX.Y.Z <sha> and git push origin vX.Y.Z) or run the workflow with its sha input once the secret exists.
  • .github/workflows/talks.yml: the talk decks (talks/) built as HTML with a pinned Marp CLI; release-tag.yml starts it after tagging, and it keeps the decks of that tag (inga-talk.it.html, inga-talk.en.html) as the workflow artifact inga-talks-<tag> for 90 days, never in the release (the maintainer’s own presentation material); run without a tag, the artifact is inga-talks.
  • .github/workflows/install.yml (Installers): when packaging/ changes, the installers’ tests against fake releases on a local server, on Linux, macOS and Windows (PowerShell 7 and 5.1), and packaging/render.py’s self-test.
  • .github/workflows/changelog.yml: on every pull request, fails one that edits CHANGELOG.md (except the release pull request, or one labelled changelog-ok), checks the fragments in changelog.d/ (python3 tools/changelog.py check) and runs the script’s tests.
  • .github/workflows/gpu.yml (the maintainer’s GPU runner, gpu-runner.md): the GPU tests, and on pull requests labelled gpu the bench of the base against the pull request, interleaved, with a comment and a GPU bench check. The check is ❌ for a regression over 3 % beyond the noise and confirmed by a second measure, ⚪ when the label perf-regression-ok accepts it or the bench gave no result, ✅ otherwise (how to read it). It is not a required check until its noise has been measured (compare: noise). gpu-bench-sweep.yml starts again the benches lost in the queue; gpu-bench-accept.yml follows the label.
  • .github/workflows/issue-triage.yml and docs-align.yml (Claude Code, secret ANTHROPIC_API_KEY, claude-actions.md): answer and label issues, and open a docs: aligned with <sha> pull request when a push to main leaves the docs out of date. Neither touches code or releases.

macOS signing and notarization

Section titled “macOS signing and notarization”

Prepared in build.yml, off until the maintainer adds the secrets. Goal: Mac binaries that open without Gatekeeper’s warning even when downloaded with a browser. Until then tools/install.sh avoids the warning (it downloads without a browser, so the file is not quarantined), and the install guide gives the xattr command for a browser download.

What the build does with the secrets. In the build job, for each macOS target, after cargo build and before the archive is packed:

  1. Sign: the Developer ID Application certificate (MACOS_CERT_P12) goes into a temporary keychain with a random password, and codesign --force --options runtime --timestamp signs inga with that identity (hardened runtime, Apple’s timestamp); codesign --verify --strict checks it.
  2. Notarize: inga zipped (ditto), sent with xcrun notarytool submit --wait and the App Store Connect API key; anything but Accepted prints notarytool log and fails the job, so no release is published with an unnotarized Mac binary.
  3. Clean up (always, even after a failure): the keychain, the .p12, the .p8 and the zip are deleted.

The archive is then packed from the signed binary, as today. The job learns whether the secrets exist through MACOS_SIGNING (true / false, set from the secrets in the job’s env); the secrets themselves reach only the steps that use them, never cargo build. Without MACOS_CERT_P12 the steps are skipped and the job is the same as before.

Not verified. None of this has run: there are no secrets yet. The first release after they are added is the test: read the macOS jobs’ log, then on a Mac codesign -dv --verbose=4 inga (the Developer ID and flags=0x10000(runtime)) and spctl -a -vv -t install inga or simply opening a browser-downloaded copy. The hardened runtime has not been tried with Inga either (Metal through the Objective-C runtime, memory mapping): if something needs an entitlement, the first signed build will show it.

One-time setup (the maintainer; agents never ask for or handle the values):

  1. Join the Apple Developer Program (99 USD a year).

  2. Create a Developer ID Application certificate (Xcode → Settings → Accounts → Manage Certificates → +, or a certificate signing request from Keychain Access uploaded at developer.apple.com → Certificates), then export it with its private key from Keychain Access as a .p12 with a password.

  3. Create an App Store Connect API key (App Store Connect → Users and Access → Integrations → App Store Connect API, team key, role Developer): download the .p8 (it can be downloaded once), and note its Key ID and the Issuer ID.

  4. Add five repository secrets (Settings → Secrets and variables → Actions):

    Secret Value
    MACOS_CERT_P12 the .p12 in base64 (base64 -i cert.p12 | pbcopy)
    MACOS_CERT_PASSWORD the .p12’s password
    APPLE_API_KEY the contents of the .p8 file
    APPLE_API_KEY_ID the key’s ID
    APPLE_API_ISSUER the issuer ID

Stapling. Apple’s notarization ticket cannot be stapled to a bare executable (only to an app bundle, a disk image or an installer package), so on the first run of a signed inga Gatekeeper asks Apple’s servers online; offline, the first run of a browser-downloaded copy may still be stopped. A .pkg installer would carry a stapled ticket (backlog, “Installers”).

Homebrew is not published: a tap’s formula cannot download a private repository’s release assets without a custom download strategy holding a token. The formula, with Scoop’s and winget’s manifests, is prepared in packaging/ for the day the repository is public (backlog, “Installers”).

Cadence

Section titled “Cadence”

Decided by the maintainer on 2026-10-19:

  • A release every two days, with what is on main and green: 0.x.0 when it holds a feature, 0.x.y for fixes only.
  • What fits in two days: one high- or two medium-effort items, plus fixes. A larger item is split into parts, each usable on its own or invisible until complete.
  • The second day is for fixes: then the release pull request. An item that is not ready moves to the next release; it never holds this one.
  • Measurements on real hardware do not hold a release: what is not measured is said in the release’s changelog section and goes into todo/real-world-checks.md.
  • A check that needs the maintainer moves to the next release (decided by the maintainer on 2026-10-22): a run on Colab, a GPU or one of the maintainer’s machines never holds a release; the release ships with what is built and tested, and the check goes into the next release’s file or todo/real-world-checks.md, done as soon as the maintainer can. The releases go on one after the other.
  • A user’s bug report comes first: it goes into the next release.
  • Three releases planned, the rest in the backlog: only the next three releases have a file in todo/. At each release’s planning (step 6) the inbox (todo/inbox.md) is triaged into the backlog (todo/backlog.md), a release the maintainer approves, or dropped, and the release three ahead is planned from the backlog with the maintainer. A planned release changes only when the maintainer decides.

Checklist

Section titled “Checklist”
  1. Check open issues and pull requests before every release (asked by the maintainer): new bug reports, model requests and ideas. Fix or schedule each one (a file of todo/), and answer it.
  2. All acceptance criteria of the release pass (design spec, §12), CI is green on main (its last nightly run) and on the release pull request. Mesh stress. When the release changed the mesh’s code (crates/inga-dist, src/commands/mesh.rs, the mesh parts of src/commands/serve.rs and crates/inga-server), run .github/workflows/stress.yml (Actions → Mesh stress → Run workflow; 30 runs on Linux, Windows and macOS by default) on main before the tag, and fix any failure: no nextest retries hide a flaky test. GPU bench. List the pull requests merged since the last release whose GPU bench check is ❌ or ⚪ accepted (perf-regression-ok) (each one’s check gives the rows and the gaps): every accepted regression is named, with its reason, in the release’s CHANGELOG.md section, and an unexplained ❌ is measured again (gpu.yml by hand with compare: base) before the tag. A ⚪ no result means the pull request was never measured: when it touched GPU or kernel code, measure it by hand (compare: base, ref its commit on main, base the commit before it).
  3. Use cases. Every user-visible use case of the release (something a person does, not an internal change: read the release’s changelog.d/ fragments for them) has its row in use-cases/README.md (the index the short README links since 2026-11-06), under its topic, with its guide: a from-zero guide in use-cases/ (follow the template there) for a use case a newcomer would look for by name, else a section of an existing guide linked by its anchor; the guide’s “Supported since” line names the release. python3 tools/release.py use-cases checks that every guide is linked from the index and that every row links a guide and a heading that exist (tools/check.sh and tools/release.py X.Y.Z run it too); which use cases the release brought is checked by hand. Re-run every existing guide and fix anything that changed.
  4. Update README.md (its status line; it stays about 250 lines, the long tour is features.md, the commands cli.md, the questions faq.md) and the “Current state” section of AGENTS.md. All documentation is in English only. Performance. Re-run the measurements in performance.md that the release can affect, with the release build, on the same machine and models, and overwrite their rows (the page keeps only the latest measurement of each, with the Inga version and date that produced it; the history is in git). Comparison. In comparison.md, mark every feature the release shipped in the Inga column with ✅ and the version (🟡 and the version for a partial one), checking every row, not only the ones planned for this release. Talks. In both decks of talks/ (inga.it.md and inga.en.md, the same slides), the release pull request updates the version (the footer and the title slide), the feature slides (what it does, before / after, what to keep), the performance slides (from the rows just overwritten in performance.md, each with its configuration and link) and the roadmap (the release titles of TODO.md‘s index), plus the tag count on the development slide; the “coming” pills (<span class="tag">x.y.z</span>) of what the release shipped are removed, the counts taken from the docs (providers, browser models) checked again, the slides of a new feature added in both decks with their lengths, and the slide counts of talks/README.md updated; the screenshots come from docs/images/, so a web UI change refreshes them there; python3 tools/talk.py check must pass. After the tag, talks.yml builds the decks’ HTML pages and keeps them as the artifact inga-talks-<tag>, not in the release. Website. The site in site/ (website.md) follows the product by itself at every build: the documentation from docs/*.md, the latest release from CHANGELOG.md, the roadmap from TODO.md and docs/todo/, the “coming in x.y” badges cleared once CHANGELOG.md names that release, the icons and the logo from the web UI’s page. The release pull request updates by hand what the landing page (site/src/pages/index.astro) says in its own words: the features the release shipped, the numbers taken from the rows just overwritten in performance.md (each with its configuration and version), a new coming('x.y.z') badge for what the next releases announce; then npm run build, npm run check:seo and npm run check:links in site/ must pass (the Website workflow runs them too).
  5. Release PR chore(release): x.y.z. python3 tools/release.py x.y.z --summary-file summary.md does the mechanical part below (the versions, the changelog, README’s status line, the decks’ version, date, specs, tags and days), runs tools/check.sh and lists what is left by hand. The parts: version in Cargo.toml ([workspace.package]) and Cargo.lock, and info.version in docs/api/*.yaml (tests/api_specs.rs checks it); the changelog: write the release’s summary paragraph in a file and run python3 tools/changelog.py release x.y.z --summary-file summary.md, which gathers every changelog.d/ fragment into a new ## [x.y.z] - date section of CHANGELOG.md (grouped Breaking, Added, Changed, Fixed), adds its compare link and deletes the fragments; read the section and polish it. This is the one pull request allowed to edit CHANGELOG.md (the Changelog check knows it by its branch release/* or its title Release x.y.z / chore(release): x.y.z). Merge when CI is green: the tag and the GitHub Release follow automatically. Check the release page.
  6. Re-survey the other projects, as sources of new ideas: the engines in comparison.md, the apps in its Part 2, the routers and gateways in its Part 3 (LiteLLM, OpenRouter, Portkey, Kong AI Gateway, Envoy AI Gateway, RouteLLM, NVIDIA LLM Router, llama-swap, Open WebUI connections) and its coding-agent proxies (free-claude-code, Claude Code Router), the Apple-side projects in comparison.md (mlx-serve, Rapid-MLX, Higgs, uzu, lithos-metal, Edge0), and any new notable project found:
    • re-survey a project’s features only if more than one week has passed since its “Last surveyed” date (features do not ship every day);
    • then check its README, releases and changelog since the last survey;
    • update its row in every feature table, the star count and the “Last surveyed” date;
    • add newly relevant projects and features;
    • update the Inga column of every comparison table (the Inga table of each section in the three parts of comparison.md) with what this release shipped, at every release, whether or not the other projects were re-surveyed.
  7. Update the TODO list (the index ../TODO.md, the files of todo/). The release’s file (docs/todo/X.Y.Z.md) is closed: remove the items the release shipped (CHANGELOG.md says what shipped, the spec’s “As built” section how; what is left of an item stays, or becomes, an open item), then run python3 tools/todo-release.py X.Y.Z NEXT (NEXT is the next planned release; --dry-run prints what it would do): it removes the items marked done, moves every item still open to the top of docs/todo/NEXT.md marked “(moved from X.Y.Z)”, deletes docs/todo/X.Y.Z.md and its line in the index; refresh the open counts of the index’s lines by hand. Then triage todo/inbox.md, where every feature newly seen elsewhere (engines, apps, routers and gateways alike) and every news item landed, and plan the release three ahead from todo/backlog.md with the maintainer (“Cadence” above: what fits in two days). Add what the release could not check (real model files, real clients, several machines, other hardware and operating systems, speed on the maintainer’s machines) as bullets in the right group (A–E) of todo/real-world-checks.md, tagged with the release ((x.y.z)) and with [runner] when the maintainer’s runner can close it (.github/workflows/real-checks.yml), [manual] otherwise; remove the checks that passed.
  8. Plan the next release in its docs/todo/ file, against the code just released.
