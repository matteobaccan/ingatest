The website

Inga’s website lives in site/: a landing page that presents the product and the documentation, made from this docs/ folder. It is private until Inga goes public (phase 5 of the launch plan): it is built by CI and downloaded as an artifact, and an unlisted preview follows main (below). The browser page stays where it is (https://matteobaccan.github.io/ingatest/, wasm.md); the landing page’s Try in your browser links to it.

What it is made of

Section titled “What it is made of”

  • Astro and Starlight (exact versions in site/package.json and site/package-lock.json), with Pagefind for the search: a static site, no server.

  • The landing page, site/src/pages/index.astro and site/src/styles/landing.css: Inga’s colours (the web UI’s Light and Dark tokens), its logo, the icons of the web UI’s sprite, the screenshots of docs/images/. Light and dark follow the computer, and the theme button (shared with the documentation) picks one.

  • The documentation: written by site/scripts/sync-docs.mjs at every build from docs/**/*.md and the README.md‘s Quick start (the command-line reference and the FAQ are docs/cli.md and docs/faq.md since 2026-11-06) into site/src/content/docs/ (ignored by git). The Markdown in docs/ stays the single source: the script adds the title from each file’s first heading, removes the source header and rewrites the relative links: to the page a file became, to the copied screenshots, or to the file on GitHub when it is not on the site. docs/superpowers/specs/ (the specs, for contributors), docs/research/, docs/talks/ (Marp slide decks, one heading per slide), and the maintainers’ tools docs/todo/, docs/comparison.md and docs/experiments.md are left out: their links go to GitHub.

  • The landing page’s facts come from the repository too: the latest release from CHANGELOG.md, the roadmap from TODO.md’s “Feature releases” and their files in docs/todo/, the icons from crates/inga-server/webui/html/icons.svg. The numbers it shows are docs/performance.md’s, with their caveats; a new measurement there means an edit of the landing page.

  • Motion: the hero shows the web UI’s animated mark, the same SVG and <style> as the #logo button of crates/inga-server/webui/html/shell.html (copied at every build into site/src/generated/logo-animated.svg): its loop (the brain bursting into sparks and coming back) starts once the page has loaded and is idle, runs only while the hero is on screen, and a hover gives it the web UI’s short turn. The feature cards’ icons (the web UI’s sprite) take the same turn on hover and draw their strokes once when they scroll into view. No animation library: CSS and a few lines of the page’s script. With prefers-reduced-motion nothing moves.

  • Pictures: sync-docs.mjs turns each screenshot of docs/images/ into AVIF and WebP, full size and 800 wide (sharp, a few seconds). The landing page shows them with <picture>, srcset, sizes, width and height (no layout shift) and lazy loading below the hero; in the docs a screenshot becomes an <img> of its WebP copy with the same attributes, and its link still opens the PNG.

  • The screenshots themselves are made from the web UI’s code, not by hand: node tools/screenshots/stubbed.cjs --docs takes every part of the web UI and the browser page on a staged machine (no build, no server, every route stubbed), into docs/images/webui-NAME.png, and webui-NAME-dark.png for the shots marked dark: true in stubbed.cjs; the landing page’s tabs name a picture by file and take its -dark twin for the dark theme, so a new tab’s picture needs that mark. node tools/screenshots/stubbed.cjs --check fails when crates/inga-server/webui/ or web/ changed since the pictures were taken (the stamp tools/screenshots/docs-images.json): tools/release.py and the release pull request’s CI run it (the checklist).

The sidebar’s groups are in site/astro.config.mjs: a new file of docs/ lands in its group by itself under use-cases/ and integrations/; a new top-level file needs a line there, or a place in the script’s EXCLUDED list to stay off the site.

Run it locally

Section titled “Run it locally”

Node.js 22.12 or later:

SITE_BASE=/inga/ npm run build builds it for a sub-path (GitHub Pages of a repository), SITE_URL sets the host for the canonical links and the sitemap, BETA_URL where Try in your browser goes.

Search engines and social cards

Section titled “Search engines and social cards”
  • Every page has its title (Page | Inga in the docs), a meta description (in the docs, the front matter’s: sync-docs.mjs takes the first paragraph that says what the page is about, skipping a guide’s “Supported since” line), an absolute canonical link, Open Graph and Twitter tags and the sitemap link. Absolute URLs are SITE_URL + SITE_BASE, so they are right under /inga/ and in the preview folder too.
  • The social card is site/public/social-preview.png (1200 x 630), drawn from the landing page’s own design by site/scripts/social-preview.mjs with Playwright’s Chromium (npm run social-preview, by hand when the design changes; it needs Playwright installed in site/ or globally, CHROMIUM= picks the browser) and committed.
  • Structured data: the landing page has JSON-LD for a SoftwareApplication (DeveloperApplication, MIT, free, by Matteo Baccan, the release) and the WebSite.
  • robots.txt (site/src/pages/robots.txt.ts) allows everything and names the sitemap (sitemap-index.xml, made by Starlight under the base). Crawlers read it only at a host’s root, so it counts with a custom domain at /; under /inga/ the sitemap is found through the pages’ <link rel="sitemap">. The site itself never says noindex: the private preview adds it in its own workflow.
  • No hreflang: the site is in English only.

Speed (Lighthouse)

Section titled “Speed (Lighthouse)”

Lighthouse 13.5.0 with Chromium 141 headless (--chrome-flags="--headless --no-sandbox"), its default simulated throttling (mobile: a Moto G Power, slow 4G, CPU x4; desktop: --preset=desktop), against the built site (SITE_BASE=/) served by python3 -m http.server, on a 4-vCPU Linux container, 2026-10-16. One run per cell; repeated runs moved TBT by 0–60 ms and LCP by 0.1 s. Scores: Performance / Accessibility / Best practices / SEO.

Page, device Before: scores Before: LCP, CLS, TBT After: scores After: LCP, CLS, TBT
Landing, mobile 99 / 100 / 100 / 100 2.0 s, 0, 10 ms 100 / 100 / 100 / 100 1.7 s, 0, 0 ms
Landing, desktop 100 / 100 / 100 / 100 0.4 s, 0, 0 ms 100 / 100 / 100 / 100 0.4 s, 0, 0 ms
Quick start (docs), mobile 98 / 100 / 100 / 100 2.1 s, 0, 0 ms 98 / 100 / 100 / 100 2.1 s, 0, 0 ms
Quick start (docs), desktop 100 / 100 / 100 / 100 0.5 s, 0, 0 ms 100 / 100 / 100 / 100 0.5 s, 0, 0 ms

The landing page went from 219 to 172 KiB: its stylesheet inlined (no render-blocking request), the hero’s screenshot 800 wide in AVIF on phones instead of the 1280-wide PNG. The animated mark first cost it 94 on mobile (TBT 270 ms: the loop’s clipped paths repainted while the page loaded), hence the loop that waits for the page to be idle. What is left: the docs’ render-blocking Starlight stylesheet (65 KB) and Pagefind’s script loaded with every page (26 KiB unused at first) are Starlight’s; the remaining “document latency” is http.server’s lack of compression, which GitHub Pages does; cache lifetimes cannot be set on GitHub Pages. No web fonts (system fonts), so no font to preload or swap.

How it is checked and shared

Section titled “How it is checked and shared”

The Website workflow (.github/workflows/site.yml) runs only when site/**, docs/**, README.md, CHANGELOG.md, TODO.md or the web UI’s page change (a separate workflow, because build.yml skips Markdown-only changes): npm ci, npm run build, npm run check:seo (every page has a title, a description, an absolute canonical link and og:image, alt text on its pictures, one h1 and no skipped heading level, and names none of the words the maintainer decided the site must not name, kept as SHA-256 digests turned into numbers in check-site.mjs, so the list names none of them) and npm run check:links (every link, picture and script into the site leads to a built file, and an anchor to another page to one of its ids; site/scripts/check-site.mjs), then the built site is uploaded as the artifact inga-website (kept 5 days). To look at it, download the artifact from the run, unzip it and serve the folder (npx serve inga-website or python3 -m http.server -d inga-website); opened as plain files, the search and the links between pages do not work.

The unlisted preview

Section titled “The unlisted preview”

On every push to main that runs site.yml, its preview job builds the site again with its base under /ingatest/p-20c8253d8a05/, marks every page noindex (and a robots.txt that disallows all), and pushes it to the folder p-20c8253d8a05/ of ingatest’s gh-pages: https://matteobaccan.github.io/ingatest/p-20c8253d8a05/. It uses the same deploy key (INGATEST_DEPLOY_KEY) and clone as the browser page below, replaces only that folder, and shares the concurrency group ingatest-pages with pages.yml, so two pushes never race. Pull requests do not publish. Without the key the job is green with a “Not published” notice. The branch site-preview and its workflow site-preview.yml are no longer needed (the branch is not deleted).

How the browser page is published

Section titled “How the browser page is published”

This repository is private, and on GitHub Free, GitHub Pages serves public repositories only. So the workflow pages.yml builds the page here and pushes only the built page (the folder web/ with the WebAssembly modules of tools/build-wasm.sh, a README.md and .nojekyll; never Inga’s source) to the gh-pages branch of the public repository matteobaccan/ingatest, which GitHub Pages serves at https://matteobaccan.github.io/ingatest/.

  • When: on every push to main that touches web/, crates/inga-wasm/, crates/inga-webgpu/, tools/build-wasm.sh or the workflow, and by hand (Actions, Inga in the browser on GitHub Pages, Run workflow).
  • How: the workflow clones gh-pages of ingatest with an SSH deploy key, replaces its files with the new build and commits Inga web <short commit> (the history is kept; nothing else of this repository is named), then pushes. The first run creates the branch. The top-level folders p-* of gh-pages are left as they are: they hold unlisted previews pushed by other workflows (the website’s, from site.yml), and web/ may not have a p-* entry of its own. Both workflows share the concurrency group ingatest-pages, so their pushes never race.
  • Without the key (the secret INGATEST_DEPLOY_KEY unset) the page is built, as a check, and not published: the run is green with a “Not published” notice.
  • Paths: every address in the page is relative, so it works under /ingatest/; the service worker that isolates the page (coi.js registers coi-sw.js next to itself) has the scope /ingatest/.
  • The report: the published page’s inga-report-repo meta tag is set to matteobaccan/ingatest, inga-guide to ingatest’s README (no script reads it at the moment: About’s and the side bar’s guide links point to wasm.md), and inga-report-template to the repository variable INGATEST_REPORT_TEMPLATE (empty: a plain issue with the report as its text). A local build (web/ as it is) still reports to this repository with the form.

One-time setup (the maintainer)

Section titled “One-time setup (the maintainer)”
  1. matteobaccan/ingatest exists, public, with a main branch (created with “Add a README file”), so gh-pages does not become its default branch.
  2. On a PC, make a key pair with no passphrase: ssh-keygen -t ed25519 -N "" -C "inga web" -f ingatest_deploy (two files: ingatest_deploy, private, and ingatest_deploy.pub, public).
  3. ingatest → Settings → Deploy keys → Add deploy key: paste the content of ingatest_deploy.pub, tick Allow write access, Add key.
  4. inga → Settings → Secrets and variables → Actions → New repository secret: name INGATEST_DEPLOY_KEY, value the whole content of the private file ingatest_deploy (from -----BEGIN OPENSSH PRIVATE KEY----- to -----END OPENSSH PRIVATE KEY-----). Then delete both files from the PC.
  5. Run the workflow once (inga → Actions → Inga in the browser on GitHub Pages → Run workflow); it also runs at the next push to main that touches web/. The first run creates the gh-pages branch on ingatest.
  6. ingatest → Settings → Pages → Build and deployment → Source Deploy from a branch, branch gh-pages, folder / (root), Save. The page is at https://matteobaccan.github.io/ingatest/ a minute later.

Optional, for the report as a form instead of a plain issue:

  1. On ingatest’s main branch, add the file .github/ISSUE_TEMPLATE/wasm-report.yml with the content below (issue forms are read from the default branch, not from gh-pages).
  2. inga → Settings → Secrets and variables → Actions → Variables → New repository variable: INGATEST_REPORT_TEMPLATE = wasm-report.yml, then run the workflow. A form added there under its earlier name, wasm-beta-report.yml, keeps working while the variable names it: the page uses the file name the variable holds.

The field ids (browser, gpu, model, speeds, log) are the ones web/report.js fills: keep them as they are.

Switching it off

Section titled “Switching it off”
  • Stop publishing: delete the secret INGATEST_DEPLOY_KEY (the runs stay green and publish nothing), or disable the workflow (Actions → Inga in the browser on GitHub Pages → ⋯ → Disable workflow). Removing the deploy key on ingatest also stops it, with a red run.
  • Take the page down: ingatest → Settings → Pages → Source None (or delete the gh-pages branch). Visitors keep the stored models in their browsers until they clear the site’s data.

When Inga goes public

Section titled “When Inga goes public”

Phase 5 of the launch plan moves the site to the main repository’s GitHub Pages:

  1. In .github/workflows/site.yml, after the build, publish site/dist with actions/upload-pages-artifact and actions/deploy-pages, built with SITE_BASE=/inga/ (or / with a custom domain), on pushes to main.
  2. Repository settings, Pages: source “GitHub Actions”.
  3. The browser page then moves under the same site (for example /inga/try/): the landing page’s BETA_URL follows it, and pages.yml builds both into one folder.
  4. The README links the site.
