Performance

Inga’s speed next to llama.cpp, on the same machine, files and commands. Prompt processing (prefill, pp: what the first token waits on) and generation (decode, tg: what the rest of the answer waits on) are in separate tables: prefill is bound by the matrix products’ arithmetic, decode by reading the weights.

Each row is the latest measurement of that test, with the Inga version and date that produced it; a new measurement overwrites its row. What each step of the speed work gained is in experiments.md, older numbers in git (and, from 0.46.0 on, in CHANGELOG.md).

Where Inga stands

Section titled “Where Inga stands”
  • Generation on the CPU (machine A’s earlier host, 2026-10-09/10): faster than llama.cpp on 1B-class models (1.3x to 1.7x), after a long prompt too; level on the 135M model’s Q8_0, Q5_0 and Q5_1 with four threads.
  • Prompt processing on the CPU (machine A’s earlier host): level on 128 tokens of the 1B model, 0.84x–0.86x at 512 and 2048 tokens, about 0.5x against llama.cpp’s AMX path on the 135M model.
  • 4-bit types llama.cpp interleaves at load (machine A’s earlier host): Q4_1 and IQ4_NL decode with four threads at 0.66x and 0.72x. Machine A’s current host has only llama.cpp’s side so far (its table): no ratio yet.
  • A tester’s RX 9060 XT (machine D, Vulkan): generation on Qwen3.8-27B Q4_0 1.1x llama.cpp’s; prompt processing 0.4x, the known weak spot on Vulkan.
  • The maintainer’s laptop (machine B, 2 cores, AVX2, CPU only): generation 0.96–1.3x llama.cpp’s on Llama-3.2-1B (both bound by the RAM), prompt processing 0.8–1.0x (2026-10-14).
  • A model larger than its RAM budget (machine C, CPU): Qwen3-30B-A3B Q4_K_M (17.28 GB) gives the same text in 8, 4 and 2 GB of RAM as with all of it in RAM, at 6.7, 2.5 and 1.7 tok/s with the OS file cache, 3.3 and 0.8 at 8 and 4 GB past it (the table, 2026-10-15).
  • The P1000 (machine C, 2026-10-16, against llama.cpp b11489): generation on CUDA 1.1x–1.6x llama.cpp’s (0.5B–1B models, every layer on the card); on Vulkan 0.5x–0.76x. Prompt processing on CUDA 0.25x–0.42x, the widest gap of one stream; on Vulkan 0.32x–1.33x (ahead at 128 tokens on three of four models, behind at 512). On the CPU, 1.04x–1.27x except Llama-3.2-1B’s generation (0.86x–0.95x).
  • An A100 (machine E, CUDA, 2026-10-24, Inga ee60ddef, the code of main 51cbffa, against llama.cpp b11489): generation 0.90x–1.03x llama.cpp’s on five Q4_K_M models (1B to 30B-A3B); prompt processing 0.94x–0.99x at 512 tokens and 1.00x–1.12x at 2048 on the dense ones, Qwen3-30B-A3B’s 2048-token prompt 1.62x (its mixture whole on the GPU), LFM2-1.2B’s 0.50x–0.67x the weak spot (the tables).
  • Serving many users (machine E, 2026-10-24, Inga 3bbb5222 against llama-server b11489 and vLLM 0.32.0): the widest gap measured. Inga’s total throughput stays at about 255 tok/s from 8 to 64 clients (Qwen3-8B and Qwen3-30B-A3B Q4_K_M, 256-token answers); llama-server reaches 756 at 64 clients on Qwen3-8B (2.9x) and vLLM with 4-bit AWQ 4955 (19x), 3821 even in BF16; with one client Inga gives 94 tok/s, llama-server 126, vLLM’s AWQ 173 (the tables). These runs are from before #901.
  • Many users with inga bench --users (machine E, 2026-10-24, Inga 3ec4272b, #901’s branch): decode groups of 16 to 64 sessions on CUDA (debug.cuda_big_groups) raise Qwen3-8B Q4_K_M’s total from 288.4 to 417.1 tok/s at 16 users (+45 %) and from 279.9 to 474.4 at 64 (+70 %); 1 and 8 users unchanged, a mixture of experts unchanged (it keeps groups of eight) (the table). inga serve under load was not measured again with them.

Inga / llama.cpp is Inga’s speed over llama.cpp’s fastest run on the same test (its default, which repacks weights and uses AMX, or --repack 0, the weights as stored): above 1, Inga is faster. Rows sorted by the gap, furthest behind first.

Compared on one machine (inga bench --compare)

Section titled “Compared on one machine (inga bench --compare)”

Numbers from different machines, models and quantizations do not compare. A comparison worth quoting says, next to its numbers, which model file and quantization ran, how long the prompt and the answer were, on how many threads and on which device, and how many runs were averaged. inga bench --compare measures the same file on Inga and on the other engines of the machine and prints all of it in one table:

  • The configuration above the table: the file and its size, the architecture, the quantization (general.file_type), the prompt and answer lengths (greedy), the threads, Inga’s device (the GPU and its layers), the machine’s CPU and system, and the runs: one warm-up, then -r measured runs (3 by default, as Sipp’s and WebLLM’s comparisons do), mean ± standard deviation.
  • The columns: the time to first token (TTFT, from the start of the request to the first token, the prompt’s processing included; the load is its own column), prefill (the prompt’s tokens over its time), decode (the tokens after the first over their time) and end-to-end (start to last token), in milliseconds and tokens per second.
  • Inga runs in its own process on a prompt of -p tokens of a fixed English text (each run starts with Run N., so no cache helps).
  • llama.cpp: llama-bench -p P -n N -pg P,N -r R -t T -ngl 0|99 -o json (--llama-bench PATH when it is not on the PATH; -ngl 99 when Inga has layers on a GPU). llama-bench times no first token: its TTFT is its prompt test’s time, marked ¹ (the first token comes from the prompt’s last logits), and its prompt is random token ids.
  • Ollama (--ollama-url, default http://127.0.0.1:11434; ollama serve must be running): the file is imported as a temporary model (/api/blobs, /api/create) and removed at the end; the same text through /api/generate (raw, greedy, num_predict, num_thread, num_gpu 0 when Inga ran on the CPU), streamed; TTFT on the client’s clock (HTTP included), prefill and decode from Ollama’s own counters, the load from a first request after unloading it. An engine that stops at the end of the text writes fewer tokens than asked: its answer column says how many.
  • --json gives the same as one object (setup, engines), to keep with a report.

An engine that is not there (no llama-bench, no Ollama answering) gets a row that says why, and the others are measured. Inga serves the same measures per request: inga_timings (ttft_ms, prompt_ms, predicted_ms, load_ms when the request loaded the model) in the OpenAI responses, LM Studio’s stats.time_to_first_token, Ollama’s load_duration, and inga_time_to_first_token_seconds_total / _last in /metrics. In the browser, each answer and the Standard test give the time to first token (wasm.md).

How to measure

Section titled “How to measure”
  • inga bench with the release build (each prompt row also gives its time to the first token, TTFT p50 ms; ttft_p50_ms, ttft_p95_ms, ttft_mean_ms in --json, as --users gives them): inga bench FILE -p 128 -n 64 -t 1,4 -r 5 (machine A’s short prompt), -p 512 -n 0 and -p 2048 -n 32 for long prompts; llama.cpp with llama-bench -m FILE and the same options. --profile prints the time of each operation kind per token.
  • --ab KEY=VALUE runs the same bench with and without a setting of inga.toml (a [debug] switch such as debug.vk_tiles=false, or gpu.max_load=50), alternated, and stops at the first logit that differs.
  • --ctx-sweep gives prefill and decode at each context frontier (2K to 32K by default; --csv in ds4-bench’s columns).
  • --users 1,4,8 is a load test, as vLLM’s benchmark_serving: that many sessions at once, each with a prompt of -p tokens and -n generated, run as inga serve --parallel N runs them; total and per-user tokens per second, time to the first token and inter-token latency (p50 / p95), and the decode steps per pass of the model (batch, or turns where the sessions cannot be batched yet).
  • inga image --timings prints, after the picture, the load, the prompt’s encoding, every sampling step (the first one also reads the mapped weights from the disk: the steps after it are the steady state), the VAE’s decoding and the peak resident memory (Linux). Compare two runs with the same seed, size, steps and sampler: the PSNR of their pictures first, then the times.
  • The GPU workflow (.github/workflows/gpu.yml, run by hand on machine C): model plus compare: llama.cpp measures Inga and the pinned llama.cpp release (LLAMA_CPP_BUILD) on the CPU, CUDA and Vulkan, pp512 and tg128; compare: base measures a branch against its base, the two interleaved, with the verdict of a pull request’s bench; compare: noise measures a commit against itself, which is how the threshold below is checked; compare: perf measures Inga and llama.cpp model by model on the three devices (machine C’s table above); without compare, tests sets the bench’s arguments when it starts with - (e.g. -p 512 -n 128 -r 3 --ab debug.vk_tiles=false). See gpu-runner.md.

The rule for performance changes

Section titled “The rule for performance changes”

A pull request that changes speed (kernels, scheduling, memory layout, a GPU path) merges only when:

  1. Same output: correctness tests show the same output as the reference — RefBackend, the CPU path for GPU work, plain decoding for speculative or batched decoding. A change behind a [debug] switch of inga.toml shows it with inga bench --ab debug.X=VALUE. A change to long prompts or attention also shows the curve before and after with inga bench --ctx-sweep, with --ab when it is behind a switch.
  2. Measured gain, no regression: a before / after inga bench on the same machine — the maintainer’s P1000 through the GPU runner for GPU work (the model input of .github/workflows/gpu.yml), the Linux CI runner or the development machine for CPU work — shows a gain and no test slower by more than 3 %.
  3. The table in the PR: the pull request carries the before / after table; label it gpu and the GPU runner posts it as a comment, the base against the pull request on the CPU, CUDA and Vulkan, with a GPU bench check that turns red on a regression over 3 % beyond the noise and measured twice; the label perf-regression-ok accepts a known one (gpu-runner.md).
  4. Logged: the result goes into experiments.md, whatever it is.

The maintainer, 2026-10-11: “bring in all the ideas; for the performance ones always run measurements; libraries that can be integrated without runtime dependencies, try them”. Every performance idea taken from another project (TODO.md) is measured this way before it is kept. An idea that does not pay off is not deleted: it is logged in experiments.md as “set aside”, with its numbers and the conditions under which it could work.
