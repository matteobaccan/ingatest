Performance

Inga’s speed next to llama.cpp, on the same machine, files and commands. Prompt processing (prefill, pp: what the first token waits on) and generation (decode, tg: what the rest of the answer waits on) are in separate tables: prefill is bound by the matrix products’ arithmetic, decode by reading the weights.

Each row is the latest measurement of that test, with the Inga version and date that produced it; a new measurement overwrites its row. What each step of the speed work gained is in experiments.md, older numbers in git and CHANGELOG.md.

Where Inga stands

Section titled “Where Inga stands”
  • Generation on the CPU: faster than llama.cpp on 1B-class models (1.3x to 1.7x), after a long prompt too; level on the 135M model’s Q8_0, Q5_0 and Q5_1 with four threads.
  • Prompt processing on the CPU: level on 128 tokens of the 1B model, 0.84x–0.86x at 512 and 2048 tokens, about 0.5x against llama.cpp’s AMX path on the 135M model.
  • 4-bit types llama.cpp interleaves at load: Q4_1 and IQ4_NL decode with four threads at 0.66x and 0.72x.
  • A tester’s RX 9060 XT (machine D, Vulkan): generation on Qwen3.8-27B Q4_0 1.1x llama.cpp’s; prompt processing 0.4x, the known weak spot on Vulkan.
  • The maintainer’s laptop (machine B, 2 cores, AVX2, CPU only): generation 0.96–1.3x llama.cpp’s on Llama-3.2-1B (both bound by the RAM), prompt processing 0.8–1.0x (2026-10-14).
  • A model larger than its RAM budget (machine C, CPU): Qwen3-30B-A3B Q4_K_M (17.28 GB) gives the same text in 8, 4 and 2 GB of RAM as with all of it in RAM, at 6.7, 2.5 and 1.7 tok/s with the OS file cache, 3.3 and 0.8 at 8 and 4 GB past it (the table, 2026-10-15).
  • The P1000 (machine C): its GPU table not measured since 0.21.0 (its runs are in TODO.md, “Real-world checks”, group E); llama.cpp not yet measured on it.

Inga / llama.cpp is Inga’s speed over llama.cpp’s fastest run on the same test (its default, which repacks weights and uses AMX, or --repack 0, the weights as stored): above 1, Inga is faster. Rows sorted by the gap, furthest behind first.

A big mixture of experts in little RAM

Section titled “A big mixture of experts in little RAM”

Qwen3-30B-A3B Q4_K_M (unsloth, a file of 17.28 GB) on machine C’s CPU (Xeon W-2123, 31.7 GB of RAM, an NVMe drive, Windows), under shrinking --mem-limit budgets. Measured on 2026-10-15 by the real-world checks’ group L on the self-hosted P1000 runner (run 38814166171, results in issue #642). Each row:

Budget Peak working set (private) Decode (tok/s) Expert cache (of 6144) Text against all in RAM
all in RAM (reference) 10.19 GB (0.80 GB) 2.7 (first, cold run through a memory map) all —
--mem-limit 8G 8.11 GB (7.43 GB) 6.7 2422 identical
--mem-limit 4G 4.04 GB (3.34 GB) 2.5 919 identical
--mem-limit 2G 2.00 GB (1.28 GB) 1.7 167 identical
8G, direct reads (past the OS file cache) 8.13 GB (7.44 GB) 3.3 2422 identical
4G, direct reads 4.03 GB (3.33 GB) 0.8 919 identical

Peak working set is the process’s peak working set, its private bytes in brackets; the OS file cache is not counted. Inga’s plan: attention, embeddings, output layer and KV cache in RAM (about 1.3 GB), the experts (16.4 GiB) read from the SSD while running, an expert cache of the size in the table, the most used experts of earlier runs pinned. The 64 tokens are the same under every budget.

What the numbers do not say:

  • The plain --mem-limit rows were largely served by Windows’ file cache (18.6 GB of RAM were free): their speed is the cache’s, not the disk’s. The direct-reads rows measure the disk.
  • The reference row is a cold first run, its file read through a memory map: its 2.7 tok/s is not the speed of a warm run with everything in RAM.
  • The runs are not independent: the experts pinned by one carry over to the next.
  • One machine, one run each.

On a 1 Gbit LAN (about 117 MB/s) the cipher runs ten times faster than the wire: a part’s 16 MiB chunk takes about 140 ms on the wire and 10–16 ms to seal, partly overlapped with the send (at most about 10 % more time, less on a desktop CPU). How to measure

Section titled “How to measure”
  • inga bench with the release build: inga bench FILE -p 128 -n 64 -t 1,4 -r 5 (machine A’s short prompt), -p 512 -n 0 and -p 2048 -n 32 for long prompts; llama.cpp with llama-bench -m FILE and the same options. --profile prints the time of each operation kind per token.
  • --ab KEY=VALUE runs the same bench with and without a setting of inga.toml (a [debug] switch such as debug.vk_tiles=false, or gpu.max_load=50), alternated, and stops at the first logit that differs.
  • --ctx-sweep gives prefill and decode at each context frontier (2K to 32K by default; --csv in ds4-bench’s columns).
  • The GPU workflow (.github/workflows/gpu.yml, run by hand on machine C): model plus compare: llama.cpp measures Inga and the pinned llama.cpp release (LLAMA_CPP_BUILD) on the CPU, CUDA and Vulkan, pp512 and tg128; compare: base measures a branch against its base, the two interleaved, with the verdict of a pull request’s bench; compare: noise measures a commit against itself, which is how the threshold below is checked; without compare, bench_args sets the bench’s arguments (e.g. -p 512 -n 128 -r 3 --ab debug.vk_tiles=false). See gpu-runner.md.

To update this page: run the section’s command on the same machine and files, overwrite the row with the new numbers, version and date (llama.cpp’s too when it was run again), keep the Where Inga stands tables sorted by the gap, and fix the bullets above if the picture changed. A new machine gets a row in the machines and its own table.

The rule for performance changes

Section titled “The rule for performance changes”

A pull request that changes speed (kernels, scheduling, memory layout, a GPU path) merges only when:

  1. Same output: correctness tests show the same output as the reference — RefBackend, the CPU path for GPU work, plain decoding for speculative or batched decoding. A change behind a [debug] switch of inga.toml shows it with inga bench --ab debug.X=VALUE. A change to long prompts or attention also shows the curve before and after with inga bench --ctx-sweep, with --ab when it is behind a switch.
  2. Measured gain, no regression: a before / after inga bench on the same machine — the maintainer’s P1000 through the GPU runner for GPU work (the model input of .github/workflows/gpu.yml), the Linux CI runner or the development machine for CPU work — shows a gain and no test slower by more than 3 %.
  3. The table in the PR: the pull request carries the before / after table; label it gpu and the GPU runner posts it as a comment, the base against the pull request on the CPU, CUDA and Vulkan, with a GPU bench check that turns red on a regression over 3 % beyond the noise and measured twice; the label perf-regression-ok accepts a known one (gpu-runner.md).
  4. Logged: the result goes into experiments.md, whatever it is.

The maintainer, 2026-10-11: “bring in all the ideas; for the performance ones always run measurements; libraries that can be integrated without runtime dependencies, try them”. Every performance idea taken from another project (TODO.md) is measured this way before it is kept. An idea that does not pay off is not deleted: it is logged in experiments.md as “set aside”, with its numbers and the conditions under which it could work.
