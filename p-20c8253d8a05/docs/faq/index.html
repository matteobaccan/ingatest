FAQ

The questions people ask about Inga: how large a model can run, which device runs what, the kinds of models, files given to a model, where Inga keeps its files, the models of LM Studio and Ollama, and which Inga is running (moved here from the main README on 2026-11-06).

How do I install Inga without the one-line installer?

Section titled “How do I install Inga without the one-line installer?”

The one-line installers of the README are the quick way. By hand:

Download the archive for your system from the Releases page and put inga on your PATH (or use the container image ghcr.io/matteobaccan/inga, after logging in to ghcr.io while the repository is private: Docker and Podman). On a Mac, inga-macos-arm64 is for Apple Silicon and inga-macos-x86_64 for an Intel Mac (the CPU only; built and tested in CI, unverified by a person on an Intel Mac). On macOS and Linux the install script does it from the terminal: it picks the archive for your system, checks its SHA-256 and puts inga in ~/.local/bin; downloaded this way, macOS opens it without the “developer cannot be verified” warning. While the repository is private it needs gh auth login (or a token in GH_TOKEN):

An archive downloaded with a browser on macOS is quarantined: after extracting it, run xattr -d com.apple.quarantine inga once (more).

How large a model can I run?

Section titled “How large a model can I run?”

There is no fixed limit: what a model needs is a disk that holds its file; the speed depends on where its weights live.

Situation What Inga does Speed
File + KV cache fit in the free RAM (or VRAM) Everything in memory Full: the memory bandwidth divided by the bytes read per token (an 8B Q4 on DDR4: ~4 tokens/s on the CPU)
A mixture of experts larger than the RAM, up to 1T parameters and more The rest in RAM or VRAM, the experts on disk with a cache in RAM Each token reads only the experts it uses: see frontier models
A dense model larger than the RAM (a 70B Q4 on 32 GB) The layers read from disk one after the other Slow: the whole file read again per token (~20 s a token from a 2 GB/s NVMe)
Several PCs Layers, experts or slices of the layers on other machines The machines’ RAM adds up

For full speed on a dense model, keep the file below the free RAM minus 1–2 GB (about 13 GB with 16 GB of RAM, 28 GB with 32 GB). inga info MODEL prints the memory plan and the expected tokens per second before anything is downloaded; --mem-limit 24G simulates a smaller machine. The cases larger than the RAM are tested on synthetic models; real files on real SSDs are still to be checked (real-world checks, group D).

Does Inga use the CPU, the GPU, the NPU, VRAM, RAM or the disk?

Section titled “Does Inga use the CPU, the GPU, the NPU, VRAM, RAM or the disk?”

The CPU and the GPU: NVIDIA ones through CUDA, any vendor’s through Vulkan (--device vulkan), a Mac’s Apple Silicon GPU through Metal (--device metal), AMD ones through ROCm / HIP (--device hip, experimental); inga devices lists them. The GPU is used by default: as many layers as its free memory holds on the best usable GPU (CUDA first, then Metal, then Vulkan; never an integrated GPU beside a discrete card, HIP or a software device unless named), the rest on the CPU; --device cuda:0,vulkan:1 splits a dense model’s layers across several GPUs; --device cpu, --gpu-layers 0 or device = "cpu" in inga.toml keep everything on the CPU, and when no GPU is used a line says why (no driver, too little free memory, a weight type or architecture the GPU does not run, a software device). A mixture of experts fills the GPU in this order: the output layer, the attention of its layers, the shared experts, then the routed experts of as many layers as fit (the last ones first); the other experts run on the CPU from RAM, or from the disk when the RAM is short (--experts-on cpu keeps them all on the CPU, --cpu-moe N the first N layers’). The weights live in RAM, memory-mapped from the file, and on the disk only when they do not fit. inga run and inga serve print where each model runs when it loads:

The web UI shows the same as badges beside the chat’s model and in the Server tab (CPU · AVX2, RAM, a red disk when weights are read from the disk, network when part of the model runs on other machines); /api/inga/status has it as placement.

What kinds of models are there, and which one reads images or audio?

Section titled “What kinds of models are there, and which one reads images or audio?”

A language model (LLM) reads and writes text; a vision-language model (VLM) also sees images, an audio-language model hears audio, a multimodal (omni) model does both; embedding models and rerankers turn texts into vectors or rank them. Images and audio go through a projector file (mmproj-*.gguf) holding an encoder — SigLIP or a vision transformer for images, Whisper for audio — next to the model or given with --mmproj. The web UI’s model library shows each model’s capabilities (text, vision, audio, tools, reasoning, embeddings, …), its Info window names the encoders, and the chat enables Image and Audio only for a model that reads them. A speech-to-text model (Whisper, Parakeet) writes down what a recording says: inga transcribe (guide). The full list: docs/supported-models.md.

Can I give a model a file, such as a Java source to comment?

Section titled “Can I give a model a file, such as a Java source to comment?”

Yes: in the web UI, Attach (the + in the message box) → File (or drop the file on the message box) attaches text and source files — Java, Python, JavaScript, PHP, Markdown, JSON, CSV, logs — for any model; they wait above the box until the next message, which carries them as fenced blocks named after the file. The same menu’s Image and Audio attach pictures and recordings for models that read them. PDF and Word (DOCX) documents, and texts too long for the context, go to the server, which reads them and gives the model the whole document when it fits in a third of the context, else the passages closest to each question, cited by page (guide).

Where does Inga keep its files and settings?

Section titled “Where does Inga keep its files and settings?”

  • The home, ~/.cache/inga (--home DIR, or home in inga.toml, moves it), readable by their owner only where they hold prompts or keys:

    What Where
    Your settings (docs/config.md, inga config) inga.toml
    Settings: model folders, embedding model, web search, each model’s variant model-dirs.json, settings.json
    Experts: use profiles and importance matrices, converted experts experts/, cache/experts/
    Model variants made by inga optimize cache/models/
    KV caches of --kv-disk auto, --kv-ram, --kv-disk-keep kv/
    Speeds measured on this machine measured.json
    Memories, documents’ collections store/
    Shared chats shared/
    Scheduled tasks and their results schedules.json, results/
    API nodes, their encrypted keys, routes nodes.json, secrets.json + secret.key, routes.json
    MCP servers, the commands approved, their sign-ins, the “always” answers mcp.json, mcp-approvals.json, mcp-tokens.json, tool-approvals.json
    Skills skills/
    Evals (and the votes of the arena of 0.45, no longer read), inga decide calibrate’s temperatures evals/, decide/
    Named API keys’ usage keys-usage.json
    Voices of inga speak voices/
    The queue of memory-heavy jobs jobs/

  • HF_HUB_CACHE / HF_HOME (default ~/.cache/huggingface/hub): the models downloaded with inga pull or the web UI — the cache huggingface_hub uses too. Without these variables, inga download-dir PATH (or the web UI’s Model folders → Download folder) puts it elsewhere, kept as download_dir in settings.json; --move (or Move the models here) moves what is there.

  • The user’s profile (profiles/default/ of the data folder above, or of --home DIR): the web UI’s chats with their pictures as files, its parameters, presets, system prompt, drafts, the project open and the opt-ins, served by /api/inga/profile/...; the same from every browser (one user today, without authentication).

  • The browser (localStorage, keys inga.*): only the web UI’s own settings — theme, language, views, filters, the side bar — per browser; the API key only for the tab (sessionStorage), unless Remember the API key on this device keeps it in localStorage too.

  • inga data shows all of it by kind with sizes and the free disk, inga data list each entry with its id, inga data rm ID deletes one and inga data clear KIND (or --all) every entry of a kind; the web UI’s Storage page does the same, and /api/inga/data serves it. Models in LM Studio’s and Ollama’s folders are listed but never deleted, and --prompt-cache files stay where you saved them, unlisted.

  • Everything else is a command-line option, a key of inga.toml or an environment variable; the files you may edit by hand are inga.toml, nodes.json, routes.json and the named keys’ file of --api-keys (re-read when they change), and mcp.json. Inga reads LM Studio’s settings and Ollama’s store to find their models, without changing them (but for inga pull ollama://... --ollama-store, which adds a model to Ollama’s store as Ollama would).

Can I use the models I downloaded with LM Studio or Ollama?

Section titled “Can I use the models I downloaded with LM Studio or Ollama?”

Yes: inga list --lmstudio and inga list --ollama list them with whether Inga runs them, ollama://name:tag runs an Ollama model (inga pull ollama://name:tag downloads one from Ollama’s library, without Ollama), and the web UI lists both by itself, with any folder you add. LM Studio’s MLX models (its mlx-community/... folders) run too: on the CPU and on a Mac’s GPU their quantized weights are read as stored by MLX kernels; for an NVIDIA or Vulkan GPU, or with --quantize, they are converted when they load (4 bits to Q4_K, 5–6 to Q6_K, 8 to Q8_0), and Inga says which (mlx: ... read as stored by MLX kernels or mlx: ... converted to Q4_K at load: N tensors).

Which Inga am I running?

Section titled “Which Inga am I running?”

inga version prints the version, the git commit and date it was built from, the target and profile, the CPU instruction set in use and the GPU backends built in and found (--json for scripts); paste it into an issue. A running server says the same at GET /api/inga/version and in the web UI’s About (with a copy button), and names itself in every answer’s Server: Inga/X.Y.Z header. With --api-key or --api-keys, the build details go only to keys that may call the admin routes; --hide-version drops the version from the header and the details for everyone but admin keys.
