The GPU runner

GitHub’s hosted runners have no GPU, so Inga’s GPU tests are #[ignore]d there. A self-hosted runner on a machine with a GPU runs them: the GPU workflow (.github/workflows/gpu.yml) starts there on demand and on pull requests labelled gpu or gpu-full. One machine is enough; today it is the maintainer’s PC with a Quadro P1000, switched on only now and then: the work is cut into jobs of 20-30 minutes, so half an hour of the PC still finishes something (The jobs).

What the machine needs

Section titled “What the machine needs”
  • An NVIDIA driver (the GPU’s usual driver: CUDA and Vulkan come with it). No CUDA Toolkit: Inga embeds its PTX.
  • Git and Rust (rustup; the release of rust-toolchain.toml is installed by the first build); on Windows the Visual Studio Build Tools that Rust asks for, and Git for Windows.
  • Optional: a folder of models for the end-to-end tests and inga bench, given to the runner as INGA_MODELS (see tools/oracle-models.md).
  • About 10 GB of free disk for the build.

Installing the runner

Section titled “Installing the runner”

  1. On GitHub: matteobaccan/inga → Settings → Actions → Runners → New self-hosted runner, pick the machine’s system (Windows x64 or Linux x64). The page shows a download command and a registration token valid for one hour.

  2. On the machine, in a folder of its own (e.g. C:\actions-runner or ~/actions-runner), run the download commands of that page, then configure with the gpu label:

    Windows (PowerShell as administrator, so it installs as a service):

    Linux:

    GitHub adds the system’s label (Windows, Linux) by itself. gpu.yml’s jobs ask for self-hosted, windows, gpu: their steps are PowerShell scripts and .exe paths, so today only a Windows runner runs them.

  3. Models (optional): set INGA_MODELS for the service; a variable of your user account is not seen by it. On Windows either a line INGA_MODELS=D:\path\to\models in the runner’s .env file (D:\actions-runner\.env) or a system environment variable, then restart the service actions.runner.* (services.msc); on Linux a line INGA_MODELS=/path/to/models in the runner’s .env file, then sudo ./svc.sh stop && sudo ./svc.sh start. The workflow’s “Models in INGA_MODELS” step lists what it finds (inga scan), or says the variable is missing. The steps run in PowerShell on Windows: the bash on a Windows path is often WSL’s, which cannot see the runner’s scripts.

  4. Check: the runner shows Idle under Settings → Actions → Runners, and Actions → GPU → Run workflow on main ends green with the GPU listed in the “Devices” step.

Using it

Section titled “Using it”
  • By hand or by the agent: Actions → GPU → Run workflow, with an optional branch and an optional model for inga bench (a file name inside INGA_MODELS).
  • On a pull request: add the gpu label; every new push to the pull request runs the quick job again (about 10 minutes: the canary model and a short subset of the CUDA and Vulkan tests), and the bench of its base against it, posted as a comment and a GPU bench check (below). The label gpu-full (with or instead of gpu) runs the full suites that the pull request’s changed paths touch instead of the quick job. Only pull requests from this repository run there, never forks.
  • A suite that failed: the run’s page → Re-run jobs → Re-run failed jobs runs that suite alone again; the bench does not depend on the suites, so it is not measured again.
  • Queueing: one run per pull request at a time; a newer push waits for the running one and replaces a run still waiting. Runs of different pull requests and runs by hand never cancel each other: they wait in GitHub’s queue for the runner, which runs one job at a time, so the card is never shared. A job waits at most a day for the runner (then GitHub fails it), so a run started while the machine is off is lost after a day; the sweep (.github/workflows/gpu-bench-sweep.yml, every two hours and after every GPU run, on a hosted runner) starts the bench again for every open pull request labelled gpu whose head has no GPU bench check and no run queued or running (at most three times per head; then it says so in its log).

The jobs

Section titled “The jobs”

Each suite is a job of its own on the runner, all after the plan job (a hosted runner, a few seconds), each meant to end within 20-30 minutes (their limit is 45; the quick job’s 25):

Job What it runs When
⚡ Quick the canary model of the nightly rotation (SmolLM2-135M Q8_0, tools/real-checks/rotation.json) with inga devices --test --model (the CPU, then CUDA and Vulkan, against the CPU’s logits); inga-cuda’s devices, kernels and sampling tests; inga-vulkan’s devices, shaders and sampling tests a pull request labelled gpu, or suites: quick
🎮 CUDA every #[ignore] test of inga-cuda full suites
🌋 Vulkan every test of inga-vulkan, one at a time full suites
🔴 HIP inga-hip, and the CUDA kernel and layer tests through HIP full suites, on a runner with INGA_HIP (below)
🧱 Layer engine and disaggregated prefill inga-gpu’s tests; tests/worker.rs (inga worker --device, CUDA then Vulkan) full suites
🕸️ Mesh the mesh’s GPU tests on CUDA, then on Vulkan full suites
📊 Compare inga bench of model, or the comparison with llama.cpp by hand, with model
📊 Bench the base against the pull request (or compare: base / noise) a pull request, or by hand
🌐 WebGPU in Chrome the browser build (web/pkg) in headless Chrome on the card (D3D12, as a user’s Windows PC): the GPU memory probe, the adapter and its features, prompt and decode speed (greedy, the chat path, each tunes configuration), the kernel times, and inga bench on Vulkan and CUDA on the same files (tools/webgpu-bench.cjs; the report in the summary and the artifact webgpu-bench) by hand only: suites: webgpu (never in all), its options in the webgpu input (models=A.gguf,B.gguf tokens=128 tunes=sg=on;rows=4 native=vulkan,cuda gpumb=N)

Which suites. By hand, every suite (suites: auto or all), or those named. On a pull request, those its changed paths touch, with what depends on them (crates/*/Cargo.toml): inga-vulkan runs the Vulkan suite, the disaggregated prefill and the mesh on Vulkan; inga-cuda runs CUDA, HIP, the disaggregated prefill and the mesh on CUDA; inga-hip runs HIP; inga-dist and src/commands/mesh.rs the mesh (prefill.rs and src/commands/worker.rs the disaggregated prefill); inga-gpu, inga-core, inga-cpu, inga-quant, inga-model, inga-engine and gpu.yml run every suite; tools/bench-compare.ps1 and examples/bench_compare.rs only the bench. With the label gpu, the quick job runs instead of those suites (its CUDA part when CUDA is touched, its Vulkan part when Vulkan is); with gpu-full, the suites themselves. The plan job’s summary says which suites it chose and why.

The build. Every job checks out with clean: false and none runs cargo clean: the runner keeps its workspace between jobs and runs, so its target folder is shared (the bench’s, the nightly’s and the real-world checks’ too) and a job builds only what changed since the last one. A broken build folder is the one case to empty it by hand (stop the runner, delete _work\inga\inga\target).

Comparisons: Inga against llama.cpp, against its base, or against itself

Section titled “Comparisons: Inga against llama.cpp, against its base, or against itself”

A run by hand can also measure Inga next to llama.cpp, or a branch next to the code it starts from, on this machine’s CPU and GPU. Actions → GPU → Run workflow with:

Input Value
ref the branch to measure (empty: the one the run starts from)
model a GGUF file inside INGA_MODELS, e.g. Llama-3.2-1B-Instruct-Q4_K_M.gguf
compare llama.cpp, base, noise, perf, or none (the default: no comparison)
tests with compare: perf, the test sizes, PROMPT,GEN separated by spaces (default 512,128)
base with compare: base or noise, the branch, tag or commit (default main)
threads CPU threads for both sides (empty: the CPU’s physical cores)
noise_runs with compare: noise, how many measures of base against itself (default 5)
suites auto (the default: by hand every suite; with pr, the pull request’s changed paths, quick unless it is labelled gpu-full), all, quick, none, or a comma list of cuda, vulkan, hip, layers, mesh
pr a pull request’s number: its GPU tests and bench, as the gpu label does

Every comparison runs pp512 and tg128 on three devices: inga bench --json with --device cpu, with --device cuda:0 --gpu-layers all and with --device vulkan:0 --gpu-layers all (tools/bench-compare.ps1).

  • compare: llama.cpp (needs model): three repetitions of each side, one after the other, with llama-bench -o json of the llama.cpp release pinned in gpu.yml (LLAMA_CPP_BUILD, one line to bump): its Windows x64 CPU build with -ngl 0 (not a GPU build: those send the prompt’s products to the GPU even with -ngl 0), its CUDA 12.4 build (the last CUDA with Pascal cards such as the P1000) with -ngl 99, and its Vulkan build with -ngl 99. The zips are downloaded once into the runner’s tool cache (RUNNER_TOOL_CACHE\llama.cpp\<build>), each checked against the SHA-256 digest GitHub publishes for release assets; when a release has none, the hash is written to the summary instead. Then a greedy generation: inga run --raw --temp 0 --no-model-sampling --device cpu and llama.cpp’s llama-completion -no-cnv --temp 0 --repeat-penalty 1 -ngl 0 complete the prompt COMPARE_TEXT (32 tokens) and the summary says whether the two texts agree.
  • compare: perf: machine C’s table of performance.md in one run. For each model of model (separated by commas: a file in INGA_MODELS, an hf:// reference, downloaded once when missing, or a file name, wildcards allowed, looked up in INGA_MODELS and the Hugging Face cache; empty: PERF_MODELS in gpu.yml, the table’s models) and each size of tests, the runs of compare: llama.cpp (no greedy text), the GPU’s free memory before them, and on CUDA and Vulkan llama.cpp once more with Inga’s placement (-ngl the layers Inga put on the card, or -ncmoe 99 when Inga keeps a mixture’s experts on the CPU): a model that does not fit the card’s free memory fails or spills with -ngl 99. One table in the summary (bench_compare perf), a row per model, device and test, with Inga / llama.cpp against llama.cpp’s faster placement. A model not found is a warning and no row. Used for each release’s P1000 rows: suites: none, compare: perf, tests: 128,64 512,128.
  • compare: base: the branch against Inga built from base, exactly as a pull request’s bench (below): interleaved, the suspect rows measured again, the same table and verdict, in the run’s summary only (no comment, no check). A change meant to make Inga faster shows here how much faster, on the GPU too. Without model, the pull requests’ model (GPU_BENCH_MODEL).
  • compare: noise: Inga at base against itself, noise_runs times, each run interleaved as a pull request’s. The summary’s table shows, row by row, the gap each run found between two measures of the same binary, the largest gap, noise and coefficient of variation, and how many measures the threshold would have called suspect. This is how the threshold is set (below).

The results are in the run’s summary (the run’s page, below the job list). With llama.cpp: one table per comparison, a row per device and test, with Inga’s and the other side’s tokens per second (mean ± standard deviation) and Inga’s speed against it in per cent (above zero, Inga is faster), and under it where each side ran (the CPU, the GPU, the layers on it). The raw JSON (inga-*.json, llama-*.json, the field names of llama-bench -o json), the two generated texts and the zips’ hashes are the run’s artifact compare-llama.cpp-<run id>; with base and noise the artifact is bench-base or bench-noise. The summaries are written by cargo run --release --example bench_compare (examples/bench_compare.rs), which reads those files; it runs on any machine, e.g. on an artifact downloaded from a run.

Reading it:

  • A run that fails (a device missing, a model a backend does not run) is a warning in the log and an empty cell, not a failed job; the other runs go on.
  • With llama.cpp the two sides run one after the other, not interleaved: on a busy machine run the comparison twice before trusting a gap of a few per cent.
  • llama-bench reports the -ngl it was given; Inga reports the layers it placed, so a model that does not fit shows fewer layers for Inga.
  • A different greedy text is a warning, not a failure: a different tokenization of the prompt, a tie between two tokens or a small numeric difference changes the rest of a greedy generation. It is worth a look when the two differ from the first words. The CPU runs the generation on both sides; the GPUs are compared with the CPU by inga devices --test.
  • A comparison with llama.cpp takes about 10 minutes on a 1B model; with base, about 25 minutes, plus the base’s build the first time each base commit is seen. Without model and compare the workflow runs as before.

On a pull request: the base against the pull request

Section titled “On a pull request: the base against the pull request”

A pull request labelled gpu (from this repository, touching GPU or kernel code: the paths of gpu.yml; or any labelled pull request, through the sweep) also gets, beside the GPU tests, the bench of its base and of itself on this runner (job bench), as the rule for performance changes asks (performance.md), and a check named GPU bench (spec 2026-10-14-gpu-bench-comparison-design.md).

How it measures:

  1. Two binaries, built first. The pull request merged into its base (refs/pull/N/merge), and its base: the merge commit’s first parent. The base is built once per commit and kept in the runner’s tool cache (RUNNER_TOOL_CACHE\inga-base\<sha>.exe, the 10 most recently used; its build folder inga-base-target is kept too), so pull requests on the same main reuse it.
  2. A quiet card. It waits until the GPU’s utilization has stayed under 5 % for 10 s (at most 2 minutes; the processes on the card are in the log), and tries to lock its clock at the application clock (nvidia-smi -lgc; it needs administrator rights, and a refusal is a notice, not an error). The clock is given back at the end.
  3. Interleaved runs. Device by device, a warm-up round (the model read into the OS cache, the clocks up; not counted), then 4 measured rounds (GPU_BENCH_ROUNDS), each one inga bench -r 1 of each side, head and base in turn (head first in even rounds, base first in odd ones): heat or a background process then weighs on both sides alike. Before and after every GPU run, nvidia-smi reads the SM clock and the temperature (gpu.csv).
  4. The threshold (examples/bench_compare.rs). A row (device × test) is suspect when the pull request’s mean is lower than the base’s by more than 3 % (GPU_BENCH_LIMIT, the rule of performance.md) and the gap is larger than twice (GPU_BENCH_SIGMAS) the combined standard error, sqrt(sd_head²/n_head + sd_base²/n_base), with at least two measured rounds per side. The devices with a suspect row are measured again the same way; a row is a regression only when the second measure is suspect too.
  5. The verdict. The table and the verdict go to the run’s summary, to one comment on the pull request (updated by every later run: it starts with the hidden marker <!-- inga-gpu-bench -->) and to the GPU bench check on the pull request’s head. Both are written by a job on a hosted runner (bench-comment, the only one with pull-requests: write and checks: write): the token that writes to the pull request never reaches this machine. The JSON files, gpu.csv, the comment and verdict.json are the run’s artifact bench-pr.

The model: the repository variable GPU_BENCH_MODEL (Settings → Secrets and variables → Actions → Variables): a file inside INGA_MODELS, a path, or an hf:// reference (hf://org/repo:Q4_K_M, hf://org/repo/file.gguf) read from the runner’s Hugging Face cache (HF_HUB_CACHE, else HF_HOME\hub) and downloaded there only when missing (tools/hf-model.ps1). Unset: hf://bartowski/Llama-3.2-1B-Instruct-GGUF:Q4_K_M. The table gives the file’s name and its SHA-256.

Reading the check

Section titled “Reading the check”

The check’s title is the verdict in one line; its details are the table.

Conclusion Title, e.g. Meaning
✅ success no regression no row slower than the threshold twice; rows slower than 3 % but within the noise, or not repeated, are counted in the title and named in the table
❌ failure 1 row slower than the threshold: CUDA tg128 -6.1 % ± 1.2 a confirmed regression: the row, its gap and the noise (both in per cent of the base’s speed)
⚪ neutral accepted (perf-regression-ok): 1 row slower ... a confirmed regression, accepted by the label
⚪ neutral no result: ... the bench gave no table (a build failed, the model is missing, nothing ran on both sides); the run’s log says why

The table’s columns: each side’s tokens per second (mean ± standard deviation of the rounds) and coefficient of variation (CV: the noise of that side), the Gap (the pull request’s speed against the base’s; below zero, slower), the Noise (twice the combined standard error, in per cent: a gap inside it is not counted), and the Verdict of the row: empty (fine), within the noise, too few runs to know the noise, suspect, not measured again, not repeated (again …) or regression (again …), the second measure’s gap and noise. A regression’s row is in bold. Below the table: the devices measured again, the GPU’s clock and temperature at the start of each side’s first run and at the end of its last (a side that ran hotter or slower clocked is visible there), and where each run ran. An empty cell (a device missing, a model a backend refuses) is never a regression.

Accepting a known regression

Section titled “Accepting a known regression”

A pull request that trades speed for something else on purpose (a fix, a feature, a precision): add the label perf-regression-ok to it. The check turns ⚪ neutral at once (.github/workflows/gpu-bench-accept.yml, a hosted runner: nothing is measured again), and every later bench of the pull request reads the label too. Removing the label turns a confirmed regression red again. Say in the pull request why the regression is accepted.

The check is not a required check of main’s branch protection until its noise has been measured on this runner (decided 2026-10-14; the steps are in the next section). A red check is then a reason to look, not a lock.

The first time, and setting the threshold

Section titled “The first time, and setting the threshold”
  1. Create the labels gpu (if missing) and perf-regression-ok (Issues → Labels).
  2. Measure the noise: Actions → GPU → Run workflow on main with compare: noise (base: main, noise_runs: 5). The summary’s last line says how many measures were suspect and the largest gap seen. With no suspect measure, keep 3 % and 2; otherwise raise GPU_BENCH_LIMIT above the largest gap of the rows that matter, or GPU_BENCH_SIGMAS, as repository variables, and run it again.
  3. Check a real comparison: a pull request with no code change (base = head) labelled gpu must end ✅ with no row suspect; one with a deliberate slowdown (e.g. a sleep of 2 ms per token in the CUDA decode) must end ❌ on CUDA tg128 and not on the CPU’s rows; two pull requests pushed while the runner is busy must both get a table.
  4. Then, if the maintainer wants it, add GPU bench to the required checks of main.

The bench job takes the two builds (the base’s only the first time) and about 30 interleaved benches of a few seconds each on a 1B model, plus the suspects again (timeout-minutes: 240). It needs only the plan job, not the suites: GitHub’s queue gives the runner the run’s jobs one at a time, in an order of its own.

Real-world checks

Section titled “Real-world checks”

The same runner runs the real-world checks of docs/todo/real-world-checks.md (real model files against llama.cpp, whisper.cpp, stable-diffusion.cpp and transcribe.cpp; real clients; Windows; speed): the Real-world checks workflow (.github/workflows/real-checks.yml), started by hand. What it needs besides this page, its inputs and the checks left to do by hand are in maintainer-checklist.md.

Each night it also runs the nightly real-file rotation (.github/workflows/real-nightly.yml): slots of about 45 minutes, one job each, after a job that builds Inga and the reference programs once per commit; an entry that passed on the same commit is not run again, so a night cut short by switching the PC off goes on from where it stopped (maintainer-checklist.md).

The 70B checks (a real model of 40+ GB pulled from the Hub, an interrupted download resumed, a dense model larger than the RAM streamed from the disk) run in .github/workflows/big-model.yml (tools/real-checks/big-model.ps1), started by hand, with the models on a disk of their own (input dir, default HF_HOME\hub of the runner, which the runner’s service account must see): gh workflow run big-model.yml -f steps=info first (the disk, the RAM, the VRAM, the Hub’s files and the room), then -f steps=download,resume,stream,chat. Every result is in the jobs’ summaries.

An AMD card (HIP)

Section titled “An AMD card (HIP)”

The workflow’s HIP job runs the CUDA kernel and layer tests through ROCm’s HIP runtime (INGA_HIP=1) only where the variable INGA_HIP is 1 (Settings → Secrets and variables → Actions → Variables, or the runner’s own): a runner with an AMD card and ROCm’s runtime installed (libamdhip64.so.6 / .7, or the driver’s amdhip64_6.dll). The P1000 runner skips it.

Macs

Section titled “Macs”

There is no Mac runner yet: volunteers with Apple Silicon Macs run the Metal checks and benchmarks by hand with the kit of mac-testers.md. A volunteer who offers a Mac as a runner follows this page’s rules (manual dispatch only, never code from forks).

Security

Section titled “Security”

The runner executes the code of the branch it tests, on the maintainer’s PC. That is why it serves only this private repository, only on demand or on labelled pull requests from the repository itself, never forks. To stop it: stop the service, or remove the runner under Settings → Actions → Runners.
