How the work is done

The working methods built up with the maintainer over the releases, written down so that any machine, session or agent can continue them. AGENTS.md holds the rules; this page holds the procedures behind them: how a question is answered, how a change is measured, how outside code and outside projects are taken in. When a procedure changes, change it here in the same pull request.

The loop

Section titled “The loop”
  1. The maintainer asks, in Italian. Answers to him are in Italian; everything in the repository (code, docs, commits, pull requests, issues) is in English.
  2. Check before answering: the code and docs on origin/main, the roadmap (TODO.md, docs/todo/), the experiments log, open pull requests and issues. Say what is on main, what is in a pull request, what is planned, what is not.
  3. Propose, then do: a code or roadmap change the maintainer has not asked for is proposed with its analysis first. A decision he takes is recorded where it applies (the item in docs/todo/, the spec, docs/experiments.md), with its date.
  4. One branch per change, from origin/main, a pull request to main, landed with tools/land.sh in the order the maintainer approves.
  5. Report with numbers: only measured numbers, with their configuration; what was not run or not measured is said to be so.

Git and pull requests

Section titled “Git and pull requests”
  • A worktree per branch (git worktree add -b BRANCH DIR origin/main), never two branches in one checkout; each worktree builds into its own target directory (CARGO_TARGET_DIR=$PWD/tgt): a shared one gave false compile errors between worktrees. On a small disk: CARGO_BUILD_JOBS=4 CARGO_PROFILE_DEV_DEBUG=0 CARGO_INCREMENTAL=0, and delete the target directories of landed branches.
  • Before a push: sh tools/check.sh and cargo fmt --all --check (check.sh formats, but a CI failure once came from a file it did not see). A fix for a CI failure is first reproduced, then shown passing.
  • Commits: the maintainer’s identity (git -c user.name="Matteo Baccan" -c user.email=matteo.baccan@gmail.com commit). Never a force-push, a rebase or a pushed tag (the release tag is made by release-tag.yml). Remote branches are deleted by the maintainer. No assistant attribution anywhere: not in commits (no Co-Authored-By), pull requests, issues or comments.
  • A pull request: created with gh api -X POST repos/matteobaccan/inga/pulls -f title=... -f head=BRANCH -f base=main -f body=., then its body from a file (gh api -X PATCH .../pulls/N -F body=@FILE): What, Why, Tests, Not verified.
  • Landing: tools/land.sh PR... in a clone of its own (it merges main into each branch, waits for the checks, squash-merges; conflicts in the lists only appended to, the specs’ table and docs/todo/inbox.md among them, are joined). tools/land.sh --batch NAME PR... merges several into land/NAME and lands them as one pull request, one round of CI, then comments on the originals and closes them. Bot and Renovate pull requests only with the maintainer’s approval.
  • New folders get a README.md saying what they hold.

Measuring

Section titled “Measuring”

The rule is docs/performance.md’s (“The rule for performance changes”); every idea, adopted or set aside, gets an entry in docs/experiments.md. A new code path ships behind a debug.* key (tunables, src/config/keys.rs, docs/config.md), off until measured; its default turns on only where it was measured, possibly per hardware (compute capability for CUDA, the vendor for Vulkan), and the key’s text says where.

On the A100 (Google Colab)

Section titled “On the A100 (Google Colab)”

The maintainer runs one test of the Colab notebook tools/colab/inga-bench.ipynb on a Colab A100 and the results come back as an issue labelled colab-results. The test is picked by the switch at the notebook’s top (TEST, with BUILD_REF, BASE_REF and SET for the builds) and everything runs with Run all; tools/colab/README.md lists the tests and how to add one (one function and one entry of its TESTS). No one-off cell is kept: a new question becomes a test of the notebook, or a few lines in an existing test’s settings. The tests share a shape:

  • GH_TOKEN from Colab’s Secrets, never printed (masked in every log line and issue);
  • each ref fetched and built in a directory and target of its own, the build skipped while its commit is the same; llama.cpp, nsys and the models only when the test needs them;
  • models from Hugging Face into /content/models (kept between runs of one session);
  • interleaved order (main, branch, branch, main: ABBA) and the mean of the rounds, each round’s value shown beside it, so a drift of the machine shows;
  • correctness first: the GPU tests of the code changed (gpu-tests: INGA_CUDA=1 cargo test --release -p inga-cuda --test NAME -- --ignored), and the same greedy text (same-text: inga run --temp 0 -n 64) on both builds, the texts printed when they differ;
  • partial results printed after every step, so a session that stops still leaves what it measured, and a table of where the time went;
  • nsys per token: the kernels of -n 192 minus those of -n 64, over the steps in between (Inga’s bench runs once untimed, so twice). llama-bench’s warm-up generates one token only, so its own difference covers half as many steps: count them, never reuse Inga’s;
  • the report posted as an issue, then a FINE line.

On the P1000 (the self-hosted runner)

Section titled “On the P1000 (the self-hosted runner)”

docs/gpu-runner.md has the runner. Measures are dispatched on gpu.yml with ref (the branch), suites (none, or vulkan:NAME / cuda:NAME for one test file), model (hf://REPO:QUANT, or a file under INGA_MODELS) and tests (the inga bench arguments; several runs separated by ;). The runner is switched on by the maintainer: ask before relying on it, and keep each dispatch short.

  • To compare settings, run the variants one after the other in one run, the baseline first and last (-p 0 -n 128 -r 5 --device vulkan; ... --set KEY=true; ...).

  • --ab KEY=V drops a --set of the same key from its default side: --set K=true --ab K=false compares off with off. Use --ab K=true alone, or separate runs.

  • Two runs on different hours are not comparable (the same bench gave 47 and 62 tokens/s on two evenings): never compare across runs.

  • The runner’s disk and load. The models were on a USB 2.0 disk until 2026-11-10; the maintainer then changed the runner’s .env (likely to an internal disk: the env print of each job shows where the models are). The machine may run other processes. So every measure that reads the disk or runs long is repeated in ABBA order (main, branch, branch, main); the job prints the processes using CPU and GPU and the disk’s read speed. A negative result there does not discard an idea without a second measure elsewhere (the Colab T4 or an internal disk).

What is not measured

Section titled “What is not measured”

Goes into docs/todo/real-world-checks.md (the group that fits) and is said in the pull request and the changelog. A release does not wait for a measure.

Looking at another project

Section titled “Looking at another project”

When the maintainer points at a repository, a model or a dataset:

  1. Clone it into a scratch directory, never into the repository, and never run its code (no install scripts, no notebooks); read its README, docs and source.
  2. Licence first: MIT, Apache-2.0 and BSD can be ported with their notice (THIRD-PARTY-NOTICES.md); GPL and AGPL give ideas only; a proprietary EULA, ideas only and said so. An unknown licence is marked ❓, never guessed.
  3. Its numbers are its claims: written as “its claim”, with the source; marked ❓ what could not be checked.
  4. Where it goes: a row in docs/comparison.md (Part 1 engines, Part 2 apps, Part 3 routers, gateways and proxies) and an entry in docs/todo/inbox.md with what Inga could take, each idea tied to its source; a decision of the maintainer moves it into the backlog or a release.
  5. A model: its config.json (architectures, model_type, layer types) and a GGUF file’s header (the first megabytes, read with a range request: general.architecture and the keys), checked against Inga’s docs/supported-models.md and llama.cpp’s src/llama-arch.cpp. A model that is a known architecture is “expected to run, not run” until run.

Where to look, and what users say

Section titled “Where to look, and what users say”
  • The reference list: rafska/awesome-local-llm (inference platforms, engines, user interfaces, tools, hardware), chosen by the maintainer on 2026-10-30 as the list to go back to for future comparisons and improvements. At each survey, look at what is new in it since the last one and at the projects closest to Inga (the platforms, the engines for one PC or a few, the multi-machine ones, the user interfaces); the data-centre engines and kernel libraries matter less.
  • Read the issues, not only the code: for each project, its most-voted and most-commented open issues (and the all-time ones when a stale bot closes them), its complaint themes and most-wanted features, and outside opinion (marked “snippet only” when seen only in search results). For each pain point: does Inga solve it (where), partly, is it planned, or not.
  • A problem Inga does not have is a feature to bring out, never a comparison: Inga’s pages never say “that project has this problem and Inga does not”. The other projects’ issues stay in the maintainers’ notes as evidence of what people struggle with; what users read is the feature, told from their side, so that someone arriving from another tool thinks “Inga solves exactly what bothered me”: the job it makes easy (“one file, nothing else to install, the GPU found by itself”), shown with a demo, a guide or a published measure, and what is not yet measured or tested said first. The one exception is measured speed (docs/performance.md): side by side with the engines it is measured against, named, with their versions and configuration, because hiding them would not be honest (the maintainer, 2026-10-30). A problem Inga shares goes into the roadmap with its value and effort.

Taking in outside code

Section titled “Taking in outside code”

llama.cpp’s kernels and shaders are ported, not rewritten:

  • vendored unchanged from a pinned llama.cpp build (today b12032 for CUDA, b11489 for Vulkan, whose shaders are the same at b12032), the files and their SHA-256 in a SOURCES file, the licence copied beside them, checked by the build scripts and CI (tools/build-spv.sh --check, tools/build-ggml-ptx.sh);
  • compiled as llama.cpp compiles them: the same defines, the same launch parameters (grid, tiles, stream-k, workgroups), ported from its source and unit-tested against ports of its selection code;
  • no patch to the vendored files: when a compiler cannot build them, the compiler is pinned to a version that can (glslang 16.6.0, tools/install-glslang.sh), decided by the maintainer on 2026-10-29 in place of a shim;
  • the committed binaries (PTX, SPIR-V) are rebuilt by the scripts only, and a change of compiler that rewrites Inga’s own modules is a measured change of its own.

Working with agents

Section titled “Working with agents”

A large task can go to a sub-agent in a worktree of its own. Its brief holds the goal, the evidence (issue numbers, numbers, files), the hypotheses to check, these rules (the branch, the commit identity, check.sh, the debug key off until measured, only measured numbers, stop and report rather than push half-done work) and what to give back (the pull request, the design and why, the tests, a test of the Colab notebook for the measure). Its result is read and checked before it is reported to the maintainer.
