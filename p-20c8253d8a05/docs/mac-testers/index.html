Testing Inga on an Apple Silicon Mac

Inga runs large language models on your own computer, from one executable with nothing else to install, on the CPU or the GPU (CUDA, Vulkan and, on a Mac, Metal).

Why we need you

Section titled “Why we need you”

Inga’s Metal backend runs every layer of a model on a Mac’s GPU, and it gives the right answers on GitHub’s virtual Mac. What that machine cannot tell us is how fast it is, and whether the faster kernels written for real Apple GPUs are right: the M3 path (simdgroup_matrix tiles for the prompt, flash attention, SIMD-group reductions in generation) has never run on real hardware. Those kernels use features of the M1 and later GPUs that the virtual Mac does not have, and their speed depends on the chip. An M3 or M4 (any variant: base, Pro, Max, Ultra) helps most; M1 and M2 Macs are welcome too.

What the kit does, and what it does not

Section titled “What the kit does, and what it does not”

mac-test.sh runs everything below on your Mac and writes a report, report.md, that you paste into a GitHub issue. Each step is timed; a step that fails is noted in the report and the next one runs.

  1. Reads the hardware: chip, performance and efficiency cores, GPU cores, memory, macOS version, free disk, and whether the Mac is on battery or in Low Power Mode (both slow it down; the report says so).
  2. Runs inga --version, inga devices and inga devices --test (a tiny model on the GPU against the CPU).
  3. Runs metal_everything: every Metal kernel and a set of small synthetic models, checked against Inga’s CPU (a few minutes).
  4. Downloads three models from Hugging Face (inga pull), checking the free disk first: Qwen3-0.6B Q8_0 (0.6 GB), Llama-3.2-1B-Instruct Q4_K_M (0.8 GB), Qwen3-4B Q4_K_M (2.5 GB); with --big also Qwen3-30B-A3B Q4_K_M (18.6 GB, only with 32 GB of memory or more).
  5. For each model: 32 tokens of the same prompt on the GPU and on the CPU, which must be the same text, then inga bench (a 512-token prompt and 128 generated tokens, three times) on the GPU and on the CPU.
  6. If you have them installed, the same measurements with llama.cpp (llama-bench, for example from brew install llama.cpp) and MLX (pip install mlx-lm; MLX downloads its own copies of the models). Optional: without them those columns stay empty.

Every GPU check runs twice: on the M2 path (the default kernels, what Inga does today) and on the M3 path, the new kernels, which are off unless the environment key debug.metal_simdgroup is true (--set debug.metal_simdgroup=true). The script sets it for you, so the report has both columns side by side. A build of Inga without the M3 kernels ignores the variable, and its M3 column then repeats M2. You can use the variable yourself too: inga --set debug.metal_simdgroup=true run ... runs the M3 kernels, unset or false the M2 ones (the M3 kernels are then not even compiled).

It sends nothing anywhere. It only downloads: the models (from Hugging Face, into the standard cache, ~/.cache/huggingface/hub, or $HF_HUB_CACHE / $HF_HOME) and, when you run it without the kit, Inga’s release. The report holds no user name, host name or personal paths: they are replaced by ~, <user> and <host> in every file before the report is written. Read report.md before you paste it: it is plain text.

Time and disk: about 30–50 minutes (--quick: about 5), about 5 GB of disk (25 GB with --big), twice that with MLX installed. You can stop it at any time with Ctrl-C: the report is written with what was done. Plug the Mac in and leave it alone while it runs: other programs change the speeds.

Getting the kit

Section titled “Getting the kit”

Any of these:

  • A released version (the simplest): download the script alone and run it; it downloads Inga’s latest release for macOS (or the one of --release 0.26.0) into ~/.cache/inga-mac-tester:

    A release does not include metal_everything (the check of every kernel): the other steps run, and the report says it was skipped.

  • The kit the maintainer sends you for a branch being worked on: a link to a GitHub Actions run; download the artifact inga-mac-tester-<commit> at the bottom of the page (a zip holding inga-mac-tester-<commit>.tar.gz) and unpack it:

  • From source, with Xcode’s command-line tools (xcode-select --install) and Rust (https://rustup.rs):

The binaries are not signed

Section titled “The binaries are not signed”

Inga’s binaries are signed ad hoc, not with an Apple Developer ID, so macOS stops files that came through a browser (“cannot be opened because the developer cannot be verified”). Remove the quarantine flag from the kit’s folder once:

A release downloaded by the script (with curl), one installed by tools/install.sh (with gh or curl, Get Inga) and a build from source are not quarantined.

Running it

Section titled “Running it”

From the kit’s folder (or with sh mac-test.sh for the script alone):

The report is in inga-mac-report-<date>/report.md, the raw logs beside it in raw/, and everything in inga-mac-report-<date>.tar.gz.

Sending the results

Section titled “Sending the results”

Open a new issue and paste the content of report.md (pbcopy < inga-mac-report-*/report.md copies it). Add anything you noticed: the fans, another program running, an error on the screen. Attach the .tar.gz only if the maintainer asks for the logs.

What happens next

Section titled “What happens next”

The maintainer reads the report, fixes what failed or tunes what is slow, and sends you a new kit (or a new release). You run it again, usually with --quick first: two to four rounds are typical. Each round takes a few minutes of your time; the rest is the Mac’s.

Optional: a runner on your Mac

Section titled “Optional: a runner on your Mac”

If you can leave a Mac on and want to help more, it can run Inga’s Metal checks itself as a GitHub Actions self-hosted runner, as the maintainer’s PC does for NVIDIA (gpu-runner.md). The same safety rules apply: jobs start only by hand (manual dispatch) from the maintainer, never on pull requests from forks, so no code from strangers runs on your machine, and you can stop the runner at any time. Ask in your issue and the maintainer will tell you the steps (a registration token, the labels).

Credits

Section titled “Credits”

If you want, you are named in CHANGELOG.md and next to your machine’s rows in performance.md. Say in the issue how you would like to be credited (a name, a GitHub handle, or nothing).
