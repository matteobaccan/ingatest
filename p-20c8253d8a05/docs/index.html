The docs folder

What each file and folder is for. Start from the main README for what Inga is; the schedule of every feature is TODO.md (one file for each of the next three releases in todo/), what each release changed is the changelog (from 0.46.0, the first public release; before it, git and its tags).

For users

Section titled “For users”
File What it is
features.md Everything Inga does: what it replaces, its five parts, the highlights, the frontier models and the strategies for them (estimates, labelled so), what it tells you, what works today area by area, the drop-in servers, the web UI’s pages, the goals.
cli.md The command-line reference: every inga command and its options, the configuration file in short, the other programs’ environment variables Inga honours.
faq.md The questions people ask: installing by hand, how large a model can run, which device runs what, the kinds of models, giving a model a file, where Inga keeps its files, LM Studio’s and Ollama’s models, which Inga is running.
legal.md The legal notes: no warranty, the models’ and services’ own terms, your data, the names, the licence.
use-cases/ One from-zero guide per use case (chat, serve, GPUs, MoE, several machines, images, voice, agents, fine-tuning, the web UI, …), with an index grouped by topic, and the rules and template every guide follows. Among them, integrating Inga in a JavaScript application: the browser build in your own web page, or any JavaScript on inga serve.
install.md Installing Inga: the one-line installers (install.sh, install.ps1) attached to every release, their options and what they change, the manual download and its checksum, uninstalling, macOS’s Gatekeeper; the package manager files in packaging/.
config.md The configuration file inga.toml: where Inga finds it, which value wins, the secrets, and every key with its flag, default and meaning; made from src/config/keys.rs and checked by a test (INGA_BLESS=1 cargo test --bin inga config_doc writes it again).
supported-models.md What Inga runs: architectures in GGUF files, safetensors classes, vision and audio projectors, weight types.
performance.md Inga’s measured speed next to llama.cpp on the same machine, files and commands: first every comparison ranked by how far Inga is from the fastest engine, then the tables (fastest first), one row per measurement, the latest one, with the Inga version and date that produced it.
what-inga-replaces.md The programs Inga can take the place of (llama.cpp, Ollama, LM Studio, LiteLLM, whisper.cpp, Open WebUI, an MCP client, a LoRA trainer, …) and the dependencies no longer needed (Python, PyTorch, the CUDA Toolkit, ffmpeg, …), with what to keep and what to check before uninstalling.
integrations/ One page per coding tool (Claude Code, Codex, opencode, pi, aider, Qwen Code) on inga serve, with inga connect.
api-node-presets.md The provider presets of inga node add and the web UI’s API nodes, grouped (cloud providers, gateways, local servers), each with its API, key variable and links.
branding.md Runtime branding (inga serve --branding DIR): the folder’s files, branding.json’s keys and the CSS variables a brand may set.
testers.md, mac-testers.md For volunteers: what to test on each kind of machine, the Mac test kit, and the Test report issue form.
wasm.md Inga in the browser at https://matteobaccan.github.io/ingatest/: a browser tab (CPU or WebGPU), what works, the browsers, the Inga in the browser report issue form.
talks/ A presentation of Inga in Marp Markdown, Italian and English with the same slides, in three lengths (5 minutes, 20 minutes, all); how to build it as PDF, HTML or PowerPoint; every release updates it and attaches its PDF and HTML.
launch-plan.md Where and in which order Inga is announced (the browser beta, then the public project), what to post and how to answer.
api/ OpenAPI 3.1 descriptions of every route of inga serve (OpenAI, Anthropic, Ollama, LM Studio, KoboldAI, Inga’s own), checked against the server’s router by tests/api_specs.rs, with curl examples and the tests that exercise each API.
images/ Screenshots of every part of the web UI and of the browser page, light and dark, used by the README, the guides and the website; node tools/screenshots/stubbed.cjs --docs makes them again.

Tables that fit the page

Section titled “Tables that fit the page”

GitHub draws a Markdown table as wide as its columns need, then scrolls it sideways, and the reader loses the first column. tests/doc_tables.rs estimates every table’s width from what cannot wrap (long words, repository names, code spans without spaces, URLs shown as text) and fails above about 110 characters; more than 5 columns, or a row over 300 characters with 5 or more, is a warning. A flagged table is fixed this way:

  1. No more than 5 columns. A comparison of six products is two tables (for example gateways, then routers), or the products become rows and the features columns. In comparison.md (Parts 1 and 3) Inga has a table of its own in each section, before the other projects’.
  2. Prose goes below the table. A cell holds a short fact: ✅ / ❌ / 🟡 and a few words. The explanation goes in a numbered note under the table (¹, ²).
  3. Shorter unbreakable pieces. context_window_fallbacks becomes “fallbacks by context window”, with the name in the note; a repository shows its name only (litellm), or the project’s name links to it, since the link holds the owner; a URL becomes a link with a short text.
  4. The first column stays short, so it is never the one scrolled away.

A table that must stay wide (a reference matrix read only on wide screens) goes in tests/doc_tables.allow (path:line reason) with the maintainer’s yes in its pull request.
