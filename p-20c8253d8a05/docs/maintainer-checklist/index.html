The maintainer's checklist

What only the maintainer can check: the real-world checks of todo/real-world-checks.md (groups A–E and H). The bullets tagged [runner] run on his self-hosted runner through one workflow; the ones tagged [manual] need him, in the sessions below. After each run or session: remove the bullets that passed from docs/todo/real-world-checks.md, and open an issue (or a fix) for each one that failed.

1. On the runner: the Real-world checks workflow

Section titled “1. On the runner: the Real-world checks workflow”

The runner is the one of the GPU workflow (gpu-runner.md): the maintainer’s Windows PC (Xeon W-2123, 32 GB of RAM, Quadro P1000), labels self-hosted, gpu. Besides what gpu-runner.md asks for, the checks use:

What For Without it
INGA_MODELS set for the runner’s service (the dedicated models disk) every group only what download fetches
HF_HUB_CACHE (or HF_HOME) set for the runner’s service, and access to huggingface.co every group: the models already in that cache are used, each group’s hf:// models looked up there first; H: the Hub itself the checks’ own cache in the tool cache
The Visual Studio C++ tools’ C++ CMake tools for Windows A: building llama.cpp, whisper.cpp, stable-diffusion.cpp, transcribe.cpp group A compares nothing
Python 3 on the PATH B: the SDKs (in a virtual environment of the tool cache); D: huggingface_hub those checks fail
Ollama (ollama on the PATH) B: its CLI against Inga, its store; E: Inga against Ollama skipped
LM Studio B: its folder read by inga list --lmstudio an empty list
Git for Windows E: tools/ollama-compare.sh through its bash (jq is downloaded) skipped
The runner’s service running as LocalSystem (an Administrator) D: inga service under the test name inga-realcheck skipped: run it by hand (session 2)
The repository secret HF_TOKEN (a read token) download: gated models public models only

Launch it: GitHub → Actions → Real-world checks → Run workflow on main (or the API: gh workflow run real-checks.yml -f groups=A,B,D,E,H,L), with:

Input Value
groups the groups to run, e.g. A, or A,B,D,E,H for all (default A)
models a models folder other than the runner’s INGA_MODELS (default: empty)
max_gb the largest model file to run, in GB (default 20: 32 GB of RAM leaves room for the reference beside it). Raise it for Mixtral-8x7B, Kimi-Linear-48B, Nemotron 3 Super and the 32B–36B models of group A, which then stream from the disk
download fetch the groups’ small models when missing (SmolLM2-135M, Qwen3-0.6B, Llama-3.2-1B, Whisper base.en) into the Hugging Face cache (the runner’s HF_HUB_CACHE when set, else the checks’ own), and run group D’s download checks (in an empty cache of their own)
hf more models for the groups, hf:// references separated by commas, looked up in the cache (and fetched with download)
fit_files group H: the Hub’s GGUF files whose header is read lean and whole (org/repo/file.gguf, separated by commas; empty: group-h.ps1’s list)

What each group does (the scripts in tools/real-checks/ say it in full):

  • A (group-a.ps1): builds llama.cpp 781dbc5 with tools/llama-oracle.cpp, whisper.cpp d1be6fd with tools/whisper-oracle.cpp, stable-diffusion.cpp f89d9b1 and transcribe.cpp 5d66f60 once into the tool cache (the first run takes about an hour); runs the ignored tests that need them (the llama.cpp oracle on the fixtures’ files, llama.cpp’s chat templates and vocabularies, a real Silero model’s probabilities against whisper-oracle --vad-probs); then, for every model under max_gb: for language models the tokens against llama-tokenize, the logits of the first 32 positions against llama-oracle logits (the same best token or a near-tie, the top 5 log-probabilities close: the pass/fail of the numbers), a greedy completion against llama-completion (info: a near-tie parts two texts for good) and the perplexity against llama-perplexity (1 %), all on the CPU, then Inga’s perplexity on its default device within 1 % of its CPU’s when a GPU runs any of it (the row says what it runs); embeddings against llama-embedding (cosine ≥ 0.999); each mmproj*.gguf with its language model against llama-mtmd-cli (the first words of a greedy description); OuteTTS with WavTokenizer (inga speak twice: the same audio, a plausible length and loudness; not against llama-tts, whose prompt and speaker differ); jfk.wav against whisper-cli (greedy and five beams; whisper.cpp’s ggml .bin files too, which inga scan does not list: found by their header) or transcribe-cli (the transcript it writes with -o, not its standard output, a report); diffusion language models against llama-diffusion-cli (info; its text is the end of its standard error); and one picture against sd-cli for Stable Diffusion / Flux checkpoints. A reference built without one of its programs (whisper-cli, llama-oracle, llama-embedding, …) fails its build row: the first run after this change builds the references again (about an hour).
  • B (group-b.ps1, clients.py): serves Qwen3-0.6B or Llama-3.2-1B (and Qwen2.5-7B-Instruct or Llama-3.1-8B-Instruct for the tool calls) with --parallel 8; the OpenAI SDK (chat, streaming, log-probabilities, a tool call, parse, the Responses API), the Anthropic SDK, the ollama client, LM Studio’s REST API, eight clients at once, Ollama’s CLI pointed at Inga; the Ollama store and LM Studio’s folder.
  • D (group-d.ps1): inga service install / status / logs / stop / start / uninstall; the Hugging Face cache without symlinks, shared with huggingface_hub both ways, a download stopped and resumed (with download); the memory Inga detects; a model larger than the free RAM streamed from the disk (the largest one in the models folder, whatever max_gb); inga devices --test; the same greedy text on the CPU, CUDA and Vulkan; the PowerShell completions.
  • E (group-e.ps1): inga bench pp512 / tg128 on the CPU and the GPU for machine C’s models, and tools/ollama-compare.sh on the CPU and the GPU for the “Inga against Ollama” models (SmolLM2-135M Q8_0, Llama-3.2-1B Q4_K_M, Qwen3-4B Q4_K_M, Qwen3-30B-A3B Q4_K_M): the rows to copy into performance.md. llama.cpp on the same card is the GPU workflow’s comparison (gpu.yml with a model and compare: llama.cpp).
  • L (group-l.ps1): a big mixture of experts in little RAM. Qwen3-30B-A3B Q4_K_M (found in the models folders) on the CPU, greedy, all in RAM, then with --mem-limit 8G, 4G and 2G (and 8G / 4G again with --set debug.direct_reads=true, past Windows’ file cache): each run’s peak working set and private bytes, decode speed, wall time and load messages, and its text byte-identical to the reference’s.
  • H (group-h.ps1): the Hub itself, from the runner. The voice: the suggested speech model’s file (SUGGESTED_TTS) and the vocoder’s exist, OuteTTS 0.3 500M’s and 1B’s cards say the licence and languages the voice spec (§2.1) and the web UI say, and the chat template the Hub reads in the file. The fit before the download: for a few real GGUF files (Llama 3.2, Qwen3, Gemma 3, a split Qwen2.5-7B, Qwen3-30B-A3B, OuteTTS), the header read without its vocabulary against the whole header, the bytes and requests of each and the verdict on the P1000 from each (the same, or the check fails), and the licence, languages and template each header holds. Its report is the job’s summary too.

The results: the run opens (or updates, the same day) the issue “Real-world checks — ”: a table of pass / fail / skip / info per group, then each group’s report. The run’s artifacts report-A … report-H hold the reports and the files behind them (pictures, the server’s log). A group that fails does not stop the next ones.

The nightly real-file rotation

Section titled “The nightly real-file rotation”

real-nightly.yml runs by itself at 01:23 UTC on the same runner (free minutes on GitHub’s Free plan; only the small job that rewrites the issue runs on a hosted runner, about a minute a night). Each night the slots of tools/real-checks/rotation.json of the UTC weekday, plus a canary (SmolLM2-135M). The PC is switched on only now and then, so a slot is meant to end within about 45 minutes: each group of the rotation is cut into slots, one job each, run in turn:

Day Group Slots What
Mon dense-text dense-text-1, dense-text-2 Qwen2.5-0.5B, TinyLlama, LFM2-350M; EXAONE 3.5, SmolLM3, Qwen3.5-0.8B
Tue gemma-phi gemma-phi-1, gemma-phi-2 Gemma 3 1B, Gemma 2 2B, Gemma 2B; Gemma 3n E2B, Phi-3-mini, Phi-4-mini
Wed weight-types weight-types-k, weight-types-legacy, weight-types-iq4-3, weight-types-iq2-1 Qwen3-0.6B F16 made into every type by llama-quantize (and llama-imatrix), a quarter of the types each (the entry’s types): perplexity of each against llama-perplexity, inga quantize’s bytes against llama-quantize’s
Thu vision vision-1, vision-2 SmolVLM-256M, Gemma 3 4B; Qwen2.5-VL-3B, Qwen3-VL-2B (images), Ultravox (audio)
Fri speech speech Whisper tiny.en / base.en / tiny-q5_1, openai/whisper-tiny against ggml-tiny.bin, Silero v5.1.2, Parakeet v3, OuteTTS + WavTokenizer
Sat encoders-hf-spec encoders-spec, hf-formats nomic-embed, bge-small, bge-m3, a reranker, Qwen3-1.7B with a Qwen3-0.6B draft; Qwen3-0.6B safetensors, MLX 4-bit, GPTQ, AWQ
Sun big big-1, big-2 a four-week cycle of larger files: gpt-oss-20b; Mamba-Codestral-7B and LFM2-8B-A1B; SD 1.5; OLMoE and LLaDA-8B (big-2 runs in weeks 2 and 4 only)

  • The jobs. plan (a hosted runner) picks the night’s slots and, from the tracking issue’s state, the entries that passed on this commit already; references builds Inga and the reference programs (llama.cpp, whisper.cpp, stable-diffusion.cpp, transcribe.cpp), each once per commit and kept in the runner’s tool cache, so their first build (an hour or more) is not counted in a slot’s time; then one job per slot (limit 75 minutes), and issue (a hosted runner), which writes every slot’s results, also when a slot failed or the run was cancelled. A slot that failed is run again alone with Re-run failed jobs.

  • Resume. An entry that passed on the same commit is not run again: the plan reads each entry’s last commit from the tracking issue, and the runner keeps a journal of the entries of the current commit (nightly-journal.json in its tool cache), so a slot stopped by a shutdown before its results reached the issue goes on from where it stopped the next time, and reports the entries it had passed. A slot whose entries all passed is not run; rerun (Run workflow) runs them again anyway. A new commit of main runs everything again.

  • The disk. Downloads go to a folder of their own (the tool cache’s inga-real-checks\nightly-hf), emptied at the start and after each model: download, check, delete. Before each download the free space of that drive is measured: a model whose files (the Hub’s sizes) and scratch space do not fit is skipped, the row saying how much it needs and how much is free. A model already in the runner’s own Hugging Face cache (HF_HUB_CACHE) is read there and never written or deleted.

  • Entries to verify. Entries of confidence M or U ("verify": true) are file names not confirmed yet: their first run reports what the Hub has (in the issue’s “Entries to verify”); a missing file is a skip there, not a failure. Fix rotation.json from it and drop the flag.

  • The results go to one issue, “Real-file checks — tracking”: its body (the coverage matrix: each entry’s last result, last pass and last failure with commit and run) is rewritten after each slot; a comment is added only when an entry flips between pass and fail. The per-date issues of the workflow above stay for the manual groups.

  • Queued nights. Nights queued while the PC is off do not pile up: the newest cancels the one waiting (the slots it finished still reach the issue).

  • On demand: Actions → Real-file nightly → Run workflow with a slot (a slot or a whole group; and a week for big), or gh workflow run real-nightly.yml -f slot=weight-types-k. The Real-world checks workflow runs a slot too, as group N (-f groups=N -f slot=vision): its results go to that run’s dated issue, not to the tracking issue.

  • The test switches the checks set for the ignored tests (not settings of Inga; development.md lists them): REAL_CHECKS_LOGITS_MODEL, REAL_CHECKS_LOGITS_TOKENS, REAL_CHECKS_LOGITS_REF, and REAL_CHECKS_LOGITS_REF_ALT for the limit relative to llama.cpp’s own spread (crates/inga-engine/tests/real_logits.rs), REAL_CHECKS_SILERO_REF, REAL_CHECKS_SILERO_SAMPLES with INGA_SILERO (crates/inga-vision/tests/vad.rs), and INGA_MODELS for mlx.rs.

2. By hand, on the runner’s PC (Windows)

Section titled “2. By hand, on the runner’s PC (Windows)”

One sitting, with inga serve running a real chat model (Qwen3-4B or larger for the agents):

  1. Clients: Open WebUI pointed at Inga’s OpenAI API (chat, streaming, the prefix cache and log-probabilities) and at its Ollama API, and a transcription; Claude Code with ANTHROPIC_BASE_URL=http://127.0.0.1:8080; Codex on the Responses API; OpenClaw with a real model (and a chat app if one is at hand); llama.vscode with Qwen2.5-Coder on /infill; SillyTavern and KoboldAI Lite; an OpenTelemetry collector (otelcol with its debug exporter); the API docs’ OpenAPI files through a generator (Python, TypeScript, Java); web search through a SearXNG instance; Inga under NVIDIA PAIR.
  2. Windows: inga service install / start / status / logs / stop / uninstall in an Administrator terminal, if group D skipped it; a download behind HTTPS_PROXY.
  3. Disks: --mirror with a copy of a model on a second NVMe disk (tools/large-model-tests.md, step 5); the frontier models too large for the runner’s checks (Kimi K3, DeepSeek V4-Flash, GLM-5.3-Flash, Qwen3.8-Flash-Next, DeepSeek V3 / V3.2, Kimi K2, GLM 5): inga info, a short answer, their speed from the disk (tools/large-model-tests.md), and against llama.cpp where it runs them.

3. A LAN session (two or three PCs)

Section titled “3. A LAN session (two or three PCs)”

The runner’s PC plus one or two others (Linux and macOS if possible), wired and then on Wi-Fi, with the same model files on each (Llama-3.1-8B-Instruct and Qwen3-30B-A3B in Q4_K_M; Mixtral-8x7B for the experts). In this order, each time the greedy text against one machine and the tokens per second:

  1. the pipeline: inga worker on the others, inga run --nodes and inga serve --nodes with a client;
  2. experts on other machines: --expert-nodes, against --nodes and against one machine streaming its experts from disk;
  3. tensor parallelism: --tp-nodes with Llama, Qwen and Gemma files;
  4. hybrid models across machines: Qwen3.5 / 3.6 and Qwen3-Next with --nodes, and with a draft model;
  5. the Inga mesh: inga satellite --mesh NAME on the others and inga serve MODEL --mesh NAME: discovery through the switch and Wi-Fi, a firewall that drops multicast (then --peers), a Mac’s mDNSResponder on port 5353, the measured speed against the placement’s estimate (within 20 %), the weights sent at the LAN’s speed and a restart that sends nothing, a satellite unplugged mid-answer, the size the received weight files take on NTFS.

4. Phones and browsers

Section titled “4. Phones and browsers”

One sitting with an Android phone (Chrome) and an iPhone (Safari) on the LAN, and Firefox and Safari on a computer: the web UI (chat, the model hub with a search and a download, the image mode, the Video button), the PWA installed on each phone (behind tailscale serve or a TLS reverse proxy, as docs/use-cases/ explains).

5. Other machines and hardware

Section titled “5. Other machines and hardware”

Whenever one is at hand; each is its own bullet of group D or E:

  • macOS (Apple Silicon): a chat with Llama-3.2-1B and Qwen3-0.6B, inga run hf://… on a clean machine, the memory against Activity Monitor, a model larger than the RAM streamed (whether MADV_DONTNEED frees its pages), inga service as a launch agent and daemon.
  • Linux: the same chat and hf:// run, inga service with a real systemd (user and system units, lingering), the zsh and fish completion scripts, the Docker images of the last release (x86-64, and ARM64 on an ARM machine).
  • Linux ARM64: the NEON kernels (inga bench), the CPU steps.
  • The laptop (machine B): its rows of performance.md with the current Inga (inga bench <model> -p 128 -n 64 -t 1,4 -r 3).
  • An Alder Lake or later client CPU: the AVX-VNNI panels against llama.cpp.
  • A Xeon with AMX: Inga against Ollama (tools/ollama-compare.sh).
  • Intel and AMD GPUs: Vulkan (inga devices --test, a model with --gpu-layers all); on an AMD card with ROCm’s runtime, HIP too (--device hip, INGA_HIP=1 cargo test -p inga-cuda -p inga-hip -- --ignored).
  • The Radeon RX 9060 XT of issues #301 / #324 (the reporter’s): Nemotron 3 Super and Ornith-1.5-35B-A3B / Qwen3.6-35B-A3B with experts on the GPU, the out-of-memory fallback; asked of the reporter on the issues.

6. Mac testers

Section titled “6. Mac testers”

Volunteers with Apple Silicon Macs run the kit of mac-testers.md and paste its report into an issue (“Mac tester report”). Each report checks both Metal paths: M2 (the default kernels) and M3 (debug.metal_simdgroup=true).

  • A released version: nothing to build. Point the volunteer to mac-testers.md: the script alone downloads the latest release (--release V for another). A release has no metal_everything, so its report checks the kernels only through inga devices --test and the greedy text of the real models.
  • A branch: Actions → Mac tester kit → Run workflow, from main, with ref = the branch, tag or commit. One macOS build (about 10–15 minutes, no test suite); the run’s page ends with the artifact inga-mac-tester-<commit> (kept 14 days). Send the volunteer the run’s link. The kit holds inga, metal_everything, mac-test.sh (from the commit the workflow ran from, so an old branch gets the current script) and MANIFEST.txt (ref, commit, date, rustc).
  • Reading a report: first the warnings (battery, Low Power Mode: ask for a re-run plugged in), then Correctness: metal_everything must say N checks, 0 failed on both paths, its FAIL rows naming the kernel or model that differs; devices --test must say OK; the greedy text of each model must be the same text on M2 and M3 (a difference late in the text can be a near tie: compare with the raw outputs, in the .tar.gz if needed). A --device metal cell marked CPU: no layer on Metal means Inga put no layer on the GPU (raw/bench-*.log says why). Speed: M3 / M2 is the gain of the M3 kernels, M3 / llama.cpp the gap to close (§4 of the Metal spec: pp512 ≥ 70 % of llama.cpp for M3, decode ≥ 80 %). The Steps table shows what failed or was skipped, and the Kit block which build ran.
  • Into performance.md: one “Machine” section per tester’s Mac (chip, cores, GPU cores, memory, macOS from the report’s Hardware table; the command: inga bench <model> -p 512 -n 128 -r 3 --device metal, with and without debug.metal_simdgroup=true), then a prefill and a decode table as the other machines’: one row per engine (Inga Metal M2, Inga Metal M3, Inga CPU, llama.cpp with its build number, MLX) with the Inga version of the report, sorted fastest first; the gaps to llama.cpp go into Where Inga stands. Credit the tester as they asked, in the section and in CHANGELOG.md.
  • The loop: fix, push, build a new kit for the same branch, ask for a re-run (--quick first); keep the reports in the same issue so the rounds can be compared.

7. Before each release: the web UI’s screenshots

Section titled “7. Before each release: the web UI’s screenshots”

Take the pictures of docs/images/ again, so they show the web UI of the release:

No build and no server: the script assembles the page from crates/inga-server/webui/ (as the build does), opens it in headless Chromium (Playwright) with every route answered by a staged machine (tools/screenshots/fixtures.cjs and gallery.cjs: a laptop with an RTX 3060 of 6 GiB, three PCs in the mesh, made-up chats, documents, projects, a picture and a clip; none of this computer’s models, chats or paths show), and takes every part of the web UI and the browser page (web/) in the light and the dark theme, 1280 x 860 (the phone’s 390 x 844), into docs/images/webui-NAME.png and webui-NAME-dark.png; then tools/screenshots/optimize.py (Pillow) makes them smaller, and tools/screenshots/docs-images.json keeps the SHA-256 of the page and of web/ they show. A picture that cannot be taken fails the run. It takes about four minutes and needs Node.js with Playwright and its Chromium (npm install -g playwright, npx playwright install chromium). --check fails when the web UI or the browser page changed since that stamp: tools/release.py stops on it, and so does the release pull request’s CI. Look at every image before committing; a new page or tab gets an entry in the script’s SHOTS (with docs: true) and a cell in the galleries (features.md, chat-in-the-browser.md) and, when it is a feature of its own, a tab on the website’s landing page (docs/website.md). Details: tools/screenshots/README.md.
