Release 0.30.1· MIT · written in Rust

Local models.
Any GPU.
Even in the browser.

One executable with no runtime dependencies. Inga runs language, vision, audio and image models on your CPU and GPU, serves them through the APIs your tools already speak, opens a chat page in the browser, and splits a model across your PCs when one is not enough. And it always tells you what it is doing.

Try in your browser Download Docs
# chat in the terminal with a model from Hugging Face
$ inga run hf://bartowski/Llama-3.2-1B-Instruct-GGUF:Q4_K_M
# or serve it: web UI + OpenAI, Anthropic, Ollama APIs
$ inga serve hf://bartowski/Llama-3.2-1B-Instruct-GGUF:Q4_K_M
  • 1executable, no Python, no DLLs, no CUDA Toolkit
  • 5GPU back ends: CUDA, Vulkan, Metal, ROCm / HIP, WebGPU
  • 5APIs: OpenAI, Anthropic, Ollama, LM Studio, KoboldAI
  • 10languages in the web UI

Beta

Try it now, in this browser

Inga compiled to WebAssembly: a GGUF model runs in a browser tab, on the device’s CPU or on its GPU through WebGPU. Nothing to install, nothing sent anywhere: the model is downloaded to the browser’s private storage and runs there. Start with a small one (SmolLM2-135M), then browse about fifty models from Hugging Face, each marked by whether it fits your device.

One executable replaces…

Don’t install a thousand different products — just use Inga

Five parts in one file — engine, API server, web app, mesh, network of nodes — usable together or on their own.

  • An inference engine

    instead of llama.cpp, whisper.cpp, stable-diffusion.cpp

    Its own engine in Rust, every llama.cpp quantization, output checked against those projects.

    inga run

  • A model runner

    instead of Ollama, LM Studio

    Models from Hugging Face, or the ones Ollama and LM Studio already downloaded, loaded on demand.

    inga list --ollama

  • GPU builds

    instead of CUDA, ROCm, multi-GPU builds

    CUDA, Vulkan, Metal and ROCm / HIP in one file, with only the driver installed.

    --device cuda:0,vulkan:1

  • An API server

    instead of vLLM, llama-server, LocalAI

    The OpenAI, Anthropic, Ollama, LM Studio and KoboldAI APIs, streaming and tool calls, several models and users.

    inga serve --no-webui

  • A router or gateway

    instead of LiteLLM, llama-swap

    Other servers and 113 provider presets as API nodes, routes with fallback, keys with budgets.

    inga node add

  • A chat web app

    instead of Open WebUI

    Chat with a model hub, an arena, web search, documents, a memory, image generation.

    inga serve

  • Speech tools

    instead of faster-whisper, a TTS server

    Transcription streamed live, text to speech, a hands-free voice chat.

    inga transcribe --stream

  • An agent host

    instead of an MCP client, a scheduler

    MCP servers’ tools, Agent Skills and scheduled prompts, each tool call approved.

    inga mcp

  • A quantizer

    instead of llama-quantize

    The same GGUF file, byte for byte.

    inga quantize

  • A LoRA trainer

    instead of Python, PyTorch

    LoRA fine-tuning of small models on the CPU, adapters for --lora.

    inga finetune

  • A cluster

    instead of one big machine

    One model over the PCs of a LAN: layers, experts or slices, found by mDNS, encrypted.

    inga satellite

Drop-in

Replace Ollama, LM Studio or llama-server

Switch the other server off, start Inga on its port: its clients do not change, and the models those apps downloaded run without a second copy.

Ollama

# the models Ollama downloaded, with whether Inga runs them
inga list --ollama
# stop Ollama, then serve on its port
systemctl stop ollama
inga serve ollama://llama3.2:3b --port 11434

Ollama’s /api/chat, /api/generate, /api/tags, /api/embed… and the OpenAI /v1 routes on the same port.

coming in 0.31 --like ollama (Ollama’s port beside Inga’s) and inga pull ollama://qwen3:0.6b, without Ollama installed.

LM Studio

# LM Studio's GGUF files and MLX folders
inga list --lmstudio
inga serve ~/.lmstudio/models/lmstudio-community/\
  Qwen3-4B-GGUF/Qwen3-4B-Q4_K_M.gguf --port 1234

LM Studio’s REST API (/api/v0/models, /api/v0/chat/completions) and the OpenAI routes. MLX weights are read as stored on the CPU and on a Mac’s GPU.

coming in 0.31 --like lmstudio: port 1234 beside Inga’s 8080.

llama-server

# the same GGUF file, the same default port
inga serve model.gguf
# OpenAI-compatible clients: http://127.0.0.1:8080/v1

Chat and text completions, embeddings, tool calls, JSON schemas and GBNF grammars, every common sampler, speculative decoding.

coming in 0.32 llama-server’s own /completion, /props and /slots.

Measured, not promised

Numbers, with their caveats

Every figure here is a row of docs/performance.md: the machine, the version, the date and the command are there.

2 GBof RAM

Qwen3-30B-A3B, a 17.28 GB file, answers in 2 GB of RAM

The same 64 tokens as with all of it in RAM, under --mem-limit 8G, 4G and2G: 6.7, 2.5 and 1.7 tokens/s on the CPU. The experts are read from the SSD while it runs.

One machine (Xeon W-2123, 32 GB, NVMe, Windows), one run each, 2026-10-15. Those speeds were largely served by Windows’ file cache; past it (direct reads) 3.3 tokens/s at 8 GB and 0.8 at 4 GB.

1.3–1.7×llama.cpp

Generation on the CPU, 1B-class models

Faster than llama.cpp on the same machine, files and commands, after a long prompt too.

Prompt processing is behind: 0.84–0.86× at 512 and 2048 tokens, about 0.5× against llama.cpp’s AMX path. Measured on a 4-vCPU cloud machine.

1.12×llama.cpp

Qwen3.8-27B on an RX 9060 XT (Vulkan)

8.9 tokens/s against llama.cpp’s 7.9, generating, on a tester’s card (0.29.0).

Prompt processing there is 0.39×: Vulkan prefill is the known weak spot, on the roadmap.
