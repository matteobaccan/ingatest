One executable · MIT · written in Rust

Local models.
Uses what you have.
GPU optional.

One executable with no runtime dependencies. Inga makes the most of the hardware you have instead of asking you to buy special hardware: it runs language, vision, audio and image models on the CPU alone, uses a GPU when there is one, reads models larger than the RAM from the SSD, and scales with what you add: another GPU, another PC on your network, a remote server. It serves them through the APIs your tools already speak, opens a chat page in the browser, even runs in one, and always tells you what it is doing.

In the browser

Try it now, in this browser

Inga compiled to WebAssembly: a GGUF model runs in a browser tab, on the device’s CPU or on its GPU through WebGPU. Nothing to install, nothing sent anywhere: the model is downloaded to the browser’s private storage and runs there. Start with a small one (Qwen3.5 0.8B or Llama 3.2 1B), then browse about fifty models from Hugging Face, each marked by whether it fits your device.

One executable replaces…

25 kinds of program, one file: Inga

Engines, model runners, servers, gateways, chat apps, speech, images, agents and trainers: the list names 25 kinds of program Inga takes the place of, and 12 things you no longer install for them (Python, PyTorch, the CUDA Toolkit…). Five parts in one file — engine, API server, web app, mesh, network of nodes — usable together or on their own.

Inga obliges you to replace nothing: use it for one of the things it does, beside your programs. One program in place of many gives you this:

  • Simpler: one program to install, update and learn.
  • The memory used as one: one server counts every model’s RAM and GPU memory, makes room for the model you ask for, keeps idle chats on the SSD and gives memory back when another program needs it.
  • Nothing goes out unless you ask: no data sent by itself; a report or an update check is shown before it is sent.
  • People who answer: ask on GitHub’s issues in your language, and the answer comes in it.

  • An inference engine

    Its own engine in Rust, every llama.cpp quantization, output checked against those projects.

Your own model

Your own model, uncensored if you want, made on your PC

Take a model Inga runs and make it yours, on your machine: its weights never leave it. The model’s licence still applies: Customize reads it, says it in plain words and stops where it does not allow the change.

Remove its refusals

inga customize MODEL.gguf --edit abliterate --fetch

For a dense model (Llama, Qwen, Mistral, Phi and the like) that refuses too often: the direction it takes when it refuses is found and taken out, the result measured beside the original and written as a new file next to it. Also the web UI’s Customize page, under Models.

Train it on your data

inga finetune MODEL.gguf --data train.jsonl \
  -o my-lora.gguf

A LoRA adapter of a small dense model trained from your JSONL, on the CPU or a GPU (--device cuda:0), then loaded with --lora: a few MB beside the original.

Steer it while it answers

inga run MODEL.gguf --steer DIRECTION.gguf:0.8

A control vector added to the model’s activations as it answers, the weights untouched: more formal or more casual, or the refusal direction Customize found, per request in inga serve too.

Replace

Six tools, one command each

Switch the other program off and start Inga in its place: its clients do not change, and the models those apps downloaded run without a second copy.

Ollama

# the models Ollama downloaded, with whether Inga runs them
inga list --ollama
# stop Ollama, then serve on its port
systemctl stop ollama
inga serve ollama://llama3.2:3b --port 11434

Ollama’s /api/chat, /api/generate, /api/tags, /api/embed… and the OpenAI /v1 routes on the same port.

--like ollama (Ollama’s port beside Inga’s) and inga pull ollama://qwen3:0.6b, without Ollama installed.

LM Studio

# LM Studio's GGUF files and MLX folders
inga list --lmstudio
inga serve ~/.lmstudio/models/lmstudio-community/\
  Qwen3-4B-GGUF/Qwen3-4B-Q4_K_M.gguf --port 1234

LM Studio’s REST API (/api/v0/models, /api/v0/chat/completions) and the OpenAI routes. MLX weights are read as stored on the CPU and on a Mac’s GPU.

--like lmstudio: port 1234 beside Inga’s 8080.

Open WebUI

# the chat page, the APIs and the models in one file
inga serve
# then open http://127.0.0.1:8080/

A chat page in the browser with a model hub, documents in collections answered with their sources, web search, a memory, and accounts with a login and roles (inga user add).

Keeping Open WebUI? Point its OpenAI connection at http://127.0.0.1:8080/v1.

vLLM

# many users at once on one GPU
inga serve model.gguf --parallel 64 \
  --device cuda:0 --gpu-layers all

The sessions generating together computed as one batch on the GPU (CUDA, HIP, Vulkan), a long prompt read beside them, a prefix cache, the OpenAI API on /v1.

GGUF files, and Hugging Face’s safetensors directories (AWQ, GPTQ, FP8 too), with no Python.

LiteLLM

# a provider or another server as a node
inga node add groq
inga node add work-pc http://192.168.1.20:8080

One endpoint for the local models and the remote ones: presets for 113 providers, routes with fallback, named keys with limits and budgets.

The keys kept encrypted on your machine.

A remote coding CLI

# a coding agent on this folder, on a local model
cd my-project
inga code
# or Claude Code on inga serve
inga connect claude-code --run

In place of a coding CLI that sends your code to a cloud model: Inga’s own agent, or Claude Code, Codex, OpenCode and others pointed at inga serve.

Your code stays on your machine.

From the smallest to the largest

Choose the model: Inga runs it

The machine decides how fast a model goes, not whether it runs: if Inga supports its architecture, it runs, and Inga says how it placed it and how fast it goes.

  • 135Mparameters: SmolLM2 135M, small enough for a phone
  • 1Tparameters: the architectures of Kimi K2, Ling-1T and Ring-1T are supported, mixtures of experts; and Meta’s Muse Spark Open, 816B
  • 0 GPUsneeded: the CPU alone runs every architecture Inga supports; a GPU of any size takes the layers that fit, the CPU the rest
  • RAM < modela model larger than the memory runs from the SSD, slower: dense layers read one after the other, a mixture’s experts streamed and cached
  • N PCsone model over the computers of your network, each running the layers or experts it can hold
