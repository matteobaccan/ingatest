Release 0.46.5· MIT · written in Rust

Local models.
Uses what you have.
GPU optional.

One executable with no runtime dependencies. Inga makes the most of the hardware you have instead of asking you to buy special hardware: it runs language, vision, audio and image models on the CPU alone, uses a GPU when there is one, reads models larger than the RAM from the SSD, and scales with what you add: another GPU, another PC on your network, a remote server. It serves them through the APIs your tools already speak, opens a chat page in the browser, even runs in one, and always tells you what it is doing.

In the browser

Try it now, in this browser

Inga compiled to WebAssembly: a GGUF model runs in a browser tab, on the device’s CPU or on its GPU through WebGPU. Nothing to install, nothing sent anywhere: the model is downloaded to the browser’s private storage and runs there. Start with a small one (Qwen3.5 0.8B or Llama 3.2 1B), then browse about fifty models from Hugging Face, each marked by whether it fits your device.

One executable replaces…

Don’t install a thousand different products — just use Inga

Five parts in one file — engine, API server, web app, mesh, network of nodes — usable together or on their own.

  • An inference engine

    instead of llama.cpp, whisper.cpp, stable-diffusion.cpp

    Its own engine in Rust, every llama.cpp quantization, output checked against those projects.

    inga run

  • A model runner

    instead of Ollama, LM Studio

    Models from Hugging Face, or the ones Ollama and LM Studio already downloaded, loaded on demand.

    inga list --ollama

  • GPU builds

    instead of CUDA, ROCm, multi-GPU builds

    CUDA, Vulkan, Metal and ROCm / HIP in one file, with only the driver installed.

    --device cuda:0,vulkan:1

  • An API server

    instead of vLLM, llama-server, LocalAI

    The OpenAI, Anthropic, Ollama, LM Studio and KoboldAI APIs, streaming and tool calls, several models and users: their answers batched, a long prompt read beside them, a paged KV cache.

    inga serve --no-webui

  • A router or gateway

    instead of LiteLLM, llama-swap

    Other servers and 113 provider presets as API nodes, routes with fallback, keys with budgets.

    inga node add

  • A chat web app

    instead of Open WebUI

    Chat with a model hub and its model cards, the models’ speeds on this computer, web search, documents, a memory, an Images page (create, transform, touch up, extend, upscale, LoRAs) and a Videos page that load their model in the running server; each model offered the tools and attachments it can use; a Report button on every error.

    inga serve

  • Speech tools

    instead of faster-whisper, a TTS server

    Transcription streamed live, text to speech, a hands-free voice chat.

    inga transcribe --stream

  • An agent host

    instead of an MCP client, a scheduler

    MCP servers’ tools, Agent Skills and scheduled prompts; each chat asks for every tool call, only for changes, or runs the pre-approved ones.

    inga mcp

  • A quantizer

    instead of llama-quantize

    The same GGUF file, byte for byte.

    inga quantize

  • A LoRA trainer

    instead of Python, PyTorch

    LoRA fine-tuning of small models on the CPU, adapters for --lora.

    inga finetune

  • A cluster

    instead of one big machine

    One model over the PCs of a LAN: layers, experts or slices, found by mDNS, encrypted; nodes of older versions kept, each node’s log read from one page.

    inga satellite

Drop-in

Replace Ollama, LM Studio or llama-server

Switch the other server off, start Inga on its port: its clients do not change, and the models those apps downloaded run without a second copy.

Ollama

# the models Ollama downloaded, with whether Inga runs them
inga list --ollama
# stop Ollama, then serve on its port
systemctl stop ollama
inga serve ollama://llama3.2:3b --port 11434

Ollama’s /api/chat, /api/generate, /api/tags, /api/embed… and the OpenAI /v1 routes on the same port.

--like ollama (Ollama’s port beside Inga’s) and inga pull ollama://qwen3:0.6b, without Ollama installed.

LM Studio

# LM Studio's GGUF files and MLX folders
inga list --lmstudio
inga serve ~/.lmstudio/models/lmstudio-community/\
  Qwen3-4B-GGUF/Qwen3-4B-Q4_K_M.gguf --port 1234

LM Studio’s REST API (/api/v0/models, /api/v0/chat/completions) and the OpenAI routes. MLX weights are read as stored on the CPU and on a Mac’s GPU.

--like lmstudio: port 1234 beside Inga’s 8080.

llama-server

# the same GGUF file, the same default port
inga serve model.gguf
# OpenAI-compatible clients: http://127.0.0.1:8080/v1

Chat and text completions, embeddings, tool calls, JSON schemas and GBNF grammars, every common sampler, speculative decoding.

llama-server’s own /completion, /props and /slots.

Measured, not promised

Numbers, with their caveats

Every figure here is a row of docs/performance.md, with its date, the Inga version and the machine; the command is there.

2 GBof RAM

Qwen3-30B-A3B, a 17.28 GB file, answers in 2 GB of RAM

2026-10-15 · Inga of that day’s main (between 0.30.1 and 0.31.0) · Xeon W-2123, 32 GB, NVMe, Windows

The same 64 tokens as with all of it in RAM, under --mem-limit 8G, 4G and2G: 6.7, 2.5 and 1.7 tokens/s on the CPU. The experts are read from the SSD while it runs.

One run each. Those speeds were largely served by Windows’ file cache; past it (direct reads) 3.3 tokens/s at 8 GB and 0.8 at 4 GB.

42 / 42layers on a 4 GB card

Gemma 4 E4B on a Quadro P1000 (Vulkan)

2026-11-06 · Inga 0.45.0 (commit 156b3a8) · Quadro P1000, 4 GB

Every layer and the output layer on the card: a 128-token prompt at 48.72 ± 0.31 tokens/s, generation at 9.64 ± 0.02 tokens/s (IQ2_M, 3.30 GiB).

One run of the GPU workflow’s bench; llama.cpp was not run on it.

1.3–1.7×llama.cpp

Generation on the CPU, 1B-class models

2026-10-09/10 · Inga 0.21–0.22 · a 4-vCPU cloud Xeon (machine A’s earlier host)

Faster than llama.cpp on the same machine, files and commands, after a long prompt too.

Prompt processing is behind: 0.84–0.86× at 512 and 2048 tokens, about 0.5× against llama.cpp’s AMX path. On a Quadro P1000 workstation’s CPU (2026-10-16) 1.04–1.27×, but Llama-3.2-1B’s generation 0.86–0.95×.

1.62×llama.cpp

Qwen3-30B-A3B’s 2048-token prompt on an A100 (CUDA)

2026-10-24 · Inga ee60ddef (main’s code before 0.38.0) · one Colab A100

6356.7 tokens/s against llama.cpp b11489’s 3930.1, the mixture’s layers whole on the GPU; generation 0.90–1.03× on five Q4_K_M models.

Serving many users is far behind: about 255 tokens/s in all from 8 to 64 clients on Qwen3-8B, where llama-server reaches 756 and vLLM (4-bit AWQ) 4955 (Inga 3bbb5222, before 0.38.0’s bigger decode groups). With them, inga bench --users gives Qwen3-8B Q4_K_M 417 tokens/s at 16 users (+45 %) and 474 at 64 (+70 %); the server under load is not measured again yet.

1.12×llama.cpp

Qwen3.8-27B on an RX 9060 XT (Vulkan)

2026-10-14 · Inga 0.29.0 · a tester’s Radeon RX 9060 XT, 16 GB

8.9 tokens/s against llama.cpp’s 7.9, generating.

Prompt processing there is 0.39×: Vulkan prefill is the known weak spot.

Platforms, GPUs and models

The GPU by default, as many layers as fit, the rest on the CPU — and the reason printed when no GPU is used.

Systems

  • Windows x86-64
  • Linux x86-64, ARM64
  • macOS Apple Silicon, Intel (CPU)
  • Docker / Podman ghcr.io image
  • Browser WebAssembly, WebGPU

Back ends

  • CPUx86-64 SSE4.1, AVX2, AVX-512 · ARM64 NEON
  • CUDANVIDIA, Pascal or newer · llama.cpp’s generation kernels, flash attention, a mixture’s layers whole on the GPU and up to 64 users in one decode group, on by default from Ampere; a long conversation’s attention split across the GPU (4× faster after 4096 positions on an A100); the pictures of Stable Diffusion, Flux, SD 3 and Qwen-Image on the GPU (experimental)
