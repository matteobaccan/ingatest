    Beta. A first public test of Inga in the browser:
    pick a model, chat, run the Standard test (Tests and report), then press "Report on GitHub" there (what works
    and what does not: the beta's guide).
    
    
    An experiment: Inga compiled to WebAssembly, running on this device's CPU (WebAssembly
    SIMD; one thread, or every core when the page is cross-origin isolated), or with its layers on the GPU
    through WebGPU (Settings, Device: experimental). A model larger than the tab's memory runs with part of it
    read from this site's storage at every token. Nothing is sent anywhere: the model runs in this page. Tested in
    headless Chromium on Linux and in Safari on an iPhone 16 Pro.

        About fifty GGUF models on Hugging Face that Inga runs (Llama, Qwen,
        Gemma, Phi, Mistral, DeepSeek R1 distills…), each quantization marked by whether it fits this browser.

        Model loading
        
      
        
        Tokens the model keeps (the KV cache): the conversation, the question and the answer must fit. Applies at the next load.
        
      
        
        
        
        
        Everything the model keeps in memory: its weights, its KV cache for the context, its
        working buffers. What does not fit is read from this site's storage while it runs (the embeddings a row
        per token, the output layer and the last layers whole at every token): much slower, but a model larger
        than the tab's memory runs; one that cannot fit is refused. A longer context leaves less for the
        weights. Auto: 1600 MB on an iPhone or iPad, under the measured ceiling (Safari kept the tab at 1.75 GiB on an iPhone 16 Pro and
        ended it at 2000 MB; a phone with less memory may need less), 3584 MB elsewhere (under the 4 GiB a
        WebAssembly module can address: a model's part in memory is capped near 4 GB, so a larger model always
        reads from storage; WebAssembly Memory64, in Chrome but not yet in Safari, would lift that). Kept in this
        browser.
        
      
        
        
        
        
        
        CPU: WebAssembly SIMD on this device's cores. GPU (experimental): the layers through WebGPU, as
        many as fit "GPU memory", the rest on the CPU (read from this site's storage when the memory limit
        asks); a model whose layers or weight types the GPU does not run stays on the CPU, and the load line
        says why. Auto: the GPU only where it was measured faster than the CPU, and never for a model larger
        than "Memory for the model" (it would be read from storage, and the GPU's share leaves the CPU fewer
        weights); on the iPhone 16 Pro the GPU was not faster (Qwen3 0.6B: 16.3 tok/s on the GPU, 25 on the
        CPU), so Auto picks the CPU for now. In a browser without WebGPU (no navigator.gpu), GPU is not available.
        
      
        
        
        
        What the GPU may hold: its layers' weights and KV cache, its working buffers. Auto:
        1024 MB on an iPhone or iPad (Llama 3.2 1B, 0.9 GiB on the GPU, is the largest model measured to load
        there); 3072 MB elsewhere, a guess: WebGPU does not tell a GPU's memory, and 3 GiB fits a 4 GB card
        (set it in MB for yours).
        
      
        
        
        One limit: the GPU's bytes are counted in "Memory for the model" (added to WebAssembly memory), in case the system counts a tab's
        GPU buffers with its memory, as iOS may; then a model that needs storage keeps fewer weights on the CPU
        and runs slower on the GPU than on the CPU alone (Qwen3-4B on an iPhone 16 Pro: 0.9 against 2.3 tok/s).
        Apart: the limit covers WebAssembly memory only; "Memory for the model" bounds WebAssembly memory and "GPU memory" the GPU's bytes, as on a
        desktop, whose graphics memory is not the tab's. Auto: one limit on an iPhone or iPad (until the test in
        the guide's step 7 shows that iOS does not count GPU buffers), apart elsewhere. The load line says which
        was used.
        
      
        
        
        A smaller stored model with the same vocabulary (for Qwen3-4B, Qwen3-0.6B; for Llama
        3.2 3B, Llama 3.2 1B) guesses a few tokens, and the model checks them in one pass: a layer read from
        storage is read once for every token the pass accepts. It is held whole, out of the same memory
        limit, so the model keeps less in memory; it turns itself off while it does not make the answers
        faster. Kept in this browser.

        Report
        
      
        Opens GitHub's issue form for this beta with what the page knows filled in: this browser and
      its GPU adapter, the model and how it loaded, the speeds (the last answer, the Standard test, the GPU
      benchmark and kernel times if you ran them), the load log and the errors the page saw. Nothing is sent from
      here: you read it on GitHub, add what you did, and submit it (a GitHub account is needed).
